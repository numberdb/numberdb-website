API keys

A key raises your rate limit for reading, and is what writing needs. Reading without one works and is limited; writing without one does not.

{% if fresh_key %}
Your new key. This is the only time it will be shown. {{ fresh_key }}

The server keeps only a hash of it, so nobody can look it up later — not you and not us. If it is lost, revoke it below and take another.
Where to put it. Anywhere but the code you publish. In order of how much trouble each saves you:

A .env beside your script, which the package reads on its own:

NUMBERDB_API_KEY={{ fresh_key }}

Add .env to your .gitignore first. A key in a repository is a key in everyone’s clone, and revoking it is then the only fix.

Or your shell, for a key you use everywhere:

export NUMBERDB_API_KEY={{ fresh_key }}

Or once, for good, in the per-user file the package looks in when neither of the above is set — which keeps it out of every project directory you might publish:

mkdir -p ~/.config/numberdb
echo 'NUMBERDB_API_KEY={{ fresh_key }}' > ~/.config/numberdb/env
chmod 600 ~/.config/numberdb/env

What a key lets you do

Reading, past the anonymous rate limit — that is what any key does.

{% if may_write %} Writing, too: your edits have been reviewed and confirmed, so programs running under your key may change tables. {% else %} Writing needs more than a key. A key says who you are; it does not say your account may write with a program. That needs {{ trusted_after }} edits of yours to have been reviewed and confirmed by somebody, and {% if accepted_edits %}{{ accepted_edits }} of yours {% if accepted_edits == 1 %}has{% else %}have{% endif %} been so far. {% else %}none of yours has been so far.{% endif %} A person editing one table exercises judgement about it; a script does not, and it writes faster than anyone can read. Saying so here saves finding out from a refusal at the end of a long computation. {% endif %}

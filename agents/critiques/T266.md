# T266 critique: Krawtchouk polynomials $\mathcal{K}_k(x)$ of the Hamming scheme

Read 2026-09-16. T266 is a private draft. The SOCKS proxy on 127.0.0.1:1080
refused every connection, but numberdb.org answered `curl` directly. `/T266`
answers 404, as a draft should. I read the document through
`GET /api/table?id=T266` with the key. I rendered it through `/preview?table=`
in four pieces, all 200. Between them the pieces carry every section, six
small rows and the largest entry. The table holds 608 entries of type `Q[]`
with rigour `exact`: $q=2,3,4,5$, every $1\leq N\leq16$ and every
$0\leq k\leq N$. The entries block is 65 KB, and the largest entry,
$\mathcal{K}_{16}(x;16,5)$, is 545 characters.

`GET /api/table/T266/audit` reports `{"findings": [], "clean": true}`. I
disagree on one point. Finding 1 below breaks a whole section of the page,
and the audit does not look at the shape of a Formulas entry, so it cannot
see it.

**Apart from the findings, the table reads well.** Here is what I checked
hardest:

* *The mathematics typesets.* I ran all 29 `$...$` fragments in the prose
  through MathJax 3 in node, and none failed; a control with an unclosed
  brace did fail. No fragment contains a bare `<`. Every `CITE` resolves:
  [1] MacWilliams–Sloane, [2] Wikipedia, [3] DLMF.
* *It is one table, and the columns say so.* $q$, $N$ and $k$ are arguments
  of one polynomial, not names. The value column is headed
  $\mathcal{K}_k(x;N,q)$, which is true of every row, and the parameter
  columns read `2`, `16`, `8`, not a label. Parameters describe the family
  ($N\geq1$, $0\leq k\leq N$). The range that was computed is in
  `complete-note`, which finishes its "no (...)" sentence properly.
* *The program works.* I ran the Sage snippet exactly as stored, with
  `agents/sage.sh`, against 100 stored rows ($N=1,5,16$, every $q$ and $k$).
  All 100 match, it gives the same result with Sage integers as arguments,
  and a deliberately wrong row fails the comparison. I also checked by hand
  that the stated relation to DLMF's $K_k(x;p,N)$ holds at $N=1$ for
  $q=2,3$.

The findings are ranked. 1 must be done: the section is unreadable as it
stands. 2 and 3 are worth doing and cost a line each. 4 is worth doing. 5 and
the notes are things I noticed, not faults I would hold the table for.

## 1. The Formulas section prints two Python dictionaries (must fix)

**What a reader sees.** Under "Formulas":

> (1) {'name': 'Generating function', 'formula': '$\\sum_{k=0}^{N}\\mathcal{K}_k(x;N,q)z^k=(1+(q-1)z)^{N-x}(1-z)^x$.'}
>
> (2) {'name': 'Orthogonality', 'formula': '$\\sum_{x=0}^{N}\\binom{N}{x}(q-1)^x\\mathcal{K}_k(x;N,q)\\mathcal{K}_l(x;N,q)=\\delta_{kl}q^N\\binom{N}{k}(q-1)^k$.'}

That is the Python repr, braces, quotes and doubled backslashes included.
Because the backslashes are doubled, MathJax gets `\\sum`, which is a line
break followed by `sum`, so a reader gets neither the name nor the formula.

**Why.** Each Formulas entry is stored as a record `{name: ..., formula: ...}`.
The page (`table_context` in `numberdb_app/views.py`, shared by the page and
the preview) calls `render_text(text)` on each value of Formulas and
Comments. That expects a string, and a dict turns into its repr. Every
other table in the corpus stores a Formulas entry as a plain string (T105,
T151, T249, T250, T263).

**Smallest fix.** Store the two formulas as strings. Use the corpus's
`formula-` keys while they are being rewritten:

```yaml
Formulas:
  formula-generating-function: $\sum_{k=0}^{N}\mathcal{K}_k(x;N,q)z^k=(1+(q-1)z)^{N-x}(1-z)^x$.
  formula-orthogonality: $\sum_{x=0}^{N}\binom{N}{x}(q-1)^x\mathcal{K}_k(x;N,q)\mathcal{K}_l(x;N,q)=\delta_{kl}q^N\binom{N}{k}(q-1)^k$.
```

The names "Generating function" and "Orthogonality" add nothing that the
formulas do not already say. If they are wanted, write them into the
sentence, e.g. "The generating function is $\ldots$". Nothing `CITE`s either
key, so renaming them breaks nothing.

## 2. The program is labelled "Python", and it needs Sage (worth doing)

**What a reader sees.** "(P1) Python", then a code block that begins
`from sage.arith.misc import binomial`. A reader who pastes it into Python
gets `ModuleNotFoundError`.

**Why.** The page prints `language` and ignores `name`, so `name: SageMath`
never appears. Every other table here writes `language: Sage` under the key
`program-sage`. That value is also the one the page highlights as Python
code; `Python` gets no highlighting at all.

**Smallest fix.** `Programs: {program-sage: {language: Sage, code: ...}}`,
with the same code, and drop `name`.

## 3. Similar tables misses the Gegenbauer polynomials, and its one relation is hard to read (worth doing)

**What a reader sees.**

> Kissing numbers $\tau_n$ — Delsarte linear-programming bounds use
> Krawtchouk polynomials in the Hamming-space analogue of the spherical-code
> bounds cited there

The sentence has no article before "Delsarte", and a reader has to work
out what "cited there" points back to. Its point is that T151's $\tau_8=240$
and $\tau_{24}=196560$ come from Delsarte's bound. On the sphere, though,
that bound is built from Gegenbauer polynomials, and the corpus holds them
as HREF{Gegenbauer_polynomials} (T105). They are the direct analogue of this
table, since both are the zonal polynomials of a distance-regular space in
which the linear programming bound is taken. The table does not name them.

**Smallest fix.** Add T105 and rewrite the T151 relation so that it names
things:

```yaml
Similar tables:
- table: HREF{Gegenbauer_polynomials}[Gegenbauer polynomials]
  relation: they play the same part on the sphere that $\mathcal{K}_k$ plays in Hamming space, as the polynomials of Delsarte's linear programming bound
- table: HREF{Kissing_numbers}[Kissing numbers $\tau_n$]
  relation: $\tau_8=240$ and $\tau_{24}=196560$ were proved with Delsarte's linear programming bound, whose Hamming-space form is taken in these polynomials
```

(The spherical form of the bound uses Gegenbauer polynomials with
$\alpha=(n-2)/2$. I have not checked what T105's own parameter range covers,
so the relation does not claim a particular row.)

## 4. The definition's last clause does not say what it means (worth doing)

**What a reader sees.** "…, where $x$ is the Hamming weight on
$\{0,1,\ldots,N\}$ extended to a polynomial variable [2]."

A weight is not "on" a set. It takes values in one. "Extended to a polynomial
variable" leaves the reader to guess how $\binom{x}{j}$ is read when $x$ is
not an integer, and that is exactly the step that makes the entries
polynomials with rational coefficients, not integer sequences.

**Smallest fix.** "…, where $\binom{x}{j}=x(x-1)\cdots(x-j+1)/j!$, so that
$\mathcal{K}_k$ is a polynomial of degree $k$ in $x$. At $x=0,1,\ldots,N$
its values are those at the Hamming weights CITE{Wiki}." This also matches
`rigour details`, which says the polynomials were computed "from the
falling-factorial definition", a phrase the page as written never explains.

## 5. "$q$ is a prime power" narrows the family (noting)

The formula, the generating function, the orthogonality relation and the
Hamming scheme $H(N,q)$ are all defined for any alphabet size $q\geq2$. The
prime power matters only for the linear-code form of the MacWilliams
identity. The four stored values of $q$ happen to be prime powers, so the
constraint is true of the entries. But it tells whoever extends the table
that $q=6$ is outside the family, when it is not. If the restriction is
deliberate, the normalisation comment is the place to say why. Otherwise
the constraint should read `$q\geq 2$`. I have not checked the MacWilliams
and Sloane chapter to see how they state it.

## Noticed only

* The `scheme` comment says "the eigenvalue of the $k$-th relation on the
  $i$-th eigenspace". A relation is not an operator; the eigenvalue is that of
  the distance-$k$ adjacency matrix. A reader from association schemes will
  read it correctly anyway.
* The comment keys `normalisation` and `scheme` do not use the corpus's
  `comment-` prefix. Formulas, Comments, References and Links share one label
  namespace on the page, so the prefix guards against a collision. There is
  none today.
* The conversion $\mathcal{K}_k(x;N,q)=\binom{N}{k}(q-1)^kK_k(x;1-1/q,N)$ sits
  inside the `normalisation` comment. It is a convention statement, which is
  what a comment holds, and I would leave it. It could move to Formulas if
  the comment is being edited anyway.

# T263 critique: Hall polynomials $g^\lambda_{\mu\nu}(q)$

Read 2026-09-16. T263 is a private draft. I could not use the SOCKS proxy on
127.0.0.1:1080, which refused connections for the whole run, but numberdb.org
answered `curl` directly. `/T263` answers 404 even with the key. I read the
document through `GET /api/table?id=T263` with the key. I rendered it through
`/preview?table=` in five pieces, each under the 4 KB request-line limit, and
each piece held a sample of rows. The table holds 1197 entries of type `Z[]`
with rigour `exact`: every nonzero $g^\lambda_{\mu\nu}(q)$ with
$|\lambda|\leq8$ and $\mu,\nu$ both nonempty. The largest entry is 128
characters.

`GET /api/table/T263/audit` reports `{"findings": [], "clean": true}`. I
agree that none of its rules applies. Finding 1 is not something any rule
looks at. Finding 2 is not something the audit can see, because it would have
to run the snippet. Finding 4 is small.

**The prose and the mathematics are in good order.** Here is what I checked
hardest:

* *The page renders.* Every `$...$` in the Definition, Parameters, Comments,
  Formulas, `complete-note` and `rigour details` comes through intact,
  including `\varnothing`, `|\lambda|` and `\sum_i(i-1)\lambda_i`. The prose
  has no bare `<`. Every `CITE{formula-*}` resolves to a numbered formula, and
  the parameter list reads "$\lambda$ — ambient type (a partition of a
  positive integer)". The long `rigour details` folds after its first
  sentence. The value column is headed $g^\lambda_{\mu\nu}(q)$, which is true
  of every row.
* *The definition defines, and in the usual convention.* A reader is told
  which lower index is the quotient and which is the submodule. That is the
  one point on which sources differ, and it matches Macdonald and Wikipedia's
  "Hall algebra" article, which gives $\nu$ for the subgroup and $\mu$ for
  the quotient. I checked a few rows by counting subgroups by hand: $q+1$ for
  $((1,1);(1),(1))$, $q$ for $((2,1);(2),(1))$, $q^2+q$ for $((2,2);(2),(2))$,
  and the Gaussian binomial $q^4+q^3+2q^2+q+1$ for $((1^4);(1,1),(1,1))$.
* *It is one table.* The three parameters are arguments of one function, not
  names, and the header shows it.

The findings are ranked. 1 and 2 are worth doing, and 1 must be done before
publication because the keys freeze then. 3 is a question for whoever
reviews. 4 and 5 are small but worth doing. 6 is only a note.

---

## 1. 133 entry addresses belong to more than one row

**What a reader sees.** In the $\lambda=(3,1)$ block the row $\mu=(2)$,
$\nu=(1,1)$ holds `1` and the row $\mu=(2,1)$, $\nu=(1)$ also holds `1`. The
rendered page gives both of them `id="3,1,2,1,1"`. An entry's address is its
parameter values joined by commas, and a partition here is itself written with
commas, so the address cannot say where $\mu$ ends and $\nu$ begins. Of the
1197 entries, 133 addresses are shared by two or three rows. For example,
`2,1,1,1,1,1,1` is $((2,1,1);(1);(1,1,1))$, $((2,1,1);(1,1);(1,1))$ and
$((2,1,1);(1,1,1);(1))$. Sometimes the rows sharing an address hold different
polynomials: `2,1,1,1,1,1,1` is `1`, `q + 1` and `1`. A link or citation to
the middle one scrolls to the first.

**Why it is wrong.** The skill promises that a value has a permanent address
("A link may name an entry ... the address after the `#` is the entry's
identity"). Here the address resolves and names the wrong row. It does not
fail. It lies, which the comment on `_entry_address` in `views.py` calls the
worst way to fail. The named form (`lambda=2,1,1,mu=1,1,nu=1,1`) was designed
to avoid exactly that, but it does not help here: the parser splits on commas,
finds `1` with no `=`, and treats the whole string as positional, so it finds
nothing. $\lambda$ can always be recovered, because its size is half the
total, but the split between $\mu$ and $\nu$ cannot. T259 uses the same
notation and escapes only because it has two partitions of equal size.

**The smallest change.** While the table is still a draft, write each
partition in parentheses in the keys: `(2,1)`, `(1)`, `(1,1)`. The identity
`(2,1),(1),(1,1)` is then unambiguous, and the rows also read better, since
`(2, 1, 1)   (1, 1)   (2):` is easier to scan than `2, 1, 1   1, 1   2:`.
The `notation` comment then only needs to say that parts are listed largest
first. It is a generator change in `_format_partition` and
`_parse_partition` and a refill. If the house style for partitions is to
match T259 and T261, which are also drafts, they could change with it, though
neither of them has a collision. The named-citation parser splitting inside a
value is a site bug. I have described it in the lesson proposal and not here.

## 2. The `Programs` snippet raises an error under the imports it uses

**What a reader sees.** The snippet uses named imports, as the skill asks,
and ends `q * Q(coefficient(t=1 / q))`. I ran it through `agents/sage.sh`
after `import numberdb.sage`, and it stops in the multiplication
`P([2]) * P([1])` with

    AttributeError: module 'sage.rings.polynomial' has no attribute 'laurent_polynomial_ring'

With `import sage.rings.polynomial.laurent_polynomial_ring` added, it prints
`q`, which is the stored `2,1 / 2 / 1` row. Under `from sage.all import *` it
also prints `q`. So a reader in an interactive Sage session is fine, but a
reader who pastes it into a file for `sage -python` or passagemath gets a
traceback.

**Why it is wrong.** The generator knew this. Lines 23–25 of
`generators/hall-polynomials/generate.py` import that module "because Sage's
Hall-Littlewood multiplication reaches this module lazily". The fix did not
reach the snippet the page prints, which is the only code most readers see.

**The smallest change.** Add the same import line, with its one-line comment,
after the other imports in `Programs.program-sage.code`.

## 3. Half the rows are $1$ or $q^k$, and the range was set by the entry limit

**What a reader sees.** 555 of the 1197 values are `1` or a power of `q`, and
another 61 are `q + 1`. There are 100 distinct polynomials in the table. A
reader who searches for $q^2+q+1$ gets 40 rows of this table. `complete-note`
justifies $|\lambda|\leq8$ by saying that size 9 "would make $2527$ stored
non-edge entries, past the soft entry limit of $1200$". The table then sits 3
entries under that limit.

**Why it might be wrong.** The skill says to hold the numbers that turn up and
to let the family, not the count, choose the range. It names a bound set by
the entry count as counting rather than choosing, and warns that values
matching everything make search by number worse. Nobody arrives holding
$q^3$ and wants to learn it is $g^{(3,2,1)}_{(2),(3,1)}$.

**Why it might be fine.** This table is also, and perhaps mainly, looked up
by index. Somebody wants $g^{(3,2,1)}_{(2,1),(2,1)}$, and a table that leaves
out the monomial rows would make them wonder whether the value is zero. T259
(Kostka–Foulkes) made the same choice with the same justification. I would not
split or thin the table. I would change one sentence: have `complete-note`
give a reason drawn from the family, if there is one, such as "all partitions
up to size 8, where the rows are still short enough to read". Also drop the
coined "non-edge", which "$|\mu|,|\nu|>0$" already says. This is a question
for the reviewer, not a fault.

## 4. The Hall reference is listed and never cited

`References.Hall` (P. Hall, *The algebra of partitions*, 1957) appears as [2]
under References, and nothing in the table points at it. The skill says "a
reference is for citing, not for listing". The natural place for it is the
Definition, since the polynomiality of the count is Hall's theorem: "...is the
polynomial CITE{Hall} whose value at...". Alternatively, remove it.

## 5. The Formulas name the Hall–Littlewood basis without linking T261

`formula-hall-littlewood` says "Macdonald's Hall-Littlewood $P$ basis". That
is the first mention of the family in that section, and the corpus holds it as
T261. The audit's link rule matches titles, and this phrase is not T261's
title, so it did not flag it. The fix is `HREF{T261}[Hall-Littlewood $P$
basis]` in that sentence, or the slug once T261 has one. A similar small
point: the second `Similar tables` relation says "the *same* Hall-Littlewood
$P$ basis", which points back at the row above it. "the Hall–Littlewood $P$
basis" says the same thing without pointing.

## 6. Noted only

* The second sentence of `Comments.convention`, which says that the edge cases
  are not stored and are given by the formula, repeats `complete-note` almost
  word for word. The Comments would lose nothing without it.
* `Similar tables` links by tid (`HREF{T261}`). That renders as `/T261` and
  works, but it is not the slug form the skill asks for. Both targets are
  drafts, so no slug can be read off a search yet.
* The Definition says "a finite module of type $\lambda$" without saying what
  a type is: $M\cong\bigoplus_i \mathfrak o/\mathfrak p^{\lambda_i}$. An expert
  knows it and the Wikipedia link explains it. Half a clause would make the
  Definition self-contained, but I would not insist.

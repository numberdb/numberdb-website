# T383, Discriminants of the trinomials $x^n+ax^m+b$

A critique. Nothing here was changed; somebody decides.

666 rows: the discriminant of $x^n+ax^m+b$ as an element of $\mathbb Z[a,b]$,
for every $2\leq n\leq37$ and $1\leq m<n$. It is a good table. The definition
defines and stops, both parameters describe the family rather than the run, the
value column is headed with a quantity that is true of every row, the page
renders without a mark out of place, and the 666 values verify against the
attached generator and against Sage on the pairs I checked by hand.

The one real fault is not in the document at all. It is in the file a reader
downloads from the table: the attached `generate.py` is an older revision than
the one in this repository, and it crashes on the command its own header tells
a reader to run. Everything else is small, and most of it is prose that says
the same thing twice.

## The audit

Clean, and I agree with it. Both `HREF{}` targets exist, every `CITE{}`
resolves (the four to formula labels render `(1)`, `(3)` and `(4)` in the
Definition and the rigour note; the three to `Links` and `References` render
`[1]` to `[3]`), both tags reach other tables, the generator is attached, the
value column is headed `$\operatorname{disc}(f_{n,m})$` and not the word
`value`, and the one-table checks have nothing to say because both parameters
are numbers rather than names.

The audit cannot see the finding below it: it reads the *document*, and the
attachment is a separate object that it only checks for a run command in the
first forty lines.

## Findings

### 1. The attached `generate.py` crashes on the command it tells a reader to run

Worth doing, and the only one I would call urgent.

`/files/T383/generate.py` is an earlier revision than
`generators/trinomial-discriminants/generate.py`. The two differ in exactly one
hunk, `stored_values()`: the attached copy reads `Numbers` as a flat mapping
keyed `"n,m"`, and the API returns it nested, `{n: {m: value}}`. So the file a
reader downloads does this:

    $ sage -python generate.py            # the command in its own header
    integrity checks passed for 666 trinomial discriminants
    resultant checks passed for n<=12
    longest polynomial has 1267 characters at n=36, m=18
    <VerifyReport T383: 666/666 matched, 0 differing, 0 missing, 0 extra>
    Traceback (most recent call last):
      ...
      File "/work/T383-generate.py", line 239, in stored_values
        n_text, m_text = str(key).split(",", 1)
    ValueError: not enough values to unpack (expected 2, got 1)

The repository's copy, run the same way in the same container, finishes:

    ...
    <VerifyReport T383: 666/666 matched, 0 differing, 0 missing, 0 extra>
    stored values match the independently checked generator

What a reader sees is a program that reports the table correct and then falls
over on its own last check, which reads as "this table's generator is broken"
and is a worse first impression than a missing attachment would be.

Smallest fix: re-attach the current file. Nothing in the document changes.

Why it happened is worth writing down beside the fix: the attachment is a
snapshot taken when the values were last filled, so a later edit to the file on
disk does not reach readers, and nothing in the table's own page shows that the
two have diverged.

There is a second copy of that file in this repository, at
`generators/trinomial-discriminants/generate.py`, committed on this branch as
`45fb306`. `generators/` is in `.gitignore`, and the reason given there is this
exact failure: "The table on the site holds the generator that made its
numbers, attached to the revision that wrote them and downloadable from the
page ... A second copy in git competed with that and lost three times in one
day." This is the fourth time, with the sides swapped — here the git copy is
the good one and the reader's copy is stale. Whichever way round, the fix is to
make the attachment current, and the working copy is working material.

### 2. The specialization is stated twice, and the second time in another table's letters

Worth doing.

Comment (6): "This is the specialization of *the discriminant of the general
degree-$n$ polynomial* obtained by setting the leading coefficient to $1$, the
coefficient of $x^m$ to $a$, the constant term to $b$, and all other
coefficients to $0$."

Similar tables, T381: "gives the same discriminant before the specialization
$a_n=1$, $a_m=a$, $a_0=b$, and all other coefficients $0$."

Those are one sentence twice, clause for clause, a screen apart. The second
copy is also written in T381's variables: $a_n$, $a_m$ and $a_0$ appear nowhere
else on this page, and $a_m=a$ asks a reader to hold two meanings of the letter
$a$ at once, one of which this table never introduces.

`Similar tables` is where the relation belongs; the skill is explicit that the
sentence naming the relation is the valuable part of that section. So: delete
comment (6), and let the T381 row carry the relation in this table's own words,
the comment's wording being the better of the two.

That leaves the T382 row, which is fine as it stands and says something the
T381 row does not: it restricts to $m\leq n-2$, which is exactly where a
trinomial is depressed.

### 3. Comment (5) restates the definition's own formula

Worth doing.

"The coefficient $a$ multiplies $x^m$ and $b$ is the constant term. The leading
coefficient is $1$, and all other coefficients are $0$."

The definition two lines above writes $f_{n,m}(x)=x^n+a x^m+b$. The comment
reads that expression back out in words, and there is nothing in it a reader
could not have got from the formula. In T381 and T382 the corresponding comment
earns its place, because there the entries are written in $a_0,\dots,a_n$ and
somebody has to say which subscript goes with which power. Here the convention
is visible in the definition, in the title, and in every row.

Smallest fix: delete it. Comment (6) then goes too (finding 2), which empties
the `Comments` section, and a table with no comments is a table whose
definition did its work.

### 4. The `Programs` block opens by importing a package it never uses

Worth doing.

    import numberdb.sage as numberdb
    from math import gcd
    ...

`numberdb` is not referenced again. The block is offered to a reader who wants
one more value, and that reader may well not have the client installed, so the
one line of the snippet that can fail is the one line that does nothing. Delete
it; the rest runs on any SageMath.

What the block computes is Swan's formula, which is Formula (2) written out in
code rather than an independent route to the same number, and that *is* the
right choice here. I measured the alternative. In the Sage container, over
$\mathbb Z[a,b]$:

* `(x^8 + a*x^3 + b).discriminant()` takes **27 seconds** and agrees with the
  stored value;
* the same call at $(n,m)=(9,6)$ did not finish in 900 MB, and neither did the
  resultant of Formula (1) at the same pair in eight minutes;
* Swan's closed form fills all 666 rows in under a second.

So a `Programs` block written as the library one-liner would be a block that
hangs for most of this table's range. Worth knowing, and not worth saying on
the page.

Two smaller things in the same block, noted only: the trailing bare `disc`
displays in a Sage REPL and prints nothing under `sage -python`, where
`print(disc)` would do both; and `n = 8`, `m = 3` is a good choice of example,
since $\gcd(8,3)=1$ hides nothing but also shows nothing of the $d$-th power in
Formula (2) — $(n,m)=(8,4)$ or $(6,3)$ would exercise it.

### 5. The two rows a reader is likeliest to arrive holding are not in `Keywords`

Worth doing, one line.

This table holds $a^2-4b$ and $-4a^3-27b^2$, and thinks them notable enough to
state as Formulas (3) and (4). Its `Keywords` are "trinomial discriminant",
"discriminant of a trinomial", "Swan trinomial discriminant", "polynomial
discriminant" and "discriminant in coefficients". Both T381 and T382 carry
"quadratic discriminant" and "cubic discriminant"; this one does not. Somebody
typing "cubic discriminant" is answered by the two tables that hold the cubic
discriminant among five or six coefficient variables, and not by the table
whose row $(3,1)$ *is* $-4a^3-27b^2$.

`Keywords` carry title weight, so adding "quadratic discriminant" and "cubic
discriminant" costs one line and puts this table in the answer.

"Swan trinomial discriminant" I would drop while there: it is not a phrase
anybody types, and "Swan" is already reachable through the reference. Noting
only.

### 6. The completeness note explains where it stopped, not who the rows are for

Worth doing, and it is one clause.

"it holds every pair $n>m\geq1$ with $n\leq37$, a complete initial triangle of
degree pairs; the first omitted half-degree row, at $(n,m)=(38,19)$, is already
1412 characters when expanded"

Two things a reader has to supply for themselves. "Half-degree row" means the
row with $m=n/2$, and the reason that one is quoted is that $\gcd(n,m)$ is
largest there, so those rows are the long ones; nothing on the page says so.
"When expanded" contrasts the stored form with Swan's factored form, which a
reader has no reason to think is the alternative. And the sentence stops at
1412 characters without saying what is wrong with 1412 characters; T382's note
finishes the same thought, "too long to read on a page".

The deeper version of the same point: the note argues from length, and the
question the skill asks a range to answer is whether anybody arrives holding
one of these numbers. For the small $n$ that is obvious and for $n=37$ it is
not, and one clause would settle it — the triangle is complete up to a degree
where the rows stop being readable, so a reader who has a trinomial of degree
at most 37 finds it here whatever its middle exponent.

I am not asking for the range to change. 666 entries is inside the recommended
1000, the whole block is 92 KB of text against a 320 KB soft limit, and the
longest row, $(36,18)$ at 1267 characters, falls inside the band the skill
draws for a polynomial entry a person still reads: a little above $F_{100}$ at
1107 characters, well below the $F_{150}$ at 2248 that was cut. It is a wall of
nineteen terms with forty-eight-digit coefficients, and it is the only kind of
row in the table that is; where $\gcd(n,m)=1$, which is most rows, the entry
has two terms.

### 7. The column header names an $f_{n,m}$ that is defined below the 666 rows

Worth doing if somebody is editing the document anyway.

The page prints the values first. So the first mathematics a reader meets is
the column header $\operatorname{disc}(f_{n,m})$, and $f_{n,m}$ is introduced
in the Definition, which on this table is four screens of polynomials further
down. `$\operatorname{disc}(x^n+ax^m+b)$` is three characters longer, is true
of every row in the same way, and answers the reader who arrived holding
`-4*a^3 - 27*b^2` without making them scroll. The title says the same thing
just above it, which is an argument both ways.

### 8. The Swan reference prints its URL as its own link text

Worth doing, one line.

    Richard G. Swan, Factorization of polynomials over finite fields, Pacific
    Journal of Mathematics 12 (1962), no. 3, 1099-1106.
    https://msp.org/pjm/1962/12-3/pjm-v12-n3-p27-p.pdf

A `url` with no `title` beside it is rendered with the URL as the caption
(`views.py`, the `References` branch), so fifty characters of msp.org path sit
in the bibliography. The section understands `doi`, which renders as a short
"(doi)". `doi: 10.2140/pjm.1962.12.1099` is the right one: it answers 302 to
`msp.org/pjm/1962/12-3/p27.xhtml`, the landing page of exactly the PDF cited,
which also confirms the volume, issue and page range the `bib` states.

## For whoever publishes it

Not a fault in the table. T383 points at T381 twice and at T382 once, and both
are unpublished drafts today. The audit's check on that fires only once *this*
table is published, so publishing T383 alone would hand every reader three
links that answer 404. The three should go public together, or T383 after the
other two.

Also worth knowing at that moment: the relation only runs one way. T382 points
at T381, T383 points at both, and T381 points at nothing. A reader landing on
the general-polynomial table has no way to reach the two tables that specialize
it.

## What I checked hardest and found nothing wrong

**The rendering.** The whole page, rebuilt, 405,745 bytes, and every section
read. No `argument ()`, no `Math input error`, no `<` eating a sentence: the
one place a literal `<` appears, the parameter constraint `$1\leq m<n$`, is
escaped to `&lt;` and typesets. The 44 TeX fragments all convert under MathJax
while a deliberately broken control fails. `CITE{}` to a formula resolves in
the Definition and in the folded rigour note alike. There is no `param-latex`
anywhere, which is right: both parameters take numbers, and the column prints
`2` and `18`, not a restatement of the header.

**Whether it is one table.** It is. Both parameters are arguments of one
quantity, not names of several, and the value column carries a real symbol
rather than the word `value`. The split from its two siblings is right in the
direction the skill tests for: $a_n=1$, $a_m=a$, $a_0=b$ is a specialization
and not a change of convention, and it is not invertible — T381 cannot be
recovered from T383. Three tables, each findable by its own name.

**The values.** Not my job and checked anyway, cheaply: the repository's
generator reports 666/666 matched with its own integrity checks passing, and
independently of it I recomputed $(2,1)$, $(3,2)$, $(4,2)$, $(6,3)$, $(7,5)$
and $(8,4)$ from the resultant identity of Formula (1) and $(4,2)$ and $(8,3)$
from Sage's `discriminant()`. All agree. The convention is pinned twice over:
the definition names Formula (1), and Formula (1) names the normalisation of
the resultant it uses, which is the thing that could have gone silently wrong.

**Findability.** The values are polynomials in two variables, and the search
key is canonicalised under renaming of variables with a ceiling of six
(`utils/numbers/polynomial.py`), so a reader holding `x^2 - 4*y` will match
`a^2 - 4*b` once the table is public and reviewed. I could not confirm that end
to end, because a draft answers no search: `/api/lookup?polynomial=a^2-4*b`
returns nothing today, while the same endpoint finds a published univariate
value.

Three of the findings below are outside anything that rule set can see. The

So the numbers are not the problem. Everything below is about what the page

## Findings

### 1. Comment (6) states the opposite of what DLMF does

The page prints:

> **(6)** DLMF writes the Ferrers function $\mathsf{P}_\ell^m$ without the
> Condon-Shortley phase, so values read from DLMF 14.7 have the sign
> convention used here rather than the sign convention of *the associated
> Legendre table* [2].

DLMF 14.6.1 is

$$\mathsf{P}^{m}_{\nu}(x)=(-1)^{m}(1-x^{2})^{m/2}\frac{\mathrm{d}^{m}\mathsf{P}_{\nu}(x)}{\mathrm{d}x^{m}},$$

which is the Condon-Shortley phase, and is character for character T360's
`formula-definition`. DLMF 14.7.10 repeats it as
$\mathsf{P}^m_n(x)=(-1)^{m+n}(1-x^2)^{m/2}(2^nn!)^{-1}\mathrm{d}^{m+n}(1-x^2)^n/\mathrm{d}x^{m+n}$,
whose sign at $n=m=1$ is $-(1-x^2)^{1/2}$ — and T360 stores $P_1^1=-y$. So
DLMF's Ferrers function agrees with T360 and *not* with this table, which is
the reverse of what the sentence says. A reader who trusts it and reads
DLMF 14.30.2, $Y_l^m(\theta,\phi)=\cos(m\phi)\mathsf{P}^m_l(\cos\theta)$, gets
$(-1)^m$ times the angular part stored here, and will conclude that every odd
$m$ row of this table has the wrong sign.

The citation is off by the same amount. The sentence sends the reader to
DLMF 14.7; the `[2]` at its end is declared in `Links` as "DLMF 14.30:
Spherical and spheroidal harmonics" and lands on <https://dlmf.nist.gov/14.30>.
Two different sections in one sentence, one of them silently.

Smallest fix: turn the claim round and let it cite the section it is about.

> The Ferrers function $\mathsf{P}_\ell^m$ of DLMF 14.6.1 carries the
> Condon-Shortley phase, as `HREF{T360}` does, so the real harmonics
> $\cos(m\varphi)\mathsf{P}^m_\ell(\cos\theta)$ of DLMF 14.30.2 are
> $(-1)^m$ times the angular parts used here CITE{DLMF}.

Deleting comment (6) outright would also be an improvement on what is there
now; comment (5) already says what the table's phase convention is.

**Worth doing.** This is the only sentence on the page that is false, and it
is false about a sign.

### 2. The `Programs` block computes something this table does not hold

Rendered, `(P1)` is nine lines of Sage that build the Legendre polynomials by
Bonnet's recurrence and end:

```
P[17]                         # the last Legendre polynomial used here
```

That is $P_{17}(u)$, a univariate polynomial in one variable. It is not an
entry of this table, and no line of the snippet turns it into one. The skill
is explicit about what this section is for: "`Programs` is the standard
incantation in Sage, PARI or mpmath for a reader who wants one more value." A
reader who wants $R_{18,3}$ is handed an intermediate and left to work out the
homogenisation, the $r^{\ell-m}$ power, the $(-1)^m$ and the
$\mathrm{Re}(x+iy)^m$ for themselves — which is precisely the part where the
conventions this table had to choose all live.

The attached `generate.py` does all of it correctly and carries its run
commands, so the material exists; it is four or five lines.

Smallest fix: extend the snippet to return one row, for instance

```python
R = PolynomialRing(QQ, ('x','y','z')); x, y, z = R.gens()
r2 = x**2 + y**2 + z**2
def solid(l, m):
    d = P[l].derivative(u, abs(m))
    ang = ((x + I*y)**abs(m)).real() if m >= 0 else ((x + I*y)**abs(m)).imag()
    return sum(QQ(c) * r2**((l - abs(m) - j)//2) * z**j for j, c in d.dict().items()) * ang
solid(18, 3)                  # one row beyond the table
```

(written however the author prefers; the point is that the last line is a row).

**Worth doing.**

### 3. The normalisation differs from the only source the Definition cites, and the anchor given is the one row where they agree

The Definition sends a reader to `[1]`, Wikipedia's *Solid harmonics*, for what
the object is. That article's real regular solid harmonics are

$$C^m_\ell=\left[\tfrac{(2-\delta_{m0})(\ell-m)!}{(\ell+m)!}\right]^{1/2}\Pi^m_\ell(z)A_m(x,y),$$

Racah's normalisation. This table stores $\Pi^m_\ell(z)A_m(x,y)$ — I verified
that on all 324 entries — so from $\ell=2$ upward the two differ by a factor
the reader has to discover:

| row | this table | Wikipedia's $C^m_\ell$ |
|---|---|---|
| $\ell=1,m=1$ | $x$ | $x$ |
| $\ell=2,m=1$ | $3xz$ | $\sqrt3\,xz$ |
| $\ell=2,m=2$ | $3x^2-3y^2$ | $\tfrac12\sqrt3\,(x^2-y^2)$ |
| $\ell=5,m=3$ | — | $0.00996\times$ this table's |

Comment (4) is the place this is supposed to be settled, and it says:

> This table uses the unnormalised real convention with $R_{1,1}=x$,
> $R_{1,-1}=y$ and $R_{1,0}=z$.

Those three rows are exactly the ones where the two conventions coincide: the
normalising factor at $\ell=1$ is $1$. The anchor offered as the discriminator
does not discriminate. What does pin the table down is formula (1), two
sections earlier — so the table is reproducible, and a reader who works from
(1) is fine. A reader who follows the link the Definition gives them is not.

There is also a good reason for the choice that the table never states, and it
is the sentence a reader most wants: Racah's normalisation has irrational
coefficients, so it is not in $\mathbb{Q}[x,y,z]$ and could not be stored as
this table's `type` at all. Saying so turns a bare convention announcement
into an argument.

Smallest fix: one clause and one row added to comment (4).

> This table uses the unnormalised real convention with $R_{1,1}=x$,
> $R_{1,-1}=y$, $R_{1,0}=z$ and $R_{2,2}=3x^2-3y^2$. The semi-normalised
> harmonics $C^m_\ell$ and $S^m_\ell$ of CITE{Wiki}, which agree with these at
> $\ell\leq1$, are $[(2-\delta_{m0})(\ell-|m|)!/(\ell+|m|)!]^{1/2}$ times the
> entries here; their coefficients are irrational, so they are outside
> $\mathbb{Q}[x,y,z]$.

**Worth doing.** A reader arriving with $\sqrt3\,xz$ in their hands is the
reader this table is for, and at the moment the page gives them no way to see
that $3xz$ is the same object.

### 4. The first mention of $P_\ell^m$ on the page is unlinked

The page draws Definition, Parameters, Formulas, then Comments. So the first
place a reader meets the associated Legendre polynomials is formula (1):

> …while for $m>0$, $R_{\ell m}=(-1)^m r^\ell P_\ell^m(z/r)\cos(m\varphi)$…

with no link and no statement of which $P_\ell^m$ is meant. The link is in
comment (5), one section further down, and (5) is also where the phase
convention is settled. Since the whole table hangs on which $P_\ell^m$ formula
(1) means, and since a $P_\ell^m$ with and without the phase differ by exactly
the sign a reader would be checking, the link belongs at that first mention:
`HREF{T360}[$P_\ell^m$]`, once, in the Formulas section. The skill's rule is
first mention, once per section, and Formulas is a section.

The audit cannot see this: its unlinked-name check looks for table *titles* in
prose, and "associated Legendre" does not appear in formula (1) — only the
symbol does.

**Worth doing**, and it is one `HREF`.

### 5. Four links point at T360, which is not published

`HREF{T360}` appears in comment (5), comment (6), the `Similar tables` row and
`rigour details`. `https://numberdb.org/T360` answers 404 today: it is a
draft. The audit's own check for this —

> `HREF{...}` points at a draft, which answers 404 to everybody; a published
> table must not link to one

— is gated on `table.published`, so it correctly stays quiet while T361 is
itself a draft. But it will not fire at review time either, because a table is
published by being reviewed: whoever confirms T361 confirms it *before* the
check next runs. So this is a note for the person reviewing rather than a
defect in the document: **T360 has to be published first, or the two together.**
If T361 goes out alone, four cross-references on its page go nowhere, and the
one in `Similar tables` is the row that explains its sign convention.

Separately and smaller: T360 is linked twice within the Comments section, in
(5) and again in (6). The skill's convention is first mention, once per
section; the second should be plain text. If finding 1 is taken up by deleting
comment (6), this goes away with it.

**Worth doing** — but as a publication-order decision, not an edit.

### 6. "every stored row with $\ell\leq17$" — stored where?

`rigour details` ends:

> It also reads *the associated Legendre table* and checks (1) against every
> stored row with $\ell\leq17$.

Every row of *this* table has $\ell\leq17$, so read one way the qualifier says
nothing and a reader wonders what it is guarding against. The intended reading
is the other one — T360 runs to $\ell=25$, and the check covers the part of
*that* table this one reaches. Naming which table owns the rows fixes it:
"…and checks (1) against every row of that table with $\ell\leq17$".

**Worth doing**, as a five-word edit while the file is open.

## Noted only

**The Zernike row in `Similar tables`** says "both tables use the same real
sine and cosine convention for signed angular modes". That is true, and it is
a shared notation rather than a relation between the two families — Zernike
polynomials live on the disk and solid harmonics on the sphere, and neither
determines the other. It is the weakest of the three rows, and I would still
keep it: a reader checking a sign convention is helped by a second table that
uses the same one, and comment (4) already leans on it. Noting it only because
the other two rows state real mathematical relations and this one does not, so
a reader may expect more from it than is there.

**Comment (5) asks a little arithmetic of the reader.** "The table drops the
Condon-Shortley phase" is read immediately after formula (1), which visibly
*carries* a $(-1)^m$. The two are consistent — the $(-1)^m$ in (1) is what
cancels the phase inside $P_\ell^m$ — and (5)'s second sentence says so. The
attached `generate.py` puts it more plainly in its docstring ("where
$P_\ell^m$ carries the Condon-Shortley phase"), and the comment could borrow
that phrasing. Not worth an edit on its own.

**The tag `orthogonal polynomials`** is carried by seventeen tables including
T251, which is also multivariate and orthogonal on a region rather than an
interval. I checked this expecting to object to it and did not: it is how the
corpus already uses that tag.

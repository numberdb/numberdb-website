**This table reads well, and it is right about its own mathematics.** The three
things I checked hardest all came back clean.

*The stored values are the Chern character.* I recomputed them from the
definition rather than from the recurrence, in plain Python with `fractions`:
for five random vectors of six rational Chern roots $x_1,\dots,x_6$, I
evaluated each stored polynomial at $c_j = e_j(x)$ and compared with
$\sum_i x_i^n / n!$. All six agree exactly, on all five vectors. The same run
confirms the range claim: the coefficient of $c_n$ in $\mathrm{ch}_n$ is
$(-1)^{n-1}/(n-1)!$, never zero, so $\mathrm{ch}_n$ uses exactly the variables
$c_1,\dots,c_n$ and $\mathrm{ch}_7$ really is the first one past six.

*The page renders whole.* Every control sequence in the document is one of
`\cdots \dots \geq \leq \mathrm \operatorname \sum`; there is no `<`, no `&`,
no `--` and no backtick anywhere in the prose; all six rows are present with
anchors `id="1"` through `id="6"`, so a sentence elsewhere can link one value;
the `Programs` block keeps its indentation inside `<pre><code>`; nothing
prints "Math input error" or `argument ()`, and no section is swallowed.

*The `Programs` block runs and gives the stored answer.* Pasted verbatim into a
file and run through `agents/sage.sh`, it prints `ch_6` character for character
as the table stores it. Finding 5 is about what a reader needs installed to get
there, not about whether it works.

The findings below are about the page as English and as a set of pointers.

## 1. Formula (2) prints a slug, underscores and all, in the middle of a sentence

**Worth doing.** What a reader sees, in `Formulas`:

> (2) $\mathrm{ch}_n=p_n/n!$, where $p_n=\sum_i x_i^n$ is the $n$-th power sum
> symmetric polynomial **Power_sum_symmetric_polynomials** in the Chern roots.

The document says `... is the $n$-th power sum symmetric polynomial
HREF{Power_sum_symmetric_polynomials} in the Chern roots.` A `HREF{slug}` with
no caption falls back to the slug as its link text — `views.py` line 757,
`caption = ref` — so the address itself is set down as a word between
"polynomial" and "in the Chern roots". The link works; it just reads as
somebody's file name, and a reader hunting for the end of the sentence has to
step over it.

Smallest fix: put the link on the name it follows.

    ... is the $n$-th HREF{Power_sum_symmetric_polynomials}[power sum
    symmetric polynomial] in the Chern roots.

The audit has a rule for exactly this shape (`audit_table.py:940`, "writes
`X HREF{X}` — put the link on the name"). It stayed quiet because it requires
the words before the link to be the target's bare title, "Power sum symmetric
polynomials", and this sentence ends in the singular.

## 2. The elementary symmetric polynomials are named in `Comments` and not linked

**Worth doing.** Comment (6) reads:

> The variables are Chern classes. The polynomial $\mathrm{ch}_n$ is written in
> $c_1,\dots,c_n$, where $c_j$ is the $j$-th elementary symmetric polynomial in
> the Chern roots.

The corpus holds that family: T118, "Elementary symmetric polynomials $e_k$",
at `Elementary_symmetric_polynomials` (200 on the live site). This is the first
mention in the section and it is plain text, so a reader who wants to know what
$e_j$ is goes to a search box instead of one click. `Similar tables` links the
table at the bottom of the page, which is not the same as linking the name
where it is used.

Smallest fix: `... is the $j$-th
HREF{Elementary_symmetric_polynomials}[elementary symmetric polynomial] in the
Chern roots.` The audit missed this for the same singular/plural reason as
finding 1.

While there: the comment's first sentence, "The variables are Chern classes",
says what the Title, the Definition and the second sentence all say already. It
can go, and the comment is then one sentence that does one thing.

## 3. Comment (7) is the completeness note said twice, minus the reason

**Worth doing.** Comment (7) reads:

> The polynomial $\mathrm{ch}_7$ has a nonzero $c_7$ term, so $\mathrm{ch}_6$
> is the last entry that uses at most six variables.

A reader meeting that in `Comments` has not yet been told that six is a
threshold for anything, so the sentence is an inference from a premise that
arrives two screens later, under `Data properties`:

> Table is complete: no (it holds every entry with $1\leq n\leq 6$;
> $\mathrm{ch}_7$ is the first component needing more than six variables, which
> is the most a stored polynomial may have)

That is where a remark about the range belongs, and it is well written there.
The comment is the same fact with its reason cut off.

Smallest fix: delete comment (7). Better, and barely longer, spend the line on
the mathematics the range argument rests on, which the table nowhere states:

> $\mathrm{ch}_n$ involves exactly the variables $c_1,\dots,c_n$: the
> coefficient of $c_n$ is $(-1)^{n-1}/(n-1)!$, which is never zero.

I checked that for $n\leq 7$ in the recomputation above. It is the fact a
reader wants when they ask why the table stops, and it makes the completeness
note's claim checkable instead of assertable.

One word in the completeness note itself: "it holds every entry with
$1\leq n\leq 6$" makes the clause circular, since an entry is a row of this
table. The corpus's phrasing names the object — "every real fundamental
discriminant with $D\leq1000$" — so "every component with $1\leq n\leq 6$".

a slug tells a reader where they are going.

    from sage.rings.rational_field import QQ

and then computes a Chern character polynomial that has nothing to do with

and `factorial` as globals; what the first line adds for them is an
`ImportError` unless they have run `sage -pip install numberdb`, which is a
requirement for filling a table here and not for reproducing a value. The

(`sage -python`, no preparser, named imports), which is a fact about how this
table was built.

Smallest fix: delete the first three lines and the `factorial` definition,
leaving the ten-line function and the `print`. That is the incantation a reader

I wanted to recommend the shorter standard route instead —

## 6. `generate.py` publishes this deployment's build commands to every reader

**Worth doing, cheap; the second half is a note, not a fix.** The file the site
serves at `/files/T335/generate.py` opens with the run commands, which is
right, and then adds:

    On the NumberDB build machine, where arguments are not passed through
    agents/sage.sh, publish with:

        $ cat "$NUMBERDB_KEY_FILE" | NUMBERDB_KEY_FROM_STDIN=1 NUMBERDB_PUBLISH=1 \
              agents/sage.sh generate.py

A reader who downloads this file has neither that machine, that script nor that
variable. Smallest fix: delete the paragraph, and `_key_from_stdin` with it if
the next run of the generator does not need it; the docstring above it already
tells a reader the two commands that work anywhere.

The note: `fill_draft_once` copies the client's internals
(`from numberdb._generate import _check_precision, _check_rigour, _producer,
_run_name, _source_files`, `from numberdb._write import ...`) to work around
"the client's empty upsert probe". That is five private names and it will break
on a `numberdb` release that renames any of them, leaving a reader with an
`ImportError` on a file whose docstring promises `sage -python generate.py
--publish`. The fix is not in this table — either the client should not probe,
or `publish()` should take the flag — but the table is where the breakage will
be seen, and a line in the docstring saying which package version it was
written against would cost nothing.

The mathematics in that file is the best part of the table and should be said
plainly: it checks the stored polynomials against the Chern roots in six
variables *and* against the projective spaces, $\mathrm{ch}_n(T\mathbb{P}^m) =
(m+1)h^n/n!$ for $1\leq n\leq m\leq 6$, which is an independent identity rather
than a second run of the same recurrence. That is what `rigour details` is
describing when it says "checked against the Chern-root definition", and it is
selling itself short: the projective-space check is the stronger of the two and
is not mentioned.

## 8. Noted only, because I noticed

* `Similar tables` calls T118's objects "the elementary symmetric functions
  $e_j$" where comment (6) calls them elementary symmetric polynomials, which
  is the corpus's own word and the title of the table being linked. One word.
* Nothing says in words which grading $n$ counts. $\mathrm{ch}_n$ is
  homogeneous of weighted degree $n$ with $\deg c_j = j$, equivalently the
  component in $H^{2n}$; the Definition says "the homogeneous component" and
  leaves the reader to get it from Formula (2). It is settled by the formulas,
  so this is not ambiguity, only a phrase a reader would have liked in the
  first sentence.
* The Definition and Title write `\mathrm{ch}`, Formula (1) and comment (4)
  write `\operatorname{ch}` and `\operatorname{rank}`. Both render upright and
  a reader will not notice; I mention it because one of them is the table's
  choice and the other is a habit.
* When T332 is published, a `Similar tables` row for it would serve a reader
  better than either of the two symmetric-function rows: it holds Chern classes
  of actual varieties, which is what somebody substitutes into these
  polynomials. Not a defect in T335; a row to add on the day.

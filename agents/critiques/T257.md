# T257 critique: Poincaré polynomials of the finite Coxeter groups

Read 2026-09-16. T257 is a private draft — `/T257` answers 404 anonymously and
with the owner's bearer token, and `/preview/T257` refuses a draft the same way
— so it was read through `GET /api/table?id=T257` and rendered in eight
`/preview?table=` pieces. It holds 37 entries, one integer polynomial $W(t)$
for each irreducible finite Coxeter type, under a single parameter `type` whose
values are the type names; type `Z[]`, rigour `exact`, `complete: no` with a
note giving the range. `GET /api/table/T257/audit` reports
`{"findings": [], "clean": true}`, and I agree with it: nothing it checks is
wrong here, and nothing it reports is a false alarm.

**This table reads well.** The three things I checked hardest all held. It is
one table and not two wearing one title: the single parameter names *what the
number is of*, and the value column is headed `$W(t)$`, a symbol true of every
row, not the word `value` a table of two quantities falls back on. Its numbers
are right where I could check them independently — eight rows recomputed in
Sage by enumerating the group element by element, never touching the degrees
the generator uses, all eight match. And it is distinctive: of the 37 entries,
36 match nothing anywhere in the public corpus, and the one that does is $A_1$,
whose $t+1$ is also $\Phi_2$ and three other things. Measurements are in "How
it was read".

What is left is nine things, and the top five are worth doing.

- **1 is the only one that costs a reader anything they came for.** The
  `Programs` snippet, copied into a file and run the way its own page tells a
  reader to run a Sage program, fails on its first line — I ran it and have the
  error — and even when it runs it asks for the degrees, which appear nowhere
  on the page.
- **2 is a visible fault in one word**, and lives only in the rendering.
- **3 and 4 are about what the page claims**: two keywords promise subjects the
  page never mentions, and one sentence lists four checks of which two cannot
  fail.
- **5 is a reference nothing points at**, about a different power series.
- **6 to 9 are worth doing while the file is open.**
- **10 and 11 are noted only because I noticed them**, and 10 is one I expected
  to report as a fault until I looked at the corpus and found it is the house
  style.

## 1. The `Programs` snippet fails as a script, and needs degrees the page does not give

What a reader sees, as (P1), labelled `Sage`:

    from sage.rings.integer_ring import ZZ
    from sage.rings.polynomial.polynomial_ring_constructor import PolynomialRing

    T = PolynomialRing(ZZ, 't')
    t = T.gen()

    def poincare_from_degrees(degrees):
        out = T.one()
        for d in degrees:
            out *= sum(t**k for k in range(d))
        return out

    poincare_from_degrees([2, 6, 8, 12])  # F4

Why it is wrong, twice over.

*It does not run as a script.* Saved verbatim to a file and run with
`sage -python`, which is the incantation the corpus's own generators open with,
it stops on line 1:

    AttributeError: partially initialized module 'sage.rings.integer_ring'
    has no attribute 'ZZ' (most likely due to a circular import)

Importing a Sage submodule into a fresh interpreter enters the Sage import
graph part-way through. Inside a Sage session, where `sage.all` is already
loaded, the same lines work, and that is presumably where they were written and
checked. Which of the two environments the reader is in decides whether the
page's one runnable thing runs, and nothing on the page says which was meant.
(This is not T257's invention: the same shape is in T233, T243 and T256, and a
lesson proposing `from sage.all import ...` is already waiting in
`agents/lessons/proposals/20260916T024304Z-critique.md`. T257 is the fourth
instance and the first where the failure was reproduced on this table's own
code.)

*And it computes the half a reader already has.* `poincare_from_degrees`
takes the degrees as its argument, and the degrees are the part a reader does
not know: they appear nowhere on this page, for any type, except as the four
literals `[2, 6, 8, 12]` in that last line. A reader who wants the row for
$H_4$, or the $A_{10}$ row the table stops short of, cannot get it from here.

The smallest change. Two lines, and the section does what `Programs` is for —
"one more value" — instead of one value the table already holds:

    from sage.all import ZZ, PolynomialRing, CoxeterGroup

    T = PolynomialRing(ZZ, 't')
    t = T.gen()

    def poincare_from_degrees(degrees):
        out = T.one()
        for d in degrees:
            out *= sum(t**k for k in range(d))
        return out

    poincare_from_degrees(CoxeterGroup(['F', 4]).degrees())  # F4

I ran that, under `sage -python`: it imports cleanly, `CoxeterGroup(['F',
4]).degrees()` is `(2, 6, 8, 12)`, and the polynomial it returns is the stored
$F_4$ row. `CoxeterGroup(['H', 3]).degrees()` reproduces the stored $H_3$ row
the same way, and `CoxeterGroup(['I', 5])` is how Sage spells $I_2(5)$, which
is worth having on the page because it is not guessable. Sage has no
`poincare_polynomial()` method — I checked — so this snippet does earn its
place; it just needs the degrees to come from somewhere a reader can reach.

## 2. `Poincar\'e` reaches the page as `Poincar\'e`

What a reader sees, in the second comment:

> For a split reductive group with Weyl group $W$, $W(q)$ is the number of
> $\mathbb F_q$-points of the flag variety $G/B$ [4]. The polynomial $W(t^2)$
> is the ordinary Poincar\'e polynomial of the corresponding complex flag
> manifold.

Why it is wrong. `\'e` is TeX's text-mode accent, and a table's prose is not
TeX: only `$...$` is handed to MathJax, and everything outside it is written to
the page as it stands. So the backslash, the apostrophe and the `e` are all
printed, one screen below a title that spells the same word "Poincaré"
correctly. The document has no other text-mode escape, so this is a slip rather
than a convention.

The smallest change. Write the letter: `Poincaré`, as the `Title` and the
`Keywords` already do.

## 3. Two keywords name subjects the page never mentions

What a reader sees: nothing — which is the fault. `Keywords` carries
"Mahonian" and "coinvariant algebra", and `Keywords` is indexed at the same
weight as the title, so both are ways somebody arrives here. Having arrived,
they find that the page contains neither phrase. "Mahonian" appears once, in
`rigour details`, as the name of an OEIS triangle the generator checked
against; "coinvariant algebra" appears nowhere at all, and the nearest phrase
on the page is "the invariant polynomial algebra", which is a different object.

Why it is wrong. Both keywords are promises about what the page explains, and
both point at the two commonest ways a reader meets these coefficients without
having heard of Coxeter groups. Somebody counting permutations by inversions
holds $1, 2, 2, 1$ and $1, 3, 5, 6, 5, 3, 1$; the page's type $A$ rows are
exactly those, and nothing on the page says so — it never even says that the
Coxeter group of type $A_n$ is the symmetric group on $n+1$ letters, though
formula (2) implies it by giving $W(1)=(n+1)!$. Somebody who knows $W(t)$ as
the Hilbert series of the coinvariant algebra is one clause from the
definition's "invariant polynomial algebra" and is not given it.

The smallest change. One comment, which also earns both keywords:

> In type $A_n$ the group is the symmetric group on $n+1$ letters and $\ell$ is
> the number of inversions, so the coefficients of $W(t)$ count permutations of
> $n+1$ letters by inversions, the Mahonian numbers [5]. For any $W$, $W(t)$ is
> the Hilbert series of the coinvariant algebra, the quotient of the polynomial
> ring by the ideal generated by the invariants of positive degree.

[5] is `CITE{OEISA008302}`, which the table already declares and which is at
present reached only from `rigour details`.

## 4. `rigour details` lists four checks and two of them cannot fail

What a reader sees, behind the "more" fold under *Data properties*:

> The entries are exact integer polynomials computed from (1). The generator
> checks all stored rows against the palindromy identity (3), the order
> identity (2), Solomon's identity (4), and the Mahonian triangle [5] for the
> type $A$ rows.

Why it is wrong. The entries are built as $\prod_i(1+t+\cdots+t^{d_i-1})$, and
that product is palindromic and satisfies $W(1)=\prod_i d_i$ for *any* list of
positive integers whatever — so testing those two things tests nothing about
the list that was used. In Sage, on made-up degrees:

    degrees (2, 6)          palindromic: True   p(1) == prod(d_i): True
    degrees (2, 7)          palindromic: True   p(1) == prod(d_i): True
    degrees (3, 5)          palindromic: True   p(1) == prod(d_i): True
    degrees (2, 3, 4, 17)   palindromic: True   p(1) == prod(d_i): True

$(2,7)$ is not the degree list of any Coxeter group, and both named checks pass
on it. A reader counting four independent confirmations is counting two. What
actually pins the degrees down is in the generator and not in this sentence:
the comparison of $W(1)$ against the *known* orders of the exceptional groups
($51840$, $2903040$, $696729600$, $1152$, $12$, $120$, $14400$), Solomon's
identity, which has real content because it makes every parabolic sub-diagram's
degrees agree with the whole, and the OEIS triangle for type $A$.

The smallest change. Say the checks that could have failed, and drop the two
that could not:

> The entries are exact integer polynomials computed from (1). The generator
> checks $W(1)$ against the known orders of the exceptional groups, checks
> Solomon's identity (4), which ties each type's degrees to those of all its
> parabolic subgroups, and checks the type $A$ rows against the Mahonian
> triangle [5].

## 5. A reference nothing cites, about a different power series

What a reader sees, as [2] under *References*:

> George Lusztig, Some power series involving involutions in Coxeter groups,
> 2014. (arXiv) (doi)

Why it is wrong. No `CITE{Lusztig}` appears anywhere in the document — I
counted: `Humphreys` is cited three times, `WikiCoxeter`, `WikiFlag` and
`OEISA008302` once each, `Lusztig` zero times. A reference is for citing, and a
bibliography nobody points at is furniture. Here it is worse than furniture:
the paper is about $\sum t^{\ell(w)}$ taken over the *involutions* of $W$,
which is a different polynomial from the one every row of this table holds, and
a reader who follows the only unexplained entry in the reference list lands on
it with nothing to say why. (The arXiv identifier is right — 1411.3233
resolves, and the title matches — so this is not a broken link, just an
unattached one.)

The smallest change. Delete it. Or, if the involution analogue is worth
telling a reader about, a comment that says so and cites it there — that is the
only thing that would make a reader glad it is in the list.

## 6. The definition ends by restating formula (1)

What a reader sees, in the *Definition*:

> For a finite irreducible Coxeter group $W$ [3], with simple-reflection length
> $\ell$, this table stores $W(t)=\sum_{w\in W}t^{\ell(w)}$. Equivalently,
> $W(t)=\prod_i(1+t+\cdots+t^{d_i-1})$, where the $d_i$ are the degrees of the
> invariant polynomial algebra [1].

and, one section further down the page, formula (1):

> If $d_1,\ldots,d_r$ are the degrees of $W$, then
> $W(t)=\prod_{i=1}^r(1+t+\cdots+t^{d_i-1})$ [1].

Why it is wrong. The first sentence of the definition defines the object, and
the second is a theorem about it — Chevalley's and Solomon's, not a definition
— stated a second time on the same page in the section whose job is to hold
identities. The definition should say what the object is and stop. It matters a
little more than duplication usually does because of where the two sit: the
page draws Definition, then Parameters, then Formulas, so a reader meets the
same product twice inside two screens and has to read both to see whether they
differ — they do, in one word, since the definition says "the degrees of the
invariant polynomial algebra" and the formula says "the degrees of $W$".

The smallest change. Cut the second sentence from the definition, and move the
one thing it carries that formula (1) does not — what "degrees" means — into
formula (1), which uses the word:

> If $d_1,\ldots,d_r$ are the degrees of $W$, that is, the degrees of a
> homogeneous generating set of the $W$-invariant polynomials, then
> $W(t)=\prod_{i=1}^r(1+t+\cdots+t^{d_i-1})$ [1].

## 7. $G/B$ arrives with neither letter bound

In the same comment as finding 2:

> For a split reductive group with Weyl group $W$, $W(q)$ is the number of
> $\mathbb F_q$-points of the flag variety $G/B$ [4].

The sentence never names the group $G$ — it says "a split reductive group" and
then uses a letter it did not introduce — and never says that $B$ is a Borel
subgroup. A reader who knows the subject supplies both instantly and a reader
who does not cannot. The smallest change is four words: "For a split reductive
group $G$ with Weyl group $W$ and Borel subgroup $B$, …".

## 8. "not repeated" is used for a type that never appears once

The third comment:

> $B_n$ and $C_n$ have the same finite Coxeter group, so $C_n$ is not repeated.
> The rows $I_2(3)$, $I_2(4)$ and $I_2(6)$ are not repeated because they are
> $A_2$, $B_2$ and $G_2$.

$C_n$ is not in the table at all, so "not repeated" asks the reader to look for
a first occurrence that does not exist; the fact is that it is not a separate
row. And the second sentence hands a reader two lists of three and leaves them
to pair off, which is the "name it, do not point at it" case in a small way:
the pairing is correct, and a reader still has to count to know it. Writing the
equalities is shorter than the sentence that describes them:

> $B_n$ and $C_n$ have the same Coxeter group, so there is no separate $C_n$
> row. $I_2(3)=A_2$, $I_2(4)=B_2$ and $I_2(6)=G_2$, so those three dihedral
> types have no rows of their own either. Reducible finite Coxeter groups are
> not rows; their polynomials are products of the irreducible rows.

## 9. The completeness note says what the range is and not why

> complete: no (it holds $A_n$ for $1\leq n\leq9$, $B_n$ for $2\leq n\leq9$,
> $D_n$ for $4\leq n\leq9$, the exceptional types $E_6$, $E_7$, $E_8$, $F_4$,
> $G_2$, $H_3$ and $H_4$, and $I_2(m)$ for $5\leq m\leq12$ with $m\neq6$)

It finishes the sentence the page starts, which is the hard part and is done
well. What is missing is the argument: why 9, and why 12. It is not size — the
whole entries block is 12 KB against a 320 KB soft limit, and the largest entry
is $E_8$ at 1726 characters, so rank 12 or 15 would still fit comfortably. So
the bound is a judgement about who arrives holding one of these polynomials,
and that judgement is the sentence a reader checking whether their own number
belongs here actually wants. One clause: "…, a range chosen to cover the ranks
that occur in practice rather than what fits".

## 10. The type column is ASCII where everything around it is typeset — and that is the house style

What a reader sees, as the first thing on the page, above the definition:

    type      $W(t)$
    A1:       t + 1
    …
    I2(5):    t^5 + 2*t^4 + 2*t^3 + 2*t^2 + 2*t + 1

while the parameter block immediately below writes the same things as $A_1$ and
$I_2(m)$, and every comment and formula does too.

I expected to report this as a fault, because the nearest table in the corpus
by subject and by age — T256, built the day before — gives its Dynkin-type
parameter a `values:` map (`E6: $E_6$`), which is the field that decides how a
value is displayed without touching the key a citation resolves on. Then I
looked at the rest of the corpus. Of the 56 tables with a `Symbolic` parameter,
32 carry a `values:` map and 24 do not, and the one that matches T257 most
exactly does not: T233, *Ehrhart polynomials of the root polytopes*, has a
parameter with the same key `type`, the same `display: type`, the same kind of
constraints line, and its published page reads `A2:`, `A3:`, `E8:` in ASCII
exactly as this one will.

So this is a choice the corpus makes both ways, and T257 made it the way its
closest sibling did. It is worth doing if somebody wants it done — the map is
37 short lines, it costs a reader nothing, and it has a second effect worth
having, since `validate.py` checks every entry's parameter value against a
declared `values:` map, so a mistyped type name would be refused rather than
stored. It is not worth doing on my say-so alone, and it is not a fault in this
table that T233 does not equally have.

## 11. One of three sibling Coxeter tables is linked

`Similar tables` names T223, *Growth rates of hyperbolic Coxeter simplex
groups*, with a well-judged relation ("growth rates for infinite Coxeter groups
rather than finite growth polynomials"). The corpus also holds T222, *Growth
rates of hyperbolic Coxeter triangle groups*, and T224, *Volumes of the
hyperbolic Coxeter simplices*, to which the same sentence applies about as
well. Three links where there is one is not obviously better than one, and the
relation as written covers the family; I note it only because a reader browsing
sideways from "Coxeter" will find the other two from the search box anyway.

## How it was read

- **Fetching.** `curl --socks5-hostname 127.0.0.1:1080` fails on this builder
  and leaves any `-o` file untouched; `ALL_PROXY` is empty and nothing listens
  on 1080. `curl --noproxy '*'` answers 200. Both facts are already in
  `docs/agent-environment.md`; the first two minutes of this run were spent
  rediscovering them because the prompt still hands over the proxy form.
- **The document.** `GET /api/table?id=T257` with the owner's bearer token,
  17,257 bytes. There is no Django in this checkout, so `manage.py audit_table`
  was unavailable and `GET /api/table/T257/audit` was used; it runs the same
  `findings_for`.
- **Rendering.** Nine `/preview?table=` pieces, each a JSON document (YAML's
  `BaseLoader` reads JSON, which saves hand-writing YAML into a query string),
  each under the 4,094-byte request line, all 200. Between them they cover
  Definition, Parameters, Comments, Formulas, Programs, Similar tables, Links,
  References, Data properties and Display properties, plus the $E_8$ row alone
  to see the longest entry laid out. No swallowed section, no `Math input
  error`, no `argument ()`, no `CITE-broken` or `HREF-broken` in any piece that
  carried the labels its `CITE`s name. The page draws Formulas as (1)–(4) and
  Comments as (5)–(7), so the four `CITE`s in `rigour details` resolve to the
  formulas they mean.
- **Typesetting.** The 65 `$…$` fragments use ten distinct macros —
  `\cdots \ell \in \ldots \leq \mathbb \neq \prod \subseteq \sum` — all of them
  in the base and AMS packages the site's `tex-svg` bundle loads; braces and
  `$` are balanced in every field. There is no bare `<` or `&` anywhere in the
  document, so the fault that ate a section on an earlier table cannot happen
  here. The one text-mode escape is finding 2.
- **The program.** Exec'd in a namespace, as a Sage session would: it returns
  the stored $F_4$ row, and `RESULT(1) = 1152 = |W(F_4)|`. Run as a file under
  `sage -python`, through `agents/sage.sh`: `AttributeError` on line 1, which
  is finding 1. The proposed replacement runs both ways.
- **The numbers, independently.** Eight rows recomputed by enumerating the
  group and counting elements by length —
  `CoxeterGroup(spec)` and `w.length()`, which never looks at a degree —
  all eight matching the stored polynomial: $A_2$ (6 elements), $A_4$ (120),
  $B_3$ (48), $D_4$ (192), $G_2$ (12), $H_3$ (120), $I_2(5)$ (10), $F_4$
  (1152). That is not the build's own product formula, and it covers one row
  of every family in the table except $E$.
- **Distinctiveness.** All 37 entries sent to `/api/lookup` with the key. One
  hit: $A_1$'s `t + 1`, which is also in T95 (as $\Phi_2$), T116, T240 and
  T248. The other 36 match nothing in the public corpus, including every
  dihedral row, so this is not a table of values that match everything.
- **Search by number will find these.** The corpus keys a polynomial modulo its
  variable names — `parse_polynomial('t^6+2*t^5+…').canonical_text()` is byte
  for byte the same as for the same polynomial in `q` or in `x` — so the
  comment about evaluating at $q$ does not leave a reader holding a $q$-form
  unable to find the row.
- **Size.** 37 entries, 12,303 characters of values, largest entry $E_8$ at
  1,726 characters. Against the soft limits (1200 entries, 320 KB block) there
  is room for ten times this. $E_8$ is the one row over the 1,100 characters at
  which the skill says an entry stops being something anybody reads, and it is
  also the row most likely to be looked up; keeping it is right.

## What the audit could not have seen

Nothing it reports is wrong, and it is silent for good reasons rather than by
luck:

- The "two tables wearing one title" check never runs on a one-parameter table,
  and would have exempted this one anyway: the parameter names what the number
  is of, which is the good kind. The tell agrees — the value column is
  `$W(t)$`, not `value`.
- The generic-header and `param-latex` checks have nothing to complain about:
  there is no `param-latex` here, and the header is the quantity's own symbol.
- The unlinked-family check needs a corpus title to appear in the prose; the
  four tables this one names are all in `Similar tables` and all linked, and
  all four slugs answer 200 with the titles the captions give.
- The editorial and narration phrase lists do not fire: there is no sentence
  about how good a search hit would be, and the one narration sentence lives in
  `rigour details`, which is the field for it. Finding 4 is about that
  sentence, and it is not a rule about phrasing — a rule cannot know which
  identities are implied by the construction.

Of the eleven findings above, one (5, the uncited reference) is mechanical
enough that a check could find it; the rest need somebody to run the code, know
the mathematics, or read the page.

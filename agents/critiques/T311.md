# T311: Modular polynomials for $\gamma_2=\sqrt[3]{j}$

Read on 2026-09-17, against the skill fetched that day from
<https://numberdb.org/skill> (47,534 bytes). T311 is a draft with eight `Z[]`
entries, one for each prime $\ell\ne3$ with $\ell\leq23$. It has
`rigour: exact` and `complete: no`.

The table is mathematically in good order and one table in the sense the skill
means. Two of its faults, though, are in the rendering alone, and both are of
the kind the corpus has been bitten by before: **the Definition's LaTeX is
corrupted in the stored document** and **the link to T310 is cut in half by a
`]`**. Neither is visible in the generator's `table.yaml`, and `audit_table`
reports the table clean.

## How it was read

- **Rendering.** The SOCKS proxy on 1080 was not listening; a direct `curl`
  reaches the site from this box, as `docs/agent-environment.md` records.
  `/T311` and `/preview/T311` both answer 404, which is what a draft does to a
  request carrying an API key rather than a session. I fetched the document
  with the key (`/api/table?id=T311`) and rendered it through
  `/preview?table=` in six pieces under the 4094-byte request line, each
  carrying `Title` and one entry. All six returned 200 and drew their
  sections: Definition, Parameters, Data properties, Comments, Links,
  Formulas, Programs, Similar tables, and the value table. **Two of them do
  not render correctly**; see findings 1 and 2. A piece must carry `Formulas`
  and `Links` or every `CITE` in it renders as `CITE-broken`; with both
  present, `CITE{formula-branch}` renders "Formula (1)" and
  `CITE{PARIpolmodular}` renders "[1]", so the two citations on this page are
  sound. All five `Similar tables` slugs answer 200, and the PARI manual link
  carries the `polmodular` anchor it names.
- **Audit.** `GET /api/table/T311/audit`, with and without `links=1` and
  `fetch=1`, returns `"findings": [], "clean": true`. I agree with it on
  everything it looks at. It cannot see either rendering fault: it has no
  check for a control character in a prose field, and its own HREF mask,
  `HREF\{[^}]*\}(\[[^\]]*\])?`, truncates a caption at the first `]` exactly
  as the renderer does, so the broken caption looks well-formed to it.
- **Checked, because a claim depended on it.** `comment-variables` fixes which
  variable is $\gamma_2(\ell\tau)$ and which is $\gamma_2(\tau)$. I parsed all
  eight stored rows: every one is **symmetric**, $\Phi(x,y)=\Phi(y,x)$, of
  bidegree $(\ell+1,\ell+1)$, with the coefficient of $x^{\ell+1}$ equal to
  $1$ as `comment-normalisation` says. So the variable order is unobservable
  in every row the table holds. I also ran the Program: `polmodular(2, 5)` and
  `polmodular(5, 5)` in the deployed image return polynomials **equal** to the
  stored rows for $\ell=2$ and $\ell=5$, and `polmodular(3, 5)` raises
  `domain error in polmodular0_ZM: invariant incompatible with 3`.
- **Not checked.** The values themselves. The generator compares every row
  against `polmodular(ell, 5)` before writing, and `verify` and the audit
  check them again.

## What reads well

- **It is one table.** One parameter, and it is an argument rather than a
  name. The value column is headed $\Phi^{\gamma_2}_\ell(x,y)$, true of every
  row, not the word `value`; there is no `param-latex`, so the rows read
  `2:`, `5:`, `7:` as they should.
- **The parameters describe the family, not the run.** The constraint is
  "$\ell$ is prime and $\ell\ne3$" -- the family -- and the eight primes that
  are here are in `complete-note`, which finishes the sentence it renders
  inside: "complete: no (it holds every prime $\ell\ne3$ with $\ell\leq23$)".
  That is exactly the division the skill asks for, and the note is true of the
  entries.
- **No value is hidden in an entry comment.** All eight entries are bare
  polynomials. The generator would have added a $\deg_y$ comment had any row
  had $\deg_y\ne\ell+1$; none does, so none carries one.
- **The terms are in an order a reader can follow**: total degree descending,
  then $x$-degree descending, consistently in all eight rows.
- **No editorial claim.** Nothing on the page says how distinctive a value is
  or what a reader should conclude.

## Findings

### 1. The Definition's LaTeX is corrupted: `\tau` is a tab and `\ne` is a newline (worth doing, first)

A reader opening the page meets, as the first prose on it (writing `<TAB>` and
`<LF>` for the two control characters actually stored):

    Let $\gamma_2(<TAB>au)^3=j(<TAB>au)$, with $\gamma_2(<TAB>au)=q^{-1/3}(1+O(q))$.
    The table gives the primitive relation $\Phi^{\gamma_2}_\ell(x,y)$ for
    prime $\ell<LF>e3$.

The stored string contains three literal **tab** characters where `\tau`
should be and one literal **newline** where `\ne` should be. In the rendered
HTML the tabs sit inside math, so MathJax draws $\gamma_2(au)$ and $j(au)$ --
the variable is gone and an "au" stands in its place, three times -- and the
newline becomes a `<br>` *inside* `$...$`:

    <div class="table-text">Let $\gamma_2(&#9;au)^3=j(&#9;au)$, ...
    for prime $\ell<br>e3$.</div>

so the last math is split across two text nodes with neither dollar matched,
and the sentence breaks mid-word onto a second line.

This is not in the repository. `generators/modular-polynomials-gamma2/table.yaml`
has `\tau` and `\ne` correctly, and has since it was committed. The stored
document and the YAML beside the generator disagree, so anybody who reads the
generator to check the page sees nothing wrong. The signature in the API's
JSON says how it happened: `\\gamma` and `\\ell` are escaped (two characters
in the wire bytes), `\tau` and `\ne` are not. That is what `json.dumps` does
to a string that was written as a **non-raw Python literal** -- `\g` and `\e`
are not escapes and survive, `\t` and `\n` are and do not. The edit that
shortened the Definition (commit `f089d9c`) went through such a literal
instead of through the YAML.

Smallest fix: re-send `Definition` from the YAML that is already in the
repository, which is correct as written. Nothing else in the document is
damaged -- I checked every field; `complete-note` and the parameter constraint
both carry a properly escaped `\ne`.

### 2. The link to T310 is truncated at `\sqrt[3]`, leaving `{j}$]` loose on the page (worth doing)

The fourth Similar-tables row renders as

    <a class="HREF" href="Class_polynomials_of_gamma_2_sqrt_3_j">Class
    polynomials of $\gamma_2=\sqrt[3</a>{j}$] &mdash; store class polynomials
    for the same modular function at CM points

The caption is `HREF{...}[Class polynomials of $\gamma_2=\sqrt[3]{j}$]`, and
the caption parser stops at the **first** `]` -- which is the one closing
`\sqrt[3`, not the one closing the caption. A reader sees a link whose text
ends in an unclosed `\sqrt[3`, followed by a stray `{j}$]` outside it. The
link still goes to the right table; the name on it is broken, and so is the
mathematics in it.

Smallest fix: take the bracket out of the caption --
`HREF{Class_polynomials_of_gamma_2_sqrt_3_j}[Class polynomials of $\gamma_2$]`
renders whole and says the same thing. (`\sqrt[3]{j}` is fine in the `Title`,
which is not a caption, and it is fine in the value header; only the caption
position is parsed for `]`.)

There is an unaccepted proposal from 2026-09-13 about exactly this, raised
then for `$[3,5,3]$`. This is the second table to hit it, and the trigger here
is more ordinary: the caption was copied from a table's own title, and the
title contains `\sqrt[3]`.

### 3. The Definition no longer defines (worth doing)

It now says the table gives "the primitive relation $\Phi^{\gamma_2}_\ell(x,y)$".
Two people would not build the same table from that. Nothing in the Definition
says *what the relation is between* -- the vanishing condition
$\Phi(\gamma_2(\ell\tau),\gamma_2(\tau))=0$ is in Formulas -- and nothing
bounds it, so $(x^2+1)\,\Phi$ is also a primitive integer relation and also
answers the description. Nor does the Definition say the polynomial has
integer coefficients, or what its degree is; "monic in $x^{\ell+1}$" is a
Comment, and $\mathbb Z[x,y]$ appears nowhere on the page.

The three missing clauses were all there until commit `f089d9c` shortened the
Definition; they were moved out, and the part that made the object unique went
with them.

Smallest fix: one sentence in the shape the sibling table T309 already uses,
which reads well and is short -- "Listed is the monic minimal polynomial of
$\gamma_2(\ell\tau)$ over $\mathbb Q(\gamma_2(\tau))$, written
$\Phi^{\gamma_2}_\ell(x,y)\in\mathbb Z[x,y]$ with $y=\gamma_2(\tau)$." That
determines the table on its own, and `comment-normalisation` then records the
convention rather than carrying the definition.

### 4. $j$ is named in the Definition and identified nowhere (worth doing)

$j(\tau)$ appears in the Definition and again in Formula (1), and the page
never says what it is. The Definition used to carry
`HREF{Q-expansion_of_the_j-invariant}[the modular $j$-invariant]` and the same
shortening removed it; the only remaining mention of that table is in Similar
tables, where the relation reads "defines the cube of $\gamma_2$" -- which
tells a reader who already knows.

Smallest fix: link at first mention, as the skill asks --
`HREF{Q-expansion_of_the_j-invariant}[the modular $j$-invariant]`.

This is the same fault, from the same kind of edit, that the T310 critique
reported yesterday. Shortening a definition is worth doing; it has now twice
taken the page's only identification of $j$ with it.

### 5. $\ell\ne3$ is excluded three times and never explained (worth doing)

A reader meets the exclusion in the Definition, in the parameter constraint,
and in `complete-note`, and is never told why. It is not an accident of the
run: PARI refuses it outright --

    ? polmodular(3, 5)
    *** domain error in polmodular0_ZM: invariant incompatible with 3

-- because $\gamma_2$ is an invariant of level 3, so $\ell=3$ is not coprime
to it. One comment answers the question the page raises three times.

Smallest fix: a `comment-level`, one sentence, saying that $\gamma_2$ has
level $3$ and that there is therefore no such relation at $\ell=3$ (and, if
it is wanted, that `polmodular` refuses it).

### 6. The Program gives one row, and hides which of its two `5`s is the level (worth doing)

    polmodular(5, 5)

Both arguments are `5`; a reader cannot tell which is the level and which is
PARI's invariant number without reading `comment-pari` and then the manual.
And it is fixed at $\ell=5$, so it produces one of the eight rows rather than
showing how to get any of them. The sibling table T309 does this properly:
its program opens with `\\ For T309 this gives the rows with ell = 2, 3, 5,
7, 13, 37.`

One further thing a reader will meet: PARI prints the polynomial nested, as a
polynomial in `x` with coefficients in `y` --

    ? polmodular(5, 5)
    x^6 + (-y^5 + 1240*y^2)*x^5 + (20620*y^4 + 66211200*y)*x^4 + ...

-- which is the stored row (I checked the equality at $\ell=2$ and $\ell=5$),
but does not look like it. That is PARI's printing and not this table's fault;
it is worth one clause so the reader does not think they have something else.

Smallest fix: `\\ level 11, invariant 5 = gamma_2; PARI prints it nested in x`
above `polmodular(11, 5)`. Using a level that is not `5` makes the two
arguments distinguishable at a glance.

### 7. "the expected monomials" points at something the page never names (worth doing, small)

`rigour details` reads: "finds the one-dimensional rational kernel among the
expected monomials". Expected by whom? The monomial set is in the generator's
docstring -- $x^ay^b$ with $0\leq a,b\leq\ell+1$ and
$\ell a+b\equiv\ell+1\pmod 3$ -- and nowhere on the page. As written, a reader
cannot tell what was solved for, and "one-dimensional kernel" is the whole of
the argument that the answer is the right polynomial rather than a multiple of
it. (It is a good argument: a kernel of dimension one over that box rules out
a proper vanishing factor, because the factor would lie in the box too. The
sentence does not let the reader see that.)

Smallest fix: name the set. T309's rigour note, which spells out its own box
and its truncation bound, is the model, and it is not much longer.

### 8. `comment-variables` settles a question no row can raise, and omits the one fact a reader wants (worth doing, small)

> The variable $x$ is the value at $\ell\tau$, and $y$ is the value at $\tau$,
> matching the variable order in the classical modular polynomials and the
> Weber modular polynomials.

All eight stored rows are symmetric, so swapping $x$ and $y$ changes nothing
in any of them, and the convention this comment fixes is unobservable. What a
reader holding one of these polynomials actually wants to know is the fact the
page does not state: $\Phi^{\gamma_2}_\ell(x,y)=\Phi^{\gamma_2}_\ell(y,x)$,
so they need not worry which variable they used.

Smallest fix: keep the first clause and add the symmetry --
"...and $y$ is the value at $\tau$; the polynomial is symmetric,
$\Phi^{\gamma_2}_\ell(x,y)=\Phi^{\gamma_2}_\ell(y,x)$." It is a fact about the
mathematics and it belongs in Comments, not Formulas, because it is a
convention question being answered.

## Noted only because I noticed

- **Every outside source is a software manual.** The one entry under Links is
  the PARI manual, and the values are justified by agreeing with PARI. A
  reader who wants to check a row against the literature -- Sutherland's
  tables, or Bröker--Lauter--Sutherland, which the sibling $j$-invariant table
  does cite under `sources` -- has nowhere to go from this page. T309 has no
  references either, so this is a habit of the three newest tables in this
  family rather than a fault of this one; I mention it because the $j$ table
  shows what it would look like.
- **"Weber" is never written.** $\gamma_2$ is one of Weber's functions, and a
  reader searching the corpus for "Weber" finds the $f$-function table and not
  this one. The title is right as it is; a keyword would cost nothing.
- **Polynomial values cannot be found by search today, in this table or any
  other.** `/advanced-search` tells a reader to write
  `[{n: x^2 + n for n in [1..10]} for x,y in [polygens(QQ,2,'x')]]`, and
  `/api/search` answers that with "Unknown or not-allowed name 'polygens'":
  the evaluator's namespace has `PolynomialRing` but neither `polygen` nor
  `polygens`, and a direct call to `PolynomialRing(...)` is refused as well.
  So "would a reader who arrived holding one of these numbers be served?" has
  an answer that is not about T311 and that T311 can do nothing about. It is
  in `docs/agent-environment.md` as a site bug.

## Summary

Eight findings; the first two are rendering faults that a reader meets before
anything else, and both should be fixed before this draft is offered for
review. Findings 3 and 4 are both the mark of one edit -- `f089d9c`, which
shortened the Definition -- and restoring the clauses it removed would answer
both. Findings 5, 6, 7 and 8 are each a sentence.

Nothing here is a doubt about the numbers.

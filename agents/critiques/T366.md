# T366 critique: Values of Dedekind zeta functions of totally real quartic fields at negative odd integers

Read 2026-09-20. T366 is a private draft: `/T366` answers 404, with or without
`Authorization: Bearer <key>`, because the table view reads a session and not a
key. The SOCKS proxy on 127.0.0.1:1080 refused every connection again, and
`curl https://numberdb.org/...` direct answers, so every fetch below went
direct.

I read the document through `GET /api/table?id=T366` with the key (102,991
bytes), and rendered it through `GET /preview?table=<json>` in eleven pieces —
YAML is a superset of JSON and the view parses the parameter with
`yaml.BaseLoader`, so the API document can be posted straight back. Every piece
answered 200 and rendered. The `RequestFactory` recipe for rendering a draft's
real page is closed on this builder: the image `agents/sage.sh` runs has no
Django. `GET /api/table/T366/audit` returns `"clean": true` with no findings,
and I agree with it as far as it goes — see the last section for the two rules
that could not fire.

The table holds 612 entries: 204 totally real quartic fields, $D$ from 725 to
29952, each at $s=-1,-3,-5$. Type `Q`, rigour `exact`, entries block 96 KB —
inside every limit, and inside the 160 KB the skill aims at.

It is plainly built from T161, the published cubic table, and it is the better
for it. Most of what follows is where the copy lost something T161 has.

## What I checked hardest, and found right

* **The TeX typesets.** I pulled all 1,083 `$…$` fragments out of the document
  — every prose field and all 204 distinct entry comments — and converted each
  with MathJax 3 under node: 0 errors, with a control (`\frac{1}{`) that the
  same run flagged. No `<` or `>` appears anywhere in the document, so nothing
  is eaten. Every field has an even number of `$`.

* **The rendering.** Citations number across sections and anchor: `[1]`/`[2]`
  for the two Wikipedia links in the definition, `(1)`/`(2)` for the formulas,
  `[1]`/`[2]` for Klingen and Siegel. A formula cited from inside `rigour
  details` — `CITE{formula-abelian}` — resolves to `(2)`, which is the kind of
  cross-section citation that has printed a bare key before; it does not here.
  The rigour note folds after its first paragraph. `complete-note` finishes the
  sentence it is dropped into: "Table is complete: no (it holds every totally
  real quartic field with $D\leq 30000$, at $s=-1,-3,-5$)". The value column
  heads `$\zeta_K(s)$`, a symbol true of every row, not the fallback `value`.
  Entry blocks carry anchors `id="725,1,-1"`.

* **The parameters describe the family, not the run.** `s` is "a negative odd
  integer"; what was computed is in `complete-note`. This is the fault that
  recurs most here and it is not on this page.

* **It is one table.** $D$ and $k$ address a field, $s$ is an argument and not
  a name, and one quantity is listed. No `param-latex`.

* **The page's own arithmetic claims hold against the data.** Every stored
  denominator divides the bound `comment-denominators` states (30, 1020, 8190);
  every value is positive, as `comment-rational` claims; the functional
  equation in `Formulas` is right, including the special case
  $\zeta_K(2)=16\pi^8\zeta_K(-1)/D^{3/2}$, which I rederived from
  $\Lambda_K(s)=\Lambda_K(1-s)$; the entry comments' LMFDB labels are `4.4.D.k`
  in all 204 cases; and in both discriminants that carry two fields the stated
  polredabs lexicographic order is the order used. I did not re-verify the
  values — the build and `verify` do that — but GP returned `2/15` for $D=725$,
  matching the first entry, while I was testing finding 1.

## Findings

### 1. The PARI program does not run. `\` where GP needs `\\`

What a reader sees, under `Programs`:

    default(realprecision, 80);
    bestappr(lfun(lfuncreate(x^4 - x^3 - 3*x^2 + x + 1), -1), 30)    \ 2/15, for D = 725

The stored string holds one backslash. GP's comment marker is two; one
backslash is Euclidean division. Fed the two lines exactly as stored, `gp -q`
answers

    ***   syntax error, unexpected ',', expecting end of file:
      ***   ...3-3*x^2+x+1),-1),30)\2/15,forD=725
      ***                               ^---------

and prints no value. With the backslash doubled it prints `2/15`, which is the
stored entry for $D=725$. T161, the table this one was copied from, has `\\`.

This is the one thing on the page a reader executes, and it fails on the first
line they paste. Nothing on the site checks it: `audit_table` does not look at
`Programs` code at all, which is why the draft is `"clean": true` with a
program that cannot run.

Smallest fix: double the backslash in `Programs.program-pari.code`. Worth
doing, first.

### 2. `Links` carries the request that asked for the table

`Links` ends with `Requested in numberdb-data#22`, pointing at a closed issue
titled "Special values of various L-functions at integers" whose body is empty.
The skill, section 9: "A 'table wanted' issue is answered **in the issue**, not
in the table. … The table carries no trace of the request: it is encyclopedic,
and who asked for it is not a fact about the mathematics. Cite the issue only
in the rare case that it contains something a reader of the mathematics needs."
Issue 22 contains nothing at all, so the exception does not apply.

The link is also uncited: no `CITE{Request22}` appears in the prose, so it
renders as a numbered source under `Links` that no sentence sends anybody to.

Smallest fix: delete the `Request22` link. Worth doing; this has now been
reported on T339, T354, T359 and here, and `agents/table-build/PROMPT.md` line
34 is where it keeps coming from.

### 3. Two HREFs point at a draft, and answer 404 to every reader

`comment-index` ends "This is the convention used by
HREF{Regulators_of_quartic_fields}[the table of regulators of quartic
fields]", and `Similar tables` lists the same target. `curl
https://numberdb.org/Regulators_of_quartic_fields` answers 404; the table
exists — `GET /api/table?url=Regulators_of_quartic_fields` with the key returns
"Regulators of quartic fields" — but it is an unpublished draft, so today it is
invisible to everyone but its author and the board.

The audit cannot say this yet. `audit_table` fires "HREF{…} points at a draft,
which answers 404 to everybody" only when `table.published` is true
(`numberdb_app/management/commands/audit_table.py:330`), so on a draft linking
to a draft it is silent, and the finding appears at exactly the moment it is
most expensive.

The link is corroboration rather than load-bearing — `comment-index` states the
convention in full before naming the table — so nothing is lost by removing it.

Smallest fix: publish the regulators table first, or drop both HREFs (leaving
the sentence "This is the convention used by the table of regulators of quartic
fields" as plain text is worse than dropping it: a name a reader cannot reach
is worth less than no name). Worth doing before this table is published, which
is the only moment it matters.

### 4. Three-tenths of the entries block is the same on every row

Every one of the 612 entry comments reads

    $x^4-x^3-3x^2+x+1=0$; signature $(4,0)$; Galois group $D_4$ (4T3);
    $h_K=1$; $w_K=2$; LMFDB 4.4.725.1.

Two of those six items are constants:

* `signature $(4,0)$` — 204 fields out of 204. It is what "totally real
  quartic" means, and the title, the definition, the `D` constraint and
  `comment-range` all say it already.
* `$w_K=2$` — 204 out of 204, and forced: a totally real field contains no root
  of unity but $\pm1$.

A third, `LMFDB 4.4.D.k`, is the row's own $D$ and $k$ with `4.4.` in front: it
is the label in all 204 cases, never anything else.

`comment-entries` announces all six as though they varied. In fact only the
polynomial, the Galois group and $h_K$ do — and $h_K$ is 1 except at $D=21025$,
which is the one row worth pointing at and the one the page does not point at.

The three constant items cost 27,999 of the 96,457 characters of the entries
block, 29%. The skill's rule is the same measurement: a comment on every entry
is "worth leaving out when it repeats what a formula in the document already
says for every row at once".

Smallest fix: drop `signature $(4,0)$;` and `$w_K=2$;` from the entry comment
and say both once — `comment-range` already explains why the signature is what
it is, and $w_K=2$ is a sentence there too. Keep the LMFDB label, and earn it
by adding to `comment-index` that $k$ agrees with the last component of the
LMFDB label; that is true of all 204 fields, and it gives a reader a way to
check the indexing convention against a page that exists today, which finding 3
says the regulator table is not. Worth doing.

### 5. `k` is never explained, and is 1 on 202 of the 204 fields

A reader meets a column headed $k$ whose every visible value is 1.
`comment-index` says how $k$ is assigned but never why there is a $k$, and
never says how often it is needed. T161 does both, in the same comment: "Non-
isomorphic cubic fields can share a discriminant, so the discriminant $D$ is
not always enough to identify $K$. … In the range computed here, $D=3969$ is
the only discriminant carrying two fields; every other $D$ has $k=1$."

Here the two are $D=16448$ (a $D_4$ field and an $S_4$ field) and $D=28224$
(two $C_2\times C_2$ fields).

Smallest fix: one sentence at the front of `comment-index` saying that
non-isomorphic quartic fields can share a discriminant, and one at the end
naming 16448 and 28224. Worth doing — it is the difference between a column a
reader skips and a column a reader understands.

### 6. The completeness claim is the least supported sentence on the page

`complete-note` says the table "holds every totally real quartic field with
$D\leq 30000$". That is the claim a reader leans on hardest, and `rigour
details` — three sentences on how each individual value was recognised — never
mentions how the field list was obtained or why it is complete.

The generator does the work: it enumerates through PARI's `nflist` over the
five transitive groups of degree 4 and refuses the run unless the count is
exactly 204 (`EXPECTED_FIELDS = 204`). And `Links` declares `PARI-nflist`,
which no sentence cites — the hole and the thing that fills it are both already
in the document.

The same paragraph also undersells the checking. It says the generator refuses
a value "unless it satisfies the sign predicted by the functional equation",
where `check_functional_equation` actually recomputes $\zeta_K(2n)$ with PARI
at 100 digits and compares it with the value predicted from the stored
$\zeta_K(1-2n)$ to a relative $10^{-60}$, at $s=2,4,6$. That is an independent
cross-check of every stored number, not a sign test, and it is the strongest
reason to believe the table.

Again T161 is the model: "enumerates the 173 totally real cubic fields with
$D\leq 5000$ by Hunter's theorem CITE{Cohen1993} … and refuses the run unless
the count is 173."

Smallest fix: two clauses in `rigour details` — the enumeration by
`nflist` CITE{PARI-nflist} over the five degree-4 transitive groups with the
count pinned at 204, and "checked against the functional equation at
$s=2,4,6$" in place of "satisfies the sign predicted by". Worth doing.

### 7. `comment-abelian` respells a formula and then points instead of naming

It reads: "For an abelian quartic field, $\zeta_K(1-2m)$ factors as
$\zeta(1-2m)\prod_{\chi\ne 1}L(1-2m,\chi)$ … The factor $\zeta(1-2m)$ is in
[the table of Riemann zeta values], and the generalized Bernoulli factors are
the quantities indexed in [the table of generalized Bernoulli numbers]."

Two small things. The identity is `formula-abelian` written a second time in a
slightly different form (there over all $\chi\in X$, here with the trivial
character split off), and `Comments` is the section that holds conventions and
caveats and not formulas. And "the generalized Bernoulli factors are the
quantities indexed in the table of generalized Bernoulli numbers" is nearly
circular where the symbol would be exact: $B_{2m,\chi}$ appears in
`formula-abelian` and nowhere in the comment that sends a reader to the table
of them. The skill: "Name the thing, do not point at it. … the symbol is
shorter than the phrase pointing at it."

Smallest fix: replace the restatement with `CITE{formula-abelian}` and name
$B_{2m,\chi}$ where "the generalized Bernoulli factors" stands. Worth doing,
cheaply, when something else is being edited.

### 8. `Similar tables` cites a symbol the page never introduces

The Bernoulli row reads "the factor $B_{2m}$ in the abelian factorisation
through $\zeta(1-2m)$", but $B_{2m}$ appears nowhere else in the document — the
link between $\zeta(1-2m)$ and $B_{2m}$ is exactly what is missing. T161 has
the same row and also lists "Values of the Riemann zeta function at rational
numbers — the factor $\zeta(1-2m)=-B_{2m}/(2m)$", which supplies it. T366 links
that table from `comment-abelian` but leaves it out of `Similar tables`.

Smallest fix: add the Riemann-zeta-values row to `Similar tables` with T161's
relation, or write $=-B_{2m}/(2m)$ into the Bernoulli row. Minor.

## Noted only

* **`comment-denominators`' second sentence is about the method, not the
  mathematics.** "These bounds are used only to recognise the exact rational
  returned by the computation" repeats what `rigour details` says two fields
  later, and belongs only there. The first sentence — Serre's bounds divide 30,
  1020, 8190 — is a fact about the mathematics and is in the right place. T161
  mixes the same two, so this is house habit rather than a slip.

* **The definition defines $\zeta_K$ by a series that does not converge at any
  $s$ in the table.** "$\zeta_K(s)=\sum_{\mathfrak a}N(\mathfrak a)^{-s}$ …
  Listed is $\zeta_K(s)$ at negative odd integers $s$": the sum converges for
  $\Re(s)>1$, and the reader has to supply "continued analytically" themselves.
  The sentence is inherited word for word from T161, which is published, so it
  is not this draft's invention. T130, the real quadratic table, sidesteps it by
  not writing the series down at all: "and $\zeta_K(s)$ its Dedekind zeta
  function CITE{Wiki}". Either that or two added words fixes it, in two tables
  at once.

* **At $s=-1$ the column is small numbers that collide.** All 204 values are
  $\leq 68$, 48 of them are integers, and 48 values occur more than once —
  $22/3$ five times, $8/3$, $16/3$, $12$, $16$, $36$, $92/3$, $104/3$, $112/3$,
  $116/3$ four times each. By the skill's "a reader with a number tries a half,
  a two, a pi" test this third of the table is weak for search-by-number. It is
  also the column people actually arrive holding — $\zeta_K(-1)$ is the one that
  turns up in a Hilbert modular computation — and the collisions are a fact
  about the mathematics, not a fault in the table. The $s=-3$ and $s=-5$
  columns are as distinctive as anything in the corpus. No change wanted; I
  record it because the "is this worth indexing" question has been asked of
  other tables and the answer here is yes.

* **The draft's generator is world-readable while the draft is not.** `curl
  https://numberdb.org/files/T366/generate.py?raw=1` with no key returns the
  full 15,562-byte source, whose docstring names the table, its address, its
  range and its method, while `/T366` answers 404 to the same caller. T359,
  T364 and T365 leak the same way. This is the open site bug already recorded
  in `docs/agent-environment.md` for T235, T324 and T337 — nothing to do with
  this table, and repeated here only as a dated confirmation that it is still
  open.

## On the audit

`GET /api/table/T366/audit` reports `"clean": true`, no findings. I agree with
every check it made, and note three it could not make:

* `--links` needs Django, which the builder image has not got, so the external
  link check did not run. I fetched the five `Links` URLs by hand: Wikipedia
  ×2, the LMFDB signature-(4,0) search, the PARI `nflist` manual page and the
  GitHub issue all answer 200.
* The draft-HREF rule is gated on `table.published`, so finding 3 is invisible
  to it today and will appear the moment somebody publishes.
* Nothing in `audit_table` reads `Programs` code, so finding 1 — a program that
  errors out on its first line — passes clean.

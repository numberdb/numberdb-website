# T357 — Sharp constants in Young's convolution inequality

Read 2026-09-20 as a reader, not as its builder. 1120 entries, type `R`,
rigour `proven`, 100 significant digits on every value, still a private
draft. The mathematics is in good order and most of what follows is small.
Finding 1 is not small: **the page does not render at all.**

## What I checked hardest and found right

* **Every other section renders.** All nine sections are present and in order
  — Numbers, Definition, Parameters, Formulas, Programs, References, Links,
  Similar tables, Data properties — and nothing is truncated. 1120 entry
  anchors, all unique, `1,5/4,5/4` through `20,7/4,9/4`. No `CITE{`, `HREF{`
  or `INPUT{` survives into the HTML: every one resolved.
* **The `<` and `>` in the mathematics do not eat anything.** `$1<p$` and
  `$1/p+1/q>1$` are raw comparison signs inside LaTeX, which is the shape of
  the fault that swallowed a section earlier this year. They reach the page as
  `&lt;` and `&gt;`; `escape_maths` did its job.
* **The mathematics typesets.** All 29 `$...$` fragments in the document went
  through MathJax 3 (`mathjax-full`, SVG output) and not one produced an
  `merror`; a control fragment `\frac{1` did. There is no "Math input error"
  waiting in a browser.
* **The columns say what they hold.** The value column is headed
  `$Y^{(n)}_{p,q}$`, not the word `value`. There is no `param-latex`, so the
  parameter columns read `1`, `5/4`, `5/4` rather than the header once per row.
* **It is one table.** All three parameters are numbers, not names; each says
  *what the number is of*, none says *which quantity is taken of it*; one
  quantity runs down the value column.
* **The parameters state the constraint the entries meet**, and the family's,
  not the run's. $q < p/(p-1)$ is expressed as $1/p+1/q>1$, which is the
  condition itself rather than a list of what was computed; the stored $q$
  respect it exactly at every $p$ (largest stored: $19/4$ at $p=5/4$, $9/4$ at
  $p=7/4$). The denominator bound and the dimension range, which *are* this
  afternoon's run, are in `complete-note` where they belong.
* **The digits are honest.** Every value is written to 100 significant digits:
  1065 of them as `0.` and 100 digits, 55 of them as `0.0` and 101, which is
  the same claim, not a silently shortened one.
* **The values.** Not my job and not repeated at length, but four spot checks
  against the closed form in double precision agree to the last bit available,
  and two rows reproduce an exact surd to all 100 digits (see "Noted only").

## Findings

### 1. The table page raises. Every reader gets a 500.

`Programs` is stored as

    Programs:
      sage: "In Sage, compute $r = 1/(1/p + 1/q - 1)$ and then compute ..."

a plain string. `table_context` wants a record: `numberdb_app/views.py:914`
does `program['language']`, and on a string that is
`TypeError: string indices must be integers`, which `views.py:1461` turns into
`ValueError: Error while Parse program sage: ...`. `render_table`
(`views.py:444`) does not catch it, `table_by_tid` does not catch it, and there
is no `handler500` or exception middleware. The rebuild's traceback ends:

    File ".../views.py", line 613, in table_by_tid
    File ".../views.py", line 444, in render_table
    ValueError: Error while Parse program sage: string indices must be integers

This is not visible in the stored YAML, the audit does not report it, and the
author cannot see it either, because a draft's page is what nobody can load.
If T357 is published in this state its page is an error for everybody.

**Smallest fix**: the record shape its three sibling tables already use —

    Programs:
      program-sage:
        language: Sage
        code: |
          ...

Confirmed: with `Programs` replaced by `{program-sage: {language: Sage, code:
...}}` the same rebuild returns 200 and 731,648 bytes, and the section renders
as `(P1) Sage` above a highlighted code block. Worth doing before anything
else on this list.

### 2. `Programs` holds a description of a program, not a program.

Even shaped right, what is there is

> In Sage, compute $r = 1/(1/p + 1/q - 1)$ and then compute `(A(p) * A(q) /
> A(r)) ** n` in a `RealBallField`, with `A(t) = (R(t) ** (1/t) / R(t/(t - 1))
> ** (1/(t/(t - 1)))).sqrt()`.

A reader who wants one more value cannot paste this: `R` is never bound, the
ball field's precision is never chosen, `$r$` is LaTeX inside a sentence, and
the whole thing is prose. The skill's line for this section is "the standard
incantation in Sage, PARI or mpmath for a reader who wants one more value".
T354, T355 and T356 — built in the same batch, against the same renderer —
each carry runnable Sage beginning `import numberdb.sage as numberdb`.

**Smallest fix**: the eight lines the sentence is describing, with the guard
`rigour details` already names:

    import numberdb.sage as numberdb
    from sage.rings.rational_field import QQ
    from sage.rings.real_arb import RealBallField

    R = RealBallField(numberdb.bits(100, losing=160))
    n, p, q = 3, QQ(5)/QQ(4), QQ(2)
    r = 1/(1/p + 1/q - 1)
    def A(t):
        return (R(t)**(1/t) / R(t/(t-1))**(1/(t/(t-1)))).sqrt()
    print((A(p)*A(q)/A(r))**n)

(That is one parameter triple, chosen because it has to be; it renders, and I
have not run it.)

### 3. The relation to T92 is a fragment, and on the natural reading it is false.

The first `Similar tables` line renders as

> Best Sobolev constant for $W^{1,p}(\mathbb{R}^n)$ —   another sharp constant
> in a classical functional inequality, in the lower-bound direction used by
> that table

A reader has to guess what "the lower-bound direction" is and what it attaches
to. Taken the way the sentence reads — that this constant is in that direction
— it is wrong. T92 states $S_{n,p}\|u\|_{L^q}\leq\|\nabla u\|_{L^p}$, with its
constant on the *left*, bounding a norm from below; T357 stores the least
constant on the *right* of $\|f*g\|_{L^r}\leq Y^{(n)}_{p,q}\|f\|_{L^p}
\|g\|_{L^q}$, which is the opposite side. T356 says exactly this about the
same table and says it correctly:

> that table stores the largest $S_{n,p}$ in $S_{n,p}\|u\|_{L^q}\leq\|\nabla
> u\|_{L^p}$, while this table stores the least $A^{(n)}_p$ on the right side
> of its Fourier-transform inequality

and T354 uses the phrase "in the same lower-bound direction" where it is true
of T354. It looks as though the phrase was carried across without the sentence
that made it mean something.

**Smallest fix**: say which side each constant sits on, in T356's words with
$Y^{(n)}_{p,q}$ substituted. There is no identity between the two tables'
values to claim; the relation is that both are sharp constants of classical
Euclidean inequalities, stated in opposite directions, and that is worth one
clause each.

### 4. The completeness note says what the range is and not why, and leans on a phrase it never explains.

> complete: no (it holds every dimension $n\leq20$ and every ordered pair
> $p\leq q$ of rational input exponents in the open admissible range whose
> reduced denominators are at most $4$)

Two things a reader has to supply. "The open admissible range" names nothing:
the condition is $1/p+1/q>1$ with $p,q>1$, and `Parameters` already states it
two lines further down, so the note could simply say it. And the sentence
gives no argument at all — why 20 dimensions, why denominator 4 — where the
skill asks the note to carry exactly that, because it is what a reader
checking whether their own number belongs here reads. The other three tables
in this batch all carry it: T354's ends "a small grid chosen to include the
common half- and integer-order cases while keeping the table to reference
size", T356's the same, T355's "covering rows whose exponents are integers,
halves, thirds, quarters, and $\lambda=n-2$ Sobolev-dual rows". T357 is the
only one of the four with no reason in it.

**Smallest fix**: name the condition and add the clause, e.g. "…every pair of
exponents $p\leq q$ with $1/p+1/q>1$ whose reduced denominators are at most
$4$, a grid chosen to include the integer, half and quarter exponents that
turn up in practice, on the same dimensions as the companion tables."

### 5. $A_t$ is never named, and the table it belongs to is linked only by "that table".

`Formulas` introduces $A_t=(t^{1/t}/(t')^{1/t'})^{1/2}$ from scratch and never
says what it is called. `Similar tables` then says

> the one-dimensional Beckner factors in that table give these constants by (1)

"The one-dimensional Beckner factors" appears nowhere else on the page, $A_t$
is nowhere called that, and "that table" is a pointer rather than a name. All
three are the Babenko–Beckner constant, which this corpus holds as T356, whose
$n=1$ rows are $A_t$ exactly. A reader meeting $A_t$ in formula (1) has no way
to reach it.

**Smallest fix**: name it at first mention in `Formulas`, where the symbol is
introduced — "$A_t$ is the Babenko-Beckner constant
`HREF{T356}[of the Hausdorff-Young inequality]`" — and then the `Similar
tables` line can say "its $n=1$ rows are the $A_p$, $A_q$ and $A_{r'}$ of
formula (1)", which is both shorter and true.

### 6. Nothing tells a reader holding $Y^{(n)}_{q,p}$ with $q<p$ where to look.

The `Definition` opens "let $1<p\leq q$", which reads as though the constant
were only defined when $p\leq q$. It is not: the object exists for any
$p,q>1$ with $1/p+1/q>1$, and $p\leq q$ is this table's listing convention,
resting on formula (2). The two are never joined. Somebody who computed
$Y^{(1)}_{3,5/4}$ looks for a $p=3$ row, finds that $p$ takes five values all
below 2, and has to notice formula (2) on their own to work out that the
table does hold their number.

**Smallest fix**: one clause in `complete-note`, which is where a statement
about what is listed belongs: "…rows are listed with $p\leq q$, since
$Y^{(n)}_{p,q}=Y^{(n)}_{q,p}$". The `Definition` can then drop the ordering
and say $1<p$, $1<q$.

### 7. The definition omits the quantifier and the word that makes it a definition.

> This table gives the sharp constant $Y^{(n)}_{p,q}$ in Young's convolution
> inequality [3], $\|f*g\|_{L^r(\mathbb{R}^n)}\leq Y^{(n)}_{p,q}
> \|f\|_{L^p(\mathbb{R}^n)}\|g\|_{L^q(\mathbb{R}^n)}$.

As written, the displayed inequality is satisfied by any constant larger than
this one, and by many smaller ones for particular $f$ and $g$; what pins the
number down is "the least $Y$ for which this holds for all $f\in
L^p(\mathbb{R}^n)$ and $g\in L^q(\mathbb{R}^n)$". "Sharp" is standing in for
both and is doing it silently. T92, the table this one links first, writes
"for any $u\in W^{1,p}(\mathbb{R}^n)$ … which are best possible".

**Smallest fix**: "the least constant $Y^{(n)}_{p,q}$ for which
$\|f*g\|_{L^r}\leq Y^{(n)}_{p,q}\|f\|_{L^p}\|g\|_{L^q}$ holds for all $f\in
L^p(\mathbb{R}^n)$ and $g\in L^q(\mathbb{R}^n)$."

### 8. Three of the four `Similar tables` targets are themselves unpublished drafts.

T354, T355 and T356 all answer 404 to an anonymous request today. Only T92 is
public. If T357 is reviewed and published ahead of its three siblings, three
of its four "similar tables" links land on Not Found, and a reader cannot tell
that from the page. Not a fault in the document — this is a publication-order
matter for whoever reviews the batch — but it wants saying to them, because
the four tables were built together and only a reviewer can keep them
together.

## The audit

`GET /api/table/T357/audit` returns two findings and `clean: false`:

    Tags: "functional analysis" reaches only this table; a tag that leads
          nowhere else leads nowhere
    Tags: "inequality" reaches only this table; a tag that leads nowhere else
          leads nowhere

**I disagree with both.** They are right in form and wrong here, and the
message is the wrong way round. The check
(`management/commands/audit_table.py:414`) reads `Tag.table_count`, which
counts published tables and so cannot see a draft. `/tags` shows "inequality
(1 table, 1024 entries)" and "functional analysis (1 table, 1024 entries)", and
`/tags/inequality` lists that one table: **T92**, published. So each tag
already reaches a table that is not this one, and the sentence "reaches only
this table" describes the opposite of the situation. Beyond that, T354, T355
and T356 carry both tags, which is the skill's own test — "propose a new one
when three or more tables would carry it, counting the others in the same
batch" — satisfied five times over once this batch is published.

Nothing needs doing about the tags. What the audit does *not* report is
finding 1: `audit_table.py:447` reads `program.get('code') if isinstance(
program, dict) else ''`, so the one check that looks at `Programs` guards
itself against exactly the malformed shape that makes the page raise, and
says nothing about it.

## Noted only

Things I noticed and would not spend a review on.

* **Every value is an algebraic number, and some are short ones.** For
  rational $t$, $t^{1/t}$ is a radical, so every $Y^{(n)}_{p,q}$ here is a
  product of rational powers of rationals. Two of them are recognisable:
  $Y^{(n)}_{3/2,3/2}=(\sqrt3/2)^n$ and $Y^{(n)}_{4/3,4/3}=(2\cdot3^{-3/4})^n$,
  both of which reproduce the stored 100 digits exactly. There is no exact
  type for these, so storing them as reals is right; but the batch's house
  style names such values — T354's `rigour details` names
  $S_{2,1/2}=\pi^{1/4}$, and T356 returns its endpoint rows as the exact
  integer 1 — and a single `Comments` line saying the values are algebraic,
  with $\sqrt3/2$ as the example, would answer a reader who recognises one.
* **53 distinct values in each dimension's 56 rows.** $Y$ is symmetric in the
  triple $(p,q,r')$, not just in $p$ and $q$, which is what the second form
  $(A_pA_qA_{r'})^n$ in formula (1) is showing without saying so; formula (2)
  records only the $p\leftrightarrow q$ half. Three pairs of rows per
  dimension collide because of it — $(5/4,5/4)$ with $(5/4,5/2)$, $(5/3,5/3)$
  with $(5/4,5/3)$, $(4/3,4/3)$ with $(4/3,2)$. A reader who lands on one and
  sees the other has nothing on the page to explain it. Half a clause on
  formula (2) would.
* **1120 entries** is over the skill's recommended 1000 and under the 1200 soft
  limit, so it passes; 1064 of them are $n$-th powers of the 56 rows at $n=1$,
  which formula (1) makes plain. Storing them is right — somebody working in
  dimension 3 will not find their number in a one-dimensional table — but if
  finding 4 is acted on, the argument for $n\leq20$ is the thing to write
  down.
* **The rendered page is 732 kB**, the heaviest I have measured against this
  recipe (T315: 497 kB for 479 rows; T352: 351 kB for 600). Nothing in the
  skill limits it and the entries block is 128 kB, well under its 320 kB soft
  limit. Recording it because the number is a consequence of the row count and
  nobody sees it until the page is public.

# T240 critique: Independence polynomials of trees

Read 2026-09-14. T240 is a private draft owned by zeta3. It has 987 entries,
one for each tree on 1 to 12 vertices, keyed by graph6 string. The type is
`Z[]` and the rigour is `exact`.

The prose sections read well. The definition defines, the parameter
describes the family, the formulas are formulas, and all of them render.
What a reader will notice is on the rows and in one link:

- 26 entry comments name another tree by a key containing a backtick. The
  code-span markup breaks, and the key a reader needs is printed in pieces.
- The link to the lattice entropy table names an entry that does not exist.
  A reader who follows it lands on a warning.
- $P_{10}$, $P_{11}$ and $P_{12}$ print as $P_1 0$, $P_1 1$ and $P_1 2$.

Findings 1 to 3 are worth doing, and each is a small change to the
generator or to one line of the YAML. Findings 4 and 5 are worth doing while
the file is open. 6 to 8 are small. The rest are notes.

## Findings, ranked

### 1. 26 entry comments print the other tree's key in pieces (worth doing)

**What a reader sees.** On row `I??GQI?Kg`:

> It has the same independence polynomial as <code>I???P</code>D<code>_</code>.

The stored comment is ``It has the same independence polynomial as `I???P`D`_`.``
On row `J????CKo`b?` a reader sees "as <code>J????GW_jE?</code> and J???G?H_r<code>?</code>".

**Why it is wrong.** The comment is there so that a reader can go to the
other tree, and the name it prints is not a key in the table. Backticks
occur in 91 of the 987 keys, since the graph6 alphabet runs from `?` to `~`.
The renderer matches a code span as `` `([^`]+)` ``, so a span stops at the
first backtick inside a key. This affects 26 of the 211 shared-value
comments. The proposal `agents/lessons/proposals/20260913T225624Z-critique.md`
found the same fault in T237. The generator here copied T237's
`` "`%s`" % other `` (`generate.py` line 167).

**Smallest change.** Write the keys in plain text:
`labels = list(mates)`. In the preview, that renders 23 of the 26 correctly.
The other 3 still break, because a backtick pair remains in plain text too:
`I???P`D`_`, `J???O`_`GM?`, and the pair `J????CKo`b?` and `J???G?H_r`?`
named in one sentence. Nothing written in prose renders those correctly
today. `&#96;` inside a code span does reach the browser as a backtick,
because the prose is not escaped, but it stores HTML in the data and gives
it to every API client. The real fix belongs to the site: accept Markdown's
double-backtick span, ``` `` I???P`D`_ `` ```. I have written this down in
`docs/agent-environment.md`. Until that exists, plain text is the right
choice for the 23. For the 3, the choice is between the entity and waiting.

### 2. The link to the hard-core constants names an entry that does not exist (worth doing)

**What a reader sees.** In Similar tables: "the hard-core entry of the
lattice entropy table — the finite hard-core partition function of a graph
is its independence polynomial evaluated at the fugacity". The link goes to
`/Entropy_constants_of_lattice_models?entry=hard-core`, and that page opens
with "This table has no entry hard-core. It may have been renumbered or
removed; the table itself is shown below."

**Why it is wrong.** T153 has three parameters, and an entry's address is
all three: `hard-core,line,kappa`. `hard-core` alone is the first of them,
so it names a group of rows, not an entry. The reader is told the entry was
removed. Two smaller problems:

- The caption is a description, where every other row of Similar tables
  gives a table's title.
- The relation says "fugacity", while T153 says "activity", and it does not
  say which of T153's numbers relates to which polynomial here.

The precise relation exists, and this table's paths are an example of it.
T153's $\kappa=\lim Z_\Lambda^{1/|\Lambda|}$, with $Z_\Lambda$ the number of
independent sets, is $\lim I(\Lambda,1)^{1/|\Lambda|}$. On the line,
$I(P_n,1)=F_{n+2}$ gives $\varphi$, which is T153's own
`formula-hard-core-line`.

**Smallest change.**

```yaml
  - table: HREF{Entropy_constants_of_lattice_models}[Entropy constants of lattice models]
    relation: its hard-core constants are $\lim I(\Lambda,1)^{1/|\Lambda|}$ over finite regions $\Lambda$ of a lattice; on the line $I(P_n,1)=F_{n+2}$, and the constant is $\varphi$
```

If a row link is wanted, the address is
`Entropy_constants_of_lattice_models#hard-core,line,kappa`. That address
answers 200, and the page scrolls to the row.

### 3. $P_{10}$, $P_{11}$ and $P_{12}$ print with a one-digit subscript (worth doing)

**What a reader sees.** On row `K@GOOGA?Q@OA`, the path on twelve vertices:
"This is the path $P_12$", which typesets as $P_1$ followed by a 2. The
same happens on the rows for $P_{10}$ and $P_{11}$.

**Why it is wrong.** TeX takes a single token as a subscript. The stars are
right because their format already has braces.

**Smallest change.** In `generate.py` line 149, change `"path $P_%d$"` to
`"path $P_{%d}$"`.

### 4. A reader holding a tree cannot find its row (worth doing)

**What a reader sees.** `comment-graph6` explains how to go from a name to a
tree ("Recover the tree in Sage with $\texttt{Graph(name)}$"). It never
explains how to go from a tree to its name. It says the name is "taken after
a canonical relabelling", without saying which one.

**Why it is wrong.** The page has two kinds of reader: one arrives with a
polynomial, the other with a tree. The second has nothing to type. graph6
strings depend on the labelling, and different canonical-labelling
algorithms give different strings for the same tree, so "a canonical
relabelling" does not let two people build the same keys. The generator
uses `canonical_label(algorithm='sage')`. In the Sage image the default
agrees on all 987 trees. The default is bliss where bliss is installed, and
I could not test bliss here.

**Smallest change.** Replace the last sentence of `comment-graph6` with:
"The name of a tree `T` is `T.canonical_label(algorithm='sage').graph6_string()`
in Sage, and `Graph(name)` recovers the tree." None of those calls contains a
backtick or an underscore that could break. Using backticks rather than
`$\texttt{}$` also follows the pending proposal
`20260913T221523Z-critique.md`.

### 5. The definition defines $I$ for trees, and the formulas use it for every graph (worth doing, small)

**What a reader sees.** The definition begins "The independence polynomial
$I(T,x)$ of a tree $T$ is ...". The formulas then use $I(G,x)$ and
$I(G\sqcup H,x)$, and formula (3) uses $I(L(G),x)$ for a line graph, which
is not a tree except when $G$ is a path. The definition ends "The table
stores this polynomial in $\mathbb{Z}[x]$".

**Why it is wrong.** Nothing on the page defines $I(G,x)$ for a graph that
is not a tree, although three formulas need it. Nothing about the
definition is special to trees; the title and the parameter already say
what is held. The last sentence repeats `type: Z[]` and is not part of the
definition.

**Smallest change.** "The independence polynomial of a finite simple graph
$G$ is $I(G,x)=\sum_{k\geq0} s_k(G)\,x^k$, where $s_k(G)$ is the number of
sets of $k$ vertices of $G$ no two of which are adjacent CITE{MathWorld}."
The sum ends at the independence number, so $\alpha$ need not be introduced.
Then drop the last sentence.

### 6. Programs enumerates vertex subsets where the table already names Sage's method (small)

**What a reader sees.** Programs holds four lines that iterate over all
$2^n$ vertex subsets, build each induced subgraph, and keep the edgeless
ones. `rigour details` says the build checked "agreement with the clique
polynomial of the complement".

**Why it is wrong.** For a reader who wants one more value, the snippet
should be the library call, and the table names it already. This is the
T239 lesson (`agents/lessons/proposals/20260913T234000Z-critique.md`) again.
On $P_{16}$, the snippet takes 4.4 s and
`G.complement().clique_polynomial()` takes 0.001 s. The two agree, and they
agree with all 987 stored rows. The snippet also ends in a bare expression,
which prints nothing when it is run as a script.

**Smallest change.**

```python
G = Graph('F@HSO')                           # the path P_7, by its name here
print(G.complement().clique_polynomial())    # t^4 + 10*t^3 + 15*t^2 + 7*t + 1
```

### 7. `comment-range` is about the table, and the range is not argued (small)

**What a reader sees.** "The table stores trees rather than arbitrary
connected graphs. The independence polynomial of a forest is the product of
the independence polynomials of its connected components." Under Data
properties: "complete: no (it holds every tree on at most twelve vertices)".

**Why it is wrong.**

- The first sentence is a remark about this website, and the title already
  says it.
- The second sentence is formula (2), written again in words.
- Neither says why the table holds trees, or why it stops at twelve
  vertices, and the skill asks the completeness note for that sentence. The
  arithmetic is easy to state: trees on at most 12 vertices give 987
  entries, and 13 vertices would add another 1301.

**Smallest change.** Delete `comment-range`. Make the complete-note: "it
holds every tree on at most twelve vertices, 987 of them; the 1301 trees on
thirteen would take the table past the entry limit". If there is a
mathematical reason to hold trees rather than connected graphs, say it in a
comment instead. The unimodality question for trees is the usual one, but I
did not check its current status, so I have not drafted that sentence.

### 8. Two Similar-tables relations say only that the keys agree (small)

**What a reader sees.** Chromatic polynomials and Tutte polynomials both
have the relation "uses the same canonical graph6 naming convention for
connected graphs".

**Why it is wrong.** The relation is true, since the 25 small trees are keys
in both tables. But it describes the website's naming convention rather
than the mathematics, and it does not tell a reader what they will find.
For trees, the answer is always the same: all 25 stored chromatic
polynomials are $x(x-1)^{n-1}$, and all 25 Tutte polynomials are $x^{n-1}$.

**Smallest change.** "holds the trees on at most 7 vertices under the same
keys; every tree on $n$ vertices has chromatic polynomial $x(x-1)^{n-1}$"
and "... has Tutte polynomial $x^{n-1}$".

## Noted only

- **The first two trees have different names in the sibling tables.** Here
  `@` and `A_` are "the path $P_1$" and "the path $P_2$". In T125 and T239
  they are "the complete graph $K_1$" and "$K_2$". Both names are true, but
  a reader comparing rows sees two.
- **The link to T239 is dead until T239 is published.** Both tables are
  drafts, and the audit allows that, but T239 should be published first or
  together with T240.
- **Formula (3) can be illustrated here only by paths.** A line graph of a
  tree is itself a tree only for a path (11 trees in range), where it reads
  $M(P_n,x)=I(P_{n-1},x)$. Saying so would give a reader a row pair to check.
- **`comment-shared-values` could give the counts:** 874 distinct
  polynomials among 987 trees, the smallest shared pair on 8 vertices.
  A reader holding a polynomial learns how often a match is ambiguous.
- **Two keywords are never mentioned on the page.** "Independent set
  polynomial" and "stable set polynomial" are plain synonyms of the title,
  so a reader who typed them is not left guessing. The bare keyword
  "hard-core" is only explained through finding 2's relation.
- **"Merrifield-Simmons"** is a pair of names and would usually take an en
  dash. It is harmless.

# Lessons proposed by the triage of build run 20260923T111320Z

Nothing here is in force. A person reads it, and what is worth keeping lands as

Two lessons, both about what the API does, both reachable by a contributor with
a laptop and a key. Neither comes from the run being triaged: it died on turn 1
with a configuration error and met no mathematics at all. They come from trying
to answer the triage prompt's own question -- *what did it leave behind, check
the draft list through the API* -- and getting the wrong answer twice before
getting it right.

Related and already filed, not repeated here: that no API call lists your own
drafts or reads a draft's offered state
(`agents/lessons/proposals/20260923T073929Z-triage.md`), and that `GET
/api/tables` is the creation endpoint answering 405
(`agents/lessons/proposals/20260923T090929Z-triage.md`). The first lesson below
is the singular `/api/table`, which is a different path and behaves differently
again.

---

## A table is read with `GET /api/table?id=<TID>`; the path form `GET /api/table/<TID>` is 405, even though `/api/table/<TID>/audit` works

What happened: wanting to know whether a failed build had half-created a table,
I probed ids with `GET /api/table/T441`. Every id answered

    405  {"error": "Use POST or PUT."}

with no `Allow` header -- including ids that certainly exist, and ids that
certainly do not. Each response is 29 bytes, so a probe loop that compares
response *sizes* across ids sees a flat line and concludes every id is alike,
which is true and useless. I read that as "T441 is gone" for several calls
before checking the path.

The confusing part is that the same prefix does serve a GET one level deeper.
Measured against numberdb.org on 2026-09-23:

    GET /api/table/T441        -> 405  {"error": "Use POST or PUT."}
    GET /api/table/T444        -> 405  {"error": "Use POST or PUT."}   (T444 is published)
    GET /api/table/T441/audit  -> 200  {"findings": [], "clean": true}
    GET /api/table?id=T441     -> 200  the full table
    GET /api/tables            -> 405  {"error": "Use POST."}

So `/api/table/<TID>` is the *edit* endpoint (POST/PUT), `/api/table/<TID>/audit`
is a readable sub-resource, and the table itself is read from the collection
path with a query parameter. Three shapes under two spellings of one noun.

What the skill says now: it gives `GET /api/table?id=<TID>` where it shows a
read, and `GET /api/table/<TID>/audit` where it shows an audit, but never says
the path form of the read does not exist. A reader who has just used
`/api/table/T441/audit` will guess `/api/table/T441` for the table, and the 405
names a method rather than the path, so it reads as "you used the wrong verb"
rather than "you used the wrong URL".

What it should say: one sentence beside the read example -- a table is fetched
as `GET /api/table?id=<TID>`; `GET /api/table/<TID>` is not a read but the edit
endpoint and answers 405 `Use POST or PUT.`, notwithstanding that
`/api/table/<TID>/audit` is a GET.

Evidence: the five requests above, 2026-09-23, anonymous and keyed alike.
`curl -sSI https://numberdb.org/api/table/T441` returns no `Allow` header.

## An unpublished draft answers `200 {"error": "... does not exist."}` to anyone without the owning key -- byte-identical to an id that was never used

What happened: having found the right path, I checked which ids exist by
comparing keyed and anonymous responses. The anonymous response for my own
finished draft is:

    GET /api/table?id=T441   ->  200  {"error": "Table with id 'T441' does not exist."}

T441 does exist. It is a draft with 903 entries and a clean audit, readable in
full (28985 bytes) at the same URL with the owner's key. And the answer for an
id that has never been used at all is:

    GET /api/table?id=T999   ->  200  {"error": "Table with id 'T999' does not exist."}

The same 49 bytes, but for `T441`/`T999`. Two things follow, and the second is
the one that costs money:

1. **The status is 200, not 404 or 403.** A client written the obvious way --
   `r.raise_for_status()`, or `if r.ok:` -- treats a missing table as a success
   and goes on to parse `r.json()["Numbers"]`, failing later and somewhere else
   with a `KeyError`. Errors are carried in the body, so the body must be
   checked for an `error` key on every read.
2. **Visibility is reported as non-existence.** There is nothing in the
   response distinguishing *"this draft exists and you may not see it"* from
   *"nothing was ever created under this id"*. A contributor who creates a
   draft, then checks it from a browser, a second terminal, or any request whose
   `Authorization` header did not survive -- a shell quoting slip, a proxy that
   strips it, `curl -K` misused -- is told in plain words that their table does
   not exist. The natural next move is to create it again, and the duplicate
   title is then refused, which reads as a third unrelated failure.

What the skill says now: nothing about how a draft appears to an unauthenticated
reader, and nothing about errors arriving under 200. It says a draft is
invisible until published, which is true and is not the same statement.

What it should say: two sentences where drafts are introduced. First, that every
`/api/table` read returns 200 and signals failure with an `error` key in the
body, so the body is what to check. Second, that an unpublished draft is
reported to an unkeyed reader as `{"error": "Table with id '<TID>' does not
exist."}` -- so seeing that message means either the id is unused *or* your key
did not reach the server, and the way to tell them apart is to re-send the
request with the key rather than to create the table again.

Evidence: 2026-09-23, numberdb.org. T441 (own draft, 903 entries, audit clean),
T444 (published), T999 (unused):

    anon  ?id=T441 -> 200  49 B  {"error": "Table with id 'T441' does not exist."}
    anon  ?id=T999 -> 200  49 B  {"error": "Table with id 'T999' does not exist."}
    anon  ?id=T444 -> 200  3997 B  full table
    keyed ?id=T441 -> 200  28985 B  full table
    keyed ?id=T999 -> 200  49 B  {"error": "Table with id 'T999' does not exist."}

Published tables (T444) read identically with and without a key, which is what
makes the draft case easy to miss in testing: everything a contributor can see
on the site behaves, and only their own unpublished work lies to them.

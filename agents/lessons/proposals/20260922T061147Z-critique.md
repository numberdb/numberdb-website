# Proposed lessons from the T400 critique, 2026-09-22

Stage three, reading draft T400 ("Kirchhoff indices of connected graphs", 996
exact rationals indexed by canonical graph6 string). Nothing here is in force.

## Run the `Programs` snippet and compare it with the row it names

What happened: T400's values are right — all 996 reproduce from the Laplacian
characteristic polynomial and again from an exact resistance-distance
computation — and its generator is right:
`generate.py` reads `c2 = QQ(polynomial[2])`, matching the table's own formula
$\mathrm{Kf}(G)=-nc_2/c_1$. The `Programs` block on the page reads
`-QQ(n) * QQ(p[n - 2]) / QQ(p[1])`. It names its own row in a comment
(`Graph('FjaHw')   # the Moser spindle`), that row says `29/2`, and the snippet
run verbatim under Sage returns **−49/48**. The two forms agree at $n=4$ and
nowhere else, so a spot-check on $K_4$ or the diamond passes it.

The `Programs` block is a *second implementation* of the quantity, written by
hand after the generator, usually shortened, and nothing anywhere checks it:
not `audit_table`, not `verify`, not the build's own cross-checks, which all
read the generator. It is also the one block on the page a reader is invited to
execute, so a mistake in it tells that reader the table is wrong.

What the skill says now: "**Programs** | the standard incantation for a reader
who wants one more value | the generator". It says what to put there and not
that it has to be run.

What it should say: before offering the draft, run the `Programs` snippet
exactly as it will be printed — copied out of the document, not out of the
generator — and check that it returns a value the table stores. Make it name
the row it reproduces, so the check is one comparison and the reader can make
it too. A snippet that computes an index into a polynomial, a term of a
sequence or a precision is the usual place this goes wrong, because those
coincide for whatever example was tried first.

Evidence: 2026-09-22, T400 critique. Under `agents/sage.sh`:
`Graph('FjaHw').laplacian_matrix().charpoly()` is
`x^7 - 22x^6 + 196x^5 - 900x^4 + 2228x^3 - 2784x^2 + 1344x`; as printed
`-7*p[5]/p[1] = -49/48`, with `p[2]` it is `29/2`, which is the stored value.
Also `BW` (−3 vs 4), `DLo` (−7 vs 10), `E~~w` (5/18 vs 5).

## An index that can contain a backslash needs a raw string in the comment that tells a reader how to use it

What happened: T400 and its five sibling tables name each graph by its
canonical graph6 string, and graph6 uses every character from `?` to `~` —
including the backslash and the backtick. Of T400's 996 names, 74 contain a
backslash and 14 of those have a Python escape letter after it: `FC\ng`,
`F?\tw`, `FT\uW`, `FC\rW`, `F?\vw`, nine more. Each table's comment tells the
reader to "Recover the graph in Sage with `Graph(name)`". A reader who pastes
the name off the page into ordinary quotes is not holding that name:
`Graph('FC\ng')` raises `RuntimeError: the string (FC) seems corrupt: for n =
7, the string is too short`, and `Graph('FT\uW')` does not parse at all. It
fails loudly, which is the good case, but the diagnostic names neither the
cause nor the cure, and it fails on 14 rows of the reader's own table.
`Graph(r'FC\ng')` gives the right seven-vertex graph.

What the skill says now: nothing about this. It has a rule about *keys as
addresses* and one about defining notation, but nothing about a key whose text
is also program text.

What it should say: when a table's keys are strings a reader is told to paste
into code, check whether any key contains a backslash, a quote or a backtick,
and write the instruction in a form that survives them — a raw string,
`Graph(r'FC\ng')`, with a real key from the table as the example rather than a
clean one. (A related trap already in `docs/agent-environment.md`: a key
containing a backtick cannot be written inside backticks in prose at all, so
name such graphs in words and leave the strings to the row labels, which is
what T400 does.)

Evidence: 2026-09-22, T400 critique, under `agents/sage.sh`: the `RuntimeError`
above for the typed `'FC\ng'`, and `Graph(r'FC\ng')` → 7 vertices, 12 edges,
canonical name `FC\ng`.

## Pin `canonical_label(algorithm=...)` when the canonical form is the key

What happened: T400 stores
`g.canonical_label(algorithm='sage').graph6_string()` and says so in both its
comment and its `rigour details`; the older sibling
`Characteristic_polynomials_of_connected_graphs` tells its reader
`g.canonical_label().graph6_string()`. Sage's `canonical_label` defaults to
`algorithm=None`, which selects bliss when the optional bliss package is
installed and Sage's own algorithm otherwise — the two need not agree on which
labelling is canonical. When the canonical form *is* the name of the row, a
name that depends on what the reader has installed is not a name.

I could not demonstrate a disagreement: bliss is absent from the image
`agents/sage.sh` runs (`import sage.graphs.bliss` → `ModuleNotFoundError`), and
with it absent the default and `algorithm='sage'` agree on every key I tried.
So this is an argument from the API, not a measurement, and whoever promotes it
should say so or find the counterexample.

What the skill says now: nothing about canonicalisation as an index.

What it should say: when entries are keyed by a canonical form, name the
algorithm that produced it, in the document and in the instruction given to the
reader. The keys are frozen at publication and a citation resolves on them.

Evidence: 2026-09-22, T400 critique. `sagecheck.py` and `sage2.py` under
`agents/sage.sh`: `bliss present: False`, and `canonical_label()` ==
`canonical_label(algorithm='sage')` for five keys including the Moser spindle
`FjaHw`, the backslash key `FC\ng`, and the backtick key E@\`w.

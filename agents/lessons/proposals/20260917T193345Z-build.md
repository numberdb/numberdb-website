## Sage's HOMFLY-PT `vz` normalisation uses the opposite Jones substitution from the common `az` formula
What happened: the HOMFLY-PT generator first checked the KnotInfo/Sage `vz`
normalisation with the Wikipedia-style substitution $v=t^{-1}$ and
$z=t^{1/2}-t^{-1/2}$. The dry run stopped at $3_1$: KnotInfo has
$P(v,z)=2v^2-v^4+v^2z^2$, and that substitution does not give the Jones
polynomial of the right-handed trefoil. Sage documents `normalization='vz'`
as $v^{-1}P(L_+)-vP(L_-)=zP(L_0)$, and the check agrees when it uses
$v=t$ and $z=t^{-1/2}-t^{1/2}$.
What the skill says now: check identities before writing them down, but
nothing about the two HOMFLY-PT coordinate systems.
What it should say: for HOMFLY-PT tables, state which skein relation the
chosen coordinates satisfy before specialising. The Jones substitution for
Sage/KnotInfo `vz` is $v=t$, $z=t^{-1/2}-t^{1/2}$; do not reuse the
$\alpha=t^{-1}$ formula from the `az` convention without checking it on the
trefoil first.
Evidence: T312 dry run first failed with
`ArithmeticError: 3_1: the HOMFLY-PT Jones specialisation disagrees`; after
changing the substitution, `dry_run.py` computed 958 entries and the
KnotInfo CSV check reported `checked 250 KnotInfo HOMFLY-PT polynomials` and
`all agree`.

## The one-quantity audit is prose-blind and can remain as a reviewer question
What happened: T312 intentionally has `knot: K | mirror`, matching T139's
mirror-image convention, and `normalisation: vz | lm`, matching the family
instruction that the two HOMFLY-PT coordinate systems belong together. The
definition was changed to say that `normalisation` is an invertible coordinate
choice and `knot` is the mirror choice for an unoriented knot name, but
`api/table/T312/audit` still reported both parameters as possible table
splits. The audit implementation does not read prose for this rule; it only
reports the structural shape on drafts.
What the skill says now: if the audit reports a table holding several named
quantities, split it unless it is one object in parts, one number in two
conventions, or a parameter that is an argument, and say which exception
applies.
What it should say: a legitimate exception can still leave this audit finding
on a draft, because the check is intentionally prose-blind. Act by making the
exception explicit in the definition and by reporting the remaining finding as
a reviewer question; do not split a family convention merely to make this
structural warning disappear.
Evidence: T312 audit after the definition edit still returned the two
findings for `knot` and `normalisation`, while `verify(sample=None)` reported
`958/958 matched`.

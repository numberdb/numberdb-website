## OEIS's JSON API answers `null`, not `[]`, when nothing matches

What happened: screening the batch meant asking OEIS whether it already held
the $\psi$-intersection numbers, the Weil--Petersson volumes and the Hodge
integrals. The obvious loop

    u = 'https://oeis.org/search?q=%s&fmt=json&start=0' % quote(query)
    with urllib.request.urlopen(Request(u, headers=UA)) as a:
        d = json.load(a)
    results = d.get('results') or []

ran fine for `Weil-Petersson volume moduli`, which has hits, and then died on
the next query with

    AttributeError: 'NoneType' object has no attribute 'get'

OEIS returns HTTP 200 with the four bytes `null` when a search has no
results. `json.load` turns that into Python `None`, and `None.get` raises --
inside a loop over queries, that stops the whole screen on the *first query
that found nothing*, which is the ordinary case for a family the database
does not hold.

What makes it expensive is how it reads. An exception at an HTTP call looks
like the site being down or blocking you, and this host does sometimes get a
Cloudflare challenge from `oeis.org`, so the natural reading is "OEIS is
unreachable today, screen without it". The truth is the opposite: OEIS
answered, and the answer was *no such sequence* -- which is a result worth
having, and is often the thing that justifies the table.

What the skill says now: OEIS is named as a link target and as a place to
look for a polynomial family's coefficient triangle. Nothing about its API.

What it should say: when you check a family against OEIS from a script,
`fmt=json` returns a bare `null` for an empty result, so write

    d = json.load(a)
    results = (d or {}).get('results') or []      # None means "no hits"

and never let a bare `except` around the call collapse "OEIS says no" into
"OEIS did not answer". The corpus already has this lesson in another costume
-- `already_here` in `agents/table-ideas/screen.py` goes out of its way so
that a failed question and an empty answer do not look the same, and the
skill records a run where a bare `except` around `numberdb.table()` turned a
rate limit into a missing table. This is the same shape at a different API.

Evidence: 2026-09-23. `oeis.org/search?q=psi+classes+moduli+space+of+curves&fmt=json`
-> HTTP 200, body `null`; `q=Weil-Petersson+volume+moduli` -> a JSON object
with two results, A115047 and A143083. The scan that finally ran found
A007888 (*Euler characteristic of mapping class group Gamma_n*), which went
into the batch as a check to be resolved rather than used.

## `source_names_it` catches a misremembered citation, and says it like a misnamed family

What happened: the batch needed a source for "Weil-Petersson volumes", and
the paper is Mirzakhani's. The arXiv identifier went into the screen from
memory. The screen answered:

    the source does not mention weil, petersson, volumes -- either the name
    is not what this family is called, or the wrong page was cited:
    https://arxiv.org/abs/math/0602012

Both halves of that sentence are offered, and the first one is the one a
reader takes, because it is the failure the check was built for. The name was
right. `math/0602012` is *On a special congruence of Carlitz*, by Sandro
Mattarei -- a real paper, fetched fine, HTTP 200, 38 kB, and about nothing in
this batch. A digit of the identifier was wrong.

The same thing happened again two proposals later, in the other direction:
"Hodge integrals of the lambda_g class" failed against `math/9810173` with
*the source does not mention lambda*. That one was a genuine miss -- the paper
is *Hodge integrals and Gromov-Witten theory* and never writes the letter --
and the fix was the other Faber--Pandharipande paper, `math/9908052`, whose
title is literally *Hodge integrals, partition matrices, and the lambda_g
conjecture*. Same message, opposite cause.

What the skill says now: `source_names_it` is described as the check against
*inventing* a family -- "a proposal for the Zhang-Liu polynomials citing a
real Wikipedia article that says nothing of them fails here". It is silent on
the far more likely case: the family is real, the name is right, and the
identifier is wrong.

What it should say: when `source_names_it` reports missing words, read the
cited page's **title** before touching the family's name. If the title is
about a different subject, the URL is wrong and the name is fine; if the
title is about the right subject and the words are still missing, the name is
wrong. Two lines settle it:

    body = fetch(url); text = strip_tags(body)
    print(re.search(r'Title:\s*(.{0,120})', text).group(1))

Never write a citation identifier -- an arXiv number, a DOI, an OEIS
A-number -- from memory. Look it up and paste it. `source_names_it` is a
better check than it is documented to be, and treating it as "is this family
real" throws away the half of its power that catches a slipped digit.

Evidence: 2026-09-23. `math/0602012` -> *On a special congruence of Carlitz*;
the paper wanted was reachable as `1103.4674` (Do, *Moduli spaces of
hyperbolic surfaces and their Weil-Petersson volumes*), against which the
same name passes. `math/9810173` -> *Hodge integrals and Gromov-Witten
theory*, no "lambda"; `math/9908052` -> *Hodge integrals, partition matrices,
and the lambda_g conjecture*, passes.

## Apply the small-integer test by counting, not by looking

What happened: the batch's first proposal is the intersection numbers
$\langle\tau_{d_1}\cdots\tau_{d_n}\rangle_g$, and the skill's warning is
sharp -- values that are a handful of small integers "match everything and
tell nobody anything", and putting them in a table makes search by number
worse for everyone. Reading the first dozen entries is no way to decide that:
they are $1$, $1$, $1/24$, $1$, $1/24$, $1/1152$, and they look bad.

Counting the whole proposed range says something different:

    entries                                630
    distinct values                        481
    values that are an integer below 100    71  (11%)
    the same, with genus 0 excluded         23  ( 5%)
    most repeated:  1 (x14), 1/24 (x12), 1/1152 (x8), 210 (x7)

Three numbers and the decision makes itself: the family is distinctive, and
the small integers are not scattered through it but concentrated in one
sub-family -- genus 0, where the closed form
$\langle\tau_{d_1}\cdots\tau_{d_n}\rangle_0=(n-3)!/\prod d_i!$ makes every
value an integer. That turns a yes/no argument into a range decision, which
is a much better argument to hand the builder: *keep genus 0 and say why*,
or *start at $g=1$*, rather than *this family is fine* or *this family is
not*.

The same count run on the batch's fourth proposal, the orbifold Euler
characteristics, went the other way and changed the proposal: genus 0 there
is $\pm(n-3)!$, factorials and nothing else, so it was excluded from the
table and moved into `Formulas`.

What the skill says now: the class-number argument, stated as a judgement --
"class numbers are mostly 1, 2, 3".

What it should say: before proposing a family, compute the distinct-value
count and the share of entries whose value is a small integer, over the
range you actually mean to publish, and put both numbers in the proposal. A
family with 481 distinct values in 630 entries is not the class-number case
whatever its first dozen rows look like; a family with 40 distinct values in
600 is, whatever its formula looks like. The count also localises the problem
to a sub-range, which a judgement cannot.

Evidence: 2026-09-23, `/tmp/dist.py`, over every stable $(g,n)$ with
$3g-3+n\le11$.

## The cost of a family can sit at the opposite end of the index from where you look

What happened: the Weil--Petersson volume $V_{g,n}$ is a number attached to a
surface of genus $g$ with $n$ marked points, and the obvious worry when
picking a range is large $g$: higher genus, harder geometry, bigger numbers.
$V_{4,0}$ has a 26-character rational in it and $V_{1,1}$ has four.

Timed across the whole index at fixed complex dimension $D=3g-3+n$, the cost
runs the other way:

    V_{3,0}  D=6   0.00s          V_{0,9}   D=6    1.52s
    V_{3,1}  D=7   0.04s          V_{0,10}  D=7   10.34s
    V_{3,2}  D=8   0.51s          V_{0,11}  D=8  101.26s
    V_{2,5}  D=8   5.73s          V_{1,8}   D=8   33.90s

Two hundred times slower at the *low*-genus end of the same dimension,
because the work is a sum over profiles of $n$ marked points and $n$ is what
grows when $g$ shrinks at fixed $D$. A range chosen by testing $g=1,2,3,4$ at
small $n$ -- the natural thing to do -- would have reported a table that
takes a second, and then hung for a quarter of an hour on $V_{0,12}$.

What the skill says now: "two things move it down: expensive digits, and
values that grow", and the worked cost analysis is the polynomial one, where
degree is the only index.

What it should say: for a family with more than one index, time the corners of
the range, not one index with the others held small. Where a constraint ties
the indices together -- here $\sum d_i = 3g-3+n$, so fixing the dimension
trades $g$ against $n$ -- the extreme of the cost is usually at an extreme of
the *constraint*, which is not the extreme of either index. Say in the
completeness note which corner set the cutoff; "3g-3+n <= 8, because
$V_{0,11}$ is 101 s and $V_{0,12}$ is the next one" is a note the next person
can act on, and "3g-3+n <= 8" alone is not.

Evidence: 2026-09-23, `/tmp/vtime.py`, pure Python with
`fractions.Fraction`, one core.

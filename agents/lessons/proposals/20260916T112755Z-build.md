## Replacing an empty draft document through `/api/table/<tid>` still needs entries

What happened: T271 was claimed as an empty draft with `POST /api/tables` and
`X-Draft: yes`. After measuring the range, the run tried to replace the
provisional prose through `POST /api/table/T271` with a complete document that
still had no `Numbers` section. The API refused it with `A table needs at
least one entry`. Sending `X-Draft: yes` to the edit endpoint did not change
the refusal. Filling the draft first, then merging the stored `Numbers` tree
into the final table document and posting that whole document, succeeded.

What the skill says now: a draft may be proposed with no numbers, and the
numbers should arrive after the prose is settled. It does not say that the
create endpoint and the replace-document endpoint differ here.

What it should say: make the first empty draft document as close to final as
the settled definition allows. If the range-dependent prose must be changed
before numbers exist, either use an editing route that accepts an empty draft
or wait until after the first replace-mode fill and include the stored
`Numbers` tree in the document replacement. Do not post a whole document
without `Numbers` to `/api/table/<tid>` and expect `X-Draft: yes` to preserve
the empty-draft exception.

Evidence: T271, 2026-09-16. The first document replacement without entries
returned `{"error": "A table needs at least one entry", ...}`; the same
request with `X-Draft: yes` returned the same refusal. After the generator
submitted 770 entries, posting `/tmp/wilson-table.yaml` merged with the
stored `Numbers` mapping returned revision
`a78c87953bd9856eaaf0f8e2986401dca7dbea369464493ab063b2a18005bfd8`.

## Draft tag audits do not count a one-table tag's planned family

What happened: T356 belongs to issue #167, whose family instructions say to
tag every table `functional analysis` and `inequality`. The family text says
both tags already exist and each reached exactly one table, T92, when the
batch was screened; the point of the batch is to make them useful routes
through several sharp-inequality tables. After T356 was filled, its audit
still reported both tags as single-table tags:

    Tags: "functional analysis" reaches only this table
    Tags: "inequality" reaches only this table

Removing the tags would have made T356 disagree with its family and with T92,
so the draft was left with the family tags and the audit finding was reported
for review.

What the skill says now: prefer existing tags, and audit refuses a tag that
reaches only this table. It does not say what to do when a proposal family
deliberately reuses a one-table tag across several sibling drafts so the tag
will become a route after review.

What it should say: when the family explicitly assigns an existing tag that
currently reaches only one published table, keep the family tag rather than
substituting a broader one solely to silence a draft audit. Report the audit
finding and name the table that already carries the tag and the sibling drafts
expected to carry it. A review can then decide whether the family is large
enough to make the tag useful.

Evidence: `python3 agents/queue.py show 167` says all six tables use
`functional analysis` and `inequality`, and that both tags reached exactly one
table at screening time. `GET /api/table/T356/audit` on 2026-09-20 reported
only those two tag findings after the definition was shortened.

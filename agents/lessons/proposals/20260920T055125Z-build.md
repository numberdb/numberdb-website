## Do not first-fill a title-only draft before the parameters exist
What happened: T362 was claimed with only its `Title`, then the first-fill
workaround sent 752 Gaunt coefficient entries through `/api/table/T362/entries`.
Because the draft document had no `Parameters` section, the table accepted the
entries but treated the table as parameterless: `GET /api/table?id=T362`
returned `Numbers` as a bare list of 752 decimal strings, with no `l1,m1,...`
labels visible in the API view. The values had to be rebuilt from the
generator after the full prose document was written, so every row again
carried `params`.

What the skill says now: create the draft before building, "Title first, prose
if you have it, no numbers", and later fill it once. Existing lessons say that
a fresh draft with no `Numbers` section may refuse the client's empty upsert
probe, but they do not say that a title-only draft also lacks the parameter
order needed to preserve identities on the first entries write.

What it should say: when claiming with the API, include the `Parameters`
section before the first entries write, even if `Numbers` is empty. If the
draft was claimed with only a title, do not fill it through the entries
endpoint yet; first create or rewrite a document that declares the parameters,
or build the full document and entries together so the first stored rows have
named parameter values.

Evidence: T362, 2026-09-20. The first entries write returned 752 entries, but
an authenticated `GET /api/table?id=T362` printed `Numbers shape: list 752`
and the first item was a decimal string. Rewriting from
`generators/gaunt-coefficients/table.yaml` with generator-built flat records
restored the parameterised table, and `generator.verify(sample=None)` then
reported `752/752 matched`.

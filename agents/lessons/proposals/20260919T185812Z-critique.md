# Lessons proposed by the T288 growth critique, 2026-09-19

## A range copied from a source's printed table is the source's range, not the family's

What happened: T288 holds $\xi_{k,\ell}$ for $2\leq k\leq7$ and
$1\leq\ell\leq6$, 35 entries in 13 KB -- a tenth of the soft block limit. Its
definition promises every $k\geq2$ and $\ell\geq1$ except one degenerate pair,
so the rectangle is a choice, and the choice is visible in the companion
table's generator:

    # Dietzfelbinger, Goerdt, Mitzenmacher, Montanari, Pagh and Rink print a
    # table indexed by the obstructing core degree. Their row l is this
    # table's bucket capacity ell = l - 1.

`PUBLISHED_TEN_DIGITS` there has exactly those 35 pairs. The range is the shape
of a table on a page in a 2010 conference paper -- what fitted, at ten decimal
places, beside the text. Nothing about it is a fact about which $(k,\ell)$ a
reader meets, and two things show it is wrong here: the corpus's own T287 holds
the same roots along $\ell=1$ out to $k=12$, so one column of the family
already runs further in a different table; and bucket capacity 8, which is what
implementations actually use, falls outside while 5 and 6, which nothing uses,
fall inside.

Copying the source's range is attractive because it comes with a free check --
every stored value can be compared against printed digits, and the T288 and
T274 generators both do that. That check is worth having. It is not a reason to
stop where the printing stopped.

What the skill says now: a great deal about *how many* entries and what they
cost, and the right rule in "Hold the numbers that turn up" -- "the question a
table has to answer about its range is not how many entries that makes ... but
whether anybody will arrive holding one of them", with a denominator bound as
the example of counting rather than choosing. It says nothing about the
commonest way a range gets chosen for a table drawn from a paper, which is
neither counting nor choosing: inheriting.

What it should say: a range taken from a table printed in the source is that
source's range. Use its values as the independent check and then ask the
question again for yourself: which parameters does a reader meet? Say in
`complete-note` why *this* rectangle, not merely which one. Two tests catch the
inherited case cheaply -- does the corpus already hold part of this family at a
wider range in another table, and does the range end exactly where a printed
table in a reference ends?

Evidence: 2026-09-19, T288 growth critique. `GET /api/table?id=T288`
(35 entries, $2\leq k\leq7$, $1\leq\ell\leq6$); `GET /api/table?id=T287`
($\xi_k$ for $3\leq k\leq12$, the same numbers along $\ell=1$ -- I recomputed
all ten and the 100-digit strings are identical);
`generators/cuckoo-hashing-thresholds/generate.py` lines 61-64 and its
`PUBLISHED_TEN_DIGITS` of exactly 35 pairs. Computing the extension to
$2\leq k\leq12$, $1\leq\ell\leq8$ took 2.6 seconds and 31 KB.

## Where a family tends to a closed form, the range ends where the digits stop distinguishing it

What happened: T288's values approach the integer $k\ell$ from below, and fast:
$\xi_{7,6}=41.99999999981\ldots$ and $\xi_{12,8}=95.999\ldots$ with thirty
nines. The gap is
$k\ell-\xi_{k,\ell}\approx k\ell\,e^{-k\ell}(k\ell)^{\ell}/\ell!$ -- checked
against the computed roots at $(7,6)$, $(12,8)$ and $(60,1)$, agreeing to the
digit at the first and third -- so the number of leading digits a stored value
shares with $k\ell$ grows linearly, about $\ell(k-1-\ln k)/\ln10$. Past sixteen
of them, anybody who computes the value in double precision gets exactly
$k\ell$ and can never arrive holding the stored number; past a hundred, the
stored value would be a decimal integer with a hundred digits of zeros after
it, which the skill already rules out for a different reason.

So the ceiling on this table's range is set by neither of the two things the
skill measures. The entries do not grow -- every value is 101 characters
whatever $k$ and $\ell$ are -- and they are not expensive: 87 roots at 100
digits in 2.6 seconds. Size and cost say "thousands of rows"; the mathematics
says the interesting region is a hyperbola-ish band near small $k$, and rows
outside it answer searches nobody can make.

What the skill says now: two things move the entry count down, "expensive
digits" and "values that grow", with polynomials as the worked example; and
separately, that a table of values which are "a handful of small integers ...
match everything and tell nobody anything". A family that *converges* to small
integers as its parameters grow is the second problem arriving through the
first door, and neither passage names it.

What it should say: when the family has an asymptotic limit with a closed form
-- $\xi_{k,\ell}\to k\ell$, a threshold tending to 1, a constant tending to
$\pi$ -- measure how many leading digits an entry shares with that limit before
choosing the range. Where the agreement passes about sixteen digits the entry
is unreachable by anybody computing in double precision, and where it passes
the table's own `digits` the entry *is* the limit. Stop at the first of those,
not at a size limit that will never bind, and put the reason in
`complete-note`.

Evidence: 2026-09-19, T288 growth critique. Roots recomputed with the table's
own bisection under `agents/sage.sh`; measured gaps $1.84\cdot10^{-10}$ at
$(7,6)$, $3.49\cdot10^{-29}$ at $(12,8)$, $3.15\cdot10^{-23}$ at $(60,1)$,
against $1.84\cdot10^{-10}$, $3.8\cdot10^{-29}$ and $3.15\cdot10^{-23}$ from
the formula. Every value 101 characters; 87 roots in 2.6 s; 880 rows would fit
the 320 KB block limit and the family stops being worth storing long before.

## A repair made to the document leaves the attached generator behind, and `verify()` is what says so

What happened: T288 was repaired on 2026-09-17 through the API -- a degenerate
row was dropped and the convention explaining it was taken out of the
definition, a formula, a comment, the program and `rigour details`. Two days
later the file attached to the table still enumerates the dropped row, still
returns `QQ(0)` for it, and still opens with a docstring explaining the
convention the table no longer states. Running it as its own header instructs:

    <VerifyReport T288: 35/36 matched, 0 differing, 1 missing, 0 extra>

So the program that is supposed to reproduce the table exits non-zero for
anybody who downloads it, and `--publish` would restore the deleted row with a
comment contradicting the page it appears on. Nothing warned: the audit is
clean, the table renders, and the drift is invisible from the document.

What the skill says now: "`generate.py` is the program that reproduces and
extends *this* table, attached to it", and, under checking the work,
"`verify(sample=None)` after publishing". Both are written about the moment the
table is filled. Nothing covers the commoner later moment, when a table is
corrected by hand or through the API and the generator is not touched.

What it should say: an edit that changes what the table *holds* -- a row
dropped, a range narrowed, a convention changed -- is an edit to the generator
too. Re-attach it in the same act, and run `verify(sample=None)` afterwards:
the report's "missing" and "extra" counts are the only thing that sees this
drift, since the audit reads the document and cannot know what the program
would produce. A stale generator is worse than none, because the next person to
extend the table starts from it.

Evidence: 2026-09-19, T288 growth critique. The attached file, run unchanged,
reports `35/36 matched, 0 differing, 1 missing, 0 extra`; this repository's own
sweep of attachments prints `RESULT MISMATCH T288` for it.
`curl 'https://numberdb.org/files/T288/generate.py?raw=1'` is byte-identical to
the pre-repair `generators/cuckoo-hashing-threshold-equation-roots/generate.py`
(12,492 bytes, `diff` empty); the live `Numbers` has no `2,1` key; the verify
report above came from running that attached file unchanged under
`agents/sage.sh`. The repair is recorded as done in
`agents/critiques/T288-repaired.md`, which lists the document fields it touched
and no file.

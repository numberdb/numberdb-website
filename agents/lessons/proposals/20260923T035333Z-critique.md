## A generator's enumeration order does not survive into a table with more than one parameter

What happened: T429 (Markov forms) is indexed by a triple `(m1, m2, m3)` and
its generator returns
`sorted(seen, key=lambda triple: (triple[2], triple[1], triple[0]))` — every
row in order of increasing $m_3$, which is the order anybody looking up a
Markov number wants. Its docstring says so, and the table's first comment
promises the reader the same thing: "listed by increasing $m_3$, then by
increasing $m_2$, then by increasing $m_1$".

The rendered page does not do that. `Numbers` is a mapping **nested by
parameter**, `m1 → m2 → m3`, so each value of the first parameter is a single
key and every row sharing it is forced contiguous, whatever order the
generator yielded. Inserting rows in $m_3$ order into that structure creates
each `m1` key at the first row carrying it, and what a reader ends up seeing is

    blocks by m1, the blocks in order of each block's smallest m3,
    each block in order of increasing m3

so the $m_3$ column runs 1, 2, 5, …, 956722026041 for thirty rows and then
starts again at 29, and the $m_1$ column runs 1, 2, 5, 13, 34, **29**, 89,
233, **169**, … The page looks unsorted, beside a sentence saying it is
sorted. Nothing in the generator, in `verify()`, or in `audit_table` sees this:
the values are all correct and the ordering claim is prose.

The rule that follows is arithmetic, not a quirk: **any row order that is not
grouped by the first parameter is unrepresentable.** Sorting a multi-parameter
table by anything but its first parameter is not merely ignored, it cannot be
stored. So the only two levers are the order of the blocks (choose the first
parameter's keys) and the order within a block — or a different parameter
order, which is frozen at publication because entry citations resolve on it.

What the skill says now: the opposite, in section 4 — "**Entries are shown in
the order the document writes them**, so the order the generator enumerates in
is what a reader sees." Its worked example is a single parameter running over
the negatives, where that is true. For two or more parameters it is false, and
the sentence reads as a guarantee.

What it should say: keep the sentence for one parameter and add the
qualification. Something like: *with more than one parameter, `Numbers` is
nested by the parameters in order, so rows sharing the first parameter's value
are contiguous however the generator enumerated. Sort the generator by the
first parameter first, or the order a reader sees will not be the order the
generator wrote — and before publishing, ask which parameter should come
first, because that choice decides the row order for good and cannot be
changed afterwards.* It belongs beside the existing advice to put the small
cases at the top, since that advice fails the same way: enumerating by $|a|$
does nothing if $a$ is the third parameter.

Could a contributor with a laptop and Sage hit this? Yes, and silently — the
generator is right, the values are right, `verify()` passes, the audit is
clean, and only somebody reading the rendered page notices.

Evidence: 2026-09-23, T429 critique. `generators/markov-forms/generate.py`
`markov_triples()`; `GET /api/table?id=T429` with the key, whose `Numbers`
top-level keys are `1, 2, 5, 13, 34, 29, 89, 233, 169, 194, 610, 433, …`;
`/preview?table=` rendering the $m_1=13$, $34$ and $29$ blocks in sequence,
showing the $m_3$ column stepping 982145940029 → 14701. A test would assert
the added sentence in `numberdb_app/test_skill.py`.

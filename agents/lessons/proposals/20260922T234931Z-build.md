## `Generator.publish()` can fail its empty writable probe on a draft with no entries

What happened: draft T422 was created with prose and no `Numbers` section, as
the stage-two prompt asks. Running the generator's normal `publish()` path
against it failed before computing any values, in `_write.check_writable()`.
That probe sends an empty upsert to `/api/table/T422/entries`; on this empty
draft the server answered `A value in these entries cannot be read as a
number. 'str' object has no attribute 'items'`. A direct call to
`submit_entries()` with the complete list of 901 records succeeded, and the
same run attached `generate.py`.

What the skill says now: create the draft first and then fill it once with the
generator; it does not mention that the client's preliminary empty upsert can
fail specifically on a draft that has no entries section yet.

What it should say: if a freshly created empty draft makes
`Generator.publish()` fail in the writable check before it computes values,
do not treat that as a mathematical or permission failure. Either add an empty
entries section to the draft before using the generator, or send the complete
entries block directly with `submit_entries(..., upsert=False)` and attach the
generator file in the same run. The direct entries write should still use the
client's `to_text()` conversion and the same `X-Rigour`/run id headers, so it
does not bypass precision or provenance.

Evidence: 2026-09-23, T422. `NUMBERDB_PUBLISH=1 agents/sage.sh
generators/linear-sieve-function-F/generate.py` failed in
`check_writable()` with the error above. `/tmp/fill_linear_sieve_entries.py`
then computed 901 entries and `submit_entries(..., upsert=False)` returned
revision `e4e0884f3469e3fc999a0aa721261e300136fcaf62c0f55a6acc2d2607f4ba6b`;
attaching `generate.py` amended the same revision.

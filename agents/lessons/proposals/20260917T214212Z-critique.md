# Proposed by the T314 critique, 2026-09-17

## A `Size exception` is for a limit actually passed, not for a note that the table fits

What happened: T314 holds 479 entries in a 213.7 KB entries block, under every
limit there is, and carries a `Size exception` under Data properties saying so:
"... the dry run measured a 213.7 KB entries block and a longest entry of 500
characters, under the 320 KB soft limit". A reader meets a line whose whole
purpose is to explain why a limit was exceeded, and whose text says it was not.
The four published knot tables of the same shape carry none, and `audit_table`
reports no size breach for T314.

What the skill says now: "A soft limit may be passed by an author who explains
why, recorded in the table as `Size exception`." It says when the field is
allowed and not that it is only for that case, so a build that measured its
block carefully writes down what it measured.

What it should say: state the field's condition in the negative as well --
a table under the soft limits carries no `Size exception`; the argument for the
range belongs in the definition and in `complete-note`, which is what a reader
checking whether their own value belongs here reads. The client tells you
whether you need one: it warns or refuses on a breach, and silence means the
field is not yours to write.

Evidence: T314 Data properties, 2026-09-17; `numberdb_app/limits.py` soft
limits 1200 entries and 320 KB against the table's 479 and 213.7 KB;
`GET /api/table/T314/audit` yields no `size:` finding.

## Sage computes four knot polynomials and not the Kauffman one; KnotInfo's accessor does

What happened: T314 wants a `Programs` block, the standard incantation for a
reader who wants one more value, and the obvious guess does not exist. On
SageMath 10.9, `sage.knots.link.Link` has `alexander_polynomial`,
`conway_polynomial`, `homfly_polynomial`, `jones_polynomial`,
`khovanov_polynomial` and `links_gould_polynomial` -- and no
`kauffman_polynomial`. What answers is the KnotInfo interface, which reads a
stored column rather than computing:

    from sage.knots.knotinfo import KnotInfo
    KnotInfo.K3_1.kauffman_polynomial()
    # a^-2*z^2 - 2*a^-2 + a^-3*z + a^-4*z^2 - a^-4 + a^-5*z

That import worked here with no `database_knotinfo` module importable, so the
small default database Sage ships was enough for the named knots.

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value", with no warning that the
method a family suggests may not exist.

What it should say: run the incantation before writing it into `Programs`, and
where the library computes nothing, the honest block is the database accessor
that answers, said to be one -- `sage.knots.knotinfo` returns tabulated values,
not a computation, and a reader should be told which they are getting.

Evidence: probe run through a throwaway SageMath 10.9 container, 2026-09-17;
`dir(Link)` as quoted, `KnotInfo.K3_1.kauffman_polynomial()` as quoted, which
matches term for term the $F$ that T314's `comment-shift` quotes for the
trefoil.

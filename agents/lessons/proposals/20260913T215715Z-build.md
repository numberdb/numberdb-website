## An entry identity containing `}` cannot be written raw inside `HREF{#...}`
What happened: the characteristic-polynomial graph table names cospectral
mates in entry comments. The parameter is a canonical graph6 string, and some
connected cospectral graphs on seven vertices have graph6 strings containing
the character `}`: for example `F?]}w`, `F@?}W`, `F@h}o`, `FBY}o` and
`FBy}w`. Writing `HREF{#F?]}w}` would close the HREF at the graph6 brace and
leave the rest as prose, so the link would not name the entry it claims to
name. The generator had to link the mates whose keys fit the syntax and name
the brace-containing graph6 strings as text instead.

What the skill says now: link an entry as `HREF{slug#entry}` or `HREF{#entry}`,
and read the entry keys out of `Numbers` rather than inventing them. It does
not say what to do when the entry identity itself contains the delimiter of
the markup syntax.

What it should say: before putting a symbolic parameter value into an
`HREF{#...}` target, check whether it contains `}`. If it does, raw `HREF`
markup cannot express that entry address safely; name the value in prose
instead, or use a site-supported escaped form if one is added later. Do not
silently drop the mate from the comment, because the collision class is the
fact the reader needs.

Evidence: `/tmp/check_characteristic_graph_polynomials.py` first failed with
`ArithmeticError: cospectral graph keys contain closing braces: ['F?]}w',
'F@?}W', 'F@h}o', 'FBY}o', 'FBy}w']` while building T237 on 2026-09-13.

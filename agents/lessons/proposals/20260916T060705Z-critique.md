## A `sage.combinat` import that reaches Symmetrica segfaults under the skill's own import style, and the failure is not an exception

What happened: to run T260's `Programs` block I followed §6 of the skill —
`import numberdb.sage as numberdb` first, then the named rings — and called
`qt_kostka([3,2,1],[3,2,1])`, which is the one function the block is built
around. The run printed the block, then this, then died:

    File ".../sage/functions/trig.py", line 23, in <module>
        from sage.symbolic.function import GinacFunction
      File "sage/symbolic/function.pyx", line 155, in init sage.symbolic.function
      File "sage/symbolic/expression.pyx", line 14220, in init sage.symbolic.expression
    AttributeError: cannot access submodule 'function' of module 'sage.symbolic'
        (most likely due to a circular import)
    Exception ignored in: 'sage.libs.symmetrica.symmetrica.late_import'
    ...
    ValueError: the base ring must be either ZZ or QQ
    Exception ignored in: 'sage.libs.symmetrica.symmetrica._op_schur_general_sf'
    ...
    enter a to abort with core dump, g to go, f to suppress
    ERROR: s_mo_k:a == NULL?:
    Unhandled SIGSEGV: A segmentation fault occurred.

Two things make this worse than an ImportError. The failing import is not one
I wrote — `sage.libs.symmetrica` does a `late_import` of
`sage.functions.all`, which needs the symbolic machinery that the named-ring
style has deliberately not initialised, and the exception is *ignored* (it is
raised inside a Cython `late_import` hook). Symmetrica then runs with a null
pointer and segfaults, so a generator that meets this in a loop dies with no
Python traceback and nothing naming the cause. And it is exactly the code a
symmetric-functions table is made of: `qt_kostka`, `schur_to_hl`, anything
routed through `sage.libs.symmetrica`.

Prefixing three imports fixes it, and T260's own generator already carries
them with a comment saying why:

    import sage.symbolic.ring      # noqa: F401
    import sage.symbolic.function  # noqa: F401
    import sage.functions.trig     # noqa: F401

`from sage.all import *` fixes it too, and is what a reader pasting the
`Programs` block into a Sage session gets for free — the block runs clean
there and agrees with the stored value.

What the skill says now: §6 gives the named-import style as the recipe ("Name
the rings you use, rather than importing `sage.all`") and lists what it does
not bring: root finding, `RealBall.str`, `QQ('1.25')`. All three of those fail
loudly. Nothing says a `sage.combinat` call can fail *silently and fatally*
under the same style. The nearest existing proposal, "A deep `sage.combinat.*`
import in a script works where `sage.rings.*` does not"
(`20260916T051929Z-critique.md`), bounds the known failures to ring modules,
and this is a counter-example to that bound: the import here is
`from sage.combinat.sf.macdonald import qt_kostka`, it succeeds, and the
*call* is what dies.

What it should say: add to §6's list of what the named imports do not bring —
anything that reaches Symmetrica (`sage.libs.symmetrica`, which is under most
of `sage.combinat.sf`: `qt_kostka`, `schur_to_hl`, the Schur-basis
conversions). It needs the symbolic function machinery, its lazy import of it
is swallowed, and the process then segfaults rather than raising. Import
`sage.symbolic.ring`, `sage.symbolic.function` and `sage.functions.trig`
before the first call, or use `sage.all`. And, as the general rule the two
proposals share: **a segfault out of a Sage script is a missing initialisation
before it is a bug in Sage** — a named-import generator that dies without a
traceback should be retried once under `sage.all` before anything else is
investigated.

Evidence: 2026-09-16, T260 critique. `/tmp/t260_checks.py` (named rings) exit
1 with the trace above; `/tmp/t260_checks2.py`, the identical computation with
`from sage.all import *`, exit 0, and the `Programs` block returns
`q^3*t^2 + q^2*t^3 + q^4 + 3*q^3*t + 4*q^2*t^2 + 3*q*t^3 + t^4 + q^2*t + q*t^2`,
the stored T260 row for $\lambda=\mu=(3,2,1)$, character for character. The
workaround is in
`generators/macdonald-kostka-polynomials/generate.py` lines 22-26, put there
by the build that met the same thing.

## A square bracket in a formula is plethysm, and a table that does not say so publishes a formula that computes zero

What happened: T260's `formula-hook` states, for a hook shape
$\lambda=(n-k,1^k)$, that $\tilde K_{\lambda\mu}(q,t)=e_k[B_\mu-1]$. The
bracket is plethystic substitution. Read the ordinary way — $e_k$ evaluated at
the single quantity $B_\mu-1$ — it gives $0$ for every $k\geq2$, which is 222
of the table's 285 hook rows, and none of those rows is zero. Read
plethystically it is right: all 285 agree. So the table carries a correct
formula that a reader can only use if they already know a convention the table
never states, and the wrong reading returns a plausible-looking answer rather
than an error.

What the skill says now: "**Define notation where you use it.** A comment
saying the values are `U_n(x,-1)` is useless until something says what `U` is.
If a symbol appears in a formula or a comment, its definition belongs in the
same table." That covers a *symbol*. A bracket is not a symbol a reader knows
to look up — it is punctuation they think they can read.

What it should say: the rule should name notation as well as symbols, and
plethystic brackets as the standing example, because symmetric-function
tables are where the corpus keeps meeting them. The cheapest fix is usually
not to define the operator but to avoid it: "$e_k[B_\mu-1]$, the elementary
symmetric polynomial of degree $k$ in the monomials $q^jt^i$ of the cells of
$\mu$ other than the corner" needs no convention and is one clause longer.
The test that catches it: **evaluate your own formula the naive way and see
whether it reproduces a stored row.** If the naive reading gives a different
number, the notation needs a sentence.

Evidence: 2026-09-16, T260 critique. `/tmp/t260_hook.py`: 285 hook rows, 285
match $e_k$ of the cell monomials with the corner removed, 0 disagree; 222 of
the 285 have $k\geq2$ and none of them is the zero polynomial.

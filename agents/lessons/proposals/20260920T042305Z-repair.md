## Python `Decimal` rounds interval arithmetic to its current context
What happened: while checking T286's last stored value against a recomputed root, I parsed the 100-digit decimal with Python's `Decimal` and then subtracted and added one unit in the last place to model the interval the stored value claims. With the default context precision of 28, that arithmetic rounded the interval endpoints to 28 digits, and the check falsely reported that the stored value did not overlap the Sage interval. Setting `getcontext().prec` above the stored precision made the claimed interval overlap the recomputed root.
What the skill says now: it says to check the interval claimed by the written number rather than the midpoint, but it does not mention Python's decimal context.
What it should say: if a check reconstructs a NumberDB real interval from a decimal string with Python's `Decimal`, set the decimal context precision before doing endpoint arithmetic, or use NumberDB's own parser. Parsing the digits is not enough; the addition or subtraction that forms the endpoints is rounded to the active context.
Evidence: `/tmp/t286_verify.py` in the T286 repair on 2026-09-20. Before `getcontext().prec = 260`, the stored rank-79 value was truncated to `1.618033986795513050281884574` during the interval calculation; after setting the context, the stored claimed interval overlapped the recomputed root of $P_{40}$.

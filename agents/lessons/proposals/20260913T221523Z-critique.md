## Code in prose goes in backticks, not in `$\texttt{...}$`

What happened: T237, and published T125 before it, told the reader to
"produce the name with `$\texttt{g.canonical\_label().graph6\_string()}$`".
MathJax sets the argument of `\texttt` as text. Without the `textmacros`
package, which the site's MathJax does not load, `\_` is not a macro there,
so the page prints `g.canonical\_label().graph6\_string()`, backslashes and
all. Pasted into Sage, that is a `SyntaxError`. Nothing reports an error:
MathJax typesets it cleanly, so a check for "Math input error" passes.

What the skill says now: "backticks mark code" in `rigour details` (section
4 table). It does not say that backticks work in every prose field, and it
does not warn against `\texttt`.

What it should say: code a reader will copy (a Sage call, a graph6 string, a
function name) goes in backticks, which render as code in every prose field.
`$\texttt{...}$` is mathematics set in a typewriter font. Inside it `\_`,
`\{` and `\\` print as written, so an identifier with an underscore comes out
wrong without any error being shown.

Evidence: 2026-09-13, T237 critique. MathJax 3 with `base`, `ams`,
`newcommand` and `noundefined` serialises `\texttt{g.canonical\_label()}` to
`<mtext mathvariant="monospace">g.canonical\_label()</mtext>`, while the
control `x^{2` raises "Extra open brace". The same sentence is live on
<https://numberdb.org/Chromatic_polynomials_of_connected_graphs>.

## An entry key with `}` or `]` in it cannot be linked the usual way, and a bare `HREF{#key}` shows its `#`

What happened: T237's entries are keyed by graph6 strings, which use every
character from `?` to `~`. Its cospectral notes link each graph to its mate
with `HREF{#key}`, and they hit three separate limits.
- With no caption, the link text is the target itself, so 57 comments read
  "It is cospectral with #E@]o".
- The target ends at the first `}`, so a mate like `F@?}W` could not be
  linked at all. The generator wrote those 8 as prose instead, which put a
  second wording on the page.
- The caption ends at the first `]`, so writing the key as the caption
  fails for five of the 65 (`E@]o`, `FA]rw`, ...).

What the skill says now: that `HREF{slug#entry}` links a row and that the
address is the key in `Numbers`. Nothing about which keys can be written
this way or what an uncaptioned link shows.

What it should say: always give an entry link a caption, because without one
the reader sees `#key`. A key containing `}` cannot be an `HREF` target, and
one containing `]` cannot appear in a caption. For keys drawn from an
alphabet like graph6, name the other row in backticks rather than linking
some rows and not others. Then check the rendered preview for the link text.

Evidence: 2026-09-13, T237 critique. The `/preview` pieces
`/tmp/crit237/n0[0-4].html` render
`<a class="HREF" href="?entry=E%40%5Do">#E@]o</a>`. In `views.py` the
renderer does `ref, part2 = part.split("}", maxsplit=1)`, then
`caption, part2 = part2[1:].split("]", maxsplit=1)`, and `caption = ref`
when no caption is given.

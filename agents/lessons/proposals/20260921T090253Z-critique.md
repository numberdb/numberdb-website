# Lessons proposed by the T379 critique, 2026-09-21

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## `prod` is a Sage *session* global, so a `Programs` block written in named imports does not run as a file

What happened: T379's `Programs` block is seven lines of Sage that open with
the two named imports the skill asks for and then use `prod`:

    from sage.arith.misc import factorial
    from sage.rings.rational_field import QQ

    k = 5
    QQ(factorial(k*k)) * prod(
        QQ(factorial(j)) / QQ(factorial(k+j))
        for j in range(k))

Run exactly as printed with `sage -python`, which is what two named imports
announce, it stops at

    NameError: name 'prod' is not defined

`sage.all` has `prod` and `sage.arith.misc` re-exports it, so pasting the
block into an interactive `sage` works, and the bare final expression echoes
`701149020` there as well. Saved to a file it does neither: the name is
unbound, and once bound the expression prints nothing, because a bare
expression is not a `print`. A contributor meets this the moment they run
their own block the way a reader will.

The trap is that the skill's advice about imports and the shape of a
`Programs` block pull in opposite directions. Section 6 says to name the rings
rather than import `sage.all`, and gives a list of what the named imports do
not bring -- root finding, `RealBall.str`, `QQ('1.25')`. `prod` belongs on that
list, and so do the other session globals a short snippet reaches for without
noticing: `prod`, `sum` over Sage elements, `binomial`, `matrix`, `var`.

What the skill says now: section 6, "What else the named imports do not bring:
root finding (`sage.numerical.optimize`), `RealBall.str`, and `QQ('1.25')`".
Section 4 says `Programs` is "the standard incantation ... for a reader who
wants one more value" and says nothing about which interpreter that reader has.

What it should say: two sentences. Add `prod`
(`sage.misc.misc_c.prod`) and `binomial` (`sage.arith.misc.binomial`) to the
list of what named imports do not bring -- importing one name from a module
does not bind its neighbours, so `from sage.arith.misc import factorial`
leaves `prod` unbound even though that module re-exports it. And say that a
`Programs` block is run as the bytes the document holds: either write it so it
runs under `sage -python`, imports and a `print` included, or write it as a
session transcript and say so. A block that works only when pasted into a
prompt is a block that half its readers cannot run.

Evidence: 2026-09-21, T379 critique. `/tmp/t379_prog.py` through
`agents/sage.sh`: the block as written printed
`FAILED: NameError name 'prod' is not defined`;
`sage.arith.misc.prod: True`, `sage.rings.rational_field.prod: False`,
`sage.all has prod: True`; with `from sage.misc.misc_c import prod` the same
expression gives `701149020`.

## The audit checks a `CITE` for a target; it does not check a `Reference` for a citation

What happened: T379 declares four sources and cites one. Counting `CITE{}`
across the definition, every formula, every comment, both `Similar tables`
relations and `rigour details`: `CFKRS` four times, `KeatingSnaith` zero,
`MehtaNormand` zero, `WikiRMT` zero. `GET /api/table/T379/audit` reports none
of it -- its one finding is about a parameter.

Reading `numberdb_app/management/commands/audit_table.py`, the citation rule
is `validate.unresolved_citations`, which is "this `CITE{x}` names no Link or
Reference". There is no rule in the other direction, so a bibliography nobody
points at passes clean. The critique of the sibling table T378, written the
day before, states that the audit checks "every `Links` and `References` key
is cited from the prose" -- it does not, and a run that believes it will skip
the check it thinks has already been made.

This is a contributor's problem as much as ours: the audit is reachable as
`GET /api/table/T<n>/audit` with any key, and it is what the skill points a
contributor at ("Let `manage.py audit_table` confirm afterwards rather than
instead").

What the skill says now: "**A reference is for citing, not for listing.**
`CITE{Koshy}` in a comment earns its place; a bibliography nobody points at is
furniture." The rule is there; nothing says it is unchecked.

What it should say: that the audit checks citations in one direction only --
a `CITE` with no target -- and that an uncited `Reference` or `Link` is
something to count by hand before offering a draft. Four lines of Python over
the document does it: collect `CITE{...}` from every prose field, subtract from
`References` and `Links`, and look at what is left. It is also worth proposing
as an audit rule, which is why this note names the function.

Evidence: 2026-09-21, T379 critique. `GET /api/table/T379/audit` returned one
finding, about the `group` parameter; the citation count above was made from
`GET /api/table?id=T379`; `audit_table.py` lines 320-324 are the only citation
check.

## `/api/lookup` takes `text=`, not `q=`, and says so only if you read the error

What happened: three text searches of the corpus were sent as
`/api/lookup?q=random+matrix` and each answered HTTP 200 with
`{"error": "Give number=<json record>, numbers=<json list>, polynomial=<text>,
polynomial_hash=<digest>, or text=<search term>."}`. A caller that reads
`tables` or `results` out of the JSON sees an empty list, which is
indistinguishable from a corpus that holds nothing on the subject -- the same
failure the skill already warns about for `search_text`, where iterating the
result object instead of `.tables` "reads exactly like an empty corpus".

With `text=`, `/api/lookup?text=random+matrix` returns T377, T378 and T171
under `tables`, which is the answer.

What the skill says now: section 1 warns that `search_text` returns an object
with a `.tables` list and that iterating it directly yields nothing and raises
nothing. It does not mention `/api/lookup`, which is the same search for
somebody working over HTTP rather than through the client.

What it should say: name the parameter. Searching the corpus over the API is
`GET /api/lookup?text=<term>`; `q=`, `query=` and `search=` are not it, and a
wrong parameter answers 200 with an `error` key rather than a 4xx, so check
for `error` before believing an empty result. `/api/search?query=` is a
different endpoint and answered `{"results": [], "messages": []}` for the same
term, which is the same trap without even an error to read.

Evidence: 2026-09-21, T379 critique. `q=random matrix` -> `{"error": ...}`;
`text=random matrix` -> T378, T171, T377; `text=Barnes` -> T93, T147, T378,
T377, T148; `/api/search?query=random matrix` -> `{"results": []}`.

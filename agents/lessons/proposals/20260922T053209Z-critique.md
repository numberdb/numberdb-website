## `ball.contains(stored)` answers the wrong question, and answers it "no"

What happened: checking T7's stored 301 digits of $\pi$ against a ball
computed independently, the natural call

```python
prog = RealBallField(1024).pi()          # the table's own Programs line
centre = QQ(int(s.replace('.', ''))) / QQ(10)**300     # the stored decimal
prog.contains_exact(centre)              # -> False
```

returned **False** on a value that is correct to every digit written. Read
alone that is "the table holds X and this run produced Y", and it is the
refusal the skill teaches you to take seriously.

It is not a disagreement. It is the two intervals being compared in the wrong
direction. The stored decimal is a *rounding* of $\pi$ to 300 places, so it
sits up to half a unit in its last place away from $\pi$ — here 0.2754 ulp,
about $2.8 \times 10^{-301}$. The ball is 1024 bits wide, a radius of
$1.1 \times 10^{-308}$, which is $1.1 \times 10^{-8}$ ulp. A ball eight orders
of magnitude *narrower* than the stored last place cannot contain the stored
midpoint, and never could have, however right the table is.

The comparison that answers the question is the other way round, because the
written decimal is the thing making a claim:

```python
ulp = QQ(1) / QQ(10)**300
abs(centre - QQ(prog.mid().exact_rational())) <= ulp        # True, at 0.2754
# or, equivalently and without arithmetic on the difference:
(QQ(prog.mid().exact_rational()) * 10**300).round() / QQ(10)**300 == centre
```

Both hold here, the second exactly.

What the skill says now: §10 has the opposite trap, "an enclosure that
contains everything agrees with everything" — a ball too *wide* reporting
success. And it states the right principle for root-finding: "Check the claim
the digits make, not the value at their midpoint. What a written number claims
is the interval its last place denotes." Neither warns that arb's own
`contains` / `overlaps` asks the containment in the direction that makes a
narrow, correct ball report failure against a stored value.

What it should say: alongside the too-wide case, the too-narrow one. A ball
narrower than the stored value's last place reports `contains = False` on a
table that is right, because a stored decimal is a rounding and the ball has
no room for the rounding. Compare the stored value's own $\pm 1$ ulp interval
against your ball, or round your ball's midpoint to the stored precision and
compare strings. Then a disagreement in ulps is a number you can act on: 0.28
is a correct rounding, 0.6 is a rounding done wrong, 40 is a wrong value.
Section 8's "the table holds X and this run produced Y" is worth a sentence
saying this is the commonest innocent cause.

Evidence: T7, 2026-09-22, in `agents/sage.sh`. `RealBallField(4000).pi()` as
reference, radius 1.5e-1204; `|stored - pi| / ulp = 0.2754129933936844` and
`inside one ulp: True`. Against the table's own program,
`RealBallField(1024).pi()`: accuracy 307.95 decimal digits, radius
1.1125369e-308, `radius / ulp = 1.1125369e-08`,
`contains_exact(centre) -> False`, and `mid rounded to 300 places == stored
-> True` with `difference in ulps: 0.0`.

## `RealBall` has no `.str`: the skill says so, in the section nobody reads for it

What happened: `prog.str(digits=320, no_radius=True)` raised
`AttributeError: 'sage.rings.real_arb.RealBall' object has no attribute
'str'`, inside a container built from the deployed image.

What the skill says now: it already names this, in §6 — "What else the named
imports do not bring: root finding (`sage.numerical.optimize`),
`RealBall.str`, and `QQ('1.25')`". So the fact is covered and this is not a
proposal to add it.

What it should say: nothing new, except perhaps where it says it. The
sentence sits under "Name the rings you use, rather than importing
`sage.all`", framed as a consequence of the import style, and I read it as
being about *modular passagemath*. It is not: the missing method bites on a
full SageMath too, and the place a contributor meets it is not while writing a
generator but while trying to *print* a ball to compare it against a table —
which is §10's business, not §6's. One cross-reference from the checking
section would have saved the turn. Recorded as a judgement about placement, so
a person can decide it is not worth a diff.

Evidence: same run, 2026-09-22. The working form is
`QQ(ball.mid().exact_rational())` and arithmetic on the rational, which is
what the first lesson above needs anyway.

## `verify()` checks the generator's rows, not the table's: `extra` is never filled

What happened: T285 grew from 5 rows to 7 when two more genera turned out to
be proven in the literature. The generator attached to the table was not
re-attached, so the file the site serves as "the program that reproduces this
table" still enumerates five genera. Run exactly as its own header instructs,
it reports

    <VerifyReport T285: 5/5 matched, 0 differing, 0 missing, 0 extra>

and exits 0. It is not merely that the check passed on a sample: `verify()`
iterates `generator.enumerate()` and looks each identity up in the stored
table, so a row the generator does not produce is never examined. And
`VerifyReport.extra` is never appended to anywhere in the client -- it is
initialised in the constructor, counted in `__str__` and in `ok`, and nothing
ever puts an identity in it. So the count that a reader would take as "rows in
the table this generator did not produce" is structurally zero, whatever the
table holds.

The drift is asymmetric and only one half of it is visible. A generator that
enumerates a row the table has lost shows up as `missing`. A table that has
grown past its generator shows up as nothing at all: clean verify, clean
audit, rendered page correct, and the next person to extend the table starts
from a file two rows short of it.

What the skill says now: "`verify(sample=None)` checks every entry" (§6), and
"`verify(sample=None)` after publishing" (§10). Both read as though `verify`
walked the table. A proposal of 2026-09-19 (T288) says a stale generator is
caught by "the report's `missing` and `extra` counts"; the `missing` half is
right and the `extra` half is not, so accepting that lesson as written would
teach a check that cannot fire.

What it should say: `verify(sample=None)` checks every entry *the generator
enumerates*, which is not the same as every entry the table holds. Before
believing a clean report, compare the counts:

    len(numberdb.table('T285')['Numbers'])        # what the table holds
    len(list(generator.enumerate()))              # what the check covered

If the first is larger, the generator has fallen behind the table and the
clean report is about a subset. Re-attach the generator in the same act that
changes what the table holds; a generator is part of the table, not a record
of how it was first filled.

Evidence: 2026-09-20, T285 growth critique. `curl
'https://numberdb.org/files/T285/generate.py?raw=1'` returns the 4290-byte
file whose `POLYNOMIALS` dictionary has genera 1 to 5, while `GET
/api/table?id=T285` returns `Numbers` with keys `['1','2','3','4','5','7','8']`
and `/files/T285` dates the attachment 2026-09-16 against a current version of
2026-09-20 02:55. Running that file unchanged under Sage printed the report
above. In `clients/python/numberdb/_generate.py`, `_verify` appends to
`report.missing` and `report.differing` only; `grep -n '\.extra'` over the
package finds the constructor, `ok`, and `__str__`, and no assignment.

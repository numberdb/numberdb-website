## An API key does not open `/drafts`: the listing is session-only, and refusing you looks like an empty page at HTTP 200

What happened: I wanted to know which drafts this account holds, and the skill
says `/drafts` "lists what is being made right now". So I fetched it with the
key that had just answered a keyed `/api/table` read. It came back `200`, 14427
bytes of HTML, and no table ids on the page — which reads exactly like "you
hold no drafts".

It was the sign-in page. The key had made no difference at all:

    GET /drafts  (no key)    -> 200  <title>Sign in - NumberDB</title>  14427 bytes
    GET /drafts  (Bearer k)  -> 200  <title>Sign in - NumberDB</title>  14427 bytes

Byte-identical. With redirects switched off the first response is visible for
what it is:

    GET /drafts  (Bearer k), redirects off -> 302  Location: /accounts/login/?next=/drafts

`/drafts` is a site page guarded by a login session, and an API key is not a
session credential. `urlopen` and `requests` follow the redirect by default, so
a caller that checks `r.status_code == 200` and then parses the HTML gets a
confident, silent, wrong answer. The tell is in `r.url` / `r.geturl()`, which
ends `/accounts/login/?next=/drafts`, and nowhere in the status.

This is the same failure shape as the `/api/table` one already proposed —
success-looking HTTP hiding a refusal — but the cause is different and the
check is different, so knowing that one does not save you from this one.

There is also no API route that lists drafts. `/api/table?id=...` reads one at
a time, and the only place the API volunteers how many you hold is the
*creation* response, which carries `drafts_held` and `drafts_remaining` — no
use to a caller that wants to know before creating anything. So counting your
own drafts through the API means probing ids one by one, and there is no
cheaper way to do it today.

What the skill says now: that `/drafts` lists what is being made right now and
is invisible from outside, and that the offer button lives there. It does not
say that the page needs a browser session, and it does not warn that an API key
gets a sign-in page at `200` rather than a `401`.

What it should say:

- `/drafts` and the other pages under the site are for a signed-in browser.
  Your API key opens `/api/...` and nothing else; presenting it to a site page
  is the same as presenting nothing.
- A page that needs a session answers `302` to `/accounts/login/`, and your
  HTTP client follows that, so you see `200` and a page with no drafts on it.
  Check `response.url` after the fetch, or fetch with redirects disabled, before
  believing an empty listing. Generally: an empty result from this site is only
  trustworthy once you have checked you were not redirected.
- There is no `/api/drafts`. To find a draft through the API, read its id
  directly with `/api/table?id=T...` and the key. The counts `drafts_held` and
  `drafts_remaining` come back only in the `201` from `POST /api/tables`.

A contributor with a laptop, a key and no browser session open — which is the
normal state of a script — hits every part of this, and the failure direction is
the bad one: it reports that the drafts they are holding do not exist.

Evidence: 2026-09-23, w3 triage of build `20260923T130623Z`. The three fetches
above, with the key piped from `$NUMBERDB_KEY_FILE`; `numberdb_app/views.py:375`
(`if not request.user.is_authenticated: return redirect(...)`);
`numberdb_app/urls.py`, which has no drafts route under `api/`;
`numberdb_app/test_draft_listing.py:157-159`, which asserts `drafts_remaining`
and `drafts_held` on the creation answer and nowhere else.

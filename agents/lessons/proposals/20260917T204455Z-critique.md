## A value written with too few digits is not merely vague: search by number drops it

What happened: T313 stores the Chern-Simons invariant of 243 hyperbolic knots,
transcribed from KnotInfo's printed column. Twenty-eight of the source strings
had lost their trailing zeros somewhere upstream -- `"0.05"` for $9_{41}$,
`"0.066236"` for $9_{49}$, `"-0.05199305"` for $8_{14}$ -- and a second column,
derived by multiplying by $2\pi^2$, was written one significant digit shorter
than its source on purpose. The values are all correct. But the table page
draws a dagger, "This number will not be found in the search", on **forty of
its 932 entries**: `findable_by_number` excludes any value whose interval is
wider than $10^{-5}$ relative to its own size, because an interval that loose
identifies nothing. So the entries a reader is most likely to arrive holding an
approximation of are the ones the database will not answer for, and nothing in
the generator, the API response or `audit_table` says so.

The two halves of it are separately worth knowing.

*Trailing zeros.* A decimal in this corpus states its own precision, so
`0.05` and `0.050000000` are different claims about the same number by a factor
of ten million. Anything that has been through a float repr on the way -- a
scraped HTML column, a CSV, `str(x)` -- has silently dropped them. I recomputed
all twenty-eight with SnapPy: every one is the nine-decimal value with zeros
stripped off the end.

*Derived columns.* Multiplying by an exact constant preserves relative
accuracy exactly, so a second normalisation should be written with the *same
number of significant digits* as the value it comes from. T313's generator
wrote one fewer, reasoning that the multiplication loses precision; it does
not, and that digit is what carried thirty-four rows over the threshold.
`-1.02630` has relative width $1.9\times10^{-5}$; `-1.0262995` has
$2\times10^{-7}$.

What the skill says now: it is good on what a written decimal *means* ("3.14 is
the interval [3.13, 3.15]", "a decimal means plus or minus one unit in its last
place however long it is") and on not writing more digits than are known. It
says nothing about the consequence of writing *fewer*: that there is a
threshold, where it is, or that the site marks what falls past it.

What it should say: in section 5, beside the interval convention -- a value
whose interval is wider than about $10^{-5}$ of its own size is shown with a
dagger and is not returned by search by number, because matching it would tell
the asker nothing. Two ways to fall over that line by accident: trailing zeros
lost by a float repr when transcribing a source (write the source's digits back
out to their full width), and a derived column written with fewer significant
digits than the column it was derived from (multiplication by an exact constant
costs no relative accuracy).

Evidence: T313, 40 of 932 entries daggered; `numberdb_app/models.py`
`findable_by_number` and `exact_relative_width`, threshold
`NUMBERDB_MAX_RELATIVE_WIDTH = 1e-5`; a `/preview` of the $9_{41}$, $9_{49}$
and $10_{17}$ rows returns eight daggers on ten entries. SnapPy 3.3.2 on the
28 short knots, all nine-decimal with a zero in the last place.

## A section entry is a string; a mapping under it renders as a Python dict

What happened: T313's `Formulas` holds two entries written as mappings,
`{display: 'mirror image', formula: '$...$'}`, which is a natural thing to
write if you think a formula wants a label -- the `Parameters` section takes
exactly that shape, with `title`, `display` and `constraints` under each key.
`Formulas` does not. The renderer prints the value, so the page carries

    (1)  {'display': 'mirror image', 'formula': '$\operatorname{CS}(S^3\setminus
         \bar K)\equiv -\operatorname{CS}(S^3\setminus K)\pmod{1/2}$'}

backslashes doubled, because that is `repr` of a Python string. MathJax then
typesets the `$...$` it finds inside **without error**: `\\` is a line break,
so the identity comes out as several lines of italic letters spelling
`o p e r a t o r n a m e C S`. There is no "Math input error" to notice, and
the stored YAML looks perfectly reasonable. `audit_table` reports the table
clean of this.

What the skill says now: section 4's table says what `Formulas` holds
("identities, closed forms, generating functions, recurrences") and the key is
used as a `CITE{}` target, but nothing says the value is a string. The example
tables in the skill never show a `Formulas` block at all.

What it should say: in the section table, or beside it -- which sections take a
string under each key and which take a mapping. `Comments` and `Formulas` take
a *string*, keyed by a name (`formula-skein`, `comment-range`) that `CITE{}`
resolves and that the page anchors. `Parameters`, `References`, `Links`,
`Programs` (`language` and `code`) and `Similar tables` (`table` and
`relation`) take a mapping. Putting a mapping where a string belongs reaches
the page as a Python `repr`, and because a `$...$` inside it still typesets, it
renders as nonsense rather than as an error.

Evidence: T313 `Formulas`, as served by `/api/table?id=T313` and drawn by
`/preview`; T141, T309, T310 and T312 all store strings. MathJax 3
(`mathjax-full`, base + ams) converts the doubled-backslash text with zero
errors, producing `<mi>` per letter.

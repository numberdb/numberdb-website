## Sage's cyclotomic p-adic regulator needs extra initialisation under named imports

What happened: building T412 under the skill's named-import rule found three
Sage initialisation failures before the control value for 37a1 at $p=5$ would
compute. Constructing the curve as `EllipticCurve("37a1")` tried to import
`PolynomialSequence_generic`; constructing it instead from the exact Cremona
database `a`-invariants avoided that path. Then `padic_regulator` needed
`sage.rings.polynomial.laurent_polynomial_ring` imported explicitly. Finally,
Sage's Monsky-Washnitzer height code reached lazy symbolic `log` and `ceil`
names in a precision branch and raised `RuntimeError: can't happen`; assigning
`sage.schemes.hyperelliptic_curves.monsky_washnitzer.log = math.log` and the
same module's `ceil = math.ceil` let Sage's documented regulator and height
methods agree.

What the skill says now: it says to import `numberdb.sage` first, name the
rings rather than importing `sage.all`, and expect some Sage machinery to be
missing. It does not name this p-adic-height path.

What it should say: for elliptic-curve `padic_regulator` and `padic_height`
generators, prefer exact Cremona `a`-invariants over the string curve
constructor, import the Laurent polynomial ring module before calling the
p-adic routines, and keep a known control row such as 37a1 at $p=5$. If
Monsky-Washnitzer reaches symbolic `log` or `ceil` under named imports, patch
that module to Python's `math.log` and `math.ceil` before computing the height.

Evidence: T412 build, 2026-09-22. The final generator checked Sage's
documented 37a1, $p=5$ value against `padic_regulator`, checked
`Reg_p(E)=h_p(P)`, and checked `h_p(2P)=4h_p(P)` over all 285 rows.

## The dry-run exactness check should accept Sage p-adics with precision

What happened: the first dry run of T412 computed the p-adic regulators but
`agents/table-build/check.py` reported every value as an unexpected
`pAdicCappedRelativeElement`. These values are not floats and are not unbounded:
they carry their own `O(p^n)` term, exactly the information a `Qp` table is
supposed to store.

What the skill says now: it says to run `exactness(values)` and that values may
be exact or carry their own error bound. The helper accepted real balls and
intervals but not p-adic elements.

What it should say: `exactness(values)` should treat Sage p-adics with an
absolute precision as bounded values, and should refuse only a p-adic with no
precision. A report naming `pAdicCappedRelativeElement` on a `Qp` table is a
checker gap, not evidence of float arithmetic.

Evidence: T412 dry run, 2026-09-22. After adding a p-adic branch to
`exactness`, the same 285 entries passed exactness, measured at 155.9 KB, and
verified against the filled draft.

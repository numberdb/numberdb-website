# Lessons proposed by the T388 critique, 2026-09-21

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## `import numberdb.sage` initialises the rings and not Singular or GAP, so `sage.coding` fails under the skill's named imports

What happened: reading T388, whose `Programs` section gives a closed form
for one stored row rather than an incantation for the family, I wrote the
replacement I wanted to recommend -- ask Sage for the code and read off its
weight distribution -- in the style the skill prescribes, rings imported by
name and no `sage.all`:

    from sage.coding.hamming_code import HammingCode
    from sage.rings.finite_rings.finite_field_constructor import GF

    C = HammingCode(GF(2), 3)
    C.weight_distribution()

It raised, from inside Sage rather than from my code:

    ValueError: a parity check matrix must be specified if
    LinearCodeSystematicEncoder is the default encoder

which is a message about encoders and has nothing to do with the cause. The
cause is two frames further in: building the Hamming code's parity check
matrix walks the points of a projective space, which calls `Sequence`, which
imports `sage.rings.polynomial.multi_polynomial_sequence`, which initialises
Singular -- and that init fails half-way with `ImportError: cannot import
name PolynomialSequence_generic`. `C.weight_enumerator()` raises that
`ImportError` directly. `C.minimum_distance()` and
`BCHCode(GF(2), 15, 5).minimum_distance()` raise `ImportError: cannot
import name libgap` for the same reason on the GAP side.

The part worth writing down is what did *not* fix it. The skill says that
importing `numberdb.sage` before the rings "is what makes the direct imports
work ... that module does the initialising". It initialises enough for
`QQ`, `ZZ` and `PolynomialRing`, and not enough for this: with
`import numberdb.sage as numberdb` as the first line, all three failures are
unchanged, character for character. `import sage.all` as the first line
fixes all three, and then the named imports below it work:

    hamming 2,3 : x^7 + 7*x^4 + 7*x^3 + 1
    minimum_distance: 3
    weight_enumerator(): x^7 + 7*x^4*y^3 + 7*x^3*y^4 + y^7
    bch 15,5 minimum_distance: 5

What the skill says now: "Name the rings you use, rather than importing
`sage.all`", then a list of what the named imports do not bring -- root
finding, `RealBall.str`, `QQ('1.25')` -- and the sentence that
`numberdb.sage` does the initialising. Everything on that list is a ring or
a numerical routine, so a contributor reads the rule as being about rings
and applies it to a coding-theory or scheme-backed computation without
expecting anything to change.

What it should say: the named-import rule has a boundary, and it is
Singular and GAP. Anything that reaches a multivariate polynomial ring, a
scheme point, or libgap through a lazy import needs Sage initialised
further than `numberdb.sage` takes it -- `sage.coding`'s
`weight_distribution`, `weight_enumerator` and `minimum_distance` are the
case measured here. On a full SageMath `import sage.all` is the fix and
costs a few seconds of startup; on a modular passagemath it is not
available, and the distribution carrying Singular has to be installed
instead. The tell is an `ImportError` naming a symbol nobody asked for
(`PolynomialSequence_generic`, `libgap`), or a `ValueError` about encoders
that is really that `ImportError` two frames up.

Evidence: three runs through `agents/sage.sh` on 2026-09-21, images
`numberdb/web:latest`: `/tmp/probe.py` (named imports only, three
failures), `/tmp/probe2.py` (`import numberdb.sage` first, same three
failures), `/tmp/probe3.py` (`import sage.all` first, all four values
correct, and `hamming,2,3` reproduced exactly as T388 stores it).

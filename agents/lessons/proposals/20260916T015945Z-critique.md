# Lessons proposed by the T255 critique run, 2026-09-16

Nothing here is in force. Format follows `agents/lessons/PROPOSALS.md`.

## A parameter key that YAML reads as a boolean: `ON`, `OFF`, `YES`, `NO`

What happened: T255 indexes its rows by sporadic group, and the O'Nan group's
key is `ON` — the same label the ATLAS and the GAP Character Table Library use.
The document is correct everywhere it matters: the API carries JSON, and the
site's own two YAML readers, `data_pipeline.utils.load_yaml_recursively` and
`views.preview`, both use `yaml.BaseLoader`, which keeps every scalar a string.
But `yaml.safe_load` is YAML 1.1, where `ON` is the boolean true. Loading the
table's own `table.yaml` with it silently turned the key into `True`, so the
`values:` lookup for `'ON'` missed and the O'Nan rows printed the bare key
instead of `$\rm{O'N}$`. It reads exactly like a missing display symbol in the
table, and it is not in the table.

The same goes for `OFF`, `YES`, `NO`, `TRUE` and `FALSE` in any case, for
`null` and `~`, and for a key like `12:30`, which YAML 1.1 reads as the
sexagesimal integer 750. Single letters are safe: `Y` and `N` stay strings.

What the skill says now: "A parameter's key is an address, not a word. It
identifies every entry under it, so it is frozen when the table is published
and a citation resolves on it." It says to choose a specific key rather than
`expression`, and nothing about keys that are not strings.

What it should say: a parameter key is a *string*, and a handful of natural
labels are not read as strings by every YAML parser. `ON`, `OFF`, `YES`, `NO`,
`TRUE` and `FALSE` in any case are YAML 1.1 booleans, `null` and `~` are None,
and `12:30` is the number 750. The corpus's own readers use `BaseLoader` and are safe, but the moment
somebody opens a `table.yaml` with `yaml.safe_load` — to check it, to diff it,
to generate from it — the key changes type and every lookup on it misses
silently. If a key has to be one of these words, quote it in the YAML
(`'ON':`), and know that a reader of the file may still have to.

Evidence: 2026-09-16, T255. `python3 -c "import yaml;
print(yaml.safe_load('ON: x'))"` gives `{True: 'x'}`;
`yaml.load('ON: x', Loader=yaml.BaseLoader)` gives `{'ON': 'x'}`. A `/preview`
chunk built by round-tripping T255's parameters through `safe_load`/`dump`
rendered the O'Nan rows as `ON`, and the same chunk built from the API's JSON
rendered them as $\mathrm{O'N}$.

## `search_integer` returns its hits as the result itself; `.tables` is empty

What happened: checking whether T255's degrees are already findable, the
obvious call looked right and answered nothing:

    r = numberdb.search_integer(196884)
    r.tables        # []

196884 is stored publicly, in T79's $q$-expansion of the $j$-invariant, and
`.tables` being empty reads exactly like the corpus not holding it. The
`SearchResults` object *is* a list of `Result`s, and the hits were in it all
along: `list(r)` gives `[Result('196884', table='$q$-expansion of the
$j$-invariant')]`, and `r[0].table` is the table. `.tables` is for text search,
where the hits are tables rather than entries, and it stays empty on a number
search.

This is the mirror image of the trap the skill already records for
`search_text`, and it fails the same way: silently, with a plausible answer.

What the skill says now: "`search_text` returns an object with a `.tables`
list, not a list -- iterating it directly yields nothing and raises nothing,
which reads exactly like an empty corpus."

What it should say: the same sentence, and its converse. A *number* search —
`search_integer`, `search_rational`, `search_real_ball`, `search_polynomial`
and the rest — returns `SearchResults` that *is* the list of matching entries;
iterate it, and read `.table` off each hit. `.tables` is populated by
`search_text` and empty here. So: iterate a number search, and read `.tables`
on a text search, and neither one raises if you do it the other way round.

Evidence: 2026-09-16, against numberdb.org.
`repr(numberdb.search_integer(196884))` is
`[Result('196884', table='$q$-expansion of the $j$-invariant')]`; the same
object's `.tables` is `[]`. `numberdb.search_text('sporadic').tables` answers with
`Orders_of_sporadic_finite_simple_groups`, and iterating that same result
directly yields nothing.

## A table's own labels may not be the labels its `Programs` snippet takes

What happened: T255 stores the 26 sporadic groups under the ATLAS labels
`M11`, ..., `ON`, `B`, `M`, and its `Programs` block is the GAP incantation

    degrees := List(Irr(CharacterTable("M24")), chi -> chi[1]);

A reader wanting one more value substitutes their group's label for `"M24"`.
That works for 25 of the 26. For the twenty-sixth it silently returns a
different group: CTblLib stores the simple group $\mathrm{Fi}_{24}'$ as `F3+`
and registers `fi24` as an alias of `F3+.2`, so `CharacterTable("Fi24")` gives
$\mathrm{Fi}_{24}'.2$ — twice the order, 183 irreducible characters instead of
108, no error. The generator knew the right name and kept it to itself.

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value." Nothing about the relation
between the snippet's arguments and the table's parameter values.

What it should say: where a parameter's values are *names*, check that the
`Programs` snippet accepts them. A reader substitutes the label they can see
for the one in the example — that is what the snippet is for — and an external
library's naming is its own. Where a label differs from the library's name for
the same object, say so in the comment that glosses the labels; where several
differ, put the library's name in the snippet and the table's label beside it.
A name that resolves to a *different* object is the dangerous case, because it
answers rather than failing.

Evidence: 2026-09-16, T255 and CTblLib 1.3.11. `data/ctofisc2.tbl` declares
`MOT("F3+", ...)` with order 1255205709190661721292800 and 108 classes,
`MOT("F3+.2", ...)` with order 2510411418381323442585600 and 183, and
`ALN("F3+.2",["fi24","fi24'.2","f24"])`. Checking all 26 of the table's labels
against the library's `MOT` and `ALN` declarations, `Fi24` is the only one that
resolves to something other than the group stored under it.

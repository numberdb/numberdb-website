## The unkeyed API allowance is 60 requests an hour, and the 429 it returns will pass a naive "does this table exist" test

What happened: I opened by probing eighteen table ids twice, once with the key
and once without, to separate "this id was never used" from "this is my draft
and an unkeyed reader cannot see it". The keyed half was right. The unkeyed
half reported every id public -- including `T446`, which does not exist. The
anonymous requests had never reached the lookup:

    GET /api/table?id=T441   (no Authorization)
    429  {"error": "Rate limit exceeded (60 requests per 60 minutes).
          An API key raises this limit; see /help#section-api.",
          "retry_after": 1365}

My test was `b"does not exist" not in body`, and a 429 body does not contain
that string, so a throttled probe read as a published table. Anything shaped
like `if "does not exist" in r.text` or `r.json()["numbers"]` has the same
hole: the failure is a 4xx with a perfectly good JSON body, not an exception.

The numbers, from `numberdb_app/throttle.py`:

* **60 requests per hour unkeyed, 1000 keyed** (`ANONYMOUS_LIMIT`,
  `IDENTIFIED_LIMIT`, `WINDOW_SECONDS`). The unkeyed counter is kept against
  the caller's IP address, so everything behind one address shares it.
* **A batch costs `1 + ceil(0.5 * n)` units**, not one. A single
  `/api/search` of a hundred numbers costs 51 -- most of an unkeyed caller's
  hour in one call. Batching is cheaper than a hundred lookups and is not free.
* **The window is fixed and aligned to the clock hour**, not rolling:
  `window_start = now - (now % window)`. So `retry_after` is the seconds left
  until the top of the hour, the whole allowance returns at once, and a caller
  can legitimately spend all 60 at 11:59 and another 60 at 12:00.
* Only `/api/*` is limited. The site's own pages are not.

What the skill says now: nothing. It documents the API's paths and the key, and
a reader following it writes a loop over ids without knowing there is a budget
or what running out looks like.

What it should say: the API is rate limited -- 60/hour unkeyed, 1000/hour with
a key, a fixed window that resets on the hour -- and a client must check the
status code before the body, because the refusals (429 throttled, 403 bad key,
405 wrong method) all arrive as valid JSON that a body-string test will
misread. Anyone probing more than a handful of ids should use their key, and
should know that a hundred-number batch costs 51 of the allowance.

Evidence: `numberdb_app/throttle.py:37-57` (`batch_cost`, `ANONYMOUS_LIMIT`,
`IDENTIFIED_LIMIT`, `WINDOW_SECONDS`), `:88-110` (`requester_of`, scope
`ip:<addr>`), `:115-138` (`_consume`, hour-aligned window). Measured
2026-09-23 11:33-11:40Z, unkeyed, against numberdb.org.

## Four URL shapes for one table, and only one of them is the page a person reads

What happened: to check whether my drafts were still drafts while the API was
throttled, I went looking for the human page and guessed `/table/T441`. It
answers 404 -- for ids that exist and ids that do not, because it is not a
route at all. The published page is at the bare id. Measured, all anonymous:

    GET /T20             -> 200  590887 bytes   the rendered table page
    GET /T441            -> 404   11533 bytes   exists, but still a draft
    GET /table/T20       -> 404   11540 bytes   not a route (site's HTML 404)
    GET /table?id=T20    -> 404   11534 bytes   not a route either
    GET /api/table?id=T20                       the API read
    GET /api/table/T441  -> 405  {"error": "Use POST or PUT."}
    GET /api/table/T441/audit -> 200            sub-resource, singular, GET

So the singular `/api/table/<TID>` prefix serves a GET for the `/audit`
sub-resource but refuses one for the table itself, and the human page lives at
the root rather than under any prefix.

Two things follow that are worth having:

* **`GET https://numberdb.org/<TID>` is a publication check that costs nothing
  against the API allowance**, because only `/api/*` is limited
  (`throttle.py:13-15`). 200 means published and readable by anybody; 404 means
  either still a draft or never created. When the API is throttled or you are
  rate-conscious, this is the cheap half of the question.
* It does not, on its own, distinguish a draft from a nonexistent id -- both
  are 404. Only a **keyed** `GET /api/table?id=<TID>` does that: it returns the
  table for your own draft and `does not exist` for an id nobody has used.

What the skill says now: it gives `/api/table?id=<TID>` for reading and the
publish endpoint, but does not say where the rendered page is, and a
contributor who wants to look at what they made -- or send somebody a link --
guesses `/table/<TID>` as readily as I did and gets a 404 that looks like their
table is gone.

What it should say: the table's page is `https://numberdb.org/<TID>`; the API
is `/api/table?id=<TID>`; `/api/table/<TID>` is the write path and refuses GET
with 405. Checking publication through the page is free; checking existence
needs the key through the API.

Evidence: measured 2026-09-23 11:34-11:40Z against numberdb.org;
`numberdb_app/throttle.py:13-15`.

## A key that is wrong gets 403; a key that never arrived gets treated as the public

What happened: the corpus notes already record the trap that a keyed read of
your own draft and a read of an id nobody ever used are indistinguishable --
both HTTP 200, both the same 49-byte `does not exist` body -- so a run whose
`Authorization` header went missing concludes its table was never created and
builds a duplicate. What was not recorded is that this only happens when the
header is **absent**. A header that is present and wrong is refused loudly:

    Authorization: Bearer not-a-real-key
    403  {"error": "Invalid API key.", "help": "/help#section-api"}

`requester_of` deliberately does not demote a bad token to the anonymous
allowance -- the comment in the source says so: "a stale key is visible to its
owner instead of looking like a slow day". The 403 is returned before the
counter is touched, so a bad-key probe costs nothing.

Which makes it a diagnostic. If you are told your own draft `does not exist`:

* getting **403** from the same request means the key is wrong, revoked or
  truncated -- fix the key;
* getting **200 `does not exist`** means your header is not being sent at all
  -- an unset environment variable, a `requests` session that dropped it across
  a redirect, a proxy stripping it -- and the table is probably fine;
* getting **429** means you are throttled and have learned nothing about the
  table either way.

Three different causes for one symptom, and the status code separates them.

What the skill says now: nothing about 403. A reader who has the ambiguity
lesson knows to suspect the header but has no way to tell which way it failed.

What it should say: before concluding a draft is missing, repeat the request
with a deliberately invalid token. If that answers **403**, your client really
does send the header -- and then your real key must be valid too, or it would
have been refused the same way, so the `does not exist` is about the table and
not about your credentials. If the deliberate-garbage request answers **200
`does not exist`** instead, nothing you put in the header is reaching the
server and the table is probably fine.

Evidence: `numberdb_app/throttle.py:88-106` (`requester_of`; a bad token
returns `None, None, False` rather than the anonymous scope) and `:176-187`
(the 403 is returned from `guarded` before `_consume` is called, so it costs no
allowance); measured 2026-09-23 11:40Z against numberdb.org.

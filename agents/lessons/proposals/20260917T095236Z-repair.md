## Avoid symbolic `sqrt` imports in numeric Sage checks
What happened: while repairing T296, the Sage check script imported `sqrt` from `sage.functions.other` after `numberdb.sage`. Under `sage -python` this reached `sage.functions.trig` and then `sage.symbolic.function`, failing with `AttributeError: cannot access submodule 'function' of module 'sage.symbolic'`. Replacing symbolic `sqrt` with the parent field's `.sqrt()` kept the check entirely in `ComplexBallField` and the script ran.

What the skill says now: it warns that named imports can leave Sage machinery uninitialised and lists several missing imports, but it does not name symbolic `sqrt`.

What it should say: for numeric generators and checks, avoid `from sage.functions.other import sqrt`; use the numeric parent, such as `CBF(2).sqrt()` or `QQ(2).sqrt()` only when the result is meant to be symbolic. Importing `sqrt` from Sage's function modules can pull in the symbolic layer in a `sage -python` run.

Evidence: `agents/sage.sh /tmp/t296_checks.py /tmp/t296-table.json /tmp/t19-table.json`, 2026-09-17, first failed at `from sage.functions.other import sqrt` with the symbolic circular-import traceback; after changing to `CBF(...).sqrt()` it checked the $r=10$ closed form, the theta and hypergeometric identities, the class-number range, and Watson's formula.

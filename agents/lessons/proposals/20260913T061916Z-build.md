## `write_table` cannot revise an empty draft into another empty draft

What happened: T223 was claimed through `POST /api/tables` with `X-Draft:
yes`, which correctly created a prose-first draft with no numbers. After the
range was narrowed from all simplex groups to the compact rank-4 slice, the
run tried to replace the draft document with the final prose and `Numbers:
[]`. The server refused the whole-document edit with `A table needs at least
one entry`, even though the target table was already an unpublished draft.
Filling the entries first, then replacing the full document while preserving
those entries, succeeded.

What the skill says now: create the draft before building, with title first
and prose if available, then fill it once after the checks.

What it should say: the API permits an empty document only at draft creation.
If the prose has to change before the first values are written, do not create
a second draft. Either get the prose right in the initial claim, or fill the
first checked entry block and then use `write_table` with a full non-empty
document that preserves the entries. Reattach the generator if the
whole-document edit becomes the head revision.

Evidence: T223, 2026-09-13. `/tmp/update_t223_doc.py` posted the final
document with `Numbers: []` and received the refusal above. The later fill
stored 9 entries in revision `e244205819794a289dc8e4d03f4388ddbdfb7bb8d7baff6776cd2d2dce35cfea`;
`/tmp/finalize_t223_doc.py` then posted the final prose with those entries and
the API accepted revision `e69565b2a4ed3ce81b471cbdce130b0cbc6a6105a0f96a291ee3a6377a4fcda2`.

# Lessons proposed by the T13 growth critique, 2026-09-21

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## Where a family is the coefficients of an asymptotic series, its range follows from the precision it serves

What happened: T13 holds the Bernoulli numbers for $0 \leq n \leq 100$ and
says nowhere why it stops there. Reading it for growth, the usual questions
gave no answer: it uses 4479 bytes of a 320 KB limit and 101 of 1200 entries,
so no limit chose 100, and "include what is common, and stop" does not say
where common ends for a family whose members are used a thousand at a time by
somebody else's computation.

For this kind of family there is an answer that can be measured. The large
Bernoulli numbers are met as correction terms in Euler-Maclaurin and Stirling
expansions, and an asymptotic series is truncated near its smallest term. For
$\log\Gamma(z)$ the terms are $B_{2k}/(2k(2k-1)z^{2k-1})$; computed in Sage,
the smallest term sits at

    z = 10   2k = 64    1e-28
    z = 20   2k = 128   1e-56
    z = 30   2k = 190   1e-83
    z = 36   2k = 228   1e-100
    z = 50   2k = 316   1e-138

which is $n \approx d/\log 10 \approx 2.3\,d$ for $d$ digits. So a table of
Bernoulli numbers serving the 100 digits this corpus works to wants $n$ up to
about 230, and one stopping at $n = 100$ serves about 44 digits: its range
stops below the precision of the work that produces its values. That is a
sharper statement than "it could be bigger", and it writes itself into the
completeness note as an argument rather than a bound.

The same reasoning has a target elsewhere: any table of coefficients that
exist to be summed -- Euler-Maclaurin, Stirling, Gauss quadrature orders,
the coefficients of a Lanczos or Spouge approximation, tangent and Genocchi
numbers -- has a range fixed by the precision its user is aiming at, and the
smallest-term index is a two-line computation.

What the skill says now: section 3 gives the size measurements for polynomial
families indexed by degree and the "n up to about 100 is the house range"
rule, and section 2 says to hold the numbers that turn up and to say which
range you chose and why. Neither says that for one common kind of family the
range is not a matter of taste: it can be computed from the precision the
values are used at.

What it should say: where the entries are the coefficients of a series
somebody truncates, find the index at which the terms stop shrinking at the
precision the table is serving, and make that the range. State it in
`complete-note`: "it holds $B_n$ for every $n$ with $0\leq n\leq 250$, which
covers the Euler-Maclaurin expansions used at up to about a hundred digits" is
a sentence a reader can check, and a byte count is not.

Evidence: 2026-09-21, T13 growth critique, `agents/critiques/T13-growth.md`.
The table above is `/tmp/stirling.py` run through `agents/sage.sh`, minimising
`abs(B_n / (n*(n-1)*z^(n-1)))` over even $n < 800$ at 200 bits. Entry sizes in
the same critique come from `len(str(bernoulli(n)))`: 90 characters at
$n = 100$, 304 at $n = 250$, 1112 at $n = 672$, where the skill's own
readability line on the Fibonacci polynomials (1107 characters) falls.

## A generator written before the current data model is a record, not a way to extend the table

What happened: T13's attached `generate.sage` (2021, 508 bytes, unchanged)
ends with `yaml.dump(numbers, stream=open('data/Combinatorics/Bernoulli_numbers/numbers.yaml', 'w'))`.
It writes a file into a repository layout that no longer exists, subclasses
nothing, talks to no API and has no `--publish`. Reading the files page it
looks exactly like a generator that could be rerun with a larger bound: the
range is right there as `for n in range(100+1)`. It cannot. Anybody extending
the table has to write a new `numberdb.Generator` first, and that is a
different-sized job from "change 100 to 250".

The file also carries, inside a triple-quoted string, an abandoned attempt to
give each zero entry an `equals` link, with a brace missing, so it could not
have been enabled even when it was written. Dead code in an attached file
reads as an intention the next person should carry out.

What the skill says now: section 6 says a generator fills a table and gives
the shape of one, and section 4 says `Programs` and `generate.py` answer
different questions. It says nothing about what to do when the attached file
predates the package.

What it should say: before planning an extension, check that the attached
generator is one the package can run -- a `numberdb.Generator` subclass with
`verify()` and `publish()` -- rather than a script that wrote a file into
whatever layout existed when the table was made. Where it is not, the old file
is a record of how the numbers were made and should stay; the extension needs
a new generator beside it, and commented-out code in the old one should be
deleted rather than inherited.

Evidence: 2026-09-21, T13. `https://numberdb.org/files/T13/generate.sage?raw=1`
is 508 bytes and imports `utils.utils`; the T13 history shows the data-model
migration of 2026-08-09, "entries rewritten as records with named parameters",
five years after the file was last touched on 2021-03-03.

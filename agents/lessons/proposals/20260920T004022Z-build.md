## Exact rational components in complex tables may need Python `Fraction`
What happened: T346 stores complex roots, but some roots are rational. Returning
`numberdb.ComplexInterval(q, 0)` for such a root was refused under
`rigour = "proven"` as a point interval. Returning a Sage `Rational` satisfied
`agents/table-build/dry_run.py`, but the installed client in the Sage image
still refused the value and told the generator to return an `int` or Python
`Fraction`. Returning `Fraction` satisfied the client for rational roots, while
the dry-run helper had to be taught that `Fraction` is exact. The same table
also had exact Gaussian-integer roots such as $-1-3i$; those had to be returned
as `numberdb.ComplexInterval(Fraction(-1), Fraction(-3))`, not as zero-width
Sage complex intervals.

What the skill says now: exact rationals may be returned as `Fraction` or
`QQ(a)/b`, and exact rational values should be written exactly. It does not say
that exact real entries inside a complex-valued table may need to be bare
rationals rather than complex intervals with imaginary part zero.

What it should say: in a `type = "C"` table, if a value lies exactly on the real
axis and is rational, return it as an exact rational (`int` or `Fraction`) rather
than as a zero-width complex interval. If both complex parts are exact
rationals, return `numberdb.ComplexInterval` with exact rational parts. The
complex parser can still store these in the table, and `proven` will otherwise
refuse zero-width Sage intervals as unjustified point enclosures.

Evidence: on 2026-09-20, filling T346 first refused
`15,481,4879,4,4` with "rigour is 'proven', and this value carries no error of
its own" when it was returned as `ComplexInterval(-1, 0)`. Returning Sage
`Rational(-1)` passed dry-run but the installed client gave the same refusal.
Returning `fractions.Fraction(-1, 1)` for real roots and
`numberdb.ComplexInterval(Fraction(-1), Fraction(-3))` for $-1-3i$ let the fill
proceed after `agents/table-build/check.py` accepted `Fraction` as exact.

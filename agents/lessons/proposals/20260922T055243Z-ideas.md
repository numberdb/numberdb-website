## A Sage method that takes a prime often refuses a Python `int`

What happened: screening a batch of $p$-adic invariants of elliptic curves, the
feasibility probe called `E.tate_curve(11)` and `E.padic_height(5, 20)` with
ordinary Python integers, because `sage -python` has no preparser and a literal
`11` in a script is an `int`. Both raised

    AttributeError: 'int' object has no attribute 'is_prime'

which reads as a fault in the curve, not in the argument: nothing in it names
the parameter that was wrong. `E.padic_regulator(5, 20)` in the *same script*
accepted the same `int` and returned the right answer, so the error looked
like a property of `tate_curve` rather than of the literal. With `ZZ(11)` and
`ZZ(5)` all three work.

What the skill says now: it warns that `sage -python` has no preparser, in the
one place it costs exactness, "`factorial(30)` is a Python `int` and
`factorial(n) / k` is float division". The type of a *loop variable* passed
into a Sage method is not mentioned.

What it should say: the missing preparser bites twice. Division is the first
way; the second is that a Sage method which asks its argument a Sage question
(`p.is_prime()`, `p.prime_divisors()`) raises `AttributeError` on a Python
`int`, and the message names the method it wanted rather than the argument.
Wrap every integer a generator enumerates in `ZZ(...)` at the point it is
made, not at the point it is used, because the methods that tolerate an `int`
and the methods that refuse one sit side by side in the same module.

Evidence: `/tmp/padic_probe.py` and `/tmp/padic_probe2.py`, run with
`agents/sage.sh` on 2026-09-22. `E.tate_curve(11)` fails, `E.tate_curve(ZZ(11))`
returns the Tate curve; `E.padic_regulator(5, 20)` succeeds with the `int`.

## Two p-adic elements can be unsubtractable while printing the same parent

What happened: checking the interpolation formula
$L_p(E,1) = (1-1/\alpha)^2 L(E,1)/\Omega_E$ over a list of curves, the run
reached a *supersingular* prime, where the unit root $\alpha$ is not in
$\mathbb{Q}_p$ but in a ramified quadratic extension. Subtracting the two
sides raised

    TypeError: unsupported operand parent(s) for -:
      '5-adic Eisenstein Extension Field in alpha defined by x^2 + 5' and
      '5-adic Eisenstein Extension Field in alpha defined by x^2 + 5'

The two parents print identically and are not the same object, so the message
says nothing a reader can act on. The real content is that the check had
silently left $\mathbb{Q}_p$: at a supersingular prime
`E.padic_lseries(p).alpha()` returns an element of
$\mathbb{Q}_p(\sqrt{-p})$, which is not a value a `Qp` table can hold at all.

What the skill says now: `Qp` is one of the searchable types, and a `Qp`
element records its own `O(p^n)`. Nothing about extensions.

What it should say: a quantity defined by "the unit root of Frobenius" or "the
$p$-stabilisation" exists in $\mathbb{Q}_p$ only at *ordinary* primes. At a
supersingular prime the same code returns an element of a ramified quadratic
extension, which is a different type and does not belong in the same table.
Constrain the parameter to ordinary primes in the definition rather than
filtering exceptions out of the loop, and read a `TypeError` between two
identically printed p-adic parents as "these are two different extensions, or
two constructions of one", not as a coercion bug.

Evidence: `/tmp/padic_probe2.py` and `/tmp/padic_probe3.py`, 2026-09-22.
`EllipticCurve('14a1').padic_lseries(ZZ(5)).alpha().parent()` is the Eisenstein
extension above, and `E.is_ordinary(5)` is `False`; at `p = 3` and `p = 5` for
`11a1`, which are ordinary, both sides subtract and agree to the precision of
the series.

## A p-adic identity that divides by the quantity loses twice its valuation

What happened: the Tate parameter $q_E$ was checked against the $j$-invariant
through $j = 1/q + 744 + 196884q + \dots$, which is an independent check worth
having, since the coefficients are HREF-able in the corpus (T79). The check
passed, but not to the precision the value carries:

    curve  p    ord_p(q)   q abs prec   valuation of j(q) - j(E)
    11a1   11   5          25           15
    14a1   7    3          23           17
    15a1   5    4          24           16
    130a1  5    3          23           17

The gap is exactly $2\,\mathrm{ord}_p(q)$: forming $1/q$ turns an absolute
precision $N$ into $N - 2\,\mathrm{ord}_p(q)$.

What the skill says now: "an enclosure that contains everything agrees with
everything", and to check that a comparison means something before believing
it. That is the real-analytic form of the same rule.

What it should say: the p-adic form of the rule is that a check reports a
*valuation*, and what makes it a check is comparing that valuation against the
precision the two sides actually carry, not against zero. Write the expected
loss down before running it: an inversion costs $2v$, a division by $n$ costs
$\mathrm{ord}_p(n)$, a logarithm costs about $\mathrm{ord}_p$ of its index.
A check that stops one digit short of the precision is passing; one that
agrees to full precision is often circular, because the same code computed
both sides.

Evidence: `/tmp/padic_probe2.py`, 2026-09-22, the four rows above. The same
run's comparison `log(u)/n - L_invariant` agreed to the *full* precision 20,
which is the circular case: Sage's `L_invariant` is implemented as `log(u)/n`.

## `Numbers` comes back with whatever shape the draft was authored with: a mapping when filled, `[]` when not

What happened: I read T443, T444 and T445 back over the API to count their
entries, with `len(doc["Numbers"])` — 1001, 3, and 0. Then I printed the types,
because a count of 0 had been misleading once already that hour, and the third
one is not the same kind of object as the first two:

    T443  Numbers  dict  len 1001     (filled)
    T444  Numbers  dict  len 3        (filled)
    T445  Numbers  list  len 0        (draft, never filled)

A filled table's `Numbers` is a JSON object keyed by parameter values. An
unfilled draft's is an empty JSON **array**. `len()` is defined on both and
returns what you expect, so a count-only reader never notices; anything that
goes on to iterate the mapping —

    for params, value in doc["Numbers"].items():

— raises `AttributeError: 'list' object has no attribute 'items'` on exactly
the table you were trying to diagnose, and on no other. The failure lands on
the empty draft, which is the case you reach for the diagnostic in the first
place, and it reads like a broken script rather than like an answer.

This is not a special empty-case representation the server chose. `/api/table`
serves the document as its author wrote it: `_ordered_document`
(`numberdb_app/api.py:334-372`) loads `TableData.full_yaml` with
`yaml.safe_load` and returns it unchanged if it parses to a dict, falling back
to the jsonb column only when it does not. Nothing on that path normalises
`Numbers`, or checks that it is a mapping, or supplies one when it is absent.
So the shape you get is the shape the draft was created with — and a draft
created with an empty `Numbers:` list keeps a list until something fills it.
The corollary is the useful part: **this is not specific to `Numbers`.** Any
key of the served document is as the author left it, and a reader that assumes
a schema the API does not enforce is guessing.

It also explains the neighbouring failure recorded at `PROPOSALS.md:4784` and
`:5043` from the write side — `'str' object has no attribute 'items'` out of
`Generator.publish()`'s preflight on an empty draft. Same class of fault, same
missing normalisation, opposite direction. Those two entries tell a contributor
what to do when `publish()` trips; neither tells them the read comes back
untyped too.

What the skill says now: it describes `Numbers` as the table's entries, keyed
by the parameters, and every example it shows is of a filled table. It does not
say the key may be absent or of another type, and it gives no shape to test
against before iterating.

What it should say: after `GET /api/table`, check the body for `"error"` first
(`20260923T121307Z-triage.md`), then check that `Numbers` is a mapping before
iterating it — do not infer "empty" from `len(...) == 0` and carry on. The
three states a contributor meets are distinguished by type, not by count:

    doc = get(f"/api/table?id={tid}")
    if "error" in doc:                      # 200, but no such table
        ...
    nums = doc.get("Numbers")
    if not isinstance(nums, dict):          # [] or None: a draft, never filled
        ...
    for params, value in nums.items():      # only now
        ...

And, generally: the API returns the author's document, not a validated schema.
Test the shape of anything you are about to index into.

drafts zeta3 holds.

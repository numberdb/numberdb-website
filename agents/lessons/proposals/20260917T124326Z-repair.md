## Polynomial irreducibility can need fuller Sage initialization than named ring imports provide

What happened: while repairing T301, a scratch Sage check imported
`numberdb.sage`, `ZZ`, and `PolynomialRing`, then called
`stored.is_irreducible()` on the integer polynomials read from the table. Under
`agents/sage.sh` this failed inside Sage's factorization path with
`ImportError: cannot import name PolynomialSequence_generic`. Running the same
check after importing `PolynomialRing` and `ZZ` from `sage.all` initialized the
missing pieces and the irreducibility checks passed for all 47 polynomials.

What the skill says now: it says to name the rings a generator uses rather
than importing `sage.all`, and lists several Sage features that named imports
do not bring in. It does not mention univariate polynomial factorization or
`is_irreducible()`.

What it should say: if a verification script or generator calls Sage's
polynomial factorization methods, run that exact import set before trusting the
check. A one-off verification script may fully initialize Sage; a generator
should either add the specific initialization its factorization call needs or
avoid that method, then run under `sage -python` before publishing.

Evidence: T301 repair on 2026-09-17.
`NUMBERDB_REMOTE=local agents/sage.sh /tmp/check_t301.py /tmp/T301-live.json /tmp/T284-live.json`
failed at `stored.is_irreducible()` with the `PolynomialSequence_generic`
ImportError. After the script used `from sage.all import PolynomialRing, ZZ`,
the same check reported that all 47 T301 polynomials matched their coefficient
keys, were monic reciprocal, and were irreducible.

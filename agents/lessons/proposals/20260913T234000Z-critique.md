## Programs uses the library's method when one exists, and the table often names it already

What happened: T239's `Programs` holds 21 lines of Sage that list every set
of $k$ edges of a graph and keep the matchings, to build the matching
polynomial. Its own `rigour details` says "Sage's `matching_polynomial()`
agreed with the signed form on every row", so the build had used the
method. `Graph('EIe_').matching_polynomial()` is one line and returns the
stored row. With `n = G.num_verts()`, the other stored form is
`sum(abs(mu[n-2*k]) * x**k for k in range(n//2+1))`, which agreed with all
996 rows. The hand enumeration grows exponentially in the number of edges,
so a reader who copies it for a slightly larger graph waits for an answer
that Sage would have given at once.

What the skill says now: "`Programs` is the standard incantation in Sage,
PARI or mpmath for a reader who wants one more value." It does not say what
to do when the generator computed the values some other way.

What it should say: the incantation is the library's own call, where the
library has one. A generator may compute differently, for independence or
speed, but that is the generator's business and does not belong in
`Programs`. Before writing a snippet, search the library for the object's
name (`G.matching_polynomial`, `pari.ellan`, `mpmath.zeta`). If the
`rigour details` names a function the values were checked against, that
function is the snippet.

Evidence: 2026-09-13, T239 critique. `agents/sage.sh /tmp/c239/sage_checks.py`
printed "one-liner and derived M disagree on 0 of 996", and the replacement
snippet printed `x^6 - 6*x^4 + 9*x^2 - 2 | 2*x^3 + 9*x^2 + 6*x + 1`.

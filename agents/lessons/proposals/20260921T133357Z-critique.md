# Lessons proposed by the T383 critique, 2026-09-21

Nothing here is in force. Format as in `agents/lessons/PROPOSALS.md`.

## The file attached to a table is a snapshot of the last fill, not of your disk

What happened: T383's page offers `generate.py`, and the copy it serves is an
older revision than the one that produced the table's current state. The two
differ in one function, `stored_values()`, which reads the `Numbers` mapping:
the attached copy expects a flat `"n,m"` key and the API returns the nested
`{n: {m: value}}` shape. So the command the file's own header gives a reader,
`sage -python generate.py`, prints `<VerifyReport T383: 666/666 matched>` and
then dies with `ValueError: not enough values to unpack (expected 2, got 1)`.
The file on disk, run the same way, finishes cleanly. The attachment went up
when the values were last written; the fix to the file came afterwards, no
values changed, so nothing re-attached it, and neither the table page nor
`audit_table` can see that the two have diverged — the audit reads the
document, and checks an attachment only for a run command in its first forty
lines.

What the skill says now: "`Programs` and `generate.py` answer different
questions ... `generate.py` is the program that reproduces and extends *this*
table, attached to it." Nothing about when the attachment is written, or about
its going stale.

What it should say: the attachment is written when values are published, so a
generator edited after the last fill leaves readers the old one. After any edit
to a generator, download `/files/<tid>/<name>` and diff it against the file you
just changed, or republish so the attachment is rewritten. The check is worth
making at the end of a build, because a program that reports a table correct
and then crashes is a worse first impression than no program at all.

Evidence: 2026-09-21, T383 critique. `/files/T383/generate.py` against
`generators/trinomial-discriminants/generate.py`, one differing hunk; both run
through `agents/sage.sh`, the attached copy raising `ValueError` at
`stored_values()` and the working copy printing "stored values match the
independently checked generator".

## `.discriminant()` is one of the things the named ring imports do not bring

What happened: checking T383's values meant asking Sage for the discriminant of
`x^n + a*x^m + b` over `ZZ[a,b]`. Written the way the skill's generator
template writes imports —

    import numberdb.sage as numberdb
    from sage.rings.integer_ring import ZZ
    from sage.rings.polynomial.polynomial_ring_constructor import PolynomialRing

— the call fails, not with a missing name but with

    AttributeError: cannot access submodule 'function' of module
    'sage.symbolic' (most likely due to a circular import)

raised inside `polynomial_element.pyx`, which reaches `lazy_series_ring` and
from there `sage.functions.other`. Adding `import sage.all` before the call
makes the same expression return the right polynomial. The failure is not about
polynomials: it is the general shape of a Sage method that reaches the symbolic
ring from a module tree that was never fully initialised.

What the skill says now: "Name the rings you use, rather than importing
`sage.all`", then "What else the named imports do not bring: root finding
(`sage.numerical.optimize`), `RealBall.str`, and `QQ('1.25')`".

What it should say: add `Polynomial.discriminant()` to that list, with the
symptom, because the error names a circular import rather than a missing
import and reads like a broken Sage. Where a method reaches the symbolic ring,
`import sage.all` first — it costs startup time and nothing else, and the
alternative is to write the identity out (`f.resultant(f.derivative())` needs
no such import).

Evidence: 2026-09-21, T383 critique, `/tmp/t383_check.py` and
`/tmp/t383_check2.py` through `agents/sage.sh`: "bare discriminant() raises:
AttributeError ...", "after import sage.all: 16*a^4*b - 128*a^2*b^2 + 256*b^3".

## A resultant over a multivariate base ring is not a way to compute a table

What happened: T383 holds `disc(x^n + a*x^m + b)` in `ZZ[a,b]` for `n` up to
37. The obvious route — the resultant of `f` and `f'` over `ZZ[a,b]`, which is
also the table's stated convention — costs 27 seconds at `(n,m)=(8,3)` and did
not finish `(9,6)` in 900 MB, nor in eight minutes at the same pair by the
resultant directly. Swan's closed form fills all 666 rows in under a second.
The generic resultant is a determinant of a Sylvester matrix over a polynomial
ring, and its intermediate expression swell is exponential in the degree, so
the cost is not "slow for the big rows" but "unreachable past about `n=9`".

What the skill says now: "Values that grow" is about the *stored* size, with
the Chebyshev table of characters per entry. Nothing about the cost of the
route to the value.

What it should say: where a family has both a closed form and a generic
construction, measure the generic one at the top of the intended range before
choosing the range, and expect symbolic linear algebra over a polynomial ring
to fall off a cliff rather than degrade. This has a consequence for `Programs`
as well: that section is meant to hand a reader the standard incantation, and
where the standard incantation cannot reach the table's range, the honest block
is the closed form the generator used, even though it repeats a formula the
table already states.

Evidence: 2026-09-21, T383 critique. `/tmp/t383_check3.py` through
`agents/sage.sh`: `ZZ[a,b] n=8 m=3 discriminant() agrees 27.43s`, then no
further line — the container was killed at `(9,6)` with
`NUMBERDB_SAGE_MEMORY=900m`; `/tmp/t383_check2.py`, eight minutes on the same
pair by `f.resultant(f.derivative())`.

## `/api/search` takes `expression`, and answers an unknown parameter with an empty result set

What happened: checking whether somebody holding one of T383's polynomials
would find it, `GET /api/search?q=Chebyshev` returned
`{"results": [], "messages": [], "time_request": "0.000s"}` — and so did
`q=3.14159`, `q=x^2-x-1` and every other term tried, while the website's own
search, `GET /?q=Chebyshev`, answered with 12 results. The endpoint reads
`expression`, not `q`, and an absent `expression` returns the empty envelope
with no message in it, so a wrong parameter name is indistinguishable from a
term that matches nothing. `expression` is an evaluator, not the search bar:
`expression=pi` returns the stored value of $\pi$, and `expression=x^2-4*y`
answers "Unknown or not-allowed name 'x'". Searching for a polynomial is a
different endpoint again, `GET /api/lookup?polynomial=x^2-x-1`, which found the
value in T217.

What the skill says now: nothing about the HTTP endpoints behind search. It
names `numberdb.search_text` and `search_polynomial`, which send the right
things, and warns that `search_text` returns an object with a `.tables` list
rather than a list.

What it should say: reach search through the package rather than by hand, and
if you do call the API directly, `api/lookup` is the one that takes a number or
a polynomial. An empty `results` from `api/search` may mean the parameter was
not understood, so check `messages` and check a term you know is there before
concluding the corpus does not hold something.

Evidence: 2026-09-21, T383 critique. `curl -s -G --data-urlencode "q=Chebyshev"
https://numberdb.org/api/search` gave an empty result set;
`https://numberdb.org/?q=Chebyshev` gave "12 results for Chebyshev";
`api/lookup?polynomial=x^2-x-1` returned the T217 entry `31.2.a.a,2`.

## A generator that loops over a hard-coded list of cases promises more in `complete-note` than the loop can deliver

What happened: T345 holds the kernel polynomial of every rational isogeny of
prime degree $\ell\geq5$ of every elliptic curve over $\mathbb{Q}$ of conductor
at most 300, and its `complete-note` says exactly that. Its generator gets the
degrees from

    PRIME_DEGREES = tuple(ZZ(p) for p in (5, 7, 11, 13, 17, 19, 37))

Over $\mathbb{Q}$ the prime degrees a rational isogeny can have are
2, 3, 5, 7, 11, 13, 17, 19, 37, **43, 67 and 163** (Mazur, Kenku), so three
cases are missing from the list. Nothing is wrong with the table: reading every
prime degree off the isogeny-class matrix of all 1172 curves with $N\leq300$
gives only 5, 7, 11, 13, and the 118 rows are all of them. The fault is in the
file the table serves to a reader: whoever raises the conductor bound inherits
a loop that cannot find a 43-, 67- or 163-isogeny, and the note above it will
still say "every rational isogeny of prime degree $\ell\geq5$". A run that
checks its own output against its own list can never see this -- both sides
agree.

What the skill says now: that a parameter states the constraint the entries
actually satisfy, and that what was computed belongs in `complete` and
`complete-note`. Nothing about the third thing, which is what the generator's
enumeration covers -- and it is the one a reader inherits.

What it should say: where the library will enumerate a parameter for you, let
it, and filter afterwards -- `E.isogenies_prime_degree()` with no argument, or
read the degrees off the isogeny class, rather than looping over the degrees you
expect. Where a fixed list is unavoidable, the theorem that closes the list
belongs in the table beside the values, so the next person can see whether the
list is complete or merely long enough. A `complete-note` is a claim about the
family; a generator's loop is a claim about the run; they are only the same
sentence when something has checked that the list is the whole of the family.

Evidence: T345 on 2026-09-20, `generate.py:39`. Reading the degrees instead of
listing them, over `CremonaDatabase().allcurves(N)` for $N\leq300$ (1172
curves), gave `[(5, 82), (7, 26), (11, 6), (13, 4)]`, total 118, against the
table's 118 rows.

## Check a definition by implementing it from the page, not from the generator

What happened: the T345 critique had to judge whether its definition is
"precise enough that two people would build the same table". The way that got
an answer was to treat the rendered definition as a specification and write a
second program from it: T345's definition recovers the Weierstrass model from
the stored $(c_4,c_6)$ by a formula in its own `Formulas` block, so the check
re-implemented that formula, rebuilt each curve from the two stored integers,
enumerated its isogenies, picked the one whose codomain matched the stored
target invariants, and compared kernel polynomials. All 118 rows agreed, and
the conductor and the Cremona label in each entry comment agreed too. That is a
stronger statement than `verify()` makes: `verify()` re-runs the generator and
says the values are reproducible from the *code*, and this says they are
reproducible from the *document*, which is what a reader has.

It also finds the failure that version does not. A definition can name a
quantity and defer what it is to an external link -- T345's says "its monic
kernel polynomial $K_\varphi(x)\in\mathbb{Q}[x]$" and cites an LMFDB knowl --
and a checker reading the generator never notices, because the generator calls
a library function whose name carries the meaning. Writing the second program
from the page is what makes the gap visible: anything you had to look up
elsewhere to write it is missing from the table.

What the skill says now: "Check new values against something independent. Not
the code that produced them", and, about a table that could not be reproduced
from its own definition, that it failed to say which square root it took. It
names that failure and does not say how to catch it.

What it should say: before publishing, write the value of one entry -- or of
every entry, if they are cheap -- from the table's own definition and formulas
alone, in a file that does not import the generator, and do not look anything
up that the table does not state. What you have to look up is what the
definition is missing. Where the definition pins a model or a normalisation by
a formula in the table, that formula is the thing to implement, and doing so
also checks that it is well posed: T345's recovery is unique because its six
admissible $b_2$ are distinct mod 12 and $-c_6\equiv b_2^3\equiv b_2$ there,
which is visible when you write it and invisible when you read it.

Evidence: T345 on 2026-09-20. `/tmp/crit345/check345.py`, one `agents/sage.sh`
run: "118 rows rebuilt from the Definition, 0 disagreements", with the model
built from $(c_4,c_6)$ by the table's Formula (1) rather than from the Cremona
database the generator reads.

## To ask whether a *value* is already in the corpus, `api/lookup` wants a `kind`, and `api/search` will not take a polynomial at all

What happened: the T345 critique wanted the question a reader asks -- does the
corpus already answer this polynomial, and with how many tables? -- and lost
four requests to the shapes the two endpoints accept. `api/search` takes
`expression` and evaluates it in a sandboxed Sage, so a polynomial is refused
as a name error:

    GET /api/search?expression=x^2+-+21*x+%2B+80
    {"results": [], "messages": [{"tags": "alert-danger", "text":
     "Unknown or not-allowed name 'x'. Only mathematical functions and
      constants provided by the search environment may be used."}]}

That is the dangerous one: `results` is an empty list, exactly like a real
answer of "nothing in the corpus holds this", and a script that reads
`results` and not `messages` concludes the value is new. `api/lookup` is the
endpoint for a value one already has, and it wants a JSON *record* with a
`kind`:

    number=x^2-21*x+80                      -> "number is not valid JSON."
    number=["x^2-21*x+80"]                  -> "number record must be an object"
    number={"type":"Q[]","value":"..."}     -> "unknown number kind None;
                                               expected one of CIF, QQ, Qp,
                                               RBF, RIF, ZZ, polynomial"
    number={"kind":"polynomial","value":"x^2-21*x+80"}   -> one hit, T345

The third error lists the kinds and never says that `kind` is the key it looked
for, so the obvious next guess is another value for `type`.

What the skill says now: section 1 says to search the corpus before writing
anything and gives `search_text` and `numberdb.table`, which answer about the
*family*. It says nothing about asking after a single value from outside the
Python client, and the table of types lists `Z[]`, `Q[]` and the rest -- which
are the `type` a table declares, not the `kind` a lookup takes.

What it should say: to ask whether a number or polynomial you are holding is
already stored, `GET /api/lookup?number={"kind":"polynomial","value":"x^2 - x
- 1"}`; the kinds are `ZZ`, `QQ`, `RBF`, `RIF`, `CIF`, `Qp` and `polynomial`,
and they are not the `type` names a table declares. `api/search` is for an
expression to evaluate and cannot be given a polynomial in `x`; when it
refuses one it answers with an empty `results` and the reason in `messages`, so
read `messages` before believing an empty result.

Evidence: 2026-09-20, against numberdb.org.
`{"kind":"polynomial","value":"x^2-21*x+80"}` answered with T345 alone,
`x^2+x-1` with T146, T217 and T345, and `x^2-1` with six tables -- which is
also how the critique judged what those rows contribute to search.

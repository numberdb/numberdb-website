## A draft can trip the tag-reach audit for a tag the finished batch is meant to grow
What happened: the family for sharp constants in classical inequalities said to use
`functional analysis` and `inequality` on all six tables. Both tags existed and
each reached T92 publicly before the batch. The Nash draft T359 used those tags,
as instructed, and `/api/table/T359/audit` reported both as reaching only this
table. Reading `/api/tag?url=functional+analysis` and `/api/tag?url=inequality`
with the draft author's key showed each tag still had `table_count: 1`, namely
T92. The audit rule counts the public tag reach; an unpublished draft does not
make the tag count as a two-table route yet.

What the skill says now: prefer an existing tag; audit refuses a tag that reaches
only this table. The family issue may also explicitly say to use a tag that
currently reaches one table because this batch is meant to make it useful.

What it should say: when a screened family explicitly tells every table in the
batch to use an existing one-table tag, keep the family tag even if a draft audit
reports the tag-reach finding. Confirm the tag already reaches a public table,
record the audit finding in the build report, and let review/publication make the
route real. Do not replace the family tag with a vaguer one just to make a draft
audit clean.

Evidence: T359 on 2026-09-20; `python3 /tmp/audit_table.py T359` reported
`Tags: "functional analysis" reaches only this table` and the same for
`inequality`; authenticated `GET /api/tag?url=functional+analysis` and
`GET /api/tag?url=inequality` each returned T92 as the only public table.

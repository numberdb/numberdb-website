## Parse ecnf-data `mwdata` from its format file
What happened: while checking T293 against the pinned ecnf-data source, the live table could only be compared correctly after reading `ecnf-format.txt` for the `mwdata.*` column order. The regulator is the `reg` column after `heights`, at zero-index `10` in a whitespace-split row; nearby columns such as `omega` and `Lvalue` are also decimal numbers and can look plausible if counted from the end.

What the skill says now: nothing specific about ecnf-data file formats.

What it should say: when reading ecnf-data `mwdata.*`, use the column order in `ecnf-format.txt`. After the four label columns, the fields are `rank`, `rank_bounds`, `analytic_rank`, `ngens`, `gens`, `heights`, `reg`, `torsion_order`, `torsion_structure`, `torsion_gens`, `omega`, `Lvalue`, and `sha`.

Evidence: T293 repair on 2026-09-19. `/tmp/t293_live_check.py` read `mwdata.2.2.{5,8,12,13,17,21}.1` at commit `10b28418e80392032b106ea00e6c5aa109d28e7b`, used `parts[10]` for `reg`, and found 1171 expected rows with 0 regulator interval mismatches against the live table.

## Treat `?` ranks in ecnf-data as unknown
What happened: the same T293 source check met rows whose `rank` column is `?`. Those rows are not positive-rank source rows, and a range count should leave them out unless a source or a person has settled their rank.

What the skill says now: nothing specific about unknown ranks in ecnf-data.

What it should say: when filtering ecnf-data `mwdata.*` rows by rank, treat `?` as unknown. Do not include those rows in a positive-rank table merely because the parser is looking for nonzero rank; report how many unknown rows were skipped if the coverage count matters.

Evidence: T293 repair on 2026-09-19. The pinned files for $D\in\{5,8,12,13,17,21\}$ contained unknown-rank rows, counted as 9, 23, 16, 10, 8, and 30 respectively by `/tmp/t293_live_check.py`; the positive-rank rows with conductor norm at most 250 still matched the live table exactly.

# Lessons proposed by the T286 growth critique, 2026-09-20

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

---

## A family converging to a constant the corpus already holds has its range decided by search, not by size

What happened: T286 holds the first 50 Pisot numbers in $(1,\varphi)$. The
family is infinite and increases to $\varphi$, so the table can never be
complete and the only real question is where to stop. Three of the four
constraints a range is usually chosen against turned out not to bind anywhere
near the interesting place:

  * size -- entry text is 10.1 KB at rank 50 and 60.5 KB at rank 190, so the
    block would be about 111 KB at rank 190, inside the 320 KB soft limit;
  * readability -- the longest entry comment is 251 characters at rank 50 and
    881 at rank 190, under the line the skill draws at 1107 for a Fibonacci
    polynomial;
  * precision -- neighbouring values stay distinct at 100 digits until about
    rank 460.

What binds instead is that $\varphi-\theta_r$ falls like $\varphi^{-n}$, so
each further entry is one more decimal place of agreement with a constant the
corpus already holds as a table of its own. Counting the rows a search for
$\varphi$ written to $k$ places would return:

    query for phi     rows of T286 inside it, if the table stops at
    to k places       r=50      r=100     r=150     r=190
      3 (1.618)         26        76        126       166
      5 (1.61803)        8        58        108       148
      8                  0        28         78       118
     10                  0        10         60       100

Rank 50 is the last rank at which somebody holding $\varphi$ to eight digits --
which is what a numerical computation hands back -- gets $\varphi$ and not a
Pisot number.

The check is cheap and a contributor can run it: for each $k$, count the stored
values inside the interval the $k$-place decimal denotes, which is the centre
plus or minus one unit in the last place. Then ask the live site the same
question with `/api/lookup?text=<digits>` and see whether the counts agree.

What the skill says now: section 3 chooses a range by what is common and by
what it costs in bytes and in readability, and section 2 says to hold the
numbers that turn up. It says a table of values that are a handful of small
integers "match everything and tell nobody anything", which is this fault for a
discrete family. It says nothing about a continuous family whose tail
accumulates at a value the corpus holds, where every entry is distinct, every
entry is legitimate, and the table still buries a famous constant in search.

What it should say: when the values of a family converge, the range is decided
by search collision and not by size. Measure it rather than guessing: count the
stored values that fall inside the interval a $k$-digit query for the limit
denotes, for $k$ from three to twelve, and stop where a query at the precision
a reader would actually type stops returning the tail instead of the limit.
Then say that in `complete-note`, which is where a reader checking whether
their own number belongs here will read it.

Evidence: 2026-09-20, T286. `/tmp/t286_growth.py` and `/tmp/t286_search.py`
under Sage for the counts; live control `GET /api/lookup?text=1.618` returned
51 results of which 26 were T286 rows, and `text=1.61803` returned 14 of which
8 were, both matching the computed column for r=50 exactly. `text=1.6180339887`
returned 6 results and none from T286.

## `/api/lookup` needs a GET, and answers a POST with a 403 HTML page

What happened: `curl https://numberdb.org/api/lookup --data-urlencode
"text=1.61803"` answered `403 Forbidden` with an HTML body -- `--data-urlencode`
makes the request a POST, and the POST is refused by CSRF before the view is
reached. The fix is `curl -G`, which puts the encoded pairs in the query
string. The failure is opaque because nothing in the body says CSRF, and a
script parsing the answer as JSON reports a decode error rather than a wrong
method.

The same shape catches the rate limit: a throttled `/api/lookup` answers
`200`-shaped JSON `{"error": "Rate limit exceeded (60 requests per 60
minutes)", "retry_after": ...}` with no `results` key, so a script written as
`json.load(...).get('results', [])` prints "0 hits" for every query and reads
exactly like "this value is in no table". Check for `error` before reading
`results`. (The limit itself is already proposed in
`20260916T003007Z-critique.md`; this is the silent-zero shape of it.)

What the skill says now: nothing about the HTTP method, and nothing about what
a throttled or errored response looks like to a parser.

What it should say: `/api/lookup` is a GET; results are under `results`, and a
response carrying `error` has no `results` at all, so test for it before
concluding a number is unknown.

Evidence: 2026-09-20. `curl -sS -i https://numberdb.org/api/lookup
--data-urlencode "text=1.61803"` -> `HTTP/2 403`, 1852 bytes of HTML; the same
with `-G` -> JSON with `results`. Seven consecutive queries earlier in the same
run returned `0` results each because the reader took `tables` rather than
`results`, and the eighth revealed the rate-limit error that the same reader
would also have shown as `0`.

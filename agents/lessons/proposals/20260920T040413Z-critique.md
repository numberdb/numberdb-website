## `/api/table` answers every failure with HTTP 200 and an `error` key

What happened: reading T354 through the API, the first attempt used
`GET /api/table?table=T354` — the parameter spelled after the thing being
asked for. It answered **HTTP 200** with a 32-byte body:

    {"error": "No id or url given."}

A script that checks the status code and then reaches for `document['Title']`
sees a successful request and raises `KeyError` somewhere else entirely, a
long way from the typo that caused it. The same is true of every other failure
on that endpoint: a table that does not exist, and a *draft the caller may not
see*, both answer 200 with an `error` key. The last is the worst of the three,
because a draft the caller lacks permission for is indistinguishable, in both
status and body, from a table number nobody has used.

The sibling path is the other half of the trap. `/api/table` with `?id=` is
the **read**; `/api/table/<tid>` is the **write**, and a `GET` of it answers
405 `{"error": "Use POST or PUT."}`. So the address that looks like the
RESTful way to read one table is the one that refuses to read, and the one
that does read takes the table number in a query parameter named `id` —
which also accepts a slug, so `?id=Best_Sobolev_constant_in_W1pRn` works and
`?url=` is a second spelling of the same thing.

What the skill says now: it documents `GET /api/table?id=T137` in passing and
says a draft is served there only to a caller whose key may see it. It says
nothing about the status code, and nothing that would stop somebody writing
`?table=`.

What it should say: `/api/table` signals failure in the body, not in the
status — check for an `error` key before using the response, because a typo in
the parameter name, a table that does not exist, and a draft your key cannot
see all answer 200. Read with `GET /api/table?id=<tid or slug>`; write with
`POST /api/table/<tid>`. A `GET` of the write address answers 405 and is not
a sign that the table is missing.

Evidence: read 2026-09-20, against numberdb.org.

    GET /api/table?table=T354   200  {"error": "No id or url given."}
    GET /api/table              200  {"error": "No id or url given."}
    GET /api/table?id=T9999     200  {"error": "Table with id 'T9999' does not exist."}
    GET /api/table/T354         405  {"error": "Use POST or PUT."}
    GET /api/table?id=T354      200  72143 bytes, the document

all four of the first with a key that may see T354. The handler is
`numberdb_app/api.py:377`; each error path builds its own `JsonResponse`
without a `status=`, which Django defaults to 200.

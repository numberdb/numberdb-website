# Lessons proposed by the T343 critique, 2026-09-19

Nothing here is in force. Format as in `agents/lessons/PROPOSALS.md`.

## A named entry citation breaks on a parameter value that contains a comma

What happened: T343 indexes its rows by `distribution`, `shape`, `unit`, and
its `shape` values are strings like `2,1/2;1/3` — a comma inside one
parameter's value. The skill documents the positional address,
`HREF{slug#Z,1,density}`, and that form works: on the published T339, which
has the same key shape, `?entry=binomial,2,1/2,nats` resolves and the row is
focused.

The *named* form does not. `?entry=distribution=binomial,shape=2,1/2,unit=nats`
answers "This table has no entry …; it may have been renumbered or removed",
and so does the hypergeometric row `shape=10,2,5`. The resolver splits the
named form on commas and requires every part to contain an `=`
(`numberdb_app/views.py:571`); `1/2` does not, so the named parse is abandoned
and the whole string is then looked up as a positional identity, which it is
not. Controls: `?entry=distribution=bernoulli,shape=1/3,unit=nats` (no comma
in the value) resolves, and `?entry=distribution=bogus,shape=1/3,unit=nats`
fails, so the mechanism discriminates correctly everywhere else.

This is not a failure a table author sees on their own page. It appears in the
*other* table, the one whose prose wrote `HREF{slug#a=…,b=…}`, as a banner
saying the entry is gone. And the named form is the one the site's own code
comment calls "the form worth writing down", because a positional identity
"does not break, it lies" if the parameters are ever renested.

What the skill says now: it gives only the positional form, and says the
address is "its parameter values, comma separated, as a citation writes them".
It does not mention the named form at all, and it does not say that a comma
inside a value is the site's parameter separator.

What it should say: two sentences beside the `HREF{slug#entry}` rule. That a
parameter value containing a comma can only be addressed positionally, so a
link to such a row must be written `HREF{slug#binomial,2,1/2,nats}` and not
`HREF{slug#distribution=binomial,shape=2,1/2,unit=nats}`; and that this is a
reason to prefer a separator the site does not use — `;`, which T343 already
uses between $P$ and $Q$ — when inventing a compound key, since the key is
frozen at publication and this is the last moment it can be chosen.

Evidence: 2026-09-19, T343 critique. Eight `?entry=` probes against
`https://numberdb.org/Shannon_entropies_of_discrete_probability_distributions`,
distinguished by the presence of the "has no entry" warning in the response:

    found     bernoulli,1/3,nats
    found     distribution=bernoulli,shape=1/3,unit=nats
    found     binomial,2,1/2,nats
    NOTFOUND  distribution=binomial,shape=2,1/2,unit=nats
    NOTFOUND  distribution=binomial,shape=2,9/7,unit=nats
    found     hypergeometric,10,2,5,nats
    NOTFOUND  distribution=hypergeometric,shape=10,2,5,unit=nats
    NOTFOUND  distribution=bogus,shape=1/3,unit=nats

A warning: `table-block-focused` is present in the HTML whether or not the
entry resolved, so it is not a usable indicator. I read it as one for a first
round of probes and drew the opposite conclusion; the "has no entry" warning
text is the one that discriminates.

## `complete:` is printed verbatim into an English sentence, so write `no`

What happened: T343 has `complete: false` under `Data properties`, and the
page reads "Table is complete: false (it holds ordered distinct Bernoulli and
geometric pairs …)". The value is not interpreted as a boolean anywhere; it is
concatenated into the label's sentence as written
(`numberdb_app/views.py:1128`, `text += escape_maths(value)`), and the
`complete-note` is then appended in brackets to finish it. A YAML literal ends
up in the middle of a sentence a reader is reading as English.

`no` is what the corpus overwhelmingly writes — 12 of the 15 published tables
I sampled, including the sibling T339 this table was built from — but `false`
is not unique to T343 (T119 and T241 also have it), and nothing checks it:
`audit_table.py` treats `complete-note` as prose and never looks at `complete`
itself.

What the skill says now: it shows `complete: no` in an example and says the
field "renders inside 'complete: no (...)', so write a clause that finishes
that sentence". It says the *note* must finish the sentence; it never says the
*value* is part of the same sentence.

What it should say: that `complete` is printed verbatim, so the word to write
is `yes` or `no` and not `true`/`false` — the reader sees "Table is complete:
<your word>", and the note continues from there. Worth a line because a
generator or an agent writing JSON will naturally reach for `false`.

Evidence: 2026-09-19, T343 critique. `/tmp/T343_page.html` (draft rebuilt
whole, 676 records, status 200, 521,249 bytes) renders "Table is complete:
false (…)". `GET /api/table?id=<tid>` for T7, T25, T59, T92, T99, T119, T174,
T241, T290, T319, T330, T335, T338, T339, T340: twelve `no`, two `false`
(T119, T241), one absent (T7).

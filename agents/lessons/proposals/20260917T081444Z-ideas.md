## An OEIS row can be misprinted, and an invariant of the row says which side is wrong

What happened: the Adams–Bashforth coefficients for $s=1..7$ were compared
with OEIS A260780, whose rows are unreduced numerators without a denominator
sequence. Rows 1–6 agreed. Row 7 did not: its second term reads `-2235440`,
where the coefficient $-18637/2520$ over the common denominator $302400$ is
`-2236440`. Two independent computations (solving the moment conditions, and
expanding $\sum_k\gamma_k\nabla^k$) agreed with each other. The decisive
fact needed neither: the coefficients of a consistent Adams method sum to 1,
and the OEIS row sums to $303400$ while every other term of it is an exact
multiple of $1/302400$.

What the skill says now: "If your recomputation disagrees with a stored
value, suspect your recomputation first." That is right, and it concerns
this database's stored values. It says nothing about external references
being wrong.

What it should say: when a comparison with OEIS or a published table fails
in one term, look for an invariant the row must satisfy (a row sum, a
symmetry, a moment condition) before deciding which side is wrong. A single
misprinted digit in a reference shows up as a broken invariant, and a
mistake in your own convention breaks the whole row, not one term. Record the
misprint in the table's `rigour details` so the next builder does not chase
it.

Evidence: `/tmp/cmp.py` and the $\gamma$-expansion script, 2026-09-17. OEIS
A260780 data, row 7: `993605,-2235440,3527745,-3441280,2035695,-672360,95435`.

## A second OEIS triangle whose name says the other object

What happened: OEIS A235936 is named "Triangle of numerators of the
unreduced coefficients of a numerical integration for a prediction Adams
method". Its rows `5,8,-1` and `251,646,-264,106,-19` are the
Adams–Moulton coefficients (the *corrector*) for $s=2$ and $s=4$, over $12$
and $720$. The predictor, Adams–Bashforth, is A260780.

What the skill says now: nothing. The Ehrhart lesson in
`20260913T175158Z-ideas.md` records the same failure for A275514.

What it should say: this is the second case, so the lesson is general. Before
comparing against an OEIS triangle, compute one row and see which object the
data holds. The name is not evidence.

Evidence: OEIS A235936 data, compared by script with the exact
Adams–Moulton coefficients: all 8 rows agree.

## A hyphen and an en dash search alike; accents do not

What happened: `numberdb.search_text('Gauss-Lobatto')` and
`search_text('Gauss–Lobatto')` return the same tables, and both find T137,
whose title uses an en dash. `search_text('Erdos-Renyi')` returns nothing,
while `search_text('Erdős–Rényi')` finds T156 and two other threshold tables.

What the skill says now: "the index has no `unaccent`: the title is 'Lévy's
constant' and `Keywords` carries 'Levy constant'." It says nothing about
dashes.

What it should say: `Keywords` needs the unaccented spelling of a name, but
not a hyphenated copy of an en-dashed one. Search splits on both, so
*Newton–Cotes* in the title already answers *Newton-Cotes*.

Evidence: the calls above, 2026-09-17.

## OEIS's JSON search answers with a bare list, or `null`

What happened: a script reading `json.load(...)['results']` from
`https://oeis.org/search?fmt=json&q=...` raised, because the answer is now a
bare list of sequence records. A query with no match answers `null`, so
`.get('results')` raises too, and a check written for the old shape reports
"no OEIS entry" or crashes, depending on how it was written.

What the skill says now: nothing about reading OEIS programmatically.

What it should say: if a check queries OEIS, treat the answer as `list or
None`, and treat `None` as "no match" only after a query known to match (for
example `id:A000045`) has returned a list.

Evidence: `/tmp/scr2.py` output, 2026-09-17: `'NoneType' object has no
attribute 'get'` for the query `Adams-Moulton`, while `Newton-Cotes` returned
a list.

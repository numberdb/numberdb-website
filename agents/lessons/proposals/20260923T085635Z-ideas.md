## A covering radius found by sampling is wrong in the third digit, and looks right

What happened: checking whether the stored covering radius of a spherical
covering can be recomputed from the published coordinates, the obvious method
was used first: draw uniform points on the sphere and take the largest distance
to the nearest of the $n$ code points. With $2\cdot10^5$ samples it returned
$70.488^\circ$ for the four-point covering, $54.646^\circ$ for six and
$37.347^\circ$ for twelve. The true values are $70.5287794^\circ=\arccos(1/3)$,
$54.7356103^\circ=\arccos(1/\sqrt3)$ and $37.3773681^\circ$. Every sampled
answer is wrong in the third significant digit and wrong *low*, because the
maximum is attained at a single point (the deepest hole) and a random sample
almost never lands on it. Nothing about the output says so: three plausible
angles, monotone in $n$, stable if you rerun.

The maximum is attained at a Voronoi vertex, so the computation is: over every
triple of code points take the two unit normals to their plane, keep those that
no other code point is nearer to, and take the largest angular distance to the
generators. That reproduced all three closed forms to seven decimals in a few
lines of plain Python, $O(n^3)$ and fast enough to $n=130$.

What the skill says now: "A measurement needs a control that returns a known
answer", with the Simpson's-rule example. True and the right instinct, but the
example is about an integral whose control silently returned zero. Here the
control *would* have caught it and the trap is one step earlier: the quantity
is a maximum over a continuum attained at isolated points, and Monte Carlo
estimates such a maximum from below, always.

What it should say: a maximum over a continuum is not measured by sampling the
continuum. Find where it is attained and evaluate there: for the covering
radius of points on a sphere that is the Voronoi vertices (circumcentres of the
Delaunay triples), for the diameter of a set it is a pair, for the deepest hole
of a lattice it is a hole of the Delaunay cell. A sampled maximum is biased
low by an amount nothing in the output reveals, and rerunning with more samples
moves it by less than the error.

Evidence: 2026-09-23, Sloane's spherical coverings `cover.3.n.txt` for
$n=4,6,12,13,20,30$. Sampling at $2\cdot10^5$ points: $70.48843$, $54.64574$,
$37.34724$. Voronoi vertices: $70.5287794$, $54.7356103$, $37.3773681$,
$37.0685427$, $29.6230958$, $23.8787580$, of which the first three are
$\arccos(1/3)$, $\arccos(1/\sqrt3)$ and the icosahedral value.

## `source_names_it` matches by substring, so an English plural fails a singular source

What happened: six proposed titles were screened against the pages a build
would cite. Four came back with a complaint of the form "the source does not
mention energies" -- for the Cambridge Cluster Database page whose column is
headed *Energy*; "does not mention radii" for Sloane's covering page, which
says *covering radius*; "does not mention best, known" for the same page, which
says *putatively optimal*. In every case the page is unmistakably about the
family, and the title is what the family is called. `_distinguishing` strips
generic words and then asks `w not in text` on the raw lowercased page, so
"radii" does not match "radius" and "energies" does not match "Energy".

The failure matters because it reads exactly like the real one it is there to
catch -- a family nobody has heard of, cited to a page that does not mention it
-- and the natural reaction is to rename the table after the source's wording,
which is how a corpus of plural titles ("Covering radii and covering densities
of the classical lattices", "Real periods of elliptic curves") acquires an odd
singular.

What the skill says now: nothing. The screen is described in the stage-one
prompt as the check that a family "is real and is called what you say", with no
note on how it matches.

What it should say: when `source_names_it` complains about one word, singularise
it and screen again before touching the title. If the singular passes, the
family is named by the source and the title is fine; record both lines. Rename
only when the distinguishing word -- the proper name, the object -- is the one
missing.

Evidence: 2026-09-23. "Global minimum energies of Lennard-Jones clusters"
against `doye.chem.ox.ac.uk/jon/structures/LJ.html` complains about *energies*;
"Global minimum energy of Lennard-Jones clusters" against the same page returns
`None`. "Covering radii of the best known spherical coverings" against
`neilsloane.com/coverings/` complains about *radii, best, known*; "Covering
radius of spherical coverings by equal caps" returns `None`.

## Drafts answer `numberdb.table` with a key, and are the only way to see work in progress

What happened: `search_text` and the `/tables` listing both show only published
tables, so a proposal screened against them cannot tell whether the table is
already half-built. The listing gave 422 tables with the highest number T444,
which leaves 38 gaps in the numbering. Asking for each gap by number with
`NUMBERDB_API_KEY` set returned 25 drafts with their titles -- Falkner-Skan,
Mathieu, the sieve functions, Tracy-Widom -- and a plain `NumberDBError` for
the rest. Without the key the same call returns nothing for all 38.

That is a cheap and complete check that nothing in the proposed area is already
being built, and it is the only one available: `/drafts` answers 302 without a
browser session, and the API has no listing endpoint at all (`GET
/api/tables` answers 405 "Use POST").

What the skill says now: "`/drafts` lists what is being made right now and is
invisible from outside, so a table can be half-built and unfindable while you
start it again." True, and it leaves the reader with no way to look.

What it should say: the gaps in the published numbering are the drafts. Scrape
`/tables?page=1..n` for the numbers that exist, then ask `numberdb.table('T<gap>')`
for each missing one with a key configured; the drafts you can see come back
with a title, the rest raise. Pace the walk -- the read API answers "too many
requests; retry in 42s" after a few dozen calls in a row, and about 1.5 seconds
between calls avoided it entirely.

Evidence: 2026-09-23. `https://numberdb.org/tables?page=1..9` yielded 422
table numbers, maximum T444; the 38 gaps queried one by one returned 25 titled
drafts (T342, T404, T405, T413, T415-T419, T422-T426, T432-T434, T436-T438,
T441, T443, T445) and `NumberDBError` for T75 and T446-T459. A `curl` of
`/drafts` with the key as `X-API-Key` answered 302; `GET /api/tables` answered
405.

## The read API rate-limits a corpus walk, and the client says so clearly

What happened: walking `numberdb.table('T1')` to `T300` in a loop with no
pause, the first 163 calls succeeded and every call after that raised
`RateLimitError: too many requests; retry in 42s`. The walk was in a script
whose output was being tailed, so it looked like the corpus simply stopped at
T163 -- the run before this one appears to have concluded the same thing.

What the skill says now: nothing about rate limits. It says "there is no call
that lists the corpus, so to see everything you walk the T-numbers", which is
the exact operation that hits this.

What it should say: the walk needs a pause between calls -- 1.5 seconds was
enough for 300 calls -- and a retry that sleeps for the number of seconds the
error names. Better still, scrape `/tables?page=N` for the titles, which is one
request per fifty tables, and use `numberdb.table` only for the documents you
actually need.

Evidence: 2026-09-23, an unpaced loop stopping at T163 with
`RateLimitError: too many requests; retry in 42s`; the same walk at 1.5-second
intervals completing without a single retry.

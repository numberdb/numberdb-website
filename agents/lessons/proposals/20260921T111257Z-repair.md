## `Generator.publish()` attaches the source under the script's basename
What happened: T11 was extended with a scratch generator at `/tmp/t11_generate.py`. `Generator.publish()` correctly added the 70 missing entries, but it also attached that source as `t11_generate.py`. The table already had an old `generate.sage`, and a later manual file POST added `generate.py`; replacing `generate.sage` fixed the stale canonical filename, but the scratch basename remained as an extra current file because the public file API has no deletion route.

What the skill says now: it says the generator is attached to the table and downloaded from it, and that the file should open with commands to run it. It does not say that the attached name is the script basename that ran `publish()`.

What it should say: when publishing from a generator, run the file under the name readers should see, usually `generate.py`, or explicitly attach that canonical filename afterward. A repair run from `/tmp/foo.py` can otherwise leave `foo.py` as a current table file beside the intended generator.

Evidence: T11 on 2026-09-21. `Generator.publish()` from `/tmp/t11_generate.py` reported `70 added` and the files page showed `t11_generate.py`; subsequent POSTs to `/api/table/T11/file/generate.py` and `/api/table/T11/file/generate.sage` made those filenames current, but did not remove `t11_generate.py`.

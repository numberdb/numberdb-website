# Lessons proposed by triage run 20260923T115512Z

Met while establishing what a failed build had left behind. All three are true
for anybody with a key and `curl` on their own laptop.

---

## There is no endpoint that lists the drafts you hold; `GET /api/tables` is the *create* endpoint answering 405

What happened: triage needed to know whether a build had created a draft before
it died. The obvious probe was a listing:

    $ curl -s -H "Authorization: Bearer $KEY" \
        "https://numberdb.org/api/tables?draft=true" -w "%{http_code}\n"
    405 application/json
    {"error": "Use POST."}

That reads like a listing endpoint rejecting a query parameter. It is not.
`api/tables` is `create_table` -- the POST that claims a new table -- and the
405 is it refusing a GET. The `?draft=true` was never looked at.

The whole `/api/` surface is per-table or per-value: `api/lookup`, `api/search`,
`api/table`, `api/tables` (create), `api/table/<TID>` and its `/entries`,
`/offer`, `/lease`, `/audit`, `/file/<name>`, plus `api/claim`, `api/tag`,
`api/costs`. **Nothing enumerates the tables a key owns.** A contributor who
holds up to five drafts and loses track of which ids they are has no way to ask.

What the skill says now: how to create a draft with `POST /api/tables` and
`X-Draft: yes`, and how to read one back by id. Nothing about the absence of a
listing, and nothing warning that the plural path is the create endpoint.

What it should say: record the `TID` your create call returns -- it is the only
copy you will get. There is no "my drafts" endpoint; to check a draft later you
must already know its id and probe `GET /api/table?id=<TID>` with your key.
And `api/tables` (plural) creates, while `api/table` (singular) reads; a GET to
the plural one answers `405 {"error": "Use POST."}` regardless of what query
string you hang off it.

Evidence: 2026-09-23, the two calls above, and `numberdb_app/urls.py:40-55`,
which is the complete `/api/` route table.

## `/api/search` is the one `/api/` path that is not CSRF-exempt, so a script cannot POST to it -- use `api/lookup`

What happened: with no listing endpoint, the next try was the search API, which
takes a POST:

    $ curl -s -X POST -H "Authorization: Bearer $KEY" \
        -H "Content-Type: application/json" -d '{"query":"","draft":true}' \
        "https://numberdb.org/api/search" -w "%{http_code}\n"
    403
    <!DOCTYPE html> ... <title>403 Forbidden</title> ...

A valid key, a well-formed body, and an HTML 403. It is not an authentication
failure and not a rate limit: `advanced_search_results` in `numberdb_app/api.py`
carries `@rate_limited` and **no `@csrf_exempt`**, while every write endpoint --
`create_table`, `write_table`, `write_entries`, `offer_table`, `table_lease`,
`write_file`, `claim`, `costs` -- does carry it. `api/search` is the backing
view for the browser's advanced-search form, so Django's CSRF middleware
rejects a POST that arrives without a session cookie and token. A key cannot
satisfy it, because CSRF is not about who you are.

The trap is the shape of the reply. An API key problem answers JSON; this
answers an HTML error page, which a script doing `response.json()` meets as a
parse error rather than as "wrong endpoint".

What the skill says now: nothing about `api/search` at all, and nothing about
which endpoints accept a key alone.

What it should say: search programmatically with **`GET /api/lookup`**, not
`POST /api/search`. `api/search` serves the website's form and cannot be driven
by a key. As a rule for the whole API: the endpoints a script may POST to are
the ones that write, plus `claim` and `costs`; reads are GETs.

Evidence: 2026-09-23, the call above; `numberdb_app/api.py:85-86` (decorators on
`advanced_search_results`) against the eight `@csrf_exempt` views in the same
file.

## `api/lookup` answers HTTP 200 to a malformed request, with `error` where `results` would be -- so the status code is not the check

What happened: a lookup with the wrong parameter name still succeeded, as far
as HTTP was concerned:

    $ curl -s -H "Authorization: Bearer $KEY" \
        "https://numberdb.org/api/lookup?value=1.6180339887&digits=8" \
        -w "%{http_code} %{content_type}\n"
    200 application/json
    {"error": "Give number=<json record>, numbers=<json list>,
      polynomial=<text>, polynomial_hash=<digest>, or text=<search term>."}

`value=` and `digits=` are not parameters this endpoint has. It took the
request, found nothing it recognised, and returned **200** with an `error` key.
A correct call is 200 too, and looks entirely different:

    $ curl -s -H "Authorization: Bearer $KEY" --get \
        --data-urlencode 'text=Steklov' "https://numberdb.org/api/lookup"
    {"results": [], "tags": [], "tables": [], "messages": [], "time_request": "0.077s"}

Both are 200. The difference is `error` versus `results`. A script that checks
`resp.status_code == 200` and then reads `resp.json().get("results", [])` sees
an empty list in both cases -- and "your parameter name was wrong" becomes
"this constant is not in the corpus", which is the answer a contributor most
wants to be sure of before adding a table. The failure is silent and it fails
in the direction that causes duplicate work.

Note also that the error body is a complete list of the accepted parameters,
so a probe with a deliberately bad query is a cheap way to see them.

What the skill says now: to check a value against the corpus with `api/lookup`
before proposing a table. It does not say that a mistyped query is
indistinguishable from an empty result unless you look for `error`.

What it should say: after any `api/lookup` call, assert that `error` is absent
before believing `results`. Treat a response carrying `error` as a failed
query, not as an empty corpus -- HTTP 200 does not mean the endpoint understood
you. The accepted parameters are `number`, `numbers`, `polynomial`,
`polynomial_hash` and `text`.

Evidence: 2026-09-23, the two calls above, triage run `20260923T115512Z`.

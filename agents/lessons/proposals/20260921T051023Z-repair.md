## A draft cannot be the second table that makes a one-member tag useful
What happened: T377's critique proposed adding the existing `moments` tag,
because `/api/tag?url=moments` reported one published table, T36. Adding it to
the draft made `/api/table/T377/audit` report `Tags: "moments" reaches only
this table; a tag that leads nowhere else leads nowhere`. Removing the tag made
the audit clean again.

What the skill says now: prefer an existing tag, and propose a new tag only
when three or more tables would carry it. It also says a tag with one table on
it is not useful, but not that an existing one-table tag still fails a draft's
audit.

What it should say: before adding an existing tag, check that it already
reaches at least two published tables. A draft under review does not raise the
tag's published reach for the audit that decides whether the draft is clean.

Evidence: T377 repair, 2026-09-21. After adding `moments`,
`GET /api/table/T377/audit` returned the one-tag finding; after removing it,
the same endpoint returned `{"findings": [], "clean": true}`.

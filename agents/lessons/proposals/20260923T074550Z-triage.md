## An empty key reads as "does not exist", so assert the key is non-empty before believing a draft is gone

What happened: checking whether an abandoned draft still existed, I read
`api/table?id=T445` with the key piped into the script, and got

    {"error": "Table with id 'T445' does not exist."}

T445 exists; it is my own draft. The key was empty, and I had sent
`Authorization: Bearer ` with nothing after it. `api.table` answers a draft the
caller may not see with the same sentence it gives a T-number nobody has ever
used, so an authentication problem is reported as a fact about the corpus. I
was one probe from concluding the draft had been deleted and that something had
cleaned up behind me.

The key was empty because of the shell, not the file. The shape

    cat "$KEY_FILE" | python3 - <<'EOF'
    ...
    EOF

sends the *heredoc* to Python as the program to run, and the pipe is discarded:
`python3 -` reads its program from stdin, the heredoc is the last redirection to
win, and `sys.stdin.read()` inside the script then returns `''`. No error, from
either the shell or Python — the key is simply gone, and the request goes out
unauthenticated. The same script in a file reads the key correctly. This is
worth naming because a heredoc is the natural way to write a throwaway check,
and piping is the right instinct for a credential: an API key in
`NUMBERDB_API_KEY` is visible in `ps` and in a shell history, and a key on stdin
is not.

Both halves of this generalise past the shell. Any route that loses the
credential — an unset `NUMBERDB_API_KEY`, a typo in the variable name, a key
file that is there but empty — arrives at the same "does not exist", because the
site cannot distinguish "you may not see this draft" from "there is nothing
here" without revealing which drafts exist. So the message is not evidence about
the corpus until you know the request was authenticated.

What the skill says now: that `publish()` needs `NUMBERDB_API_KEY`, and not to
put a key in a file you commit (§ "Publishing"). Nothing about reading a key
from stdin, and nothing about what an unauthenticated read of your own draft
looks like. The published skill's reader meets this the first time they check on
a draft they have not yet published.

What it should say: when a read of your own draft answers `{"error": "Table
with id 'T…' does not exist."}`, check the request before believing the corpus.
Print `len(key)` first — an empty key and a missing header both produce that
exact sentence, and a correct one returns the whole document. Two concrete
traps: `cat key | python3 - <<'EOF'` silently delivers an empty key, because the
heredoc becomes the program and Python's stdin is already at EOF (put the script
in a file and pipe to that, or keep the heredoc and pass the key on another
descriptor: `python3 - 3<&0 <<'EOF'`, reading it with `os.read(3, ...)`); and an
unset or misspelled `NUMBERDB_API_KEY` reaches the same place by a shorter
route. A one-line assertion at the top of any script that reads a key on stdin —
`assert key, "no key on stdin"` — turns a misleading answer about the corpus
into an accurate complaint about the invocation.

Evidence: 2026-09-23, triage of build 20260923T074456Z, draft T445 ("Skewness
and excess kurtosis of the Tracy-Widom distributions", 0 entries, unpublished).
Three requests for the same URL, from one script, differing only in the header:

    no header              {"error": "Table with id 'T445' does not exist."}
    Bearer <empty>         {"error": "Table with id 'T445' does not exist."}
    Bearer <key>           200, full document (3613 bytes)

And the shell half, reduced:

    $ printf 'SECRET\n' > /tmp/fakekey
    $ cat /tmp/fakekey | python3 - <<'EOF'
    import sys; print("read from stdin: %r" % sys.stdin.read())
    EOF
    read from stdin: ''
    $ cat /tmp/fakekey | python3 /tmp/t.py        # same two lines, in a file
    read from stdin: 'SECRET\n'
    $ cat /tmp/fakekey | python3 - 3<&0 <<'EOF'
    import os; print("fd3: %r" % os.read(3, 100))
    EOF
    fd3: b'SECRET\n'

Related: `docs/agent-environment.md`, "`api/table` needs `Authorization:
Bearer`, and any other scheme reads as a missing table" — the same misleading
answer reached by sending `Api-Key` instead of `Bearer`. That note is filed as
deployment, but the behaviour it describes belongs to the reader of the skill as
much as to us; an empty key, a wrong scheme and no header are one lesson.

## A table's prose is not LaTeX outside `$...$`, so a TeX accent reaches the page as itself

What happened: T257's second comment ends "the ordinary Poincar\'e polynomial
of the corresponding complex flag manifold". Rendered, it reads

    The polynomial $W(t^2)$ is the ordinary Poincar\'e polynomial of the
    corresponding complex flag manifold.

with the backslash and the apostrophe printed, one screen below a title that
holds the accented letter correctly ("Poincaré polynomials of the finite
Coxeter groups"). The renderer hands only `$...$` to MathJax; everything else
is written out, so a text-mode TeX escape is three literal characters. Nothing
refused it: the API accepted the document, `audit_table` reports the table
clean, and the fault is invisible in the stored YAML to anybody who reads TeX
fluently enough to see "Poincaré" where the file says `Poincar\'e`.

Why a contributor on their own laptop hits this: somebody who writes papers
types `\'e`, `\"o` and `\ss` without thinking about it, and a field full of
`$\prod$` and `$\leq$` looks like a place where that works. It is exactly the
same key as an author who writes `\textit{...}` or `~` in a definition.

What the skill says now: it mentions accents once, and only about search --
"the index has no `unaccent`: the title is 'Lévy's constant' and `Keywords`
carries 'Levy constant'". It says nothing about how prose outside `$...$` is
rendered.

What it should say: outside `$...$` a field is plain text, not LaTeX. Write the
accented character itself -- Poincaré, Lévy, Möbius -- and keep `Keywords`
carrying the unaccented spelling for search. A `\'e`, a `\textit{}` or a `~` in
a definition or a comment is printed to the page as typed.

Evidence: 2026-09-16, T257. `/preview?table=` with that comment renders
`Poincar\'e`; the same document's `Title` renders `Poincaré`. The document has
exactly one text-mode escape and 65 `$...$` fragments, all of which typeset.

## An identity that follows from how the values were built is not a check

What happened: T257's `rigour details` says the generator "checks all stored
rows against the palindromy identity (3), the order identity (2), Solomon's
identity (4), and the Mahonian triangle [5] for the type $A$ rows". The entries
are built as $\prod_i(1+t+\cdots+t^{d_i-1})$ from a list of degrees, and that
product is palindromic and satisfies $W(1)=\prod_i d_i$ for *any* list of
positive integers. Both named checks therefore pass on degrees no Coxeter group
has:

    degrees (2, 6)          palindromic: True   p(1) == prod(d_i): True
    degrees (2, 7)          palindromic: True   p(1) == prod(d_i): True
    degrees (3, 5)          palindromic: True   p(1) == prod(d_i): True
    degrees (2, 3, 4, 17)   palindromic: True   p(1) == prod(d_i): True

The sentence is true -- the generator does run those assertions -- and a reader
counting four independent confirmations is counting two. The checks with
content in that generator are the comparison of $W(1)$ against the *known*
orders of the exceptional groups, Solomon's identity, which makes each type's
degrees agree with those of every parabolic sub-diagram, and the OEIS triangle
for type $A$. Two of those three are not named in the sentence at all.

Why a contributor on their own laptop hits this: writing self-checks into a
generator is what the skill asks for, and the cheapest assertions to write are
the ones that restate the construction. They cost nothing, they never fail, and
they are the ones a tired author lists in the provenance note because they are
the ones the code visibly contains.

What the skill says now: "Check new values against something independent. Not
the code that produced them", and, in ball arithmetic, "An enclosure that
contains everything agrees with everything" and "A measurement needs a control
that returns a known answer". The idea is there for numerics and not for exact
values, where the same thing happens algebraically.

What it should say: before listing a check, ask what input would make it fail.
An identity implied by the construction -- a product of palindromes being
palindromic, a generating function evaluated at 1 returning the count it was
summed from -- is a test of the arithmetic and not of the mathematics. Run the
check against deliberately wrong input once, to see it fail; if it does not,
say so or leave it out, and name instead the checks that compare against
something the program did not produce.

Evidence: 2026-09-16, T257. `/tmp/t257_sage.py` section 4, through
`agents/sage.sh`: four invented degree lists, all four palindromic and all four
satisfying the order identity.

## A `Symbolic` parameter can say how its values are written, and the skill never mentions the field

What happened: reading T257, whose one parameter's values are the names of
Coxeter types, the numbers block reads

    type      $W(t)$
    A1:       t + 1
    I2(5):    t^5 + 2*t^4 + 2*t^3 + 2*t^2 + 2*t + 1

while every other line on the page writes $A_1$ and $I_2(5)$. The field that
changes this is `values:` on the parameter, a map from the stored key to its
display: `E6: $E_6$`. It is not obscure -- 32 of the 56 tables in the corpus
with a `Symbolic` parameter carry one, and `validate.py` uses it for a second
purpose, refusing any entry whose parameter value is not among those declared
-- and the skill does not mention it anywhere. A contributor learns it by
reading another table's YAML or not at all.

The skill's nearest paragraph is about the *other* two fields and says only
what is wrong: "`param-latex` replaces the label of the parameter group it sits
in ... it is wrong on a parameter whose value is a number". Somebody who has
just been told not to use `param-latex` has been given no field to use instead.

Why a contributor on their own laptop hits this: any table indexed by named
objects -- lattices, groups, knots, distributions, Dynkin types -- meets it on
its first render, and the wrong fix (`param-latex`, which the skill does name)
is the one that produces the fault the skill already documents: a column
reading `$L_{\Delta(2,4)}(t)$` where it should read `2`.

What the skill says now: nothing about `values:`.

What it should say, beside the `param-latex` paragraph: a parameter whose
values are names says how they are written with `values:`, a map from the
stored key to its display -- `values: {E6: $E_6$, F4: $F_4$}`. The key stays
what it is, because that is what a citation resolves on and what
`HREF{slug#E6}` addresses; only the display changes. Declaring it also declares
the permitted values, so an entry with a mistyped name is refused instead of
stored.

Evidence: 2026-09-16, T257 critique. `numberdb_app/views.py:838` reads
`Parameters[p]['values']` into `value_display`; `numberdb_app/validate.py:353`
reads the same map and cross-checks every entry's `params` against it;
`grep -c` over `generators/*/table.yaml` gives 32 tables with a map and 24
without, among 56 with a `Symbolic` parameter. T256 has one, T233 -- the table
closest to T257 in shape -- does not, and its published page reads `A2:`,
`E8:`.

## Second instance of the pending `sage.all` lesson, on a table's own code

Not a new lesson: the proposal "A `Programs` snippet that imports from `sage.*`
submodules runs in a Sage session and not in a Sage script", in
`agents/lessons/proposals/20260916T024304Z-critique.md`, predicts this exactly.
Recording the confirmation because it was made on the snippet itself rather
than on a reconstruction.

T257's `Programs` block, saved verbatim to a file and run through
`agents/sage.sh` (which runs `sage -python -u`), fails on its first line:

    Traceback (most recent call last):
      File "/work/t257_program_verbatim.py", line 1, in <module>
        from sage.rings.integer_ring import ZZ
    AttributeError: partially initialized module 'sage.rings.integer_ring'
    has no attribute 'ZZ' (most likely due to a circular import)

The same lines exec'd in a namespace, as a Sage session would, return the
stored $F_4$ row. Replacing the two imports with
`from sage.all import ZZ, PolynomialRing, CoxeterGroup` runs under
`sage -python` and returns the same polynomial. That makes four tables with the
shape (T233, T243, T256, T257) and the first where the published snippet itself
was run both ways.

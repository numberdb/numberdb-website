# Proposed from the T285 growth reading, 2026-09-20

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## A table page does not show that an entry is unreviewed, so a search miss looks like a missing value

What happened: T285 was grown from five rows to seven on 2026-09-20. Three
hours later the five older rows answered a search by number and the two new
ones answered nothing, and the page said nothing about the difference. Measured
against `/api/lookup`, with an interval of one unit in the 18th place around
each stored value:

    g=3  1.40126836793985491...   ->  T222, T285
    g=5  1.17628081825991750...   ->  T222, T284, T285
    g=7  1.11548110945659164...   ->  nothing
    g=8  1.12876086807048221...   ->  nothing

The cause is the documented one: `/revisions/T285` shows the last reviewed
revision is four days older than the rows, and values are held out of search by
number until a board member reviews them. The part that is not documented is
that the page gives a reader no sign of it. The mark that exists for a value
search will not return — `includes/not-findable-mark.html`, whose own comment
says it is there so that the table and the search do not "contradict each
other" — is driven by `findable_by_number()`, which tests the *stored
precision* and nothing else. It has no way to know a row is unreviewed, so no
dagger appears. I grepped the delivered HTML for the dagger and for any other
review marker: there is none.

This matters to a contributor with a laptop more than to a run. They publish or
extend a table, search for one of their own values to check it landed, get
nothing back, and have three explanations to choose between: the value is
wrong, the write silently failed, or the search is broken. The true one —
"it is there, correct, and waiting for review" — is the only one the page does
not offer, and the natural reaction is to re-run the generator or re-publish.

What the skill says now, at section 9:

> Values are held out of search by number until a board member reviews them.
> That is deliberate: a reader looking at a table can see an entry is
> unreviewed, and somebody typing digits into a search box cannot.

The first sentence is right. The second is the justification, and its premise
is false: a reader looking at the table cannot see it either.

What it should say: keep the first sentence, and replace the justification with
what a contributor can act on. Something like — *a search by number will not
return your values until the revision that holds them is reviewed, and nothing
on the table page marks them, so a search that misses your own new row is
evidence about the review queue and not about the value. Check
`/revisions/<tid>` for which revision was last reviewed before concluding
anything about the numbers.* Same for a partial growth: rows carried over
unchanged keep answering while the new ones do not, so a table can be half
findable with no visible seam.

Evidence: 2026-09-20, T285. Four `/api/lookup` calls with the key, `RIF`
bounds, results as tabled above; `/revisions/T285` (last reviewed 2026-09-16
22:08, six unreviewed revisions after it); `GET /T285`, 33,436 bytes, no
`&dagger;` and no review marker anywhere in the body. The same boundary,
against the same mechanism, was measured independently on T286 and T300 on this
date by another run, so it is not a fact about one table.

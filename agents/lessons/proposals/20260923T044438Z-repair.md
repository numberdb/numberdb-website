## Some Sage symbolic functions only import reliably through `sage.all`

What happened: repairing T433 needed a reader-facing Sage program for the
Dickman-de Bruijn function. The narrow import
`from sage.functions.transcendental import dickman_rho` failed under SageMath
10.9, both in the repair's check and in the earlier critique. After
`import numberdb.sage`, it raised `AttributeError: cannot access submodule
'function' of module 'sage.symbolic' (most likely due to a circular import)`.
The broad import `from sage.all import dickman_rho` worked and returned
53-bit values, including `dickman_rho(12)`.

What the skill says now: named imports are preferred over `sage.all`, and it
lists root finding, `RealBall.str` and `QQ('1.25')` as things the named
imports do not bring.

What it should say: symbolic functions such as `dickman_rho` can be another
exception. Check the import before writing a Programs block or generator; if
no stable narrow import exists, a reader-facing Programs block may use
`from sage.all import dickman_rho`, while a generator should either find a
verified narrow import or explain the exception.

Evidence: `agents/sage.sh /tmp/T433_import_check.py`, 2026-09-23, printed
`AttributeError` and the circular-import message for the narrow import.
`agents/sage.sh /tmp/T433_sage_checks.py` printed
`import: from sage.all import dickman_rho ok` and 53-bit values for
`u=3/2, 3, 5, 10, 12`.

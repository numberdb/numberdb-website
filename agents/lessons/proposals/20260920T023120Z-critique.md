# Proposed by the T285 growth critique, 2026-09-20

Two lessons, both met while asking whether T285 (minimum dilatations of
pseudo-Anosov maps with orientable foliations) can grow. Both are true for a
contributor with a laptop: one is about where a knowledge-bounded range really
comes from, the other about what the search endpoint does with a parameter it
does not know.

---

## When the range is bounded by what is *known*, the completeness note is a claim about the literature, and an abstract is not the literature

What happened: T285 holds $\delta_g^+$ for genus 1 to 5 and says

    complete: no (it holds 1 <= g <= 5; in [LT], the next cases g = 6,7,8
    are given only as lower bounds)

That sentence is exactly what its source's abstract says — Lanneau and
Thiffeault, arXiv:0905.1302: "We find the minimum dilatation ... for genus
three, four, or five, and provide a lower bound for genus six to eight." It is
not what the paper says. Two pages into the same paper, in the Remark after
the lower-bound theorem:

> In addition, Aaber & Dunfield and Kin & Takasawa have found a pseudo-Anosov
> homeomorphism realizing $\delta_7^+$, and Hironaka has done the same for
> $\delta_8^+$. Hence, all the lower bounds in [that table] except for genus 6
> are known to be realized.

A lower bound known to be attained is the minimum, so two of those three cases
were settled before the paper was printed, and the table is two rows short of
what its own reference knows. The values are 1.1154811094565916… and
1.1287608680704822…, neither of them anywhere in the corpus, and both
reachable by exactly the method the generator already uses — they are the
largest roots of the same two integer polynomials the lower bounds were stated
with.

Worse, the note had already been through a critique and a repair, and the
repair checked it *against the abstract* and recorded "checked the LT abstract
and Theorem 1.3". Abstract-checking is what made it wrong the second time.

What the skill says now: "Say which range you chose and why in the
completeness note. That sentence is the argument, and it is what a reader
checking whether their own number belongs here actually reads." It treats the
range as a choice the author makes — a denominator bound, a size target, a
count — and says nothing about the case where the range is not chosen at all
but dictated by what has been proved.

What it should say: some tables are bounded by knowledge rather than by cost
or by taste — minimum dilatations, class numbers of a type settled case by
case, "the $n$ known $X$" — and there the completeness note is a *citation*,
not a preference, and it goes stale the way a value never does. Two habits
follow.

- Read past the abstract of the source to its remarks and its "note added",
  which is where a result from the months around publication lands. The cheap
  way to do this without a PDF reader: `curl -L arxiv.org/e-print/<id>`
  returns the LaTeX source, and theorem statements are greppable in it.
- Look for a survey. One sentence in Hironaka's 2014 survey (arXiv:1403.2987)
  — "In the orientable case, $\delta_g^+$ has been computed for $g =
  2,3,4,5,7,8$" — settles in one line what four papers did, names the one
  genus that is still open, and is the sentence the completeness note should
  be paraphrasing.

Evidence:

    curl -L https://arxiv.org/e-print/0905.1302 | tar xz    # LT, systole.tex
    grep -n "realizing" systole.tex                         # the Remark above
    curl -L https://arxiv.org/e-print/1403.2987 | tar xz    # the 2014 survey
    grep -n "has been computed for" traintrack.tex

and in Sage, that the two polynomials LT state as lower bounds give the values
the later papers print:

    x^14 + x^13 - x^9 - x^8 - x^7 - x^6 - x^5 + x + 1 -> 1.11548110945659164…
    x^16 - x^9 - x^8 - x^7 + 1                        -> 1.12876086807048221…

Aaber–Dunfield print $\delta_7^+ \approx 1.11548110945659$ and Hironaka
$\delta_8^+ \approx 1.12876$.

## `GET /api/search` reads only `expression=`; every other parameter answers with an empty result list

What happened: I wanted to know whether the corpus already holds
1.1154811094565916, so I asked the API for it the obvious way:

    $ curl -H "Authorization: Bearer $key" \
        'https://numberdb.org/api/search?number=1.1154811094'
    {"results": [], "messages": [], "time_request": "0.000s"}

That reads as "no table holds this number", and it is what a contributor would
write first. It is not an answer: the endpoint takes `expression`, and with no
`expression` it returns before searching anything
(`advanced_search_results` in `numberdb_app/api.py`). The proof that the empty
list means nothing is to ask it for a number the corpus certainly holds:

    $ curl -H ... 'https://numberdb.org/api/search?number=1.1762808182'
    {"results": [], "messages": [], "time_request": "0.000s"}

Lehmer's number is in three tables. `messages` is empty too, so there is no
hint that the query was never run, and `time_request: 0.000s` is the only tell.

Through the client the same question is answered correctly:

    numberdb.search_real_ball(RR('1.176280818259917506'), RR(1e-12))
    # 3 hits: T222, T284, T285
    numberdb.search_real_ball(RR('1.115481109456591644'), RR(1e-12))
    # 0 hits -- and this one is a real zero

What the skill says now: it tells you to search the corpus before writing a
table, and gives `numberdb.search_text` and the `search_real_*` calls. It does
not say what the HTTP endpoint behind them wants, and "is this number already
here?" is precisely the question a contributor is most likely to fire at a URL
by hand. (`docs/agent-environment.md` already records the text-query half of
this — "the `api/search` route ... answers `{"results": [], ...}` to a word",
with `api/lookup` as the route that does answer. The by-value half is the one
that bites, because a by-value search is the one whose empty answer you
believe.)

What it should say: search by value through the client
(`search_real_ball`, `search_real_interval`, `search_integer`, …). If you call
the endpoint directly it is `GET /api/search?expression=...` and nothing else
— a parameter it does not recognise produces `{"results": [], "messages": []}`,
which is indistinguishable from a corpus that holds nothing near your number.
Test any by-hand search against a number you know is stored before believing a
zero.

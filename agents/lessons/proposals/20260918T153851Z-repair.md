## Preserve the parameter path when flattening `numberdb.table(... )["Numbers"]`

What happened: T333's generator claimed that a non-publish run checks the values read back from the API, but its `_flatten_numbers` helper only read `params` from record-shaped leaves. The API returned nested entries: commented leaves looked like `{"number": "...", "comment": "..."}` under `Numbers[n][d]`, and uncommented leaves were bare strings. The helper therefore skipped every row and reported `stored table has 0 values, expected 999` after `verify()` had matched all 999 values.

What the skill says now: it says `numberdb.table(...)` returns the whole document and that `Numbers` is every entry, and a separate proposed lesson says not to write the nested view back as a revision. It does not say how to consume the nested view correctly in an independent check.

What it should say: when reading `Numbers` from `numberdb.table(...)`, handle both flat record lists and nested mappings. In a nested mapping, a leaf with `number` and `comment` usually does not carry `params`; recover the parameter values from the path through the mapping. A bare nested leaf is itself the value.

Evidence: T333 repair, 2026-09-18. Before the fix, `cat "$NUMBERDB_KEY_FILE" | NUMBERDB_KEY_FROM_STDIN=1 agents/sage.sh /tmp/T333-generate-updated.py` printed `<VerifyReport T333: 999/999 matched, 0 differing, 0 missing, 0 extra>` and then failed with `AssertionError: stored table has 0 values, expected 999`. After `_flatten_numbers` yielded `dict(zip(("n", "d"), path))` for nested leaves, the same server-fetched generator printed `stored values satisfy the Hirzebruch generating-series formula`.

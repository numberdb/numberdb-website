# Lessons from the ideas run of 2026-09-22T23:44Z (the Mathieu equation)

Three things this run met that the skill does not cover. All three are true
for a contributor with a laptop; the deployment notes from the same run are in
`docs/agent-environment.md`.

## A control value catches the *library's* convention, not only your own code

What happened: the batch's checks rest on `scipy.special.mathieu_a` and
`mathieu_cem` as an independent implementation. Before comparing anything, the
run evaluated them at $q=0$, where the answers are known in closed form, and
two conventions fell out that no amount of agreement at $q\neq0$ would have
revealed:

* `mathieu_cem(1, 0, 60)` returns $0.5$. The third argument is in **degrees**.
  A generator that stores $\mathrm{ce}_n$ at $z$ radians and checks against
  scipy at the same number would have a table wrong everywhere and right at
  $z=0$, and the error is smooth, so nothing looks broken.
* `mathieu_cem(0, 0, 60)` returns $1/\sqrt2$, not $1$: scipy normalises by
  $\int_0^{2\pi}\mathrm{ce}_n^2=\pi$ for every $n$ including $n=0$, while
  Mathematica's `MathieuC` normalises at $z=0$. The two differ by a constant a
  reader would not guess.

The same probe settles the equation itself. The corpus would have been built
to $w''+(a-2q\cos2z)w=0$; Whittaker and Watson write
$y''+(a+16q\cos 2z)y=0$, and at $q=0$ both give $a_n=n^2$, so the control at
$q=0$ does *not* separate those two -- which is the other half of the lesson:
pick the control that varies the parameter whose convention you are testing.
$a_0(1)=-0.4551386041\ldots$ in the first convention separates them at once.

What the skill says now: "verify known answers as controls first", and
"`elliptic_k` takes the parameter $m$, not the modulus $k$; they differ from
the second entry onwards" -- which is the same phenomenon, stated as a warning
about one function rather than as a method.

What it should say: before comparing a computation with a library, evaluate
the library at an argument whose answer you know in closed form, and check the
units, the normalisation and the parameter meaning separately. A control at
the degenerate parameter ($q=0$, $m=0$, $x=0$) tests the units and the
normalisation and is blind to the coupling convention; a control at a generic
parameter tests the coupling. Both are one line, and a table whose check ran
only the second is a table that may be uniformly wrong in a way its own
agreement cannot see.

Evidence: 2026-09-22 ideas run, scipy 1.17.1 installed with
`python3 -m pip install --target=/tmp/pylibs scipy`.
`mathieu_cem(1,0,60) = (0.4999999999999999, -0.866\ldots)` against
$\cos 60^\circ$; `mathieu_cem(0,0,60) = 0.7071067811865475`;
`mathieu_a(0,1) = -0.45513860410741364` against a Hill-matrix computation in
mpmath at 40 digits, $-0.455138604107413548232633187529$.

## Do not label the members of a family by classifying a numerical eigenvector

What happened: the family proposed is indexed by which eigenvalue of a
periodic Schrödinger operator a number is -- $a_n(q)$ for the even
eigenfunctions, $b_n(q)$ for the odd. The obvious generator diagonalises a
truncated matrix and sorts the eigenvalues into the two families by testing
whether each eigenvector is symmetric or antisymmetric. Written that way here,
it put $b_5$ where $b_1$ belonged and $b_7$ where $b_3$ belonged, while every
*value* it produced was correct to thirty digits and agreed with scipy. The
cause is that the two families come arbitrarily close: at $q=1$,
$a_4=16.0338323\ldots$ and $b_4=16.0329700\ldots$ differ in the fifth decimal,
and a numerical eigenvector of a nearly degenerate pair is an arbitrary
combination of the two.

A table built that way is wrong in exactly the way this database cannot
tolerate: the numbers are right, the *index* is wrong, so a reader who looks
up $b_1$ is told a true number about a different object, and no digit check
anywhere catches it.

What the skill says now: "What the parameters are and what constraint they
actually satisfy", with the example of a table claiming $k\equiv1\bmod p$
while 702 of its 856 entries were not. That is a constraint nobody checked;
this is a labelling that a check would have to be designed to catch.

What it should say: when the index says *which* member of a family a value is,
derive the label from something exact -- continuation from a parameter value
where the labels are known ($a_n(0)=b_n(0)=n^2$), separate defining equations,
a count of sign changes -- and then assert an ordering the family is known to
satisfy. Here the assertion is the interlacing
$a_0<b_1<a_1<b_2<a_2<b_3<\cdots$, one line, and it fails immediately on the
swapped labelling. A family with a known ordering among its members should
assert it in the generator; it is the only check that tests the index rather
than the values.

Evidence: 2026-09-22 ideas run. The parity-classifying script reported
"b1 = 25.0208408232897663652" (which is $b_5(1)$) and "a1 = -0.11024881699"
(which is $b_1(1)$) while reproducing `scipy.special.mathieu_a` and
`mathieu_b` exactly on the same run; the interlacing, checked against scipy at
$q=5$, holds for $a_0<b_1<a_1<b_2<a_2<b_3<a_3<b_4<a_4$.

## An area absent from the corpus may still be taken: read the open `proposal` issues first

What happened: the run picked its subject by searching the live corpus for
names -- *Tracy*, *Painlev\'e*, *random matrix*, *sine kernel* -- found
nothing, and was ready to propose the universal distributions of random matrix
theory. They had been proposed fifteen hours earlier, by another run the same
day. The corpus does not show it (no table exists yet), the text search does
not show it, and `already_here` and `already_asked` both pass: a screened
family is invisible to every duplicate check the skill names until somebody
builds it.

What the skill says now: two searches before writing anything, both against
the published corpus, plus `already_asked` for issues that *request* a family.

What it should say: also look at what has been proposed and not yet built --
for this database, the open issues labelled `proposal` in `numberdb-data`, and
any batch files a campaign keeps. It costs one query
(`gh issue list --repo numberdb/numberdb-data --label proposal --state all`)
and it is the only check that sees work in flight. The same warning belongs on
the other side of the fence: a proposal is a claim about the corpus *on the
day it was screened*, so a builder should re-run the cheap checks before
spending anything.

Evidence: 2026-09-22 ideas run. `numberdb.search_text('Tracy')` returns only
the Airy values table, and `search_text('Painlev\'e')` returns nothing;
`agents/table-ideas/BATCH-2026-09-22T0807.md`, written at 08:07 the same day,
is a five-table batch on the Tracy-Widom laws and the Hastings-McLeod solution
of Painlev\'e II. Four further batches from the same day are open as issues
#190 to #193.

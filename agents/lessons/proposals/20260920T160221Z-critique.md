## `QQ` of a *string* raises until something has pulled in `sage.rings.real_mpfr`

What happened: a check script imported the two rings it needed and nothing
else, the way the skill's "name the rings you use" paragraph asks, and then
read a parameter value out of the table:

    import numberdb.sage as numberdb
    from sage.rings.polynomial.polynomial_ring_constructor import PolynomialRing
    from sage.rings.rational_field import QQ

    QQ('1/4')
    # AttributeError: module 'sage.rings' has no attribute 'real_mpfr'

Not a `TypeError` about the string, and no mention of `QQ` or of a rational:
an `AttributeError` naming a module the caller never imported. It happens
because `Rational.__set_value` (`sage/rings/rational.pyx`, line 578) walks a
chain of `isinstance` checks on its way to the string branch, and one of them
is `isinstance(x, sage.rings.real_mpfr.RealNumber)`. `sage.rings.real_mpfr`
has not been imported, so it is not an attribute of the `sage.rings` package
and the attribute lookup dies before the string is ever looked at.

It bites strings only. `QQ(1)`, `QQ(1)/4` and `ZZ('007')` all work in the same
session. So does `QQ('1/4')` itself as soon as anything has imported
`real_mpfr`, directly or otherwise: importing `sage.rings.complex_arb`,
`sage.rings.real_arb` or `sage.rings.qqbar` is enough. That is why it is easy
to miss -- every generator in the skill imports a ball field, and the
transcendental cases are the ones people test.

The generators it does reach are the exact ones: a family of polynomials or
integers needs `PolynomialRing` and `QQ` and no ball field at all, and reading
a rational parameter back out of `params` is the first thing such a generator
does. T267's `Programs` block is precisely those two imports plus a function
whose first line is `a = QQ(a)`.

What the skill says now: the named-imports paragraph lists what the imports do
not bring -- "root finding (`sage.numerical.optimize`), `RealBall.str`, and
`QQ('1.25')` -- a rational is built from a decimal *string* by hand,
`QQ(125)/10**2`, or it raises." That covers the decimal case and reads as
though `QQ('1/4')` and `QQ('7')` are fine. They are not, in an exact
generator's import set, and the error a reader gets names `real_mpfr` rather
than anything they wrote.

What it should say: extend that sentence. `QQ` of *any* string -- `'7'`,
`'1/4'`, `'1.25'` alike -- can raise `AttributeError: module 'sage.rings' has
no attribute 'real_mpfr'` when nothing has imported a real or ball field.
Build rationals from Sage integers instead, `QQ(ZZ(num))/ZZ(den)`, which works
in every import set, or import `sage.rings.real_mpfr` alongside the rings you
name. `ZZ` of a string never has the problem.

Evidence: 2026-09-20, T368 critique, three runs through `agents/sage.sh`.
`/tmp/probeqq4.py` with `PolynomialRing` and `QQ` imported: `QQ("1/4") raises
AttributeError: module 'sage.rings' has no attribute 'real_mpfr'`.
`/tmp/probeqq2.py` with `QQ` and `ZZ` only: the same for `QQ('7')`, full
traceback ending at `rational.pyx` line 578, while `ZZ('7') = 7` and
`QQ(ZZ('7')) = 7`; `QQ('7')` then answered `7` after `from sage.rings.qqbar
import AA`. `/tmp/probeqq3.py` with the skill's own example import set
(`numberdb.sage`, `QQ`, `ComplexBallField`): `QQ('3/50') = 3/50`, and the
example's `field(QQ('3/50')).elliptic_k()` line runs -- so the skill's
flagship generator is not affected, only the exact ones.

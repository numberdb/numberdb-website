## Read ecnf-data `mwdata` columns from `ecnf-format.txt`
What happened: while checking T293 against the pinned ecnf-data source, I first treated `parts[-3]` in an `mwdata` row as the regulator. That column is `omega`, not `reg`, so every stored regulator appeared to disagree with the source. Reading the documented column order showed that `reg` is column 11 of the file, zero-index `parts[10]`; after that change, all 1171 live T293 values matched the source regulator at the stored precision.

What the skill says now: nothing specific about the `mwdata` column order in ecnf-data.

What it should say: when reading ecnf-data `mwdata.*`, use the column order in `ecnf-format.txt`. After the four label columns, the fields are `rank`, `rank_bounds`, `analytic_rank`, `ngens`, `gens`, `heights`, `reg`, `torsion_order`, `torsion_structure`, `torsion_gens`, `omega`, `Lvalue`, and `sha`. Do not count backward from the end, because `omega` and `Lvalue` are also numeric and can look like plausible regulators.

Evidence: T293 repair on 2026-09-19. `/tmp/t293_checks.py` initially reported 1171 regulator mismatches using `parts[-3]`; after changing the parser to `parts[10]`, the same check reported 1171 expected rows, no missing or extra labels, and `mismatches: 0`.

## The audit has a route for somebody with no database: `GET /api/table/<tid>/audit`

What happened: the T412 critique had to audit a draft on a machine with no
Django and no database. `manage.py audit_table T412` cannot run there at all.
`GET /api/table/T412/audit` with the key in an `X-API-Key` header answered
`{"tid": "T412", "title": ..., "findings": [], "clean": true}` in about a
second. Reading `numberdb_app/api.py` afterwards, that is not a second
implementation: the route calls `findings_for(table)`, the same function the
command calls, and its docstring says it exists precisely because "a build
machine has no database and should not have one". It honours the key for a
private draft, and answers 404 to anybody who may not see the table.

Two limits worth knowing with it. It calls `findings_for` with `fetch=False`,
so external URLs in `Links` are never requested -- an `HREF{}` to another table
is checked against the corpus, a link to Wikipedia or the LMFDB is not, and a
`curl -o /dev/null -w '%{http_code}'` over the `Links` block is still the
contributor's job. And the HTML page is a different question from the audit:
`/T412` answered 404 to the same key, because a table page authenticates by
session and not by API key, so "the audit answers but the page does not" is
normal for a draft rather than a sign of anything wrong.

What the skill says now: "Let `manage.py audit_table` confirm afterwards rather
than instead", and in section 10, "`manage.py sweep_arb` (server-side)". Both
are named as if the reader had the site checked out with a database. A
contributor installing `pip install numberdb` has neither, so the skill's one
structural check reads as unavailable to the only person it is written for.

What it should say: name the API route beside the command wherever the audit is
mentioned -- `GET /api/table/<tid>/audit`, with the key, which runs the same
checks and works on a draft -- and say that it does not fetch external links.

Evidence: T412 critique, 2026-09-22. `curl -H "X-API-Key: ..."
https://numberdb.org/api/table/T412/audit` returned `clean: true`;
`https://numberdb.org/T412` returned 404 with and without the same key;
`numberdb_app/api.py:1543` (`audit`) and
`numberdb_app/management/commands/audit_table.py:109` (`findings_for(table,
fetch=False)`).

## `EllipticCurve([a1,a2,a3,a4,a6])` needs Singular; `EllipticCurve(QQ, ainvs)` does not

What happened: the T412 critique recomputed the table's claimed range from
Sage's mini Cremona database, building each curve from the `a`-invariants the
database returns. On a modular passagemath install,
`EllipticCurve([0, 0, 1, -1, 0])` raises

    ImportError: cannot import name PolynomialSequence_generic

from `sage.libs.singular.function`. The curve constructor has no base ring to
work from, so it calls `Sequence(x).universe()` to guess one, and `Sequence`
imports `sage.rings.polynomial.multi_polynomial_sequence`, which pulls in
Singular. Naming the ring -- `EllipticCurve(QQ, list(ainvs))` -- skips the
guess and the import, and the rest of the script ran unchanged: minimal model,
`c4`, `c6`, `conductor`, `ap`, all 93 curves in under a minute.

The same shape as the skill's existing warning, one layer down: the failure is
not in the elliptic-curve code, it is in the generic machinery that runs when
you do not say what ring you mean. `from sage.schemes.elliptic_curves.constructor
import EllipticCurve` after `import numberdb.sage as numberdb` is necessary and
not sufficient.

What the skill says now: "Name the rings you use, rather than importing
`sage.all`", and lists what the named imports do not bring (root finding,
`RealBall.str`, `QQ('1.25')`). It does not say that a *constructor* called
without a ring can reach a library the install does not have.

What it should say: add to that list -- a constructor that infers its base ring
from a list, `EllipticCurve([...])` being the common one, goes through
`Sequence` and needs Singular. Pass the ring: `EllipticCurve(QQ, ainvs)`.

Evidence: 2026-09-22, `/tmp/t412_range.py` under `agents/sage.sh`. The
traceback is `constructor.py:471` -> `sequence.py:296` ->
`multi_polynomial_sequence.py:173` -> `plural.pyx` -> `function.pyx:95`.

## A `Similar tables` relation is a claim about the other table, and goes stale by being written

What happened: T412, 93 curves of conductor at most 175, glosses its link to
T64 as "stores the Neron-Tate regulator of **the same rank-one curves** instead
of the cyclotomic $p$-adic regulator". T64 holds 1007 curves, conductors to
630. T412's curves are a subset of them, so the sentence is not a relation
between the two tables but a description of one of them that happens to be
false. Its neighbour in the same block is right, and by being weaker: the
L-value table is glossed "for the same rank", which stays true whatever either
table's range becomes.

Nothing checks this. `audit_table` resolves the slug and reports `clean`,
because whether two ranges coincide is not something a structural check knows;
the two documents have to be fetched and compared, which is one `GET
/api/table?url=...` each.

What the skill says now: "`Similar tables` states the *relation*, in words",
with the example "the same expansion's limits, taken over the denominators of
the convergents rather than over the partial quotients" -- a relation between
the quantities. It does not warn that a relation phrased over the *entries*
("the same curves", "the same discriminants", "the same arguments") is a claim
about somebody else's range.

What it should say: state the relation between the quantities, not between the
rows. If the ranges really do coincide and that is the point, fetch the other
table and check it before writing it, and expect the sentence to need editing
when either table is extended.

Evidence: 2026-09-22. `GET /api/table?url=Regulators_of_elliptic_curves_over_Q_of_rank_1`
gives 1007 curves with conductors 37 to 630; T412 holds 93 with conductors 37
to 175, all of them in that set. `agents/critiques/T412.md`, finding 1.

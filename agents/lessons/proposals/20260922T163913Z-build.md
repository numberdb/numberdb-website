## `dry_run.py` exactness should accept Sage p-adics
What happened: the dry run for T414 computed 566 `Qp` entries correctly, but
`agents/table-build/check.py` reported every value as `coefficient of
unexpected type pAdicCappedRelativeElement`. A Sage p-adic element carries its
own `O(p^n)` precision, which is exactly what the NumberDB client writes for a
`Qp` table. Converting it to a string to appease the check would have thrown
away type information before the client saw it.

What the skill says now: run `exactness(values)` and act on what it reports.
It describes exact integers, rationals, polynomials and enclosures, but does
not say explicitly that a p-adic value is also precision-carrying.

What it should say: for a `Qp` table, return Sage p-adic elements directly.
The dry-run exactness check should treat them like finite enclosures: exact
modulo their stated `O(p^n)`, not like an unexpected coefficient type.

Evidence: `NUMBERDB_REMOTE=local agents/sage.sh /tmp/run_unit_roots_dry.py
agents/table-build/dry_run.py agents/table-build/check.py
generators/unit-roots-frobenius-polynomials/generate.py`, before the helper
fix, reported `pAdicCappedRelativeElement` on the first five T414 rows.

## Sage p-adic polynomial roots can pull in missing compiled machinery
What happened: the first independent check for T414 tried to build
`PolynomialRing(Qp(p, prec), "x")` and call `.roots()` on
`x^2-a*x+p`. In the Sage image this imported
`polynomial_integer_dense_ntl` and failed with an undefined NTL symbol before
any root was computed. The generator was then checked instead by the Catalan
series
`alpha = a * (1 - sum_{n>=1} C_{n-1} (p/a^2)^n)`, which uses only p-adic
field arithmetic.

What the skill says now: with named imports, some Sage machinery is missing,
and a generator should write arithmetic out instead of reaching for heavy
subsystems. It names determinants, power-series operations and symmetric
function expansion, not p-adic polynomial roots.

What it should say: p-adic polynomial root finding is another path that may
reach uninitialised or missing compiled Sage modules. For a quadratic ordinary
root, use Hensel iteration or an explicit series as the independent check
rather than `PolynomialRing(Qp(...)).roots()`.

Evidence: `/tmp/check_unit_roots_independent.py` against the first T414
generator failed with
`undefined symbol: _ZN3NTL5coeffERKNS_3ZZXEl` while constructing
`PolynomialRing(field, "x")`; the Catalan-series replacement checked all 566
entries.

## Sage may not parse the p-adic series text it prints
What happened: the read-back check for T414 fetched the draft through
`numberdb.sage.table("T414")`, receiving stored p-adics as strings such as
`1 + 4*5 + 3*5^2 + O(5^72)`. Passing that string to `Qp(5, prec)(text)`
raised `TypeError: unable to convert ... to a rational`. The check had to
parse the displayed series into an integer modulo `p^n` before coercing it
back into `Qp`.

What the skill says now: check identities on the values read back out of the
database, and Qp values are written in the client's rendering of a Sage
p-adic element.

What it should say: a read-back check for a `Qp` table may need to parse the
stored series text, or use a client decoder if one is available, rather than
expecting Sage's `Qp` constructor to read the display form directly.

Evidence: `/tmp/check_stored_unit_roots.py` first failed on T414 with
`TypeError: unable to convert '1 + 4*5 + ... + O(5^72)' to a rational`;
after parsing the series terms explicitly, it checked all 566 stored entries.

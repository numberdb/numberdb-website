## Sage matrix eigenvalues over `RealField` may still be machine precision

What happened: the first Mathieu generator built finite symmetric Hill
matrices over `RealField(500)` and called `.eigenvalues()`. The dry run
accepted the resulting decimal strings, but a focused probe on one returned
eigenvalue failed with `TypeError: cannot approximate to a precision of
270 bits, use at most 64 bits`. The dense eigensolver had returned
machine-precision values, not high-precision Sage reals, so the apparent
50-digit table was only a formatted double. Replacing the eigensolver with
Sturm counts and bisection on the tridiagonal matrices fixed it.

What the skill says now: it warns that `matrix(...).determinant()` may reach
for Sage machinery that named imports did not initialise, and it warns against
fixed-precision values wrapped as intervals. It does not say that a matrix
eigensolver may silently return low-precision values from a high-precision
matrix.

What it should say: after using Sage's numerical eigensolvers, check the
parent or precision of the returned eigenvalues before trusting the digits.
For a symmetric tridiagonal matrix, prefer a Sturm-count bisection when the
table needs more than double precision: it keeps the arithmetic in the field
you chose and gives an independent count of the ordered eigenvalue.

Evidence: T436 build, 2026-09-23. `agents/sage.sh
/tmp/probe_mathieu_interlace.py generators/mathieu-characteristic-values-a/generate.py`
failed on `b.n(digits=80)` with "use at most 64 bits"; the later dry run using
Sturm bisection reported 770 entries, longest 55 characters, and
`verify(sample=None)` reported `770/770 matched, 0 differing, 0 missing, 0
extra`.

## A library cross-check can be the wrong side when branches are close

What happened: the Mathieu proposal named SciPy's `mathieu_a` as a cheap
cross-check. It agreed on the sample values and on almost every stored row,
but `scipy.special.mathieu_a(5, 21)` returned the same double-precision value
as `mathieu_a(3, 21)`. The ordered odd Fourier block and the neighbouring
values at `q=20.5,21.5,22,...` put `a_5(21)` on the next branch. Treating
SciPy as the authority would have relabelled exactly the kind of close branch
the proposal warned about.

What the skill says now: "When two computations disagree, neither is right
until you know why." It does not say what to do when the independent library
is the computation that is wrong on one branch.

What it should say: an independent library check is evidence, not an oracle.
For branch-labelled spectral quantities, check ordering or continuation
against the defining eigenproblem as well as comparing to the library. If the
library has an isolated anomaly, make the generator assert that anomaly
explicitly and use another branch-label check, rather than either deleting the
comparison or following the library blindly.

Evidence: T436 build, 2026-09-23. `agents/sage.sh
/tmp/probe_scipy_mathieu.py` printed matching odd-branch values around
`q=21`, except that at `q=21` SciPy returned
`[-15.8265..., 14.9884..., 14.9884..., 54.4877...]` for
`a_1,a_3,a_5,a_7`; the generator's interlacing check and ordered odd Fourier
block put `a_5(21)=37.4626132260...`.

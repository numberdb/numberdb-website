## A misspelt `/api/` path answers 404 with an HTML page, not JSON -- so content-type, not status, is what separates "no such endpoint" from "wrong method"

What happened: looking for a list of my own drafts I asked
`GET /api/drafts` with the key. What came back was 11541 bytes of the site's
rendered "Not found - NumberDB" page -- doctype, stylesheets, a MathJax
loader -- under status 404. `response.json()` on that raises a decode error
several frames away from the typo that caused it, and the exception names the
JSON, not the URL.

The useful part is the contrast with an endpoint that *does* exist:

    GET /api/drafts    -> 404  11541 bytes  text/html; charset=utf-8
    GET /api/nonsense  -> 404  11543 bytes  text/html; charset=utf-8
    GET /api/tables    -> 405     22 bytes  application/json

`/api/tables` is a real path that refuses the method; `/api/drafts` is not a
path at all. Both are errors, both are unhandled by a naive client, and the
**content-type tells them apart where the status code does not**: a real API
endpoint answers in JSON whatever it thinks of your request, and the HTML
body means Django's 404 handler took it, i.e. nothing is routed there.

This matters here because the corpus notes already record that
`/api/tables` answers 405 and that a throttled probe of it answers 429 before
the method check -- so a run trying to establish "does this endpoint exist"
has three different failures to distinguish and only one of them is about the
endpoint. Checking `Content-Type` first collapses that: HTML means the path is
wrong, JSON means the path is right and the request is not.

There is no drafts listing to find, which is the other half of this. Neither
`/api/drafts` nor any `/api/*` path lists your unpublished tables; `/drafts`
is a signed-in browser page that answers a key with a 302 to the login form.
A key holder enumerates their own drafts by walking T-numbers, which is
recorded elsewhere. What is new is only that the *misspelt* attempt fails in
a way that looks like a parsing bug in your own code.

What the skill says now: nothing about what an unrouted `/api/` path returns.
It documents individual endpoints, so a reader who guesses one gets an error
the skill does not explain.

What it should say: one sentence where the API endpoints are listed -- an
`/api/` path the server does not route answers 404 with an HTML error page
rather than JSON, so check `Content-Type` before `.json()`; an HTML body means
you have the URL wrong, and a JSON body means the URL is right.

Evidence: 2026-09-23, from the triage of `20260923T111940Z-build.log`.

    curl -s -o /dev/null -w "%{http_code} %{size_download} %{content_type}\n" \
         -H "Authorization: Bearer $KEY" https://numberdb.org/api/drafts
    404 11541 text/html; charset=utf-8

    ... /api/nonsense   -> 404 11543 text/html; charset=utf-8
    ... /api/tables     -> 405 22    application/json

## The reply that distinguishes a draft from a nonexistent id is the *keyed* one, and it is the only probe that settles "did the run create anything"

What happened: I had to establish that a build which died before its first
turn had created no table. The standing note is that an unpublished draft
reads to an unkeyed client as HTTP 200 carrying
`{"error": "Table with id 'T441' does not exist."}` -- byte-identical, all 49
bytes of it, to the answer for an id never used. That is true, and it means an
anonymous probe cannot answer the question at all: "does not exist" covers
both "nothing was created" and "something was created and you cannot see it",
which are the two outcomes a triage most needs to tell apart.

The keyed probe does separate them, and is the one to use:

    keyed  GET /api/table?id=T445  -> 200  3613 bytes  (the table)
    keyed  GET /api/table?id=T446  -> 200    49 bytes  does-not-exist
    keyed  GET /api/table?id=T447  -> 200    49 bytes  does-not-exist

With the owning key, a draft returns its content and only a genuinely unused
id returns the 49 bytes. So `T445` is the highest id that exists and nothing
was created -- a conclusion the anonymous probe could not have reached, since
it returns the same 49 bytes for `T445` as for `T447`.

The generalisation worth keeping: **the 49-byte does-not-exist body means
"absent" only when the request carried the key that would have made it
visible.** Without a key it means "absent or invisible", which is not an
answer. A contributor hits the same thing the first time they check whether
their own upload landed while signed out, or with the header dropped -- and
the obvious next move on reading "does not exist" is to create it again.

Note also that the singular path does not serve this: `GET /api/table/T441`
answers 405 `{"error": "Use POST or PUT."}` with no `Allow` header, while
`GET /api/table?id=T441` works and `GET /api/table/T441/audit` also works --
so the same prefix serves a GET for the sub-resource but not for the table.

What the skill says now: nothing that ties the ambiguity to the key. The
does-not-exist-under-200 behaviour is recorded as a hazard; which request
resolves it is not.

What it should say: when you need to know whether a table id exists, send the
probe **with your key**. Unkeyed, `does not exist` cannot be distinguished
from `exists but is your draft`; keyed, it means the id is genuinely unused.
Never conclude from an unkeyed 404-in-a-200 that your upload failed.

Evidence: 2026-09-23, from the triage of `20260923T111940Z-build.log`; three
keyed `GET /api/table?id=...` calls as above, against a site where `T441` and
`T445` are drafts owned by the key and `T446`/`T447` have never been used.

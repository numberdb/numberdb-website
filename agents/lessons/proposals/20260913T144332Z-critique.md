## `ComplexBallField` has no `bernoulli`, and a fixed snippet in `table.yaml` is not the snippet on the page

What happened: T227's Programs snippet computed
`CBF.bernoulli(k + 1)` with `CBF = ComplexBallField(...)`. That raises
`AttributeError: 'ComplexBallField_with_category' object has no attribute
'bernoulli'`, because `RealBallField` has the method and `ComplexBallField`
does not. The build noticed and fixed it in the local `table.yaml`, using
`CBF(QQ(bernoulli(k + 1)) * H / QQ(k + 1))` with `bernoulli` from
`sage.arith.misc`. It then sent only a later comment edit to the table. The
document on the site kept the broken line. The generator itself uses
`bernoulli` from `sage.arith.misc` and was never affected.

What the skill says now: nothing about `bernoulli` on ball fields. Nothing
says that a snippet should be checked in the form the table stores it.

What it should say: in the list of what the named imports do not bring, add
that `ComplexBallField` has no `bernoulli`. Use `RealBallField(prec).bernoulli(n)`,
or the exact `bernoulli(n)` from `sage.arith.misc` coerced into the field.
And run the `Programs` snippet as it comes back from `numberdb.table(...)`,
not from your local file. The copy a reader gets is the stored one, and an
edit that was never sent looks fixed from where you are sitting.

Evidence: T227, 2026-09-13. `/tmp/t227_sage.py` ran the stored snippet and
it failed with the error above at $k=0,1,2,19$. `/tmp/t227_repo_snippet.py`
ran the repository version, which printed $A_0$, $A_1$ and $A_{19}$ in
agreement with the stored rows. `hasattr(RealBallField(), 'bernoulli')` is
`True`.

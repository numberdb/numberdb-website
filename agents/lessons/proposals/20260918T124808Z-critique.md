## MathJax's node API reports a TeX error as an `merror` node, not as an exception

What happened: T329's mathematics was checked by converting every `$...$`
fragment with `mathjax-full@3` under node, the way the T221 note prescribes.
The first checker wrapped `doc.convert(f)` in `try`/`catch` and counted
exceptions. It reported "checked 44 errors 0" -- and three of those 44 were
controls written to be broken: `\notarealmacro{x}`,
`\begin{nosuchenv}x\end{nosuchenv}` and `\left( x`. MathJax does not throw on
a TeX error. It *typesets* the error: the output carries an `merror` element
with the message in a `data-mjx-error` attribute, exactly as the browser
renders the red "Math input error" box a reader sees. A checker that only
catches exceptions therefore passes every table, including one whose formula
prints an error box on the page, and it looks like a clean run.

Reading the converted output instead found two of the three controls:

```js
const html = adaptor.outerHTML(doc.convert(f, {display: false}));
if (/data-mjx-error|merror/.test(html)) { ... }
```

`\begin{nosuchenv}` gave "Unknown environment 'nosuchenv'" and `\left( x` gave
"Extra \left or missing \right". `\notarealmacro{x}` is silently typeset as
letters with `AllPackages` loaded, so it is not a usable control. T329's 41
real fragments gave 0 errors against that checker.

What the skill says now: nothing about checking TeX at all. "Math input error
because a JSON escape had eaten a backslash" is one of the three rendering
faults the critique prompt names, and the site renders MathJax in the browser,
so a stored document cannot be checked by fetching the page.

What it should say: MathJax reports a TeX error inside the output it produces,
not by raising. Check the converted HTML for `merror` / `data-mjx-error`
rather than catching exceptions, and use a control that MathJax genuinely
rejects -- an unknown environment, or an unclosed `\left` -- because an
undefined macro is typeset as letters and confirms nothing. This is the same
rule as "a measurement needs a control that returns a known answer", in the
place where the control is easiest to get wrong: a checker that reports zero
errors on a fragment you know is broken is measuring nothing.

Evidence: 2026-09-18, T329 critique. `/tmp/mj329/check.js` first reported
`checked 44 errors 0` with the three controls present; after reading
`adaptor.outerHTML` it reported `checked 44 errors 2`, naming both.

## `binomial` is not reachable through `sage.functions` under the named-ring import discipline

What happened: a check script for T329 built the symmetric Pascal matrix
$A_{ij}=\binom{i+j-2}{i-1}$ and imported `binomial` the way the Sage
documentation spells it:

```python
import numberdb.sage
from sage.rings.rational_field import QQ
from sage.functions.other import binomial
```

That import fails before anything runs:

```
File "sage/symbolic/expression.pyx", line 14220, in init sage.symbolic.expression
AttributeError: cannot access submodule 'function' of module 'sage.symbolic'
(most likely due to a circular import)
```

`sage.functions.other` pulls in `sage.functions.trig`, which pulls in
`sage.symbolic.function`, and the symbolic ring is part-initialised at that
point because the named-ring imports the skill prescribes never asked for it.
`from sage.arith.misc import binomial` imports cleanly and returns the same
integer; the rest of the script ran unchanged.

What the skill says now: "Name the rings you use, rather than importing
`sage.all`", followed by a paragraph of what the named imports do not bring
-- root finding, `RealBall.str`, `QQ('1.25')`. `binomial` is not in that list,
and `sage.functions.other` is where a search for it lands.

What it should say: add `binomial` and the rest of `sage.functions.*` to that
paragraph. The arithmetic functions live in `sage.arith.misc`
(`binomial`, `factorial`, `gcd`, `valuation`); `sage.functions.*` is the
*symbolic* layer and importing any of it from a script that has not
initialised the symbolic ring raises a circular-import `AttributeError`
rather than an `ImportError`, which does not look like a missing import at
all.

Evidence: 2026-09-18, T329 critique. `/tmp/signs329.py` under
`agents/sage.sh`, failing with the traceback above and running to completion
after the one-line change; SageMath in `numberdb/builder:latest`.

## A batch-level new tag can fail the first table's audit

What happened: family #185 proposed a new `quantum mechanics` tag, with nine
tables named as eventual carriers. T404 was the first table in the family to
reach the audit. With that tag present, `/api/table/T404/audit` returned
`Tags: "quantum mechanics" reaches only this table; a tag that leads nowhere
else leads nowhere`. The table already had the existing `eigenvalue` and
`physics` tags, and removing `quantum mechanics` made the audit clean.

What the skill says now: propose a new tag when three or more tables would
carry it, and `audit_table` refuses a tag that reaches only this table.

What it should say: when a screened family proposes a new tag, the first table
in that family may still need to omit it until enough published tables carry
the tag, or until a reviewer applies the tag across the already-named related
tables. Record the omitted tag and the tables that justify it in the build
report, rather than leaving the draft with an audit finding.

Evidence: T404 build, 2026-09-22. The audit with `quantum mechanics` present
returned one finding; after removing the tag it returned `{"findings": [],
"clean": true}`.

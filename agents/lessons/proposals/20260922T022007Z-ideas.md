## The corpus *can* be listed: `/tables` paginates

What happened: the skill says "There is no call that lists the corpus -- to
see everything you walk the T-numbers", so this run started to walk them, then
tried the website instead. `https://numberdb.org/tables` is an ordinary
infinite-scroll page and takes `?page=N` and `?sort_by=id|title|entry_count`.
Twelve requests returned the whole corpus -- T-number, title and entry count
for all 390 tables -- in about four seconds, against 390 API reads for the same
thing.

That matters for a proposal more than for a build. The screen's `already_here`
searches words of a name, and the skill is right that a family can sit here
under a name sharing no word with it; the only defence is having read the
titles. 390 titles is twenty seconds of reading and it is what tells you that
the corpus has chromatic polynomials, Tutte polynomials, Ehrhart polynomials of
the hypersimplices and nothing about matroids.

What the skill says now: "There is no call that lists the corpus -- to see
everything you walk the T-numbers."

What it should say: there is no *API* call that lists the corpus, but
`https://numberdb.org/tables?sort_by=id&page=N` is one page of it, and
paginating that is how to read every title before proposing a family.

Evidence:

    for p in $(seq 1 12); do
        curl -s "https://numberdb.org/tables?sort_by=id&page=$p"
    done | grep -o 'T[0-9]*:' | sort -u | wc -l
    390

## `sage.all` versus the named ring imports: `characteristic_polynomial` needs the first

What happened: the skill tells a generator to name the rings it uses rather
than importing `sage.all`, because a modular passagemath has no `sage.all` and
the named imports run on both. Written that way,
`Matroid.characteristic_polynomial()` fails on full SageMath 10.9:

    import numberdb.sage as numberdb
    from sage.rings.rational_field import QQ
    ...
    ImportError: cannot import name PolynomialSequence_generic

The same call works when the file opens `from sage.all import *`. So the rule
is not "these two are interchangeable and one is more portable": a Sage method
may reach for a module that only `sage.all` has finished importing, and the
failure surfaces inside the method with a name that has nothing to do with what
was called. `PolynomialSequence_generic` is not something a matroid generator
mentions.

What the skill says now: "Name the rings you use, rather than importing
`sage.all`. ... Importing `numberdb.sage` first is what makes the direct
imports work: a ring module imported before Sage is initialised raises 'cannot
import name QQ', and that module does the initialising." It then lists what the
named imports do not bring: root finding, `RealBall.str`, `QQ('1.25')`.

What it should say: add to that list that a Sage *method* may itself fail under
named imports, and that the error names an internal module rather than the
method. When a call that has nothing to do with rings raises `ImportError:
cannot import name <something>_generic`, the fix is to import the module that
initialises it -- or to accept `sage.all` for that generator and say so, since
a table that cannot be computed is worse than one that needs full SageMath.

Evidence: `/tmp/matroid_probe.py` (named imports) and `/tmp/matroid_probe2.py`
(`sage.all`), same method, same matroid, run minutes apart in the same image.

## Do not memoise a recursion on the Tutte polynomial

What happened: the Kazhdan-Lusztig polynomial of a matroid is defined by a
recursion over the lattice of flats, and the contractions repeat, so the first
probe cached $P$ against `(M.tutte_polynomial(), M.size(), M.rank())`. That is
wrong twice over. The Tutte polynomial is not a complete invariant, so the
cache silently returns the polynomial of a *different* matroid whenever two
non-isomorphic contractions share it -- and there is no exception, no
disagreement and nothing in the output to see. It is also slower than no cache
at all: computing a Tutte polynomial to use as a dictionary key costs more than
the recursion step it saves, and the probe was killed at 600 MB on
$U_{5,10}$ with the cache and finished the same index comfortably without it.

What the skill says now: nothing about caching. It says a great deal about
checking values against something independent, which would not catch this: a
wrong cache gives the *same* wrong answer to any implementation that uses it.

What it should say: a generator that memoises intermediate objects must key the
cache on a certificate, not on an invariant. "Two objects with the same
invariant" is the normal case, not the pathological one, and a cache keyed on
an invariant is the one kind of bug that recomputation does not find.

Evidence: with the cache, the run over 19 matroids stopped after 4 and the
container was killed; without it, the same 19 finished and every structural
assertion passed ($Z_M$ palindromic, $Z_{B_n}=(1+t)^n$ for $n\le6$, all $P_M$
coefficients non-negative, $P_M=1$ for rank $\le2$).

## An over-determined defining identity is a free check on every entry

What happened: the Elias-Proudfoot-Wakefield identity
$t^{d}P_M(1/t)=\sum_F\chi_{M|F}(t)P_{M/F}(t)$ fixes $d+1$ coefficients, and
$P_M$ has only $\lceil d/2\rceil$ of them. The surplus equations are not
redundant bookkeeping: they are an independent check that the orientation of
the recursion (restriction inside $\chi$, contraction inside $P$) was the right
one, that $\chi$ was computed with the right sign, and that no cache lied --
asserted on every entry, at no cost, by code that was going to run anyway.

The general shape: when a family is *defined* by an identity with more
equations than unknowns, the leftover equations are the check, and they are
better than most external checks because they test the whole pipeline on the
actual entry rather than a handful of published values.

What the skill says now: "How a builder would check it. Name an independent
fact: a specialisation to a known integer sequence, a value in a published
table, an identity tying it to something the corpus already holds."

What it should say: add a fourth kind -- the surplus equations of an
over-determined defining identity, asserted per entry. It is the only one of
the four that scales to every row rather than to the rows somebody published.

Evidence: worked by hand for $U_{3,6}$, where
$R(t)=6(t-1)+15(t-1)^2+(t^3-6t^2+15t-10)=t^3+9t^2-9t$ gives $c_1=[t^2]R=9$
*and* requires $[t^1]R=c_1-9=0$, which is the check. Both hold; the recursion
then reproduced $P_M=1+(L-n)t$ for all eight rank-3 matroids computed, with
$n$ points and $L$ lines.

## `screen.py requests` cannot distinguish an empty backlog from a broken call

What happened: this run was told to anchor its batch on the open `table wanted`
issues. `python3 agents/table-ideas/screen.py requests` printed nothing, which
is what it also prints when GitHub is unreachable, rate-limited or renamed --
`requests()` catches every exception and returns `[]` (`screen.py:239`).
Twenty minutes went on establishing by hand that the backlog really is empty:
126 issues have carried the label and 0 are open.

The same module's `already_here` has a long comment about exactly this failure
mode, in the function two above it: "A failed question and an empty answer must
not look the same." `requests()` was written without it.

What the skill says now: nothing -- `screen.py` is ours, not the skill's. But
the shape is general and the skill's own advice depends on it: a contributor
who searches the corpus and gets nothing back has to know whether that means
"nothing similar" or "I could not ask".

What it should say (here, as a fix rather than a lesson): `requests()` should
raise, or return a complaint the way `already_here` does. And the stage prompt
should say what a run does when the backlog is empty, because it will be empty
for every run after this one.

Evidence:

    $ python3 agents/table-ideas/screen.py requests
    $ curl -s 'https://api.github.com/search/issues?q=repo:numberdb/numberdb-data+label:"table+wanted"' | jq .total_count
    126
    $ curl -s 'https://api.github.com/search/issues?q=repo:numberdb/numberdb-data+label:"table+wanted"+state:open' | jq .total_count
    0

## When the parameters index a class of objects, the definition has to say the class agrees

What happened: T389 stores the weight enumerator $W_{q,n,k}(x)$ of a $q$-ary
MDS code with parameters $[n,k,n-k+1]_q$. Its definition reads "For a prime
power $q$ and a $q$-ary linear maximum distance separable code $C$ with
parameters $[n,k,n-k+1]_q$, $W_{q,n,k}(x)$ is the dehomogenised weight
enumerator ...". There are many such codes for one $(q,n,k)$, and the table
holds one polynomial. What makes that legitimate is a theorem -- the weight
distribution of an MDS code is determined by $q$, $n$ and $k$ -- and the
theorem is stated nowhere on the page. It can be *inferred*, because the
closed form in `Formulas` has no $C$ in it, but that asks a reader to deduce a
uniqueness statement from the absence of a symbol, below the fold of a 905-row
table.

This is not a slip of wording. It is the failure the parameterisation is most
exposed to, and it lands on exactly the reader the database exists for: they
arrive holding the enumerator of *their* MDS code and need to know that the
row for their parameters is the same polynomial, rather than one particular
code's. The same shape recurs whenever the index names a class: the
discriminant of a number field, the characteristic polynomial of a graph
given by its parameters, the volume of a manifold given by a signature. Where
the value is not in fact constant on the class, the table is broken; where it
is, saying so is one clause and is the difference between a definition and a
description.

What the skill says now: section 2 asks for "which quantity, exactly" and
gives normalisation, branch and indexing as the things that go wrong, and
section 4 says the definition holds "one or two sentences saying what the
object *is*". Neither asks whether the parameters determine the value.

What it should say: a sentence in section 2, beside "Which normalisation,
branch, and indexing". Something of the shape: **If the parameters name a
class of objects rather than one object, say in the definition why every
member gives the same value, and cite it.** "The weight distribution of an
MDS code is determined by $q$, $n$ and $k$ CITE{MacWilliamsSloane}" is the
whole fix. If no such theorem exists, the parameters are not an index and the
table needs a different one.

Evidence: 2026-09-21, T389 *Weight enumerators of the maximum distance
separable codes*, 905 entries, published mid-run. `GET /api/table?id=T389`;
the rendered page at `https://numberdb.org/T389`;
`GET /api/table/T389/audit` is clean, and no check looks for this.
Written up as finding 1 of `/home/ubuntu/numberdb-critiques/T389.md`.

## A comment may not speak for a set of tables the reader cannot enumerate

What happened: the first comment of T389 begins "Every table in this
coding-theory batch stores the dehomogenised weight enumerator ...". A reader
has no batch. They cannot see which tables are in it, cannot check the claim,
and are not told the name of the one table it is really about -- T388, the
sibling published beside it, which this table links nowhere and which shares
six of its rows. T388's own copy of the same comment is right: "This table
stores the dehomogenised enumerator ...".

A contributor uploading three related tables in an afternoon will write this
sentence, because while they are writing it the set is obvious to them. It
stops being obvious the moment the page is published, and it is a claim about
the author's work rather than about the mathematics.

What the skill says now: "A comment states a fact about the mathematics", with
examples that are all about how good a search hit would be. Nothing says a
comment may not refer to a group of tables.

What it should say: extend that rule with the case. **Speak for this table, or
name and link the others: "every table in this batch", "my other tables" and
"the series this belongs to" are sets a reader cannot enumerate.** Where the
other tables matter, `Similar tables` is the field that holds them, one line
each with the relation named.

Evidence: 2026-09-21, T389 comment `comment-dehomogenised` against T388's
comment of the same key; `GET /api/table/T389/audit` is clean, and the
audit's narration pattern catches "checked on every entry" but not "this
batch". Finding 3 of `/home/ubuntu/numberdb-critiques/T389.md`.

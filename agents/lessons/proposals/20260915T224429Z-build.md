## Polynomial variables are single letters with optional digits
What happened: the Zernike generator first returned radial polynomials in the
variable `rho`, for example `2*rho^2 - 1`. The dry run passed, but the API
refused the first fill of draft T251 with
`A value in these entries cannot be read as a number. trailing input at 'h'`.
The polynomial parser tokenises a variable as one letter with optional digits,
so it read `rho` as the variable `r` followed by unexpected text.

What the skill says now: polynomials over `Z` or `Q` are allowed, and
polynomial matching supports at most six variables. It does not say what names
the parser accepts.

What it should say: stored polynomial variables must be a single letter with
optional digits, such as `x`, `y`, `r`, `x0` or `x1`. A table may still use
`\rho` in its prose, display labels and formulas, but the value string itself
has to use a parser-friendly variable name.

Evidence: the first `NUMBERDB_PUBLISH=1 agents/sage.sh
generators/zernike-polynomials/generate.py` for T251 failed with the message
above; `clients/python/numberdb/_polynomial.py` documents the token rule.

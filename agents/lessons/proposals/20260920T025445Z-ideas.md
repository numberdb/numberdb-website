## A search by *value* returns the results themselves, and its `.tables` is empty

What happened: the batch was screened by value as well as by name, following
the lesson of 2026-09-18. Nine numbers and ten polynomials were looked up with
`search_real_ball`, `search_rational` and `search_polynomial`, and the results
were read the way the skill says to read a search — through
`.tables`. Every one of the nineteen came back empty, including
$\sqrt3/6$, which T252 and T253 both hold, and including a control:

    numberdb.search_real_ball(3.14159265358979, 1e-12).tables  ->  []

Pi is in the corpus three times over, so the empty list was not an answer, it
was a misread. `SearchResults` is a `list` subclass. For a *text* search the
matches are in `.tables` and the list itself is empty; for a *value* search it
is the other way round — the list holds one `Result` per matching entry, each
with `.table` and the matched value, and `.tables` is empty. Reading it
correctly turns the same call into seven hits, naming T7, T20, T27, T29, T59
and T92.

What the skill says now: "`search_text` returns an object with a `.tables`
list, not a list — iterating it directly yields nothing and raises nothing,
which reads exactly like an empty corpus." That sentence is true, and it
teaches the wrong habit for every other search function, because the two
behave in opposite ways.

What it should say: the same warning in both directions, once, beside the list
of search functions. A text search puts its answer in `.tables`; a search by
value puts its answer in the object itself, one `Result` per entry, and leaves
`.tables` empty. Whichever you use, run a control whose answer you know — pi,
or $x^2-x-1$ — before believing a negative. Twelve of this run's nineteen
searches by value were genuine negatives and are quoted as such in the batch;
they were only worth quoting because the control failed first and the misread
was caught.

Evidence: 2026-09-20, screening the spherical-harmonic batch.
`numberdb.search_real_ball(3.14159265358979, 1e-12)` gives
`len 7, total 7, tables []`, the first `Result('3.14159...', table='Pi')`;
`numberdb.search_text('Legendre')` gives `len 0, tables 15, total 15`.
Client `clients/python/numberdb`, `SearchResults` in `__init__.py`.

## Sage's `wigner_9j` refuses symbols that exist, and sympy's does not

What happened: sizing a table of Wigner $9j$ symbols meant evaluating every
symmetry class of arrays whose six triads are all admissible. Sage's
`wigner_9j` raised

    ValueError: j values must be integer or half integer and fulfill the
    triangle relation

on **30 of the 61** classes with every $j_i\le3/2$, and on **104 of the 251**
classes with every $j_i\le2$. The arrays are fine: `sympy.physics.wigner`'s
`wigner_9j` returns a value for every one of them, and agrees with Sage on
every class where Sage answers — 0 disagreements at $j\le1$, $j\le3/2$ and
$j\le2$. The cause is visible in the traceback: `wigner_9j` sums
`racah(j_1, j_2, j_9, j_6, j_3, kk, prec)` over an intermediate $kk$ and does
not check that $kk$ makes the intermediate triads admissible, so `racah`'s own
guard fires and the exception escapes the sum instead of contributing a zero
term.

Before that, the same function died with `NameError: name 'RR_1_10' is not
defined` from inside `sage/rings/qqbar.py`, because it compares a symbolic
prefactor to zero and that comparison goes through `QQbar`.
`sage.rings.qqbar._init_qqbar()` fixes it. `wigner_6j` and `gaunt` in the same
module are unaffected.

What the skill says now: "check new values against something independent", and
the worked examples all use one library.

What it should say: two things a table of this kind depends on. First, when a
library refuses an input you believe in, check the input against a second
implementation before changing it — a library's exception is evidence about
the library, and `wigner_9j` refuses two in five of the symbols a $9j$ table
would hold. Second, the 2026-09-18 note that `import numberdb.sage` leaves
`sage.rings.qqbar` half built is not only about `AA`: it reaches any function
that tests a symbolic expression for zero, whose signature mentions no
algebraic number at all. Call `_init_qqbar()` once at the top, next to the
ring imports.

Evidence: 2026-09-20, `/tmp/sh_probe{3,4,5}.py` under `agents/sage.sh`.
Sage 10.x in the deployed image, `sage/functions/wigner.py` lines 553 and 282.
Counts: `J=3/2 classes 61, sage raised 30`; `J=2 classes 251, nonzero 231,
sage raised 104, sage/sympy disagreed 0`.

## A named Sage import the skill recommends can fail on a circular import

What happened: the plan was to check associated Legendre polynomials against
Sage's `gen_legendre_P`, as an earlier batch had. Following the skill's rule
to name the module rather than import `sage.all`,

    import numberdb.sage as numberdb
    from sage.functions.orthogonal_polys import gen_legendre_P

raised

    AttributeError: cannot access submodule 'function' of module
    'sage.symbolic' (most likely due to a circular import)

`sage.functions.wigner` imported the same way in the same script works, and so
does every ring import. mpmath's `legenp` was the way round: it is
hypergeometric rather than symbolic, it carries the Condon-Shortley phase
(`legenp(1,1,0.5) = -0.86602540378443864676`), and it needs nothing from Sage.

What the skill says now: "Name the rings you use, rather than importing
`sage.all`. ... Importing `numberdb.sage` first is what makes the direct
imports work." It then lists three things the named imports do not bring: root
finding, `RealBall.str`, and `QQ('1.25')`.

What it should say: add the symbolic-function modules to that list, or at
least say that a named import can still fail, and that the fallback is a
library outside Sage rather than `sage.all`. A contributor who has been told
that naming the module is the safe way reads an `AttributeError` about a
circular import as their own mistake.

Evidence: 2026-09-20, `/tmp/sh_probe2.py` under `agents/sage.sh`; the same
script's `from sage.functions.wigner import gaunt, wigner_3j, wigner_6j`
succeeded, and `RealBall.str` was absent as the skill already says.

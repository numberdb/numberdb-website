# Lessons proposed by the T4 critique, 2026-09-22

## `HREF{#key}` and `CITE{key}` are not interchangeable, and getting it wrong is invisible until somebody reads the page

What happened: T4's parameter list declares $n$ as
`HREF{#CL}[Conrey index] of $\chi$`, meaning "the Conrey label knowl I declared
in `Links` under the key `CL`". `CL` *is* a key in `Links` -- it renders in the
page's Links block as "[4] LMFDB knowl: Conrey label" -- but `HREF{#...}` does
not address a `Links` key. It addresses an **entry of this table**, by its
parameter values: `HREF{#delta}` is a row, and `HREF{slug#Z,1,density}` is a
row of another table. So the one hyperlink T4 offers a reader, on the one piece
of notation the whole table depends on, renders as `<a href="?entry=CL">` and
answers with this same page plus a warning: "This table has no entry CL. It may
have been renumbered or removed; the table itself is shown below." The knowl
that would have explained the notation sits in `Links`, unreferenced, on the
same page.

Nothing catches it. A `Links` key with no `CITE` pointing at it is not a fault
(the skill only says a *reference* is for citing), and the audit's HREF check
resolves the part of the target before the `#` and skips a target that is empty,
so a same-table fragment is accepted whatever it names. The document validates,
the write succeeds, the audit reports `clean: true`, and the only symptom is a
yellow banner on a page nobody rereads. T4 has been public since it was among
the first tables here.

What the skill says now: the two forms are each described correctly and
separately, several hundred words apart -- "`CITE{key}` for a reference or
link" under §4, and "A link may name an entry: `HREF{Feigenbaum_constants#delta}`
... the address after the `#` is the entry's identity -- its parameter values,
comma separated" under the linking rules. It never says they are confusable,
and it never says which one a `Links` key takes. The nearest warning, "Never
guess a name the database resolves", is about slugs and tags.

What it should say: beside the entry-address rule, that the `#` in an `HREF`
always means a *row*, never a label the table declares. A `Links` or
`References` key is `CITE{key}`; a formula or comment label on the same page is
also `CITE{label}`; only parameter values go after a `#`. And that this
particular mistake is not caught by anything: `HREF{#label}` is stored,
published and audited clean, and shows itself only as "This table has no entry
label" to a reader who clicks. Check a same-table link by fetching
`/<tid>?entry=<label>` and looking for that banner, because the fragment alone
is never sent to a server and a browser simply fails to scroll.

Evidence: 2026-09-22, T4 critique.
`GET /api/table?id=T4` gives
`"n": {"title": "HREF{#CL}[Conrey index] of $\\chi$", ...}` with `CL` also in
`Links`; the rendered `/T4` contains
`<a class="HREF" href="?entry=CL">Conrey index</a>`;
`curl 'https://numberdb.org/T4?entry=CL'` -> 200 with
`<li class="alert-warning"> This table has no entry CL. It may have been
renumbered or removed; the table itself is shown below. </li>`;
`GET /api/table/T4/audit` -> `{"findings": [], "clean": true}`.

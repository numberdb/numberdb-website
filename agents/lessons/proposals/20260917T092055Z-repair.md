## Write formulas in the convention of the NumberDB table they link
What happened: T295 linked to the table of the complete elliptic integral
$K(m)$, but its formula used DLMF's modulus notation
$K'(k_r)/K(k_r)=\sqrt r$. A reader following the link to T25 and evaluating
$K(k_r)$ in that table's parameter convention gets the wrong quotient. The
repair rewrote the formula as $K(1-m_r)/K(m_r)=\sqrt r$ and made the similar
table relation use the same convention.

What the skill says now: it warns that `elliptic_k` takes the parameter $m$,
not the modulus $k$, and it says to link the first mention of a thing to the
table that explains it. It does not say that a linked formula should be
written in the linked table's argument convention when sources use another
one.

What it should say: when a formula names a function or object held in another
NumberDB table, write the formula in that table's convention, or put the
translation beside it. A source's notation is not enough if the table link
teaches a different argument, normalisation or branch.

Evidence: `GET /api/table?id=T295`, 2026-09-17, had
`$q=\exp(-\pi K'(k_r)/K(k_r))$, so $K'(k_r)/K(k_r)=\sqrt r$` while its
similar-table link was `Complete elliptic integral of the first kind $K(m)$`.
`agents/sage.sh /tmp/t295_checks.py /tmp/t295_live.json` checked all 100 rows
after the repair and reported `K(1-m)/K(m)=sqrt(r) failures: 0`.

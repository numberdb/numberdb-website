## Search folds the dash but the title's unique constraint does not, so the duplicate check and the backstop disagree

What happened: triaging a build, I found that the table it had been told to
make already existed -- `T441`, "Values of the Tracy-Widom distribution
functions $F_\beta(s)$", 903 entries, audit clean. It is a draft. Searching
the corpus for it finds nothing of the sort:

    GET /api/lookup?text=Tracy-Widom     -> T444, T198
    GET /api/lookup?text=Tracy–Widom     -> T444, T198
    GET /api/lookup?text=Tracy+Widom     -> T444, T198
    GET /api/lookup?text=Widom           -> T444, T198

Two useful facts in one picture. The index **folds the dash**: U+002D, U+2013
and a plain space all tokenise the same, so a name spelled either way is found
either way, and that is better than the accent case the skill already warns
about. And every one of those searches misses `T441`, because it is a draft
and search reaches published tables only.

So the search says "nobody has made this". The thing that is supposed to catch
you when search is wrong is the title: `Table.title` is `unique=True`, and it
is a plain `CharField` compared byte for byte. The corpus already holds the
proof that this is not the same folding search does -- `T441` writes the name
`Tracy-Widom` with U+002D and `T444` writes it `Tracy–Widom` with U+2013, and
both were accepted. A contributor who types the en-dash for a subject someone
else typed with a hyphen gets a second table, not a refusal.

The order matters: search folds and misses drafts; the constraint sees drafts
and does not fold. Neither of them alone is a duplicate check, and they fail on
opposite inputs.

What the skill says now: it says `/drafts` "lists what is being made right now
and is invisible from outside, so a table can be half-built and unfindable
while you start it again", and it says to search titles, tags and definitions
before reaching for an external link. It also says the index has no `unaccent`,
so "Lévy's constant" needs "Levy constant" in `Keywords`. It says nothing about
the dash -- which reads as though it were the accent case, and it is not -- and
nothing about what happens if you create a title that already exists.

What it should say: two sentences beside the accent one.

- The text index tokenises `-` and `–` alike, so a hyphen and an en-dash in a
  name are one search term and do not need a `Keywords` line each. The accent
  rule is narrower than it looks.
- Creating a table whose title already exists is refused by a unique
  constraint, but it is an exact-string one: it does not fold the dash, the
  spacing or the `$...$` the way search does. It will not save you from a
  near-duplicate, and it cannot warn you at all about a draft you could not
  see. When a search comes back empty for a subject that sounds well-studied,
  the answer may be that somebody's draft holds it; check `/drafts` while
  signed in before writing the generator, not after.

Evidence: 2026-09-23, triage of build run `20260923T090338Z`, against the live
site. The four `GET /api/lookup?text=...` above, anonymous, each returning
exactly `T444` ("Cumulants $\kappa_n$ of the Tracy–Widom distributions",
published) and `T198`; `GET /api/table?id=T441` returns the full document to
its owner's key and `{"error": "Table with id 'T441' does not exist."}`, at
status 200, to nobody's -- and `T441` appears in none of the four searches.
The constraint is `numberdb_app/models.py:322-326`,
`title = models.CharField(max_length=256, unique=True, db_index=True)`;
`title_lowercase` beside it is built at `editing.py:488` as
`title.lower().replace('$', '')` and is used for ordering, not for uniqueness.

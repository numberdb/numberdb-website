## A draft filled through the API has a third way to be offered, and it is the only one that works

What happened: build run `20260923T055938Z` created draft T441, filled it with
903 entries, audited it clean and attached its generator -- and then stopped
without offering it. The table is finished and invisible, in no listing and no
review queue, and from outside it is indistinguishable from an abandoned one.
The run had no browser session and could not have offered it the way the skill
describes.

Section 9 gives the workflow as four separate acts, and the first three are
exactly what a program does:

1. propose it as a draft -- `POST /api/tables` with `X-Draft: yes`; "a draft
   [...] may have no numbers in it yet, because the prose is written first"
2. fill it with a generator pointed at that T-number
3. offer it for review when it is finished -- "the button on `/drafts`, or
   `X-Draft: ready` at creation for a run that proposes and fills in one go"

Follow that literally and step 3 has no answer. The button needs a logged-in
browser session, which somebody driving the API from a script does not have --
an API key is not a session, and `/drafts` redirects to the login page. And
`X-Draft: ready` is read once, in `create_table`, at the moment of creation:

    if offer_now and not table.published:
        table.ready_for_review = True

By step 1's own instruction the table has no numbers yet at that moment, so
`ready` at creation is either a lie about an empty draft or unavailable to
anybody who wrote the prose first. The two routes the skill names cover the
browser worker and the one-shot creator, and between them is the workflow the
skill actually recommends.

There is a third route, and the site has it for precisely this reason.
`POST /api/table/<tid>/offer`, key required, no body:

    curl -sS -X POST -H "Authorization: Bearer $NUMBERDB_KEY" \
         https://numberdb.org/api/table/T441/offer
    {"tid": "T441", "published": false, "ready_for_review": true}

Its docstring in `numberdb_app/api.py` says why it exists, and describes the
gap above better than I can:

    This exists because the workflow it serves has three steps and the API had
    routes for two. [...] A run that creates a draft, fills it, and then wants
    a person to look had nowhere to say so.

It is worth knowing four things about it, none of which are in the skill:

* **Offering is not publishing.** It moves the draft into the queue and leaves
  it invisible and unpublished. It is inside what an ordinary contributor's key
  may do; publishing is not.
* **It is idempotent**, so it is safe in a script and safe to repeat after a
  crash. It can be sent without first working out whether an earlier attempt
  got through.
* **It refuses an empty table**, and that is the right answer -- an empty draft
  is what the review queue should not be shown. So it cannot be sent
  speculatively at the start of a build as insurance; it has to come after the
  entries.
* **It can be withdrawn**, so offering too early is recoverable.

What the skill says now: section 9, step 3 -- "the button on `/drafts`, or
`X-Draft: ready` at creation for a run that proposes and fills in one go". The
endpoint is not mentioned anywhere in `SKILL.md`; grepping the file for
`offer` returns only those two lines.

What it should say: name the endpoint in step 3 as the route for the ordinary
case -- a draft created empty, filled by a generator, and then offered -- and
say plainly that until it is sent, a finished table is in no queue and nobody
will ever be asked to look at it. Something like:

> **Offer it for review** when it is finished. From a script that is
> `POST /api/table/<tid>/offer` with your key and no body; on the site it is
> the button on `/drafts`; `X-Draft: ready` at creation does it for a run that
> proposes and fills in one go, which is not the usual shape, since the prose
> is written before there are any numbers. Offering is not publishing -- the
> draft stays invisible and unpublished, and it can be withdrawn -- and it is
> idempotent, so send it again if you are not sure it arrived. It is refused
> for a table with no entries. **A filled draft that was never offered is in no
> queue and no listing: from outside it cannot be told from one somebody
> abandoned, and nobody will ever be asked to look at it.** It is the last
> thing you do, so it is the thing an interrupted run leaves undone -- if a
> build of yours died near the end, check this before anything else.

Why it belongs in the skill rather than in the environment notes: none of it is
about this deployment. A contributor with a laptop, an API key and a Python
script hits it the first time they build a table without opening a browser --
which is the whole workflow section 9 lays out. The failure is silent in the
worst way: every request returned 200, the table is correct, the audit is
clean, and the work is simply never seen. The site keeps the draft forever, so
nothing ever surfaces it.

Evidence: 2026-09-23, triage of `agents/runs/20260923T055938Z-build.log` --
309 transcript items, no request to `/offer` anywhere in it. T441 holds 903
entries and `GET /api/table/T441/audit` returns `{"findings": [], "clean":
true}`. `numberdb_app/api.py`, `offer_table` at line 786 and the `offer_now`
branch of `create_table` at 1035; `numberdb_app/views.py`, `drafts`, which
redirects an unauthenticated request to the login page.

## A duplicate title is refused with advice, and the advice distinguishes three cases

What happened: working out what a re-run of this proposal would meet, I read
the refusal `create_table` gives when a table of that title exists. It is not
the bare "already exists" the name suggests -- it names the table, its state,
and which of three things to do:

* an unpublished draft with **no entries**: "an earlier run created it and
  stopped before filling it. Continue *that* table rather than making another:
  write its document and send its entries to T<n>."
* an unpublished draft **with entries**: "Check whether it is the table you
  were about to build; if it is, it is built, and what it needs is review
  rather than a second copy."
* **published**: "this proposal is answered. Record it against the proposal
  rather than building it twice."

The comment above it records what the bare version cost: a draft "sat empty
for twenty hours while the proposal it blocked could never be built by
anybody", because every later attempt was told only that it existed, and
stopped.

What the skill says now: nothing about what a refused title means or what to do
about it. A contributor whose build died between creating a draft and filling
it -- exactly the failure the first lesson above is about -- retries, is
refused, and has no reason to expect the error body contains their next step.

What it should say: in section 9 under step 1, that a title is unique across
the corpus, that the refusal is HTTP 400 with a `detail` naming the existing
table and what state it is in, and that the three states mean three different
things: continue the empty draft rather than making a second one, ask for
review rather than rebuilding a filled one, and record the proposal as answered
against a published one. **Read the body of a 400 before deciding the proposal
is taken** -- it usually says which of the three you are in.

Lower confidence than the first lesson, and narrower: this is good behaviour by
the site rather than a trap, and the cost of not knowing it is a few wasted
turns rather than a lost table. It is here because the sentence "if the title
is refused because it exists, that proposal is taken -- say so and stop" is
what our own build prompt tells a run, and that is right only in the third
case. In the first two the right move is to carry on with the table that is
already there.

Evidence: 2026-09-23, `numberdb_app/editing.py`, `create_table`, the
`existing is not None` branch. Not triggered in this run -- read while working
out what a `restart` verdict would have met, given that T441 already holds the
title.

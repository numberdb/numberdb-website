## PARI's `polclass(D, inv)` is not the textbook class polynomial for the same invariant

What happened: the Weber class polynomial for $D=-23$ is $x^3-x-1$, the
minimal polynomial of $\mathfrak f(\sqrt{-23})/\sqrt2=1.3247\ldots$ (the
plastic number). PARI's `polclass(-23, 1)` returns $x^3-x^2+1$. Over every
$D=-m$ with $m\equiv7\pmod 8$, $3\nmid m$, $m<1200$ (100 discriminants),
PARI's polynomial is $\pm x^hW_D(\mp1/x)$. Its root is $-\sqrt2/\mathfrak f$
in 76 cases and $+\sqrt2/\mathfrak f$ in 24. The sign is always $-$ when
$h(D)$ is odd, and is not predicted by $D$ modulo 16, 32 or 48 when $h(D)$
is even. So no fixed transform turns one into the other, and a comparison
"up to $x\mapsto -1/x$" passes on some rows and fails on others.

What the skill says now: "Check new values against something independent";
nothing about software returning a different normalisation of the same
object.

What it should say: a library's name for an object is not a definition of
it. Before using a library as the independent check, find out which root its
polynomial is the minimal polynomial *of*, by evaluating it at the value the
table defines. PARI's class invariants, in particular, are normalised for
size, not to match the literature. Compare row by row allowing the transform
you actually measured, and never generate the table by transforming the
library's output.

Evidence: `polclass(D,1)` evaluated at $\pm\sqrt2/$`weber(I*sqrt(m))` at 300
digits, 2026-09-17, `/tmp/pari4.py` and `/tmp/pari6.py`.

## $\mathfrak f(\sqrt{-m})$ is a CM value of discriminant $-4m$, though everybody indexes it by $-m$

What happened: to check the Weber class polynomial $W_{-23}$ against the
Hilbert class polynomials (T129), I took the resultant of $W_{-23}$ against
$j=(\mathfrak f^{24}-16)^3/\mathfrak f^{24}$ and compared it with $H_{-23}$.
It failed on all 33 discriminants tried. The point $i\sqrt{23}$ generates
$\mathbb Z[\sqrt{-23}]$, of discriminant $-92$, and the resultant is
$c\cdot H_{-92}$ every time. For $m\equiv7\pmod8$ the two orders have the
same class number, which is why the label $-23$ is harmless in the literature
and a trap in a check.

What the skill says now: "Which normalisation, branch, and indexing".

What it should say: when a family is labelled by a discriminant, write down
the discriminant of the order the CM point actually generates, and check
against *that* entry of $H_\Delta$. If they differ, the table's parameter is
not T129's $\Delta$ and must not share its key.

Evidence: `/tmp/pari10.py`, 33 of 33 fail against $H_D$ and 33 of 33 pass
against $H_{4D}$, 2026-09-17.

## `ellmodulareqn` is two families, chosen per level

What happened: PARI's `ellmodulareqn(ℓ)` returns `[P, t]` with $t=0$ for a
canonical (eta-quotient) modular equation and $t=1$ for an Atkin one. Below
100, `seadata` gives the canonical type only for
$\ell=2,3,5,7,13,37,73,97$, and Atkin's for every other prime. A table of
"the modular equations from `ellmodulareqn`" would silently mix two
definitions. For those seven levels up to 73, the canonical equation computed
from its definition ($q$-expansions of $\ell^s(\eta(\ell\tau)/\eta(\tau))^{2s}$
and $j$, rational kernel) is identical to `seadata`'s. So `seadata` is a good
check for either family and a source for neither.

What the skill says now: nothing.

What it should say: read the type flag of a library function that returns
"a" modular equation, and never build a table from a lookup whose choice of
object varies with the index.

Evidence: `/tmp/pari3.py` (types for $\ell<200$), `/tmp/pari8.py` (seven
exact matches), 2026-09-17.

## A one-dimensional kernel from $q$-expansions is not an identity until the precision is argued

What happened: finding a modular polynomial by linear algebra on truncated
$q$-series gave a two-dimensional kernel at $\ell=43$, because the
truncation (355 coefficients) was shorter than the number of unknowns (360).
That failure was loud. The quiet one is the same computation with more rows
than unknowns but fewer than the pole order that forces a modular function
to vanish. The kernel is then one-dimensional and can still be wrong.

What the skill says now: "Decide exactness from the definition, never from
the digits."

What it should say: for a relation found from $q$-expansions, state the
Sturm-type bound (the total pole order of the relation on the modular curve)
and truncate past it. A kernel of the right dimension is evidence, not proof.

Evidence: `/tmp/pari5.py`, `error("kernel dimension ", 2)` at $\ell=43$
before the row count was raised, 2026-09-17.

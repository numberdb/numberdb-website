# Lessons proposed by the T5 critique, 2026-09-22

## A value known only between bounds is stored, shown, and deliberately not searchable

What happened: T5 holds one entry, `[2, 2.371177]`, the interval between the
two best theorems about the exponent of matrix multiplication. The page renders
it with a dagger linking to `/help#search-precision`, and searching the site for
`2.371177` -- the exact upper endpoint, the number a reader carries away from
the paper -- answers "No match in database". So does `2.3`. That is deliberate
and right: the help page explains that matching a wide interval "would not tell
you that your number *is* that exponent, only that a wide range happens to
contain your number, which is equally true of every value in it". The cutoff is
stated there: **a relative precision of 1e-05**, about five significant digits,
relative rather than absolute, measured on what is known about the number
rather than on how it is displayed.

The consequence for a contributor is not obvious from either end. A table whose
entries are all wide intervals answers *no* search by number, so every reader
who ever reaches it reaches it by typing a word. Title, `Keywords`, `Tags` and
the prose are not one route in among several there; they are the only one. On
T5 that turns an ordinary omission into a real cost: nothing on the page says
"Coppersmith-Winograd", and `search_text('Coppersmith')` returns nothing in the
whole corpus, so the name most readers of this subject would type reaches the
one table about it not at all.

The corpus has exactly two tables of this shape -- T5 and T6, the diagonal
Ramsey numbers, whose entries run `[43, 46]`, `[102, 160]`, `[205, 492]` -- and
both are worth having. This is not an argument against storing an interval of
ignorance. It is a fact about what such a table has to do to be found.

What the skill says now: nothing about the searchability of wide values. §5
says a real is stored as an interval containing it and gives the four forms,
including `[2, 2.3728596]` as an explicit-endpoint example -- which is this very
value -- without saying that an interval that wide is excluded from search by
number. §1 says a value is worth storing if a reader might arrive holding it,
and §3 says the title is what a search reaches, but neither connects to the
case where search by number cannot answer at all. The only other mention of
"shown and cited rather than found" is about exotic `type`s.

What it should say, in §5 beside the four forms and the "a hundred digits means
something" sentence: an entry is searchable by number only if it is known to a
relative precision of about 1e-05; a wider interval is stored, displayed and
citable, and is marked on the page with a dagger explaining why search skips
it. A quantity nobody knows precisely -- $\omega$, $R(5,5)$ -- is a legitimate
table and stores the interval between the best proved bounds, at `rigour:
proven`, with `rigour details` saying the width is ignorance rather than error.
But such a table is reachable by name alone, so spend the effort there: name
every algorithm, author and alternative name a reader might be holding, in the
title, in `Keywords`, or in a comment, and check with `search_text` that each
one now returns it.

Evidence:

    $ curl --get --data-urlencode 'q=2.371177' https://numberdb.org/
    ... No match in database ...
    $ curl --get --data-urlencode 'q=2.3' https://numberdb.org/
    ... No match in database ...

    >>> numberdb.table('T5')['Numbers']
    ['[2, 2.371177]']
    >>> [t.tid for t in numberdb.search_text('Coppersmith').tables]
    []
    >>> [t.tid for t in numberdb.search_text('fast matrix multiplication').tables][:2]
    ['T5', 'T274']

and `/help#search-precision`, which states the 1e-05 cutoff and uses T5 and T6
as its two examples.

## `Numbers` is a list for a table with no parameters and a dict for every other one

What happened: reading five tables in one loop to compare them, the line
`print(numbers[0])` raised `KeyError: 0` on T6 after working on T5. `Numbers`
is not one shape. For a table with no parameters it is a **list** of values; for
a table with parameters it is a **dict** keyed by the entry's identity -- the
parameter value as a string -- and for several parameters it is a dict of dicts,
one level per parameter, in the order the table declares them. The values are
sometimes a plain string and sometimes a dict with `number`, `comment` and
other annotations beside it.

    T5   (no parameters)   ['[2, 2.371177]']
    T6   (one parameter)   {'1': '[1, 1]', '5': '[43, 46]', ...}
    T272 (one parameter)   {'3': {'number': '0.9179...', 'comment': '...'}, ...}
    T274 (two parameters)  {'2': {'1': {'number': '1/2', 'comment': '...'}, ...}, ...}

So `numbers[0]` is right on a table with no parameters and raises on every
other; `for key in numbers` yields values in the first case and keys in the
second, which is the one that bites quietly, because iterating a list of value
strings and iterating a dict of identity strings both produce strings and
neither raises.

What the skill says now: "`numberdb.table(...)` answers with the whole
document, capitalised keys and all -- `Title`, `Definition`, `Numbers` -- and
`Numbers` is every entry the table holds. Printing it is megabytes. Take the
keys you want." Nothing about its shape, and the surrounding advice ("iterating
[a search result] directly yields nothing and raises nothing, which reads
exactly like an empty corpus") is about the *other* call.

What it should say, in the same paragraph: `Numbers` is a list when the table
has no parameters and a dict keyed by the entry identity when it has, nested
one level per parameter; an entry is a value string or a dict carrying
`number` alongside its annotations. Read it with
`numbers.values() if hasattr(numbers, 'values') else numbers`, or branch on the
table's own `Parameters`, rather than indexing by position.

Evidence: the four documents above, read today with
`numberdb.table(tid)['Numbers']` against the live site.

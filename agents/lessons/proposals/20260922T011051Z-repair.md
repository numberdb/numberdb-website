## An API key can read a draft table where the HTML route still returns 404
What happened: public `GET /api/table?id=T395` and `GET /T395` both made T395 look absent, but the same table was visible to zeta3 through authenticated `GET /api/table?id=T395` and `GET /api/table/T395/audit`. Adding the same bearer token to `GET /T395` still returned the site's "Not found" HTML page, so an API key is enough for API reads and audits of the draft but not for rendering the browser page.

What the skill says now: drafts are invisible from outside, and a draft `verify()` needs the key. It does not say that API-key authentication and HTML page authentication differ.

What it should say: when checking an unpublished draft without a browser session, use the API endpoints, not the table URL. A bearer token can make `/api/table?id=T...` and `/api/table/T.../audit` see the draft while `/T...` still answers 404.

Evidence: `cat "$NUMBERDB_KEY_FILE" | NUMBERDB_KEY_FROM_STDIN=1 agents/sage.sh /tmp/t395_probe.py`, 2026-09-22, returned status 200 for `/api/table?id=T395`, status 200 with `{"findings": [], "clean": true}` for `/api/table/T395/audit`, and status 404 for `/T395`.

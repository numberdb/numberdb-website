## Search the corpus for your own *digits*, not only for the family, before you publish: that is the only way to find out whether you must declare `repeats`

What happened: T351 holds $\Gamma(a,x)$ at seven half-integer $a$ and a
hundred rational $x$. Its $a=0$ row is $\Gamma(0,x)=E_1(x)$, which the table
knows and says: `Similar tables` reads "the row $a=0$ is the exponential
integral $E_1(x)$", and `rigour details` records that the row was checked
against that table. Both sentences are correct and neither is the declaration
the corpus needs. T188 holds $E_1(x)$ at every $x$ of two decimal places with
$0<x\leq5$; T351's row runs over $x=k/10$, $1\leq k\leq100$; the fifty shared
arguments carry **fifty identical hundred-digit strings**, not a character
different. So once T351 is public, somebody typing those digits gets two
tables saying the same thing in no stated order, which is exactly what
`Data properties: repeats` exists to prevent.

The fault is easy to reach by following the skill. Section 1 sends a builder
to search for the *family*, and says in as many words that the question "is
about the family, never about the values" and that a number appearing in
several tables is the point of the database rather than a fault in it. Both
true. But the `repeats` rule later on — "If the table repeats another's
values, say so" — is a statement about values, and nothing tells the builder
how to find out. A family search cannot: "upper incomplete gamma" and
"exponential integral" are different families with different literatures, and
that is why both tables should exist. Only the digits collide.

The check is one call per row of the table, before publishing, and it works on
any laptop:

    >>> found = numberdb.search_text('1.8229239584193906660809136582918')
    >>> [(row.table.tid, row.table.title) for row in found]
    [('T188', 'Values of the exponential integral')]

One value from each value of the leading parameter is enough, because a row
that repeats another table repeats it all the way along. What comes back is
not a verdict: a value shared with twenty tables is a small integer or a
famous constant and means nothing, and two tables agreeing because of a
theorem — Hermite's constant in dimension 8 and the Hermite number of $E_8$ —
must *not* be declared. What to look for is one other table holding the
identical string for the same quantity of the same object, which is the case
`repeats` is for.

Two facts about the declaration that make it cheaper than it looks, and which
the skill does not say:

* **It folds per value, not per table.** Search compares the stored text of
  each number, so declaring `repeats` on a table that overlaps another in only
  part of its range leaves the rest untouched: T351 would fold fifty rows into
  T188 and answer for the other 650 exactly as it does now. A partial overlap
  is still a reason to declare it. (`fold_repeats`, `numberdb_app/search.py`:
  "Only equal values fold … the stored text is compared, which never merges
  two numbers that differ.")
* **The repeating table is not hidden.** The folded row keeps the other table
  beside it as `also_in`, so the page can still say where else the number is
  written down. Declaring `repeats` gives up nothing except leading on fifty
  values that somebody else published first.

And one thing the digit search tells you that is worth a sentence on the page
even when you decide against `repeats`: which *part* of the row is new. Half of
T351's $a=0$ row lies beyond T188's range, so half is a copy and half extends
a published table past where it stops — a fact a reader of either page would
want and neither page states.

What the skill says now: "**If the table repeats another's values, say so.**
`repeats: HREF{Other_table}` … Only where this table repeats that one's
computation — the same quantity of the same object, transcribed." It says what
the declaration means and when it applies, and nothing about how a builder
discovers that it applies. Section 1's search advice points the other way:
search titles, tags and definitions for the family, and do not judge a
proposal by whose numbers it shares.

What it should say: two sentences beside the `repeats` rule. Before publishing,
search the corpus for the digits of one value from each row — `search_text`
takes the digits as text, and an identical hundred-digit string in another
table is the fact `repeats` is about; a family search cannot find it, because
two tables that repeat each other's values are usually two different families,
which is why both exist. And note there that the relation folds per value, so a
table whose overlap is one row of many should still declare it.

Evidence: 2026-09-20, T351 critique. `GET /api/table?id=T351` and
`?id=T188`; all 50 of the 50 shared arguments compared equal as stored text.
`GET /api/lookup?text=1.822923958419390666080913` returned one result, T188's
entry `E1,1/10`, and no table match — T351 is an unreviewed draft and held out
of search by number, so the collision is invisible from the outside until it
is published, which is the other reason to run the check rather than wait for
it to be noticed. The audit does not report it either, by design: its
`_values_also_in_another_table` check skips a table whose prose already names
the other, and T351's `Similar tables` names T188.

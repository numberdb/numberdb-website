# Proposed lessons from the T19 growth review, 2026-09-21

Two, both of which a contributor with Python and Sage on their own laptop
would hit. The deployment-only findings from the same reading -- `/files/T19`
answering 500, and the anonymous rate limit as this runner met it -- are in
`docs/agent-environment.md` instead.

---

## A rate-limit refusal has no `results` key, so a client reads it as "no match"

What happened: a growth review surveyed the corpus by fetching
`/api/table?id=T<n>` once for each of the 374 published tables, then started
measuring what `/api/lookup` answers for a set of candidate values. Every
lookup came back with zero results, and the obvious reading -- "none of these
numbers is in the database" -- was wrong. The survey had already spent the
hour's allowance, and the lookups were 429s. A refusal body is

    {"error": "Rate limit exceeded (60 requests per 60 minutes).
               An API key raises this limit; see /help#section-api.",
     "retry_after": 1140}

with no `results` key at all, so `json.load(r)['results']` on a script that
reaches for results with a default, or `.get('results', [])`, turns a refusal
into an empty answer. Seven measurements were recorded and believed before the
eighth printed the error body.

This is the dangerous shape of the failure, not the limit itself: the database
exists to answer "has anyone seen this number before", and a silently
rate-limited client gets "no" -- the most consequential answer it can give --
with no indication that nothing was asked.

What the skill says now: nothing. It describes `/api/lookup` and
`numberdb.search_real`, and says an API key is needed for writing. It does not
say there is a read limit, what it is, or what a refused read looks like.

What it should say: reads are limited too -- 60 an hour anonymously, 1000 with
a key, per hour per caller. Anybody screening the corpus before proposing a
table will pass 60 in a few minutes, so screen with a key. And check the
status code, or check for the `error` key, before reading `results`: an empty
`results` list means "not in the database", and a missing one means "not
asked", and those must not be confused. Worth one sentence in the screening
section and one in the API description.

Evidence: 2026-09-21 T19 growth review. `curl` of
`/api/lookup?text=0.340537` -- a value that *is* in T19, at $d=3$ -- returned
the refusal above; the same request with `Authorization: Bearer <key>`
returned the T19 entry. Limits are `ANONYMOUS_LIMIT = 60`,
`IDENTIFIED_LIMIT = 1000`, `WINDOW_SECONDS = 3600` in
`numberdb_app/throttle.py`.

## Ball arithmetic throws away exponential cancellation: `exp(-x)*I0(x)` is useless on a wide ball

What happened: the T19 values are transcribed from OEIS and the table says so,
asking for help with error bounds. Recomputing them rigorously means enclosing

    u(d) = d int_0^inf g(s)^d ds,   g(s) = e^{-s} I_0(s),   p(d) = 1 - 1/u(d),

and `g^d` decays only like `s^{-d/2}`, so the integral has to be carried a long
way before an elementary tail bound is small: to $10^{18}$ for 60 digits at
$d=9$, and to $10^{62}$ at $d=4$.

Asked for

    CBF.integral(lambda x, _: ((-x).exp() * x.bessel_I(0))**9, 10^3, 10^5)

Arb returned a ball of radius **1e193465** -- not an error, a finite and
completely useless enclosure. Summing pieces like that gives `nan`, because the
total straddles zero and the final `1 - 1/(d*total)` divides by a ball
containing 0. The `nan` says nothing about which piece caused it.

I first read this as the integration contour: `acb_calc_integrate` bounds the
integrand on complex ellipses, so a long interval samples far off the real
axis. **That was wrong**, and it cost a 577-second run to find out -- splitting
into pieces with $b = 2a$, which keeps every ellipse in $\mathrm{Re}(x) > a/2$,
still gave `nan`, with each of the 51 pieces carrying a radius of 1 to 5
against true values below $10^{-14}$.

The cause is pointwise and has nothing to do with integration. Sage 10.9 offers
`ComplexBall.bessel_I(nu)` and no *scaled* variant (`RealBall` has no Bessel
functions at all), so `(-x).exp() * x.bessel_I(0)` encloses $e^{-x}$ and
$I_0(x)$ as two separate balls and multiplies them. On the real axis those two
cancel to $(2\pi x)^{-1/2}$; as balls they do not cancel at all, because each
factor's own width already spans the whole range:

    wide ball            [+/- 2.01e+3]        # the interval [1000, 2000]
    exp(-x)*I0(x) on it  [+/- 2.49e+432]      # ln(10) * 432 = 995 = the diameter

So the enclosure of $g$ is widened by $e^{\mathrm{diam}}$ and of $g^d$ by
$e^{d\,\mathrm{diam}}$, whatever the interval is called. To hold that under a
factor of 2 the pieces must have diameter below $\ln 2/d$ -- about 0.08 at
$d = 9$, which is 39,000 pieces to reach $s = 3000$ and not a finite
computation to reach the $10^{18}$ the tail bound wanted.

What the skill says now: it recommends ball arithmetic for rigour, names
`RealBallField`/`ComplexBallField`, and says an interval *is* an interval so a
table never has to say separately how far to trust it. It says nothing about
what widens a ball, and nothing about what a finite but enormous one means.

What it should say: ball arithmetic is exact about what it can prove and
proves nothing about cancellation. An expression whose value is small only
because two large terms cancel -- $e^{-x}I_0(x)$, $e^{-x}\sinh x$, an
alternating series -- is enclosed by evaluating each term on the input ball
independently, so the enclosure is as wide as the *terms*, not as the value,
and it degrades like $e^{\mathrm{diameter}}$ rather than gracefully. Two
consequences worth a sentence each: use the library's scaled or combined
primitive where there is one (Arb has `arb_hypgeom_bessel_i_scaled`; Sage does
not expose it), and when an enclosure comes back finite but wider than the
answer, narrow the *input ball* before suspecting the algorithm.

I would rank this alongside the rate-limit lesson rather than below it. It is
narrower in who meets it, but the failure is silent in the same way: an
enormous ball is a correct statement, and it is easy to read a `nan` three
steps downstream as a bug in one's own formula.

Evidence: 2026-09-21 T19 growth review. `/tmp/polya3.py` returned `nan` for
$d=4$ and $d=9$ after 316 s and 92 s; `/tmp/polya4.py` printed the per-piece
radii

    [0,1e3]      [0.11863845404237589781130352718909612422697228962879158014...]
    [1e3,1e5]    [+/- 6.25e+193465]
    [1e5,1e7]    [+/- 6.57e+19347799]
    [1e7,1e9]    [+/- 2.59e+1934781893]

while pointwise `g(10^62)` at an *exact* argument enclosed cleanly to full
precision; `/tmp/polya5.py` took 577 s over 51 ratio-2 pieces and still gave
`nan`; `/tmp/polya6.py` and `/tmp/polya7.py` isolated the wide-ball evaluation
and confirmed `bessel_I() got an unexpected keyword argument 'scaled'` on
Sage 10.9.

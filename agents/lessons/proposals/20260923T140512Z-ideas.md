# Lessons from the ideation run of 2026-09-23T14:05Z (the lattice arithmetic batch)

## PARI's `qfrep` counts pairs, and its `flag` silently changes what the index means

What happened: the batch proposes a table of theta series of lattices, so
before proposing it I checked what PARI actually returns. `qfrep(G, B, flag)`
has two traps stacked on each other, and both produce a plausible theta series
rather than an error.

* With `flag=0` the $i$-th entry is the number of $\pm$ **pairs** of vectors of
  norm $i$, not the number of vectors. The true coefficient is twice it.
  (T402's generator already doubles; nothing says why.)
* With `flag=1` the vector is indexed by **half** the norm, and only even
  norms appear at all.

The second one is the expensive one, because the wrong answer is a real theta
series of a real lattice:

    A3  qfrep(12,0)*2   [0, 12, 0, 6, 0, 24, 0, 12, 0, 24, 0, 8]
    Z3  qfrep(12,0)*2   [6, 12, 8, 6, 24, 24, 0, 12, 30, 24, 24, 8]
    A3  qfrep(12,1)     [6,  3, 12, 6, 12,  4, 24, 3, 18, 12, 12, 12]
    Z3  qfrep(12,1)     [6,  3, 12, 6, 12,  4, 24, 3, 18, 12, 12, 12]

Under `flag=1`, $A_3$ and $\mathbb{Z}^3$ are **identical** — correctly, since
the even-norm vectors of $\mathbb{Z}^3$ are exactly $D_3 = A_3$, so the
half-norm indexing of one is the full-norm indexing of the other. Two different
lattices, one stored value, no error anywhere. A table built that way would
publish $\mathbb{Z}^n$'s theta series under $A_n$'s name for every $n$ where
that coincidence holds, and every internal consistency check — coefficients
positive, $N_0=1$, degree right — would pass.

What the skill says now: nothing about `qfrep`. It says to check a value
against something independent, and it says a run of zeros is evidence rather
than proof; neither reaches a count that is off by a factor of two and shifted
in its index.

What it should say: when a family's values are *counts returned by a library*,
the convention to pin down is not only the normalisation of the object but the
normalisation of the **counting call** — whether it counts vectors or
$\pm$ pairs, and what its index means. Name a pair of objects in the family
that the wrong reading makes equal, and assert they differ. Here that pair is
$A_3$ and $\mathbb{Z}^3$; every family of counts has one, and finding it is
cheaper than finding the error later.

Evidence: `/tmp/latcheck.py`, `/tmp/latcheck3.py` under `agents/sage.sh`,
2026-09-23. The same scripts confirm $\Theta_{E_8} = 1 + 240q^2 + 2160q^4 +
6720q^6 + 17520q^8 + 30240q^{10} + 60480q^{12}$ against T81's $E_4$.

## `PowerSeriesRing(...)` built from a list, and `QuadraticForm.theta_series`, fail under `sage -python` with named imports

What happened: the natural way to compute the value of a theta-series table is
`QuadraticForm(G).theta_series(n)`. Under `sage -python` with the skill's
recommended imports — `import numberdb.sage` first, then named ring imports,
never `sage.all` — it raises:

    AttributeError: cannot access submodule 'function' of module
    'sage.symbolic' (most likely due to a circular import)

The minimal reproduction is not the quadratic form at all:

    from sage.rings.power_series_ring import PowerSeriesRing
    R = PowerSeriesRing(ZZ, 'q')     # fine
    R([1, 240, 2160], 3)             # AttributeError

Constructing the ring works; **coercing a Python list into it** does not. The
list coercion resolves a lazy import of `LazyPowerSeriesRing`, which pulls
`sage.rings.lazy_series` → `sage.data_structures.stream` →
`sage.functions.other` → `sage.symbolic.function`, and that chain is what is
half-initialised. `import sage.functions.other` first does not help; it raises
the same error itself. `theta_series` fails for exactly this reason, on its
last line.

`PolynomialRing` has no such problem and takes the same coefficient list:

    from sage.rings.polynomial.polynomial_ring_constructor import PolynomialRing
    PolynomialRing(ZZ, 'q')([1,0,240,0,2160,0,6720])
    # 6720*q^6 + 2160*q^4 + 240*q^2 + 1

What the skill says now: "Name the rings you import; don't import `sage.all`",
with the note that a ring module imported before Sage is initialised raises
"cannot import name QQ", and a list of three things missing from named imports
(root finding, `RealBall.str`, `QQ('1.25')`).

What it should say: add a fourth, and it is a different failure from the other
three — the import *succeeds* and the object breaks later. Anything that
reaches Sage's **lazy series** machinery is unavailable under named imports:
`PowerSeriesRing(...)` cannot be built from a list, and everything that goes
through it — `QuadraticForm.theta_series` among them — fails with a circular
import naming `sage.symbolic`, several frames away from the call. For a table
of type `Z[]` or `Q[]` this costs nothing, because the value that gets stored
is a polynomial: build it with `PolynomialRing` from the coefficient list and
never construct a power series at all. Truncating a series was the wrong shape
of answer anyway — a stored value has a degree.

Evidence: `/tmp/latcheck2.py` (the `theta_series` traceback), `/tmp/psr.py`
(the minimal case, and `import sage.symbolic.function` failing the same way),
`/tmp/psr2.py` (the `PolynomialRing` route working, and
`import sage.functions.other` failing), all under `agents/sage.sh`,
2026-09-23.

## Agreement between rounded columns is not agreement between numbers

What happened: T394 transcribes Packomania's circle-packing values, which the
source prints in three interdependent columns (small-circle radius, point
separation, reciprocal radius). The generator picks the stored precision by
rounding each column to $k$ significant digits and requiring the decimal
*strings* to be equal for every $2\leq n\leq500$. That test fails at the first
row whose last digit sits near a rounding boundary, whatever the source's
accuracy, so it reported "first disagreement at 10 digits" and the table was
stored at 9 digits throughout. Measuring the discrepancy instead of comparing
strings gives a different picture: median relative difference 5.9e-30, worst
8.75e-12, and 311 of the 499 values of $n$ carry 27 to 29 significant digits
that are printed and mutually consistent. Nine digits is the precision of the
worst row in the range, applied to all of them.

Two things make the string test the wrong one. Double rounding: two numbers a
hair apart round to different strings while agreeing to twenty-eight digits.
And the storage convention: `3.14` already denotes [3.13, 3.15], so a
one-in-the-last-place difference between two printed columns is inside what the
stored value claims, not evidence against it.

What the skill says now: an entry may be deliberately less precise than the
table, by returning `{'number': x, 'digits': 8}`. Nothing says how to choose
that number from a source that prints several columns at several precisions.

What it should say: when a source gives a value in several normalisations,
measure the relative discrepancy between them after converting exactly, rather
than comparing rounded strings, and choose the precision per row from the
digits that row's own source line supports. A single row printed to fewer
digits is a fact about that row and not about the family. A discrepancy of one
unit in the last place is inside the interval a written decimal denotes and is
not a reason to drop a digit.

Evidence: 2026-09-22, T394 critique. `_check_source_consistency` in
`generators/best-known-packings-equal-circles-in-circle/generate.py` compares
`_round_decimal(...) != _round_sig(...)`; the same three files, read with
`decimal` at 60-digit precision, give max relative error 8.75e-12 at $n=417$
(where the source prints ten digits) and 5.9e-30 at the median row. This
refines `agents/lessons/proposals/20260922T001325Z-build.md`, which recorded
the string comparison's answer as the source's precision.

## A MathJax check passes every fragment unless you disable two packages and make errors throw

What happened: the critique checked every `$...$` fragment of a table by
typesetting it with `mathjax-full@3` in node, the method the corpus already
uses. The first run reported "checked 42 errors 0" -- and reported the same for
two deliberately broken controls, `\frac{1}{` and `\notamacro{x}`. `AllPackages`
includes `noerrors` and `noundefined`, which exist to turn a TeX error into
rendered output rather than an exception, and MathJax 3 routes what is left
through `formatError`, which builds an `<merror>` node instead of throwing. A
check built the obvious way therefore passes everything, including a formula
that will print "Math input error" on the page.

What the skill says now: nothing about checking TeX outside the site.

What it should say: if you typeset a table's mathematics to check it, drop
`noerrors` and `noundefined` from the package list and pass
`formatError: (jax, err) => { throw err }`, then run a fragment you know is
broken and confirm the checker reports it. A checker that cannot fail its own
control has confirmed nothing, which is the same trap as a numerical control
that silently returns zero.

Evidence: 2026-09-22, T394 critique. `/tmp/mj394/check2.js` (packages filtered,
no `formatError`) printed "errors 0" with both controls in the list;
`/tmp/mj394/check3.js` (both changes) printed "Missing close brace" and
"Undefined control sequence \notamacro" and 0 errors for the table's own 42
fragments.

## Search matches a query that carries more digits than the stored value

What happened: a critique questioned whether storing nine significant digits,
where the source printed twenty-nine, would cost readers their hits. It does
not. A stored decimal is an interval, and the search matches when the query
lies inside it, however many more digits the query writes. `/api/lookup` with
`text=1836.15267343`, `1836.1526734261` and `1836.15267342617` each answers
with the same two tables, whose stored values are `1836.15267343(11)` and
`1836.152673426 +/- 0.000000160`.

What the skill says now: "A real is stored as an interval that contains it",
and that the interval convention "is the whole reason a hundred digits means
something". It does not say what that implies for somebody deciding how many
digits to store.

What it should say: storing fewer digits than you have does not lose the reader
the hit, because search asks whether their number is inside the stored
interval. What it loses is the reader's ability to check their own digits
against yours, and the reason to consult the table rather than the source. So
"will it still be found" is not the argument for more digits; "can they check
what they hold" is.

Evidence: 2026-09-22, T394 critique. Three `GET /api/lookup?text=...` queries
of increasing length against T76 and T12, each returning both tables.

## Replacing an empty draft through the API still has to pass the nonempty-document check

What happened: T388 was claimed with `POST /api/tables` and `X-Draft: yes`,
using the best prose available before measurement. After the private dry run
measured the range, a `POST /api/table/T388` with the revised document and
`Numbers: []` was refused with `A table needs at least one entry.` Sending
`X-Draft: yes` to the replacement endpoint did not change that. The edit
worked only after the generator had filled the draft, when the run fetched the
stored draft including its nested `Numbers` block, merged the revised prose
into that full document, and sent the merged document back.

What the skill says now: a draft may have no numbers because the prose is
written first, and the generator fills it. It does not say that replacing an
already-created draft document through `/api/table/TID` is still validated as
a nonempty table document.

What it should say: get the prose, parameters and data properties as close as
possible before the draft-creation request. If a draft that still has no
entries needs a prose edit through the API, `write_table` may refuse a document
whose `Numbers` block is empty. After filling a draft, preserve the stored
`Numbers` block when replacing the document, or use a client path that fetches
and merges the full document for you.

Evidence: on 2026-09-21, both `POST /api/table/T388` attempts with the local
`table.yaml` and `Numbers: []` returned
`{"error": "A table needs at least one entry."}`. After `generate.py` filled
53 entries, `/tmp/merge_weight_doc.py` fetched `numberdb.table("T388")`,
copied its `Numbers` into the measured local document, and the same endpoint
accepted revision `ce739f9...`.

## Sage's coding catalog can pull in symbolic machinery

What happened: a first scratch plan for T388 was to use Sage's documented
coding constructors, such as `HammingCode`, `GolayCode`, `BinaryReedMullerCode`,
`QuadraticResidueCode` and `BCHCode`, as an independent source of weight
enumerators. After importing `numberdb.sage` first, importing from
`sage.coding.codes_catalog` failed with
`AttributeError: cannot access submodule 'function' of module 'sage.symbolic'`.
Narrow imports from the individual coding modules failed the same way. The
generator instead builds the needed enumerators directly from MacWilliams
transforms, Boolean monomial evaluations, standard Golay distributions, and
finite-field minimal polynomials for cyclic QR and BCH codes.

What the skill says now: with named imports, parts of Sage that reach for
uninitialised modules can be missing; it names power series operations,
determinants and symmetric-function expansion.

What it should say: add Sage's coding catalog and specialised code
constructors to the list of convenience imports that may drag in symbolic
machinery. For exact code tables, prefer explicit generator matrices,
finite-field minimal polynomials, MacWilliams transforms, or other direct
arithmetic in the rings the table needs; use the coding package only after a
small import probe has passed under `sage -python`.

Evidence: `agents/sage.sh /tmp/probe_codes.py`, 2026-09-21, printed
`numberdb 0.1.10` and then failed while importing Sage coding constructors
with `AttributeError: cannot access submodule 'function' of module
'sage.symbolic'`. The final
`generators/weight-enumerators-classical-linear-codes/generate.py` imports no
Sage coding modules and passed `dry_run.py`, generator integrity checks, audit,
and `verify(sample=None)`.

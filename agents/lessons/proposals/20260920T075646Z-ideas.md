## A name search answers for the name you chose, not for the family

What happened: this run screened an optics batch -- refractive indices,
Sellmeier coefficients, Abbe numbers -- and ran `already_asked` on six
different titles for it. All six returned nothing. The family had in fact been
asked for in 2021 (numberdb-data#63, *Refraction indices of important
materials*) and proposed four hours earlier the same morning
(numberdb-data#170, *Family: Optical constants of materials*), with its first
table already claimed. Neither was reachable from any title this run wrote,
because #63 says "Refraction" where a table would say "Refractive", and #170
says "Optical constants" where this run said "Refractive indices". What found
both was `already_asked('optical material')`: two words of the *subject*, and
neither of them a word in any title considered.

What the skill says now: it says to search for what the family is a
specialisation or a multiple of, and to search the corpus by value as well as
by name. That is the same argument, applied to the corpus. It does not say it
about the backlog.

What it should say: search the **subject** as well as the name, in two or
three wordings a different person might have used, and do it before writing
anything up. A name is one of several the family could have; the subject is
what somebody else would have written down. The cheapest version of this is to
run the screen on the generic noun ("optical material", "quadrature", "zeros
of polynomials") and read the results, rather than on the exact title.

Evidence: 2026-09-20. `already_asked` on "Refractive indices of optical
materials at the Fraunhofer lines", "Sellmeier coefficients of optical
materials", "Abbe numbers of optical materials", "Ordinary and extraordinary
refractive indices of uniaxial crystals", "Birefringences of uniaxial
crystals", "Complex refractive indices of metals" -> `[]` for each;
`already_asked('optical material')` -> `['#170 [open] Family: Optical
constants of materials']`; `already_asked('Refraction indices of important
materials')` -> `['#63 [open] ...']`.

## The corpus can be listed, on the site if not through the API

What happened: the skill says there is no call that lists the corpus and that
to see everything you walk the T-numbers. So a run that wants to know what
subjects the corpus covers -- which is the whole of stage one -- either makes
360 requests or guesses. `https://numberdb.org/tables` is a paginated listing:
50 tables a page, `?page=N` for the rest, eight requests for all 352 titles,
and it is the fastest way to see the shape of the corpus before proposing
anything.

The walk is also worse than it sounds, because T-numbers are not contiguous:
this corpus has no T75, no T342 and nothing between T350 and T360, so a walk
reads gaps that look like deleted tables and wastes a request on each.

What the skill says now: "There is no call that lists the corpus. To see
everything you walk the T-numbers."

What it should say: the same sentence about the API, plus: the site's
`/tables` page lists every table, fifty to a page, and eight requests to it
answer "what is in this database" better than three hundred to the API. Say
also that the numbering has gaps.

Evidence: 2026-09-20. `curl -s "https://numberdb.org/tables?page=$p"` for
`p` in 1..8, extracting `href="/T\d+"`, gives 352 distinct T-numbers with
titles; the highest is T363 and the lowest T0.

## `dir(numberdb)` is empty, so the client cannot be explored from the REPL

What happened: a run that wanted the name of the by-value search function
tried `print([f for f in dir(numberdb) if f.startswith('search')])` and got
`[]`, then `print(dir(numberdb))` and got `[]` again. The module loads its
names lazily, so introspection shows nothing at all -- not a short list, an
empty one, which reads like a broken install rather than like a module that
answers `numberdb.search(...)` perfectly well on the next line.

What the skill says now: nothing. It gives `search`, `search_text` and `table`
by example, which is enough until a reader wants the fourth one.

What it should say: the client resolves its names on first use, so `dir()` and
tab completion are empty; read the module docstring (`help(numberdb)`) or the
README for what exists. Any call that is documented works whether or not `dir`
admits it.

Evidence: 2026-09-20, client at `clients/python`,
`python3 -c "import numberdb; print(dir(numberdb))"` -> `[]`, while
`numberdb.search('1.5168')` in the same process returns three results.

## A value known to four decimals is a weak search key, and the interval says so

What happened: screening an optics batch meant asking whether the corpus
already held a refractive index. `numberdb.search('1.5168')` returned three
entries -- a Dedekind zeta value, a Gamma value and an incomplete elliptic
integral -- none of them optical, all of them agreeing with the query to the
four decimals it carries. That is the interval convention working exactly as
documented: `1.5168` *is* $[1.5167, 1.5169]$, and a corpus of 352 tables has
several numbers in any such interval. `1.458464` and `1.03961212`, from the
same screening, returned nothing at all.

What the skill says now: it explains the interval convention thoroughly, and
it warns that junk entries devalue every hit. It does not say what a
low-precision *query* does.

What it should say: when a family's values are only known to four or five
significant digits -- measured data, transcribed literature values -- expect a
search for one of them to match unrelated entries, and say so in the table
rather than letting a reader think a coincidence is a discovery. The sharp
search key in such a family is whichever of its quantities is published to
nine digits, which for dispersion data is the fit coefficients rather than the
index itself.

Evidence: 2026-09-20. `numberdb.search('1.5168')` -> 3 hits (T162, T9, T350);
`numberdb.search('1.458464')` -> 0; `numberdb.search('1.03961212')` -> 0;
`numberdb.search('0.172')` -> 62 hits.

## `rigour: measured` exists, and so does the parenthesised-uncertainty form

What happened: a run considering a table of experimental constants could not
tell from the skill whether the database admits them: the rigour ladder it
lists is `exact`, `proven`, `assumed-bound`, `heuristic
(agreement-checked)`, `heuristic`, all of which describe a computation. T76,
*Mass ratios*, carries `rigour: measured`, with `sources` naming CODATA
through NIST, a `reliability` line pointing at the uncertainty convention, and
a `rigour details` sentence saying the interval is chosen to hold the
measurements together with their stated uncertainties. Its values are written
`1.007276466621(53)`, the physicists' form, which the database parses.

What the skill says now: five rigour values, none of them `measured`, and
nothing about how to write an experimental uncertainty.

What it should say: a sixth rigour value, `measured`, for a table whose
numbers come from experiment rather than from a computation, with `sources`
and `reliability` beside it; and that the `1.007276466621(53)` form is
accepted, so a measured value need not be rewritten as a centre and a radius.
Physics constants are a real part of this corpus (T10, T12, T76, T78) and a
contributor proposing one currently has to reverse-engineer the convention
from a stored table.

Evidence: 2026-09-20, `numberdb.table('T76')['Data properties']` ->
`{'type': 'R', 'sources': [...], 'reliability': 'See CITE{NISTuncertainty}',
'rigour': 'measured', 'rigour details': 'Not computed: the value comes from
experiment ...'}`.

## Spelling decides whether a search reaches the table

What happened: a proposed title, *Nodes and weights of generalised
Gauss-Laguerre quadrature*, failed its source check against both Wikipedia and
DLMF -- not because either page is the wrong source, but because both write
"generalized" and the title wrote "generalised". The corpus is mixed on this:
T270's title says "normalisation", T104's says "probabilist's convention", and
the text index does no spelling normalisation, so the two spellings are two
different words to it.

What the skill says now: `Keywords` carries the accent-free spelling of a
title, because the index has no `unaccent`.

What it should say: the same for -ise/-ize and for the other transatlantic
pairs. Title the table in the spelling a reader will type -- which for a name
taken from DLMF or from a Wikipedia article is that source's spelling -- and
put the other spelling in `Keywords`, where it has the same weight as the
title.

Evidence: 2026-09-20.
`source_names_it('Nodes and weights of generalised Gauss-Laguerre quadrature',
'https://dlmf.nist.gov/3.5')` -> "the source does not mention generalised";
the same call with "generalized" -> `None`.

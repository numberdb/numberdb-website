# Proposed by the T252 critique run, 2026-09-15

## Omitting the zero rows is a claim about which rows exist, and it is checkable by enumeration

What happened: T252 holds Clebsch-Gordan coefficients and Wigner $3j$ symbols
for $j_1,j_2,j_3\leq2$ and omits every row whose value is zero. Its
`complete-note` says it holds "every nonzero Clebsch-Gordan coefficient ...
with $j_1,j_2,j_3\leq 2$" and a comment says "Rows whose coefficient is zero
are omitted. The selection rules in CITE{formula-selection} determine those
values."

The rows are right. The sentence is not. Enumerating every parameter tuple in
range that satisfies every condition the table's own selection-rule formula
states gives 303 tuples; the table holds 293; the other ten are zero and
absent. Four of the ten vanish by a rule the formula omits ($m_1=m_2=m=0$ with
$j_1+j_2+j_3$ odd, DLMF 34.3.5). The other six are non-trivial zeros of the
$3j$ symbol, which no selection rule predicts at all -- the smallest being
$\begin{pmatrix}3/2&3/2&2\\-1/2&-1/2&1\end{pmatrix}=0$. So the sentence cannot
be repaired by adding one more rule; it is "if and only if" where the source,
DLMF 34.2, carefully says only "if either condition is not satisfied, then the
symbol is zero".

The check that found it took one Sage run and eleven lines: enumerate what the
stated rule admits, compare that set to the keys the table actually holds, and
look at the difference. It is not a check of any *value* -- every value was
already right -- and neither `verify` nor `audit_table` performs it, because
both start from the entries that are there.

What the skill says now: nothing. It covers `complete` and `complete-note` as
the place to say what the table covers, and it covers checking values against
an independent source. Nothing says that leaving rows out is itself a claim, or
how to check it.

What it should say: where a table omits rows because the value is zero, or is
undefined, or is a duplicate under a symmetry, the rule it gives for the
omission is a claim about the *key set*, and it should be checked the same way
a value is -- enumerate the keys the rule admits and take the symmetric
difference with the keys the table holds. Two failures it catches, both of
which this run met in one table: a necessary condition written as if it were
sufficient, and a standard vanishing rule left out of the list. And where the
rule genuinely is not sufficient, say so, with the count: "of the 303 tuples in
range that satisfy them, 293 are here and ten vanish anyway" tells a reader
more than an unqualified rule, and cannot go stale the way the unqualified one
already had.

Evidence: 2026-09-15, T252. Under `agents/sage.sh`, enumerating
$j_1,j_2,j_3\in\{0,\tfrac12,1,\tfrac32,2\}$ with the triangle condition,
$m=m_1+m_2$, $|m|\leq j_3$ and $j_3-m\in\mathbb{Z}$, and calling
`wigner_3j(j1,j2,j3,m1,m2,-m)` on each:

    tuples satisfying every rule in formula-selection: 303
    of those, zero anyway: 10
    of those, nonzero (should be rows): 293
       zero: ('1', '1', '1', '0', '0', '0')  J = 3
       zero: ('3/2', '3/2', '2', '-1/2', '-1/2', '-1')  J = 5
       ... (eight more)

and against the document from `GET /api/table?id=T252`,
`allowed - zeros == rows` is `True` on 293 keys.

## A Sage snippet that only runs at the `sage:` prompt is not a snippet a reader can run

What happened: T252's `Programs` block is

    from sage.functions.wigner import clebsch_gordan, wigner_3j

    clebsch_gordan(1, 1, 1, 1, 0, 1)
    wigner_3j(1, 1, 1, 1, 0, -1)

Run under `sage -python`, the second line answers `-sqrt(1/6)` and the first
raises

    AttributeError: 'int' object has no attribute 'sqrt'

from inside `sage/functions/wigner.py`, at `(2 * j_3 + 1).sqrt(prec)`. The
function needs Sage `Integer`s; at the `sage:` prompt the preparser supplies
them and the same line works, so the snippet looks fine to whoever wrote it.
`wigner_3j` beside it accepts plain `int`s, so it is not even consistent within
one module: there is no way to tell which Sage functions need the preparser
except by running them without it.

A `Programs` block is "the standard incantation for a reader who wants one more
value", and a reader is as likely to paste it into a script, a Jupyter cell
under a plain Python kernel, or a generator module as into the REPL. In two of
those three it is a traceback.

What the skill says now: "`sage -python` has no preparser, so `factorial(30)`
is a Python `int` and `factorial(n) / k` is [a rational, or a float]". That is
the same fact, aimed only at exactness inside a generator. It does not reach
`Programs`, and the failure mode there is different -- not a wrong type
quietly, but an `AttributeError` from library code, naming a line the reader
did not write.

What it should say: alongside the existing preparser sentence, that a
`Programs` snippet should be run the way a reader will run it -- `sage -python
snippet.py`, not pasted at the `sage:` prompt -- and that a Sage library
function may require `Integer`/`QQ` arguments and fail with an `AttributeError`
naming its own internals when given plain `int`s. Writing the literals as
`Integer(1)` (or `ZZ(1)`) makes the snippet true in both places, which is what
"standard incantation" should mean.

Evidence: 2026-09-15, T252. `agents/sage.sh` on a file containing both forms:

    clebsch_gordan(1,1,1,1,0,1) = sqrt(3)*sqrt(1/6) = 0.70710678118654752440   # Integer args
    plain ints: AttributeError: 'int' object has no attribute 'sqrt'
    wigner_3j plain ints: -sqrt(1/6)

## A `param-latex` value label is printed once per row, so its *size* is part of the design

What happened: T252's `normalisation` parameter takes two names and gives each
a LaTeX label, which is exactly what the skill says that field is for. The
labels are the two full symbols:
`$\langle j_1m_1,j_2m_2\mid j_3m\rangle$` and
`$\begin{pmatrix}j_1&j_2&j_3\\m_1&m_2&-m\end{pmatrix}$`. Typeset, they are
18.3 ex × 2.26 ex and 17.6 ex × 5.43 ex, against 1.9 ex for a `$j_1$` column
heading and about 5 ex for the widest parameter value (`-1/2`). MathJax makes
each one unbreakable, so the label sets the width of its column; and the matrix
makes each of the 293 rows it sits on about two and a half times as tall as a
normal row. The numbers beside them are 100 characters long, in a panel that is
half the page.

The site's own stylesheet already carries a comment about the width half of
this, from a table whose named parameter values pushed the digits off the page.
The height half is new: a `pmatrix`, `array`, `cases` or `\frac` in a value
label costs every row that value indexes, and nothing in the document hints at
it -- the YAML is one short line.

What the skill says now: "`param-latex` replaces the label of the parameter
group it sits in, and that is the whole of what it does. It is for a parameter
whose values are words", with `$\operatorname{vol}_{\mathrm{rel}}(B_5)$` as the
example -- a short inline symbol. And, separately, "A value's display is a
label, not a formula", which is about a conversion rule put there, not about
size. Neither says that a correct, non-formula label can still be too big.

What it should say: that the label is printed on every row the value indexes,
so it should be an inline symbol a few characters wide and one line tall --
`$\langle\,\cdot\,\rangle$` (3.1 ex × 2.3 ex) and
`$\bigl(\begin{smallmatrix}\cdot&\cdot&\cdot\\\cdot&\cdot&\cdot\end{smallmatrix}\bigr)$`
(4.9 ex × 2.7 ex) do the same distinguishing work as the two full symbols at a
quarter of the width and half of the height -- and that a label repeating the
parameter symbols that are already in the row's own columns, or restating
`number-header`, is saying it twice. The full symbols belong in the Definition,
where they are read once.

Evidence: 2026-09-15, T252. MathJax 3 (`tex` → `svg`, packages `base` and `ams`
only, which is what the page loads) reports:

    cg label    (\langle j_1m_1,j_2m_2\mid j_3m\rangle)   width 18.346 ex  height 2.262 ex
    3j label    (\begin{pmatrix}...\end{pmatrix})         width 17.550 ex  height 5.430 ex
    j_1                                                   width  1.920 ex  height 1.957 ex
    -1/2                                                  width  5.154 ex  height 2.262 ex
    \langle\,\cdot\,\rangle                               width  3.145 ex  height 2.262 ex
    \bigl(\begin{smallmatrix}...\end{smallmatrix}\bigr)   width  4.913 ex  height 2.713 ex

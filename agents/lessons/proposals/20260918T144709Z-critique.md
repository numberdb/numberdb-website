## A `Programs` snippet has the same reader as a generator, and `from sage.all import` fails for them the same way

What happened: T332's `Programs` block opens `from sage.all import
PolynomialRing, ZZ`. It is the only Sage program block in the corpus that does
-- T330, T331 and T263 all open `import numberdb.sage as numberdb` and then
name the rings they use. The snippet is correct and I ran it: under
`agents/sage.sh` it returns `-40*h^3 + 10*h^2 + 1`, character for character the
table's quintic threefold entry.

The reader it fails for is the one the skill's own install section invites:
`pip install passagemath-symbolics numberdb`. A modular passagemath has no
`sage.all`, so the page's snippet raises `ModuleNotFoundError` on its first
line for exactly the contributor the skill is addressed to.

What the skill says now: the rule is there and is filed under **§6 Write a
generator** -- "Name the rings you use, rather than importing `sage.all`. A
modular passagemath has no `sage.all`, and the generator below runs unchanged
on both it and a full SageMath". §4 describes `Programs` separately ("the
standard incantation in Sage, PARI or mpmath for a reader who wants one more
value") and says nothing about imports, so a contributor writing a `Programs`
block has no reason to think the §6 sentence is about them. The two sections
are far apart and the rule sits in the one about a different file.

What it should say: the named-import rule belongs to both files, and the
sentence in §4's `Programs` paragraph is where a contributor writing a snippet
will meet it. One clause: "and it is written with named imports, not
`sage.all`, for the same reason a generator is -- a reader on passagemath
runs it too."

Evidence: T332, 2026-09-18. The page's snippet, run verbatim under
`agents/sage.sh`, returned the stored entries for `4,5`, `2,2`, `3,4`, `5,2,4`,
`6,2,2,3`, `7,2,2,2,2` and `10,9`; the named-import version returned the same.
T330, T331 and T263 read back from `/api/table?id=...` all open with
`import numberdb.sage as numberdb`.

## The named-import rule has a second error message, and it is not the one the skill quotes

What happened: rewriting T332's snippet with named imports and nothing else,

    from sage.rings.integer_ring import ZZ
    from sage.rings.polynomial.polynomial_ring_constructor import PolynomialRing

failed under `sage -python` with

    AttributeError: partially initialized module 'sage.rings.integer_ring'
    has no attribute 'ZZ' (most likely due to a circular import)

Putting `import numberdb.sage as numberdb` above them fixed it, and the same
two lines then ran and printed the table's longest entry.

What the skill says now: it has the rule and one symptom -- "Importing
`numberdb.sage` first is what makes the direct imports work: a ring module
imported before anything has initialised Sage raises **'cannot import name
QQ'**, and that module does the initialising."

What it should say: the same thing, with the symptom described rather than
quoted. Which module is named and which message comes out depends on which
ring is imported first: `QQ` gives "cannot import name QQ", `ZZ` gives
"partially initialized module 'sage.rings.integer_ring' has no attribute 'ZZ'
(most likely due to a circular import)". A contributor who hits the second and
searches the skill for the first concludes the note is about something else and
goes looking at their install. "raises an ImportError or AttributeError naming
the ring it was asked for -- `cannot import name QQ`, or `partially initialized
module ... has no attribute 'ZZ'`" costs one clause and matches both.

Evidence: T332 critique, 2026-09-18. `/tmp/prog2.py` (named imports alone)
failed with the AttributeError above; `/tmp/prog3.py` (the same file with
`import numberdb.sage as numberdb` on line 1) printed
`-40*h^3 + 10*h^2 + 1` and the 108-character entry `10,9`. Both under
`agents/sage.sh` in `numberdb/builder:latest`.

## A MathJax check that uses `AllPackages` cannot see an undefined macro, and says nothing about it

What happened: the TeX in a table is worth checking before publishing, and the
usual way to do it without a browser is `mathjax-full` under node with
`new TeX({packages: AllPackages})`, looking for `merror` or `data-mjx-error` in
the converted output. T332's 30 distinct fragments all came back clean, and so
did the control fragment `\notacommand{x}`.

`AllPackages` includes the `noundefined` extension, which renders an undefined
control sequence as red text instead of raising. So the check catches
structural faults -- an unbalanced `\left`, a missing brace, a bad environment
-- and is blind to the commonest typo there is, a misspelled macro name.

What the skill says now: nothing about checking TeX at all. §10 has the
general rule that "a measurement needs a control that returns a known answer",
which is what caught this: the control said the checker worked, and a second
control said it did not.

What it should say: if it says anything about checking a table's mathematics
offline, that a `noundefined`-free package list is what makes the check mean
something -- or, failing that, that the macros used are worth listing and
eyeballing, which is a dozen names for a table of this size. `\left[ b` with no
`\right` did error, so the structural half works.

Evidence: T332 critique, 2026-09-18. `/tmp/mj332/check.js` over
`mathjax-full@3.2`: 5 control fragments, 1 error -- `a \left[ b`, "Extra \left
or missing \right" -- and `\notacommand{x}` not among them. The table's own 30
fragments: 0 errors, 12 distinct macros, all core.

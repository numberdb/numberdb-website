## Stop the range where an asymptotic expansion reaches the stored precision

What happened: T283 holds $\mu_n=m(1+x_1+\cdots+x_{n-1})$ for $n=3$ to $n=200$,
fifty digits a row, computed from the Bessel integral of Borwein, Straub, Wan
and Zudilin. The table defends its range in a comment: the two terms
$\tfrac12(\log n-\gamma)+\tfrac1{8n}$ "agree with $\mu_{200}$ to six decimal
digits only, so the fifty digits stored for each $n$ are not predicted by the
asymptotics". The arithmetic is right and the inference is wrong. The same
expansion is a series, and its coefficients are exact rationals obtained from
$\log J_0$ by a four-line recurrence. Carried to its optimal truncation it
reproduces **21** of the fifty stored digits at $n=50$, 40 at $n=100$, 48 at
$n=120$, and all fifty from about $n=126$. The last 75 rows of the table are a
slower way of evaluating a formula.

The rate is not a fit. The series stops being right at the size of the
beyond-all-orders term, which here is the first oscillation lobe of the
integrand: $|J_0(j'_{0,1})|^n$ with $J_0(3.83170597)=-0.4027593957$, so
$-\log_{10}(0.4027594)\,n=0.39495\,n$ digits. The measured column is
$0.395n+1$ across nineteen values of $n$. For a Laplace- or saddle-type
integral the rate is usually readable off the integrand like this, before any
value is computed.

What the skill says now: on range, that the question is "whether anybody will
arrive holding one of them", and then size — entries, digits, block bytes, and
"measure the largest entry before choosing the range". Nothing about a family
whose values become predictable. The whole of section 3 treats the stopping
point as a question about *cost* and *what is looked up*.

What it should say: for a family with an asymptotic expansion in its index --
and most families indexed by a size, a degree or a number of steps have one --
there is a third question, and it is sharper than either of the others. **Past
the $n$ at which the expansion reproduces the precision you store, a row is a
slower formula, and the range should stop there.** Two consequences worth
stating:

* Measure it rather than assume it. Compute the expansion to enough terms to
  truncate optimally, compare against the values you already have, and read off
  where the digit count crosses your stored precision. The comparison doubles as
  an unusually good check on the values: at T283 it agreed to fifty digits at
  nineteen values of $n$ by exact rational arithmetic against Gaussian moments,
  sharing no code and no quadrature with the generator that made them -- and it
  is strongest exactly where the generator's own check (reproducing a closed
  form at $n=3,4$) is weakest.
* Two terms is not "the asymptotics". A completeness note or comment that
  defends a range by truncating an expansion at the first correction is
  defending it against the wrong thing. If the range genuinely goes past the
  crossover, say so and say why; and put the expansion in `Formulas`, because
  it is the only thing the table can give a reader who wants a value past the
  last row.

Evidence: 2026-09-20, T283 growth report
(`agents/critiques/T283-growth.md`, which carries the derivation). $b_k$ for
$k\leq140$ as exact `Fraction`s, summed at `mp.mp.dps = 120` against the 198
stored values with truncation at the smallest term; $b_1=-1/8$ and
$b_2=-5/288$ reproduce the two terms the table's own comment quotes. Digits
reproduced: 3 at $n=7$, 8 at 20, 16 at 40, 21 at 50, 33 at 80, 40 at 100, 48 at
120, and the full stored 50 from $n=130$ on. Smallest term $1.4\times10^{-157}$
at $n=200$, far below the agreement, so the limit is the remainder and not the
truncation.

## A generator that needs no Sage still has to say `sage -python` to pass the audit

What happened: `GET /api/table/T283/audit` returned two findings --
"generate.py does not say how to install what it imports; put the run commands
in its docstring" and "generate.py does not give the command to run it in its
first forty lines". Both are false of the file. Its docstring, on lines 7 to 9,
reads

    $ pip install numberdb mpmath        # once
    $ python3 generate.py                # check the table against this code
    $ python3 generate.py --publish      # send it, with NUMBERDB_API_KEY set

which installs what it imports and runs it. The generator imports `mpmath` and
`numberdb` and nothing else; there is no Sage in it and no reason for any.
`numberdb_app/management/commands/audit_table.py:309` tests for the *literal*
strings `sage -pip install numberdb` and `sage -python generate.py`, which are
the three lines of the skill's own generator template.

What the skill says now: it gives the Sage incantations in the template
(`sage -pip install numberdb`, `sage -python generate.py`,
`sage -python generate.py --publish`) and says at the top that installing is
"`pip install numberdb`, or `sage -pip install numberdb` inside Sage". It does
not say that the audit checks for the Sage form by name, or what to do when a
generator is plain CPython.

What it should say: the audit wants the Sage lines by name, so carry them even
when the generator does not need Sage -- a reader who downloads the file into a
Sage session should find the incantation that works there, and a table whose
code is pure `mpmath` still passes by listing both. Better, if somebody is
changing the check: accept `python3 generate.py` and `pip install` as well, so
that a contributor who has Python and no Sage is not told their correct file is
missing its run commands. Either way the skill should say which it is, because
at present a perfectly good generator fails an audit it cannot see the rule for.

Evidence: 2026-09-20, T283. `GET /api/table/T283/audit` with the zeta3 key
returned `"clean": false` with those two findings and nothing else;
`GET /files/T283/generate.py` is byte-identical to
`generators/mahler-measures-short-random-walks/generate.py`, whose only imports
are `os`, `sys`, `multiprocessing`, `mpmath` and `numberdb`.

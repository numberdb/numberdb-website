# Proposed from the T284 growth critique, 2026-09-20

## Two lists by the same author, on the same page, can use two decimal conventions — and the second one is not as accurate as it prints

What happened: T284 holds the 47 Salem numbers below 1.3, transcribed from
Mossinghoff's `SalemList.html`. That page prints 30 decimal places, *truncated*,
and the generator's source check is built on exactly that:

    def check_source_truncation(root, source_decimal):
        lower, upper = source_truncation_interval(source_decimal)
        if not (root.lower() >= lower and root.upper() < upper):
            raise ArithmeticError(...)

It passes on all 47 rows. It is the right check for that file.

The natural way to extend a Salem-number table is the same author's other
lists, linked two lines below on the same index page — "More Salem Numbers",
eleven files `S4.txt` … `S24.txt` holding *complete* lists of Salem numbers of
each fixed even degree up to a degree-dependent bound, 1741 rows in all. They
look like the same data in the same shape: degree, decimal, polynomial. They
are not the same convention.

- `SalemList.html`: 30 places, truncated.
- `S*.txt`: 14 places, **rounded**, and only about 13 of those 14 are right.

Reconstructing the half-coefficient list from each `S*.txt` polynomial matches
29 of them to T284's rows exactly — same objects, verified by polynomial rather
than by value. Comparing the printed decimal with T284's exact root over those
29 rows: zero agree with truncation, eleven agree with rounding and only
rounding, and five agree with neither. The largest disagreement is
$7.0\times10^{-14}$ — degree 24 prints `1.29174142571457` where the root is
$1.2917414257145004\ldots$, and degree 24 prints `1.26010354035500` where the
root is $1.2601035403549909\ldots$.

So an author who extends the table by reusing the check that already works
gets a hard failure on about half the new rows — which is the good outcome,
because it is loud. The bad outcome is the author who then loosens the
tolerance until it passes, with no measurement telling them where to stop, and
publishes a check that would no longer catch a transcription error either.

Nothing on the site warns of this. The page that documents the table format
(`misc/tableformat.html`) says "Mahler measure of the polynomial, rounded (not
truncated) at the last digit shown" — but its column list is `D / Measure /
Out / Coefficients`, which is neither `SalemList.html`'s layout nor
`S*.txt`'s, so it documents a third pair of files and reading it would have
told you the wrong thing about both.

What the skill says now: §3 covers precision as something *you* choose, and
`rigour details` as the place to say how the digits were obtained. It says
nothing about the source's own digits, and nothing about a source with more
than one file.

What it should say: the decimal convention belongs to the file, not to the
author or the site, so when a table is extended from a sibling list — even one
linked from the same index page — re-derive it instead of inheriting the check
that passed. Test both readings before writing the check: quantize your exact
value at the source's printed precision with `ROUND_DOWN` and with
`ROUND_HALF_UP` and see which the source equals. Do it over every row you can
already verify, not one. And when neither reading matches, the source's last
printed digit is noise rather than data: measure the largest disagreement over
the rows you can check, and set the tolerance from that measurement, in the
generator, with the number written down. A source decimal is evidence of a
transcription, and it is only ever as good as the precision the source
actually computed in — which is not always the precision it printed.

Evidence: T284, 2026-09-20.
`https://web.archive.org/web/20210506190557/http://www.cecm.sfu.ca/~mjm/Lehmer/lists/S24.txt`
against `GET /api/table?id=T284`; 29 rows matched by reconstructed
half-coefficient list, max $|{\rm printed} - {\rm exact}| = 6.95\times10^{-14}$
at degree 24. `generators/salem-numbers-less-than-1.3/generate.py`,
`check_source_truncation`.

## A table repaired through the API leaves its generator lying, and the lie only fires the next time somebody extends it

What happened: T284 was built by `generate.py`, published, critiqued, and then
repaired. The repairs — six ranked findings, including rewriting five entry
comments to name the Coxeter triangle groups and replacing a stale "Mossinghoff
marks this row as a recent discovery" on three rows — were applied through the
API against the live table, which is the quick and obvious way to fix prose.
The generator was never touched. Four days later it still emits

    degree $10$; minimal polynomial $\dots$; this is Lehmer's number.

while the live row reads

    This Salem number has degree $10$, with minimal polynomial $\dots$ It is
    Lehmer's number and the growth rate of the Coxeter triangle group
    HREF{...}[$\Delta(2,3,7)$].

and still emits the "recent discovery" sentence the critique had removed.
`git log` on the generator shows one commit; the repair landed the same day in
a different file.

Everything looks fine, and stays looking fine, because nothing runs the
generator again. The table renders correctly, `verify` compares *values* and
those are unchanged, and `audit_table` reports `clean: true` — the audit reads
the table, not the code that claims to produce it. The damage is deferred to
the next person who wants one more row, or who lifts the generator to build a
sibling table: `generate.py --publish` silently reverts every prose repair,
and it reverts them as a normal successful run with no diff to look at.

This is not specific to any deployment. Anyone with a generator and an API key
can edit a published table in the browser or with one `curl`, and the skill
actively encourages fixing prose that way — it is faster than a rebuild and
does not touch the numbers.

What the skill says now: §5 and §6 treat the generator as the thing that
produces the table, and `verify` as the check that it still does. `verify`
compares values. It does not compare entry comments, and nothing says the two
can part company.

What it should say: the generator is the table's source of truth for
everything it writes, including entry comments — so an edit made through the
API to a field the generator produces has to be ported back into the generator
in the same sitting, or the generator has to stop producing that field. Which
of the two is a real choice: prose that is per-row and hand-tuned may be better
owned by the table than by the code, and deleting `comment=` from the
generator's `value()` is a legitimate answer. What is not legitimate is
leaving both. The check is one `verify` run read for comment differences rather
than value differences, and it is worth stating that a clean `verify` and a
clean `audit_table` will both pass over this.

Evidence: T284, 2026-09-20. `generators/salem-numbers-less-than-1.3/generate.py`
`entry_comment()` against the live `Numbers` from `GET /api/table?id=T284`;
five entry comments and three discovery attributions differ.
`agents/critiques/T284-repaired.md` records the repairs; `git log --oneline --
generators/salem-numbers-less-than-1.3/` shows the generator unchanged since
`85bab81`. `GET /api/table/T284/audit` → `{"findings": [], "clean": true}`.

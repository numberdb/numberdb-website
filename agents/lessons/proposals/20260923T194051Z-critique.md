# Lessons proposed by the T447 critique, 2026-09-23

## A parameter with exactly one value is a permanent column of nothing

What happened: T447 declares four parameters. Two of them, `size` and
`labelling`, have one value each -- `length: word length` and
`unlabelled: ordinary words` -- so every one of its 118 rows prints "word
length" and "ordinary words" between the exponent and the number, and the
parameter list renders "size — size (length)", where the title, the display,
the only value and the constraint all say the same word. Every entry address
gains two constant coordinates: the row a citation should reach as
`#2,7/3` is `#2,7/3,length,unlabelled`. Both freeze at publication, because
parameter keys and their order are what a citation resolves on, so this is
repairable only while the table is a draft. `GET /api/table/T447/audit`
returns `clean: true`: the check that exists for parameters carrying no index,
`_one_table_or_several`, skips any parameter with fewer than two distinct
labels, which is exactly this case. The sibling table T448 has the same two
parameters with two values in `labelling`, and there the audit does complain --
so the idiom is caught when it is half as bad and silent when it is complete.

What the skill says now: it says a great deal about a parameter with a *handful*
of values that are names, because that is two tables sharing a title, and it
says a value's display "is a label, not a formula" and that a label repeating
the heading above it is noise. It says nothing about a parameter with one
value, which is neither of those faults: it does not split the table and it
does not restate a heading. It is simply a column that never varies.

What it should say: a parameter must have, or be able to have, more than one
value. If every entry in the table shares one value of it, it indexes nothing:
it is a sentence about a convention, and its home is the definition or a
comment, where it is read once instead of 118 times. Check this before
publishing, because a parameter cannot be removed afterwards. The question to
ask is the one the skill already asks about names, in its degenerate case: what
would a second row under this parameter be? If there is no such row --
there is one size measure for a word, and no labelled version of a power-free
language -- it is not a parameter.

Evidence: T447, read 2026-09-23. `GET /api/table?id=T447` shows
`Parameters.size.values = {"length": "word length"}` and
`Parameters.labelling.values = {"unlabelled": "ordinary words"}`, and all 118
entries nested under those single keys. `GET /preview?table=<yaml>` renders the
header row as `$k$ | $\beta$ | size | labelling | $\gamma$` and the parameter
list as `size — size (length)`. `GET /api/table/T447/audit` ->
`{"tid": "T447", "findings": [], "clean": true}`. The threshold is
`numberdb_app/management/commands/audit_table.py:653`,
`if not 2 <= len(labels) <= self.MOST_LABELS: continue`.

## A declared reference that nothing cites is not checked in that direction

What happened: T447 declares three references and cites two. `ShurTCS` --
Shur, *Growth rates of complexity of power-free languages*, TCS 411 (2010) --
appears in no `CITE{}` anywhere in the document, so it renders as `[3]` in the
reference list and a reader has no way to learn which part of the table rests
on it. The audit checks the other direction and passes: `unresolved_citations`
asserts that every `CITE{}` names a Link, a Reference or a label in the same
table, and there is no check that every Reference is named by a `CITE{}`.

What the skill says now: "A reference is for citing, not for listing.
`CITE{Koshy}` in a comment earns its place; a bibliography nobody points at is
furniture." So the rule is written; what is missing is that nothing enforces
it and the audit's clean bill does not cover it.

What it should say: the same sentence, with a warning attached -- an audit that
returns clean has checked that your citations resolve, not that your references
are cited. Read the reference list against the prose by hand before offering a
draft. Three references and two `CITE` keys is a fault a person sees in five
seconds and no check sees at all.

Evidence: T447, 2026-09-23. `ShurTCS` occurs once in the document, as a key
under `References`; `grep -rn ShurTCS generators/power-free-language-growth-rates/`
finds only the declaration in `table.yaml:135`. `GET /api/table/T447/audit`
returns `clean: true`. The forward check is
`numberdb_app/validate.py:unresolved_citations`, called from
`audit_table.py:_check`; there is no reverse counterpart.

## The API key goes in `Authorization: Bearer`, and the wrong header fails as "does not exist"

What happened: reading a draft with
`curl -H "Authorization: Api-Key $KEY" https://numberdb.org/api/table?id=T447`
returned HTTP 429 and
`{"error": "Rate limit exceeded (60 requests per 60 minutes). An API key
raises this limit; see /help#section-api."}`. The key was valid; the header
name was not, so the request was anonymous and hit the anonymous bucket. Under
the limit the same mistake is quieter still: an anonymous read of a draft
answers `{"error": "Table with id 'T447' does not exist."}`, which reads like a
table that was never created rather than like a credential that was not
presented. `Authorization: Bearer $KEY` works.

What the skill says now: it tells a contributor to set `NUMBERDB_API_KEY` and
let the client find it, which is right and is what most people will do. It does
not say what the header is, and the rate-limit message that a reader meets --
"An API key raises this limit" -- does not either. Anybody debugging with curl,
or writing a client in another language, has to guess.

What it should say: the API reads `Authorization: Bearer <key>`. A request with
a key under any other header name is treated as anonymous, and the two symptoms
of that are a 429 naming the anonymous limit and a draft reading as "does not
exist" -- neither of which mentions authentication. The second is the same
failure the package documents for a script that never reads its key from stdin,
and it is worth naming once as "a draft that answers 'does not exist' is almost
always a key that did not arrive".

Evidence: 2026-09-23, reading T447 while writing its critique. With
`Authorization: Api-Key`, HTTP 429 with the anonymous rate-limit body; with
`Authorization: Bearer`, HTTP 200 and 12972 bytes of document, same key, same
minute. The header is set in `clients/python/numberdb/_http.py:176`,
`headers['Authorization'] = 'Bearer %s' % (key,)`.

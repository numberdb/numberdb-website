## `lfunmf` hands back one $L$-function per embedding, grouped by Galois orbit, so the Ldata is `lfunmf(mf)[o][i]`

What happened: every PARI call in the first two probes of this run failed with
`lfun: incorrect type in lfunmisc_to_ldata (t_VEC)` --
`lfun(lfunmf(mfinit([1,12],0)),6)`, `lfun(lfunmf(mf)[1],6)`, `lfunzeros`,
`lfunlambda`, `lfuncheckfeq`, all of them. It reads exactly like the modular
forms package being absent or broken in the image, and half an hour went into
deciding which. The package is fine: `lfunmf(mf)` returns a vector with one
entry per Galois orbit, and each of those is a vector with one Ldata per
complex embedding of the Hecke field. For a weight $12$ space of dimension one
that is a vector of a vector of an Ldata, so `lfunmf(mf)[1]` is still a vector
and `lfun` refuses it. `lfunmf(mf)[1][1]` works and gives
$L(\Delta,6)=0.792122838646030569355944890486735838\ldots$; `#lfunmf(mf)[1]`
is $1$ in weight $12$ and $2$ in weight $24$, which is the dimension.

What the skill says now: nothing about `lfunmf`. It names PARI as a route for a
`Programs` block and shows `mfheckemat` in T215.

What it should say: a nested type error out of `lfun` is a bracket, not a
missing feature. `lfunmf(mf)` is indexed by orbit and then by embedding.
Print `#` of it before assuming anything, and when a table's `Programs` block
shows the incantation, show both indices: a reader who copies
`lfunmf(mf)[1]` gets the error above and no hint.

Evidence: 2026-09-17, `/tmp/probe2.py` (every mf call failing) and
`/tmp/probe3.py` (`#lfunmf(mf)[1]` weight 12 = 1, weight 24 = 2; the same
calls working with the second index).

## PARI and Sage order the embeddings of a Hecke field oppositely, so an eigenform must be identified by $a_2$ and never by an index

What happened: weight $24$ has two conjugate eigenforms, with
$a_2=540\pm12\sqrt{144169}$, that is $+5096.3511717\ldots$ and
$-4016.3511717\ldots$. PARI's `lfunmf(mfinit([1,24],0))[1]` lists the
$+5096$ form first, and `lfunan` on the two confirms it. Sage's
`Newforms(1,24,names='a')[0].lseries(embedding=0)` is the $-4016$ form, and
`petersson_norm(embedding=0)` likewise. So $L(f,12)$ is $2.9332\ldots$ for the
first form in one library and $1.2194\ldots$ for the first form in the other,
and a table filled from one while checked against the other would have its
conjugates swapped with nothing looking wrong: both numbers are real, both are
the right size, and both belong to the same weight.

What the skill says now: it warns that entries display in document order and
that a parameter's key is an address. It says nothing about a parameter whose
values are supplied by a library's ordering.

What it should say: where a parameter numbers Galois conjugates, the numbering
has to be defined by a quantity of the object (here: increasing $a_2$) and
asserted in the generator against an exact computation, not inherited from
whichever library produced the value. Two libraries that agree on the set of
values can disagree on the order, and the disagreement is invisible in the
numbers.

Evidence: 2026-09-17, `/tmp/probe6.py`: `lfunan(L,2)` for the two weight $24$
L-functions gives `[1, 5096.35...]` then `[1, -4016.35...]`, `lfun(.,12)` gives
`2.9332...` then `1.2194...`, while Sage's `lseries(embedding=0)(12)` is
`1.2194...`; `/tmp/probe5.py`: `K.embeddings(CC)` index $0$ is $a_2=-4016.35$.

## Sage's `petersson_norm` does not compute the integral its docstring writes, and a direct integration is the independent check

What happened: the docstring of
`sage.modular.modform.element.ModularForm_abstract.petersson_norm` writes
$\langle f,f\rangle=\int|f(x+iy)|^2y^k\,dx\,dy$. A table copying that would
state the wrong measure. Integrating $|\Delta(x+iy)|^2y^{10}\,dx\,dy$ over the
standard fundamental domain with mpmath at $25$ digits and $59$ terms of the
$q$-expansion gave $1.035362056789\ldots\times10^{-6}$ against Sage's
$1.0353620568043209\ldots\times10^{-6}$: ten digits, so the measure is
$y^{k-2}\,dx\,dy$, equivalently $y^k$ against $dx\,dy/y^2$, and there is no
volume factor. The same docstring says the number is computed as
$(k-1)!\,L(\mathrm{Sym}^2f,k)/(2^{2k-1}\pi^{k+1})$ through
`symsquare_lseries`, which is why the integral is an independent route rather
than a rearrangement of the same computation.

What the skill says now: "Decide exactness from the definition, never from the
digits", and: name an independent fact a builder could run this afternoon.

What it should say: a docstring is not a definition. Where a value comes out of
a library whose documentation states a formula, integrate or sum the thing
itself once at low precision: it costs a minute (38 seconds here) and it is
the only way to learn which of three circulating normalisations the number
satisfies. It doubles as the independent check the table needs.

Evidence: 2026-09-17, `/tmp/probe5.py`: the printed docstring, Sage's
`1.0353620568043209e-6`, and the direct integral
`0.000001035362056789003531452093`.

## PARI 2.17 refuses `lfunsympow`; Sage does the symmetric square by Dokchitser

What happened: `lfun(lfunsympow(L,2),12)` answers
`lfunsympow: sorry, lfunsympow is not yet implemented` in PARI 2.17.1, which
looked like the end of any table of adjoint $L$-values. Sage has
`ModularForm_abstract.symsquare_lseries`, which builds the symmetric square
$L$-function from the Hecke eigenvalues and evaluates it with Dokchitser:
$L(\mathrm{Sym}^2\Delta,12)=0.63179294572788320$.

What the skill says now: it lists what arb implements for `proven` work and
does not compare PARI's and Sage's $L$-function coverage.

What it should say: the two systems do not cover the same $L$-functions. PARI's
`lfun` is the stronger route for a modular form's own $L$-function (zeros,
completed values, `lfuncheckfeq`), Sage's is the only route here for its
symmetric square, and a family refused by one is worth trying in the other
before it is written off.

Evidence: 2026-09-17, `/tmp/probe3.py` (the refusal) and `/tmp/probe5.py`,
`/tmp/probe6.py` (`symsquare_lseries` answering).

## `lfunzeros` ordinates sit on $\operatorname{Re}s=k/2$, not on $\operatorname{Re}s=1/2$

What happened: `lfunzeros` for the $L$-function of $\Delta$ returns
$9.22237939992110252224\ldots$, and it is not obvious in which normalisation
that ordinate is meant, because PARI evaluated the same object at $s=6$ to give
the arithmetic value $L(\Delta,6)$. Testing settles it:
$|L(\Delta,6+9.2223793999\ldots i)|\approx2\cdot10^{-25}$ while
$|L(\Delta,\tfrac12+9.2223793999\ldots i)|=458.79$. The ordinate is the same in
both normalisations; the line is not.

What the skill says now: "The nth zero must say where counting starts", and
that a table's `number-header` is a claim about every value under it.

What it should say: a zero table states the line as well as the counting. For a
motivic $L$-function held in the arithmetic normalisation, the critical line is
$\operatorname{Re}s=k/2$, and the one-line check is to evaluate at both
candidates and see which is $10^{-25}$.

Evidence: 2026-09-17, `/tmp/probe6.py`, the two absolute values above.

## The rational ratios of completed $L$-values are a check that needs no second implementation

What happened: looking for a check on critical $L$-values that was not "two
libraries agree", `bestappr` on $\Lambda(\Delta,j)/\Lambda(\Delta,3)$ over odd
critical $j$ returned exactly $[1620/691,\,1,\,9/14,\,9/14,\,1,\,1620/691]$,
and over even $j$ divided by $\Lambda(\Delta,2)$,
$[1,\,25/48,\,5/12,\,25/48,\,1]$. Weight $16$ gave
$[1,\,245/936,\,49/468,\,35/468,\,49/468,\,245/936,\,1]$, weight $22$ an
antisymmetric list through an exact $0$. This is Manin's rationality theorem,
and the $691$ is the weight $12$ congruence prime. A single wrong value, or a
value attached to the wrong conjugate, breaks the pattern at once. The
companion exact fact: the sign of the functional equation is $(-1)^{k/2}$, so
for $k\equiv2\pmod4$ the central value is exactly $0$ (confirmed to $115$
digits for $k=50,54$) and `lfunorderzero` returns $1$ there and $0$ for
$k=12$.

What the skill says now: a check is a specialisation to a known sequence, a
published value, an identity to a stored table, or a small brute-force count.

What it should say: add a fifth kind, the strongest of the five for special
values: an *internal* algebraicity relation. Where a theorem says some ratio or
combination of a table's own entries is rational, `bestappr` on the computed
ratio tests every row against every other and needs no second library, no
published table and no network.

Evidence: 2026-09-17, `/tmp/probe4.py` (the ratio lists, the central values
`0.E-115` for $k=50$ and `0.E-134` for $k=54$) and `/tmp/probe6.py`
(`lfunorderzero`).

## `RealBall` has no `.str`, and root finding over a ball field is not implemented

What happened: two small stops in Sage 10.9, both inside three lines of each
other. `ball.str(30)` raises
`AttributeError: 'sage.rings.real_arb.RealBall' object has no attribute 'str'`
-- `str(ball)` is the way, and it prints the `[... +/- ...]` form the database
wants. And `charpoly.roots(ring=RealBallField(400))` raises
`NotImplementedError: root finding for this polynomial not implemented`, so an
exact algebraic eigenvalue has to be found in `AA` first and then coerced:
`[RBF(r) for r in chi.roots(ring=AA, multiplicities=False)]` gives balls whose
width is genuinely the enclosure of the algebraic number.

What the skill says now: that a modular passagemath install brings no
`RealBall.str`, listed among what the named imports do not bring.

What it should say: `RealBall.str` is absent in full SageMath 10.9 as well, not
only in the modular install, so the note is about the class and not about the
packaging. And ball fields do not do root finding: the route from a
characteristic polynomial to a `proven` real value is `AA` and then the ball
field.

Evidence: 2026-09-17, `/tmp/probe4.py` (both failures) and `/tmp/probe5.py`
(the working `AA`-then-`RBF` version, weight $24$ normalised $a_2$ as
`[-1.3867134517... +/- 7.22e-120]`).

# Lessons proposed by the T396 critique, 2026-09-22

## An entry key that contains a comma is printed with a space added, because the key is read as the parameter list

What happened: T396 is indexed by one `Symbolic` parameter whose values are
matroid names, and 55 of its 147 keys are uniform matroids written `U(2,4)`,
`U(10,11)`. The page prints them `U(2, 4)` and `U(10, 11)`. The table's first
comment tells the reader that "Uniform matroids are written `U(r,n)`", so the
page contradicts its own prose on a third of its rows, and the stored YAML
shows nothing: the key is exactly what the author wrote.

The cause is the entry address. An entry's identity is its parameter values
comma separated -- which the skill already says, in the paragraph about
`HREF{slug#Z,1,density}` -- so the renderer splits a key on commas and rejoins
the parts for display, with `', '` between them
(`numberdb_app/views.py:1420`). For a table with two parameters that is
right and is why the code exists. For one parameter whose value happens to
contain a comma there is nothing to split, and the rejoin inserts a space that
was never in the document. The anchor id is built with the other separator
(`views.py:1423`), so `HREF{slug#U(2,4)}` still resolves: the fault is display
only.

Two consequences a contributor should know before choosing keys. A key
containing a comma cannot be printed verbatim. And the fix is the field that
was already worth using: `values:` on the parameter, a map from the stored key
to its display, which is consulted before the split
(`_shown_as`, `views.py:1417`) and lets the row print `$U_{2,4}$` -- real
mathematics rather than an ASCII identifier. Checked on the live `/preview`:
with a map holding `U(2,4)` and not `U(2,5)`, the first row printed
`$U_{2,4}$` and the next printed `U(2, 5)`.

One trap in doing it: `numberdb_app/validate.py:450` treats a declared
`values:` map as the list of permitted values and refuses, fatally, any entry
whose value is outside it. So the map must cover every key in the table, not
only the keys whose display you wanted to change. Declaring it for 55 of 147
rows would make the other 92 unwritable.

What the skill says now: that an entry's address is its parameter values comma
separated, and that `param-latex` is the wrong tool for a numeric value. It
does not mention `values:` at all -- proposed already, in
`agents/lessons/proposals/20260916T032246Z-critique.md`, on the ground that a
table indexed by named objects should print $E_6$ rather than `E6`. This
refines that proposal: for a key containing a comma the map is not a
refinement of the display but the only way to get the document's own text onto
the page.

What it should say, beside the `param-latex` paragraph: a parameter value is
rendered by splitting the key on commas, because that is the entry's address,
so a value that contains a comma is printed with a space after it. Write such
a value's display with `values:`, a map from the stored key to its display, and
make the map cover every key -- a declared map is also the list of values an
entry may have, and one outside it is refused.

Evidence: 2026-09-22, T396 critique (private draft, 147 entries, one
`Symbolic` parameter). `GET /api/table?id=T396` gives keys `U(2,2)`,
`U(2,11)`; two `/preview?table=...` renders of the same entries, one with a
partial `values:` map and one without, printed `$U_{2,4}$` and `U(2, 5)` side
by side. `numberdb_app/views.py:1417-1428` is the split, the id and the
`_shown_as` lookup; `numberdb_app/validate.py:427-461` is the refusal.

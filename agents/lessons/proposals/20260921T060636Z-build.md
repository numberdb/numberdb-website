## Link to a sibling draft by T-number when its slug is not yet public
What happened: T378 needed to link to T377, the sibling draft holding the
arithmetic factors $a_k$. The document first used
`HREF{Arithmetic_factors_zeta_moments}`, derived from the local generator
directory and the title rather than from a resolved address. The authenticated
`/api/table?id=T377` response exposed the draft document but no `url`, and the
audit reported `HREF{Arithmetic_factors_zeta_moments} names no table here`.
Changing the prose and Similar tables entry to `HREF{T377}` made the same
audit clean.

What the skill says now: it says not to derive a slug from a title, and it
notes that `HREF{Integers}` and `HREF{T13}` both resolve in the audit only in
code comments. It does not say what to do when the table to link is a draft
whose slug is not exposed by the API.

What it should say: ordinary prose links to a sibling draft may use the
T-number, `HREF{T123}`, when the slug is not available from a creation answer
or a trusted table read. Do not invent the slug from the title or from a local
directory name. This is only for prose links: metadata fields such as
`Data properties: repeats` may have stricter slug requirements.

Evidence: T378 build, 2026-09-21. `/api/table/T378/audit` first returned
`HREF{Arithmetic_factors_zeta_moments} names no table here`; after replacing
the two links with `HREF{T377}`, it returned `{"findings": [], "clean": true}`.

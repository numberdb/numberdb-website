## A batch-proposed tag can still fail audit on the first draft

What happened: numberdb-data #178 proposed a new `coding theory` tag for five
tables in the same family. The tag existed on the site with no published
tables. Adding it to the first finished draft, T389, made `audit_table` report
`Tags: "coding theory" reaches only this table`, because the audit counts
published tables and cannot see future companion drafts. Removing the tag made
the audit clean, but left the batch-level tag request for review.

What the skill says now: propose a new tag when three or more tables would
carry it, counting others in the same batch; it also says the audit refuses a
tag that reaches only one table.

What it should say: when building one table from a batch that proposes a new
tag, run the audit before offering the draft. If the audit reports that the
new tag reaches only this table, leave the draft clean and say in the build
report that the batch tag should be applied once enough companion tables are
reviewed together, or once existing public tables have been retagged.

Evidence: T389, `GET /api/table/T389/audit` first reported the one-table
`coding theory` tag. After removing that tag, the same audit returned
`{"findings": [], "clean": true}`.

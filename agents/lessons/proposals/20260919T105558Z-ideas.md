# Lessons from the ideas run of 2026-09-19T1055 (division polynomials and elliptic torsion)

## A real-valued search reaches the real entries of a complex table, so one family is one table

What happened: the batch proposed a table of the $x$-coordinates of the
torsion points of an elliptic curve. Some of them are real and some are
complex, and the question was whether that is one table of type `C` or two
tables split by which kind of number a row holds. Nothing in the skill says,
and splitting would have divided one family on a property of the individual
value.

T60, *Roots of unity*, already answers it. It is typed `C` and writes its real
entries as plain reals (`1`, `-1`) beside complex ones
(`0.309... + i * 0.951...`), and both are found:

    numberdb.search_integer(-1).total      -> 15, and T60 is among them
    numberdb.search_real_ball('-1.0', 1e-9) -> the same 15 tables
    numberdb.search_complex_ball('0.309...', '0.951...', 1e-18) -> T60

So a real value stored in a `C` table answers a real search. That settles the
design: one table, type `C`, real members written as reals.

What the skill says now: the type table lists `R` and `C` separately and says
what each holds; nothing says what a search of one kind reaches in a table of
the other.

What it should say: a table's `type` is about what the family holds, not about
what a reader can search for. A family with both real and complex members is
one table of type `C`; write the real ones as reals and they answer real and
integer searches too, as T60 does. Do not split a family by which kind of
number an individual row turned out to be.

Evidence: 2026-09-19 ideas run, `/tmp/cx.py` and `/tmp/cx2.py`, against
published T60.

## OEIS answers `urllib` and refuses `curl`, and its JSON search is the fastest independent check

What happened: following the existing lesson to search OEIS for a polynomial
family, `curl -s 'https://oeis.org/search?q=...&fmt=json'` returned a
Cloudflare interstitial ("Enable JavaScript and cookies to continue"), and so
did `curl https://oeis.org/A006769/internal`. The same URLs through
`urllib.request` with an ordinary `User-Agent` header returned 29 KB of JSON
immediately, listing five elliptic divisibility sequences with their names,
offsets and terms -- which became four of the five independent checks the batch
could name.

What the skill says now: OEIS is named as a link target and, in the lesson
file, as the place to look for a polynomial family. Nothing says how to ask it.

What it should say: ask OEIS with `fmt=json` from Python rather than from
`curl`, which its front end currently challenges:

    urllib.request.urlopen(urllib.request.Request(
        'https://oeis.org/search?q=elliptic+divisibility+sequence&fmt=json',
        headers={'User-Agent': 'your-tool-name'}))

`?q=id:A006769&fmt=json` returns one record with `name`, `offset` and `data`,
which is enough to compare a table's first terms without downloading a b-file.

Evidence: 2026-09-19 ideas run, `/tmp/oeis.py` and `/tmp/oeis2.py` against the
`curl` attempts in the same session.

## A rational root of a division polynomial is not a rational torsion point

What happened: the obvious independent check for a table of division
polynomials is that their rational roots are the $x$-coordinates of the
rational torsion points, which Sage will list with `E.torsion_points()`. It
is false, and it fails on the smallest curves in the table:

    15a1  torsion of order 8, x-coordinates  -13/4, -2, -1, 3, 8
          rational roots of psi_8            -7, -13/4, -2, -1, 1/2, 3, 8
    17a1  torsion of order 4, x-coordinates  11/4, 7
          rational roots of psi_4            -3/2, 11/4, 7

The extra roots are $x$-coordinates of torsion points whose $y$ is irrational,
equivalently of rational torsion points on a quadratic twist. The same trap
one level down, in the reduction check: modulo 13 the polynomial $\psi_3$ of
11a1 has the root 4, while $E(\mathbb{F}_{13})$ has no point of order 3,
because the $y$ lives in $\mathbb{F}_{13^2}$. Checking roots against
$E(\mathbb{F}_p)$ reports a disagreement on a correct table.

What the skill says now: "Check new values against something independent" and
"Verify a claim before writing it into a table, including one somebody
suggested".

What it should say: the same warning in its arithmetic form. A set of
$x$-coordinates is a set of *half* points: before comparing it with a list of
points, lift each $x$ to $y$ in the quadratic extension it may need. Written
as a check that passes:

    for x in GF(p):
        for P in E.change_ring(GF(p**2)).lift_x(F2(x), all=True):
            if P and n*P == 0: ...   # then x is a root of psi_n mod p

Evidence: 2026-09-19 ideas run, `/tmp/nb/dp2.py` (the failing form, three
disagreements out of eight) and `/tmp/nb/dp4.py` (the same check over
$\mathbb{F}_{p^2}$, agreeing everywhere).

## Cremona and LMFDB number curves differently inside an isogeny class

What happened: the batch wanted to write a curve's label in each entry's
comment, and nearly wrote "the LMFDB label" for labels taken from Sage, which
gives Cremona's. They are not the same numbering: the LMFDB's 11.a1 is
Cremona's 11a2 and the LMFDB's 11.a2 is Cremona's 11a1, while 11.a3 and 11a3
agree. A check that quotes an LMFDB data page for a row labelled the Cremona
way compares two different curves of the same conductor, and both are real
curves with real invariants, so nothing looks wrong.

    lmfdb_label 11.a1  Clabel 11a2  ainvs [0,-1,1,-7820,-263580]
    lmfdb_label 11.a2  Clabel 11a1  ainvs [0,-1,1,-10,-20]

`E.lmfdb_label()` needs Sage's optional elliptic curve database and raises
`AttributeError` without it, so the translation is not free.

What the skill says now: T211's `rigour details` cites LMFDB data pages by
label, and several elliptic curve tables carry "Cremona label" and "LMFDB
label" as keywords; nothing warns that the two disagree.

What it should say: name a curve by its invariants, not by a label -- the
corpus's elliptic curve tables already index on $(N, c_4, c_6)$ -- and when a
label is written in a comment, say whose it is. When checking against the
LMFDB, match on `ainvs` or on $(c_4,c_6)$ rather than on the label.

Evidence: 2026-09-19 ideas run, `/tmp/lm.py` against
`https://www.lmfdb.org/api/ec_curvedata/?conductor=11&_format=json`, and the
`AttributeError` from `E.lmfdb_label()` under `agents/sage.sh`.

## `QQbar` to `ComplexIntervalField` is a `proven` route for the roots of an exact polynomial

What happened: a table of the roots of integer polynomials needs enclosures,
and the skill's advice is ball arithmetic, which is about evaluating a
function rather than isolating a root. What works, and needs no guard to be
guessed, is to take the roots in `QQbar` -- which refines rigorously, by
isolating intervals with exact arithmetic behind them -- and coerce into
`ComplexIntervalField(prec)`:

    f.roots(QQbar, multiplicities=False)   # exact algebraic numbers
    ComplexIntervalField(350)(r)           # diameter ~6e-106

Measured on $\psi_3$ of 11a1: 350 bits gives diameters around $6\cdot10^{-106}$
on all four roots, so a hundred stored digits is covered with room to spare,
and the precision can be raised until the width says so rather than tuned.

What the skill says now: prefer `RealBallField`/`ComplexBallField` for
anything transcendental, and `RealIntervalField` around a float is a trap.

What it should say: add the algebraic case. For a root of an exact polynomial,
`QQbar` plus a coercion into an interval field is a genuine enclosure and
supports `rigour: proven`; it is the interval field around a *numerical*
root-finder that is refused, and rightly.

Evidence: 2026-09-19 ideas run, `/tmp/nb/dp7.py` section (F).

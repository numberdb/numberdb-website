# Lessons proposed by the T11 critique run, 2026-09-21

## `search_text` and `search_integer` return the same class with opposite conventions

What happened: checking whether a reader holding one of T11's factorials is
served, the run called `numberdb.search_integer(factorial(n))` and read
`.tables` off the result, because that is what the skill says to do. It got
`[]` for every $n$, including $14!$ and $100!$, which are in the table. The
run was one step from writing "search by number does not reach this table" in
a critique. The hits were the result object itself: `SearchResults` subclasses
`list`, and for a *number* search the matches are its elements, while
`.tables` stays empty. For a *text* search it is the other way round, which is
the case the skill already warns about.

Both wrong accesses return an empty container and raise nothing, and an empty
answer from this database does not read like a mistake -- it reads like
"nobody has seen this number", which is the one answer the whole site exists
to give. That makes this worse than an ordinary API trap.

What the skill says now: one direction only, under "Look at the database
before writing anything" -- "`search_text` returns an object with a `.tables`
list, not a list -- iterating it directly yields nothing and raises nothing,
which reads exactly like an empty corpus."

What it should say: the same sentence, and its converse. `search_text` puts
its answer in `.tables` and is empty as a list. `search_integer`,
`search_real_ball`, `search_polynomial` and the rest of the by-value searches
put their answer *in the list*, as `Result` objects carrying `.table`, and
leave `.tables` empty. So:

    numberdb.search_text('factorial').tables      # tables whose prose matches
    list(numberdb.search_integer(87178291200))    # entries equal to this number

and `len()` is the count for a value search, `len(...tables)` for a text
search. Checking `.total` tells you which one you are holding: it agrees with
the list for a value search.

Evidence, against the live corpus on 2026-09-21:

    >>> r = numberdb.search_integer(87178291200)     # 14!
    >>> len(r), r.total, r.tables
    (2, 2, [])
    >>> list(r)
    [Result('87178291200', table='Values of the Gamma function at rational numbers'),
     Result('87178291200', table='Factorial of natural numbers')]
    >>> t = numberdb.search_text('factorial')
    >>> len(t), len(t.tables)
    (0, 20)

## A table that matches an OEIS b-file exactly has inherited its range, not chosen one

What happened: T11 holds $n!$ for $0 \leq n \leq 100$ and says nothing about
why. Its 101 entries turn out to be A000142's b-file, key for key and digit
for digit, and the b-file stops at 100 because OEIS's editors stopped it
there. The table's own ceilings are elsewhere entirely: the soft block limit
is at $n \approx 550$ and the corpus's 160 KB target at $n \approx 400$. The
range was not a judgement about which factorials anybody meets; it was the
shape of the file the generator was written beside in 2021.

What the skill says now: "Say which range you chose and why in the
completeness note. That sentence is the argument." It does not say where a
range that has no argument usually comes from.

What it should say: when a table's range coincides exactly with an external
source's -- an OEIS b-file, a published table, the length of a data file --
that is worth noticing rather than trusting. The source stopped for its own
reasons, which are usually about its own storage and not about which values
are looked up. Check the range against this table's ceilings before adopting
it, and if it is kept, the completeness note should say so and cite the
source, because "this is where A000142 stops" is at least an argument where
silence is none.

Evidence: T11's `Numbers` compared against
`https://oeis.org/A000142/b000142.txt`, keys equal and values equal on all 101
entries; `agents/critiques/T11-growth.md`, 2026-09-21.

## Extending a table of large exact integers costs search nothing

What happened: weighing whether to extend T11 past $n = 100$, the usual
objection applied -- the skill's warning that a long table buries the common
values, and that a family of small integers "matches everything and tells
nobody anything". Measuring it on the live corpus showed the objection does
not reach this case at all. The number of tables a factorial matches collapses
almost at once: $0! = 1$ is in 98 tables, $5! = 120$ in five, $14!$ in two,
and $50!$ and $100!$ in one. Every value an extension would add is a 160- to
307-digit integer, which can be a spurious hit for nobody.

What the skill says now: the dilution argument, in one direction only -- "a
thousand is a listing of something nobody was looking for, and it makes the
search results worse for everybody by burying the values that are common",
and "values that are a handful of small integers ... match everything".

What it should say: the dilution cost of a range depends on how distinctive
the added values are, and that is measurable before deciding. Search a few of
the values at the current edge of the table and count the tables that answer.
Where the count is one, extending the range costs other tables nothing, and
the argument against it has to come from somewhere else -- whether anybody
meets the value, and what the entries block costs. Where the count is high,
stop, whatever the size limits allow.

Evidence: `numberdb.search_integer(factorial(n))` for
$n = 0, 5, 14, 50, 100$ returned 98, 5, 2, 1 and 1 tables respectively,
2026-09-21.

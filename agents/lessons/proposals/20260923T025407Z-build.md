## Verify an `(answers #N)` marker before putting it in a table

What happened: numberdb-data#191 marked the proposed table of
$\theta_4(0,q)$ as `(answers #128)`. Before adding the requested-link
provenance to the draft, the build read #128 and found that it was the
unrelated "Monomials" request, already closed by other tables. Adding
`Requested in numberdb-data#128` to T426 would have made the table cite a
request that did not ask for it, and letting `queue.py built` see that marker
would have commented on the wrong issue.

What went wrong: the prompt says that `(answers #N)` means somebody asked for
this table, and in the ordinary case it should be trusted enough to preserve
the provenance. This run found a family issue where the marker itself was bad.

What it should say: before adding the "Requested in numberdb-data#N" link, read
the issue named by `(answers #N)`. If it is not the request for this table,
remove or correct the marker in the family issue, report the inconsistency, and
do not put the unrelated request in the table.

## `queue.py built` can tick the wrong sibling when titles differ only in LaTeX

What happened: after T426 was filled, `python3 agents/queue.py built 191 ...`
matched the line for $\theta_3(0,q)$ rather than the intended line for
$\theta_4(0,q)$. The title matcher strips LaTeX before comparing subjects, so
the three theta-constant siblings all reduce to the same words. The command
then closed the family issue because the remaining unchecked lines were marked
as claims. The build had to move T426 to the $\theta_4$ line by hand and reopen
#191.

What went wrong: containment of non-LaTeX words is not enough when sibling
tables are distinguished by a symbol inside math mode.

What it should say: when a family has siblings whose titles differ only inside
LaTeX, inspect the family issue after `queue.py built`. If the wrong line was
ticked, patch the checklist immediately and reopen the family if claimed lines
remain.

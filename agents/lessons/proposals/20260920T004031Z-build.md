## A full-document edit of an empty draft can still be refused when `Numbers: []` is present

What happened: T345 was claimed through `POST /api/tables` with `X-Draft: yes`
and an explicit empty `Numbers: []` block. After the private checks changed the
rigour note, a whole-document `PUT /api/table/T345` with the revised prose and
the same empty `Numbers: []` was refused with "A table needs at least one
entry", even when the request sent `X-Draft: yes`. Filling the draft once
through `/api/table/T345/entries` succeeded, and the same prose edit then
succeeded after it preserved the nonempty `Numbers` block read back from the
draft.

What the skill says now: create the draft before building, with title first and
prose if available, no numbers. An earlier lesson says to include `Numbers: []`
when claiming the draft.

What it should say: treat a prose-only rewrite of an empty API-created draft as
unreliable, even when `Numbers: []` is already present. If prose needs a small
repair after the claim, either wait until the first nonempty entries block has
been submitted, or send the entries and prose together in a full document that
has at least one value. Do not create a second draft.

Evidence: T345 on 2026-09-20. The refused `PUT /api/table/T345` answered HTTP
400, "A table needs at least one entry"; after the first fill wrote 118
entries in revision `f591d90a6490c970ddd02229631f2fbce198dbaaebdaeba8986b561f890b79c2`,
the prose-only rewrite preserving those entries returned revision
`3a66f5e426e87e601a6e39d75cf2eeced05081675eb823417df766038a81e975`.

## `isogenies_prime_degree` for sporadic rational isogenies needs the period-lattice imports

What happened: the T345 generator used named Sage imports and called
`E.isogenies_prime_degree(ell)` for $\ell\in\{5,7,11,13,17,19,37\}$. The
$\ell=11$ path entered Sage's sporadic rational-isogeny code, which constructs
period lattices and real matrices. With only the elliptic-curve constructor and
rings imported, it first failed with `NameError: name 'AA_hash_offset' is not
defined`; after `sage.rings.qqbar._init_qqbar()`, it failed with
`AttributeError: module 'sage.rings.polynomial' has no attribute
'laurent_polynomial_ring'`, and Sage re-raised that internal failure as
`ValueError: 11 is not prime.` Importing
`sage.rings.polynomial.laurent_polynomial_ring` before the call fixed it.

What the skill says now: import `numberdb.sage` first, name the rings, and
expect some Sage machinery to be missing. Existing lessons mention
`period_lattice()` needing `qqbar._init_qqbar()` and real matrices needing the
Laurent-polynomial import, but not that `isogenies_prime_degree` reaches both
of those paths and can report the misleading "not prime" error.

What it should say: under named imports, a generator using
`isogenies_prime_degree` for the sporadic prime degrees should initialise
QQbar and import the Laurent-polynomial ring module before enumerating
isogenies:

```
import sage.rings.polynomial.laurent_polynomial_ring
import sage.rings.qqbar as qqbar
qqbar._init_qqbar()
```

If a prime degree is reported as "not prime", read the traceback above that
message before trusting the exception.

Evidence: T345 on 2026-09-20. The first dry run failed in
`period_lattice()` with `AA_hash_offset` missing; the second failed in
`get_matrix_class` on `laurent_polynomial_ring`; after those two imports,
`agents/table-build/dry_run.py` computed 118 exact entries and the integrity
check reported degree counts `ell=5: 82, ell=7: 26, ell=11: 6, ell=13: 4`.

## Kauffman-to-Jones specialisations can cancel fractional powers before the final polynomial

What happened: the Kauffman generator first checked
$V_K(t)=F_K(-t^{-3/4},t^{1/4}+t^{-1/4})$ by requiring each substituted
monomial to have an integral exponent of $t$. The dry run stopped at $3_1$
with a surviving-looking quarter exponent, although the full sum is the
ordinary Jones polynomial. The fix was to collect coefficients by quarter
exponent first, cancel zero coefficients, and only then require every
remaining exponent to be divisible by $4$.

What the skill says now: check every identity before writing it down, and
when two computations disagree find out why.

What it should say: when a specialisation uses fractional powers, do not
validate integrality term by term. Expand into the common fractional-exponent
lattice, combine like powers, remove zero coefficients, and validate the
surviving expression.

Evidence: `agents/table-build/dry_run.py` on
`generators/kauffman-polynomials-prime-knots/generate.py` first raised
`ArithmeticError: Jones specialisation has nonintegral quarter exponent 6`;
after collecting quarter powers, the dry run computed 479 entries and
`/tmp/check_kauffman_against_t139.py` reported `checked 479 Kauffman Jones
specialisations against T139`.

## Filling an empty draft through `Generator.publish()` may hit the client's empty upsert probe

What happened: T314 was created as an empty prose draft, then the generator
called `generator.publish(...)`. Before sending entries the client checked
writeability by submitting an empty upsert to `/api/table/T314/entries`, and
the API refused it with `A value in these entries cannot be read as a number.
'str' object has no attribute 'items'`. The same direct-fill helper used by
other fresh drafts fixed it: build an `Entries` object, validate every entry
with the client's rigour and precision checks, submit with `upsert=False`,
and then attach the generator files.

What the skill says now: `publish()` writes and needs `NUMBERDB_API_KEY`;
drafts may be created with prose first and filled later.

What it should say: a fresh draft with no `Numbers` section may need the
direct `fill_draft_once` pattern instead of `Generator.publish()`, because
the client's empty writeability probe is itself an entry submission. Keep the
same `_check_rigour`, `_check_precision`, `to_text`, `submit_entries`, and
`attach` calls the client uses.

Evidence: `NUMBERDB_PUBLISH=1 agents/sage.sh
generators/kauffman-polynomials-prime-knots/generate.py` failed on T314 with
the empty-probe error; after adding `fill_draft_once`, it returned `{'tid':
'T314', 'revision': 'eb1e62fdc19f1bba8235f3ef09e53e76258f4fbc0bdb8109919686e62666de32',
'entries': 479, 'files': ['generate.py', 'knotinfo_kauffman_data.py']}`.

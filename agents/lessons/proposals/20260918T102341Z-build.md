## Check proposal formulas against the source before computing

What happened: issue #162 described the Frank test matrix as
$A_{ij}=n-\max(i,j)$, with zero entries below the subdiagonal. The Test
Matrix Toolbox source that the family cites builds the unreflected Frank
matrix with the row vector `n:-1:1`, so in 1-based indices the finite entries
are $A_{ij}=n-\max(i,j)+1$. The missing $+1$ changes every value in that
family. The generator used the source formula, and the exact determinant
check then gave the expected determinant $1$ for every order in the table.

What the skill says now: read the family issue first and settle the
definition before computing.

What it should say: the proposal is not a source. If it gives an entry-wise
formula and also names a primary source, check the formula against the source
before using it, especially for 0-based versus 1-based indexing. Record the
source's convention in the table prose, and use a known structural fact as a
control where one is available.

Evidence: `https://github.com/carandraug/testmatrix/blob/master/Test%20Matrix%20Toolbox/gallery.m`,
the `frank` branch assigns `p = n:-1:1` and constructs the upper Hessenberg
matrix from `p`; `/tmp/condition_independent_checks_repo.py` reported
`frank determinants ok`, 2026-09-18.

## A Sage characteristic-polynomial root list can be the wrong control

What happened: the first condition-number generator took the roots of
`(A.transpose()*A).charpoly()` in `AA`. For the Hilbert matrix of order 18,
that path returned only 17 positive roots, even though the exact determinant
is nonzero. The control had become the thing failing. Calling
`B.eigenvalues()` on the exact rational matrix returned all 18 eigenvalues,
and the generator now refuses any family/order where the number of positive
squared singular values is not exactly the order.

What the skill says now: expect some Sage machinery to be missing or
uninitialised, and write the arithmetic out where necessary.

What it should say: for spectral data, count the roots or eigenvalues before
trusting them. If an exact full-rank matrix loses an eigenvalue in one Sage
path, try an independent Sage path and a structural control, rather than
filling the missing value or reducing the range.

Evidence: the failing scratch run on 2026-09-18 raised
`hilbert(18) has 17 positive squared singular values, not 18`; the checked-in
generator uses `B.eigenvalues()` and the dry run reports 351 entries with no
exactness complaints.

## Do not try to rationalise every algebraic real

What happened: several small condition numbers are exactly rational, such as
the condition numbers equal to $1$, $2$, $3$ or $5$ in small matrix orders. A
blanket `QQ(exact_value)` attempt on every algebraic condition number made
the dry run spend a long time trying to prove irrational values rational.
The generator now uses a cheap numerical filter first, and only asks Sage for
a rational coercion when the ball is very close to a small integer.

What the skill says now: an exactly rational value should be written exactly,
and a run of zeros is evidence, not proof.

What it should say: if exact rationalisation is expensive, use it as a
targeted proof step rather than as a scan over the whole family. A cheap
numeric filter may identify candidates, but the stored exact value still
needs a mathematical or exact-algebraic argument before it replaces a ball.

Evidence: the first exact-in-disguise dry run reported integer-looking
values; the checked-in generator's filtered coercion passes
`agents/table-build/dry_run.py` with `exact-in-disguise: clean`.

## A parameter value containing a comma gives an entry an address other rows share

What happened: T263 (Hall polynomials $g^\lambda_{\mu\nu}(q)$) has three
parameters, each a partition written `2,1,1`. An entry's address is its
parameter values joined by commas (`flatten.identity_of`), so the row
$\lambda=(2,1)$, $\mu=(1)$, $\nu=(1,1)$ and the row $\lambda=(2,1)$,
$\mu=(1,1)$, $\nu=(1)$ both have the address `2,1,1,1,1`. Of the 1197 entries,
133 addresses belong to two or three rows. The rendered page gives both rows
the same HTML `id`, so a link to either scrolls to whichever comes first.
`?entry=` reports the address as found. The named form does not help: the
parser splits `lambda=2,1,mu=1,nu=1,1` on commas, finds a part with no `=`, and
drops back to the positional form, which does not match. T259 has two partition
parameters and no collisions, but only because $|\lambda|=|\mu|$ fixes where
the split falls. Its named citations fail in the same way.

What the skill says now: "The address after the `#` is the entry's identity --
its parameter values, comma separated". It says nothing about values that
contain commas.

What it should say: a parameter value is part of an address that is joined
with commas. So a value containing a comma is safe only if its first parameter
alone decides where each value ends. To be sure, check that the joined
identities are distinct before creating the table: `len(set(ids)) ==
len(ids)`. A partition or a tuple should be written so that its boundaries show
without commas, for example `(2,1)` in parentheses. Or it can be written as a
word with no commas in it.

Evidence: `GET /api/table?id=T263`, 2026-09-16; joining the three keys of every
entry gave 133 identities that more than one row shares. The `/preview`
rendering of the $\lambda=(3,1)$ rows shows `id="3,1,2,1,1"` on both
$(\mu,\nu)=((2),(1,1))$ and $((2,1),(1))$.

## Hall–Littlewood multiplication needs the same `laurent_polynomial_ring` import as a real matrix

What happened: T263's `Programs` snippet uses named imports and computes
`P([2]) * P([1])` in `SymmetricFunctions(QQ['t'].fraction_field())
.hall_littlewood().P()`. After `import numberdb.sage` it raises
`AttributeError: module 'sage.rings.polynomial' has no attribute
'laurent_polynomial_ring'` from `get_matrix_class`, because the basis change
builds a matrix. The same code with `import
sage.rings.polynomial.laurent_polynomial_ring` added, or under `from sage.all
import *`, prints `q`. The generator already carried that import. The snippet
printed on the page did not.

What the skill says now: it names root finding, `RealBall.str` and
`QQ('1.25')` as things the named imports do not bring. There is a pending
proposal (20260912T223331Z-ideas) that adds matrices over `RealField`.

What it should say: widen that proposal. Any code that builds a matrix over a
ring Sage has to classify fails under named imports until
`sage.rings.polynomial.laurent_polynomial_ring` is imported. That includes
symmetric-function basis changes, which build matrices inside. The skill should
also say to run the `Programs` snippet itself under named imports, and not only
the generator, since the snippet is what a reader copies.

Evidence: `agents/sage.sh /tmp/T263_prog.py` gave the traceback above;
`/tmp/T263_prog2.py`, the same file with that one import added, and
`/tmp/T263_prog3.py`, which uses `sage.all`, both printed `q`. 2026-09-16.

## Parse API rational keys without `QQ(text)` under named Sage imports
What happened: a repair check for T30 read `/api/table?id=T30` and tried to turn the `Numbers` keys such as `-5/2` into Sage rationals with `QQ(k)`. Under the named-import setup recommended for generators, Sage raised `AttributeError: module 'sage.rings' has no attribute 'real_mpfr'` before any table check ran. Splitting `a/b` and building `QQ(int(a)) / QQ(int(b))` avoided the parser and let the check compare the stored 39 values with the intended finite box.

What the skill says now: it says named imports do not bring everything, and specifically that `QQ('1.25')` is not how to build a rational from a decimal string.

What it should say: the same warning applies to rational strings read from the API, not only to decimal strings. When parsing entry keys such as `a/b` inside a named-import Sage script, split the numerator and denominator and construct the rational from integers, or use a parser that is known to initialise the required Sage modules.

Evidence: `/tmp/t30_check.py`, 2026-09-21. The first run under `agents/sage.sh /tmp/t30_check.py /tmp/T30-live.json` failed at `QQ(k)` for the stored keys with `AttributeError: module 'sage.rings' has no attribute 'real_mpfr'`; the split-parser version reported `stored entries 39`, `box entries 39`, `missing from stored []`, and `extra in stored []`.

## The "does not exist" reply is HTTP **200**, so a sweep that classifies on the status code calls every draft published

**What happened.** I needed to know whether T441 and T443 were still
unpublished. The pending proposal gives the method -- ask without a key, ask
with it -- and gives this as the remedy for the throttle trap it describes:

    if resp.status_code == 429: raise   # do not classify this
    published = resp.status_code == 200

The first line is right. The second is exactly backwards. Asking anonymously:

    GET /api/table?id=T443   ->  200  {"error": "Table with id 'T443' does not exist."}
    GET /api/table?id=T99999 ->  200  {"error": "Table with id 'T99999' does not exist."}
    GET /api/table?id=T444   ->  200  {"Title": "Cumulants $\\kappa_n$ of the ...

T443 is an unpublished draft, T99999 is nothing at all, T444 is a published
table, and **all three are 200.** A sweep written to that rule reports every
draft and every nonexistent id as published, and it reports it confidently,
because `requests` and `urllib` both raise on 4xx and neither raises here.

It is not an accident of one endpoint. `numberdb_app/api.py` answers an unknown
id at line 392 and an unreadable draft at line 415 with `JsonResponse({'error':
...}, safe=True)` -- no `status=`, so Django's default 200 -- and the two
strings are byte-identical by design, since a draft must be indistinguishable
from a table that was never created. The 429 from `numberdb_app/throttle.py:194`
*is* a real status, and it is the only non-200 an anonymous read of this
endpoint normally produces.

So the status code and the body answer two different questions, and a sweep
needs both, in this order:

    if resp.status_code != 200:      # 429 throttle, 5xx: not an answer
        raise
    doc = resp.json()
    visible = 'error' not in doc     # published, or a draft your key may see

Used that way the test works, and it worked here: T441 and T443 returned their
documents to the zeta3 key -- 903 entries under three Dyson indices, and 1001 --
and `{"error": ... does not exist}` anonymously, so both are still drafts.

**Why the original proposal got it backwards, which is the part worth keeping.**
Its author had just been burned by the opposite mistake -- a 31-id anonymous
sweep whose 429 bodies, being JSON objects with an `error` key, read as "this
is a draft" -- and the natural repair for *body lied to me* is *trust the
status instead*. On this API neither half is sufficient alone. The body cannot
tell a throttle from an absence; the status cannot tell an absence from a
document. A contributor who has just published a table and wants to know
whether it went through will write one of the two one-liners, and a
contributor who built a family of six and sweeps for all of them will write the
other.

**What the skill says now.** Nothing: `SKILL.md` has no occurrence of
"anonymous", "status code", "404" or "rate limit", and nothing anywhere
describes reading a table back to see whether it is published.

**What it should say**, if the companion proposal's paragraph is promoted, with
this correction folded in:

> `GET /api/table?id=<tid>` answers **HTTP 200 whatever the answer is**: the
> document if you may see the table, and `{"error": "Table with id '<tid>' does
> not exist."}` if you may not -- the same sentence for a draft that is not
> yours and for a number nobody has used. Do not test for a 404; there isn't
> one. Ask anonymously and then with your key: present to your key and absent
> anonymously is the published/unpublished test, and swept over a range of
> T-numbers it is the nearest thing there is to a list of your drafts.
>
> Check the status code **first and separately**: a 429 is a refusal, not an
> answer, and its body is also a JSON object with an `error` key. `status !=
> 200` means *stop, you have learned nothing about this id*; `'error' in body`
> means *not visible to this caller*. A script that folds the two together
> reports confident nonsense in one direction or the other.

**Why it belongs in the skill and not the environment notes.** Nothing here is
about this deployment. It is the published API's behaviour, the same for
anybody with `curl`, and it is met on the first thing a contributor does after
uploading a table: look to see whether it is there.

# Lessons proposed by the T435 critique, 2026-09-23

Format and scope as `agents/lessons/PROPOSALS.md`. Nothing here is in force.

Both are true for a contributor with a laptop and `pip install numberdb`:
one is a table-shape decision the skill half-covers and the corpus decides
consistently, and one is a measurement of how search treats a repeated value,
which changes what the skill's rule about small integers actually costs.

---

## "Parts of one object" is the right answer only when the parts are not also the key

What happened: T435 (Markov triples) stores the triple as three parameters
$m_1\leq m_2\leq m_3$, and then stores the same three integers as the three
values under a `part` parameter. `audit_table` asked the parameter-is-three-
names question, the author answered it in the definition -- "the components
$m_1$, $m_2$ and $m_3$ are the three parts of one Markov triple" -- and that
answer is the one the skill blesses. The page is still wrong to read:

    $m_1$, $m_2$, $m_3$        $m_i$
    1, 5, 13     $m_1$:        1
    1, 5, 13     $m_2$:        5
    1, 5, 13     $m_3$:        13

456 rows carrying 152 distinct numbers, each row restating a third of its own
label, and a value header `$m_i$` whose index $i$ appears nowhere else in the
document -- the same tell as the fallback word `value`, one step subtler.

The corpus decides this the other way everywhere it has met it, and the
skill's own example is one of those places. T62 and T63, the $abc$-triples
the skill cites for "a triple is the thing", key their entries by the
*quality* $q$ and store $a$, $b$, $c$ as values: a row reads
`1.629911  $a$: 2`, and the value is a number the label does not already
carry. T435's three siblings do the same with the same index: T428 keys by
the Markov number $m$ and stores $L_m$, T429 keys by the triple and stores
the binary quadratic form, T430 keys by the triple and stores the quadratic
irrational. Only T435 keys by the numbers it stores.

What the skill says now: §4 gives three good answers to the audit's question,
the first being "parts of one object -- the $abc$-triples store $a$, $b$ and
$c$ because a triple is the thing ... A reader holding one part wants the
others beside it." It says nothing about where those parts sit. It does have
the neighbouring rule, about labels: "A label that repeats what the block
heading above it already says -- `(B_n)` on every row of a table already
grouped by $n$ -- is noise at the same place." The case here is the same
noise one column over, and worse, because it is the value rather than the
label.

What it should say, beside the "parts of one object" bullet: the parts are
values, and something else is the key. If the parameters and the values are
the same numbers, every row prints one number twice and the table has as many
rows as parts rather than as many rows as objects. Ask what indexes the
object that is *not* one of its parts -- the quality of an $abc$-triple, the
degree, the discriminant, the order -- and key on that. Where nothing else
exists, key on all but one part and store the last: $(m_1,m_2)$ with value
$m_3$ is 152 rows where $(m_1,m_2,m_3)$ with three parts is 456, and it loses
no searchable number, because every $m_1$ and $m_2$ in that table is some
other row's $m_3$. Check injectivity before choosing it: in T435 exactly one
key collides, $(1,1)$, shared by $(1,1,1)$ and $(1,1,2)$.

And say when the decision has to be taken, because that is what makes it
urgent rather than tidy: the parameter order freezes at publication and
citations resolve on it, so this is a draft-stage question with no
draft-stage prompt for it. The audit asks whether the table is two tables; it
does not ask whether the value column is a copy of the parameter columns.
A test for that is cheap and mechanical: a table whose entry values, read as
strings, are a subset of its own parameter values.

Evidence: 2026-09-23, T435 at 152 triples. `GET /api/table?id=T435` gives
456 value cells and 152 distinct integers, 1 appearing in 33 of them, 5 in
20, 2 in 16. `GET /api/table?id=T62` gives `Parameters: {q, v}` with
`v: {a, b, c}` and 241 keys. The rendered rows are from
`curl -G --data-urlencode "table@piece.yaml" https://numberdb.org/preview`.

## A value repeated inside one table costs one search result, not many

What happened: while weighing the finding above I assumed that storing 33
copies of the integer 1 would put 33 rows of one table in front of anybody
searching for 1, which is how the skill's rule about small integers reads.
It does not. `search.one_per_table` (`numberdb_app/search.py:134`) returns
the best row from each table and attaches `occurrences_in_table`, so the hit
list is one row per table and "and 32 more here" is shown as information --
its docstring says a value occurring many times in one table "would otherwise
fill the page with one table's rows and crowd out every other answer, which
is the opposite of what the reader asked."

Measured: `GET /api/search?expression=1` returns 98 results, exactly one per
table, and `$abc$-triples of high quality` is one of them although it holds
the integer 1 in ten cells. `expression=2` returns 47, same shape.

What the skill says now: "values that are a handful of small integers --
class numbers are mostly 1, 2, 3 -- match everything and tell nobody anything,
and putting them in a table makes search by number worse for everyone."

What it should say: the same thing, with the cost stated correctly, because
an author who believes the cost is dozens of rows will make the wrong
trade-off in both directions. A table of small integers adds *one* row to the
result list for each of them -- the harm is a page of table names none of
which identifies the number, not a page flooded by one table. The corollary
is the useful half: repeating a value inside one table is cheap in search and
expensive on the page, so decide that question by reading the page.

Evidence: 2026-09-23. `numberdb_app/search.py:134` (`one_per_table`) and
`api.py:585`, which passes `per_table=True` on every number-search path.
`GET /api/search?expression=1` -> 98 results, no table twice.

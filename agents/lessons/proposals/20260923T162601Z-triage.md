# Lessons proposed by run 20260923T162601Z (triage)

## An API key cannot list the drafts it holds: record every table id at creation

What happened: asked to check what a failed build had left behind, I went for
the drafts held by this key and found there is no way to ask. Every candidate,
with a valid `Authorization: Bearer <key>`:

    GET /api/draft            404   (HTML "Not found" page)
    GET /api/drafts           404
    GET /api/tables           405   {"error": "Use POST."}
    GET /api/table            200   {"error": "No id or url given."}
    GET /tables               200   published tables only
    GET /drafts               302 -> /accounts/login/?next=/drafts

The last two are the traps. `/tables` is the public listing and filters
`published=True`, so your own drafts are absent from it even with your key on
the request — it does not refuse, it just quietly does not include them.

And `/drafts`, the page the skill names twice — "`/drafts` lists what is being
made right now", "the button on `/drafts`" — is **session-authenticated, not
key-authenticated**. An API key does not sign you in to it. It does not answer
401 or 403: it redirects to the sign-in page, so a client that follows
redirects (`requests` and `urllib` both do, by default) gets **HTTP 200 and a
14 KB "Sign in - NumberDB" page**. A script that checks `resp.status_code ==
200`, or that counts draft rows in the HTML, sees a success and zero drafts,
and concludes it holds none. That is the same shape as the `/api/search`
trap already in the skill — a 200 that means "you asked wrongly" rather than
"the answer is empty".

So the only way to reach a draft is `GET /api/table?id=T<n>`, and only its
owner may see it. **You have to already know the id.** If you lose it — a run
dies between `POST /api/tables` and writing the id down, which is exactly what
a half-finished build leaves behind — the draft is unreachable and
unenumerable, and since only publication frees a slot and a contributor cannot
publish, it consumes one of your slots permanently.

What the skill says now: that you may hold a small number of drafts at once,
and that `/drafts` is where you see what is being made and where the offer
button is. Both are true **in a browser, signed in**. Nothing says the page is
unreachable with a key, and nothing tells you to keep the id.

What it should say: at step 1, when `POST /api/tables` returns, **record the
table id immediately — it is the only handle you will ever have on that
draft.** There is no endpoint that lists the drafts an API key holds:
`/api/draft` and `/api/drafts` do not exist, `GET /api/tables` is POST-only,
`/tables` shows published tables only, and `/drafts` needs a browser session
and answers a key with a redirect to the login page that reads as 200. If you
are driving the API from a script, keep your own list of ids; the server will
not give it back to you. How many drafts you hold is visible only in the
refusal you get when you exceed the ceiling.

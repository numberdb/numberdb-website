# Lessons from the ideation run of 2026-09-23T0742Z (Feynman periods, multiple zeta values)

Four things this run met that the skill does not cover. All four are true for
somebody with a laptop, Sage and no part of this deployment.

---

## Sage's `Multizeta` takes the arguments in the opposite order to the corpus, and the wrong order returns a plausible number

What happened: the run checked the Panzer-Schnetz census of $\phi^4$ periods
against Sage. The census writes $\zeta[5,3]$ and the corpus (T53, T54) defines
$\zeta(s_1,\ldots,s_k) = \sum_{n_1>n_2>\cdots>n_k>0} n_1^{-s_1}\cdots
n_k^{-s_k}$ with $s_1 \ge 2$. Sage's `Multizeta` uses the *other* convention,
where the last argument is the one that must be at least 2. So the corpus's
$\zeta(s_1,\ldots,s_k)$ is `Multizeta(s_k,...,s_1)`.

The failure is silent in the only direction that matters. Evaluating the
published closed form of the six-loop period $P_{6,3}$,
$\frac{432}{5}\zeta(5,3) - \frac{58}{2625}\pi^8 + 252\zeta(3)\zeta(5)$:

    Multizeta(5,3)  ->  122.1358041289149806685226633571694759775   wrong
    Multizeta(3,5)  ->  107.7110248410231180583722503561263587604   right,
                        to all 100 digits of the published value

Nothing raises, nothing looks odd, and 122.13 is as plausible a period as
107.71. The error only announces itself in the one case where the reversed
argument list ends in 1: `Multizeta(2,1,1,1)` raises `ValueError: divergent
zeta value`, while `Multizeta(1,1,1,2)` is the corpus's $\zeta(2,1,1,1)$ and
equals $\zeta(5) = 1.0369277551\ldots$ (Euler).

What the skill says now: nothing about `Multizeta`. It warns generally that a
normalisation has to be written down before computing, and gives
`elliptic_k`'s parameter $m$ as the example of a convention that differs from
the second entry on.

What it should say: add `Multizeta` to that list. The corpus's multiple zeta
convention is the reverse of Sage's, T53 and T54 already encode the reversal in
their `Programs` block, and a table built from the arguments as written will be
wrong from the first entry with two distinct exponents and right on every
symmetric one, which is the hardest kind of wrong to notice.

Evidence: `agents/sage.sh` on the check script of 2026-09-23; the two numbers
above against
`https://arxiv.org/src/1603.04289/anc/Periods`, record `Period[6,3]`.

## `len(table['Numbers'])` counts the first parameter's values, not the entries

What happened: the run read T54, *Multiple zeta values of length 3*, to see how
large it was, and printed `len(d['Numbers'])`. It printed **9**. T54 actually
holds **900** entries: `Numbers` is nested one dict per parameter, so its
length is the number of distinct values of the *first* parameter ($s_1$ from 2
to 10). T53 likewise reads as 99 and holds 990.

Nine entries and nine hundred lead to opposite decisions: this run nearly
proposed "extend the tiny length-3 table" on the strength of it.

What the skill says now: "`numberdb.table(...)` returns the whole document
with capitalised keys (`Title`, `Definition`, `Numbers`), and `Numbers` is
every entry -- printing it is megabytes." True, and it reads as though
`Numbers` were a flat list of entries.

What it should say: `Numbers` is nested by parameter, so `len` is the count of
the first parameter's values and never the entry count. To count entries, walk
it:

    def entries(numbers):
        if isinstance(numbers, dict):
            for value in numbers.values():
                yield from entries(value)
        else:
            yield numbers

The same nesting is why an entry's address is its parameter values comma
separated -- the skill already says that about `HREF{slug#a,b,c}`, and the two
facts are the same fact.

Evidence: `numberdb.table('T54')`, 2026-09-23. `len` = 9; the walk gives 900,
which is $9 \times 10 \times 10$ as the table's own `Programs` block describes.

## A ball never overlaps a published value quoted to a hundred digits, however right it is

What happened: the run recomputed the census periods in
`RealBallField(420)` and tested them with
`ball.overlaps(RBF(published_string))`. Every single one came back **False**,
including $6\zeta(3)$ against its own published digits.

The reason is not an error in either number. The published value is truncated
at 100 digits, so it differs from the true value by up to $10^{-98}$ here,
while the computed ball has radius $5\times10^{-120}$. Two intervals, one of
width zero sitting $10^{-98}$ away from a ball of width $10^{-120}$, do not
overlap. `overlaps` is answering the question it was asked, and it is the wrong
question.

Replacing it with a relative comparison against the precision the source
actually claims gave the real answer immediately: 834 of the 851 periods agree
to every printed digit, worst relative disagreement $4.6\times10^{-100}$.

What the skill says now: it tells you to check new values against something
independent, and it tells you a decimal literal in the database *is* an
interval whose last digit may be off by one. It does not say how to compare
against a published table, which is the commonest independent check there is.

What it should say: when the independent value is a printed decimal, compare on
the source's precision, not yours. Either widen the reference by one unit in
its last printed place before testing containment, or test
`abs(computed - published) / abs(published) < 10^(1-d)` for $d$ printed
digits. A ball comparison against a truncated decimal fails for every correct
value, which reads exactly like a wrong convention and sends a run looking for
a bug that is not there.

Evidence: 2026-09-23, `RBF(420)` against
`Period[3,1] = 7.212341...` (100 digits) from the arXiv ancillary file;
`overlaps` False, relative difference $3.2\times10^{-101}$.

## An arXiv paper's ancillary files are where a family's values already are, at full precision

What happened: the run needed values for a family nobody has tabulated on a
website. They turned out to exist, computed by the authors, in machine-readable
form:

    https://arxiv.org/abs/<id>            the abstract page lists them
    https://arxiv.org/src/<id>/anc        the listing of ancillary files
    https://arxiv.org/src/<id>/anc/<name> the file itself

For arXiv:1603.04289 that is 5.7 MB holding 10119 graphs, each with an edge
list, an exact multiple-zeta expression, and a numerical value **to 100
digits** -- the house precision, already there. The paper's own "Data" section
documents the field order, which is what makes the file usable rather than
guessable.

Two things follow for a table built this way. First, parse and recompute rather
than transcribe: the file's numerics and a recomputation from the file's exact
expressions are two independent computations, and comparing them is a real
check that costs one script. Second, when re-evaluating a published expression
in Python, wrap the integer literals: `432/5*zeta` is float division and throws
away every digit past the 53rd bit before the first multiplication. The skill
warns about this for `factorial(n) / k`; it bites just as hard on a
coefficient copied out of a paper, and a regex that rewrites every integer
literal to `QQ(n)` before `eval` is the shortest fix.

What the skill says now: OEIS, Wikipedia, MathWorld, DLMF and the LMFDB are
named as places to look and to link to. Ancillary files are not mentioned.

What it should say: before concluding that a family cannot be checked, look for
the paper's ancillary files; for data-heavy subjects they are usually the
source the review articles are quoting, and they carry more digits than the
article prints.

Evidence: 2026-09-23. `curl https://arxiv.org/src/1603.04289/anc` lists
`Periods` (5.667 MB) and `PeriodsNonPhi4` (434 KB); section 6 of the paper
gives the format; 834 of 851 values reproduced from them in three seconds.

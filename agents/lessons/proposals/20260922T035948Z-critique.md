# Lessons proposed by the T6 critique run, 2026-09-22

Run `20260922T035948Z`, stage three, reading T6 "Diagonal Ramsey numbers".
Both of these are about a table that holds a quantity known exactly in a few
small cases and otherwise only between two published bounds. The corpus has
three such tables — T5, T6, T151 — and they disagree with each other in both
of the ways below, so a contributor meeting the situation for the first time
has three examples and no rule.

Nothing here is in force. Format follows `agents/lessons/PROPOSALS.md`.

## A value known exactly is written as an integer even where its neighbours are intervals

What happened: T6 stores $R(n,n)$, which is known exactly for $n\leq4$ and
only between a published lower and upper bound for $5\leq n\leq10$. All ten
rows are written as intervals, so $R(4,4)=18$ is stored as `[18, 18]` and
$R(1,1)=1$ as `[1, 1]`. The page prints `[18, 18]`, and so does the answer to
a search for the integer:

    search_integer(18)  ->  Result('[18, 18]', table='Diagonal Ramsey numbers')
                            Result('18',       table='Generalized Bernoulli numbers')

Somebody who typed 18 is told a range where the fact is a number, with no note
beside it, and the neighbouring hit from a table that writes its integers as
integers reads `18`. The table's own `rigour details` says "Rows
$1\leq n\leq4$ are exact values", so two fields of one document disagree about
four of its ten rows.

Nobody notices, for two reasons. The zero-width interval *is* indexed — the
row is found by a search for 18, so nothing is broken in a way a check would
report — and writing the whole column one way looks tidier than writing it two
ways. T151, the same mixture of known and unknown, made the other choice and
writes `2`, `6`, `12`, `24`, `240` beside `[40, 44]`, `[72, 77]`,
`[126, 134]`.

What the skill says now: §5, "A string with no `.` and no `e` is an **exact
integer**, not an approximation", and §2, "Decide exactness from the
definition, never from the digits". Both are about a whole table. Neither
addresses a table where some rows are exact and some are not, and the
tidy-looking choice there is the wrong one.

What it should say: write each row in the strongest form that is true of *that
row*. On a table where some values are known and others only bounded, the
known ones are integers and the bounded ones are intervals, and the column
looks ragged because the knowledge is. A zero-width interval is accepted and
searchable, so this is not a findability bug and no check will catch it; it is
displayed verbatim on the page and in every search result, where it says a
number is unknown when it is known.

Evidence: T6's `Numbers` block, ten rows, four of them `[1, 1]`, `[2, 2]`,
`[6, 6]`, `[18, 18]`, unchanged from the 2021 import through the reviewed
revision of 2026-09-21 that rewrote the other six endpoints and changed
`rigour` on the grounds that four rows are exact. T151's `Numbers` block for
the contrast. `search_integer` output above, run through `agents/sage.sh`
against the live corpus, 2026-09-22.

## `rigour` is the weakest row's level, and `proven` is the word for an interval of ignorance

What happened: the rigour scale has no entry for a value that was not computed
at all — an interval whose lower endpoint is somebody's construction and whose
upper endpoint is somebody's proof. `proven` is defined as "interval or ball
arithmetic throughout, so the digits follow from the width of the result",
which is not what happened; `measured` is for experimental values; `exact` is
for an integer, rational or polynomial, which an interval is not. The three
tables in this corpus of that shape answer differently:

    T5    exponent of matrix multiplication   one interval           proven
    T6    diagonal Ramsey numbers             4 exact + 6 intervals  proven
    T151  kissing numbers                     6 exact + 18 intervals exact

T6 said `exact` too until 2026-09-21, with a `rigour details` reading "An
exact value -- an integer, a rational or a polynomial -- so there is no
precision to choose and nothing to be wrong about", which was false of six of
its ten rows. That revision changed it to `proven` and was reviewed. T151 is
where T6 was.

What the skill says now: §7, "One value per table, in `rigour`. The first five
are ordered, weakest last." That orders the words and does not say which word
a table with mixed rows takes, and a reader who has four exact rows and six
intervals can read "one value per table" as licence for the commonest rather
than the weakest.

What it should say: two sentences.

- A table's `rigour` is its **weakest** row's level, not its commonest. Four
  exact rows do not make a table `exact` if one row is an interval.
- An interval whose endpoints are published theorems is `proven`: the
  enclosure is proved, even though no arithmetic produced it. Then say so in
  `rigour details`, in both halves, because a wide interval otherwise reads as
  a sloppy computation. T5 opens "Not a computed value: the entry is the
  interval between the trivial lower bound of 2 and the 2026 upper bound in
  CITE{...}", and T6 closes "The width is ignorance about the exact Ramsey
  number, not numerical error". A table of this shape wants both sentences:
  what produced the endpoints, and what the width means.

Evidence: the three tables' `Data properties` as of 2026-09-22;
`/revisions/T6`, the diff of 2026-08-14 → 2026-09-21, which shows the
`exact` → `proven` change and the note it replaced.

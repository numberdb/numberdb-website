## arb's theta functions are `ComplexBall.jacobi_theta(tau)`, and Sage misdirects you to `modular_eta`

What happened: a proposal for the Jacobi theta constants needed
$\theta_2,\theta_3,\theta_4$ in ball arithmetic. The obvious name, taken from
arb's own C function `acb_modular_theta`, does not exist in Sage:

    AttributeError: 'sage.rings.complex_arb.ComplexBall' object has no
    attribute 'modular_theta'. Did you mean: 'modular_eta'?

The suggestion is the dangerous part. `modular_eta` exists, takes the same
argument, returns a complex ball, and is the Dedekind $\eta$ function, so a
script that follows the suggestion runs to completion and produces a
plausible table of wrong numbers. The method wanted is `jacobi_theta`:

    CBF(z).jacobi_theta(tau)     # -> (theta1, theta2, theta3, theta4) at (z, tau)

Two things about it that cost a run: it returns **all four at once**, so a
family of theta tables is one call per row rather than four; and it takes
$\tau$ in the upper half plane, not the nome. A table indexed by a real nome
$q\in(0,1)$ must convert, `tau = CBF(q).log() / (CBF(0,1) * CBF.pi())`, and a
sign error there is silent -- Jacobi's identity
$\theta_3^4=\theta_2^4+\theta_4^4$ is the cheap check that catches it.

arb has no Jacobi elliptic functions at all, despite having thirteen
`elliptic_*` methods (`elliptic_k`, `elliptic_p`, `elliptic_invariants`,
`elliptic_roots`, `elliptic_sigma`, `elliptic_zeta`, and the Carlson forms).
$\operatorname{sn}$, $\operatorname{cn}$, $\operatorname{dn}$ have to be built
from `jacobi_theta` by the standard representation, which is four lines and
stays `proven`.

What the skill says now: it lists what arb implements -- "`elliptic_k`,
`barnes_g`, `zeta`, `zetaderiv`, `agm`, `airy_ai`, `bessel_J`, Hurwitz
`zeta(s, a)`, `sin_integral`" -- and does not mention theta.

What it should say: add `jacobi_theta` to that list, noting it returns the
four theta functions as a tuple and takes $\tau$ rather than the nome, and
that arb has no Jacobi elliptic functions, so `sn`/`cn`/`dn` come from the
theta quotients. Worth a sentence more generally: when Sage suggests a nearby
attribute name, the suggestion is spelling advice and not mathematics, and
`modular_eta` for `modular_theta` is the case where taking it silently
succeeds.

Evidence: Sage 10.9 under `agents/sage.sh`, `/tmp/ideas1723/check.py`. After
the rename, $\theta_3(0,e^{-\pi})$ agreed with $\pi^{1/4}/\Gamma(3/4) =
1.08643481121330801457531612151$ within a ball of radius below $10^{-95}$,
and fifteen sn/cn/dn values built from `jacobi_theta` agreed with mpmath's
`ellipfun` to 70 digits.

## `RealNumber.str(25)` prints in base 25, not to 25 digits

What happened: a check script printed ball midpoints with `.mid().str(20)` to
compare them against mpmath, and got

    1.c69i5jja0187ih616jbhaggaha2i07g6cd2632

which looks enough like a decimal -- leading `1.`, digits, a few letters --
that it was read as one for two runs. The comparison then failed with
`ValueError: invalid digits` from `mpmath.mpf`, which is a confusing error for
what is actually a base-20 numeral. The positional argument of
`RealNumber.str` is the **base**. What was meant is

    ball.real().mid().str(base=10, digits=20)     # 1.6162393746095136580

The failure mode that matters is the one where it does not raise: a run that
writes such a string into a table, or into a report, has written a base-20
numeral where a reader will see a decimal, and for a value below 10 with no
letter among its first digits there is nothing to notice.

What the skill says now: nothing about `str`. It mentions `RealBall.str` only
in the list of things the named ring imports do not bring.

What it should say: `RealNumber.str(n)` takes a base; ask for digits by
keyword, `str(base=10, digits=n)`. A proposal or a table that quotes digits
should quote them from a `base=10` call, and a comparison that raises
`invalid digits` in mpmath or `ValueError` in `float()` is usually this and
not a precision problem.

Evidence: Sage 10.9, `/tmp/ideas1723/check2.py`. `.str(20)` gave
`1.c69i5jja0187ih616jbhaggaha2i07g6cd2632`; `.str(base=10, digits=20)` gave
`1.6162393746095136580`, which mpmath's `jtheta(3, 0, 0.3)` matched to every
digit compared.

## The public API rate-limits, and a loop that skips exceptions turns that into a quiet wrong answer

What happened: the corpus was walked once with `numberdb.table('T%d')` for
$n$ up to 430, which worked -- 413 tables. A second walk in the same session,
to count tags, stopped answering after about fifty tables. The loop was
written the usual way,

    try: d = numberdb.table('T%d' % n)
    except Exception: continue

so it printed a tag census with no error and no gap: 46 distinct tags, with
`polynomial` absent entirely and `elliptic curves` on 4 tables. The true
figures from the first walk are 69 tags, `polynomial` on 96 tables and
`elliptic curves` on 43. Nothing in the output said it was the answer for
T1–T52.

This is the `already_here` lesson that is already in `screen.py` -- "a failed
question and an empty answer must not look the same" -- appearing one level
up, in an ordinary loop over the corpus rather than in a search helper. The
cause is the same and the fix is the same: count the failures and print the
count, or do not catch.

What the skill says now: three gotchas about `search_text` and `table`, none
of them about rate limiting, and nothing about walking the corpus at all
beyond "there is no call listing the whole corpus; to see everything you walk
the T-numbers".

What it should say: add to that sentence that the walk is rate-limited, so
anything computed from it should be computed once and kept; and that a loop
over T-numbers must report how many calls failed, because a skipped table and
an absent table are indistinguishable in the result and the second walk is the
one that silently returns a third of the corpus.

Evidence: 2026-09-22. First walk, `missing count 1`, `max present 339`, then a
second pass to 430 that found the rest -- 413 tables, T75 absent. The tag walk
minutes later returned 46 tags whose counts match T1–T52 exactly (`abundant`
is T42, `axiom of choice` is T41, `p-adic` 7 is T44–T52), and reported no
error.

## Two members of one family can agree to the stored precision; measure before choosing the range

What happened: a batch proposed $\theta_2(0,q)$ and $\theta_3(0,q)$ as two
tables over the same grid of nomes. They are different functions with
different series, and over the obvious range $0<q<1$ they are also, over part
of it, the same stored number:

| $q$ | $(\theta_3-\theta_2)/\theta_3$ |
|---|---|
| 0.5 | $2.6\times10^{-6}$ |
| 0.8 | $2.5\times10^{-19}$ |
| 0.9 | $8.3\times10^{-41}$ |
| 0.95 | $1.1\times10^{-83}$ |
| 0.97 | not resolved at 400 bits |

Past about $q=0.96$ the two tables would hold byte-identical 100-digit strings
under the same index. That is not two tables sharing a number for a reason --
the case the skill defends, pi in T7, T59 and T92 -- but one number stored
twice with two names, which makes every search for it worse. The batch caps
the grid at $q=0.900$, where they still differ in the 41st digit, and says why
in the table rather than leaving the next extender to rediscover it.

The general point: the range test the skill gives is "will anyone arrive
holding one of these", which is about each table alone. A *family* built in
one run needs a second test -- do two of these tables collide anywhere in the
range -- and it is answered by computing the difference at the edge, not by
looking at the definitions, which say the functions are distinct and are
right.

What the skill says now: "Hold the numbers that turn up", and the range
argument throughout is about one table's own entries. The nearest thing is the
note that a rational eigenvalue forces $(x-a)^2$ whatever the field, which is
one table's entries colliding with each other.

What it should say: when a batch builds several tables on one grid, check at
the ends of the range whether any two of them agree to the stored precision,
and cut the range where they do. Say so in the `complete-note`, because it is
the sentence a reader whose value lies beyond the cut needs.

Evidence: 2026-09-22, `/tmp/ideas1723/check2.py` under `agents/sage.sh`, Sage
10.9, `ComplexBallField(400)`. The table above, and $\theta_4(0,0.9) =
7.37352693847\times10^{-10}$ against $\theta_4(0,0.999) =
1.0155\times10^{-1069}$ at the other end of the same grid.

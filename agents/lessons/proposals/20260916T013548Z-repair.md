## Removing `numberdb.sage` from a Sage `Programs` snippet may require `sage.all`
What happened: T254's critique correctly noticed that `program-sage` imported `numberdb.sage` and never used the name, so a reader without the NumberDB client would fail before any mathematics ran. The proposed smallest edit was to delete that line. During the repair, deleting it while leaving the named imports failed under `agents/sage.sh` before the snippet computed anything: `from sage.rings.integer_ring import ZZ` raised an `AttributeError` from a partially initialized Sage module. Replacing the three setup imports with `from sage.all import ZZ, PolynomialRing` removed the NumberDB dependency and printed $P_{51}$.
What the skill says now: it says `Programs` is for a reader who wants one more value, and separately says generators should import `numberdb.sage` before named Sage imports because that initializes Sage. The critique-side proposal says to delete unused `numberdb` imports from `Programs`, but not what to put back when those imports were also doing Sage initialization.
What it should say: when a Sage `Programs` snippet does not use the NumberDB client, remove the `numberdb` dependency, then run the snippet exactly as shown. If direct named Sage imports only worked because `numberdb.sage` initialized Sage first, use a reader-facing SageMath import such as `from sage.all import ZZ, PolynomialRing` in `Programs`. Keep the stricter named-import pattern in `generate.py`, where portability to modular passagemath and the NumberDB client are part of the job.
Evidence: T254 repair, 2026-09-16. `agents/sage.sh /tmp/t254_program.py` failed after only deleting `import numberdb.sage as numberdb`; the same snippet with `from sage.all import ZZ, PolynomialRing` printed the full $P_{51}$ polynomial.

# Lessons proposed by the T3 critique, 2026-09-22

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## `GET /api/search?q=` answers 200 with an empty result set, and the parameter is `expression`

What happened: reading T3, the corpus was searched over the HTTP API the way
`/api/docs` documents it -- the endpoint's own table of parameters gives one
row, `q`, "the term: a decimal, a fraction, a p-adic, a polynomial, an
expression such as `pi`, or words". Five queries were run through it
(`Riemann zeta`, `zeta zeros`, `pi`, `Bessel`, `14.13472514173469`) and every
one answered

    HTTP 200  {"results": [], "messages": [], "time_request": "0.000s"}

which reads as a corpus that holds none of those things. It holds all of them:
41 tables carry the `L-function` tag alone, and `14.13472514173469` is the
first entry of T3.

`/api/search` is routed to `api.advanced_search_results`
(`numberdb_app/urls.py:41`), whose first act is
`program = request.GET.get('expression', default=None)` followed by
`if program == None: return wrap_response(None, messages)`. The parameter is
`expression`; `q` is never read. The empty-with-no-message answer is the
documented error path for "no expression given", and it is indistinguishable
from a search that found nothing. `time_request: 0.000s` is the only tell.

Same query, right parameter:

    curl --get --data-urlencode "expression=14.13472514173469" \
         https://numberdb.org/api/search
    → T3 #1 first, then nine entries of T385

What the skill says now: it warns about the *client's* version of this --
"`search_text` returns an object with a `.tables` list, not a list -- iterating
it directly yields nothing and raises nothing, which reads exactly like an
empty corpus" -- and says nothing about the HTTP endpoint, which is the one a
contributor reaches from `/api/docs` without installing anything.

What it should say: the same warning, extended. An empty answer from the corpus
is nearly always the caller's fault, not the corpus's, and both known ways to
get one are silent. Over HTTP the search parameter is `expression`, whatever
`/api/docs` says; a `results` list that is empty while `time_request` is
`0.000s` means the request never ran. Prefer `numberdb.search_text` where
Python is available, and when a search for something you are certain is there
comes back empty, check the parameter name before believing the answer.

(The mismatch between `/api/docs` and the view is a site bug and somebody
should fix one of the two. The lesson survives the fix: it is "do not read an
empty search as an empty corpus", and this is the second mechanism to produce
one.)

Evidence: 2026-09-22, T3 critique. `/api/search?q=pi` → `{"results": [], ...}`;
`/api/search?expression=pi` → 3.14159... with its table. `numberdb_app/api.py`
lines 145-147; `numberdb_app/templates/api-reference.html` line 118.

## A parameter's `comments` is stored, is never shown, and is where three tables put the sentence a reader needs

What happened: T3's parameter `n` declares `constraints: $n \neq 0$` and
explains itself in a `comments` key on the same parameter:

    n:
      type: Z
      constraints: "$n \\neq 0$"
      comments: "The positive imaginary parts are labelled $n = 1, 2, 3,
                 \\ldots$, the negative ones are labelled $n = -1, -2, -3,
                 \\ldots$, and the index $n = 0$ is skipped."

The rendered page shows

    $n$   —   integer ($n \neq 0$)

and nothing else. The parameter block in `numberdb_app/views.py:891` reads
`display`, `title`, `type`, `constraints`, `values` and
`show-in-parameter-list`; `comments` is not among them and no other template
touches it. The write API accepts it without complaint, the document keeps it,
`GET /api/table` returns it, and no reader ever sees it. So T3's page promises
negative indices and shows none, and the one sentence reconciling the two is
invisible. T4 and T387 carry the same dead key.

What the skill says now: its table of where each thing goes lists `Parameters`
as holding "each parameter's type and the constraint the entries actually
satisfy", and `Comments` as holding "conventions, caveats, ... alternative
indexing". The right home is already named. What is not said is that the wrong
one fails *silently* -- the author sees their sentence in the document they
sent and has no reason to fetch the page back.

What it should say: a parameter carries `type`, `constraints`, `title` and
`display`, and nothing else on it is rendered. An explanation of the indexing
is a `Comments` entry, not a key on the parameter. The general form is worth
stating once: the document accepts keys the page does not print, so a sentence
that matters is checked by fetching the rendered page, not by re-reading the
YAML you sent.

Evidence: 2026-09-22, T3 critique. `GET /api/table?id=T3` returns
`Parameters.n.comments`; <https://numberdb.org/T3> renders
`<div class="table-entry"> &mdash;&nbsp;&nbsp; integer ($n \neq 0$)</div>` and
no comment. Same on T387, whose parameter comment about ties in the ordering is
likewise stored and unshown.

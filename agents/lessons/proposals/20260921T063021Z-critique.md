## Run a `Programs` snippet as the bytes the document holds, not as you retype it

What happened: T378's `Programs` block is seven lines of PARI/GP whose
`prodeulerrat(...)` call is split across two lines:

    a = prodeulerrat((1 - 1/p)^((k - 1)^2) *
      sum(j = 0, k - 1, binomial(k - 1, j)^2/p^j), 1, 2)

GP continues an unbalanced expression at an interactive prompt, so pasting the
block into a `gp` session works. Piping the same bytes into `gp -q` — which is
what a reader does with seven lines they have copied into a file — does not:

    *** syntax error, unexpected end of file: ...ulerrat((1-1/p)^((k-1)^2)*
    *** syntax error, unexpected ',', expecting end of file: ...-1,binomial(k-1,j)^2/p^j),1,2)

`a` is then unassigned, and the final `a * f` prints `0.000115740740…` (the
second factor alone) and then that number times the free variable `a`. The
reader gets a plausible-looking wrong number rather than a refusal.

`cypari2` refuses the block too, both as one string and line by line, so a
checking script that evaluates the snippet through a Python PARI binding does
**not** exercise this. The sibling table T377 carries the identical split, and
its critique reported the program "run under PARI at 140 digits exactly as
printed" with a correct value — which is only possible if the call was retyped
onto one line in the checking script. The retyped version is not the artefact
the reader gets.

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value." It says what the field is
for and nothing about checking that what is in it runs, or about how a
multi-line snippet survives being copied.

What it should say: before publishing a `Programs` block, run it the way a
reader will — the exact stored string, fed to the interpreter from a file or a
pipe, not pasted at a prompt and not retyped into a test script. Continuation
rules differ from the interactive ones: PARI/GP needs a trailing `\` on a line
that leaves an expression unbalanced, and gp reading a script file echoes
nothing, so a snippet ending in a bare expression should end in `print(...)`
if it is meant to be run that way. A one-line call needs none of this, and is
the safer shape.

Evidence: T378 critique, 2026-09-21, under `agents/sage.sh`. As printed via
`gp -q` stdin: two syntax errors, last value `0.000115740740…`. With a trailing
`\` added, or the call joined onto one line: no errors, and
`5.708527034652788398376841445252313559397328900532833950983032039199246535871335734526769079053203821…e-6`,
which is T378's stored $k=3$ row to all 100 digits. `cypari2` on the block as
printed: `PariError: syntax error, unexpected variable name, expecting end of
file`.

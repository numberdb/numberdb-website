# Lessons proposed by the T261 critique, 2026-09-16

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

---

## A parameter with no `title` renders as its type, "Symbolic (Unknown type)"

What happened: T261's second parameter is a partition, declared with
everything the skill asks for and nothing else:

    lambda:
      type: Symbolic
      display: $\lambda$
      constraints: a partition with at most $n$ parts

The rendered parameter list reads

    $n$        —  number of variables (a positive integer)
    $\lambda$  —  Symbolic (Unknown type) (a partition with at most $n$ parts)

The page prints the parameter's `title` where that second field is, and falls
back to the type's own name when there is none; for the types with no
searchable digits that name is "Unknown type", so the line an author never
wrote is the line that says the site does not recognise something. The
document is valid, the audit passes it, and nothing but the rendered page
shows it.

Why a contributor on their own laptop hits this: the skill's table of sections
says Parameters hold "each parameter's type and the constraint the entries
actually satisfy", and the worked generator in section 6 declares
`parameters = ('m',)` and no titles at all. Somebody who writes exactly what
the skill asks for gets this line, and only sees it if they look at the
rendered page rather than the document.

What the skill says now: nothing about `title` on a parameter. It names
`display`, `param-latex` (to warn against), `constraints`, and the parameter
key.

What it should say: a parameter's `title` is the phrase the page prints beside
its symbol, and without one the page prints the type instead — "Symbolic
(Unknown type)" for the types that are shown rather than searched. Give every
parameter a title, short and in the table's own words: T259 and T260 both
title their partition `shape`, so their pages read "$\lambda$ — shape (a
partition of a positive integer)".

Evidence: 2026-09-16, T261 critique. Five `/preview?table=` renderings of the
draft, all five printing `Symbolic (Unknown type)` for `lambda` and "number of
variables" for `n`, which has a title. `numberdb_app/validate.py` accepts the
document and `GET /api/table/T261/audit` reports `clean: true`.

## An `HREF` with no caption prints the slug, and the audit's check for it wants the title exactly

What happened: T261's formulas (2) and (3) are stored as

    $P_\lambda(x;0)=s_\lambda(x)$, the Schur polynomial HREF{Schur_polynomials}.

and reach the page as "the Schur polynomial **Schur_polynomials**." — the
renderer uses the target as the caption when none is given, so a slug with an
underscore in it is set in running English. Twice, in the two formulas a
reader of this table is most likely to follow.

`audit_table` has a check for exactly this shape, "a link sitting after the
name instead of on it", and it did not fire. It looks for the target table's
bare title immediately before the `HREF`, and the titles here are "Schur
polynomials" and "Monomial symmetric polynomials" while the prose writes them
in the singular. A plural would have been caught; a singular is invisible to
it. So the rule cannot be left to the audit, and has to be a habit.

The general fact — no caption means the target is the caption — is already
proposed for entry links in
`agents/lessons/proposals/20260913T221523Z-critique.md`, where 57 comments
read "It is cospectral with #E@]o". This is the same renderer behaviour doing
its damage on a *table* link in ordinary prose, where the author has written
the name they meant three words earlier.

Why a contributor on their own laptop hits this: writing "the Schur polynomial
HREF{Schur_polynomials}" is the natural word order, and the document, the
validator and the audit all accept it. Only the rendered page shows it, and a
contributor who checks their prose by reading the YAML never will.

What the skill says now: "Link a table the first time it is named, and only
the first time ... First mention in a section,
`HREF{Bernoulli_numbers}[the Bernoulli numbers]`." Every example carries a
caption; nothing says what happens without one, or that the name must be
*inside* the link rather than in front of it.

What it should say: always write the caption, and put the link on the name
rather than after it. `HREF{slug}` alone prints the slug — `Schur_polynomials`,
underscore and all — as the link text, in the middle of a sentence that
already contains the name in English.

Evidence: 2026-09-16, T261 critique. `/tmp/t261_b.html`, a `/preview` piece of
the draft: "the Schur polynomial [link Schur_polynomials]Schur_polynomials."
and the same for the monomial symmetric polynomials.
`numberdb_app/management/commands/audit_table.py:933` is the check that would
have caught the plural; `GET /api/table/T261/audit` reports `clean: true`.

## A polynomial's search key ignores what the variables are called, and which one is which

What happened: T261 stores multivariate polynomials in $x_1,\dots,x_n$ and an
indeterminate $t$, and the critique wanted to know whether a reader holding
one would have to guess those names to find it. They do not. The site's
canonical key is positional, and positions are normalised, so all of

    -x1*x2*t + x1^2 + x1*x2 + x2^2        the stored form
    -x*y*z + x^2 + x*y + y^2              a reader's own names
    -a*b*t + a^2 + a*b + b^2
    -t*x1*x2 + t^2 + t*x1 + x1^2          t and x2 exchanged

produce the identical key `3;1/1:x0^1,x1^1|-1/1:x0^1,x1^1,x2^1|1/1:x0^2|1/1:x1^2`.
The last line is worth noticing on its own: the key is invariant under
permuting the variables, so two polynomials that differ by which variable
plays which role find each other. That is the right behaviour for a table
whose variable names are an arbitrary choice, and it means a multivariate
table needs no keywords about its naming; it also means a search hit in a
multivariate table is a weaker statement than one in a table of integers.

Why a contributor on their own laptop hits this: anybody building a table of
multivariate polynomials has to decide whether to name the variables the way
their source does or the way the corpus does, and whether to say so on the
page. The answer for *search* is that it does not matter; the answer for
*reading* is that it does, and the two are easy to confuse.

What the skill says now: the type table gives `Z[]`, `Q[]` as "polynomials",
written `x^2 - x - 1`. Every example is univariate, and nothing says how a
multivariate value is matched.

What it should say: a polynomial is searched by a canonical key that records
the exponent pattern and the coefficients, not the variable names, and that is
invariant under permuting the variables. So a multivariate table's naming is a
choice about reading rather than about findability — say in a comment what the
variables are, and do not worry that a reader who calls them $x,y,z$ will miss
the row.

Evidence: 2026-09-16, T261 critique. `utils/numbers/polynomial.py`,
`parse_polynomial(...).canonical_text()` on the four forms above, all equal;
all 33 of T261's stored values parse with it. The grouping claim is the one
`manage.py check_polynomial_keys` makes: "the key groups polynomials exactly
as the stored one does, since a key that grouped differently would silently
change which polynomials find each other".

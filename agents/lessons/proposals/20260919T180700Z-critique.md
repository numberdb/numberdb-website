## A pair of tables has one range, not two: row links and row-by-row cross-checks bound how far either can grow

What happened: T289 holds the minimisers $\lambda_{k,r}$ of the formula whose
minimum is T273's core threshold $c_{k,r}$. Both hold exactly the box
$3\leq k\leq8$, $2\leq r\leq8$, and T289's `complete-note` says why: "matching
the companion core-threshold table". Asked how far T289 could grow, the size
and cost answers were easy -- every entry is a 100-digit real, so the cost per
entry is flat at 239.7 stored bytes, and the bisection runs in 0.02 s -- but
neither is the binding constraint. Two couplings to the companion are:

* **Every entry comment links a row of the companion.** Each row of T289 says
  "The associated core threshold is
  `HREF{Core_thresholds_of_random_k-uniform_hypergraphs#k,r}[$c_{k,r}$]`". A
  link to a row the companion does not have is not a 404: the page answers 200
  with a warning banner, "This table has no entry 9,2. It may have been
  renumbered or removed; the table itself is shown below." So the first row
  added beyond the companion's range greets its reader with a warning, and
  there is no error anywhere to tell the author.
* **Every row's verification reads the companion by key.** T289's
  `run_integrity_checks` does `threshold_table["Numbers"][str(k)][str(r)]` for
  each row, and a second loop reads the graph table T156 by `str(r)`. Outside
  the boxes those tables hold, that is a `KeyError` in a checking routine --
  a traceback naming a dictionary key, not a range.

So extending one table of a pair is not an extension of the pair: it is a
table whose new rows have a dangling link and no independent check, which is
exactly what the two tables were built to give each other.

What the skill says now: it discusses paired tables at length -- when two forms
are one table and when they are two, and that "one table holding both reaches a
different range in each, and a range that is ragged for this reason is a sign
of two tables rather than of one unfinished". It says nothing about two tables
that legitimately *are* two and share a range, and nothing about what extending
one of them alone does.

What it should say: when a table's rows link a companion's rows, or its
verification compares against them row by row, the two ranges are one decision.
Extend them in the same change, and write the range once in both
`complete-note`s. Before extending, scope the cross-check to the overlap
explicitly (`if (k, r) in stored`) so that the rows beyond the companion fail
the check softly and visibly, rather than raising `KeyError` -- and check the
new rows' cross-table `HREF`s, which fail silently with a banner rather than
an error.

Evidence: 2026-09-19, `agents/critiques/T289-growth.md`.
`GET /Core_thresholds_of_random_k-uniform_hypergraphs?entry=9,2` -> 200 with
the "has no entry 9,2" banner (T273 holds $k\leq8$).
`generators/core-threshold-minimisers/generate.py:run_integrity_checks`, which
indexes `T273[k][r]` and `T156[r]` directly; T156 holds $3\leq k\leq12$, T273
holds $3\leq k\leq8$, $2\leq r\leq8$. The same pairing exists at
T274/T288 (cuckoo hashing thresholds and the roots of their threshold
equation), both $2\leq k\leq7$, $1\leq\ell\leq6$.

## Widening a parameter's constraint: read the existence proof at the new boundary, not the generator's output

What happened: the same T289 reading asked whether the table could take in
$k=2$, the graph case -- the generator already computes those values to check
T156, and T156 keeps them only in entry comments, twelve digits, where no index
reaches them. The values exist for $r\geq3$ and **not** for $(k,r)=(2,2)$, and
the table's own formula says why in one line: $g'$ vanishes only at
$\lambda^*=(r-1)-1/(k-1)$, which is $0$ exactly there, so $g$ increases from
$g(0)=0$ and never returns to it. There is no minimiser; the minimum is
approached as $\lambda\to0$. A range widened to $k\geq2$ therefore has a hole
at its corner, and the `complete-note` has to say so, because a reader who
finds $\lambda_{2,3}$ and $\lambda_{3,2}$ and no $\lambda_{2,2}$ will otherwise
read it as an unfinished computation.

What the skill says now: a parameter states "the constraint the entries
actually satisfy", and the range that is actually present belongs in
`complete-note`. Nothing about widening a constraint later.

What it should say: widening a parameter's constraint is a claim about
existence, not about how much you computed. Re-read the proof in
`rigour details` at the new boundary before adding rows: the boundary is where
a uniqueness or existence argument usually degenerates, and if the family has a
hole there, the `complete-note` names the hole and the reason in a clause.

Evidence: 2026-09-19. $\lambda_{2,r}$ computed at 100 digits in the throwaway
container for $3\leq r\leq12$, agreeing with every twelve-digit value in T156's
entry comments ($\lambda_{2,3}=1.793282132901$, ...,
$\lambda_{2,12}=14.394738901917$); at $(2,2)$ the bisection cannot find a sign
change, and the algebra above says it never will.

## Corroboration: in a standalone Sage script, import from `sage.all`

The proposal of the same day about named Sage imports
(`20260919T174347Z-critique.md`) hits at import time too, not only in
arithmetic. A script whose first line was

    from sage.rings.integer_ring import ZZ

failed before running anything:

    AttributeError: partially initialized module 'sage.rings.integer_ring'
    has no attribute 'ZZ' (most likely due to a circular import)

The generators in this corpus do not see it because `import numberdb.sage as
numberdb` at the top initialises Sage first. A checking script that does not
import the client has nothing doing that for it, and `from sage.all import ZZ,
RealBallField, RealField` fixed it unchanged. Same file, same run, 2026-09-19.

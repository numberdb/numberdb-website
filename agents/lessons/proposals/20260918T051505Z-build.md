## Run `already_here` where `import numberdb` reaches the client, not the Django project
What happened: the Barker build tried the required cheap re-check with
`already_here("Barker polynomials")` from `agents/table-ideas/screen.py`, run
from the `numberdb-website` checkout root. The helper imported the local
Django project package `numberdb` instead of the Python client, so it returned
`(could not ask the corpus: AttributeError: module 'numberdb' has no attribute
'search_text')` before reaching the live corpus. The build used
`/api/lookup?text=Barker` and typed polynomial lookups for the duplicate
check instead.

What the skill says now: it says to run `already_here` and `already_asked`
from `agents/table-ideas/screen.py`, and it says the Python client has
`search_text`. It does not say that the website checkout also contains a
package called `numberdb`, which shadows the client when the helper is run
from the repository root.

What it should say: when using the screening helpers from a website checkout,
run them in an environment where `import numberdb` resolves to the client
package, not the Django project package. If the helper reports that
`numberdb` has no `search_text`, the duplicate check has not run; use a fixed
client path or the `/api/lookup?text=...` endpoint before treating the corpus
as empty.

Evidence: 2026-09-18, T322 build. `python3` from `/home/ubuntu/numberdb-website`
reported `numberdb.__file__ == "/home/ubuntu/numberdb-website/numberdb/__init__.py"`
and `hasattr(numberdb, "search_text") == False`; `already_here("Barker
polynomials")` returned the AttributeError message above. A direct lookup of
`https://numberdb.org/api/lookup?text=Barker` returned no table metadata, and
typed polynomial lookups for representative Barker polynomials returned no
same-family table.

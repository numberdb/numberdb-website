## The API can read a draft you can name, and cannot tell you its name

What happened: triaging a failed build, I wanted the obvious thing -- the list
of drafts the key's account is holding, to see whether the run had left a
half-made table behind. There is no route that answers it.

`GET /api/tables` with the key in an `Authorization: Bearer` header returns
HTTP 405 `{"error": "Use POST."}`: that path is `create_table` and nothing
else (`numberdb_app/api.py:962-963`). The page the skill points at, `/drafts`,
returns HTTP **200 with the sign-in page in the body** -- not a 401, not a
redirect the client reports as an error. It is a Django session view
(`views.py:375-379`, `if not request.user.is_authenticated: redirect(...)`),
and an API key does not make a session, so a key holder gets HTML that says
"Sign in" while every status code looks like success. Parsing that for table
numbers finds none, and the reason is not visible from the response line.

The whole API surface is fifteen routes (`numberdb_app/urls.py:40-55`), and
every table-shaped one takes a table you have already named: `api/table?id=`
or `?url=`, `api/table/<tid>`, `.../entries`, `.../offer`, `.../lease`,
`.../audit`, `.../file/<name>`. `api/search` and `api/lookup` answer over
published tables only, so they cannot find a draft either -- which the lesson
above, "A draft is readable through the API by its owner", already establishes
from the other side: `numberdb.table('T152')` with the owner's key returns the
draft's whole document, entries included.

Put together, the two halves are the actual rule, and neither is much use
without the other: **the API will hand you any draft whose T-number you can
supply, and has no way to tell you which T-numbers those are.** The draft
allowance is a few tables in flight at once, so an account that loses track of
a number can sit against a limit it cannot enumerate its way out of.

What the skill says now: "`/drafts` lists what is being made right now and is
invisible from outside, so a table can be half-built and unfindable while you
start it again." That is true in a browser and silently false for a key.

What it should say: keep the sentence, and mark whom it is for -- `/drafts` is
a signed-in page, and a script holding an API key cannot read it; it gets the
sign-in page with a 200. The API has no route that enumerates your drafts, so
**record the T-number when you create a draft** rather than expecting to look
it up later: the create call returns it, and it is the only place you will see
it without a browser. To check a draft you already know, `numberdb.table(tid)`
with your key configured. The one loop that does not need a list: if a title
is refused as already taken, the refusal names the table and its state, which
is how a resumed build finds the draft it made before it died.

Evidence: 2026-09-23T15:58Z, against numberdb.org with the zeta3 key in an
`Authorization: Bearer` header. `GET /api/tables` -> `HTTPError 405: Method
Not Allowed`. `GET /drafts` -> 200, 14427 bytes, whose stripped text begins
"Sign in - NumberDB" and contains no T-number. Compare `GET
/api/claim?family=205` with the identical header -> 200 and a JSON body, so
the key itself is good and it is the view that does not take one.

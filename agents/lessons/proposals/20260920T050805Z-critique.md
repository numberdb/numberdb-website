## A MathJax check that never fails is the enclosure that contains everything, in TeX

What happened: reading T358 as a reader, the TeX had to be typeset outside a
browser, because the page's `$...$` fragments reach the HTML untouched and
MathJax runs on the client. The obvious script -- pull every fragment out of
the document, `doc.convert(f)` inside a `try`, count the exceptions -- reported
`checked 44 errors 0`, and 44 was 43 real fragments plus the control
`\frac{1}{`. The control passed. MathJax 3's TeX input **does not throw on a
malformed formula**: it builds an `merror` node, which is the thing a reader
sees as a red "Math input error" box, and `convert` returns it happily. So the
check was measuring nothing, and it looked exactly like a clean table.

Serialising the output and testing it instead --

    const out = adaptor.outerHTML(doc.convert(f, {display: false}));
    if (/merror|data-mjx-error|Math input error/i.test(out)) { ... }

-- reported `ERROR: "\\frac{1}{" -> Missing close brace`, and the 43 real
fragments still passed. Same fragments, same library, opposite epistemic
value.

Two smaller things from the same run. A second control, `\notarealmacro{x}`,
did *not* error under `AllPackages`, so an undefined macro is not a reliable
control -- an unclosed brace is. And the fragments have to be taken from the
*parsed* document rather than from its JSON: a `\\` in the wire format is one
backslash in the prose, and checking the escaped form tests a string no reader
ever sees.

What the skill says now: it has the principle -- "A measurement needs a control
that returns a known answer", and "An enclosure that contains everything agrees
with everything" for ball arithmetic. It says nothing about TeX, and a
contributor who wants to know whether their formula renders has no way to find
out but to publish it and look.

What it should say: mathematics in a table is rendered by MathJax in the
reader's browser, so nothing on the server or in the client checks it, and a
malformed formula reaches the page as a red error box rather than as a refusal.
To check it before publishing, typeset each `$...$` fragment with
`mathjax-full` and look for `merror` in the *output*; `convert` does not throw,
so a `try`/`catch` around it passes everything. Run an unclosed-brace control
first and see it fail.

Evidence: 2026-09-20, T358 critique. `/tmp/mj358/check.js` reported
`checked 44 errors 0` with the control included; `/tmp/mj358/check2.js`, which
differs only in inspecting `adaptor.outerHTML` of the result, reported
`ERROR: "\\frac{1}{" -> Missing close brace` and `checked 45 errors 1`.


## `GET /api/table/T358` is not how to read a table, and its error says "Use POST or PUT"

What happened: reading a draft from a machine with no database, the natural
URL for the document was `https://numberdb.org/api/table/T358` -- natural
because `https://numberdb.org/api/table/T358/audit` is the documented way to
get the audit, and `.../offer`, `.../lease` and `.../file/<name>` hang off the
same stem. It answers HTTP 405 with

    {"error": "Use POST or PUT."}

which reads as a method problem on the right route. It is not: that route is
`write_table`, and reading has a different shape entirely,

    curl -G --data-urlencode "id=T358" https://numberdb.org/api/table

with the key in `X-API-Key` for a draft. The query parameter accepts a
T-number or a table's address, and returns the whole document including
`Numbers`.

The cost is small but it is spent by everybody who reaches for `curl` instead
of the client, and the error message spends it twice: it names two verbs, both
of which write, on a request that was trying to read.

What the skill says now: it shows `numberdb.table('T99')` and says the document
comes back with capitalised keys, which is the Python answer and the right one
for most people. It gives no HTTP shape for reading at all, while giving one
for creating (`POST /api/tables` with `X-Draft: yes`). A reader who has met the
second reasonably guesses the first.

What it should say: reading a table over HTTP is `GET /api/table?id=<TID>`, a
query parameter and not a path segment, and `id` takes either the T-number or
the address. The path form `/api/table/<TID>` is the write route and answers
"Use POST or PUT" to a GET, which is not a hint about the read route.

Evidence: 2026-09-20, T358 critique. `GET /api/table/T358` -> HTTP 405,
`{"error": "Use POST or PUT."}`; `GET /api/table?table=T358` -> HTTP 200,
`{"error": "No id or url given."}`; `GET /api/table?id=T358` -> HTTP 200,
22485 bytes, keys `Title` ... `Numbers`. Routes in `numberdb_app/urls.py`
lines 20 and 22.

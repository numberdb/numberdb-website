# Lessons proposed by the T331 critique, 2026-09-18

Not in force. Format as in `agents/lessons/PROPOSALS.md`.

## A `Programs` snippet must say which indexing it uses when the table states a different one

What happened: T331 defines its matrices in a comment that opens "Indices are
$1$-based" and gives the Hilbert matrix as $A_{ij}=1/(i+j-1)$. Its `Programs`
block is

```python
A = matrix(QQ, 3, 3, lambda i, j: QQ(1) / QQ(i + j + 1))
A.det()
```

with no comment. The snippet is right — it returns `1/2160`, the stored
`hilbert,3` — and it is right for a reason the page never states: Sage's matrix
constructor hands the callable 0-based indices, so `1/(i+j+1)` *is* the page's
$1/(i+j-1)$. A reader who trusts the table's own convention and substitutes its
own formula does not get a wrong number, which would be visible. They get

    ZeroDivisionError: rational division by zero

at $i=j=0$, from a program the table published as the way to compute one more
value. The sibling table T330 carries the identical snippet with the line
`# Hilbert matrix, n = 3.` above it, so the omission is a line lost in a copy
rather than a decision.

The general shape: a table states a convention — 1-based indices, counting
zeros from 1, a branch, a normalisation — and `Programs` reaches a library
that uses a different one. The translation is invisible in a snippet that
works, and it is exactly what a reader borrowing the snippet has to change.

What the skill says now: "**`Programs` and `generate.py` answer different
questions.** `Programs` is the standard incantation in Sage, PARI or mpmath for
a reader who wants one more value." Nothing about the snippet agreeing with the
table's stated conventions, and "Define notation where you use it" is about
prose.

What it should say: that a `Programs` snippet is read against the table's own
definitions, so where the library's convention differs from the table's —
0-based indexing, a different parameter, a different branch — the snippet says
so in a comment, and names the row it reproduces. One line: `# Hilbert matrix,
n = 3; Sage indexes from 0, so this is the A_ij = 1/(i+j-1) above.` Check it by
typing the table's own formula into the snippet and seeing what happens.

Evidence: 2026-09-18, T331 critique. `agents/sage.sh /tmp/t331_program.py` ran
the published snippet (`A.det() = 1/2160`, matching the stored `hilbert,3`) and
then the same constructor with the comment's `QQ(1)/QQ(i + j - 1)`, which
raised `ZeroDivisionError: rational division by zero` from
`sage/rings/rational.pyx`. T330's `Programs` for comparison:
`"# Hilbert matrix, n = 3.\nA = matrix(QQ, 3, 3, lambda i, j: QQ(1) / QQ(i + j + 1))\nA.charpoly()"`.

## `Keywords` need the accented spelling as well as the plain one, not instead of it

What happened: T331's `Keywords` carry "Kac-Murdock-Szego matrix" and not
"Kac-Murdock-Szegő matrix". Its two siblings carry both. Searching the live
corpus:

    text=Szego matrix  ->  T331, T329, T330
    text=Szegő matrix  ->  T329, T330

The correctly spelled query is the one that misses, and it is the spelling a
reader who knows whose matrix it is will type. It is easy to conclude the
opposite from a careless test: `text=Kac-Murdock-Szegő matrix` does return
T331, because "Kac" and "Murdock" are separate tokens and match on their own.
Only the bare surname fails.

What the skill says now: "that is also how an accent is handled, since the
index has no `unaccent`: the title is 'Lévy's constant' and `Keywords` carries
'Levy constant'." That covers a title with the accent in it and a keyword
without. It does not cover the commoner case here, where the accent is in
*neither*, and the plain spelling is doing duty for both.

What it should say: that with no `unaccent` in the index the two spellings are
two different words, so a name normally written with an accent needs both in
`Keywords` whenever the title does not carry one of them. Test the bare
surname, not the full hyphenated name, which can match on its other tokens.

Evidence: 2026-09-18, `GET /api/lookup?text=Szeg%C5%91+matrix` returned
`Eigenvalues of the classical symmetric test matrices` and `Characteristic
polynomials of the classical test matrices` and not `Determinants of the
classical test matrices`; `text=Szego+matrix` returned all three. T330's
`Keywords` hold both "Kac-Murdock-Szego matrix" and "Kac-Murdock-Szegő matrix";
T331's hold only the first.

## `rigour details` folds after as many whole sentences as fit in 400 characters, not after the first

What happened: T331's `rigour details` is one paragraph of five sentences, and
the rendered page shows **two** of them above the `more` disclosure:

    <p class="prose-paragraph">The generator builds each matrix over
    $\mathbb{Q}$ ... by fraction-free Bareiss elimination. Before the entries
    were written, <code>agents/table-build/dry_run.py</code> computed all 363
    entries, ... with an entries block of 58.8 KB.</p><details
    class="prose-more"><summary>more</summary>...

This corrects the T324 critique's proposal in
`agents/lessons/proposals/20260918T074121Z-critique.md`, "`rigour details`
folds after about 400 characters, cutting a single paragraph at its first
sentence", which concludes "the first sentence is therefore the whole of what a
reader sees with the page closed". That was true of T324 and is not the rule.
`_split_sentence` in `numberdb_app/prose.py` collects every sentence break in
the paragraph and takes **the last one that fits** the 400-character window —
"the opening is as much as can be read without unfolding" — falling back to the
first break anywhere only when none fits. T324's second break was past 400 and
T331's was not, which is the whole of the difference.

The advice changes with it. "Put the caveat in the first sentence" is too
strong; "keep what a reader must see inside the first 400 rendered characters"
is the rule, and a note whose first 400 characters are housekeeping — a script
name, a byte count, a character count — has spent them. T331's three real
checks (closed forms, a Leibniz determinant at $n\leq6$, 138 rows against
T330) are all behind the fold.

What the skill says now: `rigour details` holds "how the digits were obtained,
at whatever length that needs: blank lines make paragraphs, `- ` makes a list,
backticks mark code, and a long note folds after its first paragraph".

What it should say: that a note with no blank line in it folds at the last
sentence end within about 400 rendered characters — one sentence or four,
depending where the full stops fall — so the first 400 characters are what a
reader reads, and the method and its caveats go there while the run's own
bookkeeping goes last or not at all.

Evidence: 2026-09-18, `https://numberdb.org/T331` rendered HTML, two sentences
in the `prose-paragraph` and three inside the `details`;
`numberdb_app/prose.py`, `_split_sentence`: `fitting = [end for end in breaks
if end <= fold_above]` then `best = fitting[-1] if fitting else ...`.

## A table's own comments are what the entries block should be rebuilt from, and the check is cheap without Sage

Already proposed by the T330 critique
(`agents/lessons/proposals/20260918T132837Z-critique.md`, "Where prose carries
the whole definition, check that the prose rebuilds the values"), and T331 is a
second instance rather than a new lesson, so it is recorded here only as
support: thirteen matrix families, 363 entries, rebuilt from Comments (13) to
(15) alone in plain Python with `fractions.Fraction` and a Bareiss determinant
in about seven seconds, no Sage and no network. Every value agreed. The same
script checked the twelve `Formulas` against the same entries and the seven
claims in the "omitted families" formula for every $n$ from 2 to 30. A
contributor can run this on a laptop before publishing, and it is the check
that decides whether the prose on the page is a definition or a gesture at one.

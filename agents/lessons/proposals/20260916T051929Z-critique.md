## Two library functions with different names can be one computation, and a check between them checks nothing

What happened: T259's `rigour details` lists four checks the values were put
through, and the first is "checked against Sage's Schur-to-Hall-Littlewood
transition dictionary". The generator computes every value with
`KostkaFoulkesPolynomial`. Those are two public names in
`sage.combinat.sf.kfpoly` and they look like two routes to the same answer, so
comparing them looks like the independent check the skill asks for. Reading the
source in the same container says otherwise:

    sage: import inspect
    sage: from sage.combinat.sf import kfpoly
    sage: inspect.getsource(kfpoly.KostkaFoulkesPolynomial)   # ... return kfpoly(mu, nu, t)
    sage: inspect.getsource(kfpoly.kfpoly)
        nuc = _Partitions(nu).conjugate()
        f = lambda x: weight(x, t) if x[0] == nuc else 0
        return sum(f(rg) for rg in riggings(mu))
    sage: inspect.getsource(kfpoly.schur_to_hl)
        for rg in riggings(mu):
            res[rg[0]] = res.get(rg[0], 0) + weight(rg, t)

Same `riggings`, same `weight`, same module. The comparison can catch a
transcription slip between generator and table and nothing else; a wrong
`weight` passes it silently. An actually independent check — the
Lascoux–Schützenberger charge statistic and a tableau enumeration written from
the definition, in plain Python — reproduced all 901 stored values, so the
table is right; but three of its four stated checks are evidence and the fourth
is not, and a reader counting them counts four.

What the skill says now: "**Check new values against something independent.**
Not the code that produced them" (§10), with the Fibonacci example, where the
independent thing is a different *function* of the same library —
`fibonacci()` checking a polynomial table. That example teaches exactly the
move that fails here: a second entry point of the same package is *sometimes*
independent and sometimes the same loop, and the skill gives no way to tell
which.

What it should say: a second function in the same library is only an
independent check if it is a different computation, and the name does not say.
Read it — `inspect.getsource(f)` is one line and settles it. Two entry points
that reduce to the same helper (`schur_to_hl` and `kfpoly` both sum
`weight(rg, t)` over `riggings(mu)`) confirm nothing about that helper.
Independence is cheapest to get from the *definition*: re-enumerate the
combinatorial objects the definition names, in plain Python, in another
library, or in OEIS. And when a table lists its checks in `rigour details`,
list only the ones that could have failed — a check that cannot fail costs the
other three their credibility.

Evidence: 2026-09-16, T259 critique. Sources quoted above, read with
`inspect.getsource` under SageMath 10.9. The independent charge enumeration is
in the critique's "How it was read": 901 of 901 exact string matches.

## The corpus search is indifferent to a hyphen against an en dash, on both sides, so a `Keywords` entry that only changes the dash buys nothing

What happened: T259's title is "Kostka–Foulkes polynomials" with an en dash,
and its `Keywords` spends two of five slots on `Kostka-Foulkes` (hyphen) and
`Kostka Foulkes` (space). That reads as insurance modelled on the skill's
accent rule, and the accent rule is real. The dash rule is not: measured
against published tables, with `numberdb.search_text` from
`clients/python`,

    'Hardy-Littlewood'  -> Hardy-Littlewood_singular_series_of_prime_tuples, ...
    'Hardy–Littlewood'  -> Hardy-Littlewood_singular_series_of_prime_tuples, ...
    'Gauss-Laguerre'    -> ..., Nodes_and_weights_of_Gauss_Laguerre_quadrature, ...
    'Gauss–Laguerre'    -> ..., Nodes_and_weights_of_Gauss_Laguerre_quadrature, ...

identical lists in identical order in both pairs. The first pair varies the
dash in the *query* against a hyphenated title; the second varies it against
"Nodes and weights of Gauss–Laguerre quadrature", whose stored title carries
the en dash. So both the query and the index normalise it away.

The cost is not the two wasted slots on their own. It is that they were spent
instead of the name a reader actually holds: in type $A$ these polynomials are
Lusztig's $q$-analogue of weight multiplicity, and `Keywords` says nothing a
search for "Lusztig" can reach.

What the skill says now: "that is also how an accent is handled, since the
index has no `unaccent`: the title is 'Lévy's constant' and `Keywords` carries
'Levy constant'." Nothing about dashes, and the accent sentence generalises
wrongly to them.

What it should say: the index normalises hyphens and en dashes and does not
normalise accents, so `Keywords` is for the accent, not for the dash. A
keyword that differs from the title only in punctuation is a wasted slot;
spend it on the *other name* for the object, which is what the "what would
somebody type" test is actually asking for. Names a mathematician would type
and a title cannot hold: a second name for the same family (Lusztig's
$q$-analogue for the Kostka–Foulkes polynomials), an eponym the title states
as a formula, the unaccented spelling.

Evidence: 2026-09-16, T259 critique. Four `search_text` calls above, against
numberdb.org as it stood that day.

## A deep `sage.combinat.*` import in a script works where `sage.rings.*` does not

Not a new lesson; a bound on a pending one. The proposal "A `Programs` snippet
that imports from `sage.*` submodules runs in a Sage session and not in a Sage
script" (`agents/lessons/proposals/20260916T024304Z-critique.md`, with second
and third instances recorded by the T257 and T258 critiques) is stated over
`sage.*` submodules generally. T259's snippet is a counter-example and it
matters for how the eventual sentence is worded:

    from sage.combinat.sf.kfpoly import KostkaFoulkesPolynomial

    KostkaFoulkesPolynomial([4], [2, 1, 1])

runs clean under SageMath 10.9 as a script, exit 0, and the call returns `t^3`.
The three failures recorded so far are all imports of *ring* modules —
`sage.rings.integer_ring`, `sage.rings.rational_field`,
`sage.rings.polynomial.polynomial_ring_constructor` — which are the modules
that initialise Sage's coercion machinery and therefore the ones with the
circular-import problem. The skill's own §6 already says this in the other
direction, "a ring module imported before anything has initialised Sage raises
'cannot import name QQ', and that module does the initialising", and names
`import numberdb.sage as numberdb` as the fix for a generator.

So the sentence the skill grows should say *ring* modules, not `sage.*`
modules, or it will tell contributors to rewrite imports that work. The advice
that survives unchanged is the test: run the snippet in a file, not only in a
session.

Caveat on the measurement: this repository's `agents/sage.sh` runs
`sage -python -u` and has no way to pass `sage file.py`, so I measured only the
`-python` mode. The T258 critique measured both modes for the ring imports and
found them identical.

Evidence: 2026-09-16, T259 critique. `/tmp/t259_prog.py`, the stored snippet
verbatim, through `agents/sage.sh`: exit 0, no traceback.

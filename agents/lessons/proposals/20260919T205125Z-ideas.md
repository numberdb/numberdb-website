# Lessons from the ideas run of 2026-09-19T2051 (statistical distances between probability distributions)

## An arb integral over a non-analytic integrand returns a narrow, wrong ball

What happened: the total variation distance between two distributions is
$\tfrac12\int|p-q|$, and the obvious way to compute it is to hand that
integrand to `ComplexBallField.integral`. For $\Gamma(3,1)$ against
$\Gamma(5,1)$ that returns

    0.401936701881211419695...

and the true value is

    0.404667153364360896673...

wrong in the third decimal, in a ball narrow enough to look like twenty-one
good digits. arb's integration uses Gauss-Legendre with analytic continuation
into a complex neighbourhood of the path, so it requires an analytic
integrand, and `abs` is not one. It does not complain; it integrates something
else.

The fix is to split the range at the points where the two densities cross, so
that each piece has a fixed sign and no `abs` is needed:

    xs = (a1.gamma()/a2.gamma())**(1/(a1 - a2))       # the one crossing
    lo = C.integral(lambda x, _: f1(x) - f2(x), C(eps), C(xs)).real()
    hi = C.integral(lambda x, _: f2(x) - f1(x), C(xs), C(BIG)).real()
    tv = (lo + hi)/2

which gives `0.404667153364360896673`, agreeing to every printed digit with
$|F_1(x^*)-F_2(x^*)|$ computed independently. It also gives a free check on
every row: `lo` and `hi` must be *equal*, because both densities integrate to
one, and they came out equal to 21 digits.

What the skill says now: "An enclosure that contains everything agrees with
everything", about balls so wide they are vacuous, and "a nan ball overlaps
every interval there is".

What it should say: the opposite failure as well. A *narrow* ball can be
wrong, and the commonest way to get one is to put a non-analytic function
inside an arb integrand. `abs`, `max`, `min`, a `sign`, a branch chosen by a
Python `if` on the argument: any of these makes
`ComplexBallField.integral`'s error bound a bound on the wrong integral. Split
the range at the non-smooth points and integrate analytic pieces. The same
applies to `RealBallField` quadrature.

Evidence: 2026-09-19 ideas run, `/tmp/tvcheck.py` through `agents/sage.sh`,
three variants of the same integral.

## `source_names_it` has no `unaccent`, so a family named after a person fails or passes by luck

What happened: two real, correctly cited sources for the Rényi divergence were
reported as not naming it:

    source_names_it('Renyi divergence and Kullback-Leibler divergence',
                    'https://arxiv.org/abs/1206.2459')
    -> the source does not mention renyi

    source_names_it('Renyi divergence measures for commonly used univariate
                     continuous distributions',
                    'https://doi.org/10.1016/j.ins.2013.06.018')
    -> the source does not mention renyi

Both pages have the family in their *title*. They spell it *Rényi*, and the
screen lower-cases the stripped HTML and looks for the literal ASCII
`renyi`. Wikipedia's *Rényi entropy* article passes the same call, which is
worse than failing consistently: it passes because some ASCII "Renyi" happens
to be in its markup, not because the check works.

What the skill says now: it says the index has no `unaccent` and that the fix
for a *table* is to put the ASCII spelling in `Keywords` -- "the title is
'Lévy's constant' and `Keywords` carries 'Levy constant'".

What it should say: the same gap is in the proposal screen, where it produces a
false negative rather than a missed search. Screen an accented family under
**both** spellings, and read a "does not mention" complaint about a name with
an accent in it as "unknown" rather than as a refusal:

    source_names_it('Renyi divergence', url) and source_names_it('Rényi divergence', url)

If either passes, the source names the family. Names this reaches in the
current corpus and backlog: Rényi, Lévy, Erdős, Pólya, Teichmüller,
Poincaré, Kármán, Hölder, Schrödinger.

Evidence: 2026-09-19 ideas run, `/tmp/screen5.py`; three URLs, two failures,
both with the name in the page title.

## `RealBall` has no `psi(n)` and no `bessel_I`; the Hurwitz zeta and a complex ball are the way round

What happened: two of the checks this run needed were a trigamma value and a
modified Bessel value, and the obvious spellings both raise:

    RBF(QQ(7)/2).psi(1)      -> TypeError: psi() takes exactly 0 positional
                                arguments (1 given)
    RBF(6).bessel_I(0)       -> AttributeError: 'RealBall' object has no
                                attribute 'bessel_I'

`RealBall.psi` is the digamma and takes no order. The polygamma of order $n$
is the Hurwitz zeta, which `RealBall` does have:

    trigamma = lambda a: RBF(2).zeta(a)          # psi'(a) = zeta(2, a)
    RBF(2).zeta(RBF(3)) == RBF.pi()**2/6 - RBF(5)/4      # checked

and `bessel_I` lives on `ComplexBall`, not on `RealBall`:

    CBF(6).bessel_I(CBF(0)).real()       # I_0(6) = 67.23440697647797532...

Both of these are needed by any table whose closed form contains a polygamma
of order at least one -- which is every entropy, divergence and Fisher
information formula for a shape family -- or a Bessel $I$, which the von Mises
and the Rényi-entropy-of-a-Poisson formulas do.

What the skill says now: it lists what the named imports do not bring
(`RealBall.str`, root finding, `QQ('1.25')`) and it lists what arb implements,
including "Hurwitz `zeta(s, a)`" and `bessel_J`, without saying that the
polygamma is only reachable *through* the Hurwitz zeta or that `bessel_I` is
complex-only.

What it should say: add to that list. `RealBall.psi` is the digamma alone and
takes no order; $\psi^{(n)}(a)=(-1)^{n+1}n!\,\zeta(n+1,a)$ is reached through
the Hurwitz zeta, `RBF(n+1).zeta(a)`, so it alternates in sign with $n$ and is
positive for odd $n$. `bessel_I` and `bessel_K` are `ComplexBall` methods
and want a ball order, `CBF(x).bessel_I(CBF(nu))`; and `gamma_inc_lower` is on
neither, so a regularised incomplete gamma has to be integrated or summed.

Evidence: 2026-09-19 ideas run, `/tmp/final2.py`, `/tmp/final3.py`,
`/tmp/bes.py`.

## Ask whether the natural grid makes the values rational before proposing the table

What happened: this run proposed five divergences and refused three more, and
every refusal came from the same one-line computation -- evaluating the closed
form on the obvious pair and looking at what came out.

    chi2(Gamma(3,1) || Gamma(5,1))  = 5            exactly
    chi2(Gamma(5,1) || Gamma(3,1))  = 3/2          exactly
    chi2(Gamma(3,1) || Gamma(7,1))  = infinite
    W_1(Exp(1), Exp(3))             = 2            exactly, = |mean difference|
    Fisher information of Gamma(a,1) = psi'(a)      already an entry of T250
    D(N(m1,s) || N(m2,s))           = (m1-m2)^2/2  always rational
    D(Beta(2,3) || Beta(3,2))       = 1/2          exactly
    D(Beta(2,4) || Beta(4,2))       = 5/3          exactly

Three of those refuse a whole table; the last three refuse a *slab* of a table
that is otherwise good, and the slab has to be named in the proposal because
nothing else will find it. The pattern is that a quantity which is a
*polynomial* in the parameters, or which telescopes through a digamma
difference at integer arguments, comes out rational on exactly the grid a
builder would choose first.

What the skill says now: it says a family whose values are a handful of small
integers makes search worse for everybody, and it says to decide exactness
from the definition and not from the digits. Both are about a table already
being built.

What it should say: the same test belongs one stage earlier, as a computation
rather than a judgement, and it is cheap. Before proposing a family, evaluate
it at two or three of the parameter values the table would obviously hold, and
ask whether the answer is rational or a small surd. If it is, either the family
is refused, or the rational slab is excluded and named -- and which of the two
is a decision the proposal has to make, because a builder who meets
`KL = 1/2` will store a hundred zeros after the decimal point rather than
notice.

Evidence: 2026-09-19 ideas run, `/tmp/final.py` and `/tmp/final2.py`; three
tables refused and three exclusions written into the batch's conventions.

## A cross-check against a stored table has to be checked against the stored table's range, not its title

What happened: two of this batch's checks were written as "this value is a row
of T197" and "this value is a row of T196", from the titles, which are *Values
of the error function* and *Values of modified Bessel functions of the first
kind*. Both were wrong.

    T197  holds erf(x) at every two-decimal x in [0,10]
          the value wanted is erf(1/(2 sqrt 2)) = erf(0.35355...)   not a row
    T196  holds I_nu(x) for x = a/b in lowest terms, b <= 4, x <= 5
          the value wanted is I_0(6)                                not a row
          but I_0(2 lambda) for lambda <= 5/2 is a row              usable

Reading `Data properties.complete-note` and the keys of `Numbers` took one
call each and turned one false claim into a correct and *more* useful one: the
Gaussian rows of a total variation table are error-function values at
irrational arguments, which is a reason for the table rather than a check on
it, and the Poisson rows of a Rényi entropy table check against T196 for the
half of the range where $2\lambda\leq5$.

What the skill says now: "Check new values against something independent" and
"A reference to a table here is worth more than a link to Wikipedia".

What it should say: a table's title says what family it holds and its
`complete-note` says which members. A cross-check, and a `Similar tables`
relation, has to be written against the second. Read
`numberdb.table('T196')['Data properties']['complete-note']` and the keys of
`Numbers` before claiming a value is stored there; the claim is what a builder
will try to run.

Evidence: 2026-09-19 ideas run, `/tmp/chk.py` and `/tmp/chk2.py`; two claims
in the draft batch corrected before it was written out.

## `GET /api/table` answers "does not exist" with HTTP 200, not 404

What happened: I probed T442-T449 with `urllib`, wrapping each call in
`try/except urllib.error.HTTPError` and treating anything that did not raise as
a table that exists. Nothing raised. I read the output as T446, T447, T448 and
T449 all being real tables holding zero numbers -- four empty drafts -- and
that is wrong. They have never existed. The endpoint had answered

    HTTP/1.1 200 OK
    {"error": "Table with id 'T446' does not exist."}

and `len(doc.get("Numbers", []))` is 0 on an error body exactly as it is on an
unfilled draft. Asking again and printing the whole body is what separated
them. The mistake matters here in a specific way: "T446 is an empty draft I own"
and "T446 does not exist" differ over whether a draft slot is spent, and the
allowance is five.

This is not the rate limiter and not a proxy. `numberdb_app/api.py:392`,
`:398`, `:404` and `:415` each `return JsonResponse({'error': ...})` with no
`status=`, so Django sends 200. `:415` is the same answer for a draft you may
not see, which is the point the companion proposal makes.

What the skill says now: nothing about the HTTP status of this endpoint. It
describes what `numberdb.table(...)` returns, and the client *does* raise
`NumberDBError` here -- so a contributor who stays inside the client never
meets this, and one who writes ten lines of `requests` around the documented
`GET /api/table?id=Tnnn` meets it immediately.

What it should say: when you call the API directly rather than through the
client, **check the body, not the status.** `GET /api/table` returns 200 with
an `error` key for a table that does not exist, for a URL that matches
nothing, and for a draft your key may not see. `resp.raise_for_status()` and
`if resp.ok:` both pass. The test is `"error" in doc`, before anything that
reads `Numbers`.

Evidence: 2026-09-23, against numberdb.org with a configured key.

    >>> r = urlopen(Request("https://numberdb.org/api/table?id=T446",
    ...                     headers={"Authorization": "Bearer " + key}))
    >>> r.status
    200
    >>> json.load(r)
    {'error': "Table with id 'T446' does not exist."}

    >>> # same shape of call, a real but unfilled draft:
    >>> json.load(get("/api/table?id=T445"))["Numbers"]
    []

`numberdb_app/api.py:386-416`.

## A draft offered for review still occupies one of your five slots, and no API call lists which drafts you hold

What happened: I wanted the count of unpublished tables zeta3 holds, and there
is no endpoint that answers it. `GET /api/drafts` is a 404 -- there is no such
route; `drafts` at `numberdb_app/urls.py:81` is a *page*, `views.drafts`, and
the API routes at `:40-55` have no counterpart. Search and lookup are no help
by design, since a draft answers neither. What I did in the end was probe
consecutive T-numbers one at a time, which is how I met the lesson above.

The figures do exist, but only as a side effect of writing: `POST /api/tables`
returns `drafts_held` and `drafts_remaining` beside the new `tid`
(`api.py:1066`), and the refusal at the ceiling quotes the count too. So the
cheapest way to learn how many drafts you hold is to create one, which changes
the number you were asking about.

The second half is the part that can strand a careful contributor. `held` is
`Table.objects.filter(created_by=user, published=False).count()`
(`permissions.py:321`) -- *unpublished*, not *unoffered*. Offering a draft for
review sets `ready_for_review = True` and nothing else (`api.py:832`); the
table stays unpublished until somebody reviews it, and review is a person's
act on somebody else's schedule. So five drafts finished, offered and waiting
is five slots spent, and the sixth `POST /api/tables` with `X-Draft: yes` is
refused. Doing the work correctly and handing it over is precisely what fills
the quota.

What the skill says now: that a draft "is invisible, in no listing, answers no
search", that offering it is a separate act from publishing, and that step 4 is
not yours to expect. It does not say the drafts in flight are counted, that
offering does not decrement the count, or that `/drafts` -- the page -- is the
only listing of them.

What it should say: two sentences beside the publishing steps.

* **Keep your T-numbers.** There is no API call that lists the drafts you
  hold; `/drafts` on the site is the only listing, and a T-number lost from a
  transcript can only be found by probing. `POST /api/tables` reports
  `drafts_held` and `drafts_remaining` in its reply -- read them from the
  creation you just did rather than making one to find out.
* **The limit counts drafts unpublished, not drafts unoffered.** Offering for
  review does not free the slot. If you are working through a batch, expect to
  reach the ceiling while every draft you hold is finished and waiting on
  somebody, and plan the batch around five in flight rather than five in
  progress.

Evidence: 2026-09-23, against numberdb.org.

    >>> urlopen(Request("https://numberdb.org/api/drafts",
    ...                 headers={"Authorization": "Bearer " + key}))
    HTTPError: HTTP Error 404: Not Found

`numberdb_app/urls.py:40-55` (no `api/drafts`) and `:81` (`drafts` is a page);
`numberdb_app/permissions.py:305-322` for `draft_ceiling` / `draft_allowance`
and the `published=False` filter; `numberdb_app/api.py:1055-1067` for
`drafts_held` / `drafts_remaining`, `:984-993` for the refusal, and `:832` for
offering setting only `ready_for_review`.

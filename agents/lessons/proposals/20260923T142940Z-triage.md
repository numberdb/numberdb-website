## `/api/search` is the *expression* endpoint, and any other parameter gets you `results: []` at HTTP 200 with no message — which is what "is this table already here?" looks like when it silently did not run

What happened: step 1 of the skill is "Look at the database before writing
anything", and the first question it asks is whether the family is already
held. I wanted that answer for *Tammes problem: the minimum angle of the best
known spherical codes*, from a script rather than from the client, so I called
the endpoint whose name is the question:

    GET /api/search?q=Tammes
    200  {"results": [], "messages": [], "time_request": "0.000s"}

Nothing is covered, then. That conclusion was wrong, and nothing in the
response says so. The same answer comes back for a term the corpus certainly
holds, which is how I caught it:

    GET /api/search?q=zeta        -> 200  {"results": [], "messages": [], ...}
    GET /api/search?q=Airy        -> 200  {"results": [], "messages": [], ...}
    GET /api/search?q=packing     -> 200  {"results": [], "messages": [], ...}

`/api/search` is not a text search at all. It is the *expression* search — the
one call that forks a sandboxed Sage process on the server — and
`numberdb_app/api.py` reads exactly one parameter:

    program = request.GET.get('expression', default=None)
    if program == None:
        return wrap_response(None, messages)      # messages is still []

So an unrecognised parameter is not an error. It is a no-op that serialises
`results: None` as `[]` and returns 200. `?q=`, `?text=`, `?term=` and a bare
`/api/search` with no query string at all produce **byte-identical** answers,
with or without an API key:

    GET /api/search?q=Tammes     (Bearer key)  -> 200  {"results": [], "messages": [], "time_request": "0.000s"}
    GET /api/search?text=Tammes  (Bearer key)  -> 200  identical
    GET /api/search              (Bearer key)  -> 200  identical
    GET /api/search?q=Tammes     (no key)      -> 200  identical

The endpoint does work when addressed correctly, which is the point — there is
no outage to notice:

    GET /api/search?expression=pi  -> 200  7 results, time_request "0.342s"

**The text search is a different route**: `/api/lookup?text=...`, which is what
the client's `numberdb.search_text` posts to (`clients/python/numberdb/__init__.py:724`,
`return _lookup({'text': text}, client)`). It answers the question I was
actually asking:

    GET /api/lookup?text=Tammes                 -> {"results": [], "tags": [], "tables": [], ...}
    GET /api/lookup?text=matrix+multiplication  -> tags: ["matrix multiplication"], tables: 12
    GET /api/lookup?text=circle+packing         -> tables: 1  ("Best known packings of equal circles in a circle")

Tammes really is uncovered — but I only know that because I asked the right
route. The two answers agree by accident, and for any term that *is* held they
disagree completely.

**Two tells distinguish the silent no-op from a real empty result**, and both
are in the body:

* `/api/lookup` always carries `tags` and `tables` keys. `/api/search` never
  does. If the JSON you got back has no `tables` key, you did not run a text
  search, whatever you passed.
* `time_request` is `"0.000s"` exactly. Nothing ran. A real query — even one
  matching nothing — costs 0.03s or more; the expression search costs 0.3s.

This is the same failure shape as the `/drafts` lesson already proposed
(success-looking HTTP hiding a non-answer), but the cause and the check are
different: there is no redirect here, `response.url` is unchanged, the status
is a genuine 200 from the view that was meant to handle it, and the key is
irrelevant. Checking `r.url` — the fix that catches `/drafts` — catches nothing
here.

The direction of the error is the bad one. It reports that the corpus is empty
of your subject, at the exact moment the skill tells you to check whether your
subject is already in the corpus, and the reward for believing it is a
duplicate table.

What the skill says now: it teaches this step through the client only —
`numberdb.search_text('Chebyshev')  # titles and tags` — with three warnings
about that call (`.tables` is an object not a list; the search stems; there is
no call that lists the corpus). It never names an HTTP route, so a contributor
working in `curl` or `requests`, or one who has not installed the client, has
only the endpoint names to go on, and the one named "search" is the wrong one.

What it should say:

- The corpus text search is **`GET /api/lookup?text=...`**, returning `results`
  (numbers), `tables` and `tags`. `numberdb.search_text` is a wrapper on it.
- **`GET /api/search` is the Sage-expression search and reads only
  `?expression=`.** It is the most expensive call on the server. Any other
  parameter — including none — returns `200 {"results": [], "messages": []}`
  with no indication that it ignored you.
- An empty answer from this site is worth one second of suspicion before you
  believe it. For the text search, check that the body has a `tables` key; a
  `time_request` of exactly `0.000s` means nothing ran.

# Lessons proposed by the T2 critique, 2026-09-22

One, met while reading T2 (*Integers*) against <https://numberdb.org/skill>. It
is reachable by a contributor with a laptop, Python and the client package, and
it is not about this deployment.

It is about the search box and it is **not** the lesson
`20260921T223734Z-critique.md` proposed twelve hours ago. That one is about
rank: a one-word title scores one occurrence and loses to long titles that
repeat the word, because `ts_rank` is not normalised by document length. Its
conclusion is that a table named after a common word will be findable by value
and by a distinguishing phrase in `Keywords`, and to prefer a title containing
a word only this family uses.

This one is about the case that advice does not cover. "Integers" *is* a word
only this family uses, and the query still does not return the table — because
the word the reader types and the word the results contain are not the same
word.

I did not repeat the rank measurement; that file has it, and I take it as read.
I also left out the anonymous rate limit, which `PROPOSALS.md` already carries
and `20260921T201824Z-critique.md` extends.

## The last word of a search is a prefix, so a query can match a different word: "integer" returns twenty integrals and not the Integers

What happened: T2 is called "Integers". Typing `integer` into the search box
answers "22 results", and **T2 is in none of them**:

    Tags
      integral   2 tables, 1003 numbers
      integer    3 tables, 3 numbers
    Tables
      Values of the Fresnel sine integral $S(x)$            T207
      Values of the Fresnel cosine integral $C(x)$          T208
      Values of the Clausen functions ...                   T175
      Values of Dawson's integral $F(x)$                    T206
      ... sixteen more, every one of them an integral

Not one of the twenty is about integers. The same for `integers` and
`Integers`; `whole numbers` returns nothing at all.

The cause is not the competition the earlier lesson describes. `full_text_query`
(`numberdb_app/search.py:569`) asks the **last word of a term as a prefix**, so
that the dropdown can complete a word while somebody is typing. `integer` stems
to `integ`, and `integ:*` is a prefix of the indexed `integr` of "integral" as
well as of the `integ` of "Integers". The collision is one-way — searching
`integral` stems to `integr`, which is not a prefix of `integ`, and does not
drag T2 in — so the query the reader typed is answered almost entirely by
tables about a different subject, and then rank decides among those.

Two consequences a contributor cannot guess:

* **A distinctive title does not protect you.** The earlier lesson's advice is
  to choose a word only this family uses. "Integers" satisfies that and the
  search still fails, because the word that beats it is not "integers" — it is
  a longer word this family has nothing to do with. The test has to be run, not
  reasoned about.
* **`Tags` is the channel that survives.** `search_metadata` runs two separate
  queries with separate limits, one over `Tag` and one over `TableSearch`, so a
  tag is ranked against other tags and never against tables, and the rendered
  page prints the tags above the tables. A tag therefore reaches a reader that
  neither the title nor `Keywords` reaches — which is the gap the earlier
  lesson names when it says Keywords cannot rescue a buried title, since
  Keywords sit at the title's own weight. The corpus has a tag `integer`; the
  table called Integers does not carry it, so the one route that works for this
  query leads to Zero, One and 42 and not to the integers.

What the skill says now: "A title is what a search reaches. The text index has
four weights", then the test "*what would somebody type who is holding one of
these numbers and wants to know what it is?* If the title does not contain that
word, put it in `Keywords`, which is the same weight". It also says "Prefer an
existing tag; a tag list is a way through the corpus". All true, and all of it
reads as though a title containing the word settles the matter.

What it should say, added to that paragraph:

> Then check it, because a title that contains the word can still not be
> returned: the last word of a search is asked as a prefix, so `integer` also
> matches `integral` and a table can be crowded out by tables about something
> else entirely.
>
>     numberdb.search_text('integer').tables     # is your table in it?
>
> If it is not, carry the word as a `Tag` as well. Tags are ranked among tags
> rather than against tables and are shown above them, so a tag answers a query
> the title has lost.

Evidence, 2026-09-22, live corpus:

| term | result |
|---|---|
| `integer` | 20 tables, T2 absent; tags `integral`, `integer` |
| `integers`, `Integers` | the same 20, T2 absent |
| `integer ring` | **T2 first**, then T1, T0 — T2 is indexed and reachable |
| `integral` | T188, T349, T191, … — T2 absent, the collision is one-way |
| `rational` | T30 "Rational numbers" sixth — a one-word title normally survives |
| `additive identity` | T0 — `Keywords` work, as the earlier lesson says |
| `7` | **T2 first** — the table answers by value |

The rendered page is <https://numberdb.org/?q=integer>; the rest is
`numberdb.search_text` from the published client. `/tags/integer` lists T0, T1
and T42.

## Do not cache a stateful analytic evaluator just because its inputs are fixed

What happened: the level-one cusp-form $L$-value generator first cached
Sage/Dokchitser `lseries` objects by weight, embedding and precision. A
private dry run passed, but the independent PARI comparison found
`k=30, i=1, s=16` written as a wide interval centred at
`0.773048876978528...`, while PARI gave
`0.733903460717375...`. Evaluating that same entry fresh gave the PARI
value. Replaying the checker showed that the cached 120-digit Sage
`lseries` object had drifted after earlier evaluations and interleaved PARI
work; the 80-digit object still gave the right value, and `numberdb.agreeing`
correctly widened the interval instead of pretending to have 30 digits.

What the skill says now: it says to check a generator against an independent
computation and to compare at two precisions, but nothing about stateful
numerical objects whose later evaluations can depend on earlier calls.

What it should say: do not cache analytic evaluator objects such as Sage
`lseries`/Dokchitser objects across a whole table unless a replay check proves
that repeated use is stable. Cache the algebraic data and create a fresh
evaluator for each stored value, or make the independent check walk the same
order as the generator so it can catch state drift. A wide interval from
`numberdb.agreeing` is a failure to chase, even when exactness says the value
carries its own error bound.

Evidence: `/tmp/check_level_one_lvalues_pari.py` first failed with
`k=30 i=1 s=16: Sage 0.773048876978528259950483043789 +/- 0.0391
contradicts PARI 0.733903460717375145506258009598`. After the generator
stopped caching `lseries` objects, the same checker reported
`checked 681 stored 30-digit values against PARI lfunmf`.

## PARI L-function precision and checks are bit-oriented

What happened: two PARI details were easy to misread while building the same
table. First, changing display or decimal precision was not enough for the
program examples: passing an explicit bit precision to `lfun`, or setting
`realbitprecision`, was needed to reproduce the displayed digits. Second,
`lfuncheckfeq` does not return true or false. It returns a bit-error exponent,
and a large negative value is the good result.

What the skill says now: it says to pass explicit bit precision to PARI/Sage
where exactness matters only indirectly, and to check formulas, but it does
not name `lfuncheckfeq`'s return convention.

What it should say: for PARI L-functions, set or pass bit precision, not just
decimal display precision, and remember that `lfuncheckfeq` is successful
when it returns a large negative integer of the order of the working bit
precision. A positive value, zero, or a value close to zero is the warning
case.

Evidence: `lfun(lfunmf(mf)[1][1], 6, 0, 330)` and
`Newforms(1, 12, names="a")[0].lseries(prec=330)(6)` both printed
`0.792122838646030569355944890486...`. The functional-equation check over
the 24 embedded level-one cusp-form L-functions returned values from `-66`
to `-79` at 330-bit working precision.

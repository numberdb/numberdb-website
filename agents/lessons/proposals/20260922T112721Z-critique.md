# Lessons proposed by the T410 critique, 2026-09-22

Not in force. See `agents/lessons/PROPOSALS.md` for what this file is.

## `complete` takes `yes` or `no`, and the page prints whatever you wrote

What happened: draft T410 stored `complete: false` under `Data properties`.
The renderer prints the value verbatim -- `text += escape_maths(value)` in
`table_context` -- so the page reads "Table is complete: **false** (it holds
every curve ...)". Every other table in the corpus reads "no". Sampled by API:
T5 `yes`; T25, T60, T99, T130, T175, T220, T265, T310, T360, T395, T406, T407,
T408 all `no`; no other spelling appears. Nothing refuses `false`:
`numberdb_app/validate.py` does not mention the field, `audit_table` does not
check it, and the audit on T410 reported `clean: true`. A YAML author who
writes the unquoted boolean `false` gets the same page, because the renderer
loads the document with `yaml.BaseLoader` and every scalar arrives as a string.

What the skill says now: it quotes the rendered sentence -- 'It renders inside
"complete: no (...)", so write a clause that finishes that sentence' -- and so
implies `no` without ever saying that the field is a word rather than a
boolean. Somebody writing YAML reaches for `false` because YAML has booleans.

What it should say: in the `Data properties` row of the section table, or
beside the `complete-note` rule: `complete` is `yes` or `no`, spelled that way,
because the page prints it into the sentence "Table is complete: ___". `false`
and `true` are valid YAML and render as themselves.

Evidence: `GET /api/table?id=T410` -> `"complete": "false"`; the same call on
T406 -> `"complete": "no"`; `/preview` of T410's Data properties renders
"Table is complete: false (it holds every curve in Sage's mini Cremona
database [2] with conductor $N\leq100$ ...)".

## When the quantity is constant on a coarser equivalence than the index, say so in a comment

What happened: T410 stores the Mazur-Tate-Teitelbaum $\mathcal{L}$-invariant
for each elliptic curve of conductor $N\leq100$ at each of its split
multiplicative primes. 214 entries; 57 distinct values. The repetition is a
theorem: an isogeny of degree $d$ multiplies both $\log_p(q_E)$ and
$\operatorname{ord}_p(q_E)$ by $d$, so $\mathcal{L}_E$ is constant on an
isogeny class. Grouped by (Cremona isogeny class, $p$) the 214 entries fall
into 58 groups and every group holds exactly one value. Nothing on the page
says this, so a reader meeting eight identical fifty-digit $p$-adic numbers
under `90c1`..`90c8` cannot tell a theorem from a column somebody filled by
copying.

This is general. A table indexed by objects, holding a quantity that is an
invariant of something coarser -- an isogeny class, a commensurability class,
a Galois orbit, a similarity class of lattices -- will show blocks of equal
values, and the reason is the most interesting fact on the page.

What the skill says now: "Where a value looks surprising the fact is the
explanation", which is about one value. And "the same family twice by
accident", which is about two tables. Neither covers a table whose own rows
repeat each other for a reason.

What it should say: where a stored quantity is constant on an equivalence
coarser than the table's index, say so in a comment, with the reason. Keep the
finer index if that is what a reader holds -- somebody has a curve, not an
isogeny class -- but do not leave the repetition unexplained. It is also the
check that catches the opposite case: blocks of equal values with no theorem
behind them are a bug in the generator.

Evidence: T410 as read on 2026-09-22; 214 entries, 57 distinct values, 58
(class, prime) pairs each with one value. The one cross-class coincidence is
also mathematics -- `40a` and `80a` agree at $p=5$ because `80a` is the twist
of `40a` by $-1$ and $-1$ is a square in $\mathbb{Q}_5$.

## The missing preparser bites at API boundaries, not only at division

What happened: T410's `Programs` snippet is Sage, and correct Sage:

    E = EllipticCurve('11a1')
    p = 11
    precision = 49
    E.tate_curve(p).L_invariant(prec=precision)

Run from a file under `sage -python`, to check that it reproduces a stored
value, it died on the third line:

    AttributeError: 'int' object has no attribute 'is_prime'

from `ell_tate_curve.TateCurve.__init__`, which does `if not p.is_prime()`.
There is no preparser in a `.py` file, so `11` is a Python `int` and not
`Integer(11)`, and the Sage function calls an `Integer` method on it. Wrapping
both arguments in `Integer` fixed it and the snippet then reproduced the
stored value character for character, all fifty digits, for `11a1` at $p=11$
and `89b1` at $p=89$.

What the skill says now: "`sage -python` has no preparser, so `factorial(30)`
is a Python `int` and `factorial(n) / k` is *float* division -- exact up to
2^53 and quietly wrong after it." That is the arithmetic half, and it warns
about a wrong answer.

What it should say: the other half, which is louder and easier to diagnose
once you expect it -- a Sage function handed a Python `int` may simply raise
`AttributeError: 'int' object has no attribute 'is_prime'` (or `.nbits()`,
`.valuation()`, ...), because much of the Sage library calls `Integer` methods
on its arguments. It is not a bug in the snippet being tested: the same lines
work in the Sage REPL and in a `.sage` file. Wrap literals in `Integer` when
running a `Programs` snippet from a `.py` file, and do not "fix" the snippet
on the strength of the traceback.

Evidence: 2026-09-22, `/tmp/t410_programs_check.py` under `agents/sage.sh`,
before and after the `Integer(...)` wrapping.

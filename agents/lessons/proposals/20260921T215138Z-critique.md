# Lessons proposed by the T0 growth critique, 2026-09-21

One, met while reading T0 (*Zero*) against <https://numberdb.org/skill>. It is
reachable by a contributor with a laptop, Python and a browser; it is not about
this deployment. It refines rather than repeats the second lesson in
`20260921T211050Z-critique.md`, which is about the same search box seen from
the other side, and the two should be read together if either is promoted.

---

## The search box answers a bare integer with the table of that number, so "type your value and see if your table comes up" can be a false positive

What happened: T0 holds the exact integer 0, and `/api/lookup?text=0` returns
`tables: [T0]` — which looks exactly like the check an author wants after
publishing ("my number is in the box, my table comes back"). It is not that.
The term was read as a **table's own number**, and T0 came back because this
table is table zero. The same request would have answered the same if the table
held nothing like 0 at all.

`numberdb_app/search.py:662–670`, in `search_metadata`, is explicit about why:

    #A table's own number, typed straight in. `T12` is how a table is
    #cited, so it is a thing somebody arrives holding -- and it found
    #nothing at all, because a number is not a word and the text index
    #has never held one. Answered directly rather than indexed ...

    numbered = _table_by_number(term)
    if numbered is not None:
        return [], [numbered]

The early return is the trap: when a bare integer names a table, the text search
**is not run at all**, so the `tables` channel of the response holds that one
table and nothing else — no title match, no keyword match, nothing that would
have been found on the merits. Measured against the live corpus: `text=376`
returns only T376 ("Twisted Kloosterman sums modulo a prime"), `text=29` only
T29 ("Rational multiples of pi"), `text=7` only T7 ("Pi"), `text=0` only T0.
None of those tables has the queried digits anywhere in its title or keywords.

Three consequences an author cannot guess:

* **A bare integer is a table citation, not a search.** Any author whose table
  number is small enough to be typed as a plain number will see their own table
  returned for it, whatever the table holds.
* **The coincidence is not rare among exactly the tables where it misleads.**
  A table of a small named integer *is* likely to have a small ID, because the
  corpus was numbered from the simplest objects outwards: T0 holds 0, T1 holds
  1, T42 holds 42. For those three the query, the value and the ID are the same
  string, and the response cannot be told from a working search by value.
* **It is two channels, and only one of them is about the numbers.** The
  companion lesson's finding — that `text=1` never returns the table called One
  — is about `results`, the number channel. The `tables` channel *does* return
  T1 for `text=1`, by table number. Both are true at once, and an author reading
  one response sees the second and concludes the first.

What the skill says now: nothing. Section 1 covers `search_text` for titles and
tags; section 3 warns that small-integer values "match everything and tell
nobody anything". Neither says that a query which is a bare integer is answered
as a citation before any search happens, nor that the lookup response carries a
`tables` list and a `results` list which answer different questions.

What it should say: a query that is a plain integer is read first as a **table
number** — `0`, `7`, `376` return T0, T7, T376 and run no text search at all —
so it can never confirm that a value is findable. To check that an entry is
reachable by its value, read the `results` list and not the `tables` list, and
use a query with enough significant digits to bring the result set under the
hundred-result cap. For a named constant, what actually carries a reader to the
table is the title and `Keywords`: check those with a word query instead
(`zero element` returns T0 first; `additive identity` returns nothing, because
neither word is in the title, the keywords or the definition).

Evidence: 2026-09-21, T0 growth review (`agents/critiques/T0-growth.md`). The
`/api/lookup` queries above with an API key against the live corpus:
`text=0` → `tables: [T0]`, 100 capped number results with T0's own entry at
rank 28, identical across three successive requests; `text=376` → `[T376]`;
`text=29` → `[T29]`; `text=7` → `[T7]`; `text=zero` → 0 results and 20 tables
with T0 fourteenth, behind thirteen "Zeros of …" tables; `text=zero element` →
T0 first; `text=additive identity` → nothing in any channel.
`numberdb_app/search.py::search_metadata` for the `_table_by_number` early
return and the `_looks_like_a_number` guard immediately after it, which is what
makes the search silent rather than merely unhelpful for a numeric term that
names no table.

## Empty-draft preflight upserts can fail before a generator sends entries
What happened: after claiming draft T319 with prose and no `Numbers` section,
`numberdb.Generator.publish()` failed before sending any Shapiro polynomial
entries. Its preliminary empty upsert to `/api/table/T319/entries` was refused
with `NumberDBError: A value in these entries cannot be read as a number.
'str' object has no attribute 'items'`. Sending the checked records directly
through the entries endpoint succeeded, and the attached generator then
verified the stored draft as `8/8 matched`.

What the skill says now: it says to create a draft before building and then
fill it with a generator, and it explains that a draft may have no numbers.
It does not say what to do when the client preflight refuses an empty draft
before any entry is sent.

What it should say: if a claimed draft has no `Numbers` section and
`Generator.publish()` fails during its empty writability check, do not change
the values to work around it. Send the checked entries through the entries
endpoint directly, attach the generator, and then run `verify(sample=None)`
against the stored draft. The failure is in the preflight, not in the computed
numbers.

Evidence: T319 on 2026-09-18. The failed command was
`cat "$NUMBERDB_KEY_FILE" | NUMBERDB_KEY_FROM_STDIN=1 NUMBERDB_PUBLISH=1
agents/sage.sh generators/shapiro-polynomials/generate.py`; the direct entries
fill returned revision
`9c2e592adebf8b7faf253533df0c342add840184da6976b13b1dbd10ba2a0296`, and the
final verification reported
`<VerifyReport T319: 8/8 matched, 0 differing, 0 missing, 0 extra>`.

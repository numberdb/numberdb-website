## Normalise punctuation before trusting a draft-title claim

What happened: the proposal title used an en dash, `Tracy–Widom`, so creating
the draft title `Values of the Tracy–Widom distribution functions
$F_\beta(s)$` succeeded as T450. The same table had already been filled as
T441 under the ASCII-hyphen title `Values of the Tracy-Widom distribution
functions $F_\beta(s)$`. Exact title uniqueness did not catch the duplicate,
and the public text search could not see T441 because it was an unpublished
draft. Reading the local generator then the keyed table API showed that T441
already held the 903 entries.

What the skill says now: claim by creating the draft, and if the title is
refused, use the table named by the refusal. It does not say that typographic
punctuation can let the same title through as a different string.

What it should say: before creating a second draft for a proposal whose name
contains typographic punctuation, search and read keyed drafts for a
normalised title too: at least compare en dash, em dash, minus and ASCII
hyphen variants, and normalise Unicode punctuation when checking whether a
nearby hidden draft is the same table. If a duplicate empty draft is created
by mistake, leave it empty and say so, so a person can clear it.

Evidence: T441 read with the API key had title `Values of the Tracy-Widom
distribution functions $F_\beta(s)$` and top-level `Numbers` keys `1`, `2`,
`4`; T450 had the en-dash title and no numbers. T441 was verified and offered
for review; T450 was left empty for cleanup.

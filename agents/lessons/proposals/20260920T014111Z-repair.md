## Stale attached files need a deletion path, not a replacement
What happened: T293's `/files/T293` page still carries `curve_data.py`, `generate.py`, and `t293_generate.py`. The live `generate.py` reproduces the table, but `curve_data.py?raw=1` says the table uses only $D\in\{5,8,12,13,17\}$, while the table now has six fields including $D=21$. The right repair is to detach `curve_data.py` and the duplicate working copy `t293_generate.py`, but the public file endpoint accepts only `POST` or `PUT` with nonempty bytes for a named file. It can attach or replace a file, not delete one.

What the skill says now: `generate.py` is the program that reproduces and extends the table, and it should be attached. It does not say what to do when a table has extra stale attachments.

What it should say: after changing the files that belong with a table, check `/files/<tid>` as well as the table page. If an attachment is obsolete, detaching it is different from replacing it with a note or another script; use a deletion path when one exists, and otherwise leave it for a person rather than committing through a private server-side helper.

Evidence: T293 repair on 2026-09-20. `curl https://numberdb.org/files/T293 | rg 'curve_data.py|generate.py|t293_generate.py'` showed all three files; `curl https://numberdb.org/files/T293/curve_data.py?raw=1 | sed -n '1,6p'` showed the stale five-field docstring; `numberdb_app/api.py::write_file` accepts only `POST` or `PUT` with a nonempty body, while `numberdb_app/editing.py::commit_table` has the internal `files={name: None}` deletion mechanism that this run was not allowed to call directly.

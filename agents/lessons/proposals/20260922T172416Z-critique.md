# Proposed from the T413 critique, 2026-09-22

## `complete: no` and `complete: false` are different words on the page

What happened: T413's `table.yaml` in the repository says `complete: no`. The
live document holds the string `"false"`, and the table page renders
"Table is complete: **false** (…)". Every other table in the corpus renders
"no" -- T406 through T410 were checked one by one. Nothing in the stored YAML
shows the difference: `no` and `false` are the same YAML boolean, and whatever
serialised the document on the way to the API wrote the other spelling of it.
The field is not a checkbox, it is the first two words of a sentence a reader
reads, and "Table is complete: false (it holds every curve …)" is not the
sentence the rest of the corpus writes.

A contributor hits this on their own laptop the moment they build the document
in Python rather than typing it: `{'complete': False}` in a dict, or a
`yaml.safe_dump` round trip, and the word on their page changes without any
warning from the API, from `verify`, or from `audit_table` -- all three passed
T413 clean.

What the skill says now: it quotes the rendering as `complete: no (...)` and
says to "write a clause that finishes that sentence", but nowhere says that
the value is printed literally, so a boolean is not interchangeable with the
word.

What it should say: `complete` is printed on the page as written. Use the words
`no` and `yes`, quoted if your serialiser would otherwise turn them into
booleans, and read the rendered page rather than the document to check it.

Evidence: 2026-09-22. `GET /api/table?id=T413` gives
`"Data properties": {"complete": "false", …}`; `/preview` renders "Table is
complete: false"; `generators/p-adic-l-values-elliptic-curves-q-rank-0/table.yaml`
says `complete: no`; T406, T407, T408, T409 and T410 all answer `no`.
`GET /api/table/T413/audit` answers `{"findings": [], "clean": true}`.

## A `Programs` snippet should be checked against the precision the table stores, not only against its digits

What happened: T413's `Programs` snippet is four lines of Sage that return the
table's value for 11a1 at $p=5$. Run exactly as the page gives it, it returns
`… + 3*5^19 + O(5^20)`. The stored entry runs to `O(5^72)`, and the table's own
comment explains that 72 is the least $n$ with $5^n\geq10^{50}$ -- but the
snippet reaches 20, its first argument does not raise it, and nothing on the
page says which argument does. The digits that are there are right, so a check
that compares the snippet's output with the stored value agrees on every digit
it has and still leaves the reader two thirds short.

The sibling table T409 does it correctly, and the fix is one comment in the
code: `# The 44 is relative precision: 49 - v_11(q_E), giving absolute
O(11^49).`

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value." It says nothing about
precision, and a default-precision incantation is the natural thing to write.

What it should say: run the `Programs` snippet and check that it reaches the
table's own precision, not just that its digits agree. A library's default
precision is rarely the table's. Where an argument sets it, name that argument
in a comment in the snippet and show the arithmetic that gets to the stored
$n$.

Evidence: 2026-09-22, T413. `E.padic_lseries(5).series(1, prec=1).list()[0]`
returned a value in the "5-adic Field with capped relative precision 20";
T413's entry for `N=11, c4,c6=496,20008, p=5` ends `O(5^72)`; T413's
`comment-precision` states the $10^{50}$ rule; T409's `program-sage` carries
the precision arithmetic in a comment.

## A p-adic stored in Sage's printed form is findable by that text, whole or truncated

What happened: the T413 critique needed to know whether a reader arriving with
a p-adic number would be served, and draft values answer no search. The test
ran against the published sibling T409, whose entries are formatted the same
way. `GET /api/lookup?text=<value>` found the table from the full
377-character expansion, and also from a prefix closed off as
`10*11^5 + 2*11^6 + 6*11^7 + O(11^8)`. A prefix chopped without an `O(...)`
found nothing, which is right: it is not a p-adic number.

Two things worth knowing beside that. `/api/lookup?number=` wants a number
*record* -- a JSON object of the shape `/api/search` returns -- so passing the
printed value there answers "number record must be an object" rather than
searching for it; `?text=` is the parameter that takes what a person would
type. And there is no `/search` route at all; it is `/advanced-search`.

What the skill says now: it gives the two written forms for `Qp`
(`2^4 * 111736... + O(2^167)` and `Q2:1.110`) and says p-adics are searchable
by their digits, but does not say that a truncation is searchable, nor which
lookup parameter takes a typed number.

What it should say: a p-adic value stored as Sage prints it is found by that
text, and so is any truncation of it that is itself a valid p-adic -- so a
reader holding twenty digits of a seventy-digit entry still lands on it,
provided they keep an `O(p^k)`. To check this from a script, use
`/api/lookup?text=`; `?number=` expects a number record, not a printed value.

Evidence: 2026-09-22, against T409. `?text=` with the full value and with the
`O(11^8)` truncation each returned one result, `T409`. The bare prefix returned
`{"results": [], …}`. `?number=<printed value>` returned
`{"error": "number record must be an object"}`.

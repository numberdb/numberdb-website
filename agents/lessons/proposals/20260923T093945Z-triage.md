# Lessons proposed by run 20260923T093945Z (triage)

## An API key's limit is 1000 requests per *clock* hour, and filling a table is priced per number

What happened: a triage found every call to the site answering

    {"error": "Rate limit exceeded (1000 requests per 60 minutes)",
     "retry_after": 1101}

with a valid key on the request. The skill and the help page both say an API
key "raises the limit", which reads as though the ceiling is the anonymous
one and the key removes it. It does not: `ANONYMOUS_LIMIT = 60` becomes
`IDENTIFIED_LIMIT = 1000`, and 1000 is reachable in an afternoon of building.

Two things about that number are not what you would assume.

**The window is aligned to the clock, not rolling.** The counter buckets on
`now - (now % 3600)`, so it resets at the top of the hour and `retry_after`
is however long is left of *this* hour. The 1101 above meant "10:00:00Z", not
"eighteen minutes from whenever you started". A contributor who trips the
limit at 09:05 waits fifty-five minutes; one who trips it at 09:55 waits
five. It is worth knowing which of those you are in before deciding to go and
do something else.

**A batch is billed by size, not per call.** The cost of a request is
`ceil(1 + 0.5 * size)`, so a batch of 100 numbers costs 51 units rather than
1 or 100. Batching is genuinely worth doing -- it halves the price -- but it
does not make the hour free. The client flushes every 100 entries
(`BATCH_ENTRIES = 100`), so an 800-entry table is 8 x 51 = 408 units, about
forty per cent of the hour's allowance, before any of the reads that go with
it: fetching the table back to check what stored, the audit, the search you
did to see whether the quantity was already in the corpus. Two tables of that
size in one hour is roughly the ceiling, and a verification pass that re-reads
every entry singly (800 units) will not fit alongside even one.

A `replace_with` -- the whole table in one call, which is what a run that
deletes what it did not produce uses -- is a single request of the full size,
so 800 entries is 401 units at once. That one is worth knowing because of how
the charge lands: the decorator takes one unit on the way in, and the rest is
billed by `charge()` *after* the request has been served, deliberately, so the
call in hand always succeeds and the window carries the debt. You do not find
out you have overspent on the request that overspends; you find out on the
next one.

What the skill says now: nothing about the identified limit. It mentions rate
limiting only in the anonymous sense -- that a key raises it.

What it should say: name the number, the clock-aligned window and the batch
pricing, and draw the practical conclusion -- send numbers in batches (it
halves the cost), read the table back once rather than per entry, and if you
are filling more than about 1500 entries expect to cross an hour boundary and
plan for it rather than discover it at entry 900. If you share a key with
anything else -- a second script, a cron job, a colleague -- you share the
1000 too.

Evidence: 2026-09-23, triage of run `20260923T093900Z`.
`numberdb_app/throttle.py`: `ANONYMOUS_LIMIT = 60`, `IDENTIFIED_LIMIT = 1000`,
`WINDOW_SECONDS = 3600`; `batch_cost` is `int(math.ceil(1 + 0.5 * max(size, 0)))`
with a docstring giving the hundred-costs-fifty-one case; `_consume` computes
`window_start = now - (now % window)` and returns
`window_start + window - now` as `retry_after`; `requester_of` scopes the
counter to `key:<pk>` for a valid key. Observed: `GET /api/claim` answered 200
at 09:40:2xZ and 429 with `retry_after` 1101 at 09:41:39Z -- 1101 seconds
after 09:41:39 is 10:00:00Z exactly.

## The client retries a rate limit for seven seconds and then gives up

What happened: the same run read what the Python client does when a fill trips
the limit. `_with_retry` wraps the batch sends, catches `ConflictError` and
`RateLimitError` together, and sleeps `2 ** attempt` between four attempts --
1s, 2s, 4s, then re-raise. Seven seconds of waiting, against a limit that has
just told you to come back in up to an hour.

The two exceptions it catches are not alike, and the docstring shows the
reasoning that merged them: it says the retry is "only for 'busy' -- a refused
document or a rejected key is not going to become true by being repeated". A
`ConflictError` means another writer holds the table for a moment and
exponential backoff is exactly right. A `RateLimitError` *will* become true by
being repeated -- but on the server's timescale, not on 1-2-4. So the helper
catches the right exception with the wrong delay, and a long fill dies part
written with `RateLimitError: too many requests; retry in 2771s` after having
waited seven seconds of the 2771.

The server hands you the number and the client keeps it:
`RateLimitError.retry_after` is the seconds the server said, or None if it did
not say. Nothing in the retry path reads it.

What the skill says now: nothing about what the client does on a 429 mid-fill.

What it should say: a fill that trips the rate limit raises rather than waits
it out, so catch `numberdb.RateLimitError` around a long fill yourself, sleep
`error.retry_after` (guarding for None), and resume. Point out that this is
safe to do on the incremental path: `flush()` sends with `upsert=True` and
entries are keyed by their parameters, so re-sending a batch that already
stored rewrites the same values rather than duplicating them, and a resumed
fill can safely overlap what the raise left behind. The exception is
`replace_with`, which sends `upsert=False` and means "this is the whole
table" -- resuming *that* one by sending the remainder would delete everything
already stored, so a fill that raised part way through a replace has to start
the replace again from the top.

Do not wrap either in a bare retry loop with a short delay: that spends
attempts against a window that has not moved.

Evidence: 2026-09-23, triage of run `20260923T093900Z`.
`clients/python/numberdb/_generate.py:1400-1421` (`_with_retry(send, attempts=4)`,
`except (ConflictError, RateLimitError)`, `time.sleep(2 ** attempt)`), called
at `:1065` and `:1084` on the batch-send paths;
`clients/python/numberdb/_errors.py:24-34` for `RateLimitError.retry_after`;
`clients/python/numberdb/_http.py:286-299`, which parses the `Retry-After`
header into it. The observed server value at the time was 1101 seconds.

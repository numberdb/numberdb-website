## Verify a closed request's table before treating it as answered

What happened: numberdb-data#71 was already closed with a comment saying
"This is now https://numberdb.org/T380." The live table T380 was not the
requested binary-forms table; it was "Arithmetic factors $A_k$ in the moments
of quadratic Dirichlet $L$-functions". The cheap corpus checks also found no
reduced-binary-form table: `already_here` returned only unrelated matches, and
`api/lookup` on sample binary forms matched symmetric-polynomial tables or
nothing. The proposal was therefore not ticked as built from the closed issue
comment.

What the skill says now: look at the database before writing anything, and use
`already_asked` because closed requests matter as much as open ones.

What it should say: if an already-asked issue is closed and names a table,
read that table and verify that its title and definition answer the request
before recording the proposal as built. A closed issue is a pointer to check,
not proof that the corpus contains the table.

Evidence: `gh issue view 71 --repo numberdb/numberdb-data --json
title,body,comments,state,url,labels,number` returned the closing comment
naming T380; `/tmp/check_t380.py` read T380 through the NumberDB client and
printed the unrelated arithmetic-factors title and definition, 2026-09-21.

## An API key reads a draft by number but cannot list your drafts: `/drafts` is a session page, and there is no `/api/drafts`

What happened: holding a key that owns two drafts, I tried to enumerate them.

    GET https://numberdb.org/api/drafts                    -> 404
    GET https://numberdb.org/drafts   (Bearer <key>)       -> 302
                                location: /accounts/login/?next=/drafts

The 404 is the honest one: there is no such route. `numberdb_app/urls.py`
exposes `api/search`, `api/lookup`, `api/table`, `api/tables`,
`api/table/<tid>` and its `entries`, `offer`, `lease`, `audit` and `file`
sub-routes, `api/claim`, `api/tag`, `api/costs` -- and no listing of any kind.

The 302 is the one that misleads, because it looks like a credential problem
you could solve. It is not. `/drafts` is `@login_required`: it wants a browser
session cookie from `/accounts/login/`, and an API key in an `Authorization`
header is not one and never becomes one. Sending the key harder does not help.
A client following redirects silently will hand you the login page's HTML and
whatever your parser makes of it.

So the two halves of draft access are split, and the split is not obvious:

* **By number, with the key: yes.** `numberdb.table('T443')` with the owner's
  key configured returns the whole document, `Numbers` included. (Already
  proposed as a lesson in `PROPOSALS.md`, "A draft is readable through the API
  by its owner"; and reading one *without* the key is refused as
  `Table with id 'T443' does not exist`, proposed in
  `agents/lessons/proposals/20260923T073510Z-triage.md`.)
* **By enumeration, with the key: no.** Not by search -- `search_text` answers
  with published tables only -- and not by listing, because no listing exists
  outside a page your key cannot open.

The consequence is the sharp bit. The `/drafts` page's own docstring says what
it is for: "Existence, not contents ... the reason to hide what is in a draft
is not a reason to hide *that* it exists, and hiding both is how two people end
up making the same table." That protection is real and it is browser-only. A
contributor working through the API -- which is how a generator works, and how
any unattended run works -- gets exactly the failure the page was built to
prevent, and gets it in the shape the page was built to prevent it in.

What the skill says now: that a draft "is invisible, in no listing, answers no
search, and may have no numbers in it yet", and that `/drafts` "lists what is
being made right now and is invisible from outside".

What it should say: add that `/drafts` is a signed-in *web page* and there is
no API equivalent, so **an API client must keep its own record of the
T-numbers it created** -- write the number down when the draft is created,
because nothing will tell you later. And warn that requesting `/drafts` with a
Bearer key returns a 302 to the login form rather than a 401 or 403: a client
that follows redirects will parse an HTML login page as though it were data,
and one that does not will report a redirect with no explanation. Neither
reads as "this endpoint does not take API keys", which is what it means.

What to do instead, if you must check whether a draft exists before creating
it: try the title. Creating a table with a title that is already taken is
refused, and that refusal is the only enumeration an API client gets. Reading
a number you believe you own (`numberdb.table('Tnnn')` with the key) settles
that number and only that number.

Evidence: 2026-09-23, against numberdb.org with a key owning T443 and T445.
`curl -H 'Authorization: Bearer <key>' https://numberdb.org/api/drafts` -> 404;
the same against `/drafts` -> 302 to `/accounts/login/?next=/drafts`;
`api/table?id=T443` with the same key -> 1001 entries, `id=T445` -> 0 entries.
Route list: `numberdb_app/urls.py` lines 40-55 and 81; the view and its
docstring: `numberdb_app/views.py:359`.

# Lessons from the T30 growth critique of 2026-09-21T03:13Z

Reading T30, "Rational numbers", against the skill to answer whether its range
could grow. Two things the skill does not say, both about how search behaves,
and both of which a contributor with a laptop would hit the first time they
ask "is this range too small?"

## Search by number orders results by ascending T-number, not by relevance

What happened: measuring what T30's 39 entries cost the corpus, I printed the
T-numbers behind `numberdb.search_rational` results. They are sorted:

    search_rational(3, 4)  ->  T30, T155, T177, T216, T303, T304, T329,
                               T331, T346, T356, T357, T369, T374
    search_rational(3, 1)  ->  T2, T17, T30, T62, T89, T91, T130, T150,
                               T168, T177, T236, T241, T278, ...
    search_rational(1, 6)  ->  T13, T94, T130, T137, T177, T216, T253,
                               T302, T303, T304, T307, T363

Three searches, 47 results, not one inversion. So the first thing a reader
sees when they type a number is the *oldest* table holding it, and an early
table that holds a common value holds the top slot for that value
permanently. T30 is the first answer for 27 of its own 39 values, with 462
hits from other tables below it; somebody searching $3/4$ is told "Rational
numbers" before they are told it is a critical exponent of the
two-dimensional universality classes.

What the skill says now: that a table of values nobody looks for "still
answers when somebody looks for something else, and every hit in the corpus is
worth a little less for it". True, and it leaves the impression that the cost
is spread thinly over a long results list. It is not. The cost lands on the
first line, and it lands there according to an author's T-number, which is
not something they chose.

What it should say: search by number returns the tables in T-number order, so
a generic value in an early table is the first answer a reader gets for it
forever. When choosing a range, ask not only whether anybody arrives holding
the number, but whether this table is the one they should be told about
first. A low T-number raises the bar rather than lowering it.

Evidence: 2026-09-21 T30 growth review, `agents/critiques/T30-growth.md` §4;
128 calls to `numberdb.search_rational` through `clients/python`.

## "No match in database" is an answer, and a catch-all table destroys it

What happened: of 80 rationals sampled from the 368 inside $|a|,b \leq 18$
that are not in T30, **56 are held by no table in the corpus at all.** Today a
reader searching $5/11$ is told "No match in database", which is true and
useful: the corpus does not know this number, so it is not a named constant
and the reader can stop looking. Extending T30 would replace all 56 of those
honest answers with a hit that looks like an identification and carries no
information, because in that table the value column is a copy of the parameter
column — the reader is told that $5/11$ is a rational number.

What the skill says now: that values which "are a handful of small integers --
class numbers are mostly 1, 2, 3 -- match everything and tell nobody
anything". That rule is about *repetition* across rows. This is a different
failure and a worse one: a table where each value is distinct and each is
still uninformative, because the value is the parameter restated. The skill
has no test that catches it, and it catches nothing about the reader who was
better served by a miss.

What it should say: a miss is a result. Before extending a range, check what
the values you would add currently answer — if most of them answer nothing,
the extension is not filling a gap, it is converting a true negative into a
false positive. And the structural tell is cheap: if a table's value column
would print the same string as its parameter column, adding rows adds nothing
a reader can learn. That table's range is a matter of how many examples to
show, not of how much of the family to cover.

Evidence: same run, §4. The 80-value sample and the 39-value rank measurement
are both a dozen lines of `search_rational` against the public API and need no
key.

## A definition that requires another table's object should link it, and the audit disagrees

What happened: `GET /api/table/T30/audit` reports "Definition links to another
table; a cross-reference belongs in Similar tables or a comment" on

> The field of rational numbers $\mathbb{Q}$ is the field of fractions of the
> HREF{Integers}[integers] $\mathbb{Z}$.

The skill says the opposite and says it twice: "Link the first mention of a
thing to what explains it. A table if the corpus holds one", and "Link a table
the first time it is named, and only the first time." Here the link is not a
"see also" the sentence happens to carry; the definition *is* "the field of
fractions of the integers", so $\mathbb{Z}$ is a term the definition cannot do
without. An author following the skill gets a finding, and an author following
the finding breaks the definition.

What the skill says now: link at first mention, once per section, with no
exception for the `Definition` field.

What it should say: either that the first-mention rule does apply in the
definition when the linked object is a term the definition needs — which is
what I believe and what this table does correctly — or, if the audit's rule is
the intended one, that the `Definition` is the one section where a link is a
cross-reference and belongs elsewhere. The two cannot both stand. Whichever
way a person decides it, the audit rule and the skill sentence should be
changed in the same commit, because today they contradict each other on a
table that has been public since 2021.

Evidence: same run, §6. `curl https://numberdb.org/T30` shows the link
rendering correctly and once; the audit finding is reproducible against the
live API.

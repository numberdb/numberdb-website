## Nothing ever runs a `Programs` snippet, so run it yourself, and make it produce a row of *this* table

What happened: T386, a table of zeros of $\zeta(s,a)$, offers one `Programs`
snippet in Sage. It has two faults and neither was caught by anything:

    C = ComplexBallField(200)
    s = C(QQ(1)/2) + C.gen() * C(14)
    C(s).zeta(C(QQ(1)/3))

The second line raises `TypeError: gen() takes exactly 2 positional arguments
(1 given)` on Sage 10.9 — `ComplexBallField.gen` has no default index, and
wants `C.gen(0)`. `C(0, 1)` is the same ball and says what it means. So a
reader who copies the snippet gets a traceback, not a number.

Repaired to `C.gen(0)`, it runs and prints
$-1.9355\ldots + 1.8985\ldots\mathrm{i}$, which is a *value* of the Hurwitz
zeta function at a point of no significance, and not a zero. The table holds
zeros. Every row of it is a $\rho$ with $\zeta(\rho,a)=0$, and the program
offered to "a reader who wants one more value" computes something the table
does not contain — it is the right snippet for the neighbouring table of
values, one `Similar tables` entry away. The tell is that the snippet's output
cannot be compared with any stored entry, which is also what would have caught
both faults in one run.

`audit_table` answered `{"findings": [], "clean": true}`. The site never
executes a `Programs` snippet; it does not execute an attached `generate.py`
either, and says so on the files page ("These are recorded, not executed").
There is no test anywhere, on the site or in a generator, that a `Programs`
snippet parses, runs, or produces a number the table holds.

What the skill says now: "**`Programs` and `generate.py` answer different
questions.** `Programs` is the standard incantation in Sage, PARI or mpmath
for a reader who wants one more value." Nothing about running it, and nothing
about what "one more value" means for a table whose values are zeros, roots,
extrema or arguments rather than evaluations.

What it should say: run the `Programs` snippet, from a clean session, before
attaching it, because nothing else ever will. And check what it returns
against a stored entry: the incantation has to produce a row of *this* table.
For a table of zeros that means a root find (`mp.findroot`, `lfunzeros`), not
an evaluation; the evaluation belongs to the table of values, if there is one.
A snippet that computes something the table does not hold reads as an
authoritative recipe for the wrong quantity.

Evidence: 2026-09-21, T386 read as a reader. `/tmp/prog386.py` and
`/tmp/prog386b.py` through `agents/sage.sh` on Sage 10.9: the snippet as
published raises `TypeError` at `C.gen()`; with `C.gen(0)` it returns
`[-1.9355468431725488538649197720285216053308255114987637691143 +/- 3.03e-59]
+ [1.8984526472317339276251300891200558879871024321060818183345 +/- 4.19e-59]*I`.
The same script evaluated four stored entries, `rho.zeta(C(a))`, and got balls
of size $3\cdot10^{-31}$ and smaller, so the stored zeros are zeros and it is
only the snippet that is wrong. `agents/critiques/T386.md`, finding 1.

## MathJax does not raise on bad TeX, so a control fragment passes and the check confirms nothing

What happened: checking that a table's mathematics typesets means running it
through MathJax, since the site emits `$...$` and lets the browser do the
rest — a formula that reaches the page as "Math input error" is invisible in
the stored document. The obvious way is `mathjax-full@3` in node:

    const doc = mathjax.document('', {InputJax: new TeX({packages: AllPackages}), ...});
    try { doc.convert(tex); } catch (e) { errors += 1; }

That reported `checked 67 errors 0` over T386's 66 fragments **and** over a
deliberately broken control, `\frac{1}{2`. MathJax's TeX input does not throw
on a parse error by default: it catches it and renders an `merror` node, so
`convert` succeeds and returns HTML saying "Math input error". A check built
this way passes everything, including the fragment put there to prove it can
fail.

Two ways to make it real, either alone sufficient:

    tex.parseOptions.options.formatError = (jax, err) => { throw err; };
    // or: inspect the output
    if (adaptor.outerHTML(node).includes('merror')) { ...it failed... }

With those, the same run reported `FAILED CONTROL $\frac{1}{2$` and
`checked 67 errors 1`: T386's own 66 fragments all typeset.

What the skill says now: nothing. It says to use `$...$` for mathematics and
says nothing about checking that what you wrote typesets, although a JSON
escape eating a backslash has put "Math input error" on a published page here
before.

What it should say: before offering a table, typeset every `$...$` fragment of
the document, entry comments included, and check the *output* for `merror`
rather than trusting the call not to throw. This is the general rule the skill
already states for measurements — "a measurement needs a control that returns
a known answer" — in the form it takes for a checker whose failure mode is to
return success: run a fragment you know is broken and confirm your harness
says so, or the whole check is decoration.

Evidence: 2026-09-21, T386. `/tmp/mj386/check.js` against
`/tmp/mj386/fragments.json` (66 fragments extracted from `GET
/api/table?id=T386`, `HREF{}`/`CITE{}` stripped first). First form:
`checked 67 errors 0`, control included. With `formatError` throwing and the
`merror` test: `FAILED CONTROL`, `checked 67 errors 1`. `mathjax-full` 3.2.1,
node 22.

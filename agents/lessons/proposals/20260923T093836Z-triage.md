## The route you write a table to is not the route you read it from, and asking the wrong one gives 405 rather than the table

**What happened.** Having filled a draft with `PUT /api/table/T441`, the
natural next request is `GET /api/table/T441` -- same URL, safe method. It
answers

    HTTP 405  {"error": "Use POST or PUT."}

for every table in the corpus, published or not, with a key or without one.
Nothing in that reply says where the table actually is. I read seven ids that
way before noticing that every one of them was a 405 and not an answer.

The two routes are different views that happen to share a prefix
(`numberdb_app/urls.py:43,45`):

    path('api/table',                    api.table)        # read:  ?id= or ?url=
    re_path(r'^api/table/(?P<tid>...)$', api.write_table)  # write: POST or PUT

So the read is a **query parameter**, not a path segment:

    GET /api/table?id=T441          the document
    GET /api/table/T441             405, always

and the same shape holds for the sub-routes -- `/api/table/T441/entries`,
`/offer`, `/audit`, `/file/<name>` are all under the *write* path, and `/audit`
is the only one of them that answers a GET.

**Why this is worth a sentence rather than a shrug.** 405 is a plausible-looking
refusal. It is what a script gets if it builds its read URL by string-joining
the way its write URL was built, which is the natural thing to do when the
write is the request you wrote first -- and a `raise_for_status()` around it
reports "Method Not Allowed" on a URL that manifestly exists, which reads like a
permissions problem or a stale key rather than a typo. The method check at
`api.py:854` runs before any authentication, so adding the key changes nothing
and there is no second symptom to follow.

**What the skill says now:** it gives `?id=` in its examples and never remarks
on it. There is no occurrence of `405` anywhere in `SKILL.md`.

**What it should say**, wherever the read is first shown:

> Reading a table and writing one are different routes that share a prefix.
> The read is `GET /api/table?id=<tid>` -- a query parameter. The path form
> `/api/table/<tid>` is the *write* route and answers any GET with
> `405 {"error": "Use POST or PUT."}`, whatever the table is and whether or not
> you send your key. `?id=` also takes a title-address (`?id=Cyclotomic_polynomials`),
> so it is the one route you need.

## `/drafts` is a page for a signed-in person, not a listing your key can read -- and it answers a key with a redirect that your HTTP client will follow into a 200

**What happened.** Looking for a list of my own drafts I asked `/drafts` with
the zeta3 key as a bearer token and got **HTTP 200** and a body -- which, read
past its first line, is the sign-in form. With redirects disabled the real
answer appears:

    $ # with Authorization: Bearer <key>, redirects not followed
    HTTP 302  Location: /accounts/login/?next=/drafts

`urllib.request.urlopen` follows that by default, and so does `requests` unless
you pass `allow_redirects=False`. The status you see is the login page's 200.

**Why.** `/drafts` is an ordinary site page behind `login_required`, and it
authenticates a *session*, not an API key. A bearer token is understood only by
the `api/` views. So the listing is real -- it exists so that two people do not
build the same table without knowing (`numberdb_app/test_draft_listing.py`,
`docs/design/drafts-and-duplicates.md`), and any signed-in member can see that
somebody else's draft exists, though not what is in it -- and it is reachable
from a browser and not from a program.

**What this costs a script.** It is the one place where the previous lesson's
rule -- *classify on the status code, never on the body* -- gives the wrong
answer, because the status code is 200 and belongs to a different URL than the
one you asked for. A script that checks `resp.status_code == 200` concludes it
has the drafts listing; one that then searches the body for its table's title
concludes it has no drafts. Neither is told that it was never signed in.

**What the skill says now:** `SKILL.md:53` and `SKILL.md:762` both point at
`/drafts` -- "lists what is being made right now", "the button on `/drafts`" --
without saying that it is a browser page. A reader who has done everything else
in the skill with a key and `curl` has no reason to expect this one to differ.

**What it should say**, where `/drafts` is first mentioned:

> `/drafts` is a page you open in a browser while signed in; it does not accept
> an API key. Asked with a bearer token it redirects to the sign-in form, and
> because most HTTP clients follow redirects by default your script will see
> that form's `200` and think it worked -- pass `allow_redirects=False` if you
> want to see what really happened. There is no JSON draft listing: to check
> your own drafts from a program, read the ids you created with
> `GET /api/table?id=<tid>`.

**A smaller thing in the same place, worth one clause.** The throttle's refusal
names the allowance it enforced -- `Rate limit exceeded (60 requests per 60
minutes)` anonymously, `(1000 requests per 60 minutes)` with a key. That number
is the cheapest way to find out whether your key is being read at all: a `429`
saying 60 when you thought you were sending a key means the header is not
arriving (or is being stripped by something between you and the site), and a
`429` saying 1000 means it is and you have simply spent the window. The previous
lesson quotes the 60 form without noting that the number is diagnostic.

key was being read and the window merely spent.

# Proposed by the T282 growth critique, 2026-09-20

Nothing here is in force. Format follows `agents/lessons/PROPOSALS.md`.

## Re-running a generator to extend a range overwrites every entry it emits, comments included

What happened: T282 holds $m_k$ for $k=0\ldots100$ and its range could grow to
$k=1199$ by changing one constant in the attached `generate.py`. But three of
its rows carry fields the generator does not produce the current text of: the
$k=1$ comment was rewritten on the site after the file was attached (it now
states the identity $m_1=\frac{15}{4\pi^2}L(E_{15},2)$ instead of announcing
that an identity exists), and the $k=4$ row was given an
`equals: Entropy_constants_of_lattice_models#spanning-tree,square,entropy`
by hand. `generate.py`'s `_entry_comment` still returns the old $k=1$ sentence
and never emits an `equals`, and its `--publish` path sends
`submit_entries(..., upsert=False)`, which the client documents as "the
entries are replaced, which is what a full regeneration means". So the run
that adds 1099 rows also silently reverts two repairs — and the reversion is
invisible in the intent of the run, which was "add rows".

The same trap is one step smaller with the ordinary `Generator.publish()`:
that upserts, so it does not delete rows the run did not produce, but it still
sends each entry it *does* produce with whatever comment the generator builds,
so a comment edited on the site is overwritten by the stale one in the code.

Whose problem this is: anybody's. A contributor publishes a table, tidies an
entry comment through the website (which is where the skill says prose is
edited — "a generator has no opinion about them"), then extends the range six
months later from the same script.

What the skill says now: §6 says `publish()` writes, and §4 says prose is
edited on the site while a generator sends only entries. It does not say that
a per-entry comment is *part of the entry*, so the site edit and the generator
are two authors of the same field, and the last writer wins.

What it should say: a generator owns every field of the entries it produces,
comments and `equals` included. Before re-running one against a table that has
been edited since, read back the entries it will overwrite and put anything a
person added into the generator first — a table's prose is safe from a
generator, its entry comments are not. Worth a sentence beside "Prose is
edited on the site, where a person signs it", because that sentence is exactly
what makes the trap: it tells the reader that the generator cannot touch what
a person wrote, and for entry comments that is not true.

Evidence: 2026-09-20. `https://numberdb.org/files/T282/generate.py?raw=1`
(byte-identical to `generators/mahler-measures-square-lattice/generate.py`)
against the live document from `numberdb.table('T282')`; the two comments
differ and the live $k=4$ entry has an `equals` the file cannot produce.
`clients/python/numberdb/_write.py:560` for the upsert semantics,
`_generate.py:1066,1085` for which path uses which. Written up in
`agents/critiques/T282-growth.md` §5(b).

## An attached file is served as a highlighted HTML page; `?raw=1` gives the bytes

What happened: comparing a table's attached generator against a local copy,
`curl https://numberdb.org/files/T282/generate.py` returned 23,355 bytes of
HTML — the file inside `<pre class="file-source">`, with `"` as `&quot;` and
`'` as `&#x27;`. Diffing that against the repository copy produced 499 lines of
difference, every one of them an escaped quote. Stripping the tags and
unescaping gave a file that matched exactly; so does the documented route,
`?raw=1`, which serves `application/octet-stream` (10,236 bytes here, an exact
match) and is what `table_file` checks for first.

Whose problem this is: anybody downloading somebody else's generator to check
it or to compute one more value, which is what the skill's `Programs` section
and "the generator is attached to the table and downloaded from it" invite.

What the skill says now: nothing. It says the generator is attached and
downloaded, not how to download it.

What it should say: fetch an attachment with `?raw=1`; without it the address
is a rendered page, and a diff against it is a diff against HTML entities.

Evidence: 2026-09-20, `GET /files/T282/generate.py` → 200, `text/html`,
23,355 bytes; `GET /files/T282/generate.py?raw=1` → 200,
`application/octet-stream`, 10,236 bytes, `diff` clean against
`generators/mahler-measures-square-lattice/generate.py`. The view is
`numberdb_app/views.py:3190`.

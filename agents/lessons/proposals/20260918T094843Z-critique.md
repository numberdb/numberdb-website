# Lessons proposed by the T326 critique, 2026-09-18

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## `format(Decimal, '.16g')` keeps the trailing zeros that `format(float, '.16g')` drops

What happened: T326 writes each entry's Hecke eigenvalue into the entry comment
through

    def _short_decimal(value):
        return format(_decimal(value), ".16g")

where `_decimal` is `Decimal(str(value))` of a Sage real. In the six weights
where the eigenvalue is a rational integer the comment came out
`$a_2=-24.00000000000000$`, `$a_2=216.0000000000000$`, and so on: sixteen
significant digits of a number that is exactly $-24$. The `g` format is
documented as removing insignificant trailing zeros, and for a `float` it does
-- `format(-24.0, '.16g')` is `'-24'` -- but `Decimal.__format__` carries the
coefficient it was built from, so `format(Decimal('-24.000000000000000'),
'.16g')` is `'-24.00000000000000'`. Nothing raises, no check looks at prose,
and the table then claims a precision its own definition contradicts. Two
sibling tables built from the same shape of generator, T323 and T324, write
`$a_2=-24$` because they took a different path to the string.

What the skill says now: "Decide exactness from the definition, never from the
digits ... a decimal means plus or minus one unit in its last place however
long it is". It says it about *values*, and the rule is the same for a number
written into prose, where nothing type-checks it.

What it should say: the same rule applies to every number a table prints in
words, and the commonest way to break it is a formatter. Where a quantity is
exact in some cases and approximate in others -- a Hecke eigenvalue that is an
integer in one weight and an algebraic number in the next -- branch on the
mathematics and print the exact object in the exact case, rather than
formatting the embedded decimal for both. If a `Decimal` is in the path, check
one exact case by eye: `format` of a `Decimal` is not `format` of a `float`.

Evidence: T326 entries $k = 12, 16, 18, 20, 22, 26$, read 2026-09-18 through
`GET /api/table?id=T326`; `python3 -c "from decimal import Decimal;
print(format(Decimal('-24.00000000000000000'), '.16g'), format(-24.0, '.16g'))"`
prints `-24.00000000000000 -24` on plain CPython 3.12.

## A library's docstring is not evidence for the convention a table states

What happened: T326's comment defines the Petersson inner product as
$\int_{\mathrm{SL}_2(\mathbb{Z})\backslash\mathbb{H}} f(z)\overline{g(z)}
y^k\,dx\,dy/y^2$. Its source, the docstring of Sage's
`ModularForm_abstract.petersson_norm`, writes the same integral as
`|f(x + iy)|^2 y^k dx dy`, with no `/y^2` -- the invariant measure's factor is
missing there, though the identity the method actually evaluates,
$\langle f,f\rangle=(k-1)!L(\mathrm{Sym}^2f,k)/(2^{2k-1}\pi^{k+1})$, is the one
for $y^k\,d\mu$. A generator that copied the docstring into the table's comment
would have published a convention its own numbers do not satisfy, and no test
in the corpus compares a stored value against the sentence describing it.

Settling it took one numerical integration. Over the standard fundamental
domain, $\int|\Delta|^2y^{12}\,dx\,dy/y^2 = 1.0353620568\times10^{-6}$, which
is the stored value to every digit computed, and $\int|\Delta|^2y^{12}\,dx\,dy
= 1.4226500918\times10^{-6}$, which is not. Sixty terms of the $q$-expansion
and `mpmath.quad` over $x\in[-1/2,1/2]$, $y$ from $\sqrt{1-x^2}$ up, is the
whole of it.

What the skill says now: "Which normalisation, branch, and indexing" must be
decided before computing, and "Check new values against something
independent". It does not say that the sentence stating the convention needs
checking too, and that is the field nothing verifies.

What it should say: when a table's convention comes from a library's
documentation, check the convention against the numbers rather than trusting
the prose that shipped with the code. One coarse numerical evaluation of the
defining integral or sum -- five correct digits is plenty -- distinguishes the
conventions that differ, and it is the only check that reads the sentence a
reader will read.

Evidence: `/tmp/t326_measure.py`, 2026-09-18, run against SageMath; the two
integrals above; Sage's `petersson_norm` docstring as returned by
`inspect.getsource`, which the table cites at
`doc.sagemath.org/.../element.html#...petersson_norm`.

## Run a published `Programs` snippet at the smallest member of the family, not the one it was written for

What happened: T326's PARI/GP program is printed with `k = 24; i = 1;` at the
top, which is the weight it was developed on -- the smallest weight with more
than one eigenform. It reads the second Hecke coefficient with
`a2 = mfcoefs(F, 2)[3]` and then calls `nfinit(component(a2, 1))` to get the
number field, and `P[j,j]` to pick an entry of `mfpetersson`'s matrix. In every
weight where the space of cusp forms is one-dimensional -- $k = 12, 16, 18, 20,
22, 26$, including the modular discriminant -- `a2` is a `t_INT` rather than a
`t_POLMOD` and `component` raises `incorrect type in component [leaf]
(t_INT)`; `mfpetersson` returns a `t_REAL` there rather than a `t_MAT`, so the
last line fails too. The table's own generator carries a `try/except` for
exactly this and the published snippet does not, because the snippet was
written once, at the weight being debugged, and never run at the others.

A guard that costs two lines works at both:

    A2 = if (type(a2) == "t_POLMOD", nfeltembed(nfinit(component(a2, 1)), a2), [a2]);
    vecsort(vector(#A2, j, [real(A2[j]), if (#A2 == 1, P, P[j,j])]), 1)[i][2]

One thing to know if the check is run from Sage rather than from `gp`:
`sage.interfaces.gp`'s `eval` parses a statement per line, so a multi-line
`if (...)` is a syntax error ("unexpected end of file, expecting )-> or ',' or
')"). Keep each gp statement on one line.

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value." Nothing says to run it.

What it should say: run the snippet as printed, at more than the parameters it
is printed with, and pick the *degenerate* member of the family -- the weight
with one form, the degree-one field, the first index -- because that is where a
library changes the type it hands back and where a reader is most likely to
start. A `Programs` block is the only part of a table a reader executes; a
snippet that works at one parameter value and raises at another is worse than
none, since the reader believes the table is wrong.

Evidence: 2026-09-18, T326. The snippet verbatim at `k = 12` through `gp`:
`*** component: incorrect type in component [leaf] (t_INT)`. The guarded form
at `k = 12` and `k = 24` reproduces the stored values, and PARI then agrees
with Sage's `petersson_norm` on 98 significant digits at 330 bits.
`/tmp/t326_checks.py`, `/tmp/t326_pari2.py`.

## A dry run can pass while an interval carries fewer writable digits than the generator asks for

What happened: T392's generator computed all 488 Mandelbrot-center entries,
and `agents/table-build/dry_run.py` passed exactness, prose and size checks.
The first fill still refused before sending entries:
`T392 entry 7,1: 100 digits were asked for and this value carries 99`. The
roots had been isolated with `complex_roots(..., min_prec=400)`, which was
enough to identify and sort them but not enough for the client's
`to_text(..., digits=100)` and `_check_precision` path. Raising the isolation
precision to `min_prec=800` made the widest certified enclosure smaller than
`2e-145`, and the fill then accepted all 488 entries.

What the skill says now: run `agents/table-build/dry_run.py`; it computes
every entry, checks exactness, measures length and sends nothing.

What it should say: for interval or ball values, especially roots isolated at
a chosen precision, run the same write-format check the fill will use before
the first live submission: `to_text(value, wanted, generator.format)` followed
by `_check_precision`. Exactness says the value carries an enclosure; it does
not say the enclosure supports the requested number of written digits.

Evidence: T392 build on 2026-09-21. The clean dry run at `min_prec=400`
reported `488 entries computed`; the fill failed on entry `7,1` with 99
digits carried. After `ROOT_MIN_PREC = 800`, `verify()` reported
`488/488 matched`, the stored-value check found all 488 stored numbers
enclosed roots of their Gleason polynomials, and `/api/table/T392/audit`
returned `{"findings": [], "clean": true}`.

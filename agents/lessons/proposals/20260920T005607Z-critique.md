## `complete: no` becomes the word `false` if the document is loaded as YAML and posted as JSON

What happened: T344's page reads "Table is complete: **false** (it holds every
$n$ with $1\leq n\leq7$)". The generator's own document,
`generators/division-polynomials-short-weierstrass/table.yaml:41`, says
`complete: no`. Nobody typed `false` anywhere. It is a YAML 1.1 round trip,
and it is three lines to reproduce on any laptop:

    >>> yaml.safe_load('complete: no')['complete']
    False                                  # YAML 1.1 makes `no` a boolean
    >>> json.dumps({'complete': False})
    '{"complete": false}'
    >>> yaml.load('{"complete": false}', Loader=yaml.BaseLoader)['complete']
    'false'                                # what the server stores

The server reads every incoming document with `yaml.BaseLoader`, which
coerces nothing, precisely so that `complete: no` survives as the word --
`numberdb_app/api.py:706` says so in as many words. But that only defends a
document sent *as YAML bytes*. A contributor who keeps `table.yaml` on disk,
loads it with `yaml.safe_load` or `yaml.full_load` to edit a field, and posts
the result as JSON has already lost the word before the request is made. The
same trap catches `on`/`off` and `yes`, so `complete: yes` can arrive as
`true` and a table can assert completeness in a word the site does not
recognise.

Nothing catches it afterwards. `audit_table` returned `clean: true` on T344.
`limits.claims_completeness` reads the leading word and accepts `true` as well
as `yes`, so the completeness *check* behaves; only the reader is served the
wrong word. The closed vocabulary is `('yes', 'no', 'unknown')`
(`numberdb_app/metadata_form.py:44`), and the edit form marks anything else
`complete_is_odd` -- which is the only place it surfaces, and only if somebody
opens the form.

What the skill says now: it tells an author to write `complete: no` with a
`complete-note`, and shows the rendered result as `complete: no (...)`. It says
nothing about how the document gets from a file to the API, and nothing about
YAML 1.1.

What it should say: post the document as YAML bytes rather than round-tripping
it through a Python object -- the API accepts YAML and JSON alike, and the
YAML path is the one that preserves the words. If you must load it, load with
`yaml.BaseLoader`, which returns strings and coerces nothing, the same loader
the server uses. And quote the value -- `complete: "no"` -- if it is going
anywhere near a 1.1 loader. Then read the rendered page for the sentence
"Table is complete: ..." and check it is a word a person would say.

Evidence: 2026-09-20, T344 critique. `GET /api/table?id=T344` returns
`"complete": "false"`; `table.yaml` in the repository says `complete: no`;
`GET /api/table/T344/audit` returns `{"findings": [], "clean": true}`. Of the
34 tables T310-T343, 27 store `no`, 6 store `yes`, one has no `complete`, and
none stores `false`.

## PARI's `elldivpol` *multiplies* by the two-torsion factor for even $n$; Sage has three conventions under two names

What happened: the obvious guess about a division-polynomial cross-check is
that a computer algebra system hands back the $x$-only polynomial, i.e.
$\psi_n$ with the $2y$ divided out for even $n$. It is the wrong guess in both
systems a contributor is likely to reach for, and getting it wrong is a factor
of $(2y)^2 = 4(x^3+Ax+B)$, not a factor of $2y$ -- so the degrees do not even
flag it as obviously wrong, they just come out three too high.

PARI's manual states it exactly: "$f_n(X) = \psi_n(X)$ for $n$ odd, and
$f_n(X) = \psi_n(X,Y)(2Y + a_1X + a_3)$ for $n$ even". So `elldivpol(E,4)` on
$y^2=x^3+x+1$ is the **degree 9** $8x^9+48x^7+168x^6+\dots$, not the degree 6
$2x^6+10x^4+\dots$.

Sage offers three answers under two names, and the default is PARI's:

    E.division_polynomial(4)                            # 8*x^9 + ...  = psi_4 * 2y
    E.division_polynomial(4, two_torsion_multiplicity=1)#              = psi_4 itself, in y
    E.division_polynomial_0(4)                          # 2*x^6 + ...  = psi_4 / (2y)

`division_polynomial_0` is also the one that works over a function field: on
`EllipticCurve(Frac(QQ['A','B']), [A, B])` it gives the universal $\psi_n$
with formal coefficients, which is how all seven of T344's entries were
reproduced from an independent code path.

What the skill says now: "Check new values against something independent", and
it warns generally that a normalisation must be pinned down before computing.
It does not warn that the *checking tool's* convention is the thing most
likely to differ, nor that a system can offer three.

What it should say: when the family has a standard normalisation with a known
variant, state which variant the check used, not only which the table stores
-- and read the checking tool's manual page for the sentence that says so
rather than inferring it from a degree. For division polynomials specifically,
PARI's `elldivpol` and Sage's default `division_polynomial` both return
$\psi_n\cdot(2y+a_1x+a_3)$ for even $n$; `division_polynomial_0` is the
$x$-only one.

Evidence: 2026-09-20, T344 critique. PARI/GP manual, `elldivpol`, fetched from
<https://pari.math.u-bordeaux.fr/dochtml/html-stable/Elliptic_curves.html#elldivpol>
(200). Computed at $(A,B)=(1,1)$ and $(-2,3)$: `pari(E).elldivpol(4)` degree 9,
`E.division_polynomial(4)` identical, `E.division_polynomial_0(4)` degree 6.
All seven stored T344 values matched `division_polynomial_0` over
$\mathbb{Q}(A,B)$ after multiplying the even ones by $2y$.

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## A `Parameters` entry may only hold the keys the page reads; anything else is stored and silently dropped

What happened: T399 wrote a `comments:` field under two of its three
parameters. The API accepted the document, `create_table` stored it,
`audit_table` reported the table clean, and the rendered page shows neither.
The sentence that was lost is the one the table most needed:

    Parameters:
      s:
        title: spin weight of the perturbing field
        constraints: $s\in\{0,1,2\}$
        comments: >-
          The values $s=0,1,2$ correspond respectively to scalar,
          electromagnetic and gravitational perturbations. ...

The Parameters section of the page reads, in full,
`$s$ — spin weight of the perturbing field ($s\in\{0,1,2\}$)`. A reader of this
table never learns what $s=2$ means. The renderer
(`numberdb_app/views.py`, the `Parameters` loop) reads exactly six keys off a
parameter — `display`, `title`, `type`, `constraints`, `values` and
`show-in-parameter-list` — and ignores the rest without a word. Four of the 110
`table.yaml` files in `generators/` carry such a key; two are T399's, and the
other two (`level-one-cusp-form-l-zeros`, `krawtchouk-polynomial-zeros`) have
also been shipping invisible prose.

Nothing catches it. There is no schema check on a parameter's keys, the audit
has no rule for one, and the failure mode is not an error but silence: the
document round-trips, the table publishes, and the missing sentence looks like
a sentence nobody wrote.

What the skill says now: the section table has a `Parameters` row —
"each parameter's type and the constraint the entries actually satisfy"
against "aspiration" — and the two rules under it are about what a parameter
*means* (family not run, key is an address). Nothing says which fields a
parameter entry may have, and nothing warns that an unrecognised one is
dropped. A contributor who has just read that `Comments` holds "conventions,
caveats, what the values mean at a special point" will reasonably reach for a
comment *on the parameter*, because that is where the remark belongs
logically.

What it should say: name the fields. A parameter holds `display`, `title`,
`type`, `constraints`, and optionally `values` and `show-in-parameter-list`;
any other key is stored and never shown. Prose about what a parameter's values
mean goes in the table's own `Comments` section, which is the section that
renders it. And the general form of the rule is worth stating once: the
document is not validated against a schema, so a field the page does not know
is not refused — check the rendered page, not the stored document, for
anything you wrote by analogy rather than by example.

Evidence: T399 draft, 2026-09-22. `GET /api/table?id=T399` holds
`Parameters.s.comments` and `Parameters.n.comments`; the page rebuilt from that
document (sqlite draft-render recipe, status 200, 36,137 bytes) contains
neither "electromagnetic" nor "least-damped" anywhere in its 36 KB.
`GET /api/table/T399/audit` is `{"findings": [], "clean": true}`.

## YAML's bare `no` is a boolean, and the page then says "Table is complete: false"

What happened: T399's `table.yaml` has `complete: no`. PyYAML reads that as
`False`, it reaches the document as the string `"false"`, and the rendered page
says

    Table is complete: false (it holds the modes for ...)

where T398, T396, T390 and T380 all say "Table is complete: no". Of the 110
`table.yaml` files in `generators/`, 96 write `complete: 'no'` and 8 write it
bare. The page's sentence is built as "Table is complete: " + the stored value,
so whatever YAML made of the word is what a reader gets.

This is the classic YAML 1.1 boolean trap and it is not confined to `complete`:
`no`, `yes`, `on`, `off`, `y` and `n` are all booleans unquoted, and a table
with a parameter whose value is the *word* `no` (a normalisation, a flag, an
answer) would hit the same thing in a place where the damage is larger than one
word of prose.

What the skill says now: it describes `complete` and `complete-note` and gives
example text for the note, and says nothing about quoting. Every example is
written in Python rather than YAML, so the trap is invisible to a reader of
the skill and appears only for the contributor who writes a `table.yaml`.

What it should say: quote `no` and `yes` in YAML, wherever they appear as
values — `complete: 'no'`. The word is prose that the page prints verbatim, and
unquoted it is a boolean that arrives as `false`.

Evidence: T399 draft, 2026-09-22, `table.yaml:106`; the rebuilt page reads
"Table is complete: false"; `GET /api/table?id=T398` and three of its
neighbours store `'no'`.

## Two computations agreeing to every digit you printed is not an exact value, and an interval of width zero prints as a fraction

What happened: T399's generator builds each entry as a rectangle spanned by two
runs at different working precisions:

    def _as_fraction(value, digits=45):
        return str(mp.nstr(value, digits, min_fixed=-100, max_fixed=100))

    def _real_interval(a, b):
        low, high = (a, b) if a <= b else (b, a)
        return RealInterval(_as_fraction(low), _as_fraction(high))

For fourteen of the fifteen entries the two runs differed somewhere in those 45
digits, the interval had a width, and the stored value came out in the shape
the table intends: `1.012295312 + i * -0.09487051608`, ten significant digits,
33 characters. For the fifteenth they printed the same 45 digits, so
`low == high`. An interval of width zero is an exactly-known number, there are
no uncertain digits to round away, and the client wrote the rational it was
given:

    [121200982065213049039679257710553326611354597/100000000000000000000000000000000000000000000,
     121200982065213049039679257710553326611354597/100000000000000000000000000000000000000000000] + i * -0.09526584584

207 characters in a column of 33-character neighbours, and — worse than the
width — a claim that this real part is *exactly* that rational, on a table
whose `rigour details` says in so many words that it "does not claim proven
values".

The trap is that the coincidence is invisible while you are testing. It
happened on one row of fifteen, and every check on the table passes: the value
is right to every digit anybody compares, `audit_table` is clean, and search
finds it (`findable_by_number` reads a zero-width value as perfectly known).
Only the page shows it.

What the skill says now: section 7 is about saying how well the digits are
known, and the `RealInterval`/`ComplexInterval` types are described as the way
to record what you actually know. Nothing says that a degenerate interval is a
claim of exactness, or that building one from two printed strings will
occasionally produce one by accident.

What it should say: when you build an interval from two independent
computations, never let it come out with zero width unless the value really is
exact. Two runs agreeing to 45 printed digits means your printing precision is
finer than the difference, not that the answer is rational. Widen by one unit
in the last printed place when the endpoints coincide, or print at the
precision you are willing to claim. And more generally: an interval whose
endpoints are equal says "exact", and on a heuristic table that is a stronger
claim than any sentence in the document.

Evidence: T399 draft, 2026-09-22.
`generators/quasinormal-modes-schwarzschild-black-hole/generate.py`,
`_as_fraction` and `_real_interval`; the `s=2, l=6, n=0` entry in
`GET /api/table?id=T399` is 207 characters where the other fourteen are 32 or
33; the rendered page prints it verbatim
(`{{ n.number | safe }}`, `numberdb_app/templates/includes/table-snippet.html`).

## Dedekind zeta factorizations use primitive Dirichlet L-functions

What happened: the exact character check for the cyclic quartic field with
$D=1125$ first gave $\zeta_K(-1)=16/15$, while PARI's field L-function gave
$4/15$. The disagreement was not numerical precision. The quartic character
had conductor $15$, but its square was the quadratic character of conductor
$5$ represented as an imprimitive character modulo $15$. Computing
$L(1-2n,\chi^2)$ with modulus $15$ removed the Euler factor at $3$ and
multiplied the check by $4$ at $s=-1$. Replacing each character by its
primitive character before forming the generalized Bernoulli number made the
factorization agree with PARI at $s=-1,-3,-5$.

What the skill says now: check against an independent fact; nothing names this
imprimitive-character trap.

What it should say: when a Dedekind zeta function is checked by an abelian
factorization, the factors are primitive Dirichlet L-functions. If a character
has been raised to a power or lifted to a common modulus, reduce it to its
primitive character before computing $L(1-k,\chi)$ by generalized Bernoulli
numbers.

Evidence: the smoke check for T366 first raised
`no exact C4 character factorisation gives 4/15 ... candidates were [16/15]`
at $D=1125$. After `chi = chi.primitive_character()` in the L-value routine,
the same field gave $4/15$, $2522/15$, and $4407640828/315$, matching PARI's
field L-function.

## Cache PARI L-function objects only after a precision control

What happened: an attempted speed-up cached `lfuncreate(f)` as a cypari object
and then called `pari.lfun(cached, s)`. The negative values still looked
reasonable, but the functional-equation control failed for the first field:
at $D=725$, $s=-1$, the positive-side value differed from the expected value
in the sixteenth decimal place. The string-form call
`lfun(lfuncreate(f), s)`, with PARI precision set immediately before it,
had passed the same check.

What the skill says now: expect Sage machinery to be missing and write
arithmetic out; nothing says that caching a PARI object can change the
precision behaviour of a numerical L-function call.

What it should say: do not replace a working `lfun(lfuncreate(...), s)` call
with a cached cypari L-function object unless a control at the target precision
still passes. Treat the cache as a separate numerical method, not as a harmless
refactor.

Evidence: with the cached object, the T366 smoke check reported
`functional equation fails ... 1.0369329880762382418 versus
1.0369329880762384284`; reverting to the string-form PARI call restored the
agreement.

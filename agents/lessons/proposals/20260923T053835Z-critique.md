Nothing here is in force. Format follows `agents/lessons/PROPOSALS.md`.

## A paragraph break in `rigour details` is a real newline, and `"\n"` written into JSON is two visible backslashes

What happened: T438's `rigour details` is one field of 1,100 characters with
one intended paragraph break in it. The stored string carries the
two-character escape `\n` twice rather than a newline:

    >>> '\\n' in table['Data properties']['rigour details']
    True

The site renders that field through `numberdb_app/prose.py`, which makes a
paragraph at a blank *line*. So the page prints the backslashes in the middle
of a sentence — "…which gives (2).\n\nThe stored value is…" — and, because the
note is now a single paragraph rather than two, the fold that hides the tail of
a long note falls through `_split_sentence` and cuts at the first sentence
boundary past 400 characters instead of at the author's break. The reader gets
visible backslashes *and* a **more** link in the middle of a thought.

Neither `audit_table` nor `verify` looks at escape sequences, and the stored
YAML looks correct to anybody reading the document rather than the page: `\n`
inside a YAML single-quoted scalar, or inside a JSON string that was
double-escaped on the way in, is simply two characters.

This is not about this deployment. Anybody posting a table document as JSON —
`json.dumps` of a string built with `'\\n'`, a YAML single-quoted scalar, a
document hand-edited in an editor that showed the escape — can put a literal
`\n` in any prose field, and `rigour details` is the field long enough to want
a paragraph break in the first place.

What the skill says now: "`rigour details` … at whatever length that needs:
blank lines make paragraphs, `- ` makes a list, backticks mark code, and a long
note folds after its first paragraph." It says what makes a paragraph and does
not warn that the escape sequence does not.

What it should say: a blank line means an actual newline in the stored string.
`"\n"` written as two characters is printed as two characters and makes no
paragraph — and in `rigour details` it also moves the fold, because a note with
no paragraph break is cut by sentence length instead. Read the field back after
writing it (`numberdb.table('T...')['Data properties']['rigour details']`) and
check that `'\\n' in it` is false.

Evidence: T438, 2026-09-23. `GET /api/table?id=T438` with a key; the field
rendered through `/preview?table=` shows `…which gives (2).\n\nThe stored value
is the interval spanned by two computations…` inside the folded tail.
`numberdb_app/prose.py`, `_blocks` and `_split_sentence`, is where both
consequences come from.

## `Programs` renders every entry as highlighted code, whatever its `language` says and whatever is in it

What happened: T438 has a second `Programs` entry whose `language` is `Sage`
and whose `code` is an English sentence — "Run the attached `generate.py` with
SageMath. It computes the sine Fourier coefficients…". The page renders it as

    <pre><code class="table-code language-python">Run the attached `generate.py` …

so a reader sees prose set in a monospaced, syntax-highlighted box, with the
backticks showing raw because nothing inside a `Programs` block is marked up.
Note also that the class is `language-python` whatever the declared language
is, so the highlighter is guessing at the English.

The reason it happened is worth recording: neither Sage nor mpmath has a
Mathieu function, so there was no incantation to write, and a sentence went in
where the incantation would have gone.

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value. `generate.py` is the program
that reproduces and extends *this* table, attached to it. A table wants both
where both apply." It says what `Programs` is for. It does not say what
happens when there is no such incantation, and the answer is not obvious,
because "a table wants both" reads as an instruction to fill the field.

What it should say: where no library computes the quantity, leave `Programs`
out. The attachment is already offered on the page, and a pointer to it set in
a code font is worse than nothing: the field's contents are rendered verbatim
inside `<pre><code>`, so anything that is not runnable code reads as code that
does not run.

Evidence: T438, 2026-09-23, `program-sage`; the `<pre><code
class="table-code language-python">` above is from the live
`/preview?table=` render of that section. The same sentence is already in the
table's `rigour details`, which is where a description of the generator
belongs.

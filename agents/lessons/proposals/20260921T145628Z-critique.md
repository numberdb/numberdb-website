## A "Decimal expansion of" OEIS b-file is a ready-made digit-by-digit check of a stored constant
What happened: the T7 growth review wanted a source outside Sage for the 301 stored digits of $\pi$. OEIS is the obvious one and its HTML and search endpoints are refused, as the 2026-09-21 proposal already records. The b-file is not, and for a sequence of the form "Decimal expansion of X" it is not a list of terms that happen to describe the constant -- it *is* the constant, one decimal digit per line, so `''.join(line.split()[1] for line in open('b000796.txt'))` reconstructs it directly. `https://oeis.org/A000796/b000796.txt` answered 200 with 20,000 digits of $\pi$, which agreed with all 301 characters T7 stores except the last: OEIS gives `...249141273` where T7 gives `...249141274`, because the true continuation is `...2491412737` and OEIS truncates where T7 rounds. Both are inside a one-unit-in-the-last-place claim, and the difference looks exactly like an error if you are not expecting it.

What the skill says now: it names OEIS in the `Links` row of the sections table and as one of the places a value may be checked against. It does not say that a constant's decimal expansion has an OEIS sequence, that the b-file is a complete independent copy of it, or that the two conventions for the final digit -- truncated and rounded -- routinely disagree by one there.

What it should say: for a table of a real constant, find the "Decimal expansion of" sequence, fetch `https://oeis.org/Annnnnn/bnnnnnn.txt`, and join column two into the number; that is an independent check of every stored digit and costs one HTTP request. Compare all but the last stored character, and decide the last one against the next true digit rather than against OEIS -- a truncating source and a rounding table differ there by construction, and neither is wrong. The same b-file is also the right `Links` target for a reader who wants more digits than the table holds, which is the answer to "should this constant table grow in precision" (it should not).

Evidence: T7 growth review, 2026-09-21. `curl https://oeis.org/A000796/b000796.txt` returned 200 and 20,004 lines; joining them gave 20,000 digits agreeing with T7's stored value in 301 of 302 characters, and `RealField(4000)(pi)` under `agents/sage.sh` continued `...2491412737 24`, confirming T7's rounding and OEIS's truncation.

## `RealBallField(n).pi()` needs no symbolic import, and `RBF(pi)` is 53 bits
What happened: T7's `Programs` line is `numbers = [RBF(pi)]` against 301 stored digits. Run under `sage -python` it raises `NameError: name 'RBF' is not defined`; with `from sage.all import RBF, pi` supplied it returns `[3.141592653589793 +/- 3.39e-16]`, a 53-bit ball -- sixteen digits for a table holding 301. The replacement that reproduces the stored value is `from sage.rings.real_arb import RealBallField` / `RealBallField(1024).pi()`, which gave 1023 accurate bits and matched all 301 stored characters. The 2026-09-21 T8 proposal notes that `RBF(e)` additionally fails under the skill's named imports because Sage represents $e$ as `exp(1)`; the point here is a different and simpler one, and it applies to every constant including the ones that coerce cleanly.

What the skill says now: it tells an author to choose the precision and to state the working guard, and it says `Programs` holds "the standard incantation for a reader who wants one more value". It does not say that on a *one-entry* table there is no next value, so the only question the snippet can answer is "how do I get these digits" -- and that a bare `RBF(x)` or `RR(x)` answers it at 53 bits whatever the table holds.

What it should say: a `Programs` snippet must name the precision the table was built at, not inherit a default. `RBF`, `RR` and `CC` are 53 bits; write `RealBallField(bits)` explicitly. Prefer the ball field's own constructor for a named constant -- `RealBallField(1024).pi()`, `.euler_constant()`, `.log2()` -- which is exact at the requested precision and imports nothing symbolic, over coercing `RBF(pi)`. The list is short and worth checking rather than guessing: `RealBallField` has no `.catalan()`, so Catalan's constant still needs a coercion or `.zeta()`. Then run the snippet exactly as written before storing it.

Evidence: T7 growth review, 2026-09-21. `/tmp/t7_program_check.py` and `/tmp/t7_fix_check.py` under `agents/sage.sh`: the stored line NameErrors bare and gives 53 bits with imports; `RealBallField(1024).pi()` reports `accuracy 1023` bits and its midpoint printed to 305 decimals covers all 301 stored characters. `/tmp/t7_rbf_methods.py` on the same field: `pi`, `euler_constant` and `log2` each return 1023 accurate bits, and `catalan` raises `AttributeError`.

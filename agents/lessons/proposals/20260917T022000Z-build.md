## `Data properties: repeats` takes a slug, not a T-number

What happened: T288 first declared `repeats: HREF{T287}`, because the rows
with bucket capacity $\ell=1$ and $k\geq3$ repeat the roots in T287. Ordinary
cross-references to `HREF{T287}` in `Similar tables`, entry comments and
rigour details passed the audit, but the repeat relation was not recorded.
The audit reported: "Data properties: repeats was not recorded. Either T287 is
itself a repetition or another table repeats this one." Reading the code showed
that `_sync_repeats` extracts the text inside `HREF{...}` and looks it up as
`Table.url`, so `T287` is not an acceptable address for this one metadata
field. The T287 draft's `/api/table` response did not expose its slug, and
deriving one from the title is a known source of broken links, so T288 kept
the relation in `Similar tables` and entry comments and removed the `repeats`
field.

What the skill says now: it says `Data properties: repeats: HREF{Other_table}`
and separately warns never to guess a table address, but it does not say that
this field differs from ordinary prose links that may name a T-number.

What it should say: `Data properties: repeats` must use the table's slug,
`HREF{slug}`, because the server records the relation by matching
`Table.url`; `HREF{T123}` may link in prose but does not record a repeat. If
the repeated table is a draft whose slug is not available from the API or a
creation response, do not derive it from the title. Put the mathematical
relation in `Similar tables` and say in the report why repeat folding was not
declared.

Evidence: T288 draft, 2026-09-17. `/api/table/T288/audit` returned
`Data properties: repeats was not recorded...` for `repeats: HREF{T287}`;
`numberdb_app/editing.py` resolves repeats with
`Table.objects.filter(url=declared).first()`. Removing the field and moving
the Definition cross-reference out of the Definition made the audit return
`findings: []`.

## Run the final generator write before the final prose write

What happened: T313 was repaired in two stages: a whole-document prose edit, then a generator entries run. A later entries run with the same generator source restored older metadata while preserving the corrected entries, so the repaired title, Definition, Formulas, Comments and Programs had to be applied again from the current value-bearing document.

What the skill says now: it says a program should write entries through `/api/table/<tid>/entries` because that leaves prose untouched.

What it should say: when a repair needs both generator/file changes and prose changes, do the final generator/file write first and then apply the final prose document from a fresh `GET /api/table?id=<tid>`. After any generator rerun, reread the table sections as well as the entries before assuming prose survived.

Evidence: T313 on 2026-09-17. Revision `5cefb9b9...` had the corrected entries, including `10,103,K,two-pi-squared-cs = 0.042567742 +/- 4e-8`, but `/api/table?id=T313` again showed the old title and one unkeyed comment. Reapplying the prose from that live document produced revision `02684b56...`; `/api/table/T313/audit` then returned `clean: true`.

## Use `+/-` when the ball is findable but decimal shorthand is not

What happened: T313's scaled Chern-Simons values were computed by ball arithmetic from nine-decimal source values. For $10_{103}$, the ball for $2\pi^2\operatorname{CS}$ had relative width below the search threshold, but `to_text` wrote `0.042568`, whose decimal interval was too wide and still got a not-findable dagger. Writing `0.042567742 +/- 4e-8` preserved the ball's supported precision and removed the dagger without using SnapPy's extra unpublished digits.

What the skill says now: it lists `3.14 +/- 2e-2` as a valid real format, and says a real is stored as an interval that contains it.

What it should say: when a computed ball is narrow enough for search but the ordinary decimal rendering would round to an interval too wide for search, write a conservative `centre +/- radius` interval rather than dropping the value from search or claiming extra source digits. Check the interval contains the ball and that its relative width is the claim you intend.

Evidence: `/tmp/T313_scaled_after_patch.py`, T313 repair, 2026-09-17: before the interval fallback, the remaining scaled rows over the threshold included `(10,103) 0.042568`; after it, only the intrinsically tiny $10_{20}$ scaled rows remained over the threshold. The final rendered page has four not-findable markers, all on $10_{20}$.

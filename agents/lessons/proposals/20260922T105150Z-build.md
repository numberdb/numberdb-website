## `dry_run.py` computes Qp entries but `exactness()` reports Sage p-adics as unexpected

What happened: building T409, the Tate-parameter generator returned Sage
`pAdicCappedRelativeElement` values with their own `O(p^n)` precision. The
standard dry run computed all 214 entries, measured the longest value at 699
characters and the entries block at 130.6 KB, but exited nonzero because
`agents/table-build/check.py:exactness()` reported every p-adic value as
"coefficient of unexpected type pAdicCappedRelativeElement".

What the skill says now: it says to use `dry_run.py` before creating or filling
the table, and the type table says a `Qp` element is a proven value because it
carries its own `O(p^n)`.

What it should say: either `exactness()` should accept Sage p-adic elements
whose precision is finite, or the dry-run instructions should warn that a Qp
table may need an additional p-adic-specific check. Treating this dry-run
failure as a float or exactness failure is wrong; the entries can still be
valid when the generator's own check verifies finite absolute precision and the
NumberDB client accepts the values as `Qp`.

Evidence: T409 build, 2026-09-22. `agents/sage.sh` running the dry-run wrapper
for `generators/tate-parameters-elliptic-curves-q/generate.py` printed "214
entries computed", "longest 699 characters", "block 130.6 KB", and then five
sample complaints of the form
`N=11,c4=496,c6=20008,p=11: coefficient of unexpected type
pAdicCappedRelativeElement`. The generator's integrity check then verified all
214 p-adics against the split-multiplicative filter, the absolute `O(p^n)`
precision, `v_p(q_E)=v_p(\Delta_E)`, and the `j(q)` expansion.

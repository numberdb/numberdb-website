## The client rate-limits, and a loop that swallows exceptions turns that into a silent lie

What happened: surveying the corpus meant walking the T-numbers, because
there is no call that lists it. Two passes over `T1`..`T400` -- about 800
requests with an API key set -- and then

    >>> numberdb.table('T147')
    numberdb._errors.RateLimitError: too many requests; retry in 2590s

Forty-three minutes. That by itself is fine and is documented behaviour. What
is not fine is what it did to the loop I had written around it:

    for n in range(1, 400):
        try: d = numberdb.table('T%d' % n)
        except Exception: continue
        ...

which is the obvious shape for "skip the T-numbers that do not exist", and
which had worked a minute earlier. After the quota ran out it printed five
tables carrying the `discrete geometry` tag. The true answer is sixteen. I
believed the five for several minutes and started reasoning about what the
corpus does not cover from a corpus that had stopped answering.

`screen.py` already knows this -- `already_here` has a long comment about a
SOCKS proxy making the corpus look empty, and returns a complaint string
rather than `[]`. The lesson generalises past the proxy: **a missing table
and an unanswered question arrive at the same `except` clause and must not
leave by it.**

What the skill says now: nothing about rate limits, and nothing about how to
walk the corpus. Section 1 says "there is no call that lists the corpus, so
to see everything you walk the T-numbers", which is the advice that gets a
reader into this.

What it should say: walking the T-numbers costs one request each and the
server rate-limits; an API key raises the limit but does not remove it, and
the refusal arrives as `RateLimitError` with the number of seconds in it.
Catch `LookupError`/the not-found error for a missing T-number and let
`RateLimitError` propagate -- or at minimum count what you skipped and print
the count, because a survey that silently loses half the corpus reads exactly
like a survey of half a corpus. Cache the walk to a file; the second pass is
what cost me the quota.

Evidence: the two survey scripts and their outputs are in the run; the
`discrete geometry` count went from 5 (rate-limited) to 16 (a tag census run
before the limit) on the same corpus.

## Re-running an optimiser is not an independent check of an extremal value

What happened: the batch proposes six tables of optimal point configurations,
and the obvious check for each is "recompute it". For the Thomson problem
that works: pure-Python gradient descent on $\sum 1/d_{ij}$ over the sphere,
twelve random restarts, reproduced all eleven published energies for
$N = 2$ to $12$, the worst at a relative $5.5\times10^{-7}$ and most at
$10^{-11}$.

For the packing tables the same idea fails, and fails *quietly*. Maximising
the minimum pairwise distance is not smooth, so it has to be approached
through $\sum d_{ij}^{-p}$ with $p$ growing. At $p = 256$ the gradient
overflows a Python float as soon as two points come close. Capping $p$ at 64
and adding basin-hopping fixed $n = 6$, and the run still returned

    n = 3   d = 1.000000000   true  sqrt6 - sqrt2 = 1.035276180
    n = 7   d = 0.500000000   true  4 - 2 sqrt3   = 0.535898385
    n = 8   d = 0.500000000   true (sqrt6-sqrt2)/2 = 0.517638090

Three points in a unit square. The optimiser sat on three corners, reported a
converged answer with nine decimal places, and was 3.4% low. Nothing about
the output said so. Had I checked only $n = 2, 4, 5, 9$ -- which it gets
exactly right, because the optimum there *is* the obvious lattice -- I would
have concluded the method was sound and used it on the cases that matter.

The Tammes problem makes the trap explicit. The same optimiser lands to
$10^{-14}$ at $n = 3$ and $6$ and to $10^{-8}$ at $n = 4$ and $12$ -- the
triangle, the octahedron, the tetrahedron and the icosahedron -- and is short
by 0.17 to 1.21 degrees at $n = 7, 8, 9, 10, 11, 13, 14$. The four it gets
right are the four anybody would choose as a control, because they are the
four whose answers are famous.

This is the skill's existing rule about controls, in a setting it does not
name. Section 10 says "a measurement needs a control that returns a known
answer" and gives the Simpson's-rule example. The optimisation case is worse
than that one, because the failure is one-sided: a local optimum is always on
the wrong side of the true value, never scattered around it, so averaging,
more restarts and tighter tolerances all move the answer the same wrong way
and all look like convergence.

What the skill says now: the control rule, about quadrature. Nothing about
optimisation.

What it should say: when a table's values are the optimum of something, a
recomputation by local optimisation is not an independent check unless the
optimiser has first been shown to find the known answer in the *hard* cases,
not the easy ones. Choose the control from the cases where the optimum is
known and is not the obvious symmetric arrangement. Failing that, check
against a closed form, or against published coordinates -- recomputing the
functional from somebody else's configuration is a genuine check, and cheap.

Evidence: the runs are in `/tmp/w3ideas/opt.py` and `opt2.py` (scratch, not
kept); the numbers are quoted in `BATCH-2026-09-21T2205.md` under "How this
run went".

## Published coordinates say how many digits a table can honestly carry

What happened: the Tammes values are best taken from Sloane's spherical-code
files, `neilsloane.com/packings/dim3/pack.3.N.txt`, by computing the least
pairwise distance from the stored coordinates. That reproduced every angle I
could check against a proof. But `pack.3.5` and `pack.3.6` both encode
configurations whose minimum distance is exactly $\sqrt2$, and they give

    N = 5    d = 1.414213561881
    N = 6    d = 1.414213561468
    exact        1.414213562373

The two disagree in the tenth digit, and both are wrong there. So the file's
coordinates support about nine digits of the derived quantity, whatever
precision they are printed to -- the loss is in the optimisation that
produced them, not in the printing.

The general point: when the source is a configuration rather than a number,
**the digits the table may claim are not the digits the file prints**, and
the way to find out how many there are is to derive a quantity whose exact
value is known from the same file. Two files that should give the same answer
are the cheapest version of that test.

What the skill says now: sections 5 and 7 are about how precision is stored
and justified, and are all about computations you run yourself. Nothing about
a table whose input is somebody else's coordinates.

What it should say: where values are derived from published coordinates or
configurations, measure the source's accuracy before choosing `digits`, by
recomputing a case with a known exact answer; declare the measured figure per
entry with `{'number': x, 'digits': n}` rather than the table's headline
precision; and say in `rigour details` which quantity was used to measure it.

Evidence: the fetch and the arithmetic are in the batch file's "How this run
went"; the files are public.

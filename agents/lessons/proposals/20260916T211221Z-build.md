## `Generator.publish()` can fail its empty-upsert probe on a draft with no `Numbers`
What happened: T284 was created as the prompt asks, with prose and parameters but
no entries. Running the generator with `NUMBERDB_PUBLISH=1` did not reach the
first Salem number. The client's `check_writable()` sent an empty upsert to
`/api/table/T284/entries`, and the server answered:

```
NumberDBError: A value in these entries cannot be read as a number. 'str' object has no attribute 'items'
```

The table was writable, and the entries were valid. A one-off wrapper computed
all entries, submitted them as a complete entries replacement rather than an
empty upsert, and attached `generate.py` with the same run id. The draft then
verified and audited cleanly.

What the skill says now: create the draft before building anything, then fill
it once with the generator. It also says `publish()` checks permission in the
first second.

What it should say: until the client or server treats an empty draft as having
an empty entries list for `check_writable()`, a newly created draft with no
`Numbers` may refuse `Generator.publish()` before computing. The refusal above
does not mean the generator's values are unreadable. Seed or replace the first
real entries through the entries endpoint, attach the generator with the same
run id, and then use `verify(sample=None)` on the draft with the key.

Evidence: T284 build, 2026-09-16. `cat "$NUMBERDB_KEY_FILE" | NUMBERDB_REMOTE=local NUMBERDB_KEY_FROM_STDIN=1 NUMBERDB_PUBLISH=1 agents/sage.sh generators/salem-numbers-less-than-1.3/generate.py` failed in `check_writable`; `/tmp/salem_direct_fill.py` sent 47 entries as a replacement and attached the generator; `verify(sample=None)` reported `47/47 matched`, and `/api/table/T284/audit` returned `clean: true`.

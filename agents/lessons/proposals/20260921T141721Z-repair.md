## Programs snippets that drop `numberdb.sage` may need Sage's public import
What happened: T383's `Programs` block imported `numberdb.sage as numberdb` only to initialize Sage before direct imports from `sage.rings.integer_ring` and `sage.rings.polynomial.polynomial_ring_constructor`. The critique correctly said the `numberdb` name was unused, but checking the proposed deletion under `agents/sage.sh` showed the remaining named imports fail under `sage -python` with `AttributeError: partially initialized module 'sage.rings.integer_ring' has no attribute 'ZZ'`. Replacing the imports with `from sage.all import ZZ, PolynomialRing` made the reader-facing snippet run and print the stored $(8,3)$ value.

What the skill says now: it tells generators to import `numberdb.sage` before named Sage rings, and it says `Programs` and `generate.py` answer different questions. It does not say that a `Programs` snippet without `numberdb.sage` should usually use Sage's public import surface instead of the generator-style named imports.

What it should say: keep the named-import pattern in `generate.py`, where `numberdb.sage` initializes Sage and modular passagemath compatibility matters. In `Programs`, if the snippet does not use the NumberDB client, write it as reader-facing Sage code, for example `from sage.all import ZZ, PolynomialRing`, and run it exactly as shown before removing `numberdb.sage`.

Evidence: T383 repair on 2026-09-21. `/tmp/t383_program_check.py` failed after deleting only `import numberdb.sage as numberdb`; the same check passed and printed `-84375*a^8*b^2 + 16777216*b^7` after changing the imports to `from sage.all import ZZ, PolynomialRing`.

## Treat `?` ranks in ecnf-data as unknown

What happened: checking T293's repair directly against the pinned ecnf-data
`RQF/mwdata.2.2.D.1` files, a parser that treated the rank column as an
integer failed on rows whose rank is `?`. At commit
`10b28418e80392032b106ea00e6c5aa109d28e7b`, the files used for the table have
unknown-rank rows as well as rank-zero and positive-rank rows; the table's
range check had to filter for rows whose rank is an integer greater than zero.

What the skill says now: it says LMFDB data should be fetched from GitHub and
that `RQF/mwdata.2.2.D.1` has a rank column. It does not say that the rank
column may be `?`.

What it should say: when filtering ecnf-data `mwdata` rows by rank, treat `?`
as unknown, not as zero and not as positive rank. Either skip unknown-rank rows
for a positive-rank table, or make a separate decision from rank bounds or
analytic rank and say so in the table.

Evidence: direct reads of
`https://raw.githubusercontent.com/JohnCremona/ecnf-data/10b28418e80392032b106ea00e6c5aa109d28e7b/RQF/mwdata.2.2.5.1`
and the four companion real-quadratic files for T293 on 2026-09-19. Filtering
only integer positive ranks gave minimum conductor norms $199,103,47,51,17$
for $D=5,8,12,13,17$ and counts $17,63,253,195,295$ with conductor norm at
most $250$; the same pass counted unknown-rank rows in each source file.

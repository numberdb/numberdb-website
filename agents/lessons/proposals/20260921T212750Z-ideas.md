# Lessons from the ideas run of 2026-09-21T21:27Z

Batch: the parameter plane of $z^2+c$ (Mandelbrot centers, root points,
Misiurewicz points, and the integer polynomials that cut them out).

Four things this run met that the skill does not cover. All four are true for
somebody with a laptop and Sage; nothing here is about this deployment.

## Walking the T-numbers anonymously trips the API rate limit

What happened: the skill says there is no call that lists the corpus, so to
see everything you walk the T-numbers. Doing that -- 391 reads of
`numberdb.table('T%d')` -- worked from outside. A later script inside a Sage
run then read two more tables and got

    numberdb._errors.RateLimitError: too many requests; retry in 1106s.
    Anonymous use is limited -- an API key raises the limit:
    https://numberdb.org/help#section-api

which arrived 130 lines into a computation that had already done its work, and
killed the cross-check the run was there to make. The retry window was
eighteen minutes: long enough that the run would have had to end without it.

The error message is good and says exactly what to do. What is missing is that
the survey the skill *recommends* is what spends the budget, and that the cost
lands on whatever you do next rather than on the survey.

What the skill says now: "There is **no call that lists the corpus** -- to see
everything you walk the T-numbers." Nothing about how many of those a session
gets.

What it should say: walking the corpus is a few hundred requests and the
anonymous limit is smaller than that. Set `NUMBERDB_API_KEY` before the
survey, not before the publish -- reads need it too once there are enough of
them. And cache the survey to a file: the second walk is what pays for the
first.

Evidence: 391 successful anonymous reads, then `RateLimitError ... retry in
1106s` on the 393rd, from a different process on the same address. The same
script with the key set read T168 immediately afterwards without complaint.

## `rigour: proven` for the roots of a polynomial wants `complex_roots`, not `.roots(CC)`

What happened: three of the six tables proposed hold the roots of an integer
polynomial of degree up to 252. The obvious call, `p.roots(ComplexField(prec),
multiplicities=False)`, returns fixed-precision complex numbers that carry no
error of their own -- exactly the shape the skill already refuses:

    RealIntervalField(prec)(some_float_function(x))   # width zero

The call that does support `proven` is

    from sage.rings.polynomial.complex_roots import complex_roots
    complex_roots(p, min_prec=400)      # certified CIF enclosures

Measured on the Gleason polynomials in the deployed image: degree 27, 0.1 s,
worst enclosure diameter 4.4e-113; degree 63, 0.3 s, 7.6e-99; degree 120,
1.9 s, 3.6e-77; degree 252, 16.4 s, 1.4e-159. So a hundred certified digits
for several hundred algebraic numbers is seconds of work, and the reason to
know this before starting is that the alternative looks identical in the
output and is not provable.

Note the diameters are not monotone in the degree -- degree 120 came out
worst, degree 252 best -- so the guard has to be *measured on the worst entry
of the actual table*, which is what the skill already says about
`numberdb.bits(digits, losing=n)` and is easy to assume does not apply here.

What the skill says now: the rigour table covers `RealBallField`,
`ComplexBallField` and `RealIntervalField`, and warns against wrapping a
fixed-precision result in an interval. Root isolation is not mentioned, and it
is a different call from any of them.

What it should say: for a table whose values are roots of an exactly known
polynomial, `sage.rings.polynomial.complex_roots.complex_roots` (and
`sage.rings.polynomial.real_roots.real_roots`) return certified enclosures and
are what `proven` rests on. `p.roots(CC)` and `p.roots(CDF)` do not, however
many digits they print.

Evidence: the timings and diameters above, from
`agents/sage.sh` on the Gleason polynomials $G_6,G_7,G_8,G_9$ at
`min_prec=400`.

## Whether a root is real is decided by Sturm, not by reading the digits

What happened: the batch holds complex algebraic numbers, some of which are
real. A certified enclosure of a real root has an imaginary part that is a
narrow interval around zero, and writing that down stores "the imaginary part
is $0$ to 100 places" where "the imaginary part is $0$" is a theorem --
`p.change_ring(QQ).number_of_real_roots()` answers it exactly, and it agreed
with an independent count (OEIS A000048) at every degree to 495.

This is the skill's own "decide exactness from the definition, never from the
digits" rule, in a place the rule does not obviously reach: the reader is
thinking about whether a *value* is exact, and the question here is whether a
*component* of a complex value is. It also has the T174 shape -- a real root
written as a ball around zero loses information a reader needs, because a
search for their real number will not match a complex entry whose imaginary
part is merely small.

What the skill says now: "Decide exactness from the definition, never from the
digits", with the $3.000\ldots$ example, and the T174 note about not
discarding what the source certified. Both are about the whole value.

What it should say: the rule applies component by component. In a `C` table,
if the definition settles that a value is real, write the imaginary part as
exact $0$ -- and settle it with Sturm or with `QQbar`, never by looking at the
enclosure.

Evidence: real-root counts of $G_n$ for $n\leq10$ were $1,1,1,2,3,5,9,16,28,51$
by `number_of_real_roots`, matching OEIS A000048 term for term.

## OEIS answers b-files to a script and refuses the JSON endpoint

What happened: the skill points at OEIS repeatedly as the place to find an
independent copy of a sequence, and two of this run's checks were exactly
that. `https://oeis.org/search?q=id:A000740&fmt=json` returned a Cloudflare
interstitial (`<title>Just a moment...</title>`) rather than JSON, and
`fmt=text` returned 403. The b-file,
`https://oeis.org/A000740/b000740.txt`, returned 200 and plain text, which is
better data anyway -- it runs far past the terms on the page.

The same shape bit the arXiv check: `export.arxiv.org` answered 406 to the
screen's user agent and returned nothing at all over `http://`; the same query
over `https://` with a browser user agent answered 200.

What the skill says now: OEIS is named as a link target and as a place to
check a specialisation. Nothing about how to fetch one.

What it should say: fetch the b-file, not the search endpoint -- `https://
oeis.org/Annnnnn/bnnnnnn.txt` is two columns of `index value`, is not behind a
bot challenge, and holds more terms than the entry page. If a source answers
403, 406 or an empty body, try `https://` and a browser user agent before
concluding the family is not there.

Evidence: `fmt=json` on A000740 returned a Cloudflare challenge page;
`b000740.txt` returned `1 1 / 2 1 / 3 3 / 4 6 / 5 15 / ...`, which is the
degree sequence the batch checks against.

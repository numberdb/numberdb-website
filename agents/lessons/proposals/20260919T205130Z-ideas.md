# Lessons from the ideas run of 2026-09-19T2051 (sharp constants in the classical inequalities)

## The API rate-limits, and a survey of the corpus is what trips it

What happened: the skill says there is no call that lists the corpus and that
the way to see everything is to walk the T-numbers. Walking them is a request
per table, and the corpus is now well past three hundred, so the walk ran into

    numberdb._errors.RateLimitError: too many requests; retry in 44s

part way through. The next two things tried -- a `search_text` and a
`table('T92')` -- raised the same error immediately, and the screening helper
that wraps `search_text` turned it into the string

    ['(could not ask the corpus: RateLimitError: too many requests ...)']

which is a sentence in a list where every other answer is also a sentence in a
list. It reads like a screening result.

What the skill says now: "There is no call that lists the corpus; to see
everything, walk the T-numbers." Nothing about a rate limit, and nothing about
what the client raises when it is hit.

What it should say: the API rate-limits, and a walk of the T-numbers is
exactly the shape of traffic that hits the limit. Sleep between calls, catch
`numberdb._errors.RateLimitError`, and read the number of seconds out of its
message rather than guessing:

    from numberdb._errors import RateLimitError
    try:
        table = numberdb.table(tid)
    except RateLimitError as trouble:          # "retry in 44s"
        time.sleep(int(re.search(r'retry in (\d+)', str(trouble)).group(1)) + 3)

A survey walk should also be cached to a file on the first pass: the second
question about the corpus should not be a second three-hundred-request walk.

Evidence: 2026-09-19 ideas run. `/tmp/walk.py` over `range(1, 210)` finished;
the same script over `range(210, 340)` finished; the next call in a fresh
process raised `RateLimitError` with `retry in 44s`, and a `search_text` in a
second process raised it with `retry in 42s`. `/tmp/nb.py` holds the retry
wrapper that was used for the rest of the run.

## A cited Wikipedia title may be a redirect, and a source check cannot tell

What happened: the batch cited
`https://en.wikipedia.org/wiki/Hardy–Littlewood–Sobolev_inequality` as the
source for a proposed table of Lieb's sharp constants. The check passed. So
did a check of the *same* name against
`https://en.wikipedia.org/wiki/Riesz_potential`, which is a different article.
Fetching both and comparing word lists showed why: the first URL is a redirect
and serves the "Sobolev inequality" article, so the two checks had confirmed
that a page mentions Hardy, Littlewood and Sobolev -- which the Sobolev
inequality article does in passing -- and not that any page is about that
family.

The same run met the other half of it. "Polyharmonic" is not on the Sobolev
inequality page at all, so a perfectly real family failed its source check
under one of its names and passed under another ("fractional").

What the skill says now: "Link outward only to durable sources: Wikipedia,
LMFDB, OEIS, MathWorld, mpmath, or a paper." Nothing about what a link
establishes.

What it should say: a citation to a Wikipedia title that redirects lands the
reader on an article about something else, and neither a text search nor a
`200` will tell you. Before putting a Wikipedia URL in `Links`, fetch it and
check that the family is what the page is *about*, not merely a word on it --
the cheapest test is that the article's own title contains the family's name.
A name that fails on one page and passes on another is usually the name being
wrong rather than the family being absent: prefer the spelling the article
uses.

Evidence: 2026-09-19 ideas run, `/tmp/words.py`. The `Hardy–Littlewood–Sobolev
inequality` and `Sobolev_inequality` URLs return byte-identical word lists
(`optimal, aubin, nash, fractional, riesz, loss, rellich, hardy`); neither
contains `sharp`, `best`, `lieb`, `talenti` or `polyharmonic`.

## A closed form for a new family is testable against a published table before anything is built

What happened: the batch proposes six tables of sharp constants, each given by
a formula taken from the literature. Rather than propose them on the strength
of the formulas, each was evaluated in `RealBallField(400)` under
`agents/sage.sh` and compared with something already published. Two of the
comparisons were exact and cost about ten minutes:

* the proposed constant $S_{n,s}$ at $s = 1$ reproduced **the hundred stored
  digits of T92** at $p = 2$ for $n = 3, \dots, 11$ -- nine entries,
  `overlaps` true on each;
* $C_{n,n-2s}\,S_{n,s} = \gamma(2s)$, the Riesz-potential normalisation, held
  in ball arithmetic for $s = 1, 2, 3$ across five dimensions each.

The first of those is a test of the *convention*, not of the arithmetic: the
same family under the other Fourier normalisation differs by $(2\pi)^{s}$, and
that is exactly the error a proposal cannot catch in prose.

What the skill says now: "Check new values against something independent, not
the code that produced them", in the section on checking a built table.

What it should say: the same advice applies one stage earlier. A proposal that
names a closed form can usually be checked against an existing table before a
generator exists, by evaluating the form at the one parameter where the two
families meet and comparing against the stored digits. Where the two
normalisations of a family differ by a constant factor, that comparison is the
only thing that fixes which one the new table holds, and a proposal that has
run it can say which -- a proposal that has not is guessing.

Evidence: 2026-09-19 ideas run, `/tmp/chk/check.py` and `/tmp/chk/check2.py`
under `agents/sage.sh`, against published T92.

## `RealBall` still has no `.str`, and the failure is at the print

What happened: the check script above died at its first `print`, on
`'sage.rings.real_arb.RealBall' object has no attribute 'str'`, after every
value in it had already been computed correctly. The skill records that the
named imports do not bring `RealBall.str`; what it does not say is that the
missing method is reached from the formatting call rather than from the
mathematics, so the traceback arrives at the end of a long computation and
names a line that has nothing to do with the family.

What the skill says now: "What the named imports do *not* bring: root finding
(`sage.numerical.optimize`), `RealBall.str`, and `QQ('1.25')`."

What it should say: the same, plus the shape of the fix, since every script
that prints a ball needs it:

    def show(ball, digits=20):
        return ball.mid().str(digits=digits)      # the midpoint is an RealNumber

Print midpoints for reading and keep the ball for comparing: `overlaps` and
`contains_zero` are what decide agreement, and neither needs a string.

Evidence: 2026-09-19 ideas run. `/tmp/chk/check.py` first run: exit 0 with a
traceback at the line `% (n, a.str(digits=20), ...)`; second run with `show`
printed all nine comparisons.

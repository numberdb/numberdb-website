## `Generator.publish()` can fail before filling a draft with no `Numbers` section

What happened: T247 was created as an empty draft through `POST /api/tables`
with `X-Draft: yes`, carrying its prose and parameters but no `Numbers`
section. The harmonic-number generator previewed cleanly, reporting 365
entries to add, but `Generator.publish()` stopped before computing anything:
its writability probe sends an empty upsert to `/api/table/<tid>/entries`,
and the server answered 400 with `A value in these entries cannot be read as a
number. 'str' object has no attribute 'items'`. A whole-document edit adding
`Numbers: []` was refused too, because the ordinary write endpoint rejects an
empty table. Sending the first nonempty entries block directly to
`/api/table/T247/entries` succeeded, after which `Generator.publish()` could
verify that all 365 entries were unchanged and attach `generate.py`.

What the skill says now: a draft may be proposed first and filled by a
generator afterwards: "Propose it as a draft", then "Fill it with a generator
pointed at that T-number."

What it should say: until the client/server preflight is fixed, a generator
may be unable to fill a draft whose document has no `Numbers` section at all.
If `publish()` fails before computing entries with an empty-upsert error,
send one nonempty entries block through `/api/table/<tid>/entries`, or create
the draft with entries already present, then rerun the generator so it can
verify the rows and attach its source.

Evidence: T247 split from T226 on 2026-09-15. `preview()` reported
`<PublishOutcome T247: 365 added, 0 updated, 0 unchanged, 0 agreed, 0 left
alone, 0 removed, not sent>`. The first `NUMBERDB_PUBLISH=1 agents/sage.sh
generators/harmonic-number-rational-values/generate.py` failed in
`check_writable()` with the 400 above. Posting `/tmp/T247_harmonic_entries.yaml`
to `/api/table/T247/entries` returned `entries: 365`, and the subsequent
generator runs reported `365/365 matched` and `365 unchanged`.

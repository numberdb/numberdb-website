# Lessons proposed by the T341 critique, 2026-09-19

## When the parameters are invariants and the entries depend on the model, the table must give the recovery

What happened: T341 indexes division polynomials by $(N,c_4,c_6)$ and defines
its entries as the $\psi_n$ of "the elliptic curve with reduced global minimal
model $y^2+a_1xy+a_3y=x^3+a_2x^2+a_4x+a_6$ recovered from $(c_4,c_6)$". The
recovery is never written down. Every formula on the page is in the $a_i$ and
$b_i$ — the $b$-invariants from the $a$-invariants, $\psi_n$ from the
$b$-invariants, and a `Programs` snippet that opens by assigning the $a_i$ —
so a reader holding a row has the address and no route to any of it.

That would be a slow inconvenience if $\psi_n$ were an invariant of the curve.
It is not: it is an invariant of the *model*. The corpus's other table on the
same index, T211, hands a reader a model in prose, $y^2=x^3-27c_4x-54c_6$,
which is isomorphic to the minimal one and gives different polynomials — for
$(c_4,c_6)=(48,-216)$ it gives $\psi_3=3x^4-7776x^2+139968x-1679616$ where
T341's row says $3x^4-6x^2+3x-1$. So the most available guess a reader can
make is wrong, silently, and nothing on the page contradicts it.

The general shape: a table whose parameters are *invariants* of an object,
whose entries depend on a *presentation* of that object, has a third thing to
state that neither the parameters nor the definition normally carries — how the
presentation is recovered from the invariants. It is easy to leave out because
the builder's generator never needed it: the generator read the models out of a
database and computed the invariants, which is the direction nobody reading the
table can travel. Sharing an index with a published table is what makes it
dangerous rather than merely incomplete, because the sibling's recovery is the
one a reader will reuse.

What the skill says now: section 4 requires the definition to say what the
object is, precisely enough that two people would build the same table, and
warns that "when what a table stores changes, three places say what it holds".
Nothing says that a definition can be determinate and still not be usable, or
that the recovery from the index to the object is a thing to write.

What it should say: if the entries depend on a presentation and the parameters
are invariants, give the map from the parameters to the presentation, as a
formula, in the table. Check it by reconstructing one row from its own address
using only what the page says, and check whether a sibling table on the same
index publishes a *different* presentation — if it does, say which one this
table uses, because a reader who has read both will assume they agree.

Evidence: 2026-09-19, `agents/critiques/T341.md`, finding 1. T341
`Definition`, `Formulas`, `Programs`; T211 `comment-labels`. Recovery checked
under `agents/sage.sh`: $b_2\equiv-c_6\pmod{12}$ with
$b_2\in\{-4,-3,0,1,4,5\}$, then $b_4=(b_2^2-c_4)/24$,
$b_6=(-c_6-b_2^3+36b_2b_4)/216$ and $a_1=b_2\bmod2$, $a_2=(b_2-a_1^2)/4$,
$a_3=b_6\bmod2$, $a_4=(b_4-a_1a_3)/2$, $a_6=(b_6-a_3^2)/4$ reproduces the
conductor and both invariants for all 161 curves in the table. The two
$\psi_3$ above are Sage's `division_polynomial(3, two_torsion_multiplicity=1)`
for `EllipticCurve([0,0,1,-1,0])` and `EllipticCurve([0,0,0,-1296,11664])`.

## A product written as juxtaposition after a quotient reads as function application

What happened: T341's comment on conventions renders as

> For even $n$, the $x$-only polynomial without the two-torsion factor is
> $\psi_n/(2y+a_1x+a_3)$. PARI/GP's `elldivpol` and Sage's default
> `division_polynomial` use the other $x$-only convention,
> $\psi_n(2y+a_1x+a_3)$.

The last expression is a product and is correct. It reads as $\psi_n$ evaluated
at $2y+a_1x+a_3$, for three reasons at once: $\psi_n$ is a named function,
nothing separates it from the parenthesis, and the sentence immediately before
has just written the *other* convention as an operation applied to $\psi_n$, so
the reader is already parsing for operations. The table's `Formulas` section
states the same fact as $f_n(x)=\psi_n(x,y)(2y+a_1x+a_3)$, where the $(x,y)$
disambiguates but leaves an equation whose left side is a function of $x$ and
whose right side visibly contains $y$.

The second half of the trap is that the page never says why a product of two
things linear in $y$ is $x$-only. It is, because $(2y+a_1x+a_3)^2 =
4x^3+b_2x^2+2b_4x+b_6$ on $E$ — one line, absent, and it is the line that makes
the convention make sense and makes the table's own `Programs` snippet work.

What the skill says now: "Define notation where you use it. A comment saying
the values are `U_n(x,-1)` is useless until something says what `U` is." That
covers an undefined symbol. It does not cover a defined symbol written in a way
that says the wrong operation.

What it should say: write a product with $\cdot$ whenever the left factor is a
named function and the right factor is parenthesised, and, where a convention
turns on a non-obvious simplification, state the simplification in the same
table. A convention comment a reader can misparse is worse than no comment,
because they carry away a wrong conversion and never know to check it.

Evidence: 2026-09-19, `agents/critiques/T341.md`, finding 2. T341
`comment-even-polynomials`, `formula-pari-convention`. Convention verified
under `agents/sage.sh` on 37a1 for $n=2,3,4,5$: `pari(E).elldivpol(n)` and
Sage's default `division_polynomial(n)` both return $\psi_n$ for odd $n$ and
$\psi_n\cdot(2y+a_1x+a_3)$ for even $n$.

## The audit checks that every `CITE{}` has a Link, and never that every Link is cited

What happened: `GET /api/table/T341/audit` answers `{"findings": [], "clean":
true}` on a table whose `Links` section declares `Requested10`, "Requested in
numberdb-data#10", which no `CITE{}` anywhere in the document points at. It
renders on the page as a numbered reference — `[4]` — that no sentence
references. That is the "uncited decoration" the skill's section table rules
out, and the issue reference is separately ruled out by name in section 9:
"The table carries no trace of the request."

The audit has a rule for the other direction (`CITE{%s} is not a Link or a
Reference`) and none for this one, so a declared-and-never-cited Link passes
clean. A contributor who leans on the audit as the check before offering a
table will not be told.

What the skill says now: section 4, "A reference is for citing, not for
listing", and section 9 on answering a "table wanted" issue in the issue. Both
are right; nothing warns that the audit does not enforce either.

What it should say: where the skill tells a contributor to run the audit, say
what it does not see — an uncited `Link` or `Reference` among them — so that
"clean" is read as "no rule fired", not as "checked". Better still, add the
rule: every key in `Links` and `References` should appear in some `CITE{}`, and
a key that does not is either uncited decoration or a sentence somebody meant
to write.

Evidence: 2026-09-19, `agents/critiques/T341.md`, finding 3.
`GET /api/table/T341/audit` → `clean: true`; `Links` holds `PARIelldivpol`,
`Requested10`, `SageCremona`, `SageDivision`, and the `CITE{}` keys used in the
document are `PARIelldivpol`, `SageCremona`, `SageDivision`,
`formula-pari-convention`, `formula-recurrence`. The corpus already made this
decision once: `scripts/one-off/drop-the-issue-references.py` removed the same
thing from eleven tables, three of them carrying it uncited.

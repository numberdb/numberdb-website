## `dry_run.py` should accept Sage p-adics as precision-carrying values

What happened: while building a `Qp` table, `agents/table-build/dry_run.py`
would have sent every Sage p-adic value to `exactness()` as an unexpected
coefficient type. A p-adic element is not an exact integer or rational, but its
printed `O(p^n)` term is the precision certificate the database stores.

What the skill says now: return a `Qp` element for a p-adic table, since it
carries the stored precision. It also says to run `dry_run.py` before creating
or filling the table, and it warns that fixed-precision values without
certified enclosures cannot be declared `proven`.

What it should say: the dry-run exactness check must treat Sage p-adic elements
as acceptable value objects for a `Qp` table. That check is about whether the
writer can read the value and its precision mechanically; it is not a rigour
declaration. A fixed-precision p-adic computation should still use `heuristic`
or `heuristic (agreement-checked)` unless the generator supplies a certified
error argument the writer can enforce. A `Qp` generator should return the Sage
object, not a string.

Evidence: on 2026-09-22, the build of the elliptic-curve
`$\mathcal{L}$`-invariants needed to dry-run values such as
`Qp(5, 20)(1 + 5 + 5^2)`. The check was patched in commit `a9c7588` so
`exactness({'p=5': Qp(5, 20)(1 + 5 + 5^2)})` returns `[]` while
`exactness({'bad': 1.5})` still reports the float division complaint.
The later upload to `T410` refused the first `rigour = "proven"` declaration,
which is the check that caught this distinction.

# Lessons from the ideation run of 2026-09-23T11:20Z

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## The corpus has a listing: `/tables?page=N`, and the last page repeats

What happened: the run needed to know what the corpus already covers before
proposing an area it does not. Following the skill, that means walking the
T-numbers one read at a time, which is four hundred requests. The site lists
every published table instead, fifty to a page, T-number and title and entry
count, in one request per page:

    $ curl -s "https://numberdb.org/tables?page=1"
    ...
    T13: Bernoulli numbers (251 rational numbers)
    T114: Bernoulli polynomials $B_n$ (51 rational polynomials)

Nine pages gave 422 tables, which is the whole published corpus, and answered
"is there anything on Kelvin or Struve functions" by `grep` rather than by
search stemming and guesswork.

Two traps in it, both of which cost this run a wrong count:

* **The listing is sorted by title, not by T-number**, so consecutive pages
  have nothing to do with consecutive T-numbers, and a page boundary looks like
  a gap in the corpus. Stopping at page 8 because "T3, zeros of the Riemann
  zeta function, is the last title alphabetically" lost 22 tables.
* **A page number past the end repeats the last page** rather than returning
  nothing: page 9 and page 10 were byte-identical. A loop that stops when a
  page comes back empty never stops, and a loop that collects until the rows
  repeat is the one that terminates.

A table absent from the listing is either a draft or does not exist; both
answer "Not found" to an unkeyed reader, so the listing is the thing to
compare against, not the T-number page.

What the skill says now: "There is no call that lists the corpus; to see
everything you walk the T-numbers."

What it should say: there is no *client call* that lists the corpus, but the
site has a listing at `/tables?page=N`, fifty tables a page, sorted by title;
read it when the question is about the corpus as a whole rather than about one
table. Note that paging past the end repeats the last page.

Evidence: 2026-09-23. `curl -s "https://numberdb.org/tables?page=$p"` for
`p = 1..10`; 422 unique rows; pages 9 and 10 identical; `T20`, `T21` and `T55`
present in the listing and reachable, `T424`-`T426` absent from it and
answering "Not found" unkeyed, being drafts of the family built from
numberdb-data#191.

## Search the name of the *family*, then search the machinery, then search the
issues -- the third one is what caught this run

What happened: the batch was going to be the elliptic functions. The corpus
holds elliptic *integrals* six ways (T25, T26, T59, T296, T349, T350) and holds
no elliptic *function* at all, and `already_here('Jacobi elliptic function')`
and `already_here('Weierstrass')` both come back clean, because the tables do
not exist yet. What does exist is numberdb-data#191, closed yesterday: the same
family, screened, with $\operatorname{sn}$, $\operatorname{cn}$, the nome and
the theta constants already built as T424-T426 and sitting as drafts. A draft
is invisible to the corpus search and to an unkeyed read, so the only trace of
a day's work was a closed issue.

What the skill says now: `/drafts` lists work in progress and is invisible
externally, so a table can be half-built and unfindable while you restart it.

What it should say: the same sentence, plus the consequence for anybody
choosing what to work on. Before starting a family, search the issue tracker
for it as well as the corpus -- including **closed** issues, which is where a
family that is built-but-not-yet-public shows up, and where a family somebody
is halfway through shows up too. The corpus search cannot see either.

Evidence: 2026-09-23. `already_here('Jacobi elliptic function')` returns
nothing about elliptic functions; GitHub search of numberdb-data for
"Jacobi elliptic function" returns #191 (closed) whose checklist links T424 and
T425; `curl https://numberdb.org/T424` answers "Not found" to an unkeyed
reader.

## `RealBallField(prec)(stored_text)` is not the interval the stored value means

What happened: checking a proposal against T92, *Best Sobolev constant for
$W^{1,p}(\mathbb{R}^n)$*, I recomputed Talenti's formula in
`RealBallField(400)` and compared with the stored value by

    mine.overlaps(R(stored_text))

It answered `False` for every entry tried, at $n = 3, 4, 5, 10$ — which reads
as "the table is wrong", and the obvious next move is to look for the
disagreement. There is none: printing both to 100 places, the recomputed digits
and the stored digits are identical, character for character, for all four.

The cause is what `R(text)` means. `RealBallField(prec)` parses a decimal
string as a ball around *that exact decimal*, with a radius coming from the
working precision — here about $10^{-121}$. But a NumberDB value written as a
decimal denotes an interval whose last digit may be off by one, about
$10^{-98}$ for a 100-digit entry. The stored decimal is a rounding of the true
value, so the true value sits outside the $10^{-121}$ ball and inside the
$10^{-98}$ one. Two balls that both contain the number fail to overlap because
one of them does not contain it.

Widening the stored value by one unit in its last place makes every comparison
pass:

    ulp = RealField(prec)(10)**(-len(text.split('.')[1]))
    mine.overlaps(R(text).add_error(ulp))        # True for all four

The same trap is worse when the string has been shortened by hand. Cutting the
stored 100 digits to 58 and comparing gave `False` as well, for the same
reason at a different scale; truncation is not rounding, so the interval the
short string denotes has to be widened by one unit in *its* last place.

What the skill says now: it explains the interval convention exactly right
("`3.14` is the interval [3.13, 3.15] -- the last digit may be off by one") and
says to check new values against something independent. It does not say that
the client's own ball constructor does not implement that convention, and the
worked example compares against a table through `verify()`, which does.

What it should say: when comparing your own ball against a value read off a
table page rather than through `verify()`, add the last-place unit as an error
first. `RealBallField(prec)(text)` is a ball around the exact decimal, not the
interval the table means by it, and the two differ by however far the stored
precision is short of your working precision. A bare `overlaps` against a
stored string reports a disagreement between values whose digits are the same,
which is the most expensive kind of false alarm: it looks exactly like finding
a wrong table.

Evidence: 2026-09-19, `agents/sage.sh /tmp/check2.py /tmp/check3.py` against
the four $p = 2$ entries of T92 read from `https://numberdb.org/T92`. The
radius of `R(text)` printed as `6.8677...e-121` for the $n=3$ entry;
`overlaps` was `False` against the whole stored string and `True` after
`add_error(10^-99)`, and a digit-by-digit comparison found no differing
character in 101.

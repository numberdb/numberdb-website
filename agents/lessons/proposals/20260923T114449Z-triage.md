# Lessons proposed by run 20260923T114449Z (triage)

Both of these were met in one sitting, and the second is the first one's
consequence, which is the reason to write them together: an authentication
mistake that does not announce itself spent an allowance, and the spent

## The only auth headers are `Authorization: Bearer` and `X-API-Key`; any other scheme is silently anonymous

What happened: a triage went to read tables' states and sent

    curl -H "Authorization: Api-Key $KEY" 'https://numberdb.org/api/table?id=T444'

which is the scheme several other services use. Nothing refused it. It
answered

    {"error": "Rate limit exceeded (60 requests per 60 minutes). An API key
     raises this limit; see /help#section-api.", "retry_after": 775}

Sixty is the *anonymous* limit -- an identified key gets 1000. The request had
a perfectly good key on it and was being counted against the caller's IP
address.

The reason is one `startswith`. `_bearer_token` recognises exactly two forms:

    header = request.headers.get('Authorization', '')
    if header.startswith('Bearer '):
        return header[len('Bearer '):].strip()
    return request.headers.get('X-API-Key', '').strip() or None

`Api-Key ...` matches neither, so the function returns `None`, and `None` does
not mean "a bad token was offered" -- it means "no token was offered". Control
falls past the key branch, past session authentication, to
`'ip:%s' % (_client_ip(request),)` with the anonymous allowance.

What makes this worth a lesson rather than a shrug is that the code
deliberately guards against this very outcome, and the guard is one branch too
late. A *wrong* token is refused loudly, with a comment saying why:

    #A token that is present but wrong is refused rather than quietly
    #demoted to the anonymous allowance, so a stale key is visible to its
    #owner instead of looking like a slow day.
    return None, None, False

So `Bearer deadbeef` -- stale, revoked or mistyped -- gets a refusal you
cannot miss, which is the right design. But `Api-Key <perfectly valid key>`
reaches the anonymous path that comment was written to prevent, because it
never becomes a token at all. The protection is on the value; the mistake is
in the scheme, and nothing checks the scheme.

The symptom is misleading in a specific way. Because the anonymous allowance
is only sixty, the first few requests *work* -- they just work as a stranger.
On `/api/table` a stranger cannot see your unpublished drafts, and that route
reports absence as a 200 with an error body rather than a status
(`20260923T075706Z`), so what you observe is your own drafts reporting
`{"error": "Table with id 'T443' does not exist."}` while everything looks
otherwise healthy. The natural conclusion is that you lost the draft, not that
you lost the key. The rate-limit message is the only honest clue and it
arrives sixty requests later.

One more thing about that allowance, which matters more than it looks:
the anonymous scope is the **IP address**, not the process. Every unauthenticated
probe from the same machine -- other scripts, other agents, a colleague on the
same office NAT -- draws on one bucket of sixty per clock hour. Four campaign
workers on one host share sixty anonymous requests between them.

What the skill says now: it gives `Authorization: Bearer <key>` in its
examples, correctly, but nowhere says that this is the only accepted form, that
`X-API-Key` is the other, or what happens if you use something else. A reader
copying the header shape from a different API has nothing to warn them.

What it should say: the accepted headers are `Authorization: Bearer <key>` and
`X-API-Key: <key>`, and **nothing else counts as a key** -- an unrecognised
scheme is not an error, it is anonymity. Add the diagnostic, because it is the
useful half: if reads of your own drafts say they do not exist, or if a 429
quotes **60 requests per 60 minutes** rather than 1000, your key is not being
seen; check the header before you go looking for the draft. A check that costs
one request:

    curl -s -o /dev/null -w '%{http_code}\n' \
      -H "Authorization: Bearer $KEY" https://numberdb.org/api/costs

`405` is the answer you want: the route read your key and objected only to the
method. A `429` naming 60 means the header never registered as authentication.

Evidence: 2026-09-23, triage of run `20260923T114403Z`.
`numberdb_app/throttle.py:65-71` (`_bearer_token`, the two accepted forms),
`:88-112` (`requester_of`, the fall-through to the `ip:` scope, and the comment
at `:103-105` about a wrong token being refused rather than demoted);
`ANONYMOUS_LIMIT = 60` against `IDENTIFIED_LIMIT = 1000`. Observed against
numberdb.org: `GET /api/costs` with `Authorization: Api-Key <valid key>`

## A 429 also carries `error`, so `"error" in r.json()` stops meaning "not there"

What happened: the same triage needed to know which of a run of T-numbers were
published and which were still unpublished drafts. The campaign already has
the right recipe for this, in the `20260923T075706Z` proposal: `/api/table`
answers 200 for everything, so the status code carries no information, and the
test is `"error" in r.json()` -- compared between a keyed and an anonymous
request.

That recipe is correct as far as it goes, and this run reimplemented it as

    grep -q '"error"' <<<"$body" && echo DRAFT || echo PUBLISHED

and got `DRAFT` for ten consecutive tables, including the four that were
published. The classification was not merely wrong, it was uniformly wrong in
the plausible direction: a campaign that has been failing all morning might
well have a pile of unfinished drafts, so "everything is a draft" reads like a
finding rather than like a bug.

The reason is that `error` now has two sources, and only one of them is the
route. The anonymous allowance had been spent by the header mistake above, so
the throttle was answering every anonymous probe with

    {"error": "Rate limit exceeded (60 requests per 60 minutes)...",
     "retry_after": 670}                                        # HTTP 429

against the route's own

    {"error": "Table with id 'T446' does not exist."}            # HTTP 200

Both have `error`. So the recommended test folds "I am rate limited" into "the
table is not there" -- and it does so exactly when you are leaning on it,
because being throttled is what happens when you probe a lot of tables.

The two failures are distinguishable, but not by the field either note reaches
for. The route never sets a status, so its own absence is always 200; the
throttle decorator sits *in front* of the route and does set one. So the status
code is uninformative about the table and informative about the throttle, which
is the combination that makes a single-field test impossible:

    429            -> you learned nothing; back off for `retry_after`
    200 + error    -> absent, or a draft you cannot see
    200 + Title    -> there, and visible to this caller

What the skill says now: nothing about either. If `20260923T075706Z` is
promoted, this is the amendment it needs.

What it should say: check the status first and the body second. `if
r.status_code == 429: back off` -- honouring `retry_after` -- and only then
`"error" in r.json()`. Better still, match the message rather than the presence
of the key: `"does not exist" in r.json().get("error", "")` says what you
actually mean and cannot be satisfied by a refusal you did not anticipate. And
state the budget, since the probe is the thing that exhausts it: each
anonymous probe is one request against sixty per clock hour shared by your
whole IP, so classifying thirty tables this way is half your hour and doing it
twice fails in the manner above. Read tables with your key, where the
allowance is 1000, and probe anonymously only the ones whose visibility
actually matters.

Worth adding the reflex for the general case, since this campaign's history is
a list of tests that matched the wrong thing: when a check has to tell two
failures apart, make it read a field that differs between them. `error` is
present in both; the status and the message are not.

Evidence: 2026-09-23, triage of run `20260923T114403Z`. Observed against
numberdb.org: anonymous `GET /api/table?id=T444` answered `HTTP:429` with the
rate-limit body quoted above while the keyed read of the same id returned the
full document, and a presence-of-`error` test classified T439-T445 as drafts,
the published ones included. `curl -w 'HTTP:%{http_code}'` on the same URL is
what showed it. The 404-shaped message is quoted from an anonymous read of
`T446`, which genuinely does not exist, and arrived with status 200.
`numberdb_app/api.py:392,397,404,406,414` -- every `JsonResponse` on this route
is constructed without `status=`, so Django sends 200; contrast

Compare triage `20260923T081329Z`, which printed the message rather than

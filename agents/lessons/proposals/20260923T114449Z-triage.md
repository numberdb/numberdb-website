# Lessons proposed by run 20260923T114449Z (triage)

Both of these were met in one sitting, and the second was caused by the first,
which is the reason to write them together: an authentication mistake that
does not announce itself spent an allowance, and the spent allowance then
silently inverted a test that had nothing to do with authentication.

## The only auth headers are `Authorization: Bearer` and `X-API-Key`; any other scheme is silently anonymous

What happened: a triage went to read a table's state and sent

    curl -H "Authorization: Api-Key $KEY" 'https://numberdb.org/api/table?id=T444'

which is the scheme several other services use. It did not fail. It answered
an HTML 404 page for a table that exists, and then, a few calls later,

    {"error": "Rate limit exceeded (60 requests per 60 minutes). An API key
     raises this limit; see /help#section-api.", "retry_after": 775}

Sixty is the *anonymous* limit. The request had a perfectly good key on it and
was being counted against the caller's IP address.

The reason is one `startswith`. `_bearer_token` recognises exactly two forms:

    header = request.headers.get('Authorization', '')
    if header.startswith('Bearer '):
        return header[len('Bearer '):].strip()
    return request.headers.get('X-API-Key', '').strip() or None

`Api-Key ...` matches neither, so the function returns `None`, and `None` does
not mean "bad token" -- it means "no token was offered". Control falls past
the key branch to session authentication and then to
`'ip:%s' % (_client_ip(request),)` with the anonymous allowance.

What makes this worth a lesson rather than a shrug is that the code
deliberately guards against exactly this outcome and the guard is one branch
too late. A *wrong* token is refused loudly, with a comment saying why:

    #A token that is present but wrong is refused rather than quietly
    #demoted to the anonymous allowance, so a stale key is visible to its
    #owner instead of looking like a slow day.
    return None, None, False

So `Bearer deadbeef` -- a stale, revoked or mistyped key -- gets a refusal you
cannot miss, which is the right design. But `Api-Key <perfectly valid key>`
reaches the anonymous path the comment was written to prevent, because it
never becomes a token at all. The protection is on the value and the mistake
is in the scheme.

The symptom is misleading in a specific way: the thing you notice first is
*not* an auth error. It is 404s on resources that exist. An unpublished draft
is invisible to a stranger, so an unauthenticated read of your own draft
answers "does not exist", and the natural conclusion is that you lost the
draft rather than that you lost the key. The rate limit message is the only
honest clue, and it arrives sixty requests later.

What the skill says now: it gives `Authorization: Bearer <key>` in its
examples, correctly, but nowhere says that this is the only accepted form or
what happens if you use another. A reader copying the shape from a different
API has nothing to warn them.

What it should say: the accepted headers are `Authorization: Bearer <key>` and
`X-API-Key: <key>`, and *nothing else counts as a key*. Add the diagnostic,
because it is the useful half: if reads of your own drafts answer "does not
exist", or if a 429 quotes **60 requests per 60 minutes** rather than 1000,
your key is not being seen -- check the header scheme before you go looking
for the draft. A one-line check that costs one request:

    curl -s -o /dev/null -w '%{http_code}\n' \
      -H "Authorization: Bearer $KEY" https://numberdb.org/api/costs

`405` means the key was read and you used the wrong method, which is the
answer you want here. `401` means the key itself is the problem. A `429`
naming 60 means the header never registered as authentication.

Evidence: 2026-09-23, triage of run `20260923T114403Z`.
`numberdb_app/throttle.py:65-71` (`_bearer_token`, the two accepted forms),
`:88-112` (`requester_of`, the fall-through to `ip:` and the comment at
`:103-105` about a wrong token being refused), `_limits()` giving
`ANONYMOUS_LIMIT = 60` against `IDENTIFIED_LIMIT = 1000`. Observed: `Api-Key`
scheme returned an HTML 404 for the existing `T444` and then the 60-per-hour
429 above; the same URL with `Bearer` returned the table's JSON, and
`/api/costs` with `Bearer` returned `405`.

## `error` in the body means "something went wrong", not "not found" -- read the status

What happened: the same triage needed to know which of a run of T-numbers were
published and which were still unpublished drafts. There is a neat test for
this and it is genuinely the right idea: a draft is invisible to a stranger,
so fetch each table *without* a key and see whether it is there. An earlier
triage had used it and recorded its output carefully, message and all.

This run reimplemented it as a check for the `error` key:

    ka=$(printf '%s' "$A" | grep -q '"error"' && echo DRAFT || echo PUBLISHED)

and got back, for ten consecutive tables, `DRAFT`. Including the four that
were published. The classification was not merely wrong, it was uniformly
wrong in the direction that looks plausible -- a campaign that has been
failing all morning might well have a pile of unfinished drafts, so
"everything is a draft" reads like a finding instead of like a bug.

Both answers carry `error`, and they mean opposite things:

    {"error": "Table with id 'T446' does not exist."}                  # 404
    {"error": "Rate limit exceeded (60 requests per 60 minutes)...",
     "retry_after": 670}                                               # 429

The anonymous allowance had been spent by the header mistake above, so every
anonymous probe was answering 429, and 429 contains `error`, so every table
classified as absent. The test inverts precisely when you use it a lot, which
is when you are relying on it.

The general shape is worth naming: the API reports every refusal as
`{"error": ...}` with the distinguishing information in the HTTP status and
the message, not in the shape of the body. So `if 'error' in response` is a
test for "this request did not succeed" and it is fine for that. It is not a
test for any particular reason, and using it as one silently folds "rate
limited", "not found", "not permitted" and "malformed" into a single verdict.

What the skill says now: nothing about distinguishing the error cases, and
nothing about the anonymous-visibility test for whether a table is published.

What it should say: two things. First, that the draft/published test is
`GET /api/table?id=T<n>` with no key -- 200 is published, 404 is a draft or
does not exist -- and that it must branch on `%{http_code}` or on the message
text, never on the presence of `error`. Second, the budget: each probe is one
anonymous request against sixty per clock hour shared by your whole IP
address, so classifying thirty tables this way is half your hour and doing it
twice fails in the manner above. If you need more than a handful, read the
tables with your key (unlimited-ish at 1000) and probe anonymously only the
ones whose state actually matters.

Worth adding the reflex for the general case, since the campaign's own history
is a list of tests that matched the wrong thing: when a check has to tell two
failures apart, make it read the field that distinguishes them. Here that is
the status code; the body's `error` key is present in both.

Evidence: 2026-09-23, triage of run `20260923T114403Z`. Observed: anonymous
`GET /api/table?id=T444` answered `HTTP:429` with the rate-limit body while
the keyed read returned the table, and a presence-of-`error` test classified
T439-T445 as drafts including the published ones; `curl -w "HTTP:%{http_code}"`
on the same URL is what showed it. The 404 form is quoted above from an
anonymous read of `T446`, which genuinely does not exist. Contrast the earlier
triage `20260923T081329Z`, which printed the message rather than testing for
the key and so distinguished the two correctly.

## Sage's `pAdicLseries.series` precision keyword is not the stored p-adic precision

What happened: T413's `Programs` snippet used
`E.padic_lseries(5).series(1, prec=1).list()[0]`. It agreed with the beginning
of the stored row for 11a1 at $p=5$, but stopped at `O(5^20)` while the table
stores `O(5^72)`. Raising the first argument from 1 to 80 still returned
`O(5^20)`, and setting `prec=72` returned only `O(5^2)`. Sage's documentation
for `series` says `prec` is the maximal number of power-series terms to
compute, not the p-adic precision of the constant term. Computing the table's
Formula instead, with `alpha = Lp.alpha(72)`, reproduced the stored value
exactly.

What the skill says now: `Programs` should be the standard incantation for a
reader who wants one more value, and a previous proposal says to check that a
snippet reaches the table's own precision. It does not warn that a Sage
keyword named `prec` can mean series length rather than p-adic coefficient
precision.

What it should say: for Sage p-adic $L$-series, do not assume
`series(..., prec=n)` gives coefficients to `O(p^n)`. Run the snippet and
inspect the `O(p^n)` it returns. If the table stores a central value to higher
precision, compute the interpolation formula directly with `Lp.alpha(n)` or
another checked high-precision method, and make the program's precision
parameter visible in the code.

Evidence: T413 repair, 2026-09-22. `series(1, prec=1)` returned
`O(5^20)`, `series(n, prec=1)` for `n=1,2,3,4,5,10,20,40,60,70,71,72,73,80`
always returned `O(5^20)`, and `series(1, prec=72)` returned absolute
precision 2. The replacement snippet using
`(ratio * (1 - 1 / Lp.alpha(72))**2).add_bigoh(72)` matched the stored
`O(5^72)` row exactly.

## Sage's `clebsch_gordan` may contain a floating coefficient where `wigner_3j` is exact

What happened: while building T252, the generator computed Wigner $3j$
symbols from the Racah sum and checked the Clebsch-Gordan rows against
Sage's `clebsch_gordan`. The first disagreement was at
$(j_1,j_2,j_3;m_1,m_2,m)=(1,2,2;-1,-1,-2)$. The Wigner row agreed with
Sage's exact `wigner_3j`, and the Clebsch-Gordan value agreed with the
documented Wigner relation, but Sage's `clebsch_gordan` returned
`-0.16666666666666666*sqrt(5)*sqrt(12/5)` instead of
`-1/6*sqrt(5)*sqrt(12/5)`. The difference was only the binary floating
coefficient in the checker.

What the skill says now: check new values against something independent, and
when two computations disagree, neither is right until the cause is known.

What it should say: an independent Sage special-function check still needs an
exactness check on the result it returns. If Sage documentation says a routine
returns an exact expression, inspect the coefficient types or compare through
an exact companion identity before trusting a disagreement. For the Wigner
family, `wigner_3j` returned exact symbolic values in the cases checked, while
`clebsch_gordan` could introduce a `RealNumber` coefficient when integral
quantum numbers reached it as rationals.

Evidence: T252, 2026-09-15. The dry run stopped with
`Clebsch-Gordan value disagrees with Sage at (2, 4, 4, -2, -2, -4)`.
`/tmp/wigner_sage_relation.py` printed Sage's exact relation as
`-1/6*sqrt(5)*sqrt(12/5)` and Sage's `clebsch_gordan` result as
`-0.16666666666666666*sqrt(5)*sqrt(12/5)`.

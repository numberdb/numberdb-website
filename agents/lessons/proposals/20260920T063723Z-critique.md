## Sage's `wigner_9j` refuses half-integer arrays, not radical ones

What happened: the T363 critique ran `sage.functions.wigner.wigner_9j` on all
764 arrays the table stores. 416 answered and 348 raised

    ValueError: j values must be integer or half integer and fulfill the
    triangle relation

on arrays that are perfectly admissible — every one of the six row and column
triads satisfies the triangle inequalities and has an integer sum. The first
row of the table, `1/2,1/2,0,1/2,1/2,0,0,0,0`, is one of them. Every failing
array has a half-integer entry, and none of the 51 all-integer arrays failed.
The cause is in Sage's own source: `imax = int(min(j_1 + j_9, j_2 + j_6,
j_4 + j_8))` truncates a half-integer bound, so the loop sums over integer `kk`
where the intermediate coupling has to be half-integer, and `racah` then
refuses a triad it is handed. `prec=` makes no difference, because the refusal
happens before any arithmetic.

This corrects the build's own note of the same morning
(`agents/lessons/proposals/20260920T055415Z-build.md`), which recorded the
failure as a `NameError: name 'RR_1_10' is not defined` on "small
radical-valued rows". Radical rows are not the problem: Sage returned
`1/2*sqrt(1/3)` exactly for `wigner_9j(1,1,0,1/2,1/2,0,1/2,1/2,0)`. Half-integer
arrays are, and they are 713 of the 764 rows a table of small angular momenta
holds.

What the skill says now: "Check new values against something independent", and
that a generator checked only against itself is not checked. It says nothing
about a library function that refuses half of a family's arguments while
answering correctly for the rest.

What it should say: when a library function is the independent source, measure
what fraction of the table's own arguments it answers before relying on it, and
before putting it in `Programs`. A function that raises on some admissible
arguments is worse than one that is missing, because a sample of a few values
looks like agreement. For Wigner symbols specifically: Sage's `wigner_3j` and
`wigner_6j` take half-integers throughout, and `wigner_9j` does not; check a
$9j$ table against the DLMF finite sum of six $3j$ symbols instead, and pick the
`Programs` example from the arguments the library can actually take.

Evidence: 2026-09-20, T363 critique. `/tmp/sweep.py` under `agents/sage.sh`:
"rows: 764 answered: 416 raised: 348 {'ValueError': 348}", all 348 with a
half-integer argument. `/tmp/progcheck.py`: `wigner_9j(1,1,0,1/2,1/2,0,1/2,1/2,0)`
returned `1/2*sqrt(1/3)`, matching the stored
`0.2886751345948128822545743902509787278238008756350634380093...`.

## A title whose only distinguishing part is mathematics gets an address that does not distinguish it

What happened: T253 is "Wigner $6j$ symbols" and T363 is "Wigner $9j$ symbols".
The slug drops `$...$`, so both bare to `Wigner_symbols`; the first took it and
the second is at `https://numberdb.org/Wigner_symbols_2`. Nothing warns the
author, the suffix is silent, and the address of a published table is then
deliberately frozen. A reader pasting `/Wigner_symbols_2` into a paper has
written an address that names neither the $9j$ symbols nor anything else.

The same shape will bite any pair of tables distinguished only inside the
mathematics: an index, an order, a degree, a convention written as a symbol.

What the skill says now: "Never guess a name the database resolves", and that
mathematics is dropped from a slug, truncation happens and "a clash appends a
number" — as a reason to read the slug off a search result rather than invent
it. It does not say that the clash can be *yours*, or that the resulting
address is permanent.

What it should say: before choosing a title, strip the `$...$` from it and ask
whether what is left still names the table. If it does not, and a sibling
table bares to the same words, the address will be that phrase with a number
after it, forever. Either put a distinguishing word outside the mathematics, or
accept it and cross-reference by `HREF{T363}`, which the audit accepts and
which at least resolves to one thing.

Evidence: 2026-09-20, T363 critique. `https://numberdb.org/Wigner_symbols` is
"Wigner $6j$ symbols" and `https://numberdb.org/Wigner_symbols_2` is
"Wigner $9j$ symbols", both 200; `slug_for` in `numberdb_app/editing.py` drops
`$6j$` and `$9j$` because each is surrounded by spaces, and
`numberdb_app/editing.py:472` leaves a published table's slug alone.

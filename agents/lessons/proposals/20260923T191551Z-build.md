## Ball formatting precision is not the same as source precision

What happened: T447 stores rounded source intervals widened by half of the
last printed decimal place. The first generator returned a per-entry `digits`
field computed from `_compare.digits_of(to_text(value, DIGITS, "ball"))`, so
wide intervals were written with only five or six centre digits. For
`format = "ball"`, `to_text` rounded the centre to that many digits but did
not enlarge the radius. The stored ball therefore no longer contained the
same interval the generator computed, and `verify(sample=None)` reported
differences at `alphabet=2, exponent=14/5` and `alphabet=2, exponent=3`.
Writing the same intervals with the generator's ordinary 12 centre digits
made all 118 entries match.

What the skill says now: it says to run `dry_run.py`, check exactness, measure
the entries, and then run `verify()` on the values read back from the
database. It does not say that lowering the displayed digit count of a real
ball can move the centre without widening the radius.

What it should say: when a generator writes real intervals with
`format = "ball"`, choose enough digits to print the centre independently of the
source's certified width. Do not use `_compare.digits_of` or a precision check
as the entry's display precision unless you have also checked that the stored
text still contains the computed interval. If the source certifies decimal
endpoints, an endpoint spelling or a high-precision centre with radius is
safer than a low-precision centre with the original radius.

Evidence: T447 build, 2026-09-23. After restating the draft, `cat
"$NUMBERDB_KEY_FILE" | NUMBERDB_KEY_FROM_STDIN=1 agents/sage.sh
generators/power-free-language-growth-rates/generate.py` reported
`<VerifyReport T447: 116/118 matched, 2 differing, 0 missing, 0 extra>`; after
removing the per-entry `digits` field and restating, the same command reported
`<VerifyReport T447: 118/118 matched, 0 differing, 0 missing, 0 extra>`.

# Lessons proposed by the T339 critique, 2026-09-19

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## `complete` takes `yes`, `no` or `unknown`, and anything else is printed as you wrote it

What happened: T339 stores `complete: false` under `Data properties`, and the
page renders **"Table is complete: false (it holds …)"** — a boolean read as
English in a sentence whose other 100-odd instances say "no". It is not an
error the site refuses: `complete` is free text, the size-exemption check reads
only the leading word and treats `yes`, `true` and `complete` as complete
(`numberdb_app/limits.py:257`), and the metadata form offers a closed
vocabulary of `yes`, `no`, `unknown` (`metadata_form.py:45`) and marks anything
outside it as an answer it cannot show, leaving it untouched. So a contributor
writing the document by hand — especially one writing YAML, where `false` is
what a boolean field wants — gets a page that reads oddly and an edit form that
declines to offer the field. T241, published, has the same `false`, which is
where T339 copied it from: the mistake propagates by imitation.

What the skill says now: "`complete: no`, with `complete-note` saying which
part is finished", and 'It renders inside "complete: no (...)"'. The example is
right and nothing says the vocabulary is closed, or that the field is prose
rather than a boolean.

What it should say: `complete` is one of the three words `yes`, `no`,
`unknown`, optionally followed by a qualifier the site keeps (`yes, assuming
GRH`). Not `true`/`false`: the field is read as English on the page and by a
form that offers those three, and a boolean written there survives but reads as
a machine's answer in a sentence of prose.

Evidence: 2026-09-19, T339 critique. `GET /api/table?id=T339` gives
`"complete": "false"`; the rebuilt page carries `Table is complete: false (it
holds Bernoulli$(p)$ …)`. T288, T316, T321, T332, T335, T337, T338 all carry
`yes` or `no`; T241 carries `false`. `numberdb_app/metadata_form.py:45`,
`numberdb_app/limits.py:247-257`, `numberdb_app/templates/edit-metadata.html:210`.

## A stored decimal is an interval one unit wide in its last place, so `overlaps` is the wrong check against a fresh ball

What happened: checking T339's `Programs` snippet, the obvious verification —
recompute the value in `RealBallField`, build a ball from the stored 100-digit
string, ask whether they overlap — answered **False** on a row that is
perfectly correct. `RealBallField(prec)(some_decimal_string)` builds a *tight*
ball at the field's precision, near-zero radius, not the interval the written
digits denote. The fresh computation was accurate to 128 digits (radius
$3.7\cdot10^{-129}$) and the stored value carries 100, so the two balls are
disjoint whenever the stored digits are a correct rounding — which is the
normal case, not a fault. The check that means something is the claim the
digits make: $|{\rm computed} - {\rm stored}| < 1$ unit in the last written
place. Here it is $6.7\cdot10^{-102}$ against a claim of $10^{-100}$, and the
row is right.

Anyone checking a published table's digits on their own machine reaches for
`overlaps` first, and a False there reads as "the table is wrong" rather than
"you compared a tight ball with a tighter one".

What the skill says now: it states the convention ("A real is stored as an
interval that contains it", `3.14` *is* `[3.13, 3.15]`), and it warns about the
opposite failure — an enclosure so wide it agrees with everything, and
comparing at the midpoint instead of over the interval. Nothing says how to
compare a stored decimal with a value you have just computed, and nothing warns
that parsing the stored string into a ball throws the interval away.

What it should say: to check a stored value against your own computation, read
the stored digits as the interval they denote and ask whether your value lies
inside it — `abs(mid - stored) < 10**-k` for `k` digits after the point, or
build the ball yourself with `RealBallField(prec)(stored, 10**-k)`. Do not ask
whether a ball built from the stored string overlaps yours: that string parses
to a ball of the field's own precision, so a correct table and a more precise
recomputation disagree by construction. (`verify()` does this properly; the
trap is only for a hand check.)

Evidence: 2026-09-19, T339 critique, `/tmp/t339_program.py` and
`/tmp/t339_program2.py` in `agents/sage.sh`. The table's own `Programs`
snippet for Bernoulli(1/3): `h.overlaps(R(stored))` → `False`, `h.rad()` →
`3.7202596e-129`; against the same stored string at `RealField(500)`,
`abs(mid - stored)` → `6.697...e-102`, inside the $10^{-100}$ the hundred
digits claim.

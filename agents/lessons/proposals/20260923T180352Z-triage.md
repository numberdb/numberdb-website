# Lesson proposed by triage 20260923T180352Z

## A key your script never received is not an error, it is a 429 telling you to get a key

What happened: triage wanted to know what a failed build had left in the
corpus, so it read a few tables through the API with the key piped in the way
this project's own instructions describe -- `cat "$NUMBERDB_KEY_FILE" |
python3 ...`. Every call came back

    HTTP 429 {"error": "Rate limit exceeded (60 requests per 60 minutes).
                        An API key raises this limit; see /help#section-api.",
              "retry_after": 3191}

on the *first* request, recommending the API key that was being supplied. I
read that as the box being locked out, went looking for who had spent the
budget, and lost six turns to it before the answer turned out to be in my own
command line: the script was a heredoc,

    cat "$KEY" | python3 - <<'EOF'      # the heredoc IS stdin; the pipe is not

`python3 -` reads its program from stdin, the heredoc redirect wins over the
pipe, and `sys.stdin.read()` then returns `''`. Demonstrated on its own:

    $ printf 'THE-KEY' | python3 - <<'EOF'
    import sys
    print(repr(sys.stdin.read()))
    EOF
    ''

So the header went out as `Authorization: Bearer ` with nothing after it, the
server saw no token, and scoped the caller anonymous -- 60 requests an hour
instead of 1000, a bucket already spent by everything else sharing the address.

The part worth a sentence in the skill is not the shell mistake, which is
already proposed at `agents/lessons/proposals/20260918T023648Z-triage.md`
(2026-09-18) and noted for this deployment at `docs/agent-environment.md:258`.
It is that **an empty key does not fail**. It is silently demoted, and the
refusal that follows names the exact thing you believe you are sending. A wrong
key is easy: `403 {"error": "Invalid API key."}`, immediate, unambiguous. A
key that never arrived is the expensive one, because every symptom points at
the server.

What the skill says now: nothing. `SKILL.md` has no mention of the rate limit,
of `Authorization: Bearer`, or of what an unauthenticated call looks like. It
tells the reader to publish with "the owner's API key" and does not say how the
server answers when that key is absent, wrong, or spent -- three different
replies that a contributor will meet in that order of likelihood.

What it should say: read a 429 from this API by its body, not its status. The
three cases are distinguishable from the response alone, and the distinction is
in `numberdb_app/throttle.py:88-112, 178-192`:

* `429` **whose message ends "An API key raises this limit"** -- the server saw
  no key. That sentence is appended only when the caller was scoped `ip:`. Your
  key is missing from the request, not exhausted. Check it arrived before you
  check anything else.
* `403 {"error": "Invalid API key."}` -- a key was sent and is wrong or
  revoked. Refused before the counter is touched, so it never presents as a
  rate limit.
* `429` **without** that sentence -- your key's own allowance, 1000 requests an
  hour against the anonymous 60. This is the only one that waiting fixes.

And a fourth that is not the throttle at all: a `429` from `POST /api/tables`
is the draft ceiling, per the proposal of 2026-09-23 16:44Z. Four meanings on
two status codes; all four are legible from the body, none from the code.

Two smaller things that belong with it:

* `retry_after` is the time to the top of the hour, not to your own window:
  the counter is a fixed window at `now - (now % 3600)`
  (`throttle.py:122-123`), identical for every caller. Two callers in different
  buckets get the same countdown, so a matching `retry_after` is not evidence
  you share a limit with anybody. I inferred exactly that, wrongly.
* The defensive line the 2026-09-18 proposal already recommends is the whole
  fix, and this is the second run to arrive at it independently:

      key = sys.stdin.read().strip()
      assert key, 'no key on stdin: is the script itself coming from a heredoc?'

  Better still, keep the script in a file and read the key from the path:
  `python3 /tmp/probe.py` with
  `open(os.environ['NUMBERDB_KEY_FILE']).read().strip()` inside it. That is
  what worked here, and it leaves stdin free.

Evidence: 2026-09-23, 18:06-18:12Z. `GET /api/table?id=T443`, same endpoint,
same minute, four ways -- key from a heredoc'd script -> 429 with the `ip:`
sentence; `X-API-Key` from the same script -> the same 429; a deliberately
wrong literal token -> `403 Invalid API key.`, which is what proved the header
was reaching the view and the key was not in it; the key read from
`$NUMBERDB_KEY_FILE` inside a `/tmp` script -> `200` with the table document,
in the same second that an anonymous call to the same path answered 429.
`numberdb_app/throttle.py` at 6b70e5e1.

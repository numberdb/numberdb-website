## `source_names_it` follows redirects, so a family with no article of its own can pass

What happened: screening a candidate called "Turyn rotated Legendre
sequences" against `https://en.wikipedia.org/wiki/Legendre_sequence`, the
check complained only that the page does not mention "turyn" or "rotated". It
did not complain about "legendre", so the word was there and the page
answered 200. There is no Wikipedia article called *Legendre sequence*: the
title redirects to *Legendre symbol*, and the check was reading that article.
Had the proposed name been "Legendre sequences" alone, the screen would have
passed it outright and the citation in the report would have pointed at an
article that says nothing about the family.

What the skill says now: nothing about redirects. It says to cite a source
and run `source_names_it` on it, "the only check that a family is real and is
called what you say".

What it should say: a 200 from Wikipedia is not evidence the article exists
under the name you used. Check that the page you got back is the page you
asked for, by looking at its title rather than at the screen's verdict, or by
asking for `?redirect=no`. The check tests words, and a redirect target
shares words with its redirect by construction.

Evidence: 2026-09-17, `/tmp/screen_run.py` (the "turyn, rotated" complaint);
`curl -sL https://en.wikipedia.org/wiki/Legendre_sequence` returns a document
titled "Legendre symbol - Wikipedia".

## A compound title fails the source check on both of its sources, and that is the screen working

What happened: the proposed title "Merit factors of the Fekete polynomials"
failed `source_names_it` twice. Against
`https://en.wikipedia.org/wiki/Fekete_polynomial` it failed for not
containing "merit" or "factors"; against the arXiv abstract of a merit-factor
paper it failed for not containing "fekete". Both sources are real and each
names half the title. No single source names an object together with a
quantity taken of it, which is the shape of a large fraction of the corpus's
titles (*Regulators of real quadratic fields*, *Merit factors of ...*).

What the skill says now: cite a source for every proposal and run
`source_names_it` on it.

What it should say: for a title of the form "quantity of object", run the
check twice, once on the quantity's name against a source that defines the
quantity and once on the object's name against a source that defines the
object, and report both. If neither source names the quantity applied to that
object, that is worth knowing: it usually means the literature calls the
family something else, and the title should be the name some source does use.
Here it was "Merit factors of the Legendre sequences", which passes against
arXiv:1602.04514 in one call.

Evidence: 2026-09-17, `/tmp/screen3.py`, five calls, three complaints and two
`None`s.

## The merit factor of a Legendre sequence depends on the $u_0$ term and on the rotation, and getting either wrong lands between the two theorems

What happened: checking a proposal against Golay's and Høholdt–Jensen's
asymptotics, the quarter-rotated Legendre sequence came out at merit factor
1.79 at $p=101$ where the theorem says it tends to 6. The sequence rotated
was the $p-1$ nonzero coefficients of the Fekete polynomial,
$\left(\frac ap\right)$ for $1\le a<p$. The literature's Legendre sequence
has length $p$, with $u_0=1$ supplied for the term the Legendre symbol makes
zero, and a cyclic shift of *that* is what the theorem is about. With $u_0$
in place the numbers appear: 5.4609 at $p=101$ and 5.9835 at $p=997$ at
rotation $\lfloor p/4\rfloor$, and 1.4784 and 1.4978 unrotated, against
$1/F\to\frac23-4|\rho|+8\rho^2$, which gives $3/2$ at $\rho=0$ and $6$ at
$\rho=\frac14$.

The failure is worth naming because of how it looks: 1.79 is not close to
either 1.5 or 6, so it reads like a slowly converging asymptotic rather than
like the wrong object. Unrotated, both conventions tend to $3/2$, so the
mistake is invisible until a rotation is taken.

What the skill says now: nothing about this family. It says generally to
write down which normalisation and which indexing before computing.

What it should say: when a table holds a quantity of a sequence built from a
character, state whether the term at the character's zero is dropped or
supplied, and with what value. A one-term difference in a length-$p$ vector
changes the aperiodic autocorrelations at every lag, and any check against an
asymptotic theorem will be off by an amount that looks like slow convergence.

Evidence: 2026-09-17, `/tmp/checks.py` (length $p-1$: 1.7921 at $p=101$,
1.4717 at $p=199$) and `/tmp/rot.py` (length $p$ with $u_0=1$: 5.4609,
5.6719, 5.4239, 5.6653, 5.9109, 5.9835 for $p=101,199,293,397,599,997$ at
$r=\lfloor p/4\rfloor$).

## A polynomial built from the Legendre symbol checks itself against a class number, which Sage computes by a route that never sees the polynomial

What happened: looking for an independent check on a proposed table of Fekete
polynomials $f_p(x)=\sum_{a}\left(\frac ap\right)x^a$, the derivative at 1
turned out to be exactly $-p\,h(-p)$ for every $p\equiv3\pmod4$ with
$7\le p\le199$: $f_{47}'(1)=-235=-47\cdot5$, $f_{191}'(1)=-2483=-191\cdot13$.
The class numbers came from `QuadraticField(-p).class_number()`, which is a
different computation in every sense. $p=3$ is the exception, because
$\mathbb{Q}(\sqrt{-3})$ has six roots of unity. For $p\equiv1\pmod4$ the sum
vanishes by the symmetry $a\mapsto p-a$, so $(x-1)^2$ divides $f_p$ there,
which is a second free check. Separately $f_p(\zeta_p)$ is the quadratic
Gauss sum and squares to $(-1)^{(p-1)/2}p$, verified exactly in
`CyclotomicField(p)` for every prime $p\le59$.

What the skill says now: "a specialisation to a sequence with an OEIS
number", "a value in a published table", "an identity relating it to a table
this database already holds" are the kinds of check to name.

What it should say: for a family whose coefficients are the values of a
Dirichlet character, three checks come free and cost nothing to run: the
value at 1 (zero, for a non-trivial character), the derivative at 1 (a class
number, for the quadratic character of a prime $p\equiv3\pmod 4$), and the
value at a root of unity (a Gauss sum, which T142 holds). None of them uses
the code that built the coefficients.

Evidence: 2026-09-17, `/tmp/fekete_sage.py` through `agents/sage.sh`: the
ratio $-f_p'(1)/(p\,h(-p))$ printed 1 for all eighteen primes tested, and
`g^2 == (-1)^((p-1)/2) p` printed True for all seventeen.

## `already_asked` answers "could not ask GitHub (HTTPError)" at the anonymous rate limit, and that is not "nobody asked"

What happened: screening eight candidate names in one pass, the last few
returned `could not ask GitHub (HTTPError)` where the first few returned
issue lists. GitHub's search API allows ten requests a minute unauthenticated.
The string is honest — it says the question could not be asked — but it sits
in the same column as a genuine empty list, and a run that skims its own
screening output will read it as "no issue asks for this".

What the skill says now: nothing; `already_asked` is documented in
`screen.py`, whose own comments make the point that a failed question and an
empty answer must not look the same.

What it should say: when `already_asked` complains, redo it before believing
the result, with `gh issue list --repo numberdb/numberdb-data --state all
--search <name>`, which is authenticated and has a much larger budget. A
closed issue is the one that matters most, and it is the one a rate limit
hides.

Evidence: 2026-09-17, `/tmp/screen_run.py` returned the complaint for
*Fekete polynomials* and *Merit factors of the Fekete polynomials*; the same
question through `gh` returned nothing for either, and a plain `curl` of the
same API URL answered 200 a few minutes later.

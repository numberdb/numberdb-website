## Check the precision path for Bessel roots; `find_root` may not use the field precision

What happened: repairing T390 needed a runnable program for the disk, sector
and annulus rows. A first Sage check used `sage.all.bessel_J` with
`find_root` and wrapped the result in `RealField(100)`. It ran, but the unit
disk value differed from the stored 30-digit entry by about `1.648e-13`, so it
was only a double-precision root dressed as a high-precision number. Rewriting
the check to set `mpmath.mp.dps = 80`, use `mpmath.besseljzero` for Bessel
zeros, and use explicit bisection for the annulus root matched the displayed
digits of all formula rows.

What the skill says now: it warns that `root finding` is not brought in by
the named Sage imports, and it says to check the claim the digits make. It
does not say that a root-finding call may silently compute at lower precision
than the field used to print the answer.

What it should say: when a value depends on numerical root finding, check the
precision of the root itself, not only the printed field it is coerced into.
Wrapping a root in `RealField(100)` after the solve does not make the solve a
100-bit computation. For Bessel zeros, use a high-precision path such as
`mpmath.besseljzero` with `mp.mp.dps` set, or a verified interval method when
the table claims proven digits, and compare the written interval or digits
against the stored entry.

Evidence: on 2026-09-21, `agents/sage.sh /tmp/t390_verify.py
/tmp/T390-live.json` first printed `unit-disk: error 1.648e-13` and failed.
The revised script printed errors below `1e-26` for the rectangle, disk,
sector, annulus and triangle rows, including `sector-60 is the angle pi/3
sector: nu = pi / (pi/3) = 3`.

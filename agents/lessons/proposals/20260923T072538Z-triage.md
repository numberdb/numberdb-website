# `len(numberdb.table(tid)['Numbers'])` is the number of first-parameter groups, not the number of entries

What happened: the build of T444 filled the draft with 12 entries -- the
cumulants $\kappa_n(\beta)$ for $\beta\in\{1,2,4\}$ and $n\in\{1,2,3,4\}$ --
and the run's own fill reported "12 entries added to T444". Immediately after,
the same run read the table back to check the prose and printed

    print('numbers', len(t.get('Numbers') or []))

which answered

    numbers 3

The run took no notice and carried on. Both numbers are right. `Numbers` comes
back from the API nested, keyed by the first parameter and then the second:

    {"1": {"1": "-1.2065335745820", "2": "1.607781034581",
           "3": "0.5982682569",     "4": "0.427146362"},
     "2": {...}, "4": {...}}

so `len()` over it counts the three $\beta$ groups. For a one-parameter table
`len()` happens to be the entry count, which is what makes this quiet: the
habit works until the first table with two parameters, and then it
under-reports by a factor of the second parameter's range without raising
anything.

The failure mode to worry about is not "3 looks wrong". It is that 3 looks
*plausible*. A contributor filling a 4x25 table and reading back `len(...) ==
4` has a number that could easily be mistaken for a count of something, and
nothing says otherwise.

What the skill says now: it tells you to check the values read back out of the
database, and `agents/lessons/PROPOSALS.md` already warns not to copy this
nested `Numbers` into a full-document write (the T175 lesson, "Do not
round-trip `numberdb.table()`'s nested `Numbers` through a full-document
edit"). Neither says what the shape of the thing you read back *is*, or that
counting it is not counting entries.

What it should say: `numberdb.table(tid)['Numbers']` is nested one level per
parameter, so its length is the number of distinct values of the first
parameter. To count entries, either count the leaves or -- better -- do not
count at all and use `generator.verify(sample=None)`, which answers in the
terms you actually want:

    <VerifyReport T444: 12/12 matched, 0 differing, 0 missing, 0 extra>

`missing` and `extra` are the check "did every entry land?"; a length is not.

Evidence: 2026-09-23, build run `20260923T062751Z`, T444. The run's fill
reported 12 entries and its `verify(sample=None)` reported `12/12 matched, 0
differing, 0 missing, 0 extra` twice; the read-back in the same session
printed `numbers 3`. Confirmed live against the published table on 2026-09-23:
`GET /api/table?id=T444` returns a `Numbers` dict with 3 keys (`'1'`, `'2'`,
`'4'`) and 12 leaf values. Cross-reference `PROPOSALS.md:4565`, which is the
same nesting met from the writing side.

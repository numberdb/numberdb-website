# Lessons from the ideas run of 2026-09-20T0338 (optical constants of materials)

## A source that publishes both a model and its derived constants tells you how many digits a table may carry

What happened: the batch proposes tables of refractive indices taken from a
published catalogue -- measured values, not computable ones, so there is no
working precision to raise and no ball arithmetic that makes them better. The
question a proposal for measured data has to answer is *how many digits*, and
the usual answer is "as many as the source prints", which is a guess.

The source answers it itself, because it publishes the same number twice. Each
of the 156 Schott optical glasses carries a three-term Sellmeier fit *and* a
printed $n_d$ and Abbe number derived from it. Recomputing $n_d$ from each
glass's own coefficients and comparing:

    worst |n_d(Sellmeier) - n_d(catalogue)| = 4.775e-6   (N-LAK21)
    worst |V_d(computed)  - V_d(catalogue)| = 0.008746   (SF6G05)

so the catalogue's two statements of the same number agree to about six
significant figures and no further, and a table that stored eight would be
inventing two. The same comparison on a different source gave a different
answer: Ghosh's dispersion equations for calcite and quartz against the
handbook values reach only $2.2\times10^{-4}$ on calcite's extraordinary
index, so that table gets four decimals, not six. Two tables in one batch, one
physical quantity, two different precisions, each measured rather than
assumed.

What the skill says now: "Check new values against something independent, not
the code that produced them", and, for precision, that the rigour level
decides -- `measured` being "an experimental value, not on the scale". It does
not say how to choose `digits` for a measured table.

What it should say: for a `measured` table, the number of digits is not a
choice and not the number the source prints. Find two published statements of
the same quantity -- a fitted model and a tabulated value, two determinations,
a value and a derived constant -- compute the disagreement, and keep the
digits that survive it. Say the measurement in `rigour details`, because it is
the only justification a measured table's precision can have. Where a source
publishes a model, this is also the cheapest possible check of the whole
table: the run above covered every entry, not a sample, and cost a minute.

Evidence: 2026-09-20 ideas run, `/tmp/optics/catalogue.py` and
`/tmp/optics/crystals.py` under `agents/sage.sh`, against the CC0 copy of the
SCHOTT Zemax catalogue 2017-01-20b in
`github.com/polyanskiy/refractiveindex.info-database`.

## For a measured constant, the convention can move the value further than its printed precision

What happened: the catalogue prints $n_d = 1.51680$ for N-BK7, five decimals.
Two conventions that a table would otherwise leave implicit each move it
further than that:

* the *wavelength*. The optics literature's lower-case `d` line is helium at
  587.5618 nm; the physics and chemistry literature's `D` line is the sodium
  doublet, about 589.29 nm. Evaluating the same fit at both gives 1.51680003
  and 1.51672767, a gap of $7.2\times10^{-5}$ -- the fifth decimal, which is
  the last one published. The published fused-silica value 1.45846 is the
  helium one; at the sodium line the same equation gives 1.458403.
* the *medium*. Catalogue indices are relative to air at 20 °C, not to vacuum.
  The absolute index is larger by about 1.00027, which takes 1.51680 to
  1.51721 -- the fourth decimal.

Either omission produces a table whose digits are all wrong in a way no
recomputation from inside the table can detect, because the arithmetic is
right.

What the skill says now: "which normalisation, which branch, which indexing"
and the AGM and `elliptic_k` examples, all of them about mathematical
conventions where the wrong choice gives a visibly different number.

What it should say: the same rule has a sharper form for measured quantities,
where the convention often moves the value by less than a whole digit but more
than the precision published. Before storing a measured constant, write down
the argument it is a function of (here the wavelength, elsewhere a
temperature, a pressure, a frequency) and the reference state it is measured
against (here air rather than vacuum), and put both in the `Definition` rather
than a comment -- they are part of what the number is, not a caveat about it.
Two names that differ only in case, `d` and `D`, are a warning sign rather
than a coincidence.

Evidence: 2026-09-20 ideas run, `/tmp/optics/check.py` and
`/tmp/optics/catalogue.py` under `agents/sage.sh`. Fused silica from
Malitson's coefficients: 1.45846369 at 587.5618 nm, 1.45840272 at 589.3 nm.

## Checking a table against published rounded integers needs round-half-up, not Python's `round`

What happened: Schott publishes a six-digit glass code, which is
$\operatorname{round}(1000(n_d-1))$ followed by $\operatorname{round}(10V_d)$
-- an independent published integer that ties two proposed tables together and
is the best check in the batch. Recomputing it with Python's `round`
reproduced 139 of the 154 published codes. Fifteen failures reads like bad
data, and the obvious next move is to look for what is wrong with the
catalogue.

Nothing is. All fifteen were off by exactly one in the last digit, and all
fifteen were exact halves: `48.45` to be rounded to 484 or 485, `1.5725` to
572 or 573. Python's `round` rounds half to the even neighbour, as IEEE 754
says and as most published tables do not. `Decimal(...).quantize(Decimal(1),
rounding=ROUND_HALF_UP)` reproduced 150 of the 154.

The remaining four are the more interesting half. FK3, N-LAF7, P-LAF37 and
P-LAK35 are exactly the glasses whose $n_d$ prints as `1.4645`, `1.7495`,
`1.7555`, `1.6935` -- a half at the last printed place -- and the catalogue
rounded them the other way. That is not an error either: the code was computed
from digits the catalogue does not print, so a printed value ending in 5 is
itself a rounding of something unpublished. A check against rounded published
integers therefore has a floor: it cannot pass on the values that sit on the
boundary, and expecting it to pass everywhere sends a builder looking for a
bug in the right place for the wrong reason.

What the skill says now: the division trap in generators (`sage -python` has
no preparser, so `factorial(30) / k` is float division), which is the same
kind of lesson about a Python built-in quietly doing something other than the
mathematics.

What it should say: when the independent check is a *rounded* published value
-- a glass code, a rounded table column, a quoted two-decimal constant --
round half away from zero rather than with `round`, which rounds half to even,
and expect the values sitting exactly on a half to fail anyway, because the
publisher rounded digits you do not have. Report such a check as "150 of 154
and here are the four", not as a pass or a fail.

Evidence: 2026-09-20 ideas run, over the 154 Schott optical glasses that
publish a `glass_code`: 139 reproduced with `round`, 150 with
`ROUND_HALF_UP`, the residual four being FK3, N-LAF7, P-LAF37, P-LAK35.

## Write a whole-document API edit with the `Numbers` shape the API served
What happened: repairing T398, I tried to avoid round-tripping the nested
`Numbers` mapping from `GET /api/table?id=T398` by flattening the one-parameter
entries to record dictionaries before sending the whole document to
`POST /api/table/T398`. The write was refused with HTTP 400:
`{"error": "A value in this document cannot be read as a number.", "detail":
"'list' object has no attribute 'items'"}`. Sending the same prose edit with
the `Numbers` mapping exactly as the read endpoint served it succeeded, and
`generator.verify(sample=None)` then reported `14/14 matched`.

What the skill says now: it says the read endpoint returns the whole document,
but it does not say whether a whole-document prose edit should preserve the
served `Numbers` shape or normalize it first.

What it should say: for a whole-document API edit, keep the `Numbers` section
in the shape served by `GET /api/table?id=...` unless the write endpoint
explicitly asks for another shape. Flattening to record-list form is for
entries-oriented tooling, not a safe generic preflight for `POST /api/table`.

Evidence: T398 repair on 2026-09-22. The flat-list whole-document POST was
refused before writing; the nested-shape POST produced revision
`e5fb888f3adc8b813d622d5d97e3db1a258c5307cf7842394aeb89e37b91e11a`, the API
readback kept 14 numbers, `/api/table/T398/audit` returned `clean: true`, and
the generator verification returned `14/14 matched, 0 differing, 0 missing,
0 extra`.

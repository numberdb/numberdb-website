## A family-wide new tag makes the first built table audit dirty until its siblings exist

What happened: issue #163 proposed seven characteristic-class tables and said
all seven should carry the new tag `characteristic classes`. T332, the first
table built from that family, followed the family convention. Its audit then
reported `Tags: "characteristic classes" reaches only this table; a tag that
leads nowhere else leads nowhere`. Removing the tag would make the audit
clean, but would also violate the family convention and hide the tag the batch
was specifically proposing.

What the skill says now: propose a new tag when three or more tables would use
it, counting the other tables in the same batch. It also says `audit_table`
refuses a tag that reaches only this table. It does not say what the first
builder in such a batch should do before the other proposed tables exist.

What it should say: when a family explicitly proposes a new tag for three or
more tables and this is the first one built, keep the family tag and report the
audit finding as expected, naming the sibling proposals that make the tag
legitimate. Do not replace it with a broad existing tag just to make the first
draft audit clean; do not call the table clean until either the sibling tables
exist or a reviewer chooses a different tag policy.

Evidence: T332, 2026-09-18. `GET /api/tag?url=characteristic+classes` before
the build answered that the tag did not exist. After filling T332, the audit
endpoint returned a single finding for `characteristic classes` reaching only
this table. The sibling proposals in numberdb-data#163 are the Euler
characteristics of smooth complete intersections, the Todd polynomials, the
Chern-character polynomials, the Hirzebruch $L$-polynomials, the $\hat A$-genus
polynomials and the Segre classes.

# Lessons proposed by the T372 critique, 2026-09-20

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## A `Programs` snippet is stored verbatim and nothing ever runs it, so a JSON round trip can leave it as one line

What happened: T372's `Programs[program-sage].code` holds backslash-`n` as two
characters where it should hold newlines. The page prints the whole five-line
Sage program on one line, `\n` and all, inside its `<pre><code>` block. Fed to
Sage's preparser exactly as stored it is a `SyntaxError: invalid syntax
(<page>, line 1)`; with the backslashes turned into newlines it prints
`x^7 - 27*x^5 + 185*x^3 - 279*x`, which is the table's own entry for $n=8$. So
the code was right and only its storage was wrong, and the wrongness was
invisible everywhere it was looked at: `json.dumps` of the API document shows
`\\n`, which reads as a newline unless you are checking, `verify()` never
touches `Programs`, and the audit reads that field only for a stale range
pattern. The published sibling T371, written the same week, holds real
newlines — so it is the metadata write that escaped twice, not a rule anybody
followed.

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value." Nothing about checking that
the stored incantation is still the text you wrote.

What it should say: `Programs` is the only field on a page that is meant to be
copied and run, and it is the only field nothing checks — not the type system,
not `verify()`, not MathJax. After writing a table's metadata through the API,
read the field back and count its lines:

    code = numberdb.table('T372')['Programs']['program-sage']['code']
    assert '\\n' not in code and code.count('\n') == 4

`repr()` is the check, not `print()`: a string of two characters and a real
newline print the same in a JSON dump and differently in a `repr`. Better
still, run the snippet once as stored. A table whose values are exact costs
seconds to do it in.

Evidence: 2026-09-20, T372. `GET /api/table?id=T372`, `repr` of the code field;
`agents/sage.sh /tmp/prog372.py` printing "as stored on the page: FAILED ->
SyntaxError" and "with real newlines: OK -> x^7 - 27*x^5 + 185*x^3 - 279*x";
`GET /api/table/T372/audit` reporting `"clean": true` throughout.
`agents/critiques/T372.md` finding 1.

## The skill says to link a family at first mention in every section; `audit_table` refuses that in the Definition

What happened: T372's definition opens "let $He_n$ be the Hermite polynomial in
probabilist's convention" and does not link T104, which the corpus holds and
which the table links twice elsewhere. By the skill's rule — "Link a table the
first time it is named... First mention in a section" — that is a missing link,
and it was on my list until I read the audit, which yields

    Definition links to another table; a cross-reference belongs in
    Similar tables or a comment

for *any* `HREF{` in a definition. So a contributor who follows the skill
earns a finding, and one who follows the audit reads the skill as broken. The
corpus follows the audit: T133, T371 and T372 all name their parent family in
the definition in plain words and link it in a comment.

What the skill says now: "Link the first mention of a thing to what explains
it... The rule is the same in both cases: first mention, once per section", with
`Definition` listed as a section in the table of what goes where.

What it should say: the same rule with the Definition carved out — a definition
says what the object is and links nothing; the first *linked* mention goes in
`Comments`, and the relation goes in `Similar tables`. `CITE{}` in a definition
is fine and is what the corpus does. One sentence, and it removes a conflict
between two documents that a contributor is told to follow at the same time.

Evidence: 2026-09-20, T372.
`numberdb_app/management/commands/audit_table.py`, the `'HREF{' in definition`
branch; the definitions of T133, T371 and T372, none of which links.

## The audit's unlinked-family check is switched off for the family a table is named after

What happened: T372's `complete-note` reads "every $n\leq 50$ is here, the
range of the table of Hermite polynomials in probabilist's convention" — it
names a table the corpus holds, in the one field that tells a reader to go and
look at it, and does not link it. The audit reads `complete-note` (that is what
the T110 note in its source is about) and still passed it, because the check
skips any corpus title that contains this table's bare title or is contained by
it:

    if own and (name.lower() in own.lower() or own.lower() in name.lower()):
        continue

"Hermite polynomials in probabilist's convention" is a substring of "Secondary
polynomials of the Hermite polynomials in probabilist's convention". The guard
exists so a table is not told to link itself, and it takes with it exactly the
family such a table talks about most: every "Secondary polynomials of X",
"Zeros of X", "Minimal polynomials of X" is blind to X.

What the skill says now: "Link a table the first time it is named", and
elsewhere "`audit_table` finds the easy cases". A contributor reasonably reads
a clean audit as "the links are done".

What it should say: a clean audit does not mean the links are done, and there
is one family it is guaranteed not to check — the one in your own title. A
table named "… of the X" should be read by hand for unlinked mentions of X.
(If the check is to be fixed rather than documented, the guard wants to be
equality of bare titles, not containment.)

Evidence: 2026-09-20, T372. `GET /api/table/T372/audit` -> `"clean": true`;
`numberdb_app/management/commands/audit_table.py`, `_prose_faults`, the
families loop; `agents/critiques/T372.md` finding 5 and its last section.

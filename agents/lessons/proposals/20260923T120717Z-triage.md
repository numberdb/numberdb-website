## A missing table is HTTP 200 with an `error` body, and the anonymous half of a draft probe gets rate-limited

What happened: triage needed to know whether a table id was one of zeta3's
hidden drafts or simply did not exist. The documented way to tell them apart is
to ask twice — once with the key, once without — because a draft answers the
key and nothing else. Both halves of that probe went wrong, for two independent
reasons, and the second one fabricated data rather than failing.

First, `/api/table?id=...` **never 404s**. A missing table is a perfectly
ordinary `200` whose body is an error object:

    $ curl -s "https://numberdb.org/api/table?id=T9999"
    {"error": "Table with id 'T9999' does not exist."}   # HTTP 200

So `r.raise_for_status()`, `if r.ok:`, `if r.status_code == 200:` and
`urlopen` not throwing all report success for a table that is not there. A
first pass that checked the status and then read `body.get('Title', '')` scored
sixteen nonexistent ids as real tables with blank titles. The existence test is
`'error' in body`, and nothing else is.

Second, the anonymous half of the probe is rate-limited and the keyed half is
not — or is limited far more generously. Sweeping seventy ids (two requests
each) was enough to start getting

    HTTP 429 Too Many Requests

on **every** anonymous request, while requests carrying the key continued to
return full table bodies throughout. Because the probe was written as
`try: ... except: return None` and read `None` as "not visible anonymously", it
reported **55 hidden drafts** in T380–T449 — including T444, which had been
confirmed public minutes earlier by hand. Every one of those was a 429 wearing
a draft's clothes. The failure is silent, plausible and in the direction that
invents work: it claims drafts exist where there are none.

What the skill says now: that a draft is invisible, in no listing and answers
no search, and that the probe distinguishing a hidden draft from a missing
table is the key and not the parameter. It does not say that the negative
answer arrives as `200` with an error body, and it does not warn that the
unauthenticated side of that comparison is the side that gets throttled.

What it should say: when asking the API whether a table exists,

- test `'error' in response_json`, never the HTTP status — `/api/table` returns
  `200` for a table that does not exist;
- if you are comparing a keyed read against an anonymous one to detect a
  draft, treat **three** outcomes, not two: table present, `error` body
  meaning absent, and *request failed* meaning unknown. Never let an exception
  or a 429 collapse into "absent", or you will invent drafts;
- keep such sweeps small and spaced. A couple of hundred anonymous requests in
  a few seconds is enough to earn a 429 that persists for minutes; the keyed
  requests keep working, which makes the damage one-sided and easy to miss.

Both points are the contributor's as much as ours: anyone checking whether
their own draft is live, or whether an id is free, on their own laptop, meets
exactly this.

Evidence: 2026-09-23, w3 triage of build `20260923T120643Z`.
`/api/table?id=T445` with the key → full body, `"Numbers": []`; without the key
→ `{"error": "Table with id 'T445' does not exist."}` at HTTP 200 — a real
draft, correctly detected while the probe was still cheap. `?id=T461` and
`?id=T9999` → the same error body at HTTP 200 with *and* without the key. After
a 70-id sweep, `T444` anonymously → `429` on three consecutive tries five
seconds apart, while `T444` with the key → `200`, 3997 bytes, in the same
script run.

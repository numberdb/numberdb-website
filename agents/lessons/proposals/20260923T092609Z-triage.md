## Whether a table is published is a read you can do without a key -- but the anonymous allowance is 60/hour per IP, and a 429 looks like an answer

**The read.** `GET /api/table?id=<tid>` returns the document if the table is
published, and

    {"error": "Table with id 'T443' does not exist."}

if it is not -- whether it is your own draft or somebody else's. With your key
as a bearer token the same request returns your drafts in full. So the pair of
reads is a published/unpublished test, and it mutates nothing:

    $ curl -s "https://numberdb.org/api/table?id=T443"
    {"error": "Table with id 'T443' does not exist."}
    $ curl -s -H "Authorization: Bearer $NUMBERDB_API_KEY" \
           "https://numberdb.org/api/table?id=T443"
    {"Title": "Values of the Hastings–McLeod solution $q(s)$ ...

There is no `api/drafts` and no status field on the document, so this is the
nearest thing to a draft listing there is: sweep the T-numbers around your own
work and the gaps -- present to your key, absent anonymously -- are the
unpublished tables. That is how this triage established that thirteen of
T415-T445 were unpublished when four others in the same range were not.

**Filled or not.** The document tells you that too, and it is worth checking
before treating a draft as work in progress. A table created and never filled
has no `Numbers` key at all; one whose fill was started and wrote nothing has
it empty. On 2026-09-23, T415 had no `Numbers` key, T416 and T445 had it empty,
and the other ten drafts had it populated. Note that `len(Numbers)` is **not**
the entry count -- `Numbers` is keyed by parameter, so its length is the
parameter count. Use it as present/absent/empty, not as a total.

**The trap, which is the part worth a test.** Anonymous use is limited to
**60 requests per hour**, and the counter is kept against the client IP
(`numberdb_app/throttle.py`, `requester_of` -> `_client_ip`); a key raises it to
1000 and scopes it to `key:<pk>`. Two things follow that a sweep will meet:

* The anonymous allowance is **shared by everything behind one address** --
  every process on your machine, and everyone behind one NAT or one campus
  proxy. You can exhaust it without having made 60 requests yourself.
* The 429 body is a JSON object with an `error` key, exactly like the "does not
  exist" reply:

      {"error": "Rate limit exceeded (60 requests per 60 minutes). An API key
       raises this limit; see /help#section-api.", "retry_after": ...}

  So a scan that classifies by `'error' in response` reads every throttled
  probe as *"this is a draft"*, and one that matches the substring `does not
  exist` reads it as *"this is published"*. Either way it returns a clean,
  plausible, wrong answer for every id after the limit, with nothing in the
  output to say where the truth stopped.

I made the second mistake in this triage: a thirty-one-id sweep silently
classified T427-T444 as published when every one of those responses was a 429.
The sweep looked like it had worked. It was caught only because two ids probed
before the limit contradicted it.

**The remedy is one line:** send the key, and check the status code rather than
the body. With a key the limit is 1000/hour and the sweep finishes; and

    if resp.status_code == 429: raise   # do not classify this
    published = resp.status_code == 200

is the whole of it. A bare `except` around the request, or a test on the body
text, is what turns the throttle into data.

**What the skill says now:** nothing. `SKILL.md` has no occurrence of
"anonymous", "rate limit", "60 requests" or "unauthenticated". Section 9
describes offering as an act; nothing anywhere describes reading a table back
without a key, or what happens to a script that reads many.

**What it should say**, alongside the existing offer material:

> A table that is not published answers `GET /api/table?id=<tid>` with
> `{"error": "Table with id '<tid>' does not exist."}` when you ask without a
> key, and returns the document when you ask with yours. That pair is how you
> check whether something of yours has been published, and -- swept over a
> range of T-numbers -- the nearest thing there is to a list of your drafts.
> `Numbers` missing or empty means the table was created and never filled.
>
> If you sweep, **use your key**. Anonymous use is capped at 60 requests an
> hour against your *IP address*, which you share with every other process on
> your machine; a key raises it to 1000 against the key. The refusal is HTTP
> 429 and its body is `{"error": "Rate limit exceeded ..."}` -- a JSON object
> with an `error` key, just like the "does not exist" reply -- so classify on
> the **status code**, never on the body, or a throttled sweep will report
> confident nonsense for every id after the sixtieth.

**Why it belongs in the skill rather than the environment notes.** None of it
is about this deployment. The two limits are the published API's, documented on
`/help#section-api` and `/api-reference` from the same settings the throttle
reads; the visibility rule is the site's. A contributor on a laptop hits the
first half the moment they wonder whether their table went through, and the
second half the moment they check more than a handful at once -- which is
exactly what somebody who built a family of six tables will do.

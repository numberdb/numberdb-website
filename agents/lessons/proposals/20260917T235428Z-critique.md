# Lessons proposed by the T316 critique, 2026-09-18

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## A numbering "as corrected by X" has to say what the correction did to the names

What happened: T316 indexes its 243 entries by the Rolfsen name $n_k$ of a
knot, "numbered as in Rolfsen's table after Perko's correction", and says in a
comment that SnapPy's built-in names "do not" use that numbering. It never
says how they differ. They differ in six of the 243 rows, and I checked each
against SnapPy from a laptop's point of view -- `Manifold('10_83')` is this
table's $10_{86}$ and vice versa, and `Manifold('10_163')` through
`Manifold('10_166')` are this table's $10_{162}$ through $10_{165}$, because
the correction deletes a duplicate and shifts everything after it down by one.
The page also contradicts itself without that sentence: the entry comment on
$10_{161}$ says Rolfsen listed the knot twice, "as $10_{161}$ and $10_{162}$",
and a row labelled $10_{162}$ sits four rows below holding a different number.
Two older tables of the same knots, T139 and T141, both spell the shift out;
T313 and T316 copied a shorter comment that leaves it out.

The general shape: whenever a parameter is a *name from a classical table that
has since been corrected* -- Rolfsen and Perko here, but equally a renumbered
LMFDB label, a renamed census manifold, an OEIS entry that absorbed another --
the reader arrives holding a value they got from a program or a paper that
uses one of the two numberings, and the table is the only thing that can tell
them which. "As corrected by X" names the correction; it does not tell anybody
which names moved.

What the skill says now: "Which normalisation, branch, and indexing" must be
decided before computing, and "'The nth zero' needs a statement of where
counting starts". That is about where counting starts, not about two numberings
of the same objects that disagree in six places. The nearest other rule,
"Do not discard what the source certified", is about a value rather than a
name.

What it should say: where the index is a name taken from a source that has been
corrected or renumbered, say what the correction did to the names, not only
that it happened -- which names were deleted, which shifted, and which two
were interchanged -- and name the widely used program or table that still uses
the old ones. One clause per discrepancy. A reader arriving by name rather
than by digits has nothing else to go on, and the entry comment that mentions
the correction will otherwise contradict a row a few lines below it.

Evidence: T316 comment (5) against T141 comment (5) and T139's, read on
2026-09-18; and SnapPy 3.x in the build image, where

    Manifold('10_83').cusp_areas(verified=True, bits_prec=300)[0] / 2

gives 8.8017833452..., which is T316's $10_{86}$, while `Manifold('10_86')`
gives 8.5277861646..., which is its $10_{83}$; and `Manifold('10_162')`
repeats `Manifold('10_161')`.

## Run the Programs block, especially when it does not share the generator's source

What happened: T316's `Programs` block builds the knot exterior from Sage's
`sage.knots.knot_table.small_knots_table`, while its `generate.py` carries its
own copy of KnotInfo's braid words and never touches Sage's table. Nothing in
the document says the two agree, and if they had disagreed about which knot
$n_k$ names -- the very thing the table's own comment warns about for SnapPy --
the block would have quietly printed a different row's number. Running it gave
the stored value for all seven knots I tried, including the four whose names
the Perko correction moved. It also turned up a free check of a stated
property: Sage's braid word for $5_2$ is the mirror of the generator's, and
the two give the same cusp volume, which is exactly what the table's comment
on mirror invariance claims.

What the skill says now: "`Programs` and `generate.py` answer different
questions", and a lesson of 2026-09-17 adds that a `Programs` block is REPL
input and should be checked by preparsing rather than run under `sage -python`.
Both are about the block being *valid*. Neither says to check that it returns
the table's number.

What it should say: run the `Programs` block and compare what it prints with
the row it claims to reproduce. Where it reaches a different source of the data
than the generator did -- another package's table of the same objects, another
library's normalisation -- that comparison is the only thing in the document
that says the two agree, and it is cheap: one row is enough to catch a
different convention, and a row near a known discrepancy is better than the
first row.

Evidence: T316's `Programs` block run verbatim on $4_1$, $5_2$, $8_{18}$,
$10_{161}$, $10_{162}$, $10_{163}$, $10_{165}$, 2026-09-18; each agreed with
the stored entry to the digits compared. `/tmp/t316_checks.py`.

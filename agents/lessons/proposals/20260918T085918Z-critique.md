# Lessons proposed by the T325 critique, 2026-09-18

Format and scope as `agents/lessons/PROPOSALS.md`. Nothing here is in force.

## An unclosed `$` does not break the page loudly; count the delimiters in every field

What happened: 324 of T325's 432 entry comments ended
`; $a_2\approx -4016.351171716245.` — five `$` in one field, the last one
never closed. Nothing complained. `audit_table` returned `clean: true`, the
value parsers were untouched, and every well-formed fragment on the page
typeset. I expected the stray `$` to swallow forward to the next row's
`$a_2$` and delete a value from the page, and it does not: MathJax 3.2.1,
with the delimiters the site sets (`inlineMath: [['$','$'],['\\(','\\)']]`),
found exactly the six closed fragments in three consecutive rows and left the
unmatched dollar as text. So the failure is neither a crash nor an error node.
It is that the reader sees a dollar sign, a backslash and the macro name
`approx` printed as English, on three quarters of the table, forever.

The generator's two branches show how it happens: the one for eigenforms with
a rational $a_2$ wrote `"$a_2=%s$, the root of %s."` and the one for the rest
wrote `"$a_2$ is root %s of %s in increasing order; $a_2\\approx %s."`. One
character apart, and only the second branch is wrong, so a run that spot-checks
the first weight sees nothing.

What the skill says now: nothing about delimiters. It says a `--` reaches the
page as two hyphens and that everything a reader sees is read as English, and
it names three faults that lived only in the rendering (a `<` eating a
section, `argument ()`, a JSON escape eating a backslash).

What it should say: an odd number of `$` in a field is always a bug, it is
invisible in the stored document, and no renderer or audit will tell you. It
costs one line to check every string in the document and every entry comment
before publishing:

    if field.count('$') % 2:
        raise ValueError(field)

Check it inside the generator, where the format string lives, rather than by
reading the page: the fault is per-format-string, so it appears on every entry
of one branch and on none of the other, and the entries you look at first are
usually the branch that works.

Evidence: T325 draft, 2026-09-18; 324 of 432 comments with an odd count,
`generators/normalised-hecke-eigenvalues-level-one-cusp-forms/generate.py:369`;
`/tmp/findmath.js` over the rendered rows, six math items found and the
trailing `$` left as text; `GET /api/table/T325/audit` clean.

## PARI's `mfcoefs` starts at $a_0$ and `lfunan` starts at $a_1$, so the same `[2]` is two different coefficients

What happened: T325's `Programs` block offered

    mf = mfinit([1, 12], 0);
    mfcoefs(mfeigenbasis(mf)[1], 2)[2] / (2^5 * sqrt(2))

as the incantation for its own $k=12$, $p=2$ value. Run, it answers
`0.0220970869120796...`, which is not in the table. `mfcoefs(F, n)` returns
$[a_0, a_1, \dots, a_n]$ — here `[0, 1, -24]` — and PARI vectors are
1-indexed, so `[2]` is $a_1 = 1$ and the table's number needs `[3]`. The
sibling table T324 indexes `lfunan(L, 2)[2]` in the same position and is
right, because `lfunan` returns $[a_1, \dots, a_n]$ with no $a_0$. Two PARI
coefficient vectors, one offset apart, same bracket.

What the skill says now: "`Programs` is the standard incantation in Sage, PARI
or mpmath for a reader who wants one more value." Nothing about running it.

What it should say: run the `Programs` block and compare its output with the
stored entry, and then put that entry's first digits in a trailing comment on
the line. The comment is not decoration: T325's Sage block carried one and was
correct, its PARI block carried none and was off by one, and the missing
comment is why nobody noticed. Where a family is indexed by more than the
argument, write the block at a parameter value where the indexing can be
wrong — not at the smallest case, where every ordering agrees.

Evidence: T325 draft, 2026-09-18. `pari('mfcoefs(mfeigenbasis(mfinit([1,12],0))[1], 2)')`
returns `[0, 1, -24]`; index `[2]` gives `0.022097086912079610137526386315776532478`
and index `[3]` gives `-0.53033008588991064330063327157863677946`, the stored
value. `/tmp/t325_pari.py`.

## Reading a table over HTTP is `GET /api/table?id=T325`; `/api/table/T325` is the write endpoint and answers 405

What happened: `GET https://numberdb.org/api/table/T325` returned
`405 Method Not Allowed` with a 29-byte error body. The path is real — it is
`api.write_table`, which takes POST — and the read is a query parameter on a
different path, `GET /api/table?id=T325`, which also accepts an address
(`?id=Hecke_polynomials_of_level_one_cusp_forms`) in the same parameter. The
audit sits under the write path (`GET /api/table/T325/audit`), so a reader who
has just run the audit by path naturally tries the document by path and gets a
405 rather than a redirect or a hint.

What the skill says now: it names `POST /api/tables` with `X-Draft`, and
otherwise routes every read through the Python client
(`numberdb.table('T99')`). The read endpoint is not written down.

What it should say: where the skill gives an API path for a run with no client
— it already gives one for the audit — give the read path beside it, and say
that the document is `GET /api/table?id=<tid or address>` while
`/api/table/<tid>` is for writing.

Evidence: 2026-09-18, `curl -w '%{http_code}' https://numberdb.org/api/table/T325`
→ `405`; `curl ... 'https://numberdb.org/api/table?id=T325'` → `200`,
121,688 bytes. `numberdb_app/urls.py:20-27`.

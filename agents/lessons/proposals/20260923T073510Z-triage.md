## Reading back your own draft needs a configured key, and without one it is
## indistinguishable from a table that was never created

What happened: `numberdb.table("T443")` on a client with no key raised

    NumberDBError: Table with id 'T443' does not exist.

T443 exists. It is a filled, unpublished draft belonging to the key I was
holding but had not configured. The *same* call after
`numberdb.configure(api_key=...)` returned the whole document -- Title,
Definition, 300-odd entries under `Numbers`.

The trap is the wording. With the key configured, asking for T446, a T-number
nothing has ever occupied, raises

    NumberDBError: Table with id 'T446' does not exist.

Same exception class, same sentence. So one message covers two situations a
contributor most needs to tell apart: *your draft is there and you are not
authenticated*, and *your draft was never created*. The second is what the
sentence says and what a reader will believe, and it is the more alarming of
the two -- it invites you to create the table a second time, which is exactly
what the refusal-on-duplicate-title machinery then has to catch.

This bites in the ordinary shape of the work rather than in an exotic one. The
prose is written and the draft created in one session; the generator is written
and run in another, often in a different process or container; and the first
thing the second session does is read the draft back to check the T-number. A
key that was configured in the first session is not configured in the second
unless something configures it, and the read then denies the draft exists.

What the skill says now: that a draft "is invisible, in no listing, answers no
search, and may have no numbers in it yet" (the `Propose it as a draft` step),
and that `numberdb.table(...)` "answers with the whole document, capitalised
keys and all". Both true. But "invisible" is written about other people, and
nothing says the invisibility extends to the author's own unauthenticated
client, or that the refusal is worded as non-existence rather than as a
permission failure. The word "key" appears in the skill only around publishing
and authorship.

What it should say: a draft is invisible to an unauthenticated client
*including your own*, so configure the key before reading one back --
`numberdb.configure(api_key=...)`, or whatever the client's key file
arrangement is -- and read it back in every session that is going to write to
it. And, explicitly: **`Table with id 'Tnnn' does not exist` does not mean the
table was not created.** On a T-number you believe you own it means, far more
often, that no key is configured. Check the key before concluding the draft is
gone and creating it again.

Evidence: 2026-09-23, against numberdb.org.

    # no key configured
    >>> numberdb.table("T443")
    NumberDBError: Table with id 'T443' does not exist.
    >>> numberdb.table("T439")          # published
    {'Title': 'Ramsey numbers $R(k_1,\\ldots,k_r)$ of complete graphs', ...}

    # numberdb.configure(api_key=<the key that owns T443>)
    >>> numberdb.table("T443")
    {'Title': 'Values of the Hastings–McLeod solution $q(s)$ of Painlevé II',
     'Definition': "Let $q$ be the Hastings–McLeod solution of $q''(s)=...",
     ...}
    >>> numberdb.table("T446")          # no such table, ever
    NumberDBError: Table with id 'T446' does not exist.

The same probe across T435-T446 separates the two states cleanly and only with
the key: unkeyed, T436, T437, T438, T440, T441, T443 and T445 all read as "does
not exist", and keyed, every one of them returns a document.

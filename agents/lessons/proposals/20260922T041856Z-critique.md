# Lessons proposed by the T397 critique, 2026-09-22

Format as `agents/lessons/PROPOSALS.md`. Nothing here is in force.

---

## `Data properties` has a fixed vocabulary, and anything else prints "(Unknown key)" on the page

What happened: T397 declared `digits: 100` under `Data properties`, beside
`type`, `rigour`, `complete` and `rigour details`. It is a natural thing to
write -- a generator carries `digits = 100` as a class attribute, so the number
is already in the author's hands -- and it costs nothing to check, so nothing
did. The rendered page shows it as a line of its own reading

    digits: 100 (Unknown key)

between "Entries are of type: real number" and "How well the digits are known:
proven". The renderer keeps a list of the property keys it has labels for
(`numberdb_app/views.py`, `property_names`: `type`, `complete`, `sources`,
`relative precision`, `absolute precision`, `reliability`, `rigour`,
`rigour details`, `repeats`) and prints anything else as `key: value (Unknown
key)`. `manage.py audit_table` validates the *values* of `type`, `rigour` and
`repeats` and never asks whether a key is one of them, so the draft audited
clean with the line on the page.

`digits` is redundant on top of being unlabelled: a real is stored as an
interval that its own digits describe, so a hundred digits of value already say
a hundred digits, which is the whole point of the convention. Nine published
tables sampled (T7, T25, T59, T92, T174, T222, T286, T396 and the six
`...of connected graphs` tables) carry none.

What the skill says now: "Data properties | `type`, `rigour`, how the digits
were obtained, and `repeats` if this table repeats another's" -- a list of what
belongs, with nothing about what happens to a key outside it.

What it should say: that the list is the whole vocabulary, not a
recommendation, and that a key outside it reaches the reader as `key: value
(Unknown key)` rather than being ignored. In particular there is no `digits`
property: how many digits a value carries is stated by the value.

Evidence: 2026-09-22, T397 critique. `GET /api/table?id=T397` shows
`Data properties: {type, digits, rigour, complete, complete-note, rigour
details}`; the page rebuilt by the sqlite draft-render recipe
(`/tmp/T397_page.html`, 472,928 bytes) contains
`digits: 100 (Unknown key)`; `GET /api/table/T397/audit` -> `{"findings": [],
"clean": true}`.

## A `rigour details` note with no blank line folds after its first *sentence*

What happened: T397's `rigour details` is two paragraphs by intention -- how the
values were computed, then what the build checked -- separated by a single
newline. The page shows

    The generator enumerates connected simple graphs with ... and stores the
    canonical graph6 string.   [more]

and hides everything else, including the precision, which is the one thing the
label "How they were obtained" promises.

Two rules combine. `numberdb_app/prose.py` starts a new paragraph only at a
**blank** line: a run of non-empty lines is joined with spaces, so `\n` between
two sentences is not a paragraph break, it is a space. That leaves one
paragraph, and a single paragraph over the fold threshold (400 characters of
rendered HTML) is cut by `_split_sentence` at the last sentence end that fits --
which, once `<code>` markup has eaten most of the budget, was the first
sentence. A note written as two paragraphs with one newline therefore folds far
earlier than one written as two paragraphs with a blank line, and the author
cannot see the difference in the YAML.

What the skill says now: "`rigour details` | how the digits were obtained, at
whatever length that needs: blank lines make paragraphs, `- ` makes a list,
backticks mark code, and a long note folds after its first paragraph". The
markup is right and "folds after its first paragraph" is only true when there
*is* a second paragraph.

What it should say: the same, plus the consequence -- a long note with no blank
line in it is one paragraph and folds after its first sentence, so what shows on
the page is one sentence. Put the blank line in deliberately, and put the
computation in the first paragraph, because that is the half a reader sees
without clicking.

Evidence: 2026-09-22, T397 critique. Stored note 1,114 characters, one
`\n` and no blank line; rendered page has
`<p class="prose-paragraph">The generator enumerates ... graph6
string.</p><details class="prose-more"><summary>more</summary>` with the
remaining 1,232 characters of markup inside the `<details>`.
`numberdb_app/prose.py`,
`_blocks` and `_split_sentence`, `FOLD_ABOVE = 400`.

## Pin the canonicalisation, not just the format, when graphs (or anything canonical) are the index

What happened: T397 indexes 996 graphs by graph6 string, and says in a comment
that the name is produced by `g.canonical_label(algorithm='sage').graph6_string()`.
That clause is the difference between a findable table and an unfindable one: a
graph6 string is a labelling of a *labelled* graph, so the string a reader gets
depends on which canonical form they asked for, and `nauty_geng` output or
`algorithm='bliss'` need not give the same string for the same graph. Checked
under `agents/sage.sh`: all 996 keys are their own
`canonical_label(algorithm='sage')` name, so the convention is both stated and
true.

What the skill says now: "Which normalisation, branch, and indexing" -- aimed at
the value (`elliptic_k` takes $m$ not $k$, where the counting of zeros starts).
Nothing about an index whose *key* is the output of an algorithm.

What it should say: when the parameter is a canonical name rather than a number
-- a graph6 string, a census label, a normal form -- the algorithm that produced
it is part of the convention, and naming the exact call is what lets a reader
get from the object in their hands to the row. State it in a comment, and check
the round trip on every key before publishing: a key that is not its own
canonical name is a row nobody can look up.

Evidence: 2026-09-22, T397 critique. `/tmp/t397_programs.py` under
`agents/sage.sh`: "keys that are not their own sage canonical graph6: 0", 996
rows; T397's comment `comment-graph6`.

## The import-order trap is not only the ring modules, and it does not say "QQ"

What happened: a script checking T397 opened with `from sage.graphs.graph import
Graph`, which is the first line of that table's own `Programs` block. It died
before reaching anything of its own with

    AttributeError: partially initialized module 'sage.rings.integer_ring' has
    no attribute 'ZZ' (most likely due to a circular import)

raised six frames down, through `sage.graphs.graph` ->
`polynomial_ring_constructor` -> `padic_base_leaves` -> `integer_ring`. Adding
`import numberdb.sage as numberdb` above it fixed it, as the skill says it
would -- but nothing in the traceback names a ring module at the top or says
"QQ", so the note in the skill does not match what a reader sees, and the error
reads like a broken Sage install.

What the skill says now: "Importing `numberdb.sage` first is what makes the
direct imports work: a ring module imported before anything has initialised
Sage raises 'cannot import name QQ', and that module does the initialising."

What it should say: the same, with the trigger widened and the symptom
loosened. Any Sage module can pull a ring in at import time -- `sage.graphs`
does, through the polynomial ring constructor -- so the rule is about the first
`sage.*` import of the file, not about ring modules. And the error varies with
which module got there first: "cannot import name QQ" and "partially
initialized module 'sage.rings.integer_ring' has no attribute 'ZZ' (most likely
due to a circular import)" are the same fault. A Sage *session* has `sage.all`
loaded already and is not affected, which is why a `Programs` block written in
named imports can be right on the page and still fail the moment somebody puts
it in a file and runs `sage -python` on it.

Evidence: 2026-09-22, T397 critique. `/tmp/t397_programs.py` under
`agents/sage.sh` with `NUMBERDB_SAGE_PYTHONPATH=`, first run the traceback
above, second run (one line added) 996 rows checked.

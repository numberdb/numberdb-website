# `GET /api/table?id=` answers 200 whatever happens, and a draft is byte-identical to a table that does not exist

What happened: triage wanted to know which drafts the account still holds --
there is a ceiling on unpublished tables, so it matters. `/drafts` is not
reachable with a key (that is the lesson in the `20260923T074024Z` proposal),
and that note ends by recommending the probe:

    GET /api/table?id=T443     # a draft: 404 to anyone but its owner
    GET /api/table?id=T444     # published: the full document, to anyone

The second line is right. **The first is wrong, and wrong in the direction
that costs you.** Measured against numberdb.org the same morning:

    id      anonymous            with the owner's key
    T443    200  (a draft)       200  full document
    T444    200  (published)     200  full document
    T999    200  (no such id)    200  (no such id)

Every one of the six is `200`. There is no 404 anywhere in this route. What
the anonymous caller gets for a draft is

    {"error": "Table with id 'T443' does not exist."}

and for an id that genuinely was never allocated:

    {"error": "Table with id 'T999' does not exist."}

The same sentence, to the character, with only the id substituted.

Two separate traps, and the second is the nastier one.

**The status code carries no information at all.** `r.status_code == 200`,
`raise_for_status()`, `r.json()` and a content-type check all pass on a table
that is not there. Anything shaped like

    if requests.get(f"{BASE}/api/table", params={"id": tid}).ok:
        print("published!")

prints `published!` for every id you will ever pass it. The only signal is
whether the parsed body has an `error` key -- `"error" in r.json()` is the
test, and `r.json().get("Title")` is the useful form of it. This is the same
shape as the `/drafts` trap in the earlier note: the site answers questions it
cannot answer with a plausible 200 rather than a status that would have
stopped a script.

**"Does not exist" means two different things and does not say which.** For
an anonymous caller a draft and a never-allocated id are indistinguishable.
That is correct behaviour -- it is the point of a private draft not to leak
which ids are taken -- but it means the error text cannot be read as fact.
A contributor whose `offer` did not land, probing without the key out of
habit, is told their table does not exist; concluding that it was lost and
building it again is how you end up with two.

**The way to actually tell** is to run the probe twice, with the key and
without, and compare:

    keyed 200 + Title,  anon 200 + error   ->  it is your draft
    keyed 200 + Title,  anon 200 + Title   ->  it is published
    keyed 200 + error,  anon 200 + error   ->  it is not there at all

The key is what separates the first case from the third; the anonymous
request is what separates the first from the second. Neither alone answers
the question, and the earlier note's single-request version cannot.

Two smaller things found alongside. The path form `/api/table/T443` is **405**
Method Not Allowed, not 404 and not the document -- the id belongs in the
query string for this route, and the subroutes (`entries`, `offer`, `lease`,
`audit`, `file`) are what live under the path form. And the key really does
work through `/api/...`: the same header that gets the sign-in form from
`/drafts` returns both draft documents in full here, so a 200-with-error from
a keyed request is a real answer about the table and not an authentication
problem in disguise.

What the skill says now: it tells you to check your work through the API and
to offer the draft for review. It does not say that this route never uses a
status code to report failure.

What it should say: `GET /api/table?id=<TID>` returns HTTP 200 for every id,
including ones that do not exist -- test `"error" in response.json()`, never
`response.ok` or the status code. An anonymous request cannot distinguish
your unpublished draft from an id that was never allocated; both answer
`{"error": "Table with id '<TID>' does not exist."}`. To find out whether a
table of yours has published, make the request **without** your key and look
for `Title` in the body.

Also worth correcting in the `20260923T074024Z` proposal, if it is promoted:
its closing probe says a draft 404s to anyone but its owner. It does not; it
200s, with an error body.

Evidence: 2026-09-23, triage of build run `20260923T075617Z`. Live against
numberdb.org with and without the zeta3 key: `api/table?id=` for `T437`,
`T440`, `T443`, `T444` and `T999`, status codes and bodies as above; `T437`
and `T443` are zeta3's two open drafts, `T440` and `T444` are published.
`api/table/T443` -> 405.

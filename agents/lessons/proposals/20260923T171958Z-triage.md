# Lessons proposed by triage run 20260923T171958Z

## `GET /api/claim` never reports an expired claim, so its `expired` field is always false

What happened: triage wanted to know whether the claims a failing campaign
had left behind were stale or still live, and read the `expired` field that
`GET /api/claim` puts on every row. All 50 rows said `false`. That reading is
worthless, and not because the claims were fresh -- the endpoint cannot
return anything else.

The response is built by one comprehension that both filters and reports:

    return JsonResponse({'claims': [
        {'family': row.family, 'proposal': row.proposal,
         'worker': row.worker, 'since': row.claimed_at.isoformat(),
         'expired': row.expired}
        for row in rows.order_by('family', 'proposal') if not row.expired]})

The trailing `if not row.expired` drops every expired row before the dict is
built, so the `expired` key it carries is constant `false` by construction.
A caller who filters on it (`[c for c in claims if not c['expired']]`) gets
the whole list back and believes no claim has ever lapsed.

What the skill says now: nothing. It documents `POST /api/claim` for taking a
proposal, and does not say how to read the claim list back or what the fields
on it mean.

What it should say: `GET /api/claim` returns only live claims. Expired claims
are omitted from the response, not flagged in it, so the `expired` field is
always `false` and must not be used as a filter. To tell how close a claim is
to lapsing, compare its `since` timestamp against the ninety-minute lease
(`ProposalClaim.MINUTES = 90`); a proposal that is absent from the list is
free to take, whether it was never claimed or was claimed and lapsed.

Evidence:

    $ curl -sH "Authorization: Bearer $KEY" https://numberdb.org/api/claim
    {"claims": [{"family": 196, "proposal": "Skewness and kurtosis of the
     Tracy-Widom distributions", "worker": "w1",
     "since": "2026-09-23T16:25:07.241547+00:00", "expired": false}, ...]}

    total claims: 50
    by family: [(196,3),(197,6),(198,6),(199,4),(200,5),(201,5),(202,6),
                (203,6),(204,5),(205,2),(206,2)]
    expired: 0        <- tautological, not an observation

against `numberdb_app/api.py:1387-1391` (the comprehension above) and
`numberdb_app/models.py:1560`, `MINUTES = 90`.

## A claim is taken before the work starts, so a run that does nothing still holds one

What happened: a build run failed on its very first turn, before any model
read the proposal. It still held a claim on that proposal -- taken at
17:19:28Z, one second before the run stamp 20260923T171929Z -- and kept it
for the full ninety minutes.

This matters to a contributor coordinating with anyone else against the same
corpus: the presence of a claim means "somebody has begun", not "somebody is
making progress", and a claim can outlive the process that took it by an hour
and a half. The lease is the only thing that ends it; there is no release
call on the failure path.

What the skill says now: nothing about what a claim does or does not imply,
or about what happens to one when the claiming process dies.

What it should say: claiming a proposal is not a promise that work is
happening. If you take a claim and then stop -- crash, refusal, out of turns
-- it stays taken until the ninety-minute lease lapses, and nothing releases
it early. Do not treat a live claim as evidence that a table is being built,
and if you abandon a proposal deliberately, say so wherever your campaign
tracks proposals rather than assuming the claim carries the message.

Evidence: run 20260923T171929Z used 0 turns and cost $0.0000
(`agents/runs/COSTS.tsv:641`); its transcript is a single 400 repeated twice
with no tool call between them; and `GET /api/claim` shows
`{"family": 198, "proposal": "Weil--Petersson volume polynomials
$V_{g,n}(L_1,\dots,L_n)$", "worker": "w1",
"since": "2026-09-23T17:19:28.362931+00:00"}`.

# Lessons proposed by run 20260923T123151Z (triage)

## Nothing in the API lists your drafts: `/drafts` is session-only and `/api/drafts` does not exist

What happened: a triage went to answer "what has this run left behind?", which
the job describes as reading "the draft list through the API". There is no
such list. Both of the obvious ways to ask fail, and neither failure says why:

    GET https://numberdb.org/api/drafts   Authorization: Bearer <key>
      -> 404, and an HTML "Not found - NumberDB" page

    GET https://numberdb.org/drafts       Authorization: Bearer <key>
      -> 302 Location: /accounts/login/?next=/drafts

The second is the trap. `/drafts` is a Django page behind
`@login_required`, so it wants a *session* cookie; an API key is not a
session and the redirect is byte-identical with and without one:

    /drafts authed -> HTTP 302 /accounts/login/?next=/drafts
    /drafts anon   -> HTTP 302 /accounts/login/?next=/drafts

A client that follows redirects -- `requests` does by default, and so does
`urllib.request.urlopen` -- does not show you the 302 at all. It hands back
**HTTP 200** and the HTML of the sign-in form, or, with
`Accept: application/json`, a 200 whose body is the serialised login form
(`fields: {login, password}`, `field_order: ["login", "password"]`). So the
symptom of "this page does not take an API key" is a success status
containing a password prompt, which reads like a bad key rather than like the
wrong kind of credential. It is neither: the key was fine and simply had
nothing to do with that URL.

What the skill says now: "`/drafts` lists what is being made right now and is
invisible from outside, so a table can be half-built and unfindable while you
start it again." A reader takes that as an endpoint they can call. It is a
page for a signed-in human.

There is also already a lesson here saying the owner of a draft reads it
through the API as any table -- `numberdb.table(tid)` with the key configured
-- and that `search_text` returns published tables only. Both are true. What
neither says is that this only works **if you already know the number**.

What it should say: there is no API call that enumerates your drafts. The
owner can read any draft by ID with the key configured, search will not find
it, and `/drafts` is a signed-in web page rather than an endpoint -- with a
key it redirects to the login form exactly as it does for a stranger, which a
redirect-following client reports as 200 with a password field. The practical
consequence for somebody building a table over more than one sitting: write
down the `T` number when the draft is created. It is the only handle that
survives, and the moment it is lost the draft is unreachable by any query the
API offers, whether or not you hold the key that owns it.

Evidence: 2026-09-23, run `20260923T123151Z`, against `https://numberdb.org`
with a valid zeta3 key from `NUMBERDB_KEY_FILE`. `/api/drafts` -> 404;
`/drafts` -> 302 to `/accounts/login/?next=/drafts` both with the
`Authorization: Bearer` header and without it, byte-identical; the same
request with redirects followed returned 200 and a login form.
`numberdb_app/urls.py:81` routes `drafts` to `views.drafts`, a page, and no
`api/drafts` route exists.

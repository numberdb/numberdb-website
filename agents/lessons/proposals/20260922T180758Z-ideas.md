## `search_text` matches inside words, so a family named for a Greek letter cannot be screened by that letter

What happened: screening a batch on the Dickman and Buchstab functions, the
screen's `already_here` returned twenty tables for the first name and
seventeen for the second. Not one was related. The distinguishing word the
screen had to work with was the spelt-out Greek letter -- `rho`, `omega` --
and the index matches it **inside ordinary English words**:

    search_text('rho')   -> 20 tables: 'Covering radii ...' (thresholds),
                            'Keiper-Li coefficients', 'Packing densities ...'
    search_text('nu')    -> 20 tables: 'Salem numbers less than 1.3', ...
    search_text('chi')   -> 20 tables: 'Residues of Dedekind zeta functions'
                            (Dirichlet), 'Values of the lower incomplete
                            gamma function', ...
    search_text('eta')   ->  6 tables: 'Critical exponents ...', 'Gaussian
                            period polynomials', ...

`nu` reaches every table with "numbers" in the title; `chi` reaches every
table that mentions a Dirichlet character or a $\chi$; `rho` reaches
"thresholds" and "Ehrhart". A twenty-hit answer that is entirely noise reads
exactly like a twenty-hit answer that contains one real collision, and the
next person has to read all twenty to tell.

What the skill says now: "The search stems (so 'regulator' matches 'regular')
and looks into definitions and comments, so read results rather than count
them."

What it should say: the same sentence, plus that the match is on substrings
and not only on stems, so a two- or three-letter query is useless -- and that
when the only distinguishing word in a family's name is a spelt-out Greek
letter, screen it by the **eponym** instead (`Dickman`, `Buchstab`,
`Jurkat`), which is what actually settles whether the family is already here.
The same warning belongs on `Keywords`: a table whose findable word is a
Greek letter's name will be reached by every unrelated search for that
letter, which is an argument for putting the eponym in the title.

Evidence: 2026-09-22 ideation run, against the live corpus of 416 tables.
`screen.already_here("Values of the Dickman-de Bruijn function rho")` returned
twenty titles, every one matched on `'rho'`; the six targeted searches
`Dickman`, `Buchstab`, `Jurkat`, `Richert`, `Golomb`, `sieve` each returned an
empty `.tables` list, which is the answer the screen was being asked for.

## A family with a limit has its range decided by where rows stop differing, not by cost or by size

What happened: three of the six families proposed converge -- the Buchstab
function to $e^{-\gamma}$, the two linear sieve functions to $1$. Choosing
"how much to include" by the skill's usual criteria (entry count, digits,
block size) would have put the Buchstab table on $1\le u\le 20$, because
nothing there costs anything: 1901 entries of 100 digits is a 250 KB block,
inside every limit, and every row is *distinct* at 100 digits so no audit
complains.

The measurement says otherwise:

    omega(4)  - e^-gamma = -1.24e-6
    omega(6)  - e^-gamma = +2.01e-7
    omega(8)  - e^-gamma = -3.25e-11
    omega(10) - e^-gamma = -4.42e-14
    omega(12) - e^-gamma = +2.11e-18

Past $u\approx7$ every row agrees with $e^{-\gamma}$ in the first ten
significant digits. A reader arrives holding the eight or twelve digits their
own computation produced, types them, and matches four hundred rows at once;
the table answers "your number is $e^{-\gamma}$", which they could have
guessed, and every one of those four hundred rows has diluted the corpus for
everybody else.

What the skill says now: "A table is a reference, not a dump... could somebody
plausibly encounter this value and want to identify it?" -- and the worked
examples are all about *arguments* nobody meets (`erf(17/18)`, the 500th
Chebyshev polynomial). It says nothing about arguments people do meet whose
*values* have stopped being distinguishable.

What it should say: when the family has a limit, measure where consecutive
entries stop differing in the first eight to twelve significant digits -- the
number of digits a reader actually holds -- and end the range there, saying so
in `complete-note`. The test is not "is this entry distinct at the stored
precision" but "could the digits a reader has pick this entry out". This is
the class-number argument of the skill in a different costume: a table whose
tail rows all carry the same leading digits makes search by number worse for
everybody, exactly as a table of small integers does.

Evidence: 2026-09-22 ideation run, `mpmath` at 60 digits, midpoint Taylor
recursion for $\omega$, 240 terms per unit interval. The figures above are
that run's output. The proposal stops the Buchstab table at $u=8.00$ (701
entries) for this reason and says so.

## For a delay-differential family, integrate the product the equation is written in, and let the known limit be the check

What happened: the linear sieve functions are defined by
$(sF(s))'=f(s-1)$ and $(sf(s))'=F(s-1)$, with $F(s)=2e^\gamma/s$ on $(0,3]$
and $f=0$ on $(0,2]$. The first implementation stepped from interval to
interval with

    g = integral of f on the previous interval;  g[0] += F_at[k]

which adds the value of $F$ at the left endpoint where the equation calls for
the value of $sF(s)$, that is $k\,F(k)$. Everything about the result looked
right: it was continuous, it was smooth, it was positive, it was decreasing,
and on the closed-form stretch $(0,3]$ it agreed with $2e^\gamma/s$ to 61
digits, because that stretch is not produced by the recursion. The three
checks a builder would naturally run all passed.

What caught it was the limit. $F(s)\to1$ and $f(s)\to1$ as $s\to\infty$, and
the wrong recursion gave

    s=10   F-1 = -0.93597      s=20   F-1 = -0.985654

so $F$ was heading for $0$. The limit is not decoration: $2e^\gamma$ is the
unique initial constant for which these solutions tend to $1$, so a test
against the limit tests the initial condition and every step of the recursion
at once, which no spot value on the closed-form stretch can do.

What the skill says now: "Check new values against something independent, not
the code that produced them", with identities between two tables as the worked
example.

What it should say: for a family defined by a recursion, a check on a
stretch the recursion never touches -- a closed form on the initial interval,
a special value -- certifies nothing about the part of the table that is
actually computed. Prefer a check that the whole recursion has to pass: an
exact **limit** that the initial condition determines, or an integral over
the whole range. $\int_0^\infty\rho=e^\gamma$ is the same kind of check for
the Dickman function, and it passed to 53 digits at the first attempt.

And the converse, which the same run also measured: an **asymptotic
approximation** is not that check. Feeding the saddle point $\xi(u)$ into
$\rho(u)\sim\exp(-u\xi+\operatorname{Ei}(\xi))/(\xi\sqrt{2\pi u})$ gives a
ratio to the true $\rho$ of $0.848$ at $u=5$ and $0.901$ at $u=30$ -- heading
for $1$ and still 10% away. It confirms the order of magnitude and not one
digit. The distinction worth writing down is between a limit the definition
forces (strong, whole-table) and an approximation with an unmeasured error
term (magnitude only): measure the rate before deciding which one you have.

Evidence: 2026-09-22 ideation run. First pass printed
`F(2) - e^gamma = -1.5558e-61`, `F(3) - 2e^gamma/3 = -1.5558e-61`,
`f(4) - 2e^gamma log3/4 = 0.0` -- three green checks -- and
`s=20 F-1 = -0.985654`. The fix is `g[0] += k * F_at[k]`; with it,
`F-1 = 1.99e-28` at $s=20$. The $\xi$ ratios above are from the same
corrected pass.

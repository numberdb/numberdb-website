## A ball never agrees with a published decimal parsed as exact

What happened: every computed quantile in this batch was compared against the
value the literature prints, like this:

    print(ball.overlaps(RBF('1.959963984540054235524594')))

and every line reported disagreement — including the lines whose digits were
right. `RBF(s)` on that string is the *exact* decimal
$1.959963984540054235524594$, and the true $z_{0.975}$ is
$1.9599639845400542355245944305\ldots$: the published number was truncated, so
it misses the true value by about $4\times10^{-25}$, while the ball's radius
was $2\times10^{-33}$. Two numbers that agree to every digit anybody printed
were reported as disagreeing, and the same comparison would have reported
agreement between two *wrong* numbers had the ball been wide.

What the skill says now: "Check new values against something independent",
and, for arb, "An enclosure that contains everything agrees with everything".
It does not say the opposite failure exists.

What it should say: a published decimal is a truncation, not a number. To
compare a ball against one, widen the published value by an ulp of its last
printed digit before asking `overlaps`:

    published = RBF(QQ(1959963984540054235524594) / 10**24)
    assert ball.overlaps(published.add_error(10**-24))

or compare leading digits as strings. A raw `overlaps` against a parsed decimal
answers a question nobody asked, in whichever direction the widths happen to
fall.

Evidence: 2026-09-22 ideas run, `/tmp/statquant.py`. Ten lines reading
`... [1.95996398454005423552459443052055 +/- 3.28e-33] published
1.959963984540054235524594 DISAGREES`, where the ball's digits reproduce the
published ones exactly.

## Anything defined by an equation can be `proven`: bisect over rationals with a ball CDF

What happened: this batch needed inverses — quantiles $Q(p)$ solving
$F(Q) = p$ — and the skill's rigour table has no entry for a value found by
root finding. It also records that the named-import route does not bring
`sage.numerical.optimize`, so there is no root finder to reach for anyway. The
recipe that works, and that produces a genuine enclosure rather than a
fixed-precision root with an interval painted on it:

    def quantile(cdf, p, lo, hi, digits):
        p, lo, hi = QQ(p), QQ(lo), QQ(hi)        # rational bracket
        for _ in range(int(digits * 3.33) + 10):
            m = (lo + hi) / 2                    # exact rational midpoint
            v = cdf(m)                           # a ball
            if v < RBF(p):     lo = m            # arb comparison: certainly <
            elif v > RBF(p):   hi = m
            else:              raise ...         # out of working precision
        return RBF(lo).union(RBF(hi))

Two things make it rigorous rather than merely careful. The midpoints stay
*rational*, so the CDF is evaluated at an argument the ball field contains
exactly rather than at a rounded float. And arb's `<` on balls is "certainly
less than", so a step is taken only when the sign is proven; when the ball
straddles $p$ the loop must stop and say the working precision ran out, which
is the one branch a hand-written bisection usually forgets. Twenty-six values
were produced this way and every closed-form identity held.

What the skill says now: nothing about inverses. The rigour table covers a
value computed forwards.

What it should say: a value defined implicitly by a monotone equation is
`proven` if it is bracketed by rationals whose sides are decided by proven ball
comparisons, and the stored value is the union of the final bracket. Name the
straddle branch: reaching it means raise the guard, not lower the digits.

Evidence: 2026-09-22 ideas run, `/tmp/statquant2.py`, `/tmp/ks.py`,
`/tmp/anchors.py`. Identities recovered at 100 digits include
$\chi^2_{1,0.95} = z_{0.975}^2$, $\chi^2_{2,p} = -2\log(1-p)$,
$t_{1,p} = \tan(\pi(p-\frac12))$, $F_{1,10,0.95} = t_{10,0.975}^2$ and
$F_{5,5,0.5} = 1$ exactly.

## The working guard is a property of the parameters, not of the function

What happened: the same $F$-distribution generator, at
`numberdb.bits(100, losing=64)`, produces 100 digits at $d_1 = d_2 = 10$ and
*fails* at $d_1 = 60$, $d_2 = 120$ — the bisection stalls with the CDF ball
still straddling $p$ at a bracket width of $1.5\times10^{-94}$. Measured, one
evaluation of that CDF retains:

    guard  64 bits (397 total)   97 digits    bisection fails
    guard 128 bits (461 total)  116 digits    completes
    guard 256 bits (589 total)  176 digits    completes
    at d1 = d2 = 120, guard 256                139 digits

So the loss grows with the parameters, through the cancellation in the
${}_2F_1$ that the incomplete beta is built from, and a guard measured on the
first few entries of a table is not a guard for the table.

What the skill says now: "State the guard as a constant backed by a
measurement (how many digits the worst entry actually retained)."

What it should say: the same, plus *the worst entry is usually the one with the
largest parameters, not the first one you tried* — measure at the far corner of
the enumeration, and if the loss grows with an index, say so in `rigour
details` so the next person extending the range knows to re-measure.

Evidence: 2026-09-22 ideas run, `/tmp/statquant3.py`, the four-row table above.

## Three more things the named-import route does not bring

What happened: writing generators without `sage.all`, as the skill instructs,
three imports that look ordinary failed. Each cost a round trip through the
container.

* `from sage.functions.other import factorial` raises
  `AttributeError: cannot access submodule 'function' of module
  'sage.symbolic' (most likely due to a circular import)`. Everything under
  `sage.functions` pulls in the symbolic ring, which is not initialised.
  Build factorials with a loop, or use the ring you are already in.
* `matrix(RBF, rows)` raises `AttributeError: module 'sage.rings.polynomial'
  has no attribute 'laurent_polynomial_ring'`. The matrix constructor walks a
  list of special cases while choosing an implementation, and one of them names
  a module nothing has imported. `import
  sage.rings.polynomial.laurent_polynomial_ring` before the first `matrix()`
  call fixes it and is otherwise unused (`# noqa: F401`).
* `ComplexBall.beta` does not exist, and neither does a regularised incomplete
  beta. What arb does expose through Sage is `CBF(a).gamma(z)`, the *upper
  incomplete* gamma, and `CBF(x).hypergeometric([...], [...])`. So
  $B(a,b) = \Gamma(a)\Gamma(b)/\Gamma(a+b)$ by hand, and
  $I_x(a,b) = \frac{x^a}{a\,B(a,b)}\,{}_2F_1(a, 1-b; a+1; x)$ — which is enough
  for the $t$, $F$ and beta distributions, in balls, at any precision.

What the skill says now: "What the named imports do not bring: root finding
(`sage.numerical.optimize`), `RealBall.str`, and `QQ('1.25')`." (Both of the
last two were met again in this run, so the list is right as far as it goes.)

What it should say: extend that list with `sage.functions.*` (circular import),
`matrix()` (needs `laurent_polynomial_ring` imported first) and the two arb
routes above, since between them they are most of what a special-function
generator reaches for.

Evidence: 2026-09-22 ideas run; `/tmp/ks.py` failed three times in a row, once
per item, before running.

## A bare `except` around `numberdb.table()` turns a rate limit into a missing table

What happened: the corpus was walked by asking for `T1`, `T2`, … in a loop,
with the usual

    try:
        d = numberdb.table('T%d' % i)
    except Exception:
        continue

The walk reported **374 tables, highest T375**. That is false: the corpus holds
T1–T411. A later pass with the exception printed showed why — the API had begun
answering `RateLimitError: too many requests; retry in 317s`, and every
throttled read had been counted as a table that does not exist. The wrong
answer is the plausible one: a corpus that stops at T375 looks exactly like a
corpus that stops at T375.

What the skill says now, about `search_text`: "A failed question and an empty
answer must not look the same." The same sentence is needed one function over.

What it should say: the same rule for `numberdb.table`, plus the fact behind
it — the API rate-limits a few hundred reads and the client raises
`RateLimitError`, so a walk of the T-numbers must catch *that* separately, wait
the number of seconds it names, and never treat it as absence. Walking the
corpus is the only way to see its shape (there is no call that lists it), so
this is on the path of anybody trying to find out what is already here.

Evidence: 2026-09-22 ideas run. `/tmp/count.py` printed `tables: 374 highest:
375`; `/tmp/count2.py`, five minutes later and printing exceptions, showed
`T370 … T419 ERR RateLimitError too many requests; retry in 317s` for every
number, including ones whose titles an earlier pass had already read.

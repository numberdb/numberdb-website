# `GET /drafts` with an API key returns 200 and a sign-in form, not your drafts

What happened: triage wanted the list of drafts the account holds -- the
obvious question, because there is a ceiling on how many unpublished tables
one account may have, and a run that dies halfway can leave one behind. The
obvious request is the one on the site's own menu:

    GET https://numberdb.org/drafts
    Authorization: Bearer <key>
    Accept: application/json

It answers **200**, `Content-Type: application/json`, sixteen kilobytes of
it. Nothing in the status line or the content type says anything is wrong.
What comes back is the sign-in page:

    {"form": {"fields": {"login": {...}, "password": {...}},
              "field_order": ["login", "password"], "errors": []},
     "html": "<!DOCTYPE html>...<title>Sign in - NumberDB</title>..."}

The request had been redirected to `/accounts/login/?next=/drafts`, and the
login page was content-negotiated into JSON because the request asked for
JSON. The same request with no `Authorization` header at all gives a
byte-identical answer, which is the tell: **the key is not rejected, it is
never consulted.** Bearer authentication applies to the `/api/...` routes;
`/drafts`, `/review`, `/overview` and the rest of the site's pages are
ordinary session-cookie pages, and an unauthenticated visit to one is a
redirect to a login form rather than a 401.

Why this is worth a warning rather than a shrug: every reflex a careful
contributor has for catching this fails.

- `r.status_code == 200` -- passes.
- `requests`' `raise_for_status()` -- passes, there is no error status.
- `r.json()` -- parses cleanly, because the body really is JSON.
- checking the content type -- passes, it really is `application/json`.
- `len(r.json())` -- a truthy `2`.

A script that does `drafts = requests.get(BASE + "/drafts",
headers={**auth, "Accept": "application/json"}).json()` and then iterates or counts it
gets a plausible-looking object and no exception. The only signals are
`r.url`, which has become `/accounts/login/?next=/drafts`, and the `form` key
where table data was expected. Both require having suspected the problem
first. A contributor who concludes from this that they hold no drafts, and
sets out to create another, will meet the ceiling from the wrong side and have
no idea why.

The second half of the lesson: **there is no API route for this.** The API
surface is `api/search`, `api/lookup`, `api/table`, `api/tables`,
`api/table/<T>` and its `entries`, `offer`, `lease`, `audit` and `file`
subroutes, plus `api/claim`, `api/costs` and `api/tag`. There is no
`api/drafts` and nothing else that lists the tables an account owns. So the
answer is not "use the right endpoint"; it is that this question cannot be
asked over the API as it stands, and a contributor has to track their own
draft ids, or probe the ones they suspect:

    GET /api/table?id=T443     # a draft: 404 to anyone but its owner
    GET /api/table?id=T444     # published: the full document, to anyone

`/drafts` in a signed-in **browser** is the real way to see the list, and that
is fine -- it is what the route is for. The lesson is only that it is not
reachable with a key, and that it fails by looking like it worked.

What the skill says now: it tells you the account may hold a limited number of
drafts, and it tells you to use the API with a bearer token. It does not say
that the token works on `/api/...` and nowhere else, so the natural reading is
that the key is the way to reach the site generally.

What it should say: the API key authenticates `/api/...` and nothing else.
Any other path on numberdb.org is a session-cookie page; fetching one with a
key gets the login form with a 200 status, and if you asked for JSON it will
be JSON. If a numberdb.org response contains a `form` key with `login` and
`password` fields, you are not authenticated no matter what the status code
says -- and check `r.url` before trusting any page-route response. There is
currently no API route that lists your drafts; keep the ids yourself.

Evidence: 2026-09-23, triage of build run `20260923T073936Z`. Probed live
against numberdb.org with the zeta3 key: `/drafts` -> 200,
`application/json`, final URL `/accounts/login/?next=/drafts`, 16003 bytes,
body the sign-in form; the same request without the header -> identical 200
and redirect; `/api/table?id=T444` with the same key -> 200 and the table
document, 3997 bytes, so the key itself is good. Route list:
`numberdb_app/urls.py:40-55` (the `api/` routes) and `:81-83` (`drafts` as a
page route).

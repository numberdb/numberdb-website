## A `Programs` snippet that imports from `sage.*` submodules runs in a Sage session and not in a Sage script

What happened: T256's `Programs` block is labelled `Sage` and opens

    from sage.combinat.root_system.root_system import RootSystem
    from sage.rings.rational_field import QQ

Exec'd in a namespace where `from sage.all import *` had already run -- which
is what a Sage session is -- it worked and returned 248, the number its own
comment claims. The same file handed to `sage -python` failed on its first
line:

    AttributeError: partially initialized module 'sage.rings.integer_ring'
    has no attribute 'ZZ' (most likely due to a circular import)

because importing a Sage submodule into a fresh interpreter starts the Sage
import graph part-way through. It is not one table's slip: T233 and T243 open
their Sage programs the same way (`from sage.arith.misc import binomial,
factorial`), and that pair fails under `sage -python` too, with a different
error again (`NotImplementedError: _call_with_args not overridden ... for
sage.rings.rational.int_to_Q`). `from sage.all import RootSystem, QQ` works in
both.

Why a contributor on their own laptop hits this: they write a generator as a
`.py` file and run it with `sage -python generate.py`, then copy the working
lines into `Programs` -- or the reverse, copy the `Programs` block out of a
table into a file to check it. The direction they go decides whether they see
the error, and nothing on the page warns them. The snippet is *not wrong* for
the environment its `language` field names; it is wrong for the other one, and
`from sage.all import ...` is right for both at no cost.

What the skill says now: it asks for a `Programs` snippet a reader can run and
says the client returns Sage objects under `import numberdb.sage as numberdb`.
It says nothing about which imports survive outside a Sage session.

What it should say: in a `Programs` snippet, import Sage names from
`sage.all` (`from sage.all import RootSystem, QQ`), not from the submodule
they happen to live in. Submodule imports work in a Sage session, where
`sage.all` is already loaded, and raise a circular-import error in a script run
with `sage -python`. Check the snippet in whichever of the two you did not
write it in.

Evidence: 2026-09-16, T256. `/tmp/t256_checks.py` (exec in a Sage namespace:
`dimension = 248`), `/tmp/t256_import_check.py` (A, the stored form, failed;
B, `from sage.all import RootSystem, QQ`, ok), `/tmp/t256_import_check2.py`
(T233/T243's form, failed), all through `agents/sage.sh`, which runs
`sage -python -u`.

## `/api/lookup` is charged per number, not per request, and 60 an hour is four batches

What happened: the critique wanted to know how many of T256's 491 distinct
values are already findable in the corpus, and sent them to `/api/lookup`
anonymously in batches of thirty. It stopped a few batches in with `HTTP 429
Too Many Requests`, and a second attempt was refused on its very first batch,
through a back-off that waited ten, twenty, thirty and forty seconds. The
window is an hour, so waiting was never going to help.
`numberdb_app/throttle.py` charges a batch
`ceil(1 + 0.5 * size)` units -- sixteen for a batch of thirty -- against
sixty units an hour for an anonymous caller and a thousand for one with a key.
Thirty per batch is therefore four batches anonymously and sixty-two with a
key. Repeating the run with `Authorization: Bearer <key>` finished all 491
values in seventeen requests without a single 429.

Two smaller things from the same run. The batch payload goes in the query
string, so a batch is limited by the 4,094-byte request line as much as by the
hundred-number cap -- thirty ten-digit integers is about 2 KB encoded, and a
hundred is a `400 Bad Request` before the rate limit ever sees it. And the
answer's `index` is a string, not an integer, so it has to be `int()`-ed before
it indexes the chunk that was sent.

Why a contributor on their own laptop hits this: "is this family already
here?" is the first question the skill asks, and checking a few hundred values
is the honest way to answer it. Doing that anonymously stops after about a
hundred and twenty numbers, with an error that says nothing about batching.

What the skill says now: it says to search the database before writing
anything, and it documents `/api/lookup` as the way to look up a number whose
type you know. It does not mention the rate limit, its unit, or that a key
changes it by a factor of sixteen.

What it should say: `/api/lookup` costs `1 + 0.5` per number against an hourly
window -- 60 units anonymous, 1000 with a key -- so send the key for anything
past a hundred numbers, and keep batches near thirty, which is what the
4,094-byte request line allows. A 429 here means "wait an hour", not "slow
down".

Evidence: 2026-09-16, T256 critique. `numberdb_app/throttle.py`
(`batch_cost`, `ANONYMOUS_LIMIT = 60`, `IDENTIFIED_LIMIT = 1000`,
`WINDOW_SECONDS = 3600`); anonymous batches of 30 gave 429 a few batches in and
stayed there; one batch of 100 gave `400 Bad Request` for the request line; the
same seventeen batches with a bearer token returned all 491 values, of which 16
matched something in the public corpus.

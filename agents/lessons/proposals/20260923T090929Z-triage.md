## A `429` is returned before the method is checked, so a rate-limited probe cannot tell you an endpoint exists

What happened: I wanted the list of drafts and tried `GET /api/tables`. It
answers

    405  {"error": "Use POST."}

anonymously and with a key alike, and sends no `Allow` header. That is correct
and unsurprising -- `/api/tables` is the *creation* endpoint, `POST` with
`X-Draft: yes`, which the skill already describes.

What is worth writing down is what the same request answered a few hours
earlier. An ideas run made the identical anonymous `GET
https://numberdb.org/api/tables?per_page=300` and got

    {"error": "Rate limit exceeded (60 requests per 60 minutes) ...",
     "retry_after": 1201}

and concluded, in a lesson still sitting unpromoted in this directory, that
"`/api/tables` exists but is rate limited to 60 requests an hour without a key
and answered `429` on the first try". That reads as *the listing is there, come
back in twenty minutes*. There is no listing, and twenty minutes later there
will still be none: the endpoint does not serve `GET` at any rate.

The mechanism is that the rate limiter answers before the view dispatches on
method. So a `429` tells you only that you are over quota. It does not confirm
the path serves your method, does not confirm the query parameters were
understood, and in particular does not distinguish "you are asking too often"
from "you are asking the wrong way, and too often". The anonymous budget is 60
an hour, which a contributor poking at the API to see what is there will spend
in a couple of minutes -- so this is the normal case for exploration, not an
edge one.

What the skill says now: nothing about the ordering. It says there is no call
that lists the corpus and that you walk the T-numbers, and it documents `POST
/api/tables` for creating a draft. A reader who tries `GET` on that path to see
whether the skill is out of date gets a `429` as readily as a `405`.

What it should say: one sentence beside the rate-limit paragraph -- a `429` is
raised ahead of routing and method checks, so re-read a `429` against a path you
have not successfully used before as "unknown", not as "correct but throttled";
confirm the path once from under the limit before trusting a conclusion drawn
from it. (And, as a worked instance: `GET /api/tables` is `405 {"error": "Use
POST."}`, not a throttled listing. The corpus listing is the HTML `/tables?page=`,
which the same ideas lesson gets right.)

Evidence: 2026-09-23.
`GET https://numberdb.org/api/tables` -> `405 {"error": "Use POST."}`, no
`Allow` header; identical with and without an `Authorization: Bearer` header;
`GET https://numberdb.org/api/tables?per_page=300` -> the same `405`.
Against `agents/lessons/proposals/20260923T033734Z-ideas.md` line 149, where
the same URL, the same morning, returned `429 ... "retry_after": 1201`.
The `405` for this path is already noted as a fact at

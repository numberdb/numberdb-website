## Do not let a later section make the last proposal answer an issue

What happened: family #185 marked the last proposal, "Eigenvalues of the
quartic double well $-y''+(x^2-a^2)^2y$", as `(answers #128)`. The batch
report itself says the backlog was empty and that none of the proposals
answers a request. The only `numberdb-data#128` in the proposal file is in
the later "Considered and not proposed" section, where it explains why the
harmonic oscillator should not be built. `queue.py` appears to have attached
that issue number to proposal 5 because the parser split only on proposal
headings, so the final proposal's section included the trailing non-proposal
material. GitHub issue #128 is "Monomials", not a double-well request.

What the skill says now: if a checklist line says `(answers #N)`, cite the
request in the table's Links and let `queue.py built` close it.

What it should say: before citing or closing an `(answers #N)` request, read
the request and confirm it is actually asking for this table. If the family
line contradicts the batch report or the issue is about another subject, stop
and report the queue attribution as wrong rather than putting a false
provenance link in the table. The queue parser should also stop each proposal
section before "Considered and not proposed" and other batch-level sections,
so issue numbers in those sections do not attach to the last proposal.

Evidence: `python3 agents/queue.py show 185` showed `(answers #128)` on the
double-well line. `/home/ubuntu/numberdb-campaign-w3/agents/table-ideas/BATCH-2026-09-22T0131.md`
says "The backlog is empty, so nothing here answers a request"; the same file
mentions `numberdb-data#128` only under "The harmonic oscillator" in
"Considered and not proposed". `gh issue view 128 -R numberdb/numberdb-data`
returned the title "Monomials".

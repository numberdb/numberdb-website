## Reset mpmath precision before a control computation
What happened: the Hurwitz-zeta-zero generator computed roots at 50 and 65
decimal working digits, but its local-minimum search temporarily lowered
`mp.mp.dps` to 45. A later control compared cached 65-digit zeros of
$2^s-1$ with freshly computed values of $2\pi i k/\log 2$ and failed, not
because the roots disagreed, but because the fresh control value had been
formed at the lower global precision.

What the skill says now: it says to run a control whose answer is already
known before believing a numerical method. It does not say that mpmath's
precision is global state, so one helper can lower the precision seen by a
later control.

What it should say: when a generator uses mpmath at several precisions, set
`mp.mp.dps` explicitly inside each helper that computes a value used for a
check, including the independent or closed-form control. Better, wrap the
calculation in a local working-precision context if the codebase can use one.
A control value computed after another helper has lowered the global
precision can make a correct root list look wrong.

Evidence: T386 build, 2026-09-21. The first fill attempt raised
`ArithmeticError: 2^s-1 control k=1 failed`; adding
`mp.mp.dps = int(WORKING_DIGITS[1])` at the start of `check_controls()` made
the same dry run and fill pass, and the stored table verified
`60/60 matched`.

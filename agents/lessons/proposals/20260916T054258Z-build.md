## Macdonald `qt_kostka` needs a symbolic-function import prelude under named imports

What happened: the T260 generator imported `numberdb.sage` first, then used
named Sage imports as the skill asks. Importing
`sage.combinat.sf.macdonald.qt_kostka` and asking for the first modified
Macdonald-Kostka coefficients crashed in Sage's lazy Symmetrica path unless
the symbolic modules had already been initialized. `import sage.symbolic.ring`
by itself was not enough, and importing `sage.symbolic.function` before
`sage.symbolic.ring` failed. The generator ran cleanly once it imported, in
this order, `sage.symbolic.ring`, `sage.symbolic.function`, and
`sage.functions.trig`, before importing `qt_kostka`.

What the skill says now: it says to import `numberdb.sage` before named Sage
imports, and to expect some machinery to be missing. The proposed lesson about
T138 says that `sage.symbolic.ring` can fix a circular import for knot-table
code, but it does not cover the Macdonald/Symmetrica path or the extra
symbolic-function and trigonometric-function imports.

What it should say: for generators that call Sage's Macdonald symmetric
function code through `qt_kostka`, try the prelude
`import sage.symbolic.ring`, then `import sage.symbolic.function`, then
`import sage.functions.trig` before importing the Macdonald module. Keep this
as a named-import workaround rather than falling back to `sage.all`, and still
check the values by an independent formula.

Evidence: T260, 2026-09-16. The first `agents/sage.sh` probes of
`qt_kostka` crashed or failed during Sage initialization. The generator
`generators/macdonald-kostka-polynomials/generate.py` with the three imports
above passed `agents/table-build/dry_run.py`, filled 787 entries, and
`verify()` reported `787/787 matched`; its independent HHL filling-formula
check compared 209 Schur coefficients through size 6.

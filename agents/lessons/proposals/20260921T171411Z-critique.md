# Lessons proposed by the T385 critique, 2026-09-21

Format as `agents/lessons/PROPOSALS.md` describes. Nothing here is in force.

## A clean audit does not mean the table's values are unique in the corpus

What happened: T385 holds ten zero ordinates for each of 70 cubic fields.
Nineteen of its 700 rows are numbers another table of this corpus already
holds -- nine copies of the first Riemann zero, and eighteen rows of T4
"Zeros of Dirichlet L-series" under the two cyclic cubic fields $D=49$ and
$D=81$, because $\zeta_K(s)$ factors through $\zeta(s)$ and, for a cyclic
field, through two cubic Dirichlet $L$-functions. `GET
/api/table/T385/audit` answered `{"findings": [], "clean": true}`, and it was
right to: `_values_also_in_another_table` samples eight rows from the first
320 at a stride of 40, and this table's blocks are ten rows deep, so every
sampled row is an $n=1$ row -- rows 1, 41, 81, ..., 281, the first zeros of
fields 1, 5, 9, 13, 17, 21, 25 and 29, while the cyclic fields are 4, 7, 19
and 49. It would have been silent anyway: the check skips a table that already
names the other one in prose, and T4 is in `Similar tables`.

What the skill says now: "If the table repeats another's values, say so", and
that two tables agreeing because of a theorem are both worth being told about.
It does not say that the audit cannot find the overlap for you.

What it should say: a contributor should not read a clean audit as "these
numbers are new here". Two known blind spots, both deliberate and both worth
knowing: the overlap check samples a fixed stride, so a table whose entries
come in equal-sized blocks may be sampled at one position in the block only;
and naming the other table in `Similar tables` switches the check off, because
a table that already says so is not being told again. Where a family's values
are shared for a structural reason -- an $L$-function that factors, a
normalisation that coincides -- look for the overlap yourself and write the
reason into `Comments`.

Evidence: 2026-09-21, T385. `GET /api/table/T385/audit` clean;
`numberdb_app/management/commands/audit_table.py:688` (`SAMPLE = 8`,
`rows[:SAMPLE * 40]`, `step = len(rows) // SAMPLE`, and the
`if other.tid in prose ... continue` suppression); the shared values checked
against `GET /api/table?id=Zeros_of_Dirichlet_L_functions` and
`?id=Zeros_of_the_Riemann_zeta_function`.

## A table of zeros of an L-function that factors should say what it factors into

What happened: in T385 the ordinate 14.1347251417346937904572519836 appears in
nine different rows and is the only value the table writes twice. It is the
first zero of $\zeta(s)$, and it is there because $\zeta_K(s)=\zeta(s)L(s,\rho)$
for every cubic field $K$. The page states the cyclic half of that
factorisation in one comment and never states the general one, so a reader
arriving with those digits meets a number in nine rows with no explanation, and
the `Similar tables` relation calls $\zeta(s)$ "the degree-one factor" of
something the page has not said factors.

What the skill says now: "A comment states a fact about the mathematics. ...
Where a value looks surprising the fact is the explanation." That is the rule
this is an instance of, and the instance is not obvious in advance: the
repeated value is not a coincidence to be explained away but the shape of the
family.

What it should say: for a table of zeros (or of any quantity of an object
whose $L$-function factors), the factorisation belongs in `Comments`, stated
for every case the table covers and not only for the prettiest one. It is what
tells a reader why one of their digits strings is in seventy rows, it is what
makes the sibling tables findable from the row rather than from the foot of
the page, and it is the fact that decides whether a repeated value is a
duplicate to be removed or two constructions meeting, which is what the
database is for.

Evidence: 2026-09-21, T385 (draft). The nine rows holding 14.13472514...;
T385's `comment-cyclic-fields` against T159's `comment-galois`, which writes
$\zeta_K(s)=\zeta(s)L(s,\chi)L(s,\bar\chi)$ for the cyclic case; the eighteen
rows of $D=49$ and $D=81$ checked value by value against T4.

## A convention borrowed from a sibling table has to be borrowed in the entries too

What happened: T385 says twice that it uses "the same $D,k$ convention" as
T159, and copies T159's sentence about the entry comments almost word for
word: "the reduced defining polynomial $f$, so that $K=\mathbb Q(a)$ with
$f(a)=0$". T159's entries print `$a^3-a^2+1=0$; $S_3$; ...`; T385's print
`$x^3-x^2+1=0$; signature $(1,1)$; S3; ...`. So the borrowed sentence names an
$f$ and an $a$ that its own rows do not contain, and the group that the
sibling sets as $S_3$ is bare text `S3` in 700 comments. T159 also states, and
T385 does not, that no two cubic fields below its bound share a discriminant,
which is why $k$ is 1 on every row -- leaving a column of 700 identical 1s
that the page never accounts for.

What the skill says now: "Define notation where you use it", and that a
parameter says what the family is indexed by. Nothing about following a
sibling.

What it should say: when a table declares that it follows another's
parameterisation, read that table's entry comments and its parameter comments,
not only its `Parameters` block. The convention is in three places -- how the
index is defined, how the entry comment is written, and what the index
degenerates to in the range you cover -- and copying the first while diverging
in the second leaves a sentence with no referent on every row.

Evidence: 2026-09-21, T385 (draft) against T159 (published), both read through
`GET /api/table?id=...`; T385's 70 $(D,k)$ pairs are exactly T159's fields with
$|D|\leq500$, all with $k=1$.

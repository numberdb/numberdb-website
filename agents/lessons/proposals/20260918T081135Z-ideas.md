Format as `PROPOSALS.md`: what happened, what the skill says now, what it

## The six-variable ceiling does not fall where the index says it does

What happened: this batch proposes five families of universal polynomials
indexed by a degree $n$ -- the Todd, $L$, $\hat A$, Chern-character and Segre
polynomials -- and the natural assumption is that the $n$-th one is a
polynomial in $n$ variables, so the six-variable refusal puts every table at
$n\le6$. It does not. $\mathrm{Td}_7$ has **no $c_7$ term** (nor do
$\mathrm{Td}_3$ and $\mathrm{Td}_5$ have their top terms), so it is a
ten-term polynomial in $c_1,\dots,c_6$ and fits, while $L_7$, $\hat A_7$,
$\mathrm{ch}_7$ and $s_7$ each genuinely reach a seventh variable and do not.
A builder who set the range from the index rather than from the value would
have dropped a row that the server accepts.

The general shape: for a family indexed by a degree, the number of *variables*
and the degree are two different numbers, and only the first is what the limit
is about.

What the skill says now: §5 and the refusals section describe what the server
accepts; the variable limit appears in `screen.representable` as "more than six
is refused, because the key that matches polynomials differing only in variable
names is found by trying permutations". Nothing says to measure it per entry.

What it should say: when a polynomial family is indexed by a degree, set the
range by counting the variables of each computed value -- `len(f.variables())`
-- and not by the index. The two come apart whenever the family has vanishing
top coefficients, and a range chosen from the index is short by however many
rows that is.

Evidence: 2026-09-18, computed under `agents/sage.sh`.

    Td_6 vars=6 terms=11 chars=179
    Td_7 vars=6 terms=10 chars=184
    Td_8 vars=8 terms=22 chars=426
    L_6  vars=6 terms=11 chars=270
    L_7  vars=7 terms=15 chars=356
    Ahat_7 vars=7 terms=15 chars=434

Note `Td_8` jumping straight to eight variables: the odd Todd polynomials lose
their top term, the even ones do not, so the sequence of variable counts is
$1,2,2,4,4,6,6,8$ and not $1,2,3,4,5,6,7,8$.

## A corpus table of "the same" constants can hold the other sign convention, and the link must say so

What happened: the Todd polynomials are the multiplicative sequence of
$Q(x)=x/(1-e^{-x})=\sum_iB_ix^i/i!$, whose $B_1$ is $+\tfrac12$. The obvious
`Similar tables` link is T13, *Bernoulli numbers* -- and T13 holds
$B_1=-\tfrac12$, its definition being $t/(e^t-1)$. Every other coefficient
agrees, so a check that compares a few values passes and the one that
disagrees is the one the reader would look up first. T13 already carries a
`comment-sign-convention` naming $B^+_n=(-1)^nB_n$, so the fact is recorded
where somebody reading T13 will see it and not where somebody linking *to* T13
will.

What the skill says now: "Link the first mention to what explains it";
"`equals` asserts the entries are the same number ... saying equal where only
related holds is worse than silence". It warns about claiming equality; it does
not warn that a *relation* stated in words can be wrong in one coefficient.

What it should say: before pointing at a corpus table for the constants your
family is built from, read that table's own convention comment and check the
first few values against yours. Generating-function conventions differ by a
sign in exactly one place often enough -- Bernoulli at $n=1$, Pontryagin
classes, the Segre alternation -- that a `Similar tables` line should name the
difference rather than implying agreement.

Evidence: 2026-09-18. `numberdb.table('T13')`: `Definition` gives
$t/(e^t-1)$, and `Numbers` begins `{'0': '1', '1': '-1/2', '2': '1/6',
'3': '0'}`. Wikipedia's *Todd class* article defines $Q$ "with $B_1=+1/2$"
explicitly, which is the clause that makes the two different.

## A one-variable Sage polynomial ring has no `is_symmetric`, so a symmetric-function loop dies on its first iteration

What happened: expressing a symmetric polynomial in the elementary basis with
`SymmetricFunctions(QQ).from_polynomial(f)` works for every degree but the
first. `PolynomialRing(QQ, ['x1'])` returns a *univariate* ring, whose elements
are `Polynomial_rational_flint` and have no `is_symmetric` method, so
`from_polynomial`'s `check` raises `AttributeError: 'Polynomial_rational_flint'
object has no attribute 'is_symmetric'` -- not a `TypeError`, not a message
about symmetry, and from inside Sage's own code. A loop over $n=1,2,3,\dots$
fails before printing anything, which reads like the whole approach being
wrong.

The fix is one character of arithmetic: build the ring in `max(n, 2)`
variables. Degree $n$ in $N\ge n$ variables is what `from_polynomial` needs to
be exact anyway, so more variables than the degree costs nothing.

What the skill says now: §6 warns that named ring imports do not bring root
finding, `RealBall.str` or `QQ('1.25')`, and that division without the
preparser is float division. Nothing about the univariate/multivariate split.

What it should say: `PolynomialRing(QQ, ['x1'])` is univariate and
`PolynomialRing(QQ, ['x1','x2'])` is not, and they do not share an interface.
Any code that varies the number of variables with a loop index should build
`max(n, 2)` of them.

Evidence: 2026-09-18, `/tmp/cc/cc.py` under `agents/sage.sh`; the traceback
ends in `sage/combinat/sf/monomial.py", line 184, in from_polynomial / if check
and not f.is_symmetric()`.

## An entry's anchor is the parameter values comma-joined, so a list-valued parameter's address reads like a longer tuple

What happened: two tables in this batch are indexed by an ambient dimension $n$
and a multidegree $(d_1,\dots,d_k)$, and the multidegree is naturally written
`2,4`. The anchor an entry gets is built by
`utils.number_param_groups_to_string`, which flattens the parameter groups and
joins them with commas, so $n=10$ with $d=(2,4)$ is `id="10,2,4"` -- a valid,
unique anchor, and one that reads exactly like the address of a three-parameter
table. Since the skill says the address after `#` is "its parameter values
comma-separated as a citation writes them", a reader constructing
`HREF{slug#10,2,4}` by that rule gets it right only by accident.

This is not new: T121, T122 and T261 all carry a partition parameter written
`2,1,1` and are addressed the same way. So it is the house form, and the thing
missing is that anybody says so.

What the skill says now: "The address after `#` is the entry's identity -- its
parameter values comma-separated as a citation writes them -- so a
three-parameter row is `HREF{slug#Z,1,density}`. These are the keys of
`Numbers`, not the labels the page prints."

What it should say: one more sentence. A parameter whose *value* is itself a
comma-separated list (a partition, a multidegree, a signature) is flattened
into the same join, so a two-parameter row can have a three-part address. The
address is the literal join and nothing parses it back; write it exactly as the
values concatenate, and do not count commas to work out how many parameters a
table has.

Evidence: 2026-09-18. `utils/utils.py:570` `number_param_groups_to_bytes`
(`params = flatten(params)`, then `separator.join(...)`), reached from
`numberdb_app/views.py:1263`, which sets `id="%s" % param` on the entry block.
`numberdb.table('T121')` shows the matching nested keys, `Numbers[n][lambda]`
with `lambda` of the form `'2,1,1'`.

## A generating function from a second source is the strongest cheap check for a derived family

What happened: the Euler characteristic of a smooth complete intersection can
be got two ways. One is the way the batch's other table computes it -- truncate
$(1+h)^{n+1}/\prod(1+d_ih)$, take the top coefficient, multiply by $\prod d_i$.
The other is Hirzebruch's generating function, quoted on Wikipedia's *Complete
intersection* article, which never mentions a Chern class:
$\sum_m\chi(X_m(d))z^m=\prod d_i\,(1-z)^{-2}\prod_i(1+(d_i-1)z)^{-1}$. The two
agreed on 2130 of 2130 cases in about ten seconds, and the check is worth more
than any number of spot values because it exercises a different formula rather
than a different argument to the same one.

What the skill says now: §10 says "Check new values against something
independent. Not the code that produced them", and gives identities among a
family as a free test suite. That is the same instinct; what it does not say is
where to look for the independent route.

What it should say: when a family has a closed form *and* a generating
function in the literature, the generating function is usually the independent
one -- it is derived by a different argument, it computes the whole family in
one series division, and comparing them is a loop rather than a table of quoted
values. Look for one before settling for two spot values from a paper.

Evidence: 2026-09-18, `/tmp/cc/chk.py` under `agents/sage.sh`:
`Euler characteristic: 2130 cases tested against Hirzebruch, 0 mismatches`. The
per-row companion, $c_1=(n+1-\sum d_i)h$, held on all 999 rows of the proposed
grid and costs one assertion in the generator.

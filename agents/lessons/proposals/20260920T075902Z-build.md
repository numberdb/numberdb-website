## Re-check each source record's domain after a family chooses common parameters
What happened: issue #170 said the six chosen Fraunhofer lines were covered by
all 156 Schott optical-glass fits. Re-checking the source files before filling
the table found that `SF6G05.yml` states `wavelength_range: 0.46 2.5`, while
the chosen $g$ line is $0.4358343\,\mu\mathrm{m}$. The table therefore has 935
entries, not the apparent 936-entry rectangle, and its completeness note names
the omitted `SF6G05, g` value instead of extrapolating outside the source fit.

What the skill says now: measure before choosing a range, aim for a complete
rectangle, and stop rather than guessing a convention. It does not say that a
family-level screening claim about coverage should be checked per source record
before a generator enumerates a rectangle.

What it should say: when a proposed table takes a common set of arguments from
a family source, verify each source record's stated domain covers every chosen
argument before treating the table as a rectangle. If one record does not
cover one argument, do not extrapolate; either shrink the common argument set
or omit the unsupported entry with a completeness note that names the exact
source record and argument.

Evidence: for T367, `SF6G05.yml` in refractiveindex.info-database commit
`c5c2f188e848453def5970e347399d653df2ffc2` states wavelength range
`0.46 2.5`; the build check reported
`omitted [('SF6G05', 'g', '0.46', '2.5')]`.

## Search by number resolves about sixteen significant digits, whatever is stored

What happened: T8 stores $e$ to 301 significant digits, and the growth
question asked was whether it should store more — the soft digit limit is 500,
the hard one 10,000, and `RealBallField(2**20)(1).exp()` returns 315,653
correct digits in 0.087 s, so cost decides nothing. The question turned out to
be settled by the index instead. Live, against the published table, each query
an interval one unit wide in its last place:

    [2.71828182845904585, 2.71828182845904595]  differs at the 17th digit -> T8
    [2.7182818284590465,  2.7182818284590475]   differs at the 16th       -> T8
    [2.718281828459055,   2.718281828459065]    differs at the 15th       -> nothing
    [2.7182818284591,     2.7182818284592]      differs at the 13th       -> nothing

A query agreeing with the stored value to sixteen digits and disagreeing at
the seventeenth is returned as a candidate, even though the two intervals are
disjoint by 10^284 times their own width. The reason is visible in the server
but the behaviour is measurable without it: `searchable_range`
(`numberdb_app/models.py:658`) builds the indexed range from
`float(lower), float(upper)` — "the float bounds as one range, for the GiST
index to answer overlap on" — and `search_real_numbers` filters and scores on
that range alone, with no exact-arithmetic pass afterwards.

Two consequences, and the second is the one that can produce a wrong table.

* Digits past a double do not make a value easier to find, and do not make it
  harder either (a reader holding 313 digits of $e$ still lands on T8). They
  are for reading and citing. So "a hundred digits" is not a compromise
  forced by storage; it is the whole of what the search can use plus eighty-four
  digits of courtesy, and going to 500 buys a reader nothing the corpus can
  deliver.
* A search hit means *agreement to about sixteen digits*, not identity. The
  skill already says results are candidates, but the number is not stated
  anywhere, and §1's "is this family already here?" screen is run by exactly
  this call. Two constants that agree to sixteen places — a conjectured
  identity, a value and its own truncation, two members of a family that
  converges — are one answer to it. Compare the stored text before concluding
  a number is already in the corpus.

What the skill says now: §3, "A hundred digits identifies a number; a reader
who wants more of a cheap value can compute them", and §5 on intervals. §1
tells you to search before writing anything. Nothing says how finely the
search can see.

What it should say: search by number is answered from a float projection of
the stored interval, so it distinguishes values to about sixteen significant
digits and no further. Store digits for a reader to read, not to be found by —
a hundred is plenty and five hundred buys nothing — and when a search says a
number is already here, check the digits past the sixteenth yourself.

Evidence: the four interval queries above, live against
`https://numberdb.org`, 2026-09-21, via `numberdb.search_real_interval`;
`numberdb_app/models.py:658` and `search_real_numbers` in
`numberdb_app/search.py`; timings from `RealBallField(bits)(1).exp()` under
`agents/sage.sh`; `agents/critiques/T8-growth.md` §3.

## A number search's results are the `SearchResults` list itself, and reading `.tables` finds nothing quietly

What happened: this review probed a dozen constants with
`numberdb.search_real_ball(centre, radius)` and read the answers out of
`result.tables` and a guessed `result.numbers`. Every probe printed nothing,
including `e` itself, which is in the database and which the search box
answers correctly. The conclusion drawn — that $e$, $1/e$ and $\gamma$ were
all absent from the corpus — was wrong, and it survived one full round of
reasoning before `repr()` showed what was really there:

    >>> r = numberdb.search_real_ball(2.718281828459045, 1e-15)
    >>> r.tables
    []
    >>> hasattr(r, 'numbers')
    False
    >>> list(r)
    [Result('2.71828182845904523536...', table="Euler's constant e")]

`SearchResults` is a list subclass. Number matches are its elements; `.tables`
and `.tags` hold the *word* matches, which for a numeric query are empty. So
the failure mode is exactly the one the skill already warns about for text
searches, mirrored: an empty list, no exception, and a result that reads like
an empty corpus. `getattr(r, 'numbers', [])` is worse again — the attribute
does not exist, so a defensive `getattr` invents silence.

What the skill says now: "`search_text` returns an object with a `.tables`
list, not a list — iterating it directly yields nothing and raises nothing,
which reads exactly like an empty corpus."

What it should say: the same sentence with the other half added. One object
carries both: iterate it for numbers, read `.tables` for titles and tags. A
number query fills the list and leaves `.tables` empty; a word query does the
reverse; and reading the wrong one of the two is silent either way. (A string
passed to `search` or `search_text` is read *both* ways, so
`numberdb.search('2.71828182845904523536')` is a number query and its answer
is in the list.)

Evidence: the session above, `clients/python/numberdb/__init__.py:701` and
`:791`, 2026-09-21.

## `RBF(e)` fails under the named imports the skill recommends, and the other constants do not

What happened: T8's `Programs` line is `numbers = [RBF(e)]`, and checking what
it returns meant running it. Under the import style §6 of the skill
prescribes — `import numberdb.sage` first, then name the rings — it does not
run at all:

    import numberdb.sage as numberdb
    from sage.rings.real_arb import RealBallField
    from sage.symbolic.constants import e
    RealBallField(53)(e)
    RuntimeError: cannot find SymbolicFunction in table

What makes it worth a line rather than a shrug is that **it is only `e`**. In
the same session, under the same imports:

    e             FAILED  -> RuntimeError cannot find SymbolicFunction in table
    pi            coerced -> [3.141592653589793239 +/- 5.96e-19]
    golden_ratio  coerced -> [1.618033988749894848 +/- 2.62e-19]
    catalan       coerced -> [0.915965594177219015 +/- 1.02e-19]
    euler_gamma   coerced -> [0.5772156649015328606 +/- 4.35e-20]

The other four are `Constant` objects with an `_arb_` of their own. Sage's
`e` is not a constant at all: it is the symbolic expression `exp(1)`, so
coercing it goes through `Expression._arb_`, which looks the operator up in
the symbolic function table — and `import numberdb.sage` initialises the rings
without populating that table. So the one import failure a contributor meets
is the one they will not suspect, because the four constants they tried first
all worked. It works after `from sage.all import RBF, e`, which is the import
the skill tells you not to write because a modular passagemath has no
`sage.all`.

The way out is better than either, and is what T8 should have said in the
first place: build the constant from the field.

    RealBallField(1024)(1).exp()        # e, as a ball of radius 2.3e-308

That takes a precision, which `RBF(e)` does not — the stored table holds 301
digits and `RBF(e)` returns sixteen — so the same change fixes a published
table's `Programs` line and sidesteps the import problem at once. The field
carries the rest too, verified in the same run: `field.pi()`,
`field(2).log()`, `field(5).sqrt()`, `field.euler_constant()`,
`field.catalan_constant()`.

What the skill says now: §6, "Name the rings you use, rather than importing
`sage.all`", with a list of what the named imports do not bring: root finding,
`RealBall.str`, and `QQ('1.25')`.

What it should say: add a fourth item — `RBF(e)` raises
`cannot find SymbolicFunction in table`, because Sage's `e` is the expression
`exp(1)` rather than a constant, while `RBF(pi)` and the other symbolic
constants are fine. Build a constant from the ball field rather than coercing
a symbolic one: `RealBallField(prec)(1).exp()`, `RealBallField(prec).pi()`.
That is the right habit regardless, since it is the form that takes a working
precision.

Evidence: the traceback above, under `agents/sage.sh` on the deployed builder
image, 2026-09-21; `agents/critiques/T8-growth.md` §4.

## The audit over the API never fetches a link, and a live URL can still be the wrong page

What happened: T8's only external link is captioned `Wikipedia: e` and points
at `https://en.wikipedia.org/wiki/E`, which is the article about **the letter
E** — title `E - Wikipedia`, categories "ISO basic Latin letters" and "Vowel
letters". The mathematical constant is at
`https://en.wikipedia.org/wiki/E_(mathematical_constant)`. The table is a
published seed table from 2021 and `GET /api/table/T8/audit` answers
`{"findings": [], "clean": true}`.

Two separate things, and a contributor who audits over the API meets both.

The link would not have been caught even by the fetching check, because it
answers 200: it is a good link to the wrong page, which is a question about
meaning and not about shape. So the first mention of a family, and every
external link, is something a person has to *open* once.

And the fetching check does not run over the API at all. `--links` is a flag
on `manage.py audit_table`, which needs the database; the API route calls
`findings_for(table)` and the signature is `findings_for(table, fetch=False)`
(`numberdb_app/management/commands/audit_table.py:109,149`). There is no
parameter on `GET /api/table/<tid>/audit` that turns it on. A contributor
without a database — which the skill's reader is, by construction — gets a
`clean: true` that has said nothing whatever about their links.

What the skill says now: §10 lists the checks to run, and §4 says to link
outward only to sources that will still exist. `audit_table` is named as the
thing that confirms a slug afterwards rather than instead.

What it should say: the audit does not check links unless it is run on a
server with `--links`, and over the API it never does — so open each external
link once yourself and read the title of the page that comes back. A URL that
answers is not a URL that is right, and a table with one link has no second
opinion.

Evidence: `curl -L https://en.wikipedia.org/wiki/E` and
`.../E_(mathematical_constant)`, 2026-09-21, titles quoted above;
`numberdb_app/api.py:1440,1452`;
`numberdb_app/management/commands/audit_table.py:109,149`;
`agents/critiques/T8-growth.md` §5 and §8.

## The API cannot list your drafts; record the tid when you create one, because nothing will give it back

What happened: asked what a failed run had left behind, I went to check which
drafts the key's account was holding, and found there is no way to ask. Every
route:

    GET  /api/tables            -> 405 Method Not Allowed   (create_table is POST-only)
    GET  /api/table             -> {"error": "No id or url given."}
    GET  /drafts                -> 302 to the login page     (session auth, not the key)
    numberdb.drafts()           -> AttributeError
    numberdb.Client(...).drafts -> AttributeError

`numberdb.Client` has exactly these public attributes, and no listing among
them:

    ['api_key', 'as_sage', 'base_url', 'close', 'for_sage', 'request',
     'submit', 'timeout']

and the module's own surface offers `table`, `search*`, `tag`, `configure` --
all of which take a number, an expression or a query, none of which enumerates.

So the existing lesson below is right but incomplete. The owner *can* read a
draft through the API -- but only one they can already name. `api/table` matches
on `id` or `url` and returns `{"error": "No id or url given."}` when given
neither; there is no `mine=1`, no `draft=1`, no listing endpoint at all. The
only enumeration of drafts anywhere is the signed-in `/drafts` HTML page, which
answers a session cookie and not an API key -- `views.drafts` redirects to
`account_login` when `request.user` is not authenticated, so a key in an
`Authorization` header does not reach it.

This matters most to exactly the reader the skill is written for: a program, or
a person driving one, that creates a draft in one process and fills it in
another. The tid in the creation response is the *only* copy of that name they
will ever be handed. Lose it and the draft is unreachable by the API -- still
counting against the few-in-flight allowance, still invisible to search, and
recoverable only by signing in to the website in a browser.

What the skill says now: "`/drafts` lists what is being made right now and is
invisible from outside, so a table can be half-built and unfindable while you
start it again" (SKILL.md:53). A reader takes from that sentence that `/drafts`
is a thing they can consult. Through the API it is not. `PROPOSALS.md` already
proposes adding that the owner reads a draft with `numberdb.table(tid)` -- which
presupposes the tid, and is silent on where it comes from.

What it should say: keep the `numberdb.table(tid)` addition, and add that the
tid must be kept from the creation response, because no API call will enumerate
your drafts. `/drafts` needs a browser session. Suggested wording:

> Save the `tid` the creation call returns. The owner can read a draft back
> with `numberdb.table(tid)`, but nothing in the API will *list* the drafts you
> hold -- `GET /api/tables` is POST-only, `api/table` needs an `id` or a `url`,
> and the `/drafts` page answers a signed-in browser rather than a key. A tid
> you did not record is a draft you can only reach by logging in to the site.

Evidence: 2026-09-23, against numberdb.org with a valid key.
`GET /api/tables?draft=1&mine=1` raised `HTTPError: HTTP Error 405: Method Not
Allowed`. `numberdb.drafts()` raised `AttributeError: module 'numberdb' has no
attribute 'drafts'`; the module surface printed in that traceback contains
`table`, `search*`, `tag`, `configure` and no listing. `dir(Client(...))` gave
the eight attributes above. In the source: `urls.py:44`
`path('api/tables', api.create_table)` with `api.py:962`
`if request.method != 'POST': return JsonResponse(..., status=405)`;
`api.py:377-405` returning `{'error':'No id or url given.'}` when both `id` and
`url` are absent; `views.py:375-379` redirecting `/drafts` to
`reverse('account_login')` for an unauthenticated request. No route in
`urls.py` lists tables by owner or by draft state.

# Proposed from the T364 critique, 2026-09-20

## The audit does not fetch your external links, and the dead one is usually the one you copied from a sibling table

What happened: T364's Definition opens "Let $K$ be a quartic field
CITE{Wiki-quartic} of discriminant $D$", and `Wiki-quartic` is
`https://en.wikipedia.org/wiki/Quartic_field`. There is no such article.
The URL answers 404 with "Wikipedia does not have an article with this exact
name", and `en.wikipedia.org/w/api.php?action=query&titles=Quartic%20field&redirects=1`
answers `"missing": ""`, so it is not a redirect either. It is the first link
in the first sentence of the table, and it is the citation that exists for the
reader who does not already know the term.

`GET /api/table/T364/audit` says `{"findings": [], "clean": true}`. It is not
wrong: `findings_for(table, fetch=False)` is the default, the URL check is
gated on `fetch`, and only `manage.py audit_table T364 --links` passes it.
An author who audits through the API — which is what an author without a
database has — never fetches a link at all, and a clean audit reads like "the
links are fine".

The way the link got in is worth more than the link. T364 is the degree-four
member of a family: T131 real quadratic, T158 cubic, T364 quartic. T158
carries `Wiki-cubic` → `https://en.wikipedia.org/wiki/Cubic_field`, which is a
real article. The new table copied the sibling's link keys and swapped the
degree word. `Cubic field` is a Wikipedia article; `Quartic field` is not, and
neither is `Quartic number field`. Nothing about the surrounding table changed
to signal it, because everything else in the mirror was right: the parameters,
the ordering convention, the number-header, four of the five other links.

The same shape is available to anybody: a link key adapted from a nearby table
by substituting one word, an OEIS A-number incremented by one, an LMFDB
knowl slug with `cubic` changed to `quartic`. Each of these looks correct in
the YAML and is only ever wrong at the far end.

What the skill says now: section 4 says `Links` holds "sources outside:
Wikipedia, LMFDB, OEIS, MathWorld", and section 1 says "Never guess a name the
database resolves -- an address or a tag", with `HREF{...}` and `Tags` as the
examples. The rule against guessing a name is there, and it stops at the
corpus's own addresses; an outward URL is exactly as guessable and is not
covered. Nothing says the audit will not check one.

What it should say: fetch every URL in `Links` before publishing, because
nothing else will — the audit's link check is behind `--links` and the API
audit never passes it. `curl -s -o /dev/null -w '%{http_code}\n' <url>` for
each is the whole of it. Say also where the dead one comes from: a link key
adapted from a sibling table by changing one word, where the sibling's article
exists and yours does not. When a table is the degree-$n$ member of a family
that is already in the corpus, the links are the part of the mirror that has
to be checked rather than copied.

Evidence: T364, 2026-09-20.
`curl -s -o /dev/null -w '%{http_code}' https://en.wikipedia.org/wiki/Quartic_field`
→ `404`, and the same for `/wiki/Quartic_number_field`; `/wiki/Cubic_field`
(T158's, the one it was copied from) and `/wiki/Algebraic_number_field` →
`200`. `GET /api/table/T364/audit` → `{"tid": "T364", "title": "Regulators of
quartic fields", "findings": [], "clean": true}`.
`numberdb_app/management/commands/audit_table.py:109` (`fetch=False`), `:150`
(`--links`), `:464` (the check the flag gates).

## A tag list is inherited from the family, not chosen fresh

What happened: T364 carries `Tags: ['number theory']`. Its two siblings, T131
"Regulators of real quadratic fields" and T158 "Regulators of cubic fields",
both carry `['number theory', 'transcendental']`. `/tags/transcendental` holds
five tables, two of which are those siblings, so the degree-2, degree-3,
degree-4 run of regulator tables is complete on `number theory` and breaks at
degree four on `transcendental` — and a reader browsing sideways from the
cubic regulators, which is what a tag is for, does not reach the quartic ones.

Nothing catches this. The audit checks that each tag reaches other tables,
which `number theory` does abundantly; it has no notion of a tag a table ought
to have. And the author's own check is the wrong way round: one asks "is this
tag true of my table?", which `number theory` is, rather than "what do the
tables I am about to list under `Similar tables` carry?".

What the skill says now: "Every table has at least Title, Definition, Tags
(two is typical), Links and Data properties. Prefer an existing tag; a tag
list is a way through the corpus and a tag with one table on it is not." It
says how many and where they come from, and nothing about which.

What it should say: when a table joins a family the corpus already holds, read
the tags off the tables it names in `Similar tables` and carry the ones that
are true of it, rather than choosing from the tag list cold. A new member of a
family with fewer tags than the members either has a reason or has an
omission, and "two is typical" will not find it, because one broad tag reaches
the count. The check is one call per sibling:
`numberdb.table('T158')['Tags']`.

Evidence: T364, 2026-09-20. `['number theory']` against T131's and T158's
`['number theory', 'transcendental']`; `https://numberdb.org/tags/transcendental`
lists T158, T131, T154, T7, T8.

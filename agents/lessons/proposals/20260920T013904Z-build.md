## Run the writer's precision check before the first fill

What happened: the Gauss hypergeometric generator for T348 passed
`agents/table-build/dry_run.py`: exactness was clean, `exact_in_disguise`
reported none, and the measured block was under the target. The first fill
still stopped before submitting anything:
`T348 entry 3/2,3/2,1/2,-1/2: 100 digits were asked for and this value
carries 1`. The ball was centred near zero,
`1.686...e-120 +/- 4.22e-120`, so the write path correctly refused it as a
one-digit value. A scratch scanner using `numberdb._write.to_text()` and
`numberdb._compare.digits_of()` found a second row of the same kind. Both rows
were exact zeros by Pfaff's transformation followed by a degree-one terminating
polynomial, so the generator omitted them as rational rows and the final fill
succeeded with 761 entries.

What the skill says now: run `dry_run.py`; it computes every entry, checks
exactness, measures the size, and exits non-zero while anything is wrong.
It also says exact-looking decimals are evidence, not proof, and must be
settled from the definition.

What it should say: before the first fill, run the same precision check the
writer will run, or make `dry_run.py` do it: format every generated value with
`to_text(value, digits, generator.format)` and refuse rows where
`counts_digits(text)` is true but `digits_of(text) < digits`. A certified ball
near zero can pass exactness and avoid the trailing-zero heuristic while still
carrying far fewer significant digits than the table asks for. When that
happens, do not merely increase precision or lower the row's digits; first
decide from an identity whether the value is exact and should be written or
omitted as exact, or whether it is genuinely a small inexact value needing a
wider computation.

Evidence: `agents/sage.sh /tmp/run_dry_hyper.py ... generate.py` reported
`763 entries computed` and `exact in disguise: none`; the first
`NUMBERDB_PUBLISH=1 agents/sage.sh generators/values-gauss-hypergeometric-function/generate.py`
raised the one-digit `DisagreementError`; `/tmp/find_short_hyper.py` found
the two short rows; after the Pfaff-zero omission rule, the same scanner
reported `short rows: 0`, and the draft fill of T348 wrote 761 entries.

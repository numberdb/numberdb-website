# Lessons proposed by the T381 critique run, 2026-09-21

## Polynomial search ignores variable names, and stops at six variables

What happened: T381 holds the discriminant of the general degree-$n$
polynomial as an element of $\mathbb Z[a_0,\dots,a_n]$, and the critique had
to answer two reader questions the skill gives no way to answer. Does somebody
holding the schoolbook $b^2-4ac$ reach the row stored as `a1^2 - 4*a0*a2`?
Yes: the search key is canonicalised over every renaming of the variables, so
the two have the same key and the same hash. And why does the table stop at
degree 5 rather than at a size limit? Because the next entry has seven
variables, and the key is refused beyond six.

Both facts live in one module, `numberdb/_polynomial.py`, which is shipped in
the client package for exactly this reason -- the server and the client must
produce the same bytes, since a long polynomial is looked up by hash rather
than sent. So a contributor can check both on their own laptop, and neither is
in the skill.

The cap matters when choosing a range, in the way the skill already cares
about: a table of seven-variable polynomials would store and display and cite
perfectly well and answer no search by value at all, which is the one thing
the database is for. The renaming-invariance matters in the opposite
direction: two tables that differ only in what they call their variables are
the same table to search, and the naming of the variables is free -- $a_i$ or
$c_i$ or $b^2-4ac$ all land in the same place, so it can be chosen for the
reader rather than for the index.

What the skill says now: section 5 says polynomials are written `x^2 - x - 1`
and are searchable by their digits. Nothing about several variables, about
renaming, or about a cap.

What it should say: a polynomial's search key is taken modulo a renaming of
its variables, so `x^2-2` and `y^2-2` find each other and the names you store
are a display choice. The key is refused above six variables
(`MAX_VARIABLES_FOR_CANONICAL_FORM`), because it is found by trying every
permutation; a value with seven or more can be stored and shown but answers no
search by value, so count the variables before choosing a range.

Evidence, 2026-09-21. Run against this deployment's `utils/numbers/polynomial.py`,
which is byte-identical to the module the client ships as
`numberdb/_polynomial.py` (md5 `81c9d227840e40fdda716fc768ee47e9` for both), so
the same two lines hold on a contributor's laptop:

    >>> from numberdb._polynomial import parse_polynomial
    >>> parse_polynomial('b^2-4*a*c').canonical_text() == \
    ...     parse_polynomial('a1^2-4*a0*a2').canonical_text()
    True
    >>> parse_polynomial('a0*a1*a2*a3*a4*a5*a6').canonical_text()
    ParseError: too many variables for a renaming-invariant key

and the six-variable degree-5 discriminant, 59 terms, canonicalises in 0.09 s
to a key of 1565 characters. T381's completeness note gives the cap as its
reason for stopping, which is the right reason and is checkable.

## The text search ranks, it does not filter, so a missing word costs position rather than the hit

What happened: the critique was about to write that somebody typing "quartic
discriminant" would not find T381 at all, having read the query builder: the
words before the last are ANDed with a prefix match on the last. That is what
the query says and it is not what the search does. Both the dropdown and the
results panel annotate with `ts_rank` and keep everything scoring above 0.01,
and `ts_rank` scores the lexemes of a query without regard to its operators.
So a query whose first word matches nothing still answers, on the strength of
its other words.

The consequence for a table is worth stating in the skill, because it changes
what the `Keywords` rule buys. A word that a reader types and that is in none
of the four indexed fields does not lose them the table; it loses the table
its position, which for a common word like "discriminant" means being one of a
dozen tables that mention one rather than the answer.

The second half of this is which fields are indexed, which the skill states
correctly and which is easy to read too generously. `Formulas`, `Programs` and
`rigour details` are outside it. T381 says "quadratic" and "cubic" in its
provenance note, which reads on the page as if the words were in the table,
and they are invisible to search.

What the skill says now: "The text index has four weights: the title and
`Keywords` first, then `Tags`, then the `Definition`, then the table's
`Comments`. An entry's own comment is in none of them."

What it should say: the same, and then -- everything else is outside the index
too, including `Formulas`, `Programs` and `rigour details`, so a word that
appears only there is not searchable. And the search ranks rather than
filters: a word of the query that the table does not carry does not exclude
it, it only fails to lift it, so the test for `Keywords` is not "would they
find it" but "would they find it *first*".

Evidence, live, 2026-09-21:

    /suggestions?term=zzqqzz              0 entries
    /suggestions?term=zzqqzz+zzqqzz       0 entries
    /suggestions?term=zzqqzz+discriminant 10 entries, every one a table
                                          matching only "discriminant"

`zzqqzz` is in no table, and the third query still answers ten.

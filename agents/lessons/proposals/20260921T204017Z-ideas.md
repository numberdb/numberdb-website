# Lessons from the 2026-09-21T20:40Z ideation run

The batch is *the filters of the discrete wavelet transform*: Daubechies,
symlets, coiflets, the CDF biorthogonal pair of JPEG 2000, and the regularity
exponents. Five lessons. The deployment-specific half of what this run met is
in `docs/agent-environment.md`.

## An identity check cannot see a time-reversed filter

What happened: this run built the Daubechies filters from the spectral
factorisation of the Daubechies polynomial in `ComplexIntervalField(300)`, and
checked them against the three identities that define the family: $\sum h_k =
\sqrt2$, $\sum_k h_k h_{k+2m} = \delta_{m0}$, and $\sum_k (-1)^k k^m h_k = 0$
for $m < N$. All three held, at every $N \le 10$, to between $10^{-90}$ and
$10^{-79}$. The filter was nevertheless wrong: it was the time-reverse of the
standard one, because the construction keeps one root of each reciprocal pair
$\{z, 1/z\}$ and the other choice gives $h$ read backwards. Every identity
above is invariant under $h_k \mapsto h_{2N-1-k}$, so nothing in the check
could see it. It was caught only by comparing with a published table, at the
8 decimals that table carries.

The general shape: when a family is determined by its defining relations *up
to a symmetry*, the relations cannot fix which member of the orbit is stored,
and the symmetry is usually exactly the convention the table exists to record
— orientation, sign, conjugate, branch. Other instances in the corpus's
vocabulary: a sign convention (T174's alternating eigenvalues), a conjugate
pair, a filter and its reverse.

What the skill says now: "Check new values against something independent, not
the code that produced them", and gives identities tying two tables together
as the good case ("A family with known identities gives a free test suite").
It also says a measurement needs a control that returns a known answer.

What it should say: an identity is a free test suite for the *values* and no
test at all for the *convention*. Before trusting one, ask what transformations
leave it invariant; if the family's stated convention is one of them, a
published value is not optional, and it is the citation that belongs in
`rigour details`.

Evidence: 2026-09-21, `agents/sage.sh` run in this run's batch file,
"The Daubechies construction" table. First factorisation: all identities below
$10^{-79}$, `vs Wikipedia` about 1.0 for every $N \ge 2$ and 0 for $N = 1$
(the Haar filter is symmetric, so the bug hid there too). After reversing the
comparison the gaps fall to 5e-9.

## The reference implementation is a check, not a source, and its accuracy varies by family

What happened: PyWavelets 1.8.0 stores its filters as hard-coded decimal
tables. Put through the orthonormality identity, they are not equally good:

    coif1..coif17   worst |sum h - sqrt2| 2.2e-16   worst orthonormality 1.4e-17
    sym2..sym20     worst |sum h - sqrt2| 4.4e-16   worst orthonormality 4.3e-12
    bior4.4         perfect reconstruction                            1.4e-12

So the same library carries about seventeen good digits for one family and
twelve for another, with nothing in its interface saying so. A run that had
decided "copy the library, extend later" would have published twelve digits as
a hundred for the symlets and would have been right for the coiflets.

Measuring it took three lines, and it also told the builder something useful:
twelve digits is plenty to *pin a discrete choice* (which of a dozen
factorisations the library calls `symN`) while being useless as the value.

What the skill says now: return balls rather than floats; `assume_accurate`
requires a `because` and notes that most libraries state no accuracy at all.

What it should say: when a library is the only published source, measure its
accuracy with the family's own identities before deciding what role it can
play — value, seed, or tie-breaker — and say which role it played in
`rigour details`. "Most libraries state no accuracy" understates it: the same
library's accuracy differs between neighbouring families.

Evidence: 2026-09-21, PyWavelets 1.8.0, the table under "The published
coiflets, and what the libraries actually carry" in this run's batch.

## The published table a reader will compare against may be wrong, and saying so is part of the table

What happened: checking against the Wikipedia table of Daubechies coefficients
— the first result for anybody who searches — turned up one wrong digit group:
D14, tap 6 is printed 0.10084670 where the value is 0.100846465. This run's
interval computation and PyWavelets agree with each other to 1e-9 and against
that number by 2.35e-7, and Wikipedia's own column sums to 2 only to 2.4e-7,
by exactly the discrepancy. Every other tap of every other order agrees to
5e-9, which is that table's rounding.

The consequence for a table is not only that the corpus should hold the right
value. It is that a later reader will check the table against the same page,
find a disagreement, and "fix" it — unless the table says where the published
source is wrong and how that was established.

What the skill says now: "the table holds X and this run produced Y — a real
disagreement. Investigate before passing `correcting=True`". That is about a
disagreement with the corpus's own stored value.

What it should say: the same for an external source. When a table disagrees
with a source a reader is likely to reach, record the disagreement in
`rigour details` with the two independent computations that settle it. A value
that is right and unexplained gets corrected back.

Evidence: 2026-09-21, as above; `en.wikipedia.org/wiki/Daubechies_wavelet`
fetched with `action=raw`.

## `source_names_it` passes on a coincidence of one common word

What happened: screening a proposal for *wavelet connection coefficients*
against `en.wikipedia.org/wiki/Wavelet` returned `None`, i.e. the source names
the family. It does not: the article does not contain the phrase "connection
coefficient" anywhere (`grep -ic` returns 0). The screen splits the name into
distinguishing words, drops the generic ones — here `coefficients` is on the
generic list — and looks each remaining word up separately, so "wavelet" and
"connection" both occurring somewhere in a long article is a pass.

The failure mode matters because the screen is described as the check against
inventing a family, and it reads exactly the same when it passes for the wrong
reason. The proposal was dropped on the reading, not on the screen.

What the skill says now: nothing; the screen lives in the stage-one prompt
rather than the skill.

What it should say (wherever `source_names_it` is documented): a pass means
every distinguishing word occurs *somewhere* in the page, not that the page
names the family. For a multi-word name whose words are individually common,
confirm the phrase by hand; the check is a filter against invention, not
evidence of naming.

Evidence: 2026-09-21. `source_names_it('Wavelet connection coefficients',
'https://en.wikipedia.org/wiki/Wavelet')` returns `None`;
`curl .../Wavelet?action=raw | grep -ic "connection coefficient"` returns 0.

## Two small Sage facts a bare SageMath contradicts

What happened, twice in one script:

* `from sage.functions.other import binomial` fails in the container's
  SageMath with `AttributeError: cannot access submodule 'function' of module
  'sage.symbolic' (most likely due to a circular import)` — the symbolic ring
  is not initialised at that point. `ZZ(n).binomial(ZZ(k))` works and needs
  nothing but `sage.rings.integer_ring`.
* `RealIntervalField(p)(x).center()` returns a `RealField` element, and
  comparing it with an `RIF` element raises `TypeError: unsupported operand
  parent(s) for >`. So `max(RIF(0), something.center())` fails, which is easy
  to write while accumulating a worst-case residual. Accumulate in `float`.

What the skill says now: "Name the rings you use, rather than importing
`sage.all`", and lists what the named imports do not bring: root finding,
`RealBall.str`, `QQ('1.25')`.

What it should say: add `binomial` and the other `sage.functions.*` entry
points to that list — they are behind the symbolic ring, not behind a ring
module — and note that `.center()` leaves the interval field, so a residual
accumulated with `max` must be converted first.

Evidence: 2026-09-21, both raised by `/tmp/w3_daub_check.py` under
`agents/sage.sh` before the fixes; the run's output after them is in the batch.

# Lessons proposed by the T0 critique, 2026-09-21

One, met while reading T0 (*Zero*) against <https://numberdb.org/skill>. It is
reachable by a contributor with a laptop, Python and the client package, and it
is not about this deployment. It is the third lesson about this search box
proposed today and it repeats neither: `20260921T215138Z-critique.md` is about a
bare integer being read as a table's own number, and `20260921T211050Z-critique.md`
about the number channel. This one is about the ranking of the *word* channel.

---

## Text search ranks by how often a word occurs, not by how well the title matches, so a short exact title is buried under long ones

What happened: T0 is a table called "Zero". A reader who types the table's own
name gets it **fourteenth**, behind thirteen tables called "Zeros of the …" —
zeros of the Dedekind zeta functions, of Bessel functions, of the polygamma
functions, and so on. The exact and only name of the family loses to every
table that merely mentions the word.

That is not a tie broken badly. The site annotates with Django's
`SearchRank(F('search_vector'), query)` and no `normalization` argument
(`numberdb_app/search.py:679`), which is Postgres `ts_rank` at normalisation 0:
the score grows with the **number of weighted occurrences** of the query's
lexemes and is never divided by the length of the document. The index has four
weights — title and `Keywords` (A), `Tags` (B), `Definition` (C), `Comments`
(D) — so a table that says its subject once, in a one-word title, scores one
occurrence at weight A, while a table that says it in a long title, a tag, a
definition and nine comments accumulates a dozen.

Measured: counting occurrences of the stem in each of the 20 tables the query
returned and weighting them by Postgres's defaults (1, 0.4, 0.2, 0.1)
reproduces the site's order almost exactly, monotone down the list, with one
inversion between the eighteenth and nineteenth:

    rank  score   A  B  C   D   table
     1     7.0    5  1  1  14   Zeros of the Dedekind zeta functions of cubic fields
     2     5.9    4  1  2  11   Zeros of the Hurwitz zeta function
     3     4.2    3  1  1   6   Zeros of the L-functions of level one cusp forms
     …
    13     1.6    1  1  1   0   Zeros of Bessel functions of the second kind
    14     1.0    1  0  0   0   Zero
    15     1.0    1  0  0   0   Laurent series coefficients of ... zeta ...
    16     0.5    0  1  0   1   Teichmüller representatives in Z_p

The same shape shows on other one-word titles: "Pi" is fifth for `pi`, behind
the Pisot numbers and a Gagliardo–Nirenberg table; "One" does not reach the
first six for `one`, which are all "… of level one cusp forms".

Two consequences a contributor cannot guess, and which matter at exactly the
moment the skill asks them to choose a title:

* **A short title is a weak search position, not a strong one.** The skill's
  test — "what would somebody type who is holding one of these numbers?" — is
  necessary and not sufficient: if that word is also a word other tables in the
  corpus use *about* their subject, the short title loses to them.
* **`Keywords` does not rescue it.** Keywords sit at weight A with the title,
  so they raise the score only by adding another occurrence of a word already
  there. Adding a synonym reaches a query the title misses, which is what the
  skill already says; it does not move the table up for the word it is named
  after.

What the skill says now: "A title is what a search reaches. The text index has
four weights: the title and `Keywords` first, then `Tags`, then the
`Definition`, then the table's `Comments`." That describes the weights and
implies that the highest weight wins. It says nothing about occurrence counts,
nothing about length normalisation, and nothing about a common word being
crowded out.

What it should say: the four weights are added up over **every occurrence** and
the total is not divided by the length of the document, so a table that names
its subject once ranks below one that names it many times, however exact the
first title is. Where a family's name is a common word other tables use about
their own subjects — "zero", "one", "pi", "values", "polynomials" — expect the
table to be findable by *value* and by a distinguishing phrase in `Keywords`
("zero element", "additive identity"), and not by the bare word. That is a
reason to choose a title that contains a word only this family uses, and a
reason not to conclude that a table is unfindable because a one-word query
buries it.

Evidence: 2026-09-21, T0 critique (`agents/critiques/T0.md`). Live corpus
through the repository client: `numberdb.search_text('zero')` → 20 tables with
"Zero" fourteenth; `search_text('pi')` → "Pi" fifth; `search_text('one')` → no
"One" in the first six. The per-table occurrence counts above come from
`numberdb.table(tid)` for each of the 20 returned tables, counting
`re.findall('zero', …, re.I)` in `Title` + `Keywords`, `Tags`, `Definition` and
`Comments`. The ranking call is `numberdb_app/search.py:679`; Django's
`SearchRank` with `normalization` unset emits `ts_rank(vector, query)`, whose
documented behaviour is to ignore document length.

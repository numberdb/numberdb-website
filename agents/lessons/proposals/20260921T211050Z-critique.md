# Lessons proposed by the T1 growth critique, 2026-09-21

Two, met while reading T1 (*One*) against <https://numberdb.org/skill>. Both
are reachable by a contributor with a laptop, Python and a browser; neither is
about this deployment.

---

## A table whose definition names one object needs `complete: yes`, and the skill's advice on `complete` is written only for the other case

What happened: T1 holds the integer 1, defined as "the neutral element of
multiplication in the ring of integers". A monoid has exactly one neutral
element, so the table is complete by a one-line proof and can never gain a row.
Its `Data properties` nevertheless carry no `complete` and no `complete-note`,
so the rendered page says nothing whatever about whether one entry is all there
is — and the table was accordingly queued for a growth review, which is a
person's afternoon spent re-deriving a fact the author knew when they wrote the
definition.

It is not one table. Of the twelve tables in this corpus with exactly one
entry, five declare `complete: yes` (T5, T7, T8, T173, T189) and seven declare
nothing (T0, T1, T37, T38, T39, T42, T43). The seven are indistinguishable, on
their own pages, from a table somebody started and abandoned.

There is a cheap and exact test for this class, and no field in the document
records its answer: **a table with no parameters cannot grow.** T1's
`Parameters` is the empty string and its single entry is `params: {}`. There
is nothing to enumerate along, so `complete` can only be `yes`, and a
parameterless table without it is always a gap rather than a judgement call.

What the skill says now: section 4 explains `complete` entirely in terms of a
range that stops somewhere — "`complete: no`, with `complete-note` saying which
part is finished… it holds every real fundamental discriminant with $D \leq
1000$, at $s = -1, -3, -5$". Every word of that assumes a family being sampled.
A one-constant table cannot use any of it: there is no part that is finished,
because there are no parts. The skill also says, correctly, that a table of a
named constant is a legitimate thing and that several such constants make
several tables — but it never says what such a table writes in `complete`, and
the corpus's split of five to seven is what that silence produces.

What it should say: where the definition names a single object rather than a
family, the table is complete and must say so —

    complete: yes
    complete-note: it holds the single number named by the definition

which is T8's clause verbatim and reads on the page as "Table is complete: yes
(it holds the single number named by the definition)". The test is mechanical:
if the table has no parameters, `complete: yes` is the only honest answer, and
omitting it is not modesty but an unanswered question that somebody else will
have to answer by reading the mathematics. Where a convention or a companion
table takes the near misses, the clause should say so, as T7's does: "…; the
scaled values $a\pi$ are held by rational multiples of $\pi$."

This is the opposite end of the case recorded in
`20260921T201824Z-critique.md`, which is about a table of *examples* of an
infinite family needing its note to say that it is examples. Between them they
cover the two tables whose entry count cannot be read at face value: the
handful-of-examples table that should not grow, and the one-object table that
cannot.

Evidence: 2026-09-21, T1 growth review (`agents/critiques/T1-growth.md`).
`/bundle/T1` — `Parameters: ''`, entry `params: {}`, `Data properties` holding
`type`, `rigour` and `rigour details` only. The twelve one-entry tables from
`/tables?sort_by=entry_count`, their `Data properties` read through
`/api/table?id=…`, giving the five/seven split above. `/T7` and `/T8` for the
rendered sentence. `numberdb_app/limits.py::claims_completeness` reads only the
leading word, so `yes` alone is enough and the clause is free.
`numberdb_app/metadata_form.py` offers `yes | no | unknown` plus a condition, so
the site already expects this to be answered. `GET /api/table/T1/audit` returns
one finding and nothing about the missing `complete`: no rule asks.

## The search box takes a digit string, not a value, so a short query answers nothing and a table's own entry can be absent from its own search

What happened: T1's entry is the exact integer 1 — zero width, `reviewed`,
carrying no not-findable dagger, and scored by `search.py` at the maximum a
value can get. A reader who arrives holding the number 1 and types `1`
nevertheless never reaches it:

    /api/lookup?text=1      100 results and "We only show the first 100
                            results"; five tables (T197 ×96, T61, T11, T93,
                            T329); T1 in none of them, identically on three
                            successive requests
    /api/lookup?text=42     100 results; T42 second        (control: it can work)
    /api/lookup?text=1729   25 results; exact 1729 first, then 0.1728010…,
                            1.1728741…, 8796.1729141…

The third line is the mechanism and it is the part that surprises. `1729`
matched values at three different exponents, so **a query is a run of
significant digits, not a number** — the shape `/api/lookup`'s own docstring
names as "the search bar's grammar: `3.14159`, `1415`, `Q5:1010`". So `1` asks
for every stored value whose significant digits begin with 1, which by
Benford's law is about a third of the corpus. Once more than a page of values
lie inside a query, `search_real_numbers` takes its documented fast path and
returns the first hundred **in arbitrary order** — "they are all equally good
answers by the ranking, and for a query this broad the useful next step is a
narrower query rather than a better-sorted page", which is sound, and which
means absence from the results carries no information at all.

Two things follow that an author cannot guess.

**You cannot confirm your published table is searchable by typing a short
prefix of its value.** The obvious check after publishing — put the number in
the box — returns a capped page that need not contain your table however
correctly it was indexed. Type enough digits that the result set falls under
the cap; if the value has no further digits, as an integer does not, the check
is simply unavailable.

**The skill's warning about small integers is stronger than it states.** It
says values that are a handful of small integers "match everything and tell
nobody anything, and putting them in a table makes search by number worse for
everyone". Measured, the harm is not that such a row is one weak hit among
many: it is that the row is *absent*, and so is every other row in the
over-capped set, chosen by nothing. A table of small integers does not dilute
the answer, it randomises it.

What the skill says now: section 1 covers `search_text` for titles and tags and
warns that it stems and returns an object rather than a list. Section 3 warns
about small integers, as quoted. Section 10 says to verify against an
independent computation. Nothing anywhere says what the number search does with
a query, that it is digit-based rather than value-based, that there is a
hundred-result cap, or that over the cap the order is arbitrary.

What it should say: the number search matches a **digit string**, at any
exponent — `1729` finds 0.1728…, 1.1728… and 8796.1729… — and it returns at
most a hundred results, in arbitrary order once more than a hundred match. So a
query of few digits is not a weak search, it is no search; verifying an entry
by searching for it needs enough digits to bring the result set under the cap;
and a value with few significant digits is unreachable by number however
correctly it is stored. That last point is the real form of the existing
small-integer rule, and it is worth saying in the same breath as it.

Evidence: 2026-09-21, T1 growth review. The three `/api/lookup` queries above,
with `X-API-Key`, against the live corpus; the `text=1` query repeated three
times with an identical set of five tables and no T1.
`numberdb_app/search.py::search_real_numbers` — the containment fast path
(`contained = list(inside[:limit])`, returned unsorted when it fills) and its
docstring naming the arbitrary order as a deliberate trade; `PAGE_SIZE = 100`;
`_SCORE_SQL_TEMPLATE`, which gives a zero-width value the maximum score of 1,
so T1's absence is the fast path and not the ranking. `/T1` shows the value
without the `not-findable-mark` dagger, so the site holds it to be searchable.

## `Programs` is a mapping with `language` and `code`, and a string there answers 500

What happened: draft T356 wrote its `Programs` section as prose, the way every
other prose field in a table is written:

```yaml
Programs:
  sage: In Sage, compute $A^{(n)}_p$ from `(R(p) ** (1/p) / R(q) ** (1/q)) **
    (n/2)` in a `RealBallField`, with `q = p/(p - 1)`.
```

The API accepted it. `commit_table` validates citations, parameters, types and
size, and says nothing about the shape of a program. The audit accepted it too:
its only `Programs` check guards with `if isinstance(program, dict)` and reads
an empty string otherwise, so `GET /api/table/T356/audit` came back with two
unrelated tag findings and nothing about this.

The renderer does not accept it. It reads `program['language']` and
`program['code']`, so a string raises `TypeError: string indices must be
integers, not 'str'`, which the table page turns into a 500 -- not a broken
sentence in one section, the whole page. Title, definition, parameters,
formulas, comments, references and all 140 values are gone, over one field that
nothing on the way in objected to. The table was clean on the audit and
unreadable on the page at the same time.

A contributor on their own laptop hits this exactly as this run did: they write
a document, the API takes it, the audit passes, and the page they wrote it for
is a server error. The only way to find out is to look at the rendered page,
which is the thing the skill does not currently tell anybody to do before
offering a draft for review.

What the skill says now: §4's table gives `Programs` as "the standard
incantation in Sage, PARI or mpmath for a reader who wants one more value", and
§6 distinguishes it from `generate.py`. Neither says what a `Programs` entry
*is* -- both read as though the value were a sentence -- and no example of the
section appears anywhere in the skill.

What it should say: a `Programs` entry is a mapping with two keys, not a
string.

```yaml
Programs:
  program-sage:
    language: Sage
    code: |
      import numberdb.sage as numberdb
      from sage.rings.rational_field import QQ
      from sage.rings.real_arb import RealBallField

      R = RealBallField(numberdb.bits(100, losing=96))
      print(R(QQ(5) / QQ(4)).log())
```

`language` is printed above the snippet and picks the syntax highlighting;
`code` is escaped and shown as a block, so `R.<x> = ZZ[]` survives. A string
where the mapping is expected is accepted by the API, passes the audit, and
answers the table page with a 500.

And the rule under it, which is what makes the fault findable in general:
**fetch the rendered page before offering a draft for review.** The document
round-tripping through the API is not evidence that it renders; three faults
this year lived only in the rendering.

Evidence: 2026-09-20, draft T356. `GET /api/table?id=T356` returns
`"Programs": {"sage": "In Sage, compute ..."}`, a string, where T354 and T355
of the same batch return `{"program-sage": {"language": "Sage", "code":
"..."}}`. `GET /preview?table=<the document with Title, Definition, Programs
and one entry>` answers 200 with `Error while Parse program sage: string
indices must be integers, not 'str'` and an empty body; the same document
without `Programs` renders every section. `numberdb_app/views.py:914` and
`:925` index the program; `:1460` re-raises as `ValueError`; `render_table` at
`:442` catches nothing and no middleware does. The audit's guard is
`audit_table.py:447`.

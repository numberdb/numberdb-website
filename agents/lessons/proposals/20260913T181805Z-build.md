## A claimed draft with no `Numbers: []` can still trip the generator preflight

What happened: T232 was claimed with title and prose only, as a draft with no
`Numbers` section. The generator passed the dry run, but its first ordinary
publish attempt failed before sending the real entries: the client posted the
empty upsert it uses as a writability check, and the server answered
`A value in these entries cannot be read as a number. 'str' object has no
attribute 'items'`. Replacing the entries with a non-empty block, and then
attaching the source, filled the draft.

What the skill says now: create the draft first with title and prose, no
numbers, and fill it once after the generator passes its private checks.

What it should say: when claiming a draft through the API, include
`Numbers: []`. It is still an empty draft, but it gives the generator's empty
preflight an entries section to merge into. If the exact parser error above
appears before the first value is computed, no values have been sent; add the
empty section or send the first non-empty entry replacement directly.

Evidence: `cat "$NUMBERDB_KEY_FILE" | NUMBERDB_KEY_FROM_STDIN=1
NUMBERDB_PUBLISH=1 NUMBERDB_ASSISTED_BY=codex-cli agents/sage.sh
generators/birkhoff-polytope-ehrhart-polynomials/generate.py`, 2026-09-13,
failed with the quoted message before any entry was computed. The same
generator filled T232 after `fill_draft_once()` skipped only the empty upsert
probe and called `/api/table/232/entries` with eight records.

## The source range is not the table range when exact polynomials become unreadable

What happened: Beck and Pixton publish the full Birkhoff-polytope Ehrhart
polynomials through $n=9$, and the first T232 fill stored both Ehrhart and
$h^*$ forms for $3\leq n\leq9$. `dry_run.py` then measured the actual strings:
$H_7(t)$ was 2252 characters, $H_8(t)$ was 4542, and $H_9(t)$ was 8679. The
complete rectangle through $n=6$ has longest entry 966 characters, so the draft
was trimmed to $3\leq n\leq6$ before it was offered for review.

What the skill says now: measure the largest entry before choosing a range,
and aim for a complete rectangle.

What it should say: for exact polynomial families, a source's last published
row is evidence about what can be computed, not about what should be stored.
If a later complete row crosses the readability threshold and no companion
table forces the range, trim to the previous complete rectangle and report the
first omitted row's written length.

Evidence: `/tmp/measure_birkhoff_rows.py`, 2026-09-13, printed
`7 ehrhart 2252`, `8 ehrhart 4542`, and `9 ehrhart 8679`; the final dry run
for T232 printed `8 entries, longest 966 characters at form=ehrhart,n=6`.

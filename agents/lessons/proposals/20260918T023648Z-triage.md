Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force.

Both of these are about reading a draft back over the API, which is what
triage does and what anybody filling a table in two sittings does too.

---

## `/api/table` answers "does not exist" for a table you are not allowed to see, and says it with HTTP 200

What happened: checking what a failed run had left behind, the draft it had
just created answered

    $ curl -s 'https://numberdb.org/api/table?id=T320'
    {"error": "Table with id 'T320' does not exist."}

which reads as "your draft is gone" and is in fact "you did not authenticate".
The table was there the whole time. Two separate things make this hard to see:

**It is the same sentence for both cases, when you query by `id`.** A draft
you may not see and a number past the end of the corpus are indistinguishable:

    ?id=T320     -> {"error": "Table with id 'T320' does not exist."}   (exists)
    ?id=T99999   -> {"error": "Table with id 'T99999' does not exist."} (does not)

**Querying by `url` tells the two apart.** The not-found branch names what you
asked for, and the hidden-draft branch names the table's id -- which it could
only have learned by finding the row:

    ?url=Complementary_Shapiro_polynomials
      -> {"error": "Table with id 'T320' does not exist."}
         ^ answered with an *id* you did not supply: the table exists, you
           cannot see it
    ?url=No_Such_Table_At_All_XYZ
      -> {"error": "Table with url 'No_Such_Table_At_All_XYZ' does not exist."}
         ^ answered with your *url*: there is genuinely no such table

So: if you hold a draft's address and `?url=` answers you with a `T`-number,
the draft is alive and your key is the problem. If it answers with your own
url back, the table is really not there.

**And every one of these is HTTP 200.** Not 404. `/api/table` returns its
errors through a plain `JsonResponse` with no status, so a client that
branches on `resp.status` or uses `curl -f` treats "does not exist" as a
successful fetch and only discovers the problem when it indexes the payload.
The sibling endpoint `/api/table/<tid>/audit` *does* answer 404 for the same
condition, so the two cannot be handled the same way.

What the skill says now: that a draft is private to its author and the board,
and that a request carrying their key sees it. It does not say what the refusal
looks like -- and the refusal is indistinguishable from deletion, which is the
one thing that would make somebody stop looking for their own work.

What it should say: a draft you cannot see answers "does not exist", not
"forbidden", and answers it with HTTP 200. Before concluding a draft was lost,
query it by `url` rather than `id`: an answer naming a `T`-number you did not
ask for proves the table exists and the key did not arrive. Check status codes
per endpoint rather than across the API; `/api/table` uses 200 for errors and
`/audit` uses 404.

Evidence: 2026-09-18, triage of build run 20260918T023210Z, against the live
site. `/tmp/probe2.py`, the five queries above, all HTTP 200. The same draft
read back in full with the key attached (`Title`, `Definition`, ... eight keys,
no `Numbers`), and `/api/table/T320/audit` returning findings once
authenticated. Branches at `numberdb_app/api.py:380-420`.

## `cat key | python3 - <<'PY'` sends an empty key, silently

What happened: the shape the skill gives for feeding a key to a script is a
pipe --

    cat "$NUMBERDB_KEY_FILE" | agents/sage.sh fill.py

-- and writing the script as a heredoc in the same command instead of putting
it in a file destroys it:

    $ cat /tmp/fakekey | python3 - <<'PY'
    import sys
    print('read from stdin: %r' % sys.stdin.read())
    PY
    read from stdin: ''

    $ cat > /tmp/reader.py <<'PY'
    ... same two lines ...
    PY
    $ cat /tmp/fakekey | python3 /tmp/reader.py
    read from stdin: 'SECRET-VALUE\n'

`python3 -` reads the *program* from stdin, and the heredoc is what stdin is;
the pipe is discarded before the program ever runs. There is no error. The
script gets `''`, builds the header `Authorization: Bearer `, and the server
answers as it would for an anonymous caller -- which, for a draft, is the
"does not exist" above. The two failures compose into a convincing story that
your table was deleted.

Both idioms are ones a contributor already has: a heredoc to avoid leaving a
scratch file around, a pipe to keep the key off the command line. They are
individually correct and cannot be used together.

What the skill says now: that the key goes in by pipe and is never an
argument, and shows the pipe form. It does not say that the pipe form fixes
what stdin is, so the script cannot also come from there.

What it should say: a script that reads the key from stdin has to live in a
file -- `python3 /tmp/fill.py`, not `python3 - <<'PY'` -- because a heredoc
*is* stdin and silently wins. A one-line assertion at the top is worth it,
since the failure is a plausible-looking answer rather than an error:

    key = sys.stdin.read().strip()
    assert key, 'no key on stdin: is the script itself coming from a heredoc?'

Evidence: 2026-09-18, triage of build run 20260918T023210Z. The two runs
above, verbatim, with a throwaway file; and four API probes that appeared to
show a just-created draft missing, all of which were the empty-key path.

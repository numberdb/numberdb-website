## Whether a draft has been offered is the one thing the API will not tell you

What happened: the previous triage established that draft T441 was finished
(903 entries, audit clean) and never offered, and proposed `POST
/api/table/T441/offer` as the fix -- the lesson in
`agents/lessons/proposals/20260923T072522Z-triage.md`, since committed as
`fa8bf4ba`. Eighty minutes later I had to check whether anything had acted on
that. It is a read, it should have been one request, and there is no request
that answers it.

`GET /api/table?id=T441` with the author's key works and returns the draft --
200, `application/json`, 28985 bytes. But what it returns is
`_ordered_document(table)`, and the document is the table's *contents*:

    ['Comments', 'Data properties', 'Definition', 'Display properties',
     'Formulas', 'Keywords', 'Links', 'Numbers', 'Parameters', 'Programs',
     'References', 'Similar tables', 'Tags', 'Title']

No `ready_for_review`, no `published`, no state of any kind. A draft and a
draft in the review queue are byte-identical through this route.

The page that does show it is `/drafts`, and it is a browser page, not an API.
Sending it a key is worse than useless, because it does not fail in a way a
script notices:

    GET /drafts, Authorization: Bearer <key>
      -> 302, Location: /accounts/login/?next=/drafts

`urllib` and `requests` both follow that by default, so a naive script gets
**HTTP 200** and a `text/html` body -- the sign-in page. `resp.status_code ==
200` is true, `raise_for_status()` passes, and anything looking for a T-number
in the body finds nothing and concludes the draft is gone. An API key is not a
session; only a cookie reaches that view.

The full list of API routes is in `numberdb_app/urls.py`: `api/search`,
`api/lookup`, `api/table`, `api/tables`, and per-table `write`, `entries`,
`offer`, `lease`, `audit`, `file`, plus `api/tag`, `api/claim`, `api/costs`.
There is no `api/drafts` and no status read anywhere among them.

So the only way to learn that a draft is offered is to offer it. Which is
survivable, and this is the practical answer: `offer_table` sets
`ready_for_review = True` unconditionally and returns

    {"tid": "T441", "published": false, "ready_for_review": true}

It is idempotent -- the prior lesson says so and the source confirms it -- so
sending it again when you are unsure costs nothing and is the check. Its
refusals are informative too: 409 `"%s has no numbers in it yet"` if the draft
is empty, 409 `"%s is already published"` if it has been through review, 404 if
the table is not yours. Between the success body and those three, the POST is
the status read. It is just not a read.

What the skill says now: nothing. Section 9 describes offering as an act and
never as a state, and there is no sentence anywhere in `SKILL.md` about
checking whether it happened. A contributor following the newly proposed step 3
will send the POST, get a 200, and be fine -- until a script dies between
filling and offering, or a `curl` scrolls off, and they want to know where they
got to.

What it should say: alongside the `POST /api/table/<tid>/offer` sentence, that
the offered state cannot be read back through the API, and that re-sending the
POST is how you check --

> There is no API call that tells you whether a draft has been offered. `GET
> /api/table?id=<tid>` returns the document -- title, prose, numbers -- and no
> state, and `/drafts` is a signed-in browser page which will *redirect* an API
> key to the login form, so a script that follows redirects gets HTTP 200 and a
> page of HTML rather than an error. If you are not sure whether your offer
> landed, **send it again**: it is idempotent, the reply is
> `{"ready_for_review": true}`, and that reply is the only status read there
> is. A 409 means the draft is empty or already published, and either way tells
> you where you are.

Why it belongs in the skill rather than the environment notes: none of it is
about this deployment. It is the shape of the public API at numberdb.org, and a
contributor on a laptop hits it the first moment they wonder whether a build
they interrupted got as far as the offer -- which is exactly the situation the
lesson in `fa8bf4ba` tells them to check for. That lesson ends "if a build of
yours died near the end, check this before anything else", and this is the
finding that checking is not possible as a read. The two belong in the same
paragraph.

Smaller than the lesson it follows, and it is a companion to it rather than a
finding on its own: the remedy -- re-send the idempotent POST -- is a sentence
the earlier lesson nearly contains already. What it adds is the reason you
would need to, and the 302 trap, which is the part that silently gives a wrong
answer rather than no answer.

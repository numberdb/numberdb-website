## A rule restated in words has to say which count it means, or it is a second definition of a different table

What happened: T319's `Formulas` gives the Rudin-Shapiro coefficient rule as
the one thing a reader can rebuild the whole table from without the
recurrence:

> $P_n(x)=\sum_{j=0}^{2^n-1}a_jx^j$, where $a_j=1$ if the binary expansion of
> $j$ has an even number of adjacent $11$ pairs and $a_j=-1$ otherwise.

Occurrences of `11` can be counted overlapping or not, and the two readings are
different sequences. `111` has two overlapping occurrences and one
non-overlapping, so the two agree up to $n=2$ and part company at $n=3$: 1
coefficient of $P_3$ differs, then 3, 7, 17, and 39 of the 128 coefficients of
$P_7$. The table is right under the overlapping reading -- the attached
generator computes `(j & (j >> 1)).bit_count()`, which is unambiguous -- and
nothing about the wrong answer looks wrong, because it is still a $\pm1$
sequence of the right degree. The cited article says "the number of pairs of
consecutive ones", which has only one reading.

What the skill says now: section 2 makes this demand of the *Definition* --
"Which quantity, exactly. Not 'the AGM' but 'the AGM, taking at each step the
square root nearer to the new arithmetic mean'" -- and section 4 says
"Define notation where you use it". Neither reaches a `Formulas` entry, and a
formula is where a family like this is usually restated in a form a reader
would actually compute from.

What it should say: a formula that restates the definition in a form a reader
could recompute the table from is a second definition, and is held to the same
standard as the first. The commonest way it fails is a count with two readings:
occurrences of a pattern (overlapping or not), divisors (proper or not), roots
(with multiplicity or not), an index (from 0 or from 1). Where a count can be
read two ways, say which -- and prefer the source's own words, since a family
in the literature has usually already fixed it.

Evidence: 2026-09-18, T319. Both readings built in
`agents/sage.sh /tmp/t319_check.py`: `overlapping: True / non-overlapping:
False` from $n=3$, with the differing-coefficient counts above; smallest
disagreement at $j=7$ (`111`), the coefficient of $x^7$ in $P_3$, which the
table stores as $+1$.

## Fourth instance of the pending `sage.*` submodule lesson, and the import that hides it

Not a new lesson, but it changes the shape of the pending one. The proposal
"A `Programs` snippet that imports from `sage.*` submodules runs in a Sage
session and not in a Sage script"
(`agents/lessons/proposals/20260916T024304Z-critique.md`, with instances
recorded by the T257 and T258 critiques) predicts a failure on line 1. T319
does not fail on line 1, and that is worth adding, because it is the case
where the existing advice passes the snippet.

Its `Programs` block opens with the generator's four lines:

    import numberdb.sage as numberdb
    from sage.rings.integer_ring import ZZ
    from sage.rings.polynomial.polynomial_ring_constructor import PolynomialRing

The `numberdb.sage` import is what initialises Sage, so the two submodule
imports that fail on their own succeed here -- measured both ways in the same
image:

    from sage.rings.integer_ring import ZZ          # first line of the file
      -> AttributeError: partially initialized module
         'sage.rings.integer_ring' has no attribute 'ZZ'

    import numberdb.sage as numberdb                # first line of the file
    from sage.rings.integer_ring import ZZ          # then this
      -> ok

So the snippet gets past its imports and dies four lines later on session
syntax instead:

    P, Q = P + x^(2^k)*Q, P - x^(2^k)*Q
      -> RuntimeError: Use ** for exponentiation, not '^', which means xor
         in Python, and has the wrong precedence.

The two halves of the block come from different places: the imports are the
generator's, which needs them because it runs as a file, and the `^` is the
session's. Its sibling T318, written in the same batch with the same imports,
writes `**` and runs both ways.

What the skill says now: "`Programs` and `generate.py` answer different
questions", and that `sage -python` has no preparser.

What it should say, alongside the pending proposal: a `Programs` block adapted
from the table's generator inherits the generator's imports, which say "run me
as a file", and `**` is the only exponent that is then true of it. Writing
`**` costs nothing in a session and is what makes the block correct in both;
`^` in a block that opens with `import` lines is the tell that two idioms were
spliced. Checking it by preparsing alone will not catch this, because
preparsing is the reading in which it works.

Evidence: 2026-09-18, T319 critique. `/tmp/t319_progs2.py` (imports without
`numberdb` first, `AttributeError`), `/tmp/t319_progs3.py` (imports with it,
then the `RuntimeError` on the loop), `/tmp/t319_check.py` (the same block
preparsed, which runs and returns $P_8$).

## Editing an empty draft through the table endpoint is refused

What happened: the draft for T413 was created empty, as the workflow asks:
prose first, numbers later. After deciding not to rely on one of the checks
named in the first prose revision, I tried to update the draft document through
`POST /api/table/T413` with the corrected document and `Numbers: []`. The
server answered `400` with "A table needs at least one entry" and told the
caller to send `X-Draft: yes`, which only applies to creating a draft. The
same prose edit has to wait until after the generator has filled at least one
entry, or be made by creating the draft with the final prose in the first
place.

What the skill says now: it says a draft may have no numbers and should be
created before the build, with title and prose if available. It does not say
that the full-document edit endpoint refuses an empty draft document.

What it should say: if the prose of an empty draft has to be changed before
the numbers are filled, the API route that replaces a table document will
refuse it. Either create the draft only after the prose has settled, or make
the prose repair after filling the entries, reading the draft back first so the
replacement document includes its numbers.

Evidence: `POST /api/table/T413` with the corrected table document and
`Numbers: []`, 2026-09-22, returned
`{"error": "A table needs at least one entry.", ...}`.

## For Sage's ordinary p-adic L-series, `prec` counts T-terms, not p-adic digits

What happened: the family issue said the table of values $L_p(E,1)$ could not
meet the house precision target because computing the ordinary p-adic
$L$-series to high approximation requires many modular-symbol summands. Sage's
`pAdicLseriesOrdinary.series(n, prec=...)` does use about
$(p-1)p^{n-1}$ summands for a full approximation, and its `prec` argument is
the number of terms in the power series in $T$, not the p-adic precision of
the coefficients. For the central value alone, the source also states the
interpolation formula
$L_p(E,1)=(1-\alpha^{-1})^2L(E,1)/\Omega_E$, so the generator can compute the
constant term directly from the exact modular symbol and a Hensel lift of the
unit root, at the usual $p^n\geq10^{50}$ precision, without computing the full
series.

What the skill says now: it says to settle the normalization and check every
identity, but it does not warn that a library argument called `prec` may be a
series truncation parameter rather than a value precision.

What it should say: when a source routine has both an approximation order and a
precision-looking argument, read the documentation and test a small control
before setting the table's precision. If the table stores a special value of a
series and the source gives an interpolation or constant-term formula, compute
that named value directly rather than asking the library for a whole high-order
series.

Evidence: Sage's documentation for
`pAdicLseriesOrdinary.series(n, quadratic_twist=1, prec=5, eta=0)` says `n` is
the approximation order and `prec` is the maximal number of series terms; the
T413 generator computes only the interpolation value and checks its exact
rational factor against PARI's complex $L$-value.

## Qp values may need a client rigour workaround when writing as proven

What happened: the dry-run exactness check accepts a Sage $p$-adic value as a
value carrying its own precision, because its printed form includes an
$O(p^n)$ term. The Python client's publish rigour check did not make the same
recognition. It refused the first T413 upload before writing entries, saying
that a `Qp` value under `rigour = "proven"` carried no error of its own. The
client's comparison code already compares $p$-adics by their $O$-terms, so the
generator patched the client's `_carries_its_own_error` predicate during the
run to treat Sage $p$-adic elements as bounded.

What the skill says now: it says a `Qp` value carries its precision in its
$O$-term, and `dry_run.py` follows that convention. It does not mention that
the upload client may lag behind the checker.

What it should say: until the Python client recognises Sage $p$-adics in its
publish rigour gate, a proven `Qp` generator may need either a client update or
a narrowly scoped runtime patch that marks $p$-adic elements as carrying their
own error. Do not lower the table's rigour merely to satisfy the writer when
the value is actually bounded by its $O(p^n)$ term.

Evidence: `generator.publish()` for T413, 2026-09-22, refused entry
`11,496,20008,5` with "rigour is 'proven', and this value carries no error of
its own"; the same entry had passed `agents/table-build/dry_run.py`.

## Draft tag audits do not count sibling drafts toward a new family tag
What happened: numberdb-data#163 proposes the new tag `characteristic classes`
for seven related tables. T332 already existed as a draft with that tag, and
T333 was then built as a second draft with the same tag. The audit for T333
still reported `Tags: "characteristic classes" reaches only this table`, and
`GET /api/tag?url=characteristic+classes` reported zero public tables.

What the skill says now: it says to propose a new tag when three or more
tables would use it, counting other tables in the same batch. A previous lesson
from T332 says the first table in such a family may have an expected audit
finding until siblings exist. It does not say that sibling drafts may still
not count for the audit.

What it should say: when a family proposes a new tag and several siblings are
still drafts, do not expect those sibling drafts to make the tag audit clean.
Keep the family tag when the batch justifies it, and report the tag finding as
expected until the sibling tables are published or a reviewer chooses a
different tag policy.

Evidence: T333, 2026-09-18. T332 and T333 both carried `characteristic
classes` as drafts. The authenticated audit endpoint for T333 returned a
single finding saying the tag reaches only this table, and the authenticated
tag endpoint reported `table_count: 0`.

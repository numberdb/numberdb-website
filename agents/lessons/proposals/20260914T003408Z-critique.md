## An entry link names every parameter; a prefix lands on "This table has no entry"

What happened: T240's Similar tables links
`HREF{Entropy_constants_of_lattice_models#hard-core}`. T153 has three
parameters, so its rows are `hard-core,line,kappa` and so on. `hard-core`
by itself is a group of eight rows, not an entry. The link renders as
`/Entropy_constants_of_lattice_models?entry=hard-core`. That page answers
200, but opens with "This table has no entry hard-core. It may have been
renumbered or removed; the table itself is shown below." `manage.py
audit_table` does not catch it. It checks only the slug before the `#`
(`target = href.split('#')[0]`), so the link passes.

What the skill says now: "a row of a three-parameter table is
`HREF{slug#Z,1,density}`", and "Read the keys out of the table rather than
inventing them". It does not say what happens with a partial key, or that the
audit does not check the part after the `#`.

What it should say: an entry address is the whole tuple of parameter
values. A leading part of it names a group of rows, and the page tells the
reader that the entry was removed. To mean the whole table, link the table.
To mean a row, write every parameter of it and open the link once. The
audit does not check what follows the `#`.

Evidence: 2026-09-14, T240 critique. `curl https://numberdb.org/Entropy_constants_of_lattice_models?entry=hard-core`
contains `alert-warning` "This table has no entry hard-core". `?entry=hard-core,line,kappa`
instead contains `table-block-focused` and scrolls to the row.

## A subscript made by `"$P_%d$"` is right up to 9 and wrong from 10

What happened: T240's generator names paths with `"path $P_%d$" % n`. The
rows for $n\leq 9$ read correctly. $P_10$, $P_11$ and $P_12$ typeset as
$P_1$ followed by a digit, because TeX takes one token as a subscript. The
stars beside them were right, since `"$K_{1,%d}$"` already had braces. A
preview of the first rows, which is what people look at, shows nothing
wrong.

What the skill says now: nothing.

What it should say: brace every subscript and superscript that a generator
fills with a number, `$P_{%d}$`. When previewing generated comments, look at
the row with the largest index as well as the first rows.

Evidence: 2026-09-14, T240 critique. The stored entry comment of
`K@GOOGA?Q@OA` is `This is the path $P_12$.`, and the same holds for $P_{10}$ and
$P_{11}$.

## Plain text does not rescue every graph6 key from the code-span rule

What happened: the pending proposal `20260913T225624Z-critique.md` says to
put a key that may contain a backtick in plain text, not in a code span.
T240 repeated T237's `` "`%s`" `` and broke 26 comments. I sent the plain-text
form to `/preview`, and 3 of the 26 still broke. The renderer's
`` `([^`]+)` `` applies to any two backticks in a comment, not only to
backticks the author wrote as markup. So `I???P`D`_` in plain text renders
as `I???P<code>D</code>_`, and so does a sentence naming `J????CKo`b?` and
`J???G?H_r`?`, pairing across the two keys. No form of prose shows those
keys correctly. `&#96;` reaches the browser as a backtick, because prose is
not escaped, but it stores HTML in the data.

What the skill says now: nothing. The pending proposal says plain text is
safe.

What it should say: in prose, a key with two or more backticks in the same
sentence cannot be shown correctly, whether it is written as code or as
plain text. Count the backticks in the whole generated comment, not in
each key. Write a comment that names such keys as plain text only when the
comment has at most one backtick in total, and check the rest in the
preview.

Evidence: 2026-09-14, T240 critique. A `/preview?table=` piece with the
comment "plain: It has the same independence polynomial as I???P`D`_."
rendered `I???P<code class="prose-code">D</code>_.`. Over T240's 211
shared-value comments, 26 name a key with a backtick, and 3 of those have
two or more backticks in the sentence.

# Proposed from the T321 critique, 2026-09-18

## The page draws Formulas before Comments, so notation defined in a comment is undefined where a formula uses it

What happened: T321's document writes its sections in the order `Definition`,
`Parameters`, `Comments`, `Formulas`, so in the document the symbol $U_p$ is
introduced -- "If $U_p(x)=\sum_{j=0}^{p-1}u_jx^j$, then ..." -- before the
formula that uses it. The rendered page reverses the two blocks. What a reader
gets is

    Formulas
    (2)  If $\|U_p\|_4^4$ denotes the integral of $|U_p(z)|^4$ over $|z|=1$ ...
    Comments
    (6)  If $U_p(x)=\sum_{j=0}^{p-1}u_jx^j$, then $U_p(x)=1+f_p(x)$ ...

and $U_p$ is undefined at the only place it matters. Nothing refuses this and
nothing warns: `audit_table` has a "notation used in a formula and defined
nowhere in the table" check, satisfied by a definition *anywhere* in the
document, and a separate check for prose that says "the comment below", which
this formula does not say. Its message for that second check is the sentence
that names the trap -- "The page draws Formulas before Comments, whatever order
the document is written in, so a reader who looks where they are told may not
find it" -- and the commoner case is the author who does not tell the reader
anything, because in the document the definition was already above.

A contributor on their own laptop hits this the first time they write a
document in a sensible narrative order and read the published page. It is not
about this deployment: it is the site's fixed section order, the same for
everybody.

What the skill says now, under "Where each thing goes": "**Define notation
where you use it.** A comment saying the values are `U_n(x,-1)` is useless
until something says what `U` is. If a symbol appears in a formula or a
comment, its definition belongs in the same table." The last three words are
what needs strengthening: in the same table is not enough, because the reader
reads in the page's order and not the document's.

What it should say, added to that paragraph: the page draws sections in a fixed
order -- Definition, Parameters, Formulas, Comments, Programs, Similar tables,
References, Links -- which is not the order the document is written in, and
`Formulas` comes before `Comments`. A symbol a formula uses must be defined in
the Definition or in that formula's own sentence; a definition parked in a
comment is below the formula on the page however the YAML is arranged. Check it
by reading the rendered page, not the document.

Test, if this is promoted: assert the sentence naming the Formulas-before-
Comments order is in `SKILL.md`.

## A searched decimal is a point, not the interval its last digit denotes, so `3.14` does not find $\pi$

What happened: the T321 critique wanted to know whether a reader arriving with
a merit factor would find the table, so it asked the corpus for numbers it
already holds, through `GET /api/search?expression=...` -- the endpoint the
Advanced search page uses. On public tables, on 2026-09-18:

    -691/2730                       1 result   (T13, Bernoulli numbers)
    -0.253113                       0
    -0.2531135531                   0
    -0.2531135531135531             1 result   (T13)
    1/6                            11 results
    0.1666667                       0
    0.16666666666666669            11 results
    3.14                            0
    3.14159                         0
    3.141592653589793               7 results  (T7, T20, T27, T29, T59, ...)
    3.1415926535897932384626433832795   7 results
    pi                              7 results
    4.5                             1 result   (T130, which stores 9/2)

and, with explicit intervals,

    [3.1, 3.2]                      1 result   (T177)
    [3.14, 3.15]                    0
    [3.1415926535, 3.1415926536]    0          -- and this one contains pi
    [4.4, 4.6]                      0
    3.14 +/- 2e-2                   "Could not parse expression: invalid syntax"

Two rules account for all of it. A bare decimal in a *query* is an exact
literal, a point, and not the interval its last place denotes -- `4.5` finds
the stored `9/2` because 4.5 is exactly 9/2, while `[4.4, 4.6]`, the interval
that decimal is said to denote, finds nothing. And a match requires the query
to lie **inside** the stored enclosure, not to overlap it: an interval
*containing* $\pi$ matches nothing, and `3.14` misses T7's hundred digits of
$\pi$ while `pi` and a 32-digit decimal both hit it. For an exact rational the
stored enclosure is about as wide as a double, which is why
`0.16666666666666669` finds 1/6 and `0.1666667` does not.

So the reader has to know the number at least as precisely as the table does.
That is the opposite of what the storage convention suggests to a contributor
reading the skill:

> `3.14` -- the interval [3.13, 3.15] ... This convention is the whole reason a
> hundred digits means something: `3.14` *is* an interval, so a table never has
> to say separately how far to trust it.

The convention is right about *storage*. It does not describe the search box,
and the two sentences are next to each other in a contributor's head.

Why it belongs here rather than in `docs/agent-environment.md`: it is not about
the build box or the containers. It is how numberdb.org answers a contributor
on their own laptop, and it changes what they do. Section 1 of the skill tells
them to search the database before writing anything; a contributor who checks
"is my family already here?" by pasting four decimal places is told no when the
answer is yes, and `search_text` is the call that answers that question. It
also changes what a table is worth publishing at: digits are what makes a table
reachable, and a value stored to six places can be found only by somebody who
has it to six places.

What the skill should say, in section 5 beside the storage convention: a
searched number is a point and must fall inside the stored enclosure, so a
reader finds a value only if they know it at least as precisely as the table
stores it. Search a family by text, not by a rounded value.

Two caveats for whoever reads this. First, I did not find the code path that
sets the tolerance; the reading above is behavioural, measured against the live
site on 2026-09-18. Second, if the asymmetry is judged a bug rather than the
intended behaviour, the right home for it is an issue against the site, and the
skill should say only what a contributor should do in the meantime.

Test, if this is promoted: assert the sentence about a searched number being a
point inside the stored enclosure is in `SKILL.md`.

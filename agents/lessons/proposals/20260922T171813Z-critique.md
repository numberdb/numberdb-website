## Checking your table's TeX: MathJax does not raise, it returns an `merror`

What happened: T411's prose was checked by pulling every `$...$` fragment out
of the document and typesetting it with `mathjax-full` in node, which is what
the T221 note in this repository describes. The first script wrapped
`doc.convert(tex)` in `try`/`catch`, counted the exceptions, and appended one
deliberately broken control, `$\frac{1}{$`, so that a run reporting zero would
be known to be measuring something. It reported

    checked 32 errors 0 (one error expected: the control)

which is the control failing silently: `mathjax-full`'s `doc.convert` does not
throw on a TeX error. It catches the `TeXError` itself and returns a node
containing an `<merror>`, and the message only appears once the node is
serialised. Probed directly:

    A: convert only                 -> no throw
    B: convert then outerHTML       -> no throw, html has merror: true

So the check has to look at the output:

```js
const node = doc.convert(tex, {display: false});
const html = adaptor.outerHTML(node);
if (/merror|data-mjx-error/.test(html)) { /* broken */ }
```

With that, the same 32 fragments still passed and two of three controls --
`$\frac{1}{$` "Missing close brace" and `$x^{$` "Extra open brace or missing
close brace" -- were caught. The third, `$\notacommand{x}$`, is *not* an
error under `AllPackages`: an unknown macro is typeset as text, which is what
the browser does too, so it is not usable as a control.

What the skill says now: nothing about checking TeX offline. Section 10 says
to check values against something independent and that "a measurement needs a
control that returns a known answer", which is the rule this breaks; it does
not say that the commonest way to typeset-check a table has a control that
passes when it should fail.

What it should say: a contributor who typesets their own fields before
publishing -- the cheap way to catch the `<` that eats a section, the brace
that never closes, the backslash a JSON round-trip ate -- must assert on the
rendered output containing no `merror`, because `doc.convert` returns rather
than raises. And the general form of the rule, which is already in the skill
for numerical controls and belongs beside it here: a control that cannot
distinguish "nothing broken" from "nothing measured" has confirmed nothing.
An undefined macro is not a broken one.

Evidence: 2026-09-22, T411 critique. `/tmp/mj352/probe.js` printed
`A: no throw` and `B: no throw, html has merror: true` on `\frac{1}{`;
`/tmp/mj352/check411.js` (catch only) printed `checked 32 errors 0` with the
control included, and `/tmp/mj352/check411b.js` (merror test) printed
`checked 32 fragments + 3 controls; errors 2`. mathjax-full 3, node 22.

## A table whose parameter is a physical strength wants the conversion to the other kinetic normalisation

What happened: T411 stores eigenvalues of $-y''+(x^2-a^2)^2y=Ey$ and its
definition says, correctly and prominently, "with no factor of $\tfrac12$ on
the kinetic term". That sentence tells a reader that their number will not
match. It does not tell them what would. For the half convention,
$-\tfrac12 y''+(x^2-a^2)^2y=\tilde E y$, the relation is

$$\tilde E_n(a) = 2^{-2/3} E_n(2^{1/6}a),$$

so the row a reader needs is at $2^{1/6}a$, which is irrational for every
rational $a$ and therefore never in the table. The skill's own test for
whether a family is covered -- "a reader with a number tries a half, a two, a
pi, and stops" -- is failed, and failed invisibly, because the argument moves
as well as the value.

This is not special to one table. Every Schrödinger-operator table in this
corpus states a kinetic normalisation and none states the map to the other
one, and the map is never a factor anybody guesses: the scaling that removes
the $\tfrac12$ rescales the potential too, so it lands on a different
parameter.

What the skill says now: "Which normalisation, branch, and indexing" must be
decided and stated, with `elliptic_k`'s $m$ against $k$ as the example -- two
conventions of the same *argument*, where the values coincide and only the
labelling differs. And: "Where two entries are one object in two conventions,
one table", whose test is invertibility.

What it should say: stating the normalisation is half the job. Where the
competing convention rescales the *argument* as well as the value, the
conversion is not a table's worth of second rows -- the other convention's
arguments are not in your parameter set at all -- so it belongs in `Comments`
as an identity the reader can apply, naming which quantity is which. A
sentence a reader can compute with is worth more than a sentence that warns
them off.

Evidence: 2026-09-22, T411 critique. Derived from the table's own two
formulas and checked against the control in its attached `generate.py`,
`_check_ronto_pollak_scaling`, which runs the same conversion at
$a^2=6\cdot2^{-2/3}$ to compare with $-\tfrac12 y''+x^4-6x^2$; both routes
give $\tilde E = 2^{-2/3}(E_n(a)-a^4)$ for the unshifted potential.

## `/tables` lists the whole corpus for nothing; walking the T-numbers spends an allowance and still misses tables

What happened: this run began by walking `numberdb.table('T1')` to
`numberdb.table('T299')` to see what the corpus holds, which is what the
skill says to do. It answered for 298 tables, and then every further API
call -- with the key as well as without it -- returned `too many requests;
retry in 1860s` for the next half hour, so `search_text` was unavailable for
the whole screening step.

Worse than the wait: the walk stopped at the number I picked. `/tables`,
fetched as an ordinary web page, listed **353** tables, and the 55 the walk
never reached included T302 *Newton-Cotes weights* and T328 *Lebesgue
constants of the classical interpolation node families* -- the first two
tables this batch was about to propose. A corpus survey that stops at a
guessed upper bound reads exactly like a complete one.

What the skill says now: "there is no call that lists the corpus, so to see
everything you walk the T-numbers", and separately that `search_text`
returns an object with a `.tables` list.

What it should say: the site's own pages are rendered server-side and are not
rate limited; only `/api/*` is. So

    https://numberdb.org/tables           # every table, paginated, free
    https://numberdb.org/tables?page=2    # and so on
    https://numberdb.org/T133             # one table's prose, free

give the corpus listing and each table's definition, conventions, formulas,
`Similar tables` and completeness note without touching the allowance. The
API is then worth spending on what only it answers: the entries themselves,
and `search_text`, which reaches definitions and comments that a title
listing does not. The anonymous allowance is 60 requests an hour, so a
contributor who walks T-numbers gets sixty tables and a wall; the listing
page costs one request per fifty-odd tables and cannot stop early at a
number the reader guessed.

Evidence: 2026-09-20, ideation for the w4 campaign.
`numberdb.table('T300')` and eight others, all `RateLimitError: too many
requests; retry in 1860s`, immediately after the walk; the same URL with
`X-API-Key` set, `HTTP Error 429`. `curl -s https://numberdb.org/tables`,
200, 23158 bytes, 57 table links; eight pages give 353 distinct T-numbers.
`numberdb_app/throttle.py`: `ANONYMOUS_LIMIT = 60`, `IDENTIFIED_LIMIT =
1000`, `WINDOW_SECONDS = 3600`, and the module docstring, "Only ``/api/*`` is
limited."

## A table's `Programs` line is not its range, and the range is what a companion table must inherit

What happened: this batch proposes companion tables for the classical
orthogonal polynomials, and the rule it adopted was to inherit the degree
range of the table being companioned. T101's `Programs` line reads
`polynomials = {n: legendre_P(n,x) for n in [0..100]}`, and T102's, T103's
and T98's say `[0..100]` too, so `n <= 100` looked like the house range. It
is not T101's range: T133, the one companion table that exists, records in
its completeness note that it holds "every $n\leq 50$ ... the range of the
table of Legendre polynomials". A build that inherited 100 would have
published twice the family it was matching, and the mismatch would only show
when a reader followed the link.

What the skill says now: `Programs` is "the standard incantation in Sage,
PARI or mpmath for a reader who wants one more value", and the range that is
actually there belongs under `Data properties` as `complete-note`. Both true,
and neither says what to do when you are reading somebody else's table.

What it should say: when a new table inherits a grid from an existing one,
read the grid from `complete-note`, not from `Programs` -- the program is an
example a reader can run, and its bounds are frequently rounder than the
table's. Where the older table has no `complete-note` (T101, T102, T103 and
T105 have none), the range has to be read from the entries themselves, which
means the API and not the page, since the entry block is loaded by script.
The cheapest reliable source is a sibling that already states it, which is
how T101's 50 was found.

Evidence: 2026-09-20. `https://numberdb.org/T133`, "Table is complete: no
(every $n\leq 50$ is here, the range of the table of Legendre polynomials)";
`https://numberdb.org/T101`, `Programs (P1) Sage polynomials = {n:
legendre_P(n,x) for n in [0..100]}` and a `Data properties` block with no
completeness note at all.

## A family can be unrepresentable at the type level because of the *scale* of a measure, not its shape

What happened: numberdb-data#93 asks for the secondary polynomials
$q_n(x)=\int (p_n(t)-p_n(x))/(t-x)\,\rho(t)\,\mathrm{d}t$ of each classical
orthogonal family, and T133 builds them for Legendre against the density
$\rho=1$, getting rational coefficients. The same construction against the
density each of the other tables declares -- $e^{-t^2}$ for T103,
$(1-t^2)^{-1/2}$ for T98, $(1-t)^\alpha(1+t)^\beta$ for T106 -- gives
coefficients that are $\sqrt\pi$, $\pi$ or a Beta value times a rational,
because $q_n$ is *linear in $\rho$* and those weights have irrational total
mass. There is no `R[]` type; the family is simply not storable until the
density is normalised to total mass 1, after which every coefficient is
rational again for every rational parameter.

What the skill says now: "What each value will be: an exact integer, rational
or polynomial, or an approximation", and the type table lists `Z[]` and `Q[]`
and no polynomial type over anything else.

What it should say: when a family is defined by an integral against a
measure, check the *scale* of that measure before choosing the type, not only
the shape of the integrand. A normalisation that is invisible in the
literature -- most sources write "the density $\rho$" and leave the mass
implicit -- can be the difference between a `Q[]` table and no table. And
when a corpus table already made that choice, as T133 did, the companion
tables inherit a factor: T133's entries are twice what the probability
density gives, which is not an error but is a relation every sibling must
state.

Evidence: 2026-09-20, ideation for the w4 campaign. The normalised moments of
$(1-t)^\alpha(1+t)^\beta$ on $[-1,1]$ are
$m_i=\sum_k\binom{i}{k}2^k(-1)^{i-k}(\beta+1)_k/(\alpha+\beta+2)_k$, rational
for rational $\alpha,\beta$; the unnormalised ones carry
$B(\alpha+1,\beta+1)2^{\alpha+\beta+1}$. T133's own `Similar tables` records
the same phenomenon from the other side: "the same construction for $T_n$
gives $\pi\,U_{n-1}$".

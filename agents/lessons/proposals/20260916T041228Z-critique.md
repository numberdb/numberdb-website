## Third instance of the pending `sage.all` lesson, and it is not a `-python` artifact

Not a new lesson. The proposal "A `Programs` snippet that imports from `sage.*`
submodules runs in a Sage session and not in a Sage script", in
`agents/lessons/proposals/20260916T024304Z-critique.md`, predicts T258's failure
exactly, and the T257 critique already recorded a second instance. Three
measurements are new, and each of them widens what the pending lesson has to
say.

**It is not about `sage -python`.** The first two instances were both measured
through `agents/sage.sh`, which runs `sage -python -u`, and the proposal's
sentence says so. A contributor writing a Sage program is at least as likely to
run `sage program.py`, which preparses and is the mode the `language: Sage`
label most naturally names. T258's stored snippet, saved verbatim, fails
identically in both, on line 1:

    $ sage -python p1.py          rc=1
    $ sage p1.py                  rc=1
    AttributeError: partially initialized module 'sage.rings.integer_ring'
    has no attribute 'ZZ' (most likely due to a circular import)

So the rule is "in a script", not "under `-python`", and the advice "check the
snippet in whichever of the two you did not write it in" should say that both
script modes are the same one of the two.

**The commonest opener in the corpus fails on its own.** A probe of single-line
scripts under SageMath 10.9, each run both ways:

| first line of the script | `sage -python` | `sage file.py` |
|---|---|---|
| `from sage.rings.integer_ring import ZZ` | fails | fails |
| `from sage.rings.rational_field import QQ` | fails | fails |
| `from sage.rings.polynomial...import PolynomialRing` then `ZZ` | fails | fails |
| `from sage.all import ZZ, PolynomialRing` | ok | ok |

`from sage.rings.rational_field import QQ` failing alone matters because it is
the single most common opener in this corpus's `Programs` blocks, and because
it fails with a *different* message — `ImportError: cannot import name QQ` —
which does not mention a circular import and so does not look like the same
fault. Reordering the imports does not help: the second row of the table is
`PolynomialRing` first, and it fails at the `ZZ` line.

**The scale.** This repository's generators carry 131 `Programs` snippets
labelled `Sage`. Sixty-nine import no Sage name at all and are unaffected. Of
the 62 that do, 61 open with a deep `sage.*` submodule import and one with
`from sage.all`. This is the house style, not one table's slip, and any
sentence the skill grows has to be read as changing the style rather than
correcting a mistake.

Why a contributor on their own laptop hits this: unchanged from the original
proposal. They test in a Sage session, where `sage.all` is already loaded and
every one of these imports works, and the reader who copies the block into a
file is the one who sees the error.

What the skill says now: §6 says the opposite, and for a reason —
"**Name the rings you use, rather than importing `sage.all`.** A modular
passagemath has no `sage.all` ... Importing `numberdb.sage` first is what makes
the direct imports work". That is right for a **generator**, which does import
`numberdb.sage` first and so is never a fresh interpreter. A `Programs` snippet
imports nothing of the sort, and the same rule inverts there. The skill does
not currently distinguish the two files, though §4 already says they answer
different questions.

What it should say: keep the named-ring rule for `generate.py`, and say beside
it that a `Programs` snippet is a standalone script — it does not import
`numberdb.sage`, so nothing has initialised Sage, and its Sage names must come
from `sage.all`. Check it by saving it to a file and running `sage file.py`,
which is what a reader does with it.

Evidence: 2026-09-16, T258. `/tmp/p1.py` (the stored snippet verbatim),
`/tmp/runp2.py` (five invocations), `/tmp/imp.py` (the import table above), all
through `agents/sage.sh` against SageMath 10.9; the working variant returns
`q^15 - q^13 - q^12 - q^11 + q^10 + q^9 + q^8 - q^6`, the stored $A_3$ row. The
61-of-62 count is over `generators/*/table.yaml`.

## A `sources` list is a claim about a document, and it is worth opening the document

What happened: T258 lists two sources, a Wikipedia article and Gerhard Hiss's
survey *Finite groups of Lie type and their representations*, and cites the
survey in its Definition. The survey is an excellent citation for the
definition — its §1.1.2 and §1.1.3 define finite groups of Lie type and name
every family the table holds. As a source of the table's *data* it carries five
of the sixteen order formulas, all in one Example on page 3, after which it
asks "Is there a systematic way to derive these formulae?" and goes on to
representations for thirty-seven pages. Two of the five are the $GL_n$ and
$GU_n$ orders, which are not the $SL_n$ and $SU_n$ orders the table stores. The
canonical source for exactly this table — Solomon, *The orders of the finite
Chevalley groups*, J. Algebra 3 (1966), 376–393 — is reference [72] of the
survey that was cited instead.

Nothing catches this. `audit_table --links` fetches a URL and checks that it
answers; it cannot ask whether the document behind it contains the numbers.

Why a contributor hits this: the natural way to pick a source is to find the
best-known modern writing on the subject, which is usually a survey. A survey
is the right thing to cite for *what the objects are* and often the wrong thing
to cite for *where the values come from*, and the two claims are made by two
different fields — `CITE{}` in the Definition, and the `sources` list under
`Data properties`. The bibliography of the survey is where the second one
usually is.

What the skill says now: "A reference is for citing, not for listing", and the
section table separates `Links` ("sources outside: Wikipedia, LMFDB, OEIS,
MathWorld") from `References` ("papers and books"). Nothing about `sources`
being a claim that has to hold.

What it should say: `sources` under `Data properties` names where the *values*
came from, which is a stronger claim than a citation in the prose. Open the
document and find the formulas or the table you took; if a survey gives the
definition and someone else gives the numbers, cite both, in the two places.
And a paper goes in `References` with a `bib` line, not in `Links` as a URL to
an author's homepage — that is the address in a table most likely to stop
answering.

Evidence: 2026-09-16, T258's critique. `pypdf` over the 40-page survey at
`https://www.math.rwth-aachen.de/~Gerhard.Hiss/Preprints/StAndrewsBath09.pdf`;
the order formulas occur exactly once, in Example 1.3 on page 3; "Solomon" is
in the bibliography as [72] and nowhere else in the text. `pypdf` is not in the
Sage image and `pip install`s into the throwaway in a couple of seconds, which
is enough to read a cited PDF in a run.

## Two draft tables can be checked against each other by an identity, before either is public

What happened: T257 (Poincaré polynomials $W(t)$ of the finite Coxeter groups)
and T258 (order polynomials $P(q)$ of the finite groups of Lie type) were built
in the same batch, from independent generators — one enumerates Coxeter degrees,
the other multiplies cyclotomic-shaped factors — and are related by

    P(q) = q^N (q-1)^rank W(q)

with `N` the number of positive roots. Reading both drafts through
`GET /api/table?id=...` with the owner's key and multiplying out the stored
*strings* with fifteen lines of integer polynomial arithmetic checked all 28
rows the two share. All 28 agree. That is a real independent check of both
tables, it needed no Sage, and it took one local script.

It also found the thing the critique reports: neither table points at the
other, though the identity is the most useful sentence either could carry for a
reader arriving from the other side.

Why a contributor hits this: a batch of related tables is the normal way this
corpus grows, and the skill already says a family with known identities gives a
free test suite — but it says it about identities *within* one family
(`L_n = F_(n-1) + F_(n+1)`). The cross-table case is stronger, because the two
sides were computed by different code, and it is available while both are still
drafts and neither can be checked against search.

What the skill says now: §10, "Check new values against something independent
... A family with known identities gives you a free test suite", with
within-table examples. §1 says to search the corpus for what a new table should
point at, framed as linking rather than as checking.

What it should say: the same, plus that when a batch builds two tables related
by an identity, the identity checks both — read the stored values of both
through the client and evaluate it on every row they share. A draft is readable
by its owner, so this works before either is public, and the `Similar tables`
line the check justifies is the one a reader gets the most from.

Evidence: 2026-09-16, T257 and T258. Both documents fetched with the zeta3 key;
`P(q) == q^N (q-1)^rank * W(q)` over $A_1$–$A_9$, $B_2$–$B_9$, $D_4$–$D_9$,
$E_6$, $E_7$, $E_8$, $F_4$, $G_2$: 28 agree, 0 disagree.

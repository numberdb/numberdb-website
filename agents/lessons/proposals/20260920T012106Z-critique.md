## A range is bounded by where the values stop being distinct, not only by the size limits

What happened: T286 holds the first 50 Pisot numbers in $(1,\varphi)$, an
infinite family that converges to $\varphi$. Asked how far it could grow, the
obvious answer is "1200 entries or 320 KB, whichever comes first". Both are
wrong. The values close in on $\varphi$ geometrically, and the spacing between
*neighbouring* entries closes twice as fast as the distance to the limit
($0.2764\,\varphi^{-2n}$ against $0.4472\,\varphi^{-n}$, because the two
polynomial families agree to first order). Writing each value to the 100
significant digits the table stores, ranks 471 and 472 come out as the *same
decimal string*. A 100-digit table of this family cannot hold 472 entries, at
any size, ever.

The same arithmetic gives a second and tighter bound. Search matches by
interval overlap, and the query interval is never narrower than the
searcher's own precision: somebody arriving from a numerical computation has
a `double`, so about $10^{-16}$. The neighbouring gaps fall under that at
rank 73. Past there the table answers such a reader with two rows and no way
to choose between them.

What the skill says now: §3 "How much to include" bounds a range by how many
entries are common, by the entry count, the digit count and the block size,
and by how long the largest entry is to read. Nothing asks whether the values
are far enough apart to be separate answers. The nearest sentence is about
the opposite failure — "values that are a handful of small integers … match
everything and tell nobody anything".

What it should say: for a family whose values converge, the range is also
bounded by the point at which consecutive entries stop being distinguishable.
Two tests, and the second is the one that bites:

* **They must differ in the stored digits.** Two entries written the same way
  are one answer given twice. Compute the spacing between neighbours, not
  only the distance to the limit — for a family built from two subfamilies
  the neighbours can be quadratically closer than the family's own decay.
* **They should differ by more than a reader's precision.** Somebody arriving
  from a numerical computation has about 16 significant digits. Where the
  entries are closer together than that, the table can no longer say which
  one they have, and the extra rows make the answer worse rather than longer.

Evidence: T286 growth critique, 2026-09-20 (`agents/critiques/T286-growth.md`).
Measured under `agents/sage.sh`: building every Pisot number in $(1,\varphi)$
with $n\leq240$ (479 of them) takes 67 s; the first pair written identically
at 100 significant digits is ranks 471 ($P_{236}$) and 472 ($Q_{237}$); the
fitted spacing $0.276393\,\varphi^{-2n}$ matches the computed roots to six
figures for $n=20\dots100$ and predicts rank 471 exactly.

## An entry's comment can make the block quadratic, so extrapolating bytes per entry is wrong

What happened: T286's 50 entries occupy 13.3 KB, which is 267 bytes an entry
and suggests about 1200 entries inside the 320 KB soft limit. But each comment
carries the row's minimal polynomial, whose degree grows with the rank: at
rank 47 the comment is 251 characters, at rank 199 it is 937, at rank 467 it
is 2277. Measured properly, the block is 74.8 KB at 200 entries, 222.2 KB at
400 and 291.3 KB at 470 — the limit arrives at about a third of the
extrapolated count, and the skill's "aim at half the soft limit" target
arrives at rank 330.

What the skill says now: "A comment on every entry is part of the entries
block", with a measurement of one table at 166 KB with comments and 152 KB
without — a fixed overhead per row. And separately, "*Values that grow*: a
polynomial of degree n costs O(n²) characters and a table running to n costs
O(n³)", which is about the *values*.

What it should say: the growing thing may be the comment rather than the
value. Where the comment names an object whose size grows with the index — a
minimal polynomial, a discriminant, a defining equation — the block grows
faster than the entry count, and "bytes so far ÷ entries so far" understates
the cost of extending. Measure the block at the range you are proposing, by
building the entries, rather than scaling the one you have.

Evidence: T286 growth critique, 2026-09-20. Entries reconstructed in the live
table's wording and measured with the same `yaml.dump` call as
`numberdb_app/limits.py`: 13.0 KB at 50 ranks, 29.3 at 100, 74.8 at 200,
138.9 at 300, 222.2 at 400, 291.3 at 470.

## `search_by_expression` with a truncated decimal finds nothing, and that reads like "not in the database"

What happened: checking whether the corpus already held a value, I searched
through the API's expression endpoint — which is what
`numberdb.search_by_expression` calls — for the golden ratio and the plastic
ratio at several truncations:

    1.618033988749895     -> 5 tables (T32, T35, T153, T222, T297)
    1.61803398874989      -> nothing
    1.324717957244746     -> T222 and T286
    1.32471795724474      -> nothing

Sixteen correct significant digits match; fifteen do not. The failing queries
are not wrong, they are *short* — every digit typed is a correct digit of a
stored value. The endpoint **evaluates** what it is given, so a shortened
decimal is simply a different number, taken at about double precision, and a
stored value that differs in the next place is outside it. The site's own
search box does not behave this way: it reads a typed decimal as uncertain in
its last place, and `/suggestions?term=1.3247` finds the same row.

What the skill says now: §1 tells you to search the database before writing
anything and gives `search_text`. For numbers the client's own docstring
carries the principle — `search()` refuses a bare `float` because "a float
states no precision, so searching for one would invent an uncertainty it does
not have" — but nothing in the skill says that the same trap is waiting for a
*string* of digits handed to the expression search.

What it should say: to ask whether a value is already in the corpus, say what
you know rather than typing digits: `search_real_ball(centre, radius)`, or
`search_real_interval`. `search_by_expression('1.32471795')` answers "nothing"
for a value that is in two tables, and "nothing" is exactly the answer that
sends somebody off to build a table that already exists.

Evidence: T286 growth critique, 2026-09-20. `GET
https://numberdb.org/api/search?expression=…` and `GET
https://numberdb.org/suggestions?term=…` on the live site, the queries above.
Two different numbers in two different tables, same threshold.

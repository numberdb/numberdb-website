## A tag can exist and carry no table, and `numberdb.tag` says which

What happened: the batch was about to propose `spectral geometry` as a tag that
does not exist. It does exist.

    numberdb.tag('spectral geometry')  -> {'name': 'spectral geometry',
                                           'table_count': 0,
                                           'number_count': 0, 'tables': []}
    numberdb.tag('vibration')          -> Tag with url 'vibration' does not exist.
    numberdb.tag('geometry')           -> Tag with url 'geometry' does not exist.
    numberdb.tag('zzzz qqqq')          -> Tag with url 'zzzz qqqq' does not exist.
    numberdb.tag('number theory')      -> table_count 124
    numberdb.tag('statistical mechanics') -> table_count 16

So the call has three answers, not two: a record with tables, a record with
none, and an exception. The middle one is a name somebody already put in the
vocabulary that nothing is filed under -- which is a different thing to propose
than a new tag, and an easier one: nothing has to be agreed, the tables have
only to carry it.

It also matters the other way. A proposal that says "three or more tables would
carry a tag that is not in the tag list" is making a claim about the list, and
the only way to test the claim is to ask. Asking is one call and it changed the
section this batch wrote.

What the skill says now: "Prefer an existing tag; a tag list is a way through
the corpus and a tag with one table on it is not... propose a new one when
three or more tables would carry it." It does not say how to find out whether a
tag exists, and `numberdb.tag` is not mentioned in the tag paragraph at all.

What it should say: before proposing a tag, call `numberdb.tag('the name')`.
An exception means it is not in the vocabulary; a record with `table_count: 0`
means it is, and is unused, which is the strongest case for a batch to adopt a
name rather than coin one. Two-word tags are ordinary here -- `number theory`,
`statistical mechanics` -- so do not contort a name into one word.

Evidence: the six calls above, against the live site on 2026-09-23.

## A table's title names the objects; only the `Definition` says what is stored

What happened: this batch claims that the Neumann eigenvalues of the unit disk
are squares of entries of T22. T22 is titled *Local extrema of Bessel functions
of the first kind $J_\alpha$*, and on the title alone the entries would be the
extreme values $J_\alpha(j'_{\alpha,n})$ -- numbers between $-0.5$ and $0.6$,
whose squares are nothing to do with an eigenvalue. The claim would have been
wrong in a way that survives every screen, because `already_here` matches
titles and the screen has no opinion about what a table holds.

The `Definition` settles it in one line:

    Title:      Local extrema of Bessel functions of the first kind $J_\alpha$
    Definition: The list contains the first zeros of the derivative of
                Bessel functions of the first kind $J_\alpha$.
    Numbers:    alpha 0, n 2 -> 3.8317059702075123156...

The abscissae, not the values. So $(j'_{0,2})^2 = 14.6819706421239$, and T390's
`half-disk` Dirichlet entry is `14.6819706421238932572197777686` -- the same
number, because $j'_{0,k}=j_{1,k}$. That identity is now a check the build can
run on its first afternoon, and it exists only because the definition was read.

What the skill says now: it tells you to search the corpus and to link to
related tables, and `numberdb.table('T99')` is given as the way to see what a
neighbour holds. It does not say that the title can mislead about the quantity.

What it should say: when a proposal or a build asserts an identity to a table
that already exists -- "these are the squares of T22", "this is a rational
multiple of T94" -- read that table's `Definition` and one of its `Numbers`
before writing the sentence. A title names the *objects*; the definition names
the *quantity*, and in a family like zeros, extrema and turning points the two
differ by exactly the thing the identity depends on.

Evidence: `numberdb.table('T22')` and `numberdb.table('T390')`, 2026-09-23.

## `source_names_it` is exact about plurals, and the source usually has one of them

What happened: two candidate names were rejected for a word that was on the
page in the other number.

    "Clamped plate eigenvalues"   https://en.wikipedia.org/wiki/Vibration_of_plates
        -> the source does not mention eigenvalues
    "Clamped plate biharmonic eigenvalue"   same page
        -> OK

The page contains `clamped`, `plate`, `biharmonic` and `eigenvalue`, and does
not contain `eigenvalues`. The check tests membership of each word of the name,
so the singular passes and the plural does not, on the same page, for the same
family.

The same run, the other direction: "Steklov eigenvalues" passes against
arXiv:1411.6567, and "Steklov eigenvalues of planar domains" fails on `planar`
and `domains` -- a survey called *Spectral geometry of the Steklov problem*
says neither word in its abstract.

Both are worth reading rather than working around. A page about *plates* that
mentions "eigenvalue" once in passing is a page about the objects, not about
the spectrum, and a proposal citing it should find a spectral source as well --
which is the same lesson as the OEIS one in the 0921 run, arriving from the
other side. And the words the source will not say are the words to keep out of
`Keywords`, where they would be the ones a reader is least likely to type.

What the skill says now: "Cite a source for every proposal and run
`source_names_it` on it," with the five kinds of source listed.

What it should say: when `source_names_it` rejects one word, retry with the
singular or the plural before changing the citation -- and if only the passing
form appears, take it as a signal about the page, not about the check. A source
that carries your family's name in one number only is usually a source about
the objects rather than the quantity.

Evidence: the four screen calls above, 2026-09-23.

## Run the cheap root-finding before proposing; it produces the check and the ranking

What happened: five proposals here rest on transcendental equations, and
twenty minutes of mpmath under Sage turned every "there is a known closed form"
into a number with a published value beside it:

    cantilever, cos b cosh b = -1      1.87510406871196   4.69409113297417
    clamped-clamped, cos b cosh b = 1  4.73004074486270   7.85320462409584
    clamped-pinned, tan b = tanh b     3.92660231204792   7.06858274562873
    clamped disk, J0 I1 + I0 J1 = 0    k = 3.19622061658254, k^4 = 104.363105558844
    annulus 1:2, J0(x)Y0(2x)-J0(2x)Y0(x)   kappa^2 = 9.7533221247507149107

The last line is the one that changed the batch. T390's `annulus-1-2` entry is
`9.75332212475071491068952390873`: twenty digits of agreement between a
proposed table and a table somebody else built from the same equation, found
before any table was made, and it moved the cross-product proposal up the
ranking because its check is now free. The clamped-plate $k^2 = 10.2158$ is the
frequency parameter the engineering literature prints, so that row has a
published anchor too -- while the *square* plate has none I could verify, which
is what pushed that proposal to fourth.

What the skill says now: the 0921 run's lesson says to run the ratio test
before proposing a constant defined as a limit, because the digits it reaches
decide the rigour level and the build order.

What it should say: the same thing for a constant defined as the root of a
scalar equation, where it is cheaper still. Bisect it to thirty digits, then
search the corpus for the value -- not for the name. A family whose values are
already in the corpus under another name is the collision the name search
cannot find, and a family whose first value agrees with a stored one to twenty
digits arrives with its check already done.

Evidence: `/tmp/spec_checks.py` under `agents/sage.sh`, Sage 10.9, mpmath at 30
decimal digits, bisection to $10^{-40}$, 2026-09-23; compared against T390's
`annulus-1-2` and `half-disk` entries.

# Lesson proposed by triage 20260923T164413Z

## A 429 from `POST /api/tables` may be the draft ceiling, and waiting never clears it

What happened: triage needed to know whether a stalled campaign would be able
to create tables again once its writer was fixed, so it went looking for how
many drafts the account held. That turned up a refusal path worth writing down
for anybody, because the status code says the opposite of what is wrong.

An account may hold only so many unpublished drafts at once --
`permissions.py:268`, `DRAFTS_IN_FLIGHT`, fifteen by default, raised to
`BULK_DRAFTS_IN_FLIGHT` (100) for members of the bulk-drafts group. At the
ceiling, `api.py:984-999` refuses a new draft with **HTTP 429**:

    {"error": "This account already holds 15 unpublished drafts.",
     "detail": "Publish one, or abandon it, and then this will go through.
                The limit is on drafts in flight rather than on drafts made
                ..."}

429 is the rate-limit code, and the client reads it as one.
`clients/python/numberdb/_http.py:281-282` short-circuits every 429 into
`_from_status`, which builds a `RateLimitError` from the `Retry-After` header
and **discards the parsed `detail` from the body** that every other status code
gets at `:277-284`. This refusal carries no `Retry-After`, so the contributor
sees exactly:

    numberdb.RateLimitError: too many requests

That is a trap with no floor. The obvious response to a rate limit is to sleep
and retry, and no amount of sleeping clears this one: the count only falls when
a draft is published or abandoned. A loop that backs off and retries will back
off forever while the real message sits unread in the response body.

Seeing the count is awkward but possible, and the skill should say how. There
is no API that lists drafts: `/drafts` is an HTML page that redirects an API
key to a login form, and the JSON API has no drafts route. But a table is a
draft exactly when its public page 404s while `GET /api/table?id=T<n>` returns
it to an authenticated key -- drafts are readable by id, just absent from every
listing and every search. Walking a range of ids both ways gives the answer.

What the skill says now: nothing about a ceiling. The publishing walkthrough
says "**Propose it as a draft** -- `POST /api/tables` with `X-Draft: yes`" and
"A draft is invisible, in no listing, answers no search", and leaves the reader
to think the only limits are on size. Nothing anywhere mentions that drafts in
flight are counted, that the count is enforced at creation, or that the
enforcement arrives as a 429.

What it should say: in the publishing section, that drafts in flight are
capped, that the cap is on drafts *held* rather than drafts made, and that the
way out is to publish or abandon one rather than to wait. And where the skill
covers errors: that a `RateLimitError` from the client is not proof of a rate
limit -- 429 is also how the draft ceiling refuses -- so read
`error.read()`/the response body, or check `GET /api/table?id=` against the
public page to count what you hold, before sleeping on it.

Evidence:

* `numberdb_app/permissions.py:268-335` -- `DRAFTS_IN_FLIGHT = 15`,
  `BULK_DRAFTS_IN_FLIGHT = 100`, `draft_allowance`,
  `may_create_drafts_through_api`.
* `numberdb_app/api.py:984-999` -- the 429 and its body.
* `clients/python/numberdb/_http.py:277-299` -- 429 routed to `_from_status`,
  `detail` dropped, `RateLimitError("too many requests")` when there is no
  `Retry-After`.
* `numberdb_app/views.py:375-379` -- `/drafts` redirects an unauthenticated
  request to the login form; it is not an API.
* Measured against the live site, 2026-09-23 17:00Z: walking `T360`-`T450`,
  22 tables answer `GET /api/table?id=` while their public page 404s. The
  account creating them held at least 17 when its next creation succeeded, so
  the ceiling in force there is the bulk one, not the default.

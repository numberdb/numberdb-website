## Run the `Programs` snippet as it is *stored*, not as you wrote it: one escaping level eats the comment marker, and nothing on the site checks it

What happened: T366 stores a PARI/GP incantation that ends with a comment
giving the expected answer, in the shape T161 uses:

    bestappr(lfun(lfuncreate(x^4 - x^3 - 3*x^2 + x + 1), -1), 30)    \\ 2/15, for D = 725

What reached the document was one backslash, not two. The code was written in
a Python string inside a script that posted the table as JSON, and `"\\ "` in
the source is one backslash by the time GP sees it; T161, built the same way,
has `"\\\\ "` and is right. GP's comment marker is `\\`; a single `\` is
Euclidean division, so the stored line is not a commented-out answer, it is an
expression. Fed the two stored lines exactly, `gp -q` prints no value and

    ***   syntax error, unexpected ',', expecting end of file:
      ***   ...3-3*x^2+x+1),-1),30)\2/15,forD=725

With the backslash doubled it prints `2/15`, the stored entry for $D=725$.

Nothing catches this. `audit_table` never reads `Programs` code — it checks
the *attached generator* for install and run lines and says nothing about the
snippet — so `GET /api/table/T366/audit` answers `"clean": true` on a table
whose one runnable thing errors on its first line. `verify` checks numbers,
not prose. The author is the only check there is.

The same trap is one level wider than PARI: any `Programs` block whose language
uses a backslash — a `\\` GP comment, a `\n` in a shell line, LaTeX inside a
Sage docstring — passes through the escaping of whatever wrote the document,
and what a reader pastes is the string that survived, not the string that was
typed.

What the skill says now: section 4, "`Programs` and `generate.py` answer
different questions. `Programs` is the standard incantation in Sage, PARI or
mpmath for a reader who wants one more value." Nothing about testing it, and
nothing about escaping.

What it should say: before publishing, read the `Programs` code back out of
the stored document — `numberdb.table('T…')`, or `GET /api/table?id=T…` — and
run *that* text, character for character, in the interpreter it names. It
should print the value the comment claims. Do not run the copy in your build
script: one level of escaping stands between the two, and the site checks
neither. A snippet that ends with the expected answer as a comment is a good
habit precisely because it makes this testable.

Evidence: 2026-09-20, T366 critique. `GET /api/table?id=T366` gives
`'…, 30)    \\ 2/15, for D = 725'` in Python `repr`, one backslash;
`/tmp/gp366.py` under `agents/sage.sh` ran both forms through
`/home/sage/sage/local/bin/gp -q` and got the syntax error above from the
stored one and `2/15` from the doubled one. T161's stored code, fetched the
same way, has two. `GET /api/table/T366/audit`: `{"findings": [], "clean":
true}`.

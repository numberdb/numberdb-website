# Lessons proposed by run 20260923T154348Z (triage)

## Do not name a scratch file `numbers.py`: it shadows the standard library and the traceback never mentions your file

What happened: a triage put a throwaway script beside some others in a scratch
directory and `import numberdb` died before reaching the network:

    AttributeError: module 'numbers' has no attribute 'Number'

Nothing in the traceback names the offending file. The frames are
`fractions.py` and `decimal.py`, both standard library, so the obvious reading
is that the Python installation is broken -- or, on this project, that the
client is at fault, because `numberdb` is the thing that failed to import. The
actual cause was a one-line file called `numbers.py` sitting in the same
directory, left over from an earlier session.

Python puts the *script's own directory* first on `sys.path` -- not the
current directory, the script's -- so any `.py` there beats the standard
library of the same name. The minimal case needs no third-party code at all:

    $ cat numbers.py
    # my scratch notes on numbers
    $ cat t.py
    import decimal
    print("ok")
    $ python3 t.py
    Traceback (most recent call last):
      File "/tmp/scratch/t.py", line 1, in <module>
        import decimal
      File "/usr/lib/python3.12/decimal.py", line 3, in <module>
        from _decimal import *
    AttributeError: module 'numbers' has no attribute 'Number'

`decimal` imports `numbers`, gets the scratch file, and finds no `Number` in
it. Deleting `numbers.py` fixes it with no other change.

This matters here more than it would elsewhere, for two reasons. The first is
that `numbers.py` is the most natural name a contributor to a *database of
numbers* will reach for, and so are `fractions.py`, `decimal.py`,
`statistics.py`, `types.py` and `random.py` -- every one of them is a
standard-library module, and every one of them is a plausible name for a
generator's helper. The second is that the client is a direct casualty:
`numberdb` imports `fractions`, which imports `decimal`, which imports
`numbers`. So the symptom a contributor sees is "the NumberDB client will not
import", pointing at exactly the wrong thing.

The failure is also sticky in a way a syntax error is not. A harmless-looking
file is enough -- it does not have to contain anything wrong.

**And if the shadowing file has side effects, they happen, and their output
looks like yours.** This is the part worth the warning. A second scratch file
in the same directory, `inspect.py`, was not notes but a working script: it
began `import screen, json`, then `import numberdb`, then fetched four tables
and printed them. Importing *anything* that reaches `inspect` -- which
`dataclasses` does, which most of the standard library does -- executed it.
The triage ran a script to list its drafts and got back a neat banner of
`T147`, `T150`, `T402` with their definitions and entry counts, and read that
for a moment as the answer to the question it had asked. It was not. It was a
different script's output, about four hard-coded table ids, printed during an
import, before the triage's own first statement ran. The real result was the
`TypeError` several lines further down.

So the symptom is not always an error. It can be plausible, well-formatted,
entirely wrong output that belongs to somebody else's file.

What the skill says now: nothing. It says to keep scratch out of the
repository, and names no constraint on what the scratch may be called. The one
adjacent note in `PROPOSALS.md` is about `from sage.all import *` shadowing
standard-library names *inside* a module, which is a different mechanism --
that one is a namespace collision at runtime, this one is an import-path
collision before your first line runs.

What it should say: name your working scripts so they cannot collide with the
standard library -- `check_values.py`, not `numbers.py`. If an import that
worked yesterday starts failing inside a standard-library file, or if a script
prints something you did not write, run `ls *.py` in the script's directory
and compare against
`python3 -c "import sys; print(sys.stdlib_module_names)"` before suspecting
your installation or the client. `numbers`, `fractions`, `decimal`,
`statistics`, `types`, `random` and `inspect` are the ones this corpus tempts
you into. Putting each piece of work in its own directory is the cheap
prevention; a shared scratch directory accumulates these and they outlive the
session that made them.

Evidence: reproduced on 2026-09-23 under Python 3.12 on Ubuntu.

  * With `numbers.py` present in the script's directory, `import numberdb`
    (from `clients/python`) raises
    `AttributeError: module 'numbers' has no attribute 'Number'`;
    `rm numbers.py` and the same script prints `client ok`.
  * The two-file minimal case above needs no third-party code: `import
    decimal` alone is enough to trigger it.
  * `sys.path[0]` is the script's directory, not the working directory:
    `python3 /path/to/shadow3/t.py` fails identically when run from
    `/home/ubuntu/numberdb-campaign-w4`, a directory containing no
    `numbers.py`.
  * The side-effect case: with `/tmp/inspect.py` present (791 bytes, first
    line `import screen, json`, then `import numberdb`, then a loop printing
    `T147`, `T150`, `T402`, `T151`), any script run from `/tmp` executed it
    during `import dataclasses` -> `import inspect`. A script that asked the
    API for something else entirely printed those four tables instead.

## OEIS serves its b-files to a script and refuses everything else

What happened: this run wanted to follow the 2026-09-20 lesson, "search OEIS
for a polynomial family too: it holds coefficient triangles", for four
proposed families of weight enumerators. Every search returned a 403 carrying
a Cloudflare page titled "Just a moment..." -- and so did the plain sequence
page `https://oeis.org/A000045`. The static b-files answer normally:
`https://oeis.org/A000045/b000045.txt` returns 200 and 429 KB of Fibonacci
numbers, and `https://oeis.org/A305474/b305474.txt` returns 200 and the Hilbert
class polynomial coefficients that lesson was about. So a script can *check*
against an A-number it already knows, and cannot *find* one.

The failure mode is the dangerous part: a screen that fetches a page and looks
for the family's name in it gets a 5 KB HTML document that mentions none of the
words, which is indistinguishable from a real source that does not name the
family. An empty OEIS search and a blocked OEIS search look identical too.

What the skill says now: it names OEIS as a link target and as a place to look
for a coefficient triangle. It does not say that only one OEIS URL shape is
reachable without a browser.

What it should say: check against `https://oeis.org/Annnnnn/bnnnnnn.txt`,
which is a plain text file of `index value` lines and is the thing to compare a
table against anyway. Find the A-number in a browser; a search from a script
will be refused, and the refusal is an HTML page rather than an error, so a
script must treat a response whose title is "Just a moment..." as a failure and
not as an answer.

Evidence: 2026-09-21. `curl -s -A "Mozilla/5.0" -o /dev/null -w "%{http_code}"`
gave 403 for `https://oeis.org/A000045`, 403 for
`https://oeis.org/search?q=1,759,2576,759,1&fmt=text`, 403 for
`https://oeis.org/search?q=id:A000045&fmt=json`, and 200 for
`https://oeis.org/A000045/b000045.txt` and
`https://oeis.org/A305474/b305474.txt`.

## The arXiv API refuses `Python-urllib` with 406 and accepts any other agent

What happened: looking for a source that names the Duursma zeta polynomial,
`urllib.request.urlopen('https://export.arxiv.org/api/query?...')` raised
`HTTPError: HTTP Error 406: Not Acceptable`, over both http and https and for
every query. The same URL through `curl -A "Mozilla/5.0 numberdb-screen"`
returned the Atom feed at once. The API filters on the User-Agent, and the
default one Python sends is on its list.

This matters beyond one run: an arXiv abstract page is often the only stable
public source that names a research-level family, and a contributor writing a
check or a screen in Python will meet this before they meet any mathematics.

What the skill says now: nothing. It names Wikipedia, LMFDB, OEIS, MathWorld
and "a paper" as link targets and says nothing about fetching any of them.

What it should say: set a User-Agent on every request a script makes. One line,
`urllib.request.Request(url, headers={'User-Agent': '...'})`, and it is the
difference between an answer and a 406 that reads like the paper not existing.

Evidence: 2026-09-21. Three queries, all `HTTP Error 406` through urllib with
its default agent; all three answered through curl with an agent set, returning
`arXiv:math/0302172`, "Results on zeta functions for codes", I. M. Duursma.

## A family defined by uniqueness gives no internal sign that you solved for the wrong thing

What happened: proposal 3 of this batch is the extremal weight enumerator of a
Type II self-dual code -- the unique element of Gleason's ring
$\mathbb C[W_8,W_{24}]$ with $A_0=1$ and $A_i=0$ for $0<i<4\lfloor
n/24\rfloor+4$. The first computation assembled the linear system wrongly, and
returned, at $n=24$,

    1 + 42x^4 + 591x^8 + 2828x^12 + 591x^16 + 42x^20 + x^24

which has every property one would check in passing: integer coefficients, the
right degree, the palindromic symmetry a self-dual code forces, coefficients of
a plausible size, and a unique solution to the system as posed. It is not the
answer. The answer at $n=24$ is the extended Golay code's enumerator,
$1+759x^8+2576x^{12}+759x^{16}+x^{24}$, and the wrong system had imposed the
vanishing at the wrong coefficients.

The general shape: when the definition is "the unique object with such and such
properties", a wrong system is still a system, and it still has a unique
solution that satisfies whichever properties you did impose. There is no
residual, nothing overdetermined, no warning. Every family of this shape --
extremal enumerators, interpolation conditions, a normalisation fixed by
vanishing conditions, a polynomial pinned down by initial values -- needs an
*anchor*: one member of the family whose value is known from somewhere else.

What the skill says now: "Check new values against something independent. Not
the code that produced them", and "a measurement needs a control that returns a
known answer". Both are about measurements and recomputations.

What it should say: the same rule stated for exact linear algebra, where it is
easier to skip because nothing is approximate and the answer looks exact. If a
family is defined as the unique solution of a linear system, name a member
whose value is published, and compute that one first. Here the anchors are
$n=8$ (the extended Hamming code), $n=24$ (the extended Golay code) and $n=48$
(the extended quadratic residue code), all three published, and the first of
them would have caught this in a minute.

Evidence: 2026-09-21, `/tmp/w3-ideas/codes_check.py` and `codes_check2.py`
through `agents/sage.sh`. The first printed `n=24 ... 1 + 42x^4 + 591x^8 +
...`; the corrected system reproduces the Golay enumerator that the same run
computed independently from `codes.GolayCode(GF(2))`.

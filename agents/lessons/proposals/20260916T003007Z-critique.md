# Lessons proposed by the T253 critique, 2026-09-16

Not in force. Format as in `agents/lessons/PROPOSALS.md`.

## Check a claim about another table by fetching that table once, not by looking up each value

What happened: T253's `comment-algebraic` says "Many of the simplest radicals
are also in [the table of algebraic numbers of degree 2]". To test it I started
sweeping the table's 193 distinct irrational values through
`GET /api/lookup?text=`. The anonymous limit is **60 requests per 60 minutes**,
and the sweep was cut off in its first minute; every later request, including
`GET /api/table?id=T35`, answered

    HTTP 429
    {"error": "Rate limit exceeded (60 requests per 60 minutes). An API key
     raises this limit; see /help#section-api.", "retry_after": 1109}

The body is JSON with a top-level `error` key, so a script that does
`json.load(...)['Numbers']` reports `KeyError: 'Numbers'` and reads like a
corrupt table rather than a throttle. `retry_after` was over eighteen minutes.

The right shape was one request. `GET /api/table?id=T35` returns the whole
document; T35's keys are `a2,a1,a0,n`, and reading them showed every
coefficient lies in $[-5,5]$. Since every irrational value in T253 is
$\sqrt{1/N}$, with minimal polynomial $Nx^2-1$, the overlap is exactly the
$N\le5$ cases: three values, on three of 485 rows. That settled a sentence that
193 lookups would have settled more slowly and less completely — the lookups
say which values are there, the document says *why the rest cannot be*.

What the skill says now: it teaches `search_text` and `table(...)` for finding
out whether a family is already held, and warns that `Numbers` is "every entry
the table holds" and that printing it is megabytes. It says nothing about rate
limits, and nothing about which of the two calls answers a question about
overlap.

What it should say: the public API is rate-limited (60 requests per 60 minutes
without a key; a key raises it), and a 429 comes back as JSON carrying `error`
and `retry_after` rather than as a table, so a script should check for `error`
before indexing. More usefully: a question of the form "do these values also
appear in table X" is a question about X's *range*, and one `table('TX')` plus
a local comparison answers it exactly, where per-value lookups answer it only
for the values you happened to try. Downloading `Numbers` is the cheap move
when the alternative is hundreds of requests; it is the expensive move only
when you meant to print it.

Evidence: 2026-09-16, T253 critique. The sweep script's 429s; the single
keyed fetch of T35 (852 entries); three of T253's 158 distinct magnitudes in
T35, against four of six spot-checks hitting for the same sentence in T252.

## `sage -python` cannot run `sage.functions.wigner` without `sage.all`, and the failure waits for the first irrational answer

What happened: T253's `Programs` snippet is

    from sage.functions.wigner import wigner_6j
    wigner_6j(1, 1, 1, 1, 1, 1)    # 1/6

Run under `sage -python` with named imports only, as the skill's generator
pattern prescribes, that line works and prints `1/6`. Every row whose value is
*not* rational then fails, in two different places depending on how much was
imported:

    from sage.rings.rational_field import QQ    # before Sage is initialised
    ImportError: cannot import name QQ          # the documented one

    from sage.functions.wigner import wigner_6j # initialises Sage
    from sage.rings.rational_field import QQ
    wigner_6j(QQ(1)/2, QQ(1)/2, 0, QQ(1)/2, QQ(1)/2, 0)
    AttributeError: module 'sage.rings' has no attribute 'real_mpfr'

    import sage.rings.real_mpfr                 # past that one
    ...
    NameError: name 'RR_1_10' is not defined    # in sage.rings.qqbar

The skill's own remedy for the first of those — "Importing `numberdb.sage`
first is what makes the direct imports work" — fixes the `ImportError` and not
the two after it: `import numberdb.sage as numberdb` followed by `QQ` and
`wigner_6j` still raises the `real_mpfr` `AttributeError`.

`import sage.all` first makes all of it work:

    (1,   1,   0,  0,   0,   1  ) -> sqrt(1/3)
    (1/2, 1/2, 0,  1/2, 1/2, 0  ) -> -1/2
    (7/2, 7/2, 3,  7/2, 7/2, 3  ) -> 31/616
    (1/2, 1/2, 0,  0,   0,   1/2) -> -sqrt(1/2)

The shape of the trap is that the *all-integer* call — the one a `Programs`
snippet is most likely to show, and the one I used to confirm the snippet — is
the one that succeeds, because `wigner_6j` returns a plain rational and never
enters the symbolic path. The half-integer and radical cases go through the
symbolic ring and `QQbar`, whose module-level globals only `sage.all` sets up.

What the skill says now: "Name the rings you use, rather than importing
`sage.all`", with a list of what named imports do not bring — root finding,
`RealBall.str`, and `QQ('1.25')`. `sage.functions` is not on that list, and
the pattern reads as though named imports always suffice.

What it should say: add to that list that anything routing through the
symbolic ring or `QQbar` — `sage.functions.wigner`, and the `functions`
package generally — needs `sage.all` under `sage -python`, and that it fails
late: a call returning a rational succeeds and the same function returning a
radical raises `AttributeError: module 'sage.rings' has no attribute
'real_mpfr'` or `NameError: RR_1_10`. When a `Programs` snippet is the thing
being checked, run it on a row whose value is irrational as well as one whose
value is rational, or the check passes on the easy half. (T253's own generator
is unaffected: it computes Racah's sum itself from `ZZ`, `QQ` and
`RealBallField`, and never touches `sage.functions`.)

Evidence: 2026-09-16, T253 critique. Six runs under `agents/sage.sh`:
`/tmp/t253_prog.py` (integers only, printed `1/6`), `/tmp/t253_prog2.py`
(`ImportError: cannot import name QQ`), `/tmp/t253_prog3.py` and
`/tmp/t253_prog4.py` (`AttributeError: ... real_mpfr`, the second with
`import numberdb.sage` first), `/tmp/t253_prog5.py` (`NameError: RR_1_10`),
`/tmp/t253_prog6.py` (`import sage.all`, all six rows printed).

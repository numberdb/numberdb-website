# Lessons proposed by the T346 critique, 2026-09-20

Format as in `agents/lessons/PROPOSALS.md`. Nothing here is in force. A person
promotes a lesson as a diff to the skill together with a test in
`numberdb_app/test_skill.py`.

Both of these are reachable by somebody with Sage on their own laptop and a
`generate.py`: one is what a named Sage import does not bring, the other is
what the client writes.

## A complex value that is really a real number writes its zero part as `[0, 0]`

What happened: T346 stores the roots of division polynomials as `type: C`. Its
generator takes exact roots in `QQbar` and coerces each into
`ComplexIntervalField(350)`, which is the right thing for the complex ones.
But 188 of its 588 roots are *real*, and a Sage complex interval whose
imaginary part is exactly zero goes through the client's interval writer like
any other component, so the value that reaches the page is

    4.34630815820539442196949079058342587368667471444835624064974603476864218…
        + i * [0, 0]

That is not a bug and it is not unsearchable: `utils/utils.py` parses
bracketed components deliberately, and `numberdb_app/test_interval_spelling.py`
pins the spelling. It is a *claim*, and the wrong one. That test file states
the distinction the corpus keeps: "a zero-width interval is written as an
interval — `[3/2, 3/2]`, not `3/2` — so that the page says which of the two
things it is: a value declared exact, or interval arithmetic that landed on a
point. Both assert the same number; only one is a rational." Here the
generator *knows* the root is real — `QQbar` knows it exactly — and the page
says interval arithmetic merely landed on zero.

The fix is one line and the package already has the type for it. Writing each
component by its own rule is what `numberdb.ComplexInterval` is for, and its
docstring says so ("exact on one axis and an approximation on the other"):

    from fractions import Fraction
    return numberdb.ComplexInterval(interval_of_the_real_part, Fraction(0))

which writes `4.34630… + i * 0` — the spelling the published complex table
T317 uses for the mirror case, `0 + i * 3.46410161513775…`.

What the skill says now: section 5 gives the complex form as
`0.309... + i * 0.951...` and the four real forms including `[2, 2.3728596]`,
and section 2 says "Decide exactness from the definition, never from the
digits." It does not say that a *component* of a complex value is written by
the same rules as a real one, and it does not say that a `CIF` element carries
its exactly-zero part into the table as an interval.

What it should say, in section 5 beside the complex row: a complex value is
written component by component, and each component obeys the real rules — so
`CIF(x)` for a value you know to be real writes `… + i * [0, 0]`, which says
"interval arithmetic landed on zero" and not "this number is real". Where the
definition gives you the exactness, say it: return
`numberdb.ComplexInterval(interval, Fraction(0))`, which writes `… + i * 0`.
The same applies to a rational component beside an irrational one.

Evidence: 2026-09-20, T346 read as a draft. 188 of 588 values in the form
`<decimal> + i * [0, 0]`, 300 in the form `<decimal> + i * <decimal>`, 12 as
Gaussian integers `-1 + i * -3`, 50 bare integers and 38 bare rationals — five
spellings in one column. T317 (published, 466 values) writes its purely
imaginary values `0 + i * 3.4641…`, with no brackets anywhere in the table.
`clients/python/numberdb/_write.py:_interval_text` is where the brackets come
from and `numberdb_app/test_interval_spelling.py` is where the distinction is
written down.

## `EllipticCurve(...)` is unreachable from a named-imports generator until one more module is imported

What happened: a check script for T346 did what the skill's generator template
does — `import numberdb.sage as numberdb`, then name the pieces it wants —
and called `EllipticCurve`:

    import numberdb.sage as numberdb
    from sage.schemes.elliptic_curves.constructor import EllipticCurve
    E = EllipticCurve([0, -1, 1, 0, 0])

    ImportError: cannot import name PolynomialSequence_generic

Both spellings fail, the Cremona label `'11a1'` and the list of $a$-invariants,
because the constructor calls `Sequence` on whatever it is given, and
`sage.rings.polynomial.multi_polynomial_sequence` is circular from a cold
start: it imports `plural`, which imports `multi_polynomial_libsingular`,
which imports `sage.libs.singular.function`, which imports
`PolynomialSequence_generic` back out of the module still being loaded.
Importing `multi_polynomial_sequence` directly fails the same way, so the
obvious workaround is not one.

Entering the cycle from the other end fixes it, and one named import is
enough — no `sage.all`:

    import numberdb.sage as numberdb
    import sage.libs.singular.function          # unwedges the cycle
    from sage.schemes.elliptic_curves.constructor import EllipticCurve

after which `EllipticCurve([0, -1, 1, 0, 0])`, `EllipticCurve('11a1')` and
`E.division_polynomial(...)` all work.

This is not particular to elliptic curves: anything that goes through
`Sequence` on a cold `sage -python` will hit it. It is the same family of
trap as the three the skill already names, and it is why one published
generator here builds its curves out of `CremonaDatabase` and PARI instead.

What the skill says now: section 6, "What else the named imports do not bring:
root finding (`sage.numerical.optimize`), `RealBall.str`, and `QQ('1.25')`".

What it should say: add a fourth item — anything reached through Sage's
`Sequence`, `EllipticCurve` most of all, which raises `ImportError: cannot
import name PolynomialSequence_generic` from a cold start; `import
sage.libs.singular.function` before it and the cycle resolves.

Evidence: 2026-09-20, three runs of `agents/sage.sh` on the deployed image
(SageMath 10.x). Cold: both `EllipticCurve([0,-1,1,0,0])` and
`EllipticCurve('11a1')` raise `ImportError: cannot import name
PolynomialSequence_generic`, traceback through `multi_polynomial_sequence.py:173`
→ `plural.pyx` → `multi_polynomial_libsingular.pyx` → `libs/singular/function.pyx:95`.
After `import sage.libs.singular.function`, both return the curve and
`E.division_polynomial(4, two_torsion_multiplicity=0)` returns
`2*x^6 - 4*x^5 + 10*x^3 - 10*x^2 + 4*x - 1`.

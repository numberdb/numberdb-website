# Lessons from the build run of 2026-09-23T05:08:54Z

## Do not pass rational parameter strings to `QQ`

What happened: the generator for T438 enumerated the argument as strings such
as `"1/36"` and read them back with `QQ(str(z_text))`. Under the Sage runner
this failed before any values were computed:

```
AttributeError: module 'sage.rings' has no attribute 'real_mpfr'
```

The same code path is exactly the kind of partial Sage import the skill warns
about for `QQ('1.25')`. It is not limited to decimal strings: a fractional
string can also reach a parser that is not initialised in a narrow Sage
environment.

What the skill says now: it names `QQ('1.25')`, and says to build a rational
from a decimal string by hand.

What it should say: do not rely on `QQ(text)` for parameter strings at all in
a generator that names its imports. Parse the text with Python's
`fractions.Fraction`, then construct `QQ(f.numerator) / QQ(f.denominator)`;
for mpmath, pass the numerator and denominator to `mp.mpf` rather than
round-tripping through Sage's string parser.

Evidence: `agents/sage.sh /tmp/mathieu_dry_run.py ... generate.py` for
T438 failed on `QQ("1/36")`; replacing it with `Fraction("1/36")` followed by
exact `QQ` construction made the dry run compute all 456 entries.

## An empty draft with no entries section can defeat `Generator.publish`

What happened: T438 was created as an empty draft, with prose but no
`Numbers` section. Running `MathieuOddValues().publish()` did not compute or
send entries. It failed in the client's first-second writability check, where
`check_writable()` sends an empty upsert:

```
numberdb._errors.NumberDBError: A value in these entries cannot be read as a number. 'str' object has no attribute 'items'
```

Submitting the actual entries with `numberdb._write.submit_entries(...,
upsert=False)` succeeded, and the attached generator then verified the stored
draft as `<VerifyReport T438: 456/456 matched, 0 differing, 0 missing,
0 extra>`.

What the skill says now: a generator fills a draft with `publish()`, and an
empty draft is the ordinary claim made before the numbers are built.

What it should say: if `publish()` refuses an empty draft during the empty
upsert check, do not recreate the table. Submit the first full entries block
as a replacement, not an upsert, then attach the generator with the same run
id. After that, ordinary `verify(sample=None)` works with the draft's key.
This is a workaround for the empty draft state, not a reason to avoid the
title claim.

Evidence: T438 on 2026-09-23. The failed path was
`Generator.publish()` -> `check_writable()` -> empty upsert. The successful
path was `/tmp/mathieu_fill_entries.py`, which used `submit_entries` with
`upsert=False` and then `attach`, producing revision
`3dc36ab93782dea5db9f1f694a9558a52f2249af2c0577e992222bb3c57157b5`.

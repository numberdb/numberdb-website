## A code span cannot hold a backtick, and graph6 keys contain them

What happened: after the T237 critique, the cospectral comments were rewritten
to name the other graph in backticks, as the proposal
`20260913T221523Z-critique.md` recommends. The graph6 alphabet runs from
`?` to `~` and includes `` ` ``, and prose code is matched by
`` `([^`]+)` `` (`numberdb_app/prose.py`), so a span ends at the first
backtick inside the key. "`` as `F`Gyw`. ``" renders as
`<code class="prose-code">F</code>Gyw`` ` ``, which shows the reader a
one-letter code span followed by a fragment of the key. Six of T237's
comments render that way. T238 names the same kind of keys in plain text,
and 24 of its 119 cospectral comments would break the same way if they were
put in backticks. 81 of the 996 keys contain a backtick.

What the skill says now: nothing about code spans in prose, beyond
`rigour details` accepting backticks. The pending proposal above says to
name graph6 keys "in backticks", which is wrong for those keys.

What it should say: backticks mark code in prose, and a code span ends at the
next backtick, so it cannot contain one. A key that may contain a backtick,
such as a graph6 string, goes in plain text. Otherwise the generator has to
check each key and choose. Look at the rendered preview of a comment that
names such a key.

Evidence: 2026-09-13, T238 critique. `/preview?table=` with an entry comment
"It has the same characteristic polynomial as `` `F`Gyw` ``." returned
`as <code class="prose-code">F</code>Gyw``.` T237's comments on
`F_?~w`, `F?L^?`, `FGC^w`, `FA_~o`, `F@Tl_` and `FA]rw` are stored in that
form.

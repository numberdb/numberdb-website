# Lessons proposed by the T360 critique, 2026-09-20

## A relation written in `Similar tables` is an identity a reader will apply; check it on one stored entry first

What happened: T360, associated Legendre polynomials, glossed its link to the
Jacobi polynomials as "for fixed order, associated Legendre polynomials are
Jacobi polynomials multiplied by $(1-x^2)^{m/2}$". That is a sentence anybody
would write from memory and it is false: the true identity is

    P_l^m(x) = (-1)^m (l+m)! / (2^m l!) * (1-x^2)^(m/2) * P_{l-m}^(m,m)(x)

and the constant is $-3/2$ at $(\ell,m)=(2,1)$ and $-63$ at $(6,3)$. A reader
who applies the sentence as written gets a polynomial off by a factor of
sixty-three and concludes one of the two tables is wrong.

Checking it cost nothing: the Jacobi polynomial $P_n^{(m,m)}$ from its
explicit sum in `Fraction` arithmetic, divided into the stored entry
coefficient by coefficient, over every $0\leq m\leq\ell\leq15$. The ratio was
a single constant in every case, which is what said the *shape* of the gloss
was right and only the constant was missing. No Sage needed.

The same check answers the other half of the question, which is whether the
link lands at all. `Jacobi_polynomials` restricts to $\alpha<\beta$ and so
holds no $P_n^{(m,m)}$ row; the corpus keeps $\alpha=\beta$ in
`Gegenbauer_polynomials`, which the Jacobi table's own comment says.

What the skill says now: `Similar tables` "states the *relation*, in words"
and "that sentence is the valuable part". It says nothing about the sentence
being checkable, and nothing about checking that the table pointed at actually
holds the objects the relation names.

What it should say: a relation in `Similar tables` is a formula a reader will
use, so it is verified like a formula -- evaluate both sides on one stored
entry before writing it, and prefer "a constant multiple of" to a constant you
have not computed. And read the other table's own parameter constraints: a
relation that names rows the target excludes is a pointer to nothing.

Evidence: 2026-09-20, T360 critique. Pure-Python check over the 136 entries
with $0\leq m\leq\ell\leq15$; zero mismatches against the corrected constant,
136 mismatches against a constant of 1.

## A convention note that tells a reader to *correct* a value is a claim about two conventions, and it is checkable in one line

What happened: T360 carried the comment "DLMF writes the Ferrers function
$\mathsf{P}_\ell^m$ without this phase, so a value read from DLMF 14.7 must be
multiplied by $(-1)^m$ before comparison". It is backwards. DLMF 14.7.8 is
$\mathsf{P}_n^m(x)=(-1)^m(1-x^2)^{m/2}\,d^m\mathsf{P}_n/dx^m$: the Ferrers
function *carries* the Condon-Shortley phase and already equals the stored
values. What DLMF writes without the phase is $P_n^m$ (14.7.11,
$(x^2-1)^{m/2}\,d^mP_n/dx^m$) -- the same symbol the table itself uses for the
phased object. A reader who followed the instruction would flip the sign of
every odd-order entry.

The trap is specific and the shape of it is not. A source that holds **two
functions under two typefaces of one letter** -- $\mathsf{P}$ and $P$,
$\boldsymbol{Q}$ and $Q$ -- invites a convention note written from the section
title instead of from the equation. The comment named "DLMF 14.7" and the
table's `Links` entry pointed at 14.3, so nothing on the page could be
followed to the formula that would have settled it.

The check is one line of Sage and it was never run: `gen_legendre_P(2,1,x)`
returns `-3*sqrt(-x^2+1)*x`, which is the stored `-3*x*y` -- so Sage's
convention, DLMF's Ferrers function and the table all agree and no correction
is needed by anybody.

What the skill says now: "Which normalisation, branch, and indexing", with
`elliptic_k`'s parameter-versus-modulus as the example, and "Verify a claim
before writing it into a table, including one somebody suggested". Neither
covers a note whose whole content is *how another source differs*.

What it should say: a comment that tells a reader to apply a correction to a
value from a named source is a claim about that source, and it is checked the
same way a value is -- compute one entry both ways and see which needs the
correction. Cite the equation, not the section: "DLMF 14.7.8", not "DLMF 14.7",
and make the `Links` entry point at the section the sentence names.

Evidence: 2026-09-20, T360 critique. DLMF 14.7.1 ($\mathsf{P}_n^0=P_n$),
14.7.8 (with the phase), 14.7.11 (without it), all fetched directly.
`agents/sage.sh`: `gen_legendre_P(1,1,x) = -sqrt(-x^2+1)`,
`gen_legendre_P(2,1,x) = -3*sqrt(-x^2+1)*x`, `gen_legendre_P(4,-1,x) =
1/8*(7*x^3-3*x)*sqrt(-x^2+1)`, against stored `-y`, `-3*x*y`,
`7/8*x^3*y - 3/8*x*y`.

## A table whose values need a second variable should say so in the header, not only in a comment

What happened: T360 stores $P_\ell^m$ as an exact polynomial in $x$ and $y$
with $y=\sqrt{1-x^2}$, which is the right decision -- for odd $m$ the object
is not a polynomial in $x$ at all, and the corpus's polynomial parser takes
"polynomials over Q in arbitrary variables". But `number-header` reads
$P_\ell^m(x)$, so the first screen shows a column headed with one variable
over rows containing two, and what $y$ means is four sections further down,
under `Comments`, after `Definition`, `Parameters` and `Formulas`.

What the skill says now: "A value's display is a label, not a formula", and
the `number-header` rule, which is about a header claiming something the table
does not hold (T174's $|\lambda_n|$). Both are about *removing* things from a
label.

What it should say: the same rule cuts the other way when the stored
representation introduces a symbol. A header that names a variable the values
do not use, or omits one they do, is the same fault; where the entries carry
an auxiliary variable, the header is where it is defined, because Comments
renders below the values a reader came for. `$P_\ell^m(x)$, with
$y=(1-x^2)^{1/2}$` renders intact and is still a label.

Evidence: 2026-09-20, T360 critique; rendered through `/preview?table=` with
the longer header, 200, header intact beside rows reading `-3*x*y`.

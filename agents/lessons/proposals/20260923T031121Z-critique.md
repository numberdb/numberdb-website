## A stored value read back as a ball is a point, not the interval it denotes

What happened: the T426 critique checked the stored $\theta_4(0,q)$ against its
own arb recomputation the obvious way,

    stored = '0.80019999800000019999999980000000000199999999999980000...'   # 100 digits
    computed.overlaps(RealBallField(prec)(stored))

and got `False` at every $q$ it tried, on values whose digits are in fact
identical. `RealBallField(prec)(<decimal string>)` parses the string as a
*number* and gives a ball of radius $2\times10^{-125}$ around it -- the
rounding error of the parse, nothing else. The two balls then miss each other
by the first digit beyond the hundred that were stored, which at $q=1/10$ is
$2.5\times10^{-121}$: larger than either radius and a hundred orders of
magnitude inside what the stored value actually claims. Adding the last place
back makes the comparison say what it was asked,

    ulp = RealBallField(prec)(QQ(1) / QQ(10)**100)      # the digits' last place
    computed.overlaps(RealBallField(prec)(stored).add_error(ulp))   # True

What the skill says now: it says what a stored real *means* -- "3.14 the
interval [3.13, 3.15] -- the last digit may be off by one" -- and it says
that convention "is the whole reason a hundred digits means something". It
says nothing about reading one back. Everything in section 10 about checking
work ("if your recomputation disagrees with a stored value, suspect your
recomputation first", "an enclosure that contains everything agrees with
everything") is about the other direction, where a comparison wrongly succeeds.

What it should say: a stored decimal is an interval, so compare against the
interval. Reading it into a ball or an interval field gives a point with the
parser's rounding error for a radius, and `overlaps` against that reports a
disagreement whenever the recomputation is *more* precise than the table --
which it usually is, since a table is stored at 100 digits and computed with a
guard above it. Widen the stored value by one unit in its last place before
comparing, `RBF(stored).add_error(RBF(QQ(1)/QQ(10)**digits))`, or compare the
decimal expansions as strings. `numberdb`'s own `verify()` already does the
right thing; this bites the hand-written check beside it, which is the one
somebody writes when a table looks wrong.

Evidence: 2026-09-23, T426 critique. `/tmp/t426_digits.py` printed the
computed midpoint and the stored string side by side at $q=1/10$, $1/2$ and
$9/10$ -- all 100 digits equal, `overlaps` `False` all three times, computed
radius $1.2\times10^{-123}$ against stored radius $2.2\times10^{-125}$.
`/tmp/t426_ulp.py`: `as a point, overlaps: False` / `with one ulp, overlaps:
True`.

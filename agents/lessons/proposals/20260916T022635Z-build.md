## A full-document edit of an empty draft is refused unless it carries entries
What happened: T256 was claimed as an empty draft with `POST /api/tables` and
`X-Draft: yes`, which is allowed. After the dry run found that the intended
range should be inclusive at the boundary, a full-document edit to
`POST /api/table/T256` was sent with the corrected prose and no `Numbers`
section. The API refused it with "A table needs at least one entry", even
though the table was still an unpublished draft. The same full-document edit
was accepted after the generator filled the draft and the request preserved the
stored `Numbers`.

What the skill says now: create the draft before computing anything, with
title first and prose if you have it, then fill it once. It does not say that
an empty draft cannot be replaced by a later full-document edit while it is
still empty.

What it should say: get the prose as close as possible when creating the empty
draft. If a correction to the prose is needed before any entries exist, either
fill the draft first and then replace the full document while preserving
`Numbers`, or use a route that edits individual metadata sections rather than
`POST /api/table/TID` with an empty document.

Evidence: 2026-09-16, T256. The create request returned 201 for an empty draft;
the later full-document edit returned HTTP 400 with "A table needs at least one
entry"; after the entries revision, the corrected full document was accepted
and `verify()` still reported 599/599 matched.

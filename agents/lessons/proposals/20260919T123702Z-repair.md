## `Generator.publish()` will not restate a comment when the number is unchanged

What happened: repairing T293 extended the table from 32 to 823 regulators.
The first publish used `generator.publish(overwrite=False)`, which correctly
added only the 791 missing rows. A rendered-page readback then showed the new
entry comments had copied ecnf-data conductor ideals like `$(-3*w+16)$`, while
the existing comments used `$(-3w+16)$`. Fixing `_entry_comment()` and rerunning
`publish(overwrite=True)` would not have restated those comments: when the
stored number and produced number are the same, the client records the entry as
unchanged and sends no upsert for it. The repair needed an explicit
`submit_entries(..., upsert=True)` pass carrying the same numbers and corrected
comments.

What the skill says now: it says `publish(overwrite=False)` adds what is
missing and leaves the rest alone, and it says `Programs` and `generate.py`
answer different questions. It does not say that entry comments are skipped
when a generator produces the same number already stored.

What it should say: `Generator.publish()` compares the number, not the whole
entry. If the repair changes only comments, displays or other per-entry prose
for rows whose numbers are already stored, send those entries explicitly with
the entries API or `numberdb._write.submit_entries(..., upsert=True)`. Do not
expect `overwrite=True` to restate same-number rows.

Evidence: T293 repair, 2026-09-19. After adding 791 entries, the audit endpoint
showed no findings but the rendered page showed new comments with `*w`. After
fixing `_entry_comment()`, a custom upsert run restated 823 entries; readback
reported `star_w: [] count 0`, generator verify reported `<VerifyReport T293:
823/823 matched, 0 differing, 0 missing, 0 extra>`, and the audit endpoint
returned `{"findings": [], "clean": true}`.
